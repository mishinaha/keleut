# KIR 仕様

バージョン 1.0。

本書は、Keleut の中間言語 KIR(Keleut Intermediate Representation)を定める。
1.0 は、仕様を確定したバージョンである。
1.0 より後のマイナーバージョンは、1.0 で定めたセクション、命令、エンコーディングの意味を変えない。
1.0 は、バイナリのスキップできるセクション(13 節)の内容の形式を定めない。
バージョンの扱いと、バージョンを変えずに行う本文の改訂は 14 節に書く。

本書が「言語仕様」と書くときは `doc/LangSpec.md` を指し、その節を「§13.6」のように書く。
本書の節は「本書 9 節」のように書く。

## 1. 適用範囲

KIR は、型検査と精緻化(elaboration)を済ませた Keleut のプログラムを表す中間言語である。
ファイル形式は 2 つある。

| 拡張子 | 形式 |
| --- | --- |
| `.kir` | バイナリ(本書 13 節) |
| `.kirt` | 正準なテキスト(本書 12 節)。バイナリと 1 対 1 に対応し、相互に変換できる(ラウンドトリップ) |

「正準」(canonical)は、同じプログラムの書き方が一意に決まることを指す。

**ライタ**(writer):Keleut のソースから KIR を作る処理系。
Diktor(`diktor --emit-ir`)と RustKeleut のフロントエンド(`keleut emit-kir`)がこれに該当する。
**リーダ**(reader):KIR を読み込み、検証し、実行する処理系。
Diktor(`diktor --run-ir`)と RustKeleut(`keleut run`)がこれに該当する。

KIR のプログラムの意味は、言語仕様が、そのプログラムを書き出した元の Keleut のプログラムに定める意味である。
言語仕様が処理系に任せている点のうち、実行の結果に影響するもの(論理的な深さの上限と、1 回の確保の要素数の上限)は、本書 11 節が値と数え方を定める。
深さの上限を検査するリーダは、どれも同じ深さを数え、同じ位置で `depth_limit` の実行時エラーにする(本書 11.2 節〜11.5 節)。
`N_alloc_max` の検査は RustKeleut のすべてのバックエンドが同じ値で行い、Diktor(`--run-ir`)は行わない(本書 11.6 節)。

本書に従うリーダは、同じ KIR のプログラムに対して同じ出力を書き、同じ終了コードで終了する。
ただし、次の場合はこの保証の対象外である。

- 実行時エラーのメッセージと `cancel` 節の抑制の記録の中で、レコードの中の、ラベルの異なるフィールドを書く順序(付録 B)。
  違うのは診断のメッセージだけで、終了コードは同じである。
- `sin`、`cos`、`exp`、`log` の結果の 1 ulp の違い(正しい値に最も近い 2 つの `Float64` のどちらを返すか)。
  言語仕様 §17 が処理系に任せている。
- 1 回の確保の要素数が `N_alloc_max` を超える場合。
  RustKeleut のバックエンドはメモリ不足(終了コード 3)で終了し、Diktor(`--run-ir`)は検査しないので確保が成功することがある(本書 11.6 節)。
- `N_alloc_max` の検査によらないメモリ不足。
  メモリが尽きる時点はリーダごとに違い、メモリが尽きたリーダはメモリ不足(終了コード 3)で終了する。
  Diktor での確保も、この項目に該当する(本書 11.1 節、11.6 節)。
  Diktor は、ヒープを少しずつ使い尽くすと、minor GC の中で確保に失敗し、終了コード 134 で終了することがある。
  RustKeleut のバックエンドと OS が原因で終了コードが 3 にならない場合を、次の 3 項目に挙げる。
- RustKeleut の WasmGC バックエンドが V8 のヒープを使い尽くす場合と、仮想メモリを制限しているとき(`ulimit -v`)に `keleut run` が Node を起動できないか、Node のスタックやスレッドを確保できない場合。
  どちらも終了コードは 3 でなく 70 になる(本書 11.1 節)。
- RustKeleut のインタプリタと LLVM バックエンドで、LLVM の内部の確保が失敗する場合と、グローバルアロケータの予備領域を使い切った後に Rust の確保が失敗する場合。
  リーダは SIGABRT(終了コード 134)で異常終了する。
  ただし、`.kir` の読み込み、検証、LIR への変換(lowering。RustKeleut が KIR を内部表現の LIR に変える処理)の間にメモリを確保できなくなった場合は、本書 13.9 節が定める例外に従い、終了コード 65 で終了する。
  134 で異常終了することがあるのは、実行中の確保、引数の解析やファイルの読み込みのようなメインスレッドの確保、`keleut repl` の変換スレッドの確保、LLVM の内部の確保が失敗したときである。
- OS が物理メモリ不足でプロセスを強制終了する場合。
  リーダは SIGKILL(終了コード 137)で終了する。
  どのリーダでも起こることがある。
- Diktor(`--run-ir`、`--via-ir`)が、深さが上限 `L` に達する前に OCaml のスタックを使い尽くす場合。
  Diktor は非末尾呼び出し 4,096 段ごとに新しい OCaml のファイバーを使うので、4,096 段分のスタックがファイバーごとのスタックの上限を超えると起こる。
  `OCAMLRUNPARAM` の `l` で上限を下げたときや、各段の中の式の入れ子が極端に深いプログラムがこれに該当し、Diktor はスタックオーバーフローの実行時エラー(終了コード 3)で終了する(本書 11.5 節)。
- Diktor で、生きている継続の長い連鎖を OCaml 5 の GC がたどる間に、システムのスタックを使い尽くす場合。
  GC は継続の連鎖を C のスタックの上で再帰的にたどるので、Diktor は構文木の評価器(構文木を直接たどって評価する。`--run-ir` も `--via-ir` も付けない実行)でも KIR の評価器でも SIGSEGV(終了コード 139)で異常終了することがある。
  異常終了するかどうかは GC のタイミングとシステムのスタックサイズで決まり、`ulimit -s` でスタックを大きくすると起こりにくくなる。
  これはホストの実行環境の制限であり、深さの規則の違いではない(本書 11.5 節)。

ノードの深さが `N_nest` を超える Keleut のプログラムは、KIR を持たない(本書 13.9 節)。
ライタはそのプログラムの KIR を書かずに、`処理系の限度` の行を書いて終了する。
同じプログラムをソースから直接実行する処理系(Diktor の構文木の評価器)は、そのまま実行することがある。
対話的な実行(REPL)の入力も同じで、KIR を通して実行する処理系は、ノードの深さが `N_nest` を超える入力を、処理系の限度として受理しない。

KIR を作る段階で、ライタは次の処理を済ませる。

- 構文の脱糖(糖衣構文の展開。`if`、タプル、`with`、末尾ブロック)。
- 名前の解決(グローバルはシンボルで、ローカルはスロットの番号で表す)。
- クロージャ変換(関数ごとにキャプチャの並びを決める。辞書の引数もキャプチャする)。
- 辞書渡しの明示(証拠の平坦化、インスタンスの対象の型の解決、メソッドの辞書の位置)。
  証拠(evidence)は、どのインスタンスの辞書を使うかを表す項である。
- 数値リテラルの確定と module の平坦化。
- 末尾の印と操作節の分類(本書 5.3 節、9.2 節)。
- `run` の消去と、二項演算子と前置の `-` のメソッド呼び出しへの書き換え。

KIR は木であり、子は符号化に現れる順に評価する(本書 5 節)。
中間の結果をすべて変数に束縛する形(ANF)にはしない。

RustKeleut の内部表現(LIR とバイトコード)は本書の対象ではない。
それらはファイルに書かず、互換性も保証しない。

リーダの検証(本書 13.8 節)は、型の健全性を保証しない。
型の健全性は、型検査を済ませたライタが保証する。

## 2. プログラムと単位

### 2.1 プログラム

`.kir` の 1 ファイルは、自己完結したプログラムである。
組み込みとプレリュードを含むすべての単位(コンパイル単位)を、次の順に並べて持つ。

1. 組み込みの単位 `builtin`。
2. プレリュードの単位 `prelude`。
3. 起点(コマンド行で渡したファイル)が import する単位を、初期化の順(§15.4。import を書いた順に深さ優先でたどった帰りがけ順)に並べたもの。
4. 起点の単位 `main`。

**単位**:プログラムを構成するコンパイル単位で、キー、元のファイルのパスの並び、初期化手順(本書 10 節)の並びを持つ。
`builtin` の単位は初期化手順を持たない。
`--no-prelude` を付けて実行したライタも、初期化手順のない `prelude` の単位を書く。

単位ごとの `.kir` と、そのリンク(分割コンパイル)は 1.0 では定めない。

### 2.2 単位のキー

単位のキーは次の規則で決める。
キーは、処理系のプロセスや作業ディレクトリによらず、コマンド行と import の文で決まる。
ただし、下の「起点のディレクトリ」の規則でパスの表記から相対パスを決められないときだけは、ファイルシステムを参照する。

| 単位 | キー |
| --- | --- |
| 組み込み | `builtin` |
| プレリュード | `prelude` |
| コマンド行の起点(複数のファイルを連結した 1 単位) | `main` |
| import した単位 | 下の規則で決めた、`.kel` で終わるパス |

import した単位のキーは、その単位に初めて到達した import の文から決める。
初めて到達した文とは、起点のファイルを書いた順にたどり、各ファイルの import を書いた順に深さ優先でたどったとき、最初に現れたその単位への import の文である。

- **正規化**:パスを `/` で要素に分け、空の要素と `.` を取り除き、`..` を直前の要素とともに取り除く。
  次の 3 種類の `..` は取り除かずに残す。
  1 つ目は、直前の要素がない `..` である。
  2 つ目は、直前の要素が `..` である `..` である。
  3 つ目は、直前の要素が先頭の要素で、その要素が `@` と 1 個以上の数字だけからなるときの `..` である。
  `@` と数字だけからなる要素は、下の「検索パスの import」が付ける接頭辞である。
  先頭の `/` も空の要素として取り除くので、正規化したパスは `/` で始まらない。
- **基準のディレクトリ** `B`:コマンド行の最初のファイルの `dirname`(POSIX の `dirname` で、`/` を含まない名前では `.`)。
- **ディレクトリ** `dir(K)`:キー `K` の最後の `/` より前の部分で、`/` を含まないキーでは空文字列である。
- **起点のディレクトリ**:起点の j 番目のファイルの `dirname` を `D` とする。
  `B` と `D` を正規化した要素の並びから、先頭の共通する要素を取り除く。
  `B` の残りの要素の数だけ `..` を並べ、`D` の残りの要素を続けて `/` でつないだパスを、そのファイルの `dir(K)` とする(`B` と `D` が同じなら空文字列)。
  `B` と `D` の一方だけが `/` で始まるときと、`B` の残りの要素に `..` があるときは、パスの表記から相対パスを決められない。
  そのときは、`B` と `D` の `realpath` に同じ規則を適用したパスを使う。
- **相対パスの import**(`./p` と `../p`):import を書いたファイルのキーを `K` とする。
  `dir(K)`、import に書いたパス、`.kel` を連結し(`dir(K)` が空でなければ間に `/` を置く)、正規化したパスをキーとする。
- **検索パスの import**:`--import-path` の i 番目(1 始まり)のディレクトリで見つけたファイルのキーは、`@i/`、import に書いたパス、`.kel` を連結したものである。
  複数の i で同じファイルが見つかったときは、最小の i を使う。

キーは `.kel` で終わるので、`builtin`、`prelude`、`main` と重ならない。
例を示す。
`diktor a/m.kel` が `./lib/x` を import し、`a/lib/x.kel` が `../y` を import すると、キーは `lib/x.kel` と `y.kel` になる。
`--import-path vendor` の下の `util` は `@1/util.kel` になる。
`diktor a/m.kel c.kel` で、`a/m.kel` と `c.kel` がどちらも `./w` を import すると、キーは `w.kel`(ファイル `a/w.kel`)と `../w.kel`(ファイル `w.kel`)になる。
起点を絶対パスで書いても、キーは変わらない。

この規則はパスの表記だけでキーを決めるので、異なる 2 つのファイルが同じキーになることがある。
たとえば、シンボリックリンクであるディレクトリの下の `..` は、表記の上で要素を取り除いた結果と、OS が解決した結果とで、別のディレクトリを指す。
ライタは、異なるファイル(`realpath` が違うファイル)の単位が同じキーになったら、KIR を書かずに使い方のエラー(終了コード 64)で終了する。

起点のディレクトリの規則は、コマンド行に書いたディレクトリの名前をキーに入れる。
そのため、UTF-8 でない名前のディレクトリに置いた 2 つ目以降の起点のファイルから import すると、キーが UTF-8 でなくなる。
UTF-8 でない名前を持つプログラムは KIR を持たない(本書 13.4 節)。

### 2.3 元のファイルのパス

単位の `paths` は、診断に使うパスの並びであり、実行時の意味には使わない。

| 単位 | `paths` |
| --- | --- |
| `builtin` | 空 |
| `prelude` | 埋め込みのプレリュードなら `<prelude>`、`--prelude PATH` なら `PATH`、`--no-prelude` なら空 |
| `main` | コマンド行に書いたファイルのパスの並び(書いた順) |
| import した単位 | 下の規則で決めた表示用のパス 1 個 |

import した単位の表示用のパスは、Diktor が診断の位置に書くファイル名でもある。
次の手順で決める。
ここでの正規化は、本書 2.2 節の正規化と次の 2 点で違う。
先頭の `/` を残すことと、`@` で始まる要素を特別に扱わないことである。

1. **相対パスの import**:import を書いたファイルの表示用のパスの `dirname` を `P` とする。
   起点のファイルの表示用のパスは、コマンド行に書いたパスそのものである。
   `P`、`/`、import に書いたパス、`.kel` を連結して正規化したパスを `S` とする。
2. **検索パスの import**:そのファイルを見つけた `--import-path` のディレクトリのうち、番号が最小のもののパス(書いたまま。空なら `.`)を `P` とする。
   `P`、`/`、import に書いたパス、`.kel` を連結して正規化したパスを `S` とする。
3. **実際に開くパス**:相対パスの import では、import を書いたファイルの実際に開くパスの `dirname` と、import に書いたパスに `.kel` を付けたものを、`/` でつないだパスである。
   起点のファイルの実際に開くパスは、コマンド行に書いたパスである。
   検索パスの import では、ディレクトリのパスと、import に書いたパスに `.kel` を付けたものを、`/` でつないだパスである(ディレクトリが空ならつながない)。
4. `S` の `realpath` が実際に開くパスの `realpath` と同じなら、`S` を表示用のパスにする。
   違うとき(シンボリックリンクの下の `..`)と `S` を解決できないときは、実際に開くパスから空の要素と `.` の要素だけを取り除いたパス(先頭の `/` は残す)を表示用のパスにする。

表示用のパスは作業ディレクトリによって変わる。
テキストを比較するときは、同じ作業ディレクトリと同じ引数で書いたもの同士を比較する。

## 3. 名前

### 3.1 シンボル

Diktor のオブジェクトの番号やハンドラの起動(activation)の番号のように、1 つのプロセスの中でしか通用しない番号は、KIR に書かない。
KIR は表の項目をシンボルで指定する。

**シンボル**:`単位の鍵/名前` の形式の文字列。
`単位の鍵` の部分は単位のキー(本書 2.2 節)である。
名前の部分は `/` を含まない。
そのため、シンボルが属する単位のキーは、シンボルの最後の `/` より前の部分である。

**修飾名**:module の平坦化の後の名前(`M.f`、`M.N.T` など)。
Diktor が起点でない単位の宣言に付ける接頭辞 `%N.` は、修飾名に含めない。
Keleut の識別子は `$`、`#`、`:`、`[`、`]`、`/` を含まないので、本書 3.2 節〜3.4 節が名前に付ける接尾辞と目印(`#n`、`instance:`、`$init<k>`、`$n`、`$h<n>`)は、ユーザが書いた名前と重ならない。

シンボルはリンクと診断にだけ使い、実行時の意味には使わない(§18.1)。
シンボルの文字列は表ごとに一意である。
グローバルのシンボルと関数のシンボルは別の表に属するので、同じ文字列でもよい(本書 3.4 節)。

### 3.2 グローバル

グローバルのシンボルは `単位の鍵/修飾名` である。
同じ単位で同じ修飾名を再束縛したときは、2 つ目に `#1`、3 つ目に `#2` を付ける(`main/x`、`main/x#1`、`main/x#2`)。
再束縛した名前は別のグローバルである(§6.1)。
数えるのは、単位の初期化手順(本書 10 節)が定義するグローバルである。
初期化手順の順に数え、同じ初期化手順が複数のグローバルを定義するときは、その初期化手順に書いた並びの順に数える。
`extern` の宣言も数える。

組み込みの値のシンボルは `builtin/Ref.new` などである(付録 A)。

### 3.3 型、エフェクト、クラス、インスタンス

| 対象 | シンボルか名前 |
| --- | --- |
| 名目的な型 | `単位の鍵/修飾名`。組み込みの型は `builtin/Int32` など(付録 A) |
| コンストラクタ | 宣言に書いた名前(`Some`)。module の中の型のコンストラクタにも module の名前を付けない(`main/M.Tree` の `Leaf`)。型のシンボルと合わせて指定する |
| エフェクト | `単位の鍵/修飾名` |
| 操作 | エフェクトの中の修飾しない名前(`write`)。エフェクトのシンボルと合わせて指定する |
| クラス | `単位の鍵/修飾名`。組み込みのクラスは `builtin/Eq` など(付録 A) |
| メソッド | クラスの中の修飾しない名前(`eq`)。クラスのシンボルと合わせて指定する |
| インスタンス | `単位の鍵/instance:C[H]`。`C` はクラスのシンボルの名前の部分、`H` はインスタンスの対象の型の先頭にある型構成子のシンボルの名前の部分である |

インスタンスのシンボルの単位は、インスタンスを宣言した単位である。
同じ単位で同じ `C[H]` の表記が 2 回現れたとき(別の単位の同名の型に対するインスタンス)は、グローバルと同じく 2 つ目から `#1`、`#2` を付ける。
例は `prelude/instance:Show[List]` である。

### 3.4 関数

**ルート関数**:トップレベルの実体ごとに 1 個ある関数。
トップレベルの実体とは、次の表の左の列に挙げる 4 種類である。
ルート関数は、次の表のシンボルを持つ。

| 実体 | ルート関数のシンボル |
| --- | --- |
| 種類が `fn` か `dictabs` のグローバル `g` | `g` と同じ文字列 |
| `def_value g` の初期化式 | `g` と同じ文字列 |
| `def_pattern` の初期化式と `run_exp` の式 | `単位の鍵/$init<k>`。`k` は、その初期化手順の単位の中での番号(0 始まり)。初期化手順を作らない宣言(型の宣言、辞書を受け取る式文など)は数えない |
| インスタンス `I` のメソッド `m` の実装 | `I` のシンボルに `.m` を付けたもの(`prelude/instance:Show[List].show`) |

**持ち上げた関数**:ルート関数の本体の中で作る関数(ラムダリフティングで取り出した関数)。
持ち上げた関数を作る式は、`closure`、`dictabs`、`handle` の 3 種である。
この 3 種の式を関数の**生成箇所**と呼ぶ。

生成箇所の番号は次のとおりに振る。
ルート関数を、正準なテキスト(本書 12 節)に現れる順にたどる。
生成箇所に達したら、その生成箇所に次の番号(0 始まり)を振り、続けてその生成箇所が作る関数の内容をたどってから、生成箇所の後ろへ進む。
`handle` の生成箇所では、本体、操作節(書いた順)、`return` 節、`cancel` 節の関数をこの順にたどる。
関数の内容は、操作節のパターンとガード、本体の順にたどる。
番号は、ルート関数ごとに 0 から振り直す。
入れ子の生成箇所にも、ルート関数の中の通し番号を振る。

持ち上げた関数のシンボルは、ルート関数のシンボル `R` と生成箇所の番号 `n` から作る。

| 生成箇所 | 関数のシンボル |
| --- | --- |
| `closure`、`dictabs` | `R$n` |
| `handle` の本体 | `R$h<n>.body` |
| `handle` の操作 `op` の操作節 | `R$h<n>.op.<op>`。同じ操作の 2 つ目の節から `#1`、`#2` を付ける |
| `handle` の `return` 節 | `R$h<n>.return` |
| `handle` の `cancel` 節 | `R$h<n>.cancel` |

たとえば、`main/f` の本体の最初の無名関数の中にハンドラ式があれば、無名関数は `main/f$0`、ハンドラの本体は `main/f$h1.body` である。
同じ操作 `ask` に 2 つの節を書いたハンドラの節は、`$h1.op.ask` と `$h1.op.ask#1` である。

### 3.5 修飾しない名前とローカル

レコードとヴァリアントのラベル、コンストラクタ、操作、メソッドの名前は、シンボルではなく修飾しない名前で書く。
バイナリは、ラベルを文字列表の添字で表し、コンストラクタ、操作、メソッドを、それを持つ型、エフェクト、クラスの中の位置で表す(本書 13.4 節、13.6 節)。
コンストラクタ、操作、メソッドの名前は、types、effects、classes のセクションにだけ文字列として現れる。
ローカルは、関数の中のスロットの番号で表す(本書 6.4 節)。

### 3.6 決定性

書き出しは決定的でなければならない。
ライタは、同じ入力(同じコマンド行、同じファイルの内容)からは、プロセスが違っても同じバイト列を出力する。
表の順序(本書 12.4 節)はどれも宣言の順か本書が定める固定の順であり、ハッシュ表の走査の順を使ってはならない。

## 4. Rep

**Rep**:値の実行時の表現の種類。
`bool`、`i32`、`i64`、`f64`、`str`、`any` の 6 種がある。

型 `τ` の Rep `rep(τ)` は、`τ` の束縛の連鎖をたどった結果が引数のない型構成子 `Boolean`、`Int32`、`Int64`、`Float64`、`String` ならそれぞれ `bool`、`i32`、`i64`、`f64`、`str` であり、それ以外(型変数、関数、レコードを含む)は `any` である。

Rep は次の位置に付ける。

| 位置 | Rep |
| --- | --- |
| 引数のスロット | 仮引数のパターンのノードが持つ型の Rep |
| ローカルのスロット | そのスロットを束縛する変数パターンのノードが持つ型の Rep。`let` の名前が変数のときは、束縛の型の Rep。`closure` と `dictabs` を束縛するスロットは `any` |
| キャプチャ | キャプチャした元の変数の Rep。辞書の引数をキャプチャしたものは `any` |
| 関数の結果 | 本書 6.2 節 |
| 種類が `value` のグローバル | 束縛する変数パターンのノードが持つ型の Rep。`let` の名前が変数のときは、束縛の型の Rep |

Rep は検証と最適化のためのものであり、プログラムの意味を変えない。
リーダは、関数の境界でどの Rep の値をどう渡すかを、自分で決めてよい。
末尾の印(本書 5.3 節)は Rep によらない。

**`yield` の印**:関数と `call` に付ける 1 ビット。
`noyield` は、継続のキャプチャがその関数やその呼び出しの外へ及ばないことを表す。
`yield` と `noyield` は次の規則で決め、ライタはこの規則のとおりに書く。

- 型 `τ` が `noyield` であるとは、`τ` の束縛の連鎖をたどった結果が関数の型で、そのエフェクト行が閉じていて、行のラベルがすべてプレリュードの `Console`、組み込みの `Heap`、組み込みの `Blocking` のどれかであることをいう。
- 種類が `lambda` の関数は、その無名関数か関数定義の型が `noyield` なら `noyield`、それ以外は `yield` である。
- それ以外の種類の関数は `yield` である。
- `call` は、呼び出し先の式の型が `noyield` なら `noyield`、それ以外は `yield` である。

この印は最適化にだけ影響する。

完全な型は、スキップできるセクション types-debug(本書 13.2 節)にテキストで置く予定である。
1.0 は、その内容の形式を定めない。
リーダの検証は、完全な型を使わない。

## 5. 式と評価順序

### 5.1 式

式の子は、正準なテキスト(本書 12 節)に現れる順に評価する。
レコードの拡張と更新のように評価の順が構文の順と違う式は、テキストに子を評価の順に書く。
次の表の「テキスト」の列は本書 12.5 節の文法の形式で、`e` は式、`d` は辞書の式、`p` はパターン、`N` は非負の整数を表す。
`"シンボル"` はシンボルを、`"表記"` はリテラルのソース上の表記を書く位置である。

| 式 | テキスト | 評価の順と意味 |
| --- | --- | --- |
| 定数 | `(lit bool true)`、`(lit i32 N)`、`(lit i64 N)`、`(lit f64 0xHHHHHHHHHHHHHHHH)`、`(lit str "…")` | 定数。`f64` は IEEE 754 のビット列である |
| 範囲外のリテラル | `(lit_error lit_range "表記")` | 評価したら実行時エラーになる(本書 10.4 節) |
| ローカル | `(local N)` | スロット `N` を読む |
| キャプチャ | `(env N)` | `N` 番目のキャプチャを読む |
| グローバル | `(global "シンボル")` | グローバルを読む。初期化の前なら実行時エラーになる(本書 10.3 節) |
| 構築 | `(construct "型" C (field N e)…)` | `e` を書いた順に評価し、それぞれをフィールドの位置 `N` に格納する。項目はソースに書いた順に並べる |
| ヴァリアント | `(variant L e)` | `e` を評価し、ラベル `L` を付ける。ペイロードのないヴァリアントは `e` が `(rec_empty)` である |
| 呼び出し | `(call tail\|ntail yield\|noyield f a…)` | `f` を先に、次に引数を左から評価して呼ぶ(§5.1) |
| メソッドの値 | `(method "クラス" m d o…)` | `d` と `o` を評価し、メソッドの値を作る(本書 5.4 節) |
| 演算子の呼び出し | `(opcall "クラス" m d a…)` | `d`、引数の順に評価し、メソッドを選んで呼ぶ。末尾呼び出しにならない |
| 否定 | `(not e)` | |
| 論理積、論理和 | `(and e1 e2)`、`(or e1 e2)` | 短絡する |
| クロージャ | `(closure "関数" c…)` | キャプチャ `c` を左から読み、関数と対にする |
| 辞書の抽象 | `(dictabs "関数" c…)` | キャプチャを左から読み、種類 `dictabs` の関数と対にする。本体は評価しない |
| 辞書の適用 | `(dictapp e d…)` | `e` を評価し、次に `d` を左から評価し、`e` の値に辞書を渡す(本書 7.5 節) |
| 束縛 | `(let N e1 e2)` | `e1` の値をスロット `N` に置いて `e2` を評価する |
| パターンの束縛 | `(letpat p e1 e2)` | `e1` の値を `p` と照合する。一致しなければ実行時エラーになる |
| 再帰の束縛 | `(letrec (rec N e)… e0)` | 各 `e`(`closure` か `dictabs`)の値をすべて作ってスロット `N` に置いてから、キャプチャを埋める。そのためキャプチャは同じ `letrec` のどのスロットも読める。その後で `e0` を評価する |
| 列 | `(seq e1 … en)` | 左から評価し、最後の値を返す。`n` は 2 以上である |
| 照合 | `(match e (clause p e1)…)`、ガード付きは `(clause p (guard g) e1)` | `e` を 1 回評価し、節を上から試す(本書 8 節) |
| 空のレコード | `(rec_empty)` | Unit でもある |
| レコードの拡張 | `(rec_extend L v r)` | `v` を先に、`r` を後に評価し、`r` の最も外側にラベル `L` のフィールドを追加する |
| 選択 | `(rec_select L e)` | 最も外側の `L` のフィールドを読む |
| 除去 | `(rec_restrict L e)` | 最も外側の `L` のフィールドを 1 つ取り除く |
| 更新 | `(rec_update L r v)` | `r` を先に、`v` を後に評価し、最も外側の `L` のフィールドを置き換える。フィールドの位置は変えない |
| `perform` | `(perform "エフェクト" op a…)` | 引数を左から評価し、最も内側のハンドラへ送る(本書 9 節) |
| ハンドラ式 | `(handle tail\|ntail "エフェクト" (body "関数" c…) (op op N\|T\|G "関数" c…)… [(return "関数" c…)] [(cancel "関数" c…)])` | 各部分のキャプチャを書いた順に読んでから、本体の関数を呼ぶ(本書 9 節) |
| `resume` | `(resume tail\|ntail e)` | `e` を評価してから、継続が再開済みかを調べて再開する(本書 9.5 節) |
| 穴 | `(hole)` | `???`。評価したら実行時エラーになる |

ラベル `L`、コンストラクタ `C`、メソッド `m`、操作 `op` は修飾しない名前である(本書 12.2 節)。
`!=` は `(not (opcall "builtin/Eq" eq d l r))` に変換する。

### 5.2 辞書の式

辞書の式は次の 6 種である(本書 7 節)。
辞書の式の評価はエフェクトを起こさず、実行時エラーにもならない。

| 式 | テキスト | 意味 |
| --- | --- | --- |
| インスタンス | `(dinst "インスタンス" d…)` | ユーザが宣言したインスタンスに、前提の辞書を渡したもの |
| 辞書の引数 | `(dparam N)` | 関数の `N` 番目の辞書の引数 |
| キャプチャ | `(env N)` | キャプチャした辞書 |
| レコード | `(drecord (field L d)…)` | 閉じたレコード型の構造的な `Eq` の辞書 |
| ヴァリアント | `(dvariant (field L d)…)` | 閉じたヴァリアント型の構造的な `Eq` の辞書 |
| 組み込み | `(dbuiltin "クラス" "型")` | 組み込みのインスタンス(付録 A) |

### 5.3 末尾の印

`call`、`handle`、`resume` は、`tail` か `ntail` の印を必ず持つ。
印は、本節の規則で計算した末尾位置にその式があるとき `tail` で、それ以外は `ntail` である。
リーダの検証は末尾位置を計算し直し、印と違えば拒否する。

末尾位置は、関数ごとに、本体の最も外側の式からたどって決める。
本体の最も外側の式が末尾位置かどうかは、関数の種類で決まる。
操作節の分類 N、T、G は本書 9.2 節が定める。

| 関数の種類 | 本体の最も外側の式 |
| --- | --- |
| `lambda` | 末尾位置 |
| 分類 N の `opclause`、`retclause` | その関数を持つ `handle` の印が `tail` なら末尾位置 |
| それ以外(`thunk`、`dictabs`、`handlebody`、分類 T と G の `opclause`、`cancelclause`) | 末尾位置でない |

末尾位置にある式の子のうち、末尾位置にあるのは次のものだけである。

- `let`、`letpat`、`letrec` の本体の式(最後の子)。
- `seq` の最後の子。
- `match` の各節の本体(ガードと照合対象は末尾位置にない)。
- `and` と `or` の右辺。

`opcall`、`perform`、`dictapp` は、末尾位置にあっても末尾呼び出しにならない。

**`resume` の背骨**:分類 T と G の `opclause` の本体の最も外側の式から、上の 4 つの規則でたどった末尾位置。
`resume` の印は、背骨の上にあるとき `tail`、それ以外は `ntail` である。
`handle`、`closure`、`dictabs` が作る関数は別の関数なので、背骨はその中には入らない。
そのため、T と G の節の中のハンドラ式の本体(`handlebody` の関数)に書いた `resume` は、背骨の上になく `ntail` である(本書 9.2 節)。

本節の規則は §5.7 を関数ごとに書き直したものである。
§5.7 は、ハンドラ式が末尾位置にあるときに限って、その `return` 節の本体と、再開しない操作の節の本体を末尾位置とする。
上の表は、`handle` の印が `tail` のときに限ってこれらの節の本体の最も外側の式を末尾位置とすることで、§5.7 のこの規則を表している。
同じハンドラの、末尾位置にない `resume` で再開した計算の中でこれらの節を評価するときは、末尾呼び出しの返る先がその `resume` になる。
リーダは、その場合も節の関数が使うメモリを一定に保つ。

### 5.4 メソッドの値

`(method "C" m d o…)` は、`d` と `o…` を評価して**メソッドの値**を作る。
メソッドの値を作る時点では、インスタンスを選ばない。
メソッドの値を引数とともに呼ぶと、引数をすべて評価した後で、`d` の辞書から次の手順でメソッドを選んで呼ぶ。

1. `d` が `dinst(I, ps)` の値なら、インスタンス `I` が初期化済みかを調べる。
   初期化の前なら実行時エラー(付録 B の、`インスタンスは宣言より前の位置では使えません` を含むメッセージ)になる。
   初期化済みなら、`I` のメソッド `m` の実装の関数に、辞書の並び `ps ++ o…` を渡して値を得る(本書 7.4 節)。
   その値を引数とともに呼ぶ。
2. `d` が `dbuiltin(C, T)` の値なら、付録 A の組み込みのメソッドを呼ぶ。
3. `d` が `drecord` か `dvariant` の値なら、`C` は `builtin/Eq` で、構造的な等値比較を行う(§12.5)。

`(opcall "C" m d a…)` は、`(call ntail noyield (method "C" m d) a…)` と同じ時点で同じメソッドを選ぶ。
演算子のメソッドの型はメソッド自身の制約を持たないので、`opcall` は `o` に相当する辞書を持たない。

メソッドの値を 1 回呼ぶことは、論理的な深さ(本書 11 節)では、選んだ実装を 1 回呼ぶことと数える。
インスタンスは一度初期化されたら初期化の前に戻らないので、選んだメソッドの値をキャッシュして次の呼び出しで再利用しても、観測できる違いは生じない。
リーダはそうしてよい。

### 5.5 ライタの変換規則

ライタは、精緻化を済ませた木の各構文を次のとおりに変換する。
2 つのライタが同じバイト列を出力するように、この変換規則は規定とし、ライタは必ず従う。

| 構文 | KIR |
| --- | --- |
| 真偽値、文字列 | `lit` |
| 数値 | 型の Rep の `lit`。範囲外の整数なら `lit_error`(本書 10.4 節) |
| ローカル変数 | `local` か `env`。辞書を受け取るローカルの束縛なら、それを `dictapp` で包む |
| トップレベルの値 | `global`。辞書を渡して使う箇所では `dictapp` で包む |
| 組み込みの値 | `global "builtin/…"` |
| クラスのメソッド | `method`。使用箇所の辞書の並び(メソッドの型スキームの正準順。本書 7.1 節)のうち、クラスパラメータの型変数とそのクラスの組の位置にある辞書を `d` に、残りをその並びの順に `o` に置く。たとえば `[B: Show + Eq]` の `o` は `Eq`、`Show` の順である |
| 引数のないコンストラクタの参照 | フィールドのない `construct` |
| `???` | `hole` |
| 適用 `f(a…)` | `call`。引数のレコード(`_item` の行)を、外側の要素から順に引数の並びにする |
| コンストラクタの適用 | `construct` |
| ヴァリアント | `variant` |
| `&&`、`\|\|` | `and`、`or` |
| それ以外の二項演算子 | 組み込みのクラスの `opcall`(`!=` は `not` で包む) |
| `!e` | `not` |
| 前置の `-` | `(opcall "builtin/Neg" neg d e)` |
| 無名関数 | `closure` |
| 関数定義の `let` | `let` で `closure` を束縛する。辞書を受け取るなら `dictabs` を束縛する(本書 7.5 節) |
| 値の `let` | 名前が変数なら `let`。辞書を受け取るなら `dictabs` を束縛する。名前がそれ以外のパターンなら `letpat` |
| `let rec` | `letrec`。各項目は `closure`、辞書を受け取るものは `dictabs` |
| 文の並び | 要素が 0 個なら `rec_empty`、1 個ならその式、2 個以上なら `seq` |
| `match` | `match` |
| レコードの 5 つの操作 | `rec_empty`、`rec_extend`、`rec_select`、`rec_restrict`、`rec_update` |
| `perform` | `perform`。引数のレコードを引数の並びにする |
| ハンドラ式 | `handle` |
| `resume()`、`resume(e)` | `(resume … (rec_empty))`、`(resume … e)` |
| `run h { e }` | `e`(`run` は消す) |

`if`、タプル、`with`、末尾ブロックは構文解析の段階で脱糖されている。
型注釈のパターンは、注釈を取り除く。

## 6. 関数とキャプチャ

### 6.1 関数の種類

関数の表の各項目は、次の 7 種のどれかである。

| 種類 | 作る箇所 | 引数 | 辞書の引数 | キャプチャ |
| --- | --- | --- | --- | --- |
| `lambda` | 無名関数、関数の定義、種類 `fn` のグローバル | 仮引数の個数 | 0 | 外側の変数 |
| `opclause` | `handle` の操作節 | 操作の引数の個数 | 0 | 外側の変数 |
| `retclause` | `handle` の `return` 節 | 1 | 0 | 外側の変数 |
| `cancelclause` | `handle` の `cancel` 節 | 0 | 0 | 外側の変数 |
| `handlebody` | `handle` の本体 | 0 | 0 | 外側の変数 |
| `thunk` | `def_value`、`def_pattern`、`run_exp` の式 | 0 | 0 | 0 |
| `dictabs` | 辞書を受け取る束縛、インスタンスのメソッドの実装 | 0 | 受け取る辞書の個数 | 外側の変数 |

トップレベルの名前は `global` で読むので、ルート関数(本書 3.4 節)はキャプチャを持たない。

### 6.2 フィールド

関数の項目は次のフィールドを持つ。

- シンボル(本書 3.4 節)と種類。
- `yield` の印(本書 4 節)。
- `params`:引数のスロットの Rep の並び。
- `locals`:引数でないスロットの Rep の並び。
  スロットの番号は、引数に `0` から振り、続けてローカルに振る。
- `dicts`:辞書の引数の個数。
- `caps`:キャプチャの Rep の並び。
- `result`:結果の Rep。
- `opclause` だけが持つ `pats`(引数ごとのパターン)と、省略できる `guard`(ガードの式)。
- 本体の式。

結果の Rep は、関数の本体に対応するソースの式の型から決まる Rep である。

| 種類 | 結果の Rep を決める式 |
| --- | --- |
| `lambda` | 無名関数か関数の定義の本体 |
| `opclause`、`retclause`、`cancelclause` | 節の本体 |
| `handlebody` | ハンドラ式の本体 |
| `thunk` | 初期化式か式文。変数でないパターンに束縛する値束縛が辞書を受け取るときの `def_pattern` では `any` |
| `dictabs` | 値の束縛の初期化式。関数の定義とインスタンスのメソッドの実装では `any` |

変数でないパターンに束縛する値束縛が辞書を受け取るとき、`def_pattern` の `thunk` の本体は `dictabs` の生成箇所の式である。
その `dictabs` の関数は初期化式を本体とし、結果の Rep は初期化式の Rep である。

本体の中では、キャプチャを `env(i)` で、辞書の引数を `dparam(i)` で、スロットを `local(i)` で読む。

### 6.3 仮引数のパターン

`lambda` と `retclause` の仮引数は、次のとおりに変換する。
`j` 番目の仮引数のパターンから型注釈を取り除いたものを `p` とする。

- `p` が変数なら、その変数はスロット `j` そのものである。
- `p` が `_` なら、何もしない。
- それ以外のパターンなら、本体を `(letpat p' (local j) …)` で包む。
  `p'` は `p` を変換したパターンである。
  `letpat` は仮引数の順に重ね、最初の仮引数の `letpat` を最も外側に置く。

照合が失敗したときは、`letpat` と同じ実行時エラーになる。

`opclause` の仮引数は、`pats` のフィールドに書く。
`j` 番目のパターンは `local j` と照合する。
変数のパターンはスロット `j` そのものとし、`pats` には `(wild)` と書く。
それ以外のパターンは、変換したものを書く。
どれかのパターンが一致しない節は飛ばして、次の節を試す(本書 9.4 節)。

### 6.4 スロットの番号

スロットの番号は、関数ごとに次の規則で振る。

1. 引数に `0` から `n−1` を振る。
2. 続けて、関数を正準なテキストに現れる順にたどり、スロットを束縛する箇所に着くたびに次の番号を振る。
   束縛する箇所は、`let` の `N`、`letrec` の `rec` の `N`、パターンの `bind`(`letpat`、`match` の節、`opclause` の `pats` のもの)である。
   たどる順は、`pats`、`guard`、本体である。
   持ち上げた関数の中には入らない。

そのため、テキストを先頭から読むと、束縛の番号は `n`、`n+1`、`n+2` と 1 ずつ増える。
1 つのスロットを束縛する箇所はちょうど 1 つで、スロットを再利用しない。
たとえば `(let 2 (let 3 e1 e2) e3)` では、内側の `let` は外側の `let` の `2` より後に現れるので、そのスロットは `3` である。

**スコープ**:スロットを読む `(local i)` は、式としても、`closure`、`dictabs`、`handle` の各部分のキャプチャとしても、次の位置にだけ書ける。

- `i` が引数のスロットなら、関数のどこにでも書ける。
- `(let i e1 e2)` の `i` なら、`e2` の中に書ける。
  `e1` の中には書けない。
- `letpat` のパターンが束縛するスロットなら、その `letpat` の本体の式の中に書ける。
  初期化式の中には書けない。
- `match` の節のパターンが束縛するスロットなら、その節のガードと本体の中に書ける。
- `letrec` の `rec` のスロットなら、各項目の式と、その `letrec` の本体の式の中に書ける。
- `opclause` の `pats` が束縛するスロットなら、ガードと本体の中に書ける。

リーダがスコープの外のスロットにどんな値を置くかは、本書は定めない。
そのため、スコープの外でスロットを読む KIR は、リーダごとに違う値を読むことになる。
検証は、KIR がこの規則を満たすことを検査する(本書 13.8 節の 4)。

`def_pattern` のパターン(本書 10.1 節)の `bind` は、スロットではなく、その初期化手順が定義するグローバルの並びの中の番号を指す。
この番号も、現れる順に `0` から振る。

### 6.5 キャプチャ

持ち上げた関数 `F` のキャプチャは、`F` の本体が読む、外側の関数の変数の集まりである。
`F` の中で持ち上げた関数がキャプチャする変数も、`F` の本体が読むものとして数える。
使わない変数はキャプチャしない。

キャプチャの並びの順序は、外側の関数での読み方で決める。
`dparam` を番号の昇順に、続けて `env` を番号の昇順に、続けて `local` を番号の昇順に並べる。
`F` の中の `env(i)` は、この並びの `i` 番目である。
生成箇所の式(`closure`、`dictabs`、`handle` の各部分)は、この並びを外側の関数での読み方(`(dparam N)`、`(env N)`、`(local N)`)で書く。

`letrec` はすべての値を作ってからキャプチャを埋めるので、`letrec` の項目は、同じ `letrec` のスロット(自分のスロットを含む)をキャプチャしてよい。

### 6.6 データ

名目的な型の値は、型のシンボル、コンストラクタ、フィールドの値の並びからなる。
フィールドは宣言の順に置く。
コンストラクタは第一級の値ではない。

レコードは、ラベルで操作する式(本書 5.1 節の `rec_*`)のまま表す。
レコードのレイアウトはリーダが決め、実行の結果に影響しない(§18.3)。
ただし、実行時エラーのメッセージと `cancel` 節の抑制の記録では、`<値>` の中のフィールドの順序にレイアウトが現れてよい(付録 B)。
ヴァリアントは、ラベルとペイロード 1 個からなる。

## 7. 辞書

### 7.1 辞書の引数の順

辞書を受け取る束縛が辞書の引数を受け取る順序(**正準順**)は、束縛の一般化した型 `τ` から次のとおりに決める。

1. `τ` を左から深さ優先でたどる。
   型構成子の適用は引数を左からたどり、関数の型は引数のレコード、結果、エフェクト行の順にたどる。
   レコードとヴァリアントの行は、各フィールドの型をラベル名のバイト列の昇順にたどり、最後に行の末尾をたどる。
   同じラベルのフィールドが 2 つ以上あるときは、外側のものを先にたどる。
2. 一般化した型変数に初めて達したら、その変数に付いた制約のクラスを、クラスの表(本書 12.4 節)での位置の昇順で、正準順の並びの末尾に追加する。
   予約述語(`Integral`、`Fractional`)は追加しない。
   同じ変数に再び達しても何も追加しない。

並びの `i` 番目の制約の辞書が `dparam(i)` である。
束縛を使う側も、同じ正準順で辞書を渡す。

型の行の中のフィールドの順序と、型変数に制約が付く順序は、型検査がソースのどの部分を先に処理したかで変わる。
正準順はどちらも使わないので、型だけから決まる。
たとえば `show(r.b) + show(r.a)` と `show(r.a) + show(r.b)` のどちらでも、`r` の型の正準順は `a` のフィールドの制約が先である。
`[A: Show + Eq]` と `[A: Eq + Show]` のどちらでも、`Eq` が先である。
Diktor では、`unify.ml` の `constraints_of` がこの順序を決める。

### 7.2 インスタンス

インスタンスの項目は、シンボル、クラス、対象の型の先頭にある型構成子、前提の個数、メソッドの実装の並びを持つ。
前提の辞書は、インスタンスの宣言の型パラメータの左からの順に並べ、同じパラメータの制約の辞書は、制約を書いた順に並べる。
`dinst(I, [前提…])` の前提もこの順序である。

メソッドの実装の項目は、`(method m k "関数")` である。
`m` はメソッドの名前、`k` はメソッド自身の辞書の個数、`"関数"` は実装の関数である。
メソッド自身の辞書は、クラスの宣言でメソッドの型に付いた制約の辞書である。
ただし、クラスパラメータに付く、そのクラス自身の制約は含めない。
項目はインスタンスの本体に書いた順に並べる。
この順序は、クラスのメソッドの順序と同じでなくてよい。
インスタンスの本体にはクラスのすべてのメソッドを書かなければならないので、実装の項目はクラスのメソッドごとにちょうど 1 つある。

### 7.3 メソッドの実装の関数

実装の関数は種類 `dictabs` で、辞書の引数の個数は `前提の数 + k` である。
辞書の引数は `前提の辞書 ++ メソッド自身の辞書` の順に受け取る。
本体は、メソッドの束縛の値 `V` である。

| メソッドの束縛 | `V` |
| --- | --- |
| 関数の定義 | `closure` |
| 値の束縛 | 初期化式 |
| `let rec` のグループの 1 つ | グループ全体の `letrec` で、本体の式がそのメソッドのスロットを読むもの |

実装の型がインスタンスの宣言の型よりも一般的で、独自の制約を持つときは、`V` の代わりに `(dictapp (dictabs "F" c…) d…)` を本体にする。
`F` は種類 `dictabs` の関数で、辞書の引数を実装の型の正準順に受け取り、`V` を本体とする。
`d…` は、インスタンスの文脈でその制約を満たす辞書である。
メソッドが `let rec` のグループの 1 つであるときは、独自の制約を持つ項目がグループの `letrec` の中ですでに `dictabs` になっているので、本体は `(dictapp V d…)` である。

### 7.4 メソッドの選択

`(method "C" m d o…)` が作るメソッドの値は、呼ばれたときに、本書 5.4 節のとおりにメソッドを選ぶ。
`d` が `dinst(I, ps)` の辞書なら、`I` の `m` の実装の関数に `ps ++ o…` を渡す。
辞書の引数が 0 個の実装の関数では、`def_instance` が 1 回だけ評価した値(本書 10.1 節)を使う。

使う側の辞書の並びは、メソッドの型スキームの正準順(本書 7.1 節)である。
ライタは、この並びのうち、(クラスパラメータの型変数, そのクラス) の組に対応する位置の辞書を `d` にし、残りを順に `o…` にする。

### 7.5 辞書の適用と使うたびの評価

`(dictapp e d…)` は、`e` の値に辞書の並びを渡す。

| `e` の値 | 結果 |
| --- | --- |
| `dictabs` の値(ローカルの束縛か、種類 `dictabs` のグローバル) | 辞書の引数を `d…` にして関数の本体を評価した値 |
| 辞書を受け取る `extern` のグローバル | その `extern` の値。辞書は捨てる |

`e` が `(global g)` のとき、`g` の種類は、`dicts` のフィールドが 1 以上の `extern` か、`dictabs` である。
`d…` の個数は、`extern` では `dicts` のフィールドの値と、`dictabs` では関数の `dicts` と同じである。
`e` が `(dictabs F …)` のときも、`d…` の個数は `F` の `dicts` と同じである。
それ以外の `e` では、受け取る辞書の個数は型で決まるので、検証は個数を検査しない。

**使うたびの評価**:辞書を受け取る値束縛は、使うたびに初期化式を評価する(§6.4、§12.2)。
リーダが結果を保存して再利用してよいのは、`dictabs` の関数の本体が構文上 `closure` のときだけである。
ただし、同じ辞書の並びに対して前の結果を返すメモ化は、それ以外の本体でも観測できないので許す。
初期化式はエフェクトを起こせず、1 回目の評価が実行時エラーになるか停止しないときは 2 回目の評価が行われないからである。

### 7.6 構造的な辞書と組み込みの辞書

`drecord` と `dvariant` は `builtin/Eq` の辞書であり、閉じた行の型にだけ現れる。
項目は、ラベルと、そのフィールドの型の `Eq` の辞書である。
項目は、ラベル名のバイト列の昇順に並べる。
同じラベルが行に 2 回現れたときは 2 つの項目を書き、外側のフィールドの項目を先にする。
`drecord` の比較は、項目を書いた順に進める。
各項目では、両辺から最も外側の同名のフィールドを取り出して比較し、取り出した残りで次の項目へ進む。
ある項目の比較が偽なら、その時点で全体の結果を偽とし、残りの項目の辞書を呼ばない。
結果が真になるのは、すべての項目が等しく、両辺の残りが空になったときだけである。
ユーザのインスタンスが実行時エラーになるか停止しないときは、比較をどこでやめるかを観測できる。
`dvariant` の比較は、両辺のラベルが等しく、そのラベルの項目の辞書でペイロードが等しいときに真である。

`dbuiltin(C, T)` は組み込みのインスタンスである。
ライタは、型検査がインスタンスとして選んだ組 `(C, T)` が組み込みのインスタンス(付録 A)なら `dbuiltin` を、ユーザが宣言したインスタンスなら `dinst` を書く。

## 8. パターン

パターンは次の 6 種である。

| パターン | テキスト | 意味 |
| --- | --- | --- |
| ワイルドカード | `(wild)` | 値を受け取り、束縛しない |
| 変数 | `(bind N)` | 値をスロット `N` に束縛する |
| リテラル | `(lit …)` | 値がリテラルと等しいかを調べる |
| レコード | `(record closed\|open (field L p)…)`、`(record rest (field L p)… p0)` | 書いた順に、各ラベルの最も外側のフィールドを取り出して `p` と照合し、取り出した残りで次へ進む。`rest` は最後の残りを `p0` と照合する |
| コンストラクタ | `(ctor "型" C (field N p)…)` | コンストラクタが `C` で、位置 `N` のフィールドの値が `p` に一致するかを、書いた項目ごとに調べる |
| ヴァリアント | `(variant L p)` | ラベルが `L` で、ペイロードが `p` に一致するかを調べる |

ペイロードを書かないヴァリアントのパターン `#L` は、`(variant L (record closed))` と書く。
ペイロードの位置に書くのは、空のタプルのパターンである。
これは、ペイロードのないヴァリアントの式が `(variant L (rec_empty))` であることに対応する。

照合は、項目を書いた順に進め、一致しない項目に達したらそこで失敗する。
パターンに書いたラベルを持たないレコードとの照合は、実行時エラーではなく照合の失敗である。

レコードのパターンの `closed`(タプルのパターン)と `open`(既定のレコードのパターン)は、照合では同じように動作し、どちらも書いたラベルのフィールドだけを調べる。
`closed` では、残りのフィールドがないことを型検査が保証している。
`open` のパターンは、パターンに書いていないフィールドを持つレコードにも一致する(`case {x}` は `{x = 1, y = 2}` に一致する)。
そのためリーダは、`open` のパターンと照合するレコードがどのフィールドを持つかを、パターンのラベルの並びから決めてはならない。

コンストラクタのパターンの項目は、ソースに書いたフィールドだけを、フィールドの位置の昇順に並べる。
書かなかったフィールドは調べない。

数値の `lit` には、照合対象の型で解釈した値を書く(`case 0xFFFFFFFF` は `Int32` の `-1` である)。
パターンの数値の範囲は型検査が検査するので、パターンに `lit_error` は現れない。
`f64` の `lit` は、IEEE 754 の `==` で照合する(§11.1)。
そのため `0.0` の `lit` は `-0.0` にも一致し、NaN にはどの `lit` も一致しない。
`str` の `lit` は、バイト列が等しいときに一致する。

`match` は、節の順序とガードを保つ。
ガードは、パターンが一致した節でだけ評価する。
ガードが偽なら次の節へ進む。
どの節にも一致しなければ実行時エラーになる(§11.2)。
リーダは決定木を作ってよいが、ガードを評価する順序と回数を変えてはならない。

## 9. エフェクトと抽象機械

本節は、エフェクトの意味を抽象機械の言葉で定める。
本節の規則は、リーダがハンドラと継続をどう実装するかによらない。
本節は §13 を KIR の水準で書き直したものであり、§13 と食い違うときは §13 に合わせて本書を直す。

### 9.1 ハンドラと操作節

`handle` は、エフェクト、本体の関数、操作節の並び、`return` 節(省略できる)、`cancel` 節(省略できる)を持つ。
操作節は、引数のパターン、ガード(省略できる)、本体を 1 つの `opclause` の関数にまとめたものである。
操作の名前と分類は、`handle` の操作節の項目 `(op op N|T|G "関数" c…)` に書く(本書 5.1 節)。
1 つの `handle` は 1 つのエフェクトを処理する(§13.4)。

### 9.2 操作節の分類

各操作節は、N、T、G のどれか 1 つに分類する。

| 分類 | 条件 |
| --- | --- |
| N | 操作の返り値の型が `Never` である |
| T | N でなく、本体の中の `resume` がすべて末尾 `resume` である(`resume` のない分岐を含んでよい) |
| G | それ以外 |

ライタは分類を書く。
リーダの検証は、操作の `never` の印と `resume` の `tail` の印から分類を計算し直し、書いてある分類と違えば拒否する。

`resume` を書けるのは、T と G の節の本体の中と、その本体の中にあるハンドラ式の本体の中だけである。
ハンドラ式の本体は `handlebody` の関数であり、入れ子のハンドラ式の本体もこれに含む。
操作節のガード(種類 `opclause` の関数の `(guard …)` のフィールド)、`return` 節、`cancel` 節、N の節、無名関数の本体には書けない。
T か G の節の本体の中、またはその中の `handlebody` の関数の中にある `match` のガードは、その本体の一部なので、`resume` を書ける。
ガードは背骨の上にないので(本書 5.3 節)、その `resume` は `ntail` であり、囲む操作節は G になる。
リーダの検証は、書ける位置以外にある `resume` を拒否する。

`handlebody` の関数の中の `resume` は、その関数を作ったハンドラ式を囲む操作節の継続を再開する。
間にある `handlebody` の関数は、囲む関数の継続をそのまま引き継ぐ。
この `resume` は背骨の上にないので `ntail` であり(本書 5.3 節)、囲む操作節は G になる。
Diktor の型検査は、操作節の本体の中にあるハンドラ式の本体に書いた、外側の節の `resume` を受理する。

### 9.3 抽象機械の状態

抽象機械は、評価の文脈ごとに次のものを持つ。

- **ハンドラの連鎖**:有効なハンドラの起動の並び。
  最も内側の起動が先頭にある。
- **ハンドラの起動**:`handle` を 1 回評価するたびに作るもの。
  エフェクト、操作節、`return` 節、`cancel` 節、親の起動、深さ `h`(本書 11 節)を持つ。
- **継続**:G の節が受け取る、中断した計算。
  1 回だけ再開できる。
  節の外へは持ち出せない。

ハンドラの起動は、単調に増える 64 ビットの番号で識別する。
巻き戻しの宛先は、この番号で指定する。
同じ `handle` の式を入れ子に起動したとき(再帰や、同じ関数の 2 回の呼び出し)、内側の起動が外側の起動宛ての巻き戻しを受け取ってはならない。

### 9.4 `perform`

`perform(E, op, [a…])` は、引数を左から評価した後、次の順に進む。

1. ハンドラの連鎖から、エフェクトが `E` である最も内側の起動を探す。
   以下、この起動を宛先の起動と呼ぶ。
2. 操作節を上から試す。
   パターンが一致した節でだけガードを評価する。
   パターンが一致しない節とガードが偽の節は飛ばして、次の節へ進む。
3. 選んだ節の分類によって、次のとおりに進む。
   - T:節の本体を評価する。
     末尾 `resume` である `resume(v)` は、`perform` の値を `v` にする。
     節が `resume` せずに値 `r` になったときは、`perform` の位置から宛先の起動までの計算を破棄し、`r` をハンドラ式の値にする。
   - N:`perform` の位置から宛先の起動までの計算を破棄し、その後で、ハンドラの外で節の本体を評価する(9.6 節の 2)。
     ガードは破棄の前に評価してある。
   - G:`perform` の位置から宛先の起動までの計算を継続としてキャプチャし、宛先の起動を連鎖から外して、節の本体を継続とともに評価する。

どの節にも一致しない操作を、外側のハンドラへ送り直すことはない。
その `perform` は実行時エラー(付録 B の 9 番)になる。

`runtime` の印の付いた操作(プレリュードの `Console` の `write`。本書 12.5 節)の `perform` は、KIR ではほかの操作と同じように書く。
プレリュードの `Console` はユーザのハンドラでは処理できず、最も外側でランタイムが処理する。
リーダは、`runtime` の印の付いた操作の `perform` を、ランタイムの直接呼び出しに置き換えてよい。
その場合も、標準出力への書き込みの順序と、出力エラーの扱い(9.7 節)は変えない。
`user` の操作の `perform` は、名前が `Console` のエフェクトのものでも、ランタイムの直接呼び出しに置き換えてはならない。

### 9.5 `resume`

`resume(e, tail)` は、まず `e` を評価する。
その後で、継続がすでに再開されていれば、この `resume` は実行時エラーになる。
再開されていなければ、再開済みのフラグを立ててから再開する。
`e` の評価の中で同じ継続を再開したときも、この検査で外側の `resume` が実行時エラーになる(§13.5)。

再開した計算の中では、継続をキャプチャしたハンドラの起動が再び連鎖に入る。
再開した計算の中で決まった `return` 節の値と、`resume` しない節の値は、ハンドラ式の値ではなく、この `resume` の値になる(§13.6)。

末尾 `resume` で再開するとき、リーダは、節の評価のために持っていた情報を捨てる。
T の節の本体、N の節の本体、`return` 節は、何回繰り返して評価しても、一定のメモリで評価できなければならない(§5.7)。
G の節の末尾位置にない `resume` が使うメモリは保証しない。

### 9.6 規定

次の規定は、本書 9 節の規則のうち、取り違えやすい点を定める。

1. 本体の側から届いた巻き戻しの宛先がこのハンドラの起動でないときは、このハンドラの `cancel` 節を 1 回実行してから巻き戻しを続ける。
   宛先がこの起動なら、`cancel` 節を実行しない。
   `return` 節も実行しない。
2. `return` 節は、ハンドラを連鎖から外した後で評価する。
   そのため、`return` 節の中でエラーが起きても、自分の `cancel` 節を実行しない。
   N の節の本体も、継続を破棄してハンドラを外した後で評価する。
   G の節の中で `resume` が戻った後のコードも、そのハンドラが連鎖に入っていない状態で実行する(§13.6)。
3. 節の選択(パターンとガード)と T の節の本体を評価する間は、ハンドラの連鎖を、そのハンドラの親の起動から始まる連鎖に差し替える。
   そのため、節の中で起こした操作は外側のハンドラへ届く(§13.4)。
   節を抜けたら、連鎖を `perform` の時点のものに戻す。
4. `cancel` 節は、自分のハンドラの外で実行する。
   `cancel` 節の中で起きた脱出(実行時エラー、破棄、論理的な深さが上限を超えたこと)は、すべて抑制する。
   抑制したら、標準出力を flush してから標準エラーに抑制の記録を書き、元の巻き戻しを続ける。
   この flush が失敗したら、抑制の記録を書かず、残りの `cancel` 節も実行せずに、出力エラーの診断を書いて終了コード 74 で終了する(9.7 節)。
5. ハンドラの起動は、単調に増える 64 ビットの番号で識別する(9.3 節)。

### 9.7 巻き戻しと `cancel` の順序

巻き戻しは、破棄する計算の中のハンドラを、内側から外側の順にたどる。
宛先でない起動に達するたびに、9.6 節の 1 のとおり `cancel` 節を実行する。

T と G の節が `resume` の前に脱出したとき(`resume` の引数の評価中を含む)は、次の順に `cancel` 節を実行する(§13.6)。
節の評価の中で起動したハンドラの `cancel` 節、継続の中の `cancel` 節(内側から外側の順)、宛先の起動の `cancel` 節、さらに外側の起動の `cancel` 節の順である。
宛先の起動の `cancel` 節も実行するのは、宛先の起動の継続がまだ生きているからである。
G の節が `resume` の後に脱出したときは、宛先の起動はもう連鎖に入っていないので、その `cancel` 節は実行しない。

N の節では、計算を破棄する前にガードを評価する。
ガードの中で脱出したときは、継続がまだ生きているので、宛先の起動の `cancel` 節を実行する。
本体の中の脱出は、ハンドラ式を抜けた後に起きたものとして扱い、宛先の起動の `return` 節と `cancel` 節を実行しない。

`cancel` 節の中から、まだ連鎖に入っているハンドラの G の操作を起こしてよい。
そのハンドラが継続を再開すると、`cancel` 節の残りと、中断していた巻き戻しの残りを実行する。

実行時エラーは操作ではなく、ハンドラでは捕捉できない。
実行時エラーが起きると、有効なハンドラを内側から外側の順に巻き戻し、各起動の `cancel` 節を実行する(§15.5)。
最上位に達したら、標準出力を flush し、メッセージ(付録 B)を標準エラーに書いて、終了コード 3 で終了する。

`runtime` の印の付いた操作(プレリュードの `Console` の `write`)の書き込みが失敗したら、その出力エラーを実行時エラーと同じように巻き戻し、`cancel` 節を実行してから終了コード 74 で終了する。
出力エラーの後のバッファの扱いは、エラーの種類によって違う。
エラーが `EBADF`、`EPIPE`、`ECONNRESET` なら、未出力のバッファを捨てる。
それ以外のエラー(`/dev/full` への書き込みの `ENOSPC`、`EIO` など)なら、まだ書けていないバイトをバッファに残す。
どちらの場合も、その後の書き込みはバッファに追記し、次の flush で改めて書き出しを試みる。
この動作は OCaml 5.2 のチャネルと同じである。

バッファを捨てるエラーでは、前の失敗の後に何も追記していなければ、バッファは空なので flush は成功する。
追記したものを書き出せなければ、flush はまた失敗する。
そのため、`cancel` 節が書き込んでから脱出すると、9.6 節の 4 で抑制の記録を書く前の flush が失敗するので、抑制の記録を書かずに終了コード 74 で終了する。
書き込まずに脱出すると、抑制の記録を書いてから巻き戻しを続ける。

バッファに残すエラーでは、残したバイトのために次の flush もまた失敗する。
そのため、`cancel` 節が書き込んだかどうかに関わらず、9.6 節の 4 で抑制の記録を書く前の flush が失敗し、抑制の記録を書かずに終了コード 74 で終了する。

## 10. 初期化

### 10.1 初期化手順

各単位の初期化は、次の 6 種の初期化手順の並びである。
リーダは、単位を本書 2.1 節の順に処理し、各単位の初期化手順を書いた順に実行する。

| 初期化手順 | テキスト | 意味 |
| --- | --- | --- |
| `def_value` | `(def_value "グローバル" "関数")` | `thunk` の関数を評価し、値をグローバルに置いて、初期化済みにする |
| `def_pattern` | `(def_pattern "関数" (globals "グローバル"…) p)` | `thunk` の関数を評価し、結果をパターン `p` と照合する。一致しなければ実行時エラーになる(メッセージは `letpat` と同じ)。一致すれば、束縛した値を各グローバルに置き、並びの順に初期化済みにする |
| `def_fns` | `(def_fns "グローバル"…)` | 種類が `fn`、`dictabs`、`extern` のグローバルを、評価せずに初期化済みにする |
| `def_dictabs` | `(def_dictabs "グローバル")` | 辞書を受け取る値束縛のグローバルを、評価せずに初期化済みにする(本書 7.5 節) |
| `def_instance` | `(def_instance "インスタンス")` | 辞書の引数が 0 個の実装の関数を、メソッドを書いた順に 1 回だけ評価し、すべて評価し終えてからインスタンスを初期化済みにする |
| `run_exp` | `(run_exp "関数")` | `thunk` の関数を評価し、値を捨てる |

`def_pattern` の `p` の `bind k` は、グローバルの並びの `k` 番目に束縛することを表す(本書 6.4 節)。
`def_instance` で評価した値は、メソッドを選ぶたびに再利用する。
実装の関数を評価している間、インスタンスはまだ初期化の前である。
その間にそのインスタンスからメソッドを選ぶと、実行時エラー(付録 B の 6 番)になる(本書 5.4 節)。
したがって、まだ評価していない実装の値を選ぶことはない。
たとえば `let k = { let n = sz(B(1)); fn(b) => n }` を実装に持つ `Sz[B]` のインスタンスは、`k` を評価する途中で `Sz[B]` の `sz` を選ぶので、`def_instance` の中で実行時エラーになる。

### 10.2 宣言の変換規則

ライタは、各単位のトップレベルの宣言を、書いた順(module を平坦化した後の順)に、次のとおりに変換する。

| 宣言 | 初期化手順とグローバル |
| --- | --- |
| 関数の定義の `let`(仮引数を持つ) | `def_fns`。辞書を受け取らなければ種類 `fn`、受け取れば種類 `dictabs` で、`dictabs` の関数の本体は `closure` |
| 値の `let` で、名前が変数で辞書を受け取らないもの | `def_value`。種類 `value` |
| 値の `let` で、名前が変数で辞書を受け取るもの | `def_dictabs`。種類 `dictabs` で、関数の本体は初期化式 |
| 値の `let` で、名前が変数でないもの | `def_pattern`。束縛する変数ごとに種類 `value` のグローバル。`_` だけならグローバルの並びは空 |
| `let rec` のグループ | グループ全体で 1 つの `def_fns`。各項目は辞書を受け取らなければ `fn`、受け取れば `dictabs` |
| `extern` | `def_fns`。種類 `extern` |
| `type instance` | `def_instance` |
| 式文 | 辞書を受け取らなければ `run_exp`。辞書を受け取る式文には何も書かない |
| `newtype`、`effect`、`type class` | 初期化手順を書かない(型、エフェクト、クラスの表に書く) |
| `type`(型エイリアス) | 何も書かない。型の表にも項目を作らない |

`let rec` の項目の右辺が無名関数(`let rec f = fn(x) => …`)のときは、その無名関数を関数の定義と同じように扱う。
種類 `fn` のグローバルの関数は、その無名関数か関数の定義から作る `lambda` の関数で、シンボルはグローバルと同じである。

### 10.3 初期化済みのフラグ

グローバルとインスタンスは、初期化済みのフラグを持つ。
種類が `builtin` のグローバルは、プログラムの開始時点で初期化済みである。
初期化の前のグローバルを読むと、実行時エラー(付録 B の 2 番)になる。
初期化の前のインスタンスからメソッドを選ぶと、実行時エラー(付録 B の 6 番)になる(本書 5.4 節)。

**検査を省いてよい条件**:リーダがグローバル `g` の初期化の検査を省いてよいのは、次の 2 つの場合だけである。
1 つは、`g` の参照を含む、最も外側のトップレベルの実体の初期化手順が、`g` の初期化手順より後にある場合である。
もう 1 つは、その実体と `g` が同じ `def_fns` の初期化手順にある場合である。
たとえば `let p = {f = fn(x) => h(x)}` で `h` が後に宣言されているときは、ここで作った無名関数を `h` の初期化の前に呼べるので、検査を省いてはならない。

### 10.4 範囲外のリテラル

範囲外の数値リテラルは `(lit_error lit_range "表記")` と書く。
この式は、評価したときに初めて実行時エラー(付録 B の「数値リテラルが範囲外です」)になる。
リーダは、この式に定数畳み込みを行ったり、評価の位置を前に動かしたり、式を取り除いたりしてはならない(§4.2)。

`"表記"` に書く表記は、次の 3 つを空白を挟まずに連結したものである。

1. リテラルに `-` をまとめたとき(§4.2)だけ書く `-`。
   `-` とリテラルの間の空白とコメントは表記に入れない。
2. ソースに書いた数字の表記。
   `0x`、`0o`、`0b` の接頭辞と区切りの `_` を残す。
3. ソースに書いた接尾辞(`i32` など)。書いていなければ何も書かない。

たとえば `- 2147483649` の表記は `-2147483649`、`0x1_0000_0000i32` の表記は `0x1_0000_0000i32` である。
Diktor では、この表記を `Lexer.show_number` が作る。

数値リテラルの値は、ライタが、リテラルの型の先頭にある型構成子の Rep に従って確定する。
`i32` と `i64` のリテラルは、言語仕様 §4.2 が定める範囲と表記の規則に従って読む。
`f64` のリテラルは次の規則で読む。

1. 接尾辞(`f64` など)を除いた数字の表記から、区切りの `_` をすべて取り除く。
   `1_f64` や `1.0_` のような末尾の `_` も取り除く。
2. 残りを 10 進数として読み、IEEE 754 の binary64 に正しく丸める(最も近い値に丸め、2 つの値から等距離なら偶数のほうに丸める)。
   `99999999999999999999f64` のように、整数の表記に接尾辞 `f64` を付けたリテラルも、同じ規則で読む。
3. 絶対値が binary64 の範囲を超えるリテラルは +inf になり、`-` をまとめた(§4.2)ときは -inf になる。
   絶対値が小さすぎるリテラルは、非正規化数か ±0 になる。

`f64` のリテラルは `lit_error` にならない。
`Float64` のリテラルが `0x`、`0o`、`0b` の接頭辞を持つことはない。
`0b101f64` のような表記は、字句解析が拒否する。
`0x10f64` のような表記は、字句解析が整数のリテラルとして読むが、`Float64` は `Integral` のインスタンスでないので、`Float64` のリテラルにはならない。
たとえば `1e400` の値は `0x7ff0000000000000`、`- 1e400` の値は `0xfff0000000000000`、`1_000.5` の値は `0x408f440000000000`、`2.5e-324` の値は `0x0000000000000001` である。
言語仕様 §4.2 は、無限大を直接書くリテラルはないとしているが、`1e400` を評価すると無限大になる。
この食い違いをどう扱うかは、言語仕様の側で決める課題として残す。
`-` をまとめた `0x`、`0o`、`0b` のリテラルは、`-` を除いた数字を型のビット幅のビット列として読み(§4.2)、その値の符号を反転する。
符号の反転が型のビット幅でオーバーフローしたときは、結果を折り返す(2 の補数で下位のビットだけが残る)。
ビット幅に収まるかどうかの検査は、`-` を除いた数字に対して行う。
`Int32` の例を示す。

| リテラル | 値 |
| --- | --- |
| `-0x80000000` | `-2147483648` |
| `-0xffffffff` | `1` |
| `-0x1ffffffff` | `lit_error`(表記は `-0x1ffffffff`) |

## 11. 実行時エラーと論理的な深さ

### 11.1 実行時エラーの種類

KIR の評価を止めるエラーは、次の 4 種である。

| 種類 | 起きる場面 | 終了コード |
| --- | --- | --- |
| 実行時エラー | 言語仕様が「実行時エラーになる」と書く場面(付録 B) | 3 |
| `depth_limit` | 論理的な深さが上限を超えた(本書 11.2 節〜11.5 節) | 3 |
| メモリ不足 | 確保の要素数が `N_alloc_max` を超えた(本書 11.6 節)か、リーダがヒープを拡張できない | 3(注) |
| 出力エラー | 標準出力に書けない(本書 9.7 節) | 74 |

どのエラーも、有効なハンドラを内側から巻き戻して `cancel` 節を実行する(本書 9.7 節)。
メッセージは付録 B に定める。

注:メモリが尽きたときに、`cancel` 節を実行せず、3 以外の終了コードで終了する場合がある。
RustKeleut の WasmGC バックエンドでは、V8 のヒープそのものを使い尽くすと Node のプロセスが異常終了し、`keleut run` は終了コード 70 で終了する。
仮想メモリを制限しているとき(`ulimit -v`)に `keleut run` が Node を起動できないか、Node のスタックやスレッドを確保できない場合も、終了コード 70 で終了する。
RustKeleut のインタプリタと LLVM バックエンドは、LLVM の内部の確保が失敗した場合と、グローバルアロケータの予備領域を使い切った後に Rust の確保が失敗した場合に、SIGABRT(終了コード 134)で異常終了する。
Diktor(`--run-ir`)は、ヒープを少しずつ使い尽くすと、minor GC の中で確保に失敗し、終了コード 134 で終了することがある。
OS が物理メモリ不足でプロセスを強制終了した場合は、どのリーダも SIGKILL(終了コード 137)で終了する。
これらは §15.5 との既知の相違であり、本書 1 節は、これらを、リーダが同じ結果になる保証の対象外としている。

### 11.2 論理的な深さ

§15.5 は、評価に使えるメモリの上限をどれだけにするかを処理系に任せている。
一方で、上限を超えたときの動作(`cancel` 節を実行して終了コード 3 で終了する)は、実行の結果に影響する。
そこで本書は、評価の文脈ごとに整数の深さ `d` を定め、すべてのリーダが同じ値を数えるようにする。
深さは、リーダのスタックの使い方とは無関係に、次の表の境界で決まる。

| 場面 | 深さ |
| --- | --- |
| 最上位の初期化手順 | 0 |
| 深さ `d` の文脈での、非末尾呼び出しの `call`、`opcall`、`dictapp` と、組み込みがユーザの関数を呼ぶ呼び出し(組み込みの中で末尾位置にあっても、この行で数える) | 呼び出し先は `d+1` |
| 末尾呼び出し、末尾 `resume` | 呼び出し元の深さを引き継ぐ(増えない) |
| 深さ `h` の `handle` の本体 | `h+1` |
| 深さ `p` の `perform` の、節の選択(パターンとガード)と T の節の本体 | `p+1` |
| G の節の本体(宛先のハンドラの起動の深さを `h` とする) | `h+1` |
| G の節の中の、深さ `c` での末尾位置にない `resume`(継続の深さの差を `Δ = p − h` とする) | 再開した `perform` は深さ `c+Δ` で値を返す |
| N の節の本体、`return` 節 | `h`(ハンドラ式の位置の深さを引き継ぐ) |
| `cancel` 節 | 巻き戻されるハンドラの起動の `h` |

ここで、ハンドラの起動の深さ `h` は、その `handle` の式を評価した文脈の深さである。

`runtime` の印の付いた操作(プレリュードの `Console` の `write`。本書 12.5 節)の `perform` は、深さを変えず、上限の検査もしない。
`user` の操作の `perform` は、名前が `Console` のエフェクトのものでも、上の表に従う。

深さは上の表のとおりに数える。
リーダが内部で行う呼び出しの回数(ハンドラの本体を関数として呼ぶ、関数をインライン展開する、など)は、深さに影響しない。

表の各行は、次のように適用する。

- 非末尾呼び出しには、プリミティブ、`extern`、組み込みの値、組み込みのインスタンスのメソッドを呼ぶものも含む。
  呼び出し先の深さ `d+1` を上限と比べる。
- 組み込みの値(付録 A.4)は、その呼び出しの呼び出し先の深さで実行する。
  非末尾呼び出しなら呼び出し元の `d+1`、末尾呼び出しなら `d` である。
  組み込みがユーザの関数を呼ぶ呼び出しは、組み込みの深さに 1 を足す。
- メソッドの値の呼び出し(本書 5.4 節)では、実装を選び、辞書を受け取る実装なら辞書を渡して実装の関数を評価し、得た関数を呼ぶ。
  これを 1 回の呼び出しとして数え、実装の関数の評価も、得た関数の本体も、その呼び出しの呼び出し先の深さで実行する。
- `opcall` と `dictapp` は末尾呼び出しにならない(本書 5.3 節)ので、末尾位置にあっても呼び出し先を `d+1` と数える。
  `dictapp` の関数が `extern` のグローバルでも同じである。
- 構造的な辞書(`drecord`、`dvariant`)の `Eq` のメソッドは、フィールドを比較するたびに、そのフィールドの辞書のメソッドを非末尾呼び出しで呼ぶ。
  そのため、各比較は、比較する側の深さに 1 を足した深さで実行する。
- 初期化手順(本書 10 節)は、`def_value` の値の評価も `def_instance` の実装の評価も、深さ 0 で実行する。
- `runtime` の操作の `perform` の引数は、ほかの式と同じように評価し、引数の中の呼び出しは表のとおりに数える。

### 11.3 上限の検査

リーダは、表で深さが増えるすべての境界で、新しい深さを上限 `L` と比べる。
対象は、非末尾呼び出し、`handle` の本体に入るとき、節の選択、T の節の本体、G の節の本体、末尾位置にない `resume` である。
新しい深さが `L` を超えるときは、その境界に入る前に `depth_limit` のエラーにする。

末尾位置にない `resume` では、再開した `perform` の深さ `c+Δ` を、継続を再開する前に `L` と比べる。
比べるのは、`e` を評価し、継続がまだ再開されていないことを検査した後で、再開済みのフラグを立てる前である(本書 9.5 節)。
`c+Δ` が `L` を超えたときは、継続はまだ再開されていないので、節が `resume` の前に脱出したときと同じように、継続の中の `cancel` 節と宛先の起動の `cancel` 節を実行する(本書 9.7 節)。

### 11.4 再開での深さのずれ

深さ `c` で継続 `K` を再開するとき(`K` をキャプチャしたハンドラの起動の深さを `h` とする)、`K` の中の各文脈の深さと、`K` の中で始まったすべてのハンドラの起動の `h` を、`c − h` だけずらす。
`K` をキャプチャしたハンドラの起動自身の `h` は `c` になる。
そのため、再開した計算の中で実行するそのハンドラの `return` 節と、`resume` しない節は、深さ `c` で実行する。
これは、それらの値がこの `resume` の値になること(本書 9.5 節)と整合する。

末尾 `resume` は、T の節でも G の節でも深さをずらさない。
T の節の末尾 `resume` は、節の選択の前の状態に戻り、`perform` を評価した文脈の深さのまま続ける。
G の節の末尾 `resume` は、節の本体の評価を捨て、継続をハンドラ式の位置(深さ `h`)で再開するので、`c − h = 0` である。

`K` の中で始まったハンドラの起動は、`K` が持つ、連鎖の切り出した部分の中のものだけではない。
T の節(またはガード)を評価している間は、そのハンドラの起動と、`perform` の位置からそのハンドラまでの起動が、連鎖から外れている(本書 9.6 節の 3)。
その節の中から外側のハンドラの G の操作を起こすと、これらの起動は連鎖の切り出した部分には入らず、`K` の中の文脈からだけ到達できる。
これらの起動の `h` もずらす。

`K` の中の節がキャプチャして、まだ再開していない継続 `K2` の深さは、`K2` をキャプチャした起動の `h` からの差で決める。
`K2` の中の各文脈の深さと、`K2` の中で始まったハンドラの起動の `h` と、`Δ = p − h` は、キャプチャしたときに、その起動の `h` からの差として決まる。
この差は、後で `K` を再開しても変わらない。
`K2` をキャプチャした起動は `K` の中で始まったので、`K` の再開でその `h` は `c − h` だけずれ、`K2` の中の文脈の深さと起動の `h` も同じだけずれる。
深さ `c2` で `K2` を再開すると、`K2` をキャプチャした起動の `h` は `c2` になり、`K2` の中の文脈と起動の深さは、`c2` にそれぞれの差を足した値になる。
再開した `perform` が値を返す深さは `c2 + Δ` である。
`K2` を再開せずに破棄したときは、`K2` の中の起動の `cancel` 節を、その起動の、ずれた後の `h` で実行する。
`K2` の中の節がキャプチャしてまだ再開していない継続も、同じ規則で、`K2` をキャプチャした起動の `h` に従ってずれる。

リーダが継続のフレームと起動の `h` を絶対の深さで持つなら、`K` を再開するときに、`K` から到達できる、まだ再開していない継続のフレームと、その中の起動の `h` も `c − h` だけずらす。
`K2` を再開するときは、`c2` と、ずらした後の `K2` をキャプチャした起動の `h` との差だけずらす。
キャプチャしたときの `h` を継続に記録しておき、`K2` を再開するときだけ、`c2` からその記録した値を引いた分だけずらす実装は、この規則を満たさない。
その実装では、`K2` を再開したときのフレームの深さは合うが、`K2` を破棄したときの `cancel` 節の深さが合わないからである。

### 11.5 予備の深さと既定の上限

**予備の深さ**:`depth_limit` の巻き戻しが伝播している間は、上限を `L + R` に引き上げる。
この `R` を予備の深さと呼ぶ。
`R = max(1024, L / 64)` で、`/` は切り捨ての整数除算である。
巻き戻しが最上位に達したら、上限を `L` に戻す(対話的な実行では、その入力の終わりに戻す)。
`cancel` 節の中で深さが、引き上げた上限も超えたときは、その `depth_limit` のエラーを `cancel` 節からの脱出として抑制し、抑制の記録を書く(本書 9.6 節の 4)。
`cancel` 節が終わるとき(最後まで実行したときも、抑制したときも)は、上限をその `cancel` 節を実行する前の値に戻す。
そのため、伝播しているエラーが `depth_limit` なら、入れ子の `cancel` 節も、引き上げた上限のもとで実行する。
`depth_limit` 以外のエラーが伝播している間に `cancel` 節の中で上限を超えて抑制したときや、N の節が継続を破棄して実行した `cancel` 節の中で上限を超えて抑制したときは、上限は `L` に戻る。

既定の上限は `L = 2^20 = 1,048,576` である。
リーダは、上限を変える手段(`keleut run --max-depth N`、`diktor --run-ir --max-depth N`)を持つ。

この値で、WasmGC バックエンドが `L + R` 段の非末尾の再帰に必要なスタックを確保できることは、実測で確かめてある。

Diktor の構文木の評価器(`--run-ir` も `--via-ir` も付けない実行)は、本節の上限に従わない。
その上限は OCaml のスタックで決まる。
深さが `L` を超えるのに構文木の評価器では最後まで実行できるプログラムがあっても、それは上限を処理系に任せた §15.5 の範囲内の違いであり、不具合として扱わない。

Diktor の KIR の評価器(`--run-ir` と `--via-ir`)は本節の上限に従う。
この評価器は非末尾呼び出しのたびに OCaml のスタックも使い、1 段あたりの使用量は、関数の中で次の呼び出しを囲む式の入れ子が深いほど増える。
評価器は、非末尾呼び出しが 4,096 段進むたびに、その呼び出しを新しい OCaml のファイバーで実行する。
OCaml のスタックの上限はファイバーごとに適用されるので、上限が制限するのは 4,096 段分のスタックだけで、段数は制限しない。
それでも、Diktor の KIR の評価器は、次の 3 つの場合に、深さが `L` に達する前に終了することがある。
本書 1 節は、どの場合も、リーダが同じ結果になる保証の対象外としている。

- 4,096 段分のスタックが、ファイバーごとのスタックの上限を超える場合。
  スタックオーバーフローの実行時エラー(終了コード 3)で終了する。
  超えるかどうかは、段数でなく、その 4,096 段の中の式の入れ子の深さで決まる。
  `OCAMLRUNPARAM` の `l` で上限を下げたときや、各段の中の入れ子が極端に深いときに起こる。
- 生きている継続が長い連鎖をなす場合。
  OCaml 5 の GC は継続の連鎖を C のスタックの上で再帰的にたどるので、システムのスタックを使い尽くして SIGSEGV(終了コード 139)で異常終了することがある。
  異常終了するかどうかは GC のタイミングとシステムのスタックサイズで決まり、構文木の評価器でも同じことが起こる。
- マシンのメモリが尽きる場合。
  使うメモリは、段数と各段の入れ子の深さに比例して増える。

### 11.6 1 回の確保の上限

**`N_alloc_max`**:1 回の確保で作れる要素数の上限。
長さを指定する確保(`MutableArray.new` と、文字列を作るプリミティブ)は、確保の前に長さを `N_alloc_max` と比べ、超えていればメモリ不足のエラーにする。
`N_alloc_max` の値は、RustKeleut のすべてのバックエンドで同じにする。

`N_alloc_max = 2^26 = 67,108,864`(要素数)である。
V8 は、WasmGC の配列の長さを、内容がおよそ 1 GiB になる長さまでに制限している。
この上限は要素が 8 バイトの配列で最も小さく、`2^27 − 8` である。
`N_alloc_max` は、それ以下で最大の 2 の冪である。

Diktor には 1 回の確保の上限がない。
Diktor でメモリ不足になるかどうかはマシンの空きメモリで決まり、上限を処理系に任せた §15.5 の範囲内の違いとして扱う。
本書 1 節は、上限を超える確保と、マシンの空きメモリによるメモリ不足の両方を、リーダが同じ結果になる保証の対象外としている。

## 12. テキスト

### 12.1 正準形

`.kirt` は S 式で書く。
`.kirt` とバイナリは 1 対 1 に対応し、相互に変換できる。
相互に変換できるのは、本書 13 節の必須のセクション(id が 0x01 から 0x0B のもの)の内容である。
スキップできるセクション(0x80 以上)はテキストに書かない。

ライタは、本節の正準形だけを出力する。
正準形は一意に決まるので、2 つのテキストが同じかどうかは、バイト単位の比較で判定する。
`diktor --emit-ir-text` と `keleut kir dis` は、どちらも正準形を出力する。
テキストを読む `keleut kir asm` は、正準形を必ず受理する。
正準でない空白の並びを受理するかどうかは、リーダが決めてよい。
空白以外の正準でない書き方(正準形でない文字列のエスケープや、名前の字句に一致するのに文字列で書いた、修飾しない名前など)を受理するかどうかも、リーダが決めてよい。
`keleut kir asm` はどれも拒否する(終了コード 65)。

文字列の表(strings)と blobs の表は、テキストに書かない。
名前とリテラルはテキストの中に直接書き、バイナリの表とその添字は符号化のときに作る。
表の順序は、テキストの内容だけから決まる規則で定める(本書 13 節)。
prims の表も同じで、`extern` のグローバルから作る。

### 12.2 字句

テキストはバイト列で、次の字句からなる。

| 字句 | 表記 |
| --- | --- |
| 括弧 | `(` と `)` |
| 整数 | `0` か、`1`〜`9` で始まる 10 進数字の並び。後者は前に `-` を付けてもよい |
| ビット列 | `0x` に続く 16 桁の 16 進数字(`0`〜`9` と小文字の `a`〜`f`) |
| 文字列 | `"` で囲んだバイト列(下の規則) |
| 名前 | 正規表現 `[A-Za-z_][A-Za-z0-9_]*(\.[A-Za-z_][A-Za-z0-9_]*)*` に一致する表記 |

**文字列の表記**:文字列の各バイト `b` を次のとおりに書く。

- `b` が `"`(0x22)なら `\"`、`\`(0x5C)なら `\\`。
- `b` が 0x20 から 0x7E の、それ以外のバイトなら、そのまま。
- それ以外(0x00〜0x1F、0x7F、0x80〜0xFF)は `\x` と小文字の 16 進数字 2 桁(`\x0a`、`\xe3`)。

UTF-8 の多バイト文字も、バイトごとに `\xHH` で書く。
そのため、正準なテキストは ASCII だけからなる。

**修飾しない名前の表記**:ラベル、コンストラクタ、操作、メソッドの名前は、名前の字句に一致すれば名前として書き、一致しなければ文字列として書く。
シンボル(本書 3 節)とファイルのパスは、常に文字列として書く。
キーワード(`lit`、`tail`、`i32` など)は名前の字句と同じ表記で、置かれた位置で区別する。

**数の表記**:`i32` と `i64` の値と、個数や番号は整数で書く。
`f64` の値はビット列で書く。
そのため、NaN のペイロードと負のゼロもビット列に残る。

### 12.3 インデントと改行

テキストの各要素を**ノード**と呼ぶ。
ノードは括弧で囲んだ並びで、先頭のキーワード、アトム(整数、ビット列、文字列、名前)、子のノードがこの順に並ぶ。
アトムと子が混ざることはなく、アトムはすべて子より前にある。

**葉**:子を持たないノード。
ノードは次の規則で出力する。
ノードの開き括弧の桁を `c` とする。

1. ノードの子がすべて葉なら、ノード全体を 1 行に書く。
   キーワード、アトム、子を 1 個の空白で区切る。
2. それ以外の場合は、1 行目にキーワードとアトムを空白で区切って書く。
   続けて、各子を改行して桁 `c+2` から書き、子の出力にも同じ規則を適用する。
   閉じ括弧は最後の子の閉じ括弧のすぐ後ろに置く。

行の幅では折り返さない。
行末に空白を置かない。
インデントの空白は入れ子の深さに比例するので、正準なテキストのサイズは入れ子の深さの 2 乗に比例して増える。
深さ `d` の入れ子では、構文によって、およそ `d²` から `4·d²` バイトになる。
`N_nest`(本書 13.9 節)に近い深さのプログラムのテキストは、およそ 10〜40 GB になる。
それでもテキストはバイナリと 1 対 1 に対応する。
ライタがテキストを書き終えられないのは、出力先の空き容量かマシンのメモリが足りないときであり、そのライタの出力エラーとして扱う。
改行は LF(0x0A)で、ファイルの最後の行も LF で終える。
最上位のノードは桁 0 から書き、最上位のノードの間に空行を置かない。

### 12.4 ファイルの構成と表の順序

ファイルは、次の最上位のノードをこの順に並べたものである。

1. ヘッダ `(kir 1 0 0)`。3 つの整数は、順にメジャーバージョン、マイナーバージョン、必須機能ビットである。
2. 単位 `(unit …)`。本書 2.1 節の順に書く。
3. 型 `(type …)`。まず付録 A の組み込みの型を付録の順に書き、続けて各単位の型を、単位の順、単位の中では宣言の順に書く。
4. エフェクト `(effect …)`。単位の順、単位の中では宣言の順に書く。
   組み込みの `Heap` と `Blocking` は操作を持たないので書かない。
5. クラス `(class …)`。まず付録 A の組み込みのクラスを付録の順に書き、続けて各単位のクラスを、単位の順、単位の中では宣言の順に書く。
6. インスタンス `(instance …)`。単位の順、単位の中では宣言の順に書く。
7. グローバル `(global …)`。まず付録 A の組み込みの値を付録の順に書き、続けて各単位のグローバルを、単位の順、単位の中では初期化手順の順、初期化手順の中ではその初期化手順に書いた並びの順に書く。
8. 関数 `(fn …)`。下に述べる順に書く。
9. 初期化 `(init …)`。単位ごとに、本書 2.1 節の順に書く(`builtin` も書く)。

関数の順序は次のとおりである。
単位の順、各単位の初期化手順の順に、初期化手順が持つルート関数を並べる。
初期化手順が持つルート関数は、初期化手順の種類ごとに次のとおりである。

- `def_value`、`def_pattern`、`run_exp` では、`thunk` の関数。
- `def_fns` では、種類が `fn` と `dictabs` のグローバルの関数。
  初期化手順に書いた並びの順に並べる。
  `extern` は関数を持たない。
- `def_dictabs` では、グローバルの関数。
- `def_instance` では、実装の関数。
  メソッドを書いた順に並べる。

各ルート関数のすぐ後に、そのルート関数から持ち上げた関数を、生成箇所の番号の順に並べる。
`handle` の生成箇所の関数は、本体、操作節(書いた順)、`return` 節、`cancel` 節の順である。

### 12.5 文法

次の文法は、空白を取り除いた字句の並びに対するものである。
空白と改行は本書 12.3 節の規則で入れる。
`INT` は整数、`BITS` はビット列、`STR` は文字列(`unit` と `init` では単位のキー)、`NAME` は修飾しない名前の表記(名前か文字列)、`SYM` はシンボルの文字列である。
`X*` は 0 個以上の繰り返し、`X+` は 1 個以上の繰り返し、`[X]` は省略できることを表す。

```
file      ::= header unit* type* effect* class* instance* global* fn* init*
header    ::= (kir INT INT INT)
unit      ::= (unit STR (paths STR*))
type      ::= (type SYM (ctor NAME INT)*)
effect    ::= (effect SYM (op NAME INT never|resume runtime|user)*)
class     ::= (class SYM (method NAME INT)*)
instance  ::= (instance SYM SYM SYM (premises INT) (method NAME INT SYM)*)
global    ::= (global SYM builtin)
            | (global SYM extern prim|C STR INT)
            | (global SYM fn SYM)
            | (global SYM dictabs SYM)
            | (global SYM value rep)
fn        ::= (fn SYM kind yield|noyield (params rep*) (locals rep*) (dicts INT) (caps rep*) (result rep)
                 [(pats pat*)] [(guard exp)] exp)
kind      ::= lambda | opclause | retclause | cancelclause | handlebody | thunk | dictabs
rep       ::= bool | i32 | i64 | f64 | str | any
init      ::= (init STR step*)
step      ::= (def_value SYM SYM) | (def_pattern SYM (globals SYM*) pat) | (def_fns SYM+)
            | (def_dictabs SYM) | (def_instance SYM) | (run_exp SYM)

lit       ::= (lit bool true|false) | (lit i32 INT) | (lit i64 INT) | (lit f64 BITS) | (lit str STR)
cap       ::= (local INT) | (env INT) | (dparam INT)
exp       ::= lit | (lit_error lit_range STR) | (local INT) | (env INT) | (global SYM)
            | (construct SYM NAME (field INT exp)*) | (variant NAME exp)
            | (call tail|ntail yield|noyield exp exp*)
            | (method SYM NAME dict dict*) | (opcall SYM NAME dict exp*)
            | (not exp) | (and exp exp) | (or exp exp)
            | (closure SYM cap*) | (dictabs SYM cap*) | (dictapp exp dict*)
            | (let INT exp exp) | (letpat pat exp exp) | (letrec (rec INT exp)+ exp)
            | (seq exp exp exp*) | (match exp clause*)
            | (rec_empty) | (rec_extend NAME exp exp) | (rec_select NAME exp)
            | (rec_restrict NAME exp) | (rec_update NAME exp exp)
            | (perform SYM NAME exp*)
            | (handle tail|ntail SYM (body SYM cap*) (op NAME N|T|G SYM cap*)+
                 [(return SYM cap*)] [(cancel SYM cap*)])
            | (resume tail|ntail exp) | (hole)
clause    ::= (clause pat exp) | (clause pat (guard exp) exp)
dict      ::= (dinst SYM dict*) | (dparam INT) | (env INT) | (drecord (field NAME dict)*)
            | (dvariant (field NAME dict)*) | (dbuiltin SYM SYM)
pat       ::= (wild) | (bind INT) | lit
            | (record closed|open (field NAME pat)*) | (record rest (field NAME pat)* pat)
            | (ctor SYM NAME (field INT pat)*) | (variant NAME pat)
```

各ノードのフィールドの意味は次のとおりである。

- `type` の `(ctor NAME INT)` は、コンストラクタの名前とフィールドの個数である。
  組み込みの型は `ctor` を持たない。
  ユーザの型で `ctor` を持たないのは、右辺を省いた `newtype X` だけである。
  型エイリアスは型の表に現れない。
- `effect` の `(op NAME INT …)` は、操作の名前、引数の個数、返り値の型が `Never` である(`never`)かそうでない(`resume`)か、ランタイムが処理する(`runtime`)かそうでない(`user`)かである。
  `runtime` は、プレリュードの単位の `Console`(シンボル `prelude/Console`)の、引数が 1 個の `write` にだけ付く。
  ほかの単位が宣言した `Console` の操作は、`--no-prelude` のときの起点の単位のものも含めて、どれも `user` である。
  そうした `Console` の操作はトップレベルのエフェクト行に入らないので、型検査に通ったプログラムではユーザの `handle` が処理する。
  本書 4 節の `noyield` の規則でも、同じくプレリュードの `Console` だけを対象にする。
- `class` の `(method NAME INT)` は、メソッドの名前と、メソッド自身の辞書の個数である(本書 7.2 節)。
  メソッドはクラスの宣言の順に並べる。
- `instance` の 3 つの `SYM` は、順に、インスタンスのシンボル、クラスのシンボル、対象の型の先頭にある型構成子のシンボルである。
- `global` の `extern` に続くフィールドは、ABI、実装名(修飾しない元の名前)、受け取って捨てる辞書の個数である。
  `fn` と `dictabs` に続く `SYM` は、そのグローバルの関数のシンボルである。
- `fn` の `(pats …)` と `(guard …)` は種類 `opclause` の関数だけが持ち、`(pats …)` は `opclause` では必ず書く。
- `def_pattern` の `(globals …)` は、パターンが束縛するグローバルの並びである。
- `handle` の `(op …)` は、操作節を書いた順に並べる。

スロットの Rep は関数の `params` と `locals` が持つので、`(let INT exp exp)` は Rep を持たない。

### 12.6 例

例を `doc/ir/examples/` に置く。
各 `.kirt` は、`doc/ir/examples/` を作業ディレクトリにして、同じ名前の `.kel` をファイル名だけで `diktor --no-prelude --emit-ir-text` に渡して書き出したものである。
次は `loop.kel` の関数 `main/loop` である。
`loop` のエフェクト行は一般化した行変数なので、関数も再帰呼び出しも `yield` である。

```
(fn "main/loop" lambda yield
  (params i32 i64)
  (locals)
  (dicts 0)
  (caps)
  (result i64)
  (match
    (opcall "builtin/Eq" eq (dbuiltin "builtin/Eq" "builtin/Int32") (local 0) (lit i32 0))
    (clause (lit bool true) (local 1))
    (clause
      (lit bool false)
      (call tail yield
        (global "main/loop")
        (opcall "builtin/Sub" sub (dbuiltin "builtin/Sub" "builtin/Int32") (local 0) (lit i32 1))
        (opcall "builtin/Add" add (dbuiltin "builtin/Add" "builtin/Int64") (local 1) (lit i64 1))))))
```

## 13. バイナリ

### 13.1 ヘッダとセクションの並び

バイナリの先頭 16 バイトはヘッダで、内容は次のとおりである。
ヘッダの整数は固定長のリトルエンディアンで、`u16le` は 2 バイト、`u32le` は 4 バイトである。
本書 13.3 節の `u32`(uLEB128)は、ヘッダの後ろにあるセクションのサイズとセクションの内容にだけ使う。

| オフセット | サイズ | 内容 |
| --- | --- | --- |
| 0 | 4 | マジックナンバー `00 4B 49 52`(`\0KIR`) |
| 4 | 2 | メジャーバージョン(`u16le`) |
| 6 | 2 | マイナーバージョン(`u16le`) |
| 8 | 4 | 必須機能ビット(`u32le`) |
| 12 | 4 | セクションの個数(`u32le`) |

1.0 のメジャーバージョンは 1、マイナーバージョンは 0 である。
1.0 は必須機能ビットを 1 つも定義しないので、ライタは 0 を書く。

ヘッダの後ろに、セクションを id の昇順に並べる。
各セクションは、id(1 バイト)、内容のサイズ(本書 13.3 節の `u32`)、内容の順に書く。
ファイルは最後のセクションの内容で終わり、その後ろにバイトを置かない。
ヘッダに書くセクションの個数は、スキップできるセクションを含めた、ファイルの中のセクションの個数である。

**必須のセクション**:id が 0x01 から 0x0B の 11 個のセクション。
どのファイルも、必須のセクションを 1 個ずつすべて持つ。
表が空でもセクションは省かない。

**スキップできるセクション**:id が 0x80 以上のセクション。
1.0 は、スキップできるセクションの内容の形式を定めない。
リーダは、スキップできるセクションの内容を調べずに読み飛ばす。
Diktor のライタは、スキップできるセクションを書かない。

id が 0x00 のセクションと、0x0C から 0x7F のセクションは定義しない。

**正準なバイナリ**:必須のセクションだけを持ち、LEB128 をすべて最短のエンコーディングで書いたバイナリ。
テキスト(本書 12 節)と 1 対 1 に対応するのは、正準なバイナリである。
ライタは正準なバイナリを書く。
リーダは、本書 13.3 節の規則を満たす冗長な LEB128 と、スキップできるセクションも受理する。

### 13.2 セクション

| id | セクション | 内容 |
| --- | --- | --- |
| 0x01 | strings | 名前。UTF-8 でなければならない(本書 13.4 節) |
| 0x02 | blobs | `String` のリテラルと元のファイルのパス。任意のバイト列で、NUL と不正な UTF-8 も許す(§4.4) |
| 0x03 | units | 単位のキー、元のファイルのパス(本書 2 節)。順序は初期化の順 |
| 0x04 | types | 名目的な型と、そのコンストラクタとフィールドの個数 |
| 0x05 | effects | エフェクトと、その操作、引数の個数、`never` の印、ランタイムが処理することを表す印 |
| 0x06 | classes | クラスと、そのメソッド、メソッド自身の辞書の個数 |
| 0x07 | instances | インスタンス(本書 7.2 節) |
| 0x08 | prims | このファイルの `extern` のグローバルが使う ABI と実装名。付録 A にない名前も許す |
| 0x09 | globals | グローバルのシンボル、種類(`builtin`、`extern`、`fn`、`dictabs`、`value`)と種類ごとのフィールド |
| 0x0A | functions | 関数の表(本書 6 節)。本体は前順に並べた木で、各ノードは 1 バイトの番号とそのフィールド |
| 0x0B | init | 単位ごとの初期化手順(本書 10 節) |
| 0x80 | producer | 予約。ライタの名前とバージョン、元のファイルのハッシュを置く予定である |
| 0x81 | locations | 予約。ノードの前順の番号から(ファイル、行、桁)を求める表を置く予定である |
| 0x82 | types-debug | 予約。完全な型のテキストを置く予定である |

グローバルが属する単位はシンボルから決まる(本書 3.1 節)ので、globals のセクションは単位のフィールドを持たない。

prims のセクションにあって付録 A にない名前の呼び出しは、読み込みでは拒否せず、呼び出したときに実行時エラー(付録 B の未実装のプリミティブ)にする(§17)。

### 13.3 基本のエンコーディング

セクションの内容は、次の記法の値を並べたものである。

| 記法 | エンコーディング |
| --- | --- |
| `u8` | 1 バイト |
| `u32` | uLEB128。値は 0 以上 2^32 未満 |
| `s32` | sLEB128。値は `i32` の範囲 |
| `s64` | sLEB128。値は `i64` の範囲 |
| `f64` | IEEE 754 の binary64 のビット列を、8 バイトのリトルエンディアンで書いたもの |
| `bool` | `u8`。0 が偽、1 が真で、それ以外の値はエラー |
| `bytes` | 長さの `u32` と、その長さのバイト列 |
| `vec(X)` | 個数の `u32` と、その個数だけ並べた X |
| `str` | strings の表の添字(`u32`) |
| `blob` | blobs の表の添字(`u32`) |
| `rep` | `u8`。`bool` が 0、`i32` が 1、`i64` が 2、`f64` が 3、`str` が 4、`any` が 5 |

個数、長さ、添字、スロットの番号、引数の個数、辞書の個数のような非負の整数は、すべて `u32` で書く。
添字は 0 始まりである。
`f64` はビット列をそのまま書くので、NaN のペイロードと負のゼロも保たれる。

LEB128 のエンコーディングは Wasm と同じ規則に従う。

- `u32` と `s32` の最長のエンコーディングは 5 バイト、`s64` の最長のエンコーディングは 10 バイトである。
  最長のエンコーディングの最後のバイトは、継続ビット(第 7 ビット)を立てない。
- 最長のエンコーディングの最後のバイトのうち、値に使わないビットには次の制約がある。
  `u32` の 5 バイト目は、第 4〜6 ビットが 0 である。
  `s32` の 5 バイト目は、第 4〜6 ビットが第 3 ビット(値の符号)と同じである。
  `s64` の 10 バイト目は、0x00 か 0x7F である。
- ライタは最短のエンコーディングを書く。
  リーダは、上の制約を満たす冗長なエンコーディング(値を変えない 0x80 や 0xFF のバイトを追加したエンコーディング)も受理する。

印のバイト(本書 13.6 節の `call`、`handle` など)は、定義したビットの和である。
定義していないビットが立っていたらエラーである。

### 13.4 表と参照

**strings の表**:次の名前の集まりを、重複を取り除いて、バイト列の昇順に並べたもの。

- 単位のキー。
- 型、エフェクト、クラス、インスタンス、グローバル、関数のシンボル。
- コンストラクタ、操作、メソッドの名前。
- ラベル(レコードとヴァリアントの式とパターン、`drecord` と `dvariant` の項目)。
- `extern` のグローバルの実装名。
- 範囲外のリテラルの表記。

**blobs の表**:式とパターンの `str` のリテラルの値と、単位の元のファイルのパス(`paths`)の集まりを、重複を取り除いて、バイト列の昇順に並べたもの。
ファイルのパスは UTF-8 とは限らないので、blobs に置く。

バイト列の昇順では、先頭から符号なしのバイトとして比べ、一方が他方の先頭部分と等しいときは短いほうを先にする。
strings と blobs の表は、どちらも厳密な昇順であり、どの項目も 1 回以上参照される。
ほかの表の項目が自分のフィールドとして持つ添字(types のセクションのコンストラクタの名前や、units のセクションのキーなど)も参照に数える。
strings の表の項目は UTF-8 でなければならない。
UTF-8 でない名前(単位のキーやシンボルなど、strings の表に入る名前)があるプログラムは、KIR を持たない。
ライタは、そうしたプログラムのテキストもバイナリも書かず、使い方のエラー(終了コード 64)で終了する。
テキストだけを求められたときも同じにするのは、テキストとバイナリが 1 対 1 に対応し、相互に変換できる(本書 12.1 節)からである。
UTF-8 でない名前を書いたテキストは KIR ではないので、テキストのリーダ(`keleut kir asm`)はそれを読み込みエラー(終了コード 65)として拒否する。

**prims の表**:`extern` のグローバルの ABI と実装名の組の集まりを、重複を取り除いて並べたもの。
順序は、ABI の番号(`prim` が 0、`C` が 1)の昇順で、同じ ABI の中では実装名のバイト列の昇順である。
どの項目も、1 個以上の `extern` のグローバルから参照される。

それ以外の表(units、types、effects、classes、instances、globals、functions)の順序は、テキストの最上位のノードの順序(本書 12.4 節)と同じである。
表の項目は、その表の中の位置で指す。
コンストラクタ、操作、メソッドは、それを持つ型、エフェクト、クラスの中の位置で指す。

### 13.5 セクションの内容

各セクションの内容は次のとおりである。

| セクション | 内容 |
| --- | --- |
| strings | `vec(bytes)` |
| blobs | `vec(bytes)` |
| units | `vec(unit)`。`unit` は、キー `str`、元のファイルのパス `vec(blob)` |
| types | `vec(type)`。`type` は、シンボル `str`、`vec(ctor)`。`ctor` は、名前 `str`、フィールドの個数 `u32` |
| effects | `vec(effect)`。`effect` は、シンボル `str`、`vec(op)`。`op` は、名前 `str`、引数の個数 `u32`、印 `u8`(`never` が 0x01、`runtime` が 0x02) |
| classes | `vec(class)`。`class` は、シンボル `str`、`vec(method)`。`method` は、名前 `str`、メソッド自身の辞書の個数 `u32` |
| instances | `vec(instance)`。`instance` は、シンボル `str`、クラス `u32`、対象の型の先頭にある型構成子 `u32`、前提の個数 `u32`、`vec(impl)`。`impl` は、メソッド `u32`(クラスの中の位置)、辞書の個数 `u32`、関数 `u32` |
| prims | `vec(prim)`。`prim` は、ABI `u8`、実装名 `str` |
| globals | `vec(global)`。`global` は、シンボル `str`、種類 `u8`、種類ごとのフィールド |
| functions | 関数の個数 `n`(`u32`)、関数のシンボル `str` を `n` 個、関数の項目を `n` 個 |
| init | `vec(vec(step))`。外側の並びの `i` 番目は、units のセクションの `i` 番目の単位が持つ初期化手順の並びである。外側の並びの長さは単位の個数と同じである |

グローバルの種類ごとのフィールドは次のとおりである。

| 種類 | 番号 | フィールド |
| --- | --- | --- |
| `builtin` | 0 | なし |
| `extern` | 1 | prims の表の添字 `u32`、受け取って捨てる辞書の個数 `u32` |
| `fn` | 2 | 関数 `u32` |
| `dictabs` | 3 | 関数 `u32` |
| `value` | 4 | `rep` |

functions のセクションは、関数のシンボルの並びを関数の項目より前に置く。
globals、instances、init のセクションと関数の本体は、ファイルの中で後ろにある関数も添字で指す。
リーダは、シンボルの並びを先に読んでおけば、どのセクションを読むときも関数の添字からシンボルを求められる。

関数の項目には、次のフィールドをこの順に書く。

1. 種類 `u8`(`lambda` が 0、`opclause` が 1、`retclause` が 2、`cancelclause` が 3、`handlebody` が 4、`thunk` が 5、`dictabs` が 6)。
2. `yield` の印 `bool`(`yield` が 1)。
3. `params` の `vec(rep)`、`locals` の `vec(rep)`、`dicts` の `u32`、`caps` の `vec(rep)`、`result` の `rep`。
4. 種類が `opclause` のときだけ、`pats` の `vec(pat)` と、ガードの有無の `bool`(ガードがあれば、続けてガードの `exp`)。
5. 本体の `exp`。

初期化手順 `step` は次のとおりである。

| 初期化手順 | 番号 | フィールド |
| --- | --- | --- |
| `def_value` | 0 | グローバル `u32`、関数 `u32` |
| `def_pattern` | 1 | 関数 `u32`、グローバルの `vec(u32)`、`pat` |
| `def_fns` | 2 | グローバルの `vec(u32)`(1 個以上) |
| `def_dictabs` | 3 | グローバル `u32` |
| `def_instance` | 4 | インスタンス `u32` |
| `run_exp` | 5 | 関数 `u32` |

### 13.6 式、辞書、パターン

式、辞書、パターンのノードは、1 バイトの番号とフィールドからなる。
ノードは前順に書く。
子の個数は子より前に書く。
番号は、式、辞書、パターンのそれぞれで別に振る。
どの位置にどの種類のノードが来るかは、文法(本書 12.5 節)から決まる。

ノードのフィールドに現れる構成要素は次のとおりである。

| 構成要素 | エンコーディング |
| --- | --- |
| `lit` | 種類 `u8` と値。偽が 0、真が 1(どちらも値は書かない)、`i32` が 2(`s32`)、`i64` が 3(`s64`)、`f64` が 4(`f64`)、`str` が 5(`blob`) |
| `cap` | 種類 `u8`(`local` が 0、`env` が 1、`dparam` が 2)と番号 `u32` |
| `part` | 関数 `u32` と、キャプチャの `vec(cap)` |
| `clause` | ガードの有無 `bool`、`pat`、ガードがあればガードの `exp`、本体の `exp` |

式の番号とフィールドは次のとおりである。

| 番号 | 式 | フィールド |
| --- | --- | --- |

### 13.7 読み込みの検査

リーダは、バイナリを読むときに次の点を検査し、1 つでも満たさなければ、実行せずに拒否する。

1. ヘッダ:16 バイトあること、マジックナンバーが正しいこと、メジャーバージョンが自分のメジャーバージョンと同じであること(マイナーバージョンは問わない。本書 14 節)、必須機能ビットが 0 であること。
2. セクションの並び:id が厳密な昇順であること、定義していない id がないこと、必須のセクションがすべてあること、セクションのサイズがファイルの残りを超えないこと、最後のセクションの後ろにバイトがないこと、ヘッダに書いたセクションの個数が実際の個数と同じであること。
3. エンコーディング:本書 13.3 節の LEB128 の規則を満たすこと、`bool` と種類と番号のバイトが定義した値であること、印のバイトに定義していないビットがないこと。
   必須のセクションは、どれも内容をちょうど読み終えなければならない。
   セクションの終わりを越えて読むのはエラーである。
   個数と長さは、セクションの残りのバイト数を超えてはならない。
4. 表:strings と blobs が厳密な昇順であり、どの項目も参照されること、strings の項目が UTF-8 であること、prims が厳密な昇順であり、どの項目も `extern` のグローバルから参照されること、init のセクションの単位の個数が units のセクションと同じであること。
5. 添字:すべての添字が、指す表の範囲にあること。
   コンストラクタ、操作、メソッドの添字は、それを持つ型、エフェクト、クラスの中の並びの範囲にあること。
6. 個数の下限:`letrec` の項目、`handle` の操作節、`def_fns` のグローバルが 1 個以上で、`seq` の要素が 2 個以上であること。
7. 入れ子の上限(本書 13.9 節)を超えないこと。

### 13.8 検証

リーダは、読み込んだプログラムを次の点で検証し、1 つでも満たさなければ、実行せずに拒否する。
検証は型の健全性を保証しない(本書 1 節)。
検証が検査するのは、型を使わずに計算できる性質だけである。

1. **名前**:単位のキーと、型、エフェクト、クラス、インスタンス、グローバル、関数のシンボルは、表ごとに一意である。
   コンストラクタ、操作、メソッドの名前は、それを持つ型、エフェクト、クラスの中で一意である。
   インスタンスのメソッドの実装の名前も、そのインスタンスの中で一意である。
   テキストはこれらを名前で書くので、重複があると名前から項目を決められないからである。
   型、エフェクト、クラス、インスタンス、グローバル、関数のシンボルは、本書 3.1 節の `単位の鍵/名前` の形式である。
   つまり、シンボルは `/` を 1 個以上含み、最後の `/` の後ろの名前の部分は空でなく、前の部分は units の表にある単位のキーである。
   本節の 12 と 13 と付録 B はシンボルが属する単位のキーを使うので、この形式でないシンボルを許すと、リーダごとに動作が分かれる。
2. **関数を作る箇所**:各関数は、次の表の箇所のちょうど 1 か所で作られ、種類はその箇所に対応する種類である。
   ルート関数の `caps` は空である。

   | 作る箇所 | 種類 |
   | --- | --- |
   | 種類が `fn` のグローバル、`closure` | `lambda` |
   | 種類が `dictabs` のグローバル、インスタンスのメソッドの実装、式の `dictabs` | `dictabs` |
   | `def_value`、`def_pattern`、`run_exp` | `thunk` |
   | `handle` の本体、操作節、`return` 節、`cancel` 節 | `handlebody`、`opclause`、`retclause`、`cancelclause` |

3. **関数のフィールド**:`dicts` は、種類が `dictabs` でなければ 0 である。
   `pats` とガードは、種類が `opclause` の関数だけが持つ。
   `params` の個数は、`dictabs`、`thunk`、`handlebody`、`cancelclause` では 0、`retclause` では 1、`opclause` では操作の引数の個数である。
   `opclause` の `pats` の個数は `params` の個数と同じである。
4. **スロット**:本書 6.4 節の順に束縛する箇所をたどったとき、束縛する番号は `params` の個数から始まって 1 ずつ増え、すべてたどり終えると `params` と `locals` の個数の和に達する。
   `local` の番号はスロットの個数より小さく、`env` の番号は `caps` の個数より小さく、`dparam` の番号は `dicts` より小さい。
   `local` は、式としてもキャプチャとしても、本書 6.4 節のスコープの中にだけ書ける。
5. **キャプチャ**:`closure`、`dictabs`、`handle` の各部分のキャプチャの個数は、作られる関数の `caps` の個数と同じである。
   各キャプチャの Rep(`local` はスロットの Rep、`env` は `caps` の Rep、`dparam` は `any`)は、作られる関数の `caps` の同じ位置の Rep と同じである。
6. **Rep**:`let` と `letrec` が `closure` か `dictabs` を束縛するスロットの Rep は `any` である。
   `def_value g f` では、`g` の Rep と `f` の `result` が同じである。
7. **構文**:`construct` は各フィールドの位置をちょうど 1 回ずつ書く。
   `ctor` のパターンのフィールドの位置は、厳密な昇順で、フィールドの個数より小さい。
   `method` の `o` の個数は、クラスのメソッド自身の辞書の個数と同じである。
   `opcall` のメソッドは、メソッド自身の辞書を持たない。
   `perform` の引数の個数は、操作の引数の個数と同じである。
   `dinst` の前提の個数は、インスタンスの前提の個数と同じである。
   `drecord` と `dvariant` の項目は、ラベルのバイト列の昇順に並ぶ(同じラベルの項目が複数あってもよい)。
   `letrec` の各項目の式は、`closure` か `dictabs` である。
   `(dictapp e d…)` の `e` が `(global g)` か `(dictabs F …)` なら、辞書の個数は本書 7.5 節の規則に合う。
   辞書を書く位置のうち、その辞書が属すべきクラス(以下「求めるクラス」)が名前から決まる位置では、辞書のクラスは求めるクラスと同じである。
   求めるクラスが名前から決まる位置は、`(method C m d o…)` と `(opcall C m d …)` の `d`(クラス `C`)と、`drecord` と `dvariant` の項目(`builtin/Eq`)である。
   その位置の `dinst I` は `I` のクラスが、`dbuiltin C' T` は `C'` が、求めるクラスと同じである。
   `drecord` と `dvariant` は、求めるクラスが `builtin/Eq` の位置にだけ書ける。
   `dinst` の前提、`method` の `o`、`dictapp` の辞書の位置は、求めるクラスがインスタンスと関数の表に書かれていないので検査しない。
   `dparam` と `env` の辞書のクラスも検査しない。
   どの位置の `dbuiltin C' T` も、組 `(C', T)` が付録 A.3 の表にある。
8. **末尾の印**:`call` と `handle` の印は、本書 5.3 節の規則で計算した末尾位置と一致する。
   本書 5.3 節の表の「分類 N の `opclause`」に該当するかどうかは、ファイルに書いた分類ではなく、操作の `never` の印で決める。
9. **`resume`**:`resume` の**持ち主**は、その `resume` が再開する継続を受け取る操作節である。
   `resume` を含む関数の持ち主を、次のとおりに決める。
   `opclause` の関数の持ち主はその関数自身で、`handlebody` の関数の持ち主はそれを作った `handle` を含む関数の持ち主であり、それ以外の関数は持ち主を持たない。
   ただし、`opclause` のガードのフィールドの中の `handle` が作る `handlebody` の関数は、持ち主を持たない。
   自分を作った `handle` を含む関数を順にたどっても `opclause` に達せずに循環する `handlebody` の関数(本体の中の `handle` が互いを作る 2 つの関数など)も、持ち主を持たない。
   `resume` を書けるのは、持ち主のある関数の本体の中だけで、その持ち主は分類 N でない操作節でなければならない。
   `opclause` のガードのフィールドには `resume` を書けない。
   `resume` の印は、本書 5.3 節の背骨の上にあるとき `tail`、それ以外は `ntail` である。
10. **分類**:各操作節の分類は、操作の `never` の印が立っていれば N である。
    そうでなく、その操作節を持ち主とするすべての `resume` の印が `tail` なら T、それ以外は G である(本書 9.2 節)。
11. **インスタンス**:実装の各メソッドはクラスにあり、クラスの各メソッドはちょうど 1 つの実装の項目を持つ。
    実装の項目の順序は、クラスのメソッドの順序と同じでなくてよい(本書 7.2 節)。
    実装の項目の辞書の個数は、クラスのメソッド自身の辞書の個数と同じである。
    実装の関数の `dicts` は、前提の個数と実装の項目の辞書の個数の和である。
12. **単位と初期化**:単位の並びは `builtin`、`prelude` で始まり、`main` で終わる。
    `builtin` の単位は初期化手順を持たない。
    初期化手順は、種類が `builtin` でないグローバルをちょうど 1 回ずつ定義し、`builtin` のグローバルを定義しない。
    初期化手順は、インスタンスをちょうど 1 回ずつ `def_instance` で定義する。
    初期化手順が定義するグローバルとインスタンスのシンボルは、その初期化手順を持つ単位に属する(単位のキーが同じである)。
    初期化手順が定義するグローバルの種類は、次の表のとおりである。

    | 初期化手順 | グローバルの種類 |
    | --- | --- |
    | `def_value` | `value` |
    | `def_pattern` | `value` |
    | `def_fns` | `fn`、`dictabs`、`extern` |
    | `def_dictabs` | `dictabs` |

    `def_pattern` のパターンの `bind` は、グローバルの並びの位置を 0 から 1 ずつ増える順に 1 回ずつ指し、並びのすべてのグローバルを束縛する。
13. **組み込みの表**:types の表は、付録 A.1 の型をその順に、コンストラクタを持たない項目として先頭に置く。
    classes の表は、付録 A.2 のクラスをその順に、付録 A.2 のメソッドを辞書の個数 0 で持つ項目として先頭に置く。
    globals の表は、付録 A.4 の値をその順に、種類 `builtin` の項目として先頭に置く。
    これらの先頭の部分のほかに、単位のキーが `builtin` の型、クラス、グローバルと、種類が `builtin` のグローバルはない。
    単位のキーが `builtin` のエフェクトとインスタンスもない。
    リーダは組み込みの値をシンボルで実装に対応付けるので、付録 A にないシンボルを持つ組み込みの値は実行できない。
14. **操作の印**:操作に `runtime` の印が付くのは、エフェクトのシンボルが `prelude/Console`、操作の名前が `write`、引数の個数が 1 のときだけで、そのときは必ず付く。
    `runtime` の印の付いた操作を持つエフェクトは、`handle` のエフェクトにできない。
    リーダは、`runtime` の操作の `perform` を、ハンドラを探さずにランタイムの直接呼び出しに置き換えてよい(本書 9.4 節)。
    そのため、この 2 つの規則がないと、リーダごとに動作が分かれる。

`extern` のグローバルは KIR の中に Rep を持たないので、検証はプリミティブの引数と結果の Rep を検査しない。

RustKeleut と Diktor は、本書 13.7 節の検査と本節の検証のどちらで拒否したときも、終了コード 65 で終了する。
本書は、拒否するときの診断のメッセージ、メッセージの中の `位置 N` が指す位置、複数の検査を満たさないときにどれを報告するかを定めない。
本書が定めるのは、本書 13.9 節の上限のメッセージだけである。
RustKeleut のリーダと検証器は、メッセージと検査の順序を Diktor に合わせている。
`rustkeleut/conformance/kir-bad/` のテストがメッセージまで比較するのはそのためであり、本書の規則によるものではない。

### 13.9 入れ子の上限

**ノードの深さ**:式、辞書、パターンのノードの入れ子の深さ。
関数の本体、`opclause` のガード、`opclause` の `pats` の各パターン、`def_pattern` のパターンを深さ 1 とする。
式、辞書、パターンの子のノードは、親より 1 深い。
`clause`、`part`、`cap`、`field` のような構成要素はノードに数えない。
たとえば `match` の節のパターン、ガード、本体は、`match` のノードより 1 深い。

**`N_nest`**:ノードの深さの上限。
`N_nest = 100,000` である。
リーダは、深さが `N_nest` 以下のプログラムを受理し、深さが `N_nest` を超えるノードを持つファイルを、読み込みか検証のどちらかで拒否する(終了コード 65)。
この上限で拒否したときの診断は、読み込みでは `処理系の限度: KIR の読み込みで入れ子が深すぎます` を、検証では `処理系の限度: KIR の検証で入れ子が深すぎます` を含む。
リーダは、この上限に達する前に自分のスタックを使い尽くして異常終了してはならない。

深さが `N_nest` 以下のプログラムを受理するというこの規定には、例外が 1 つある。
スタックやメモリを既定より小さく制限したリーダである。
入力が `.kir` のとき(`keleut run FILE.kir`、`keleut kir verify|dis|asm`)、RustKeleut のリーダは、`--native-stack` か仮想メモリの制限(`ulimit -v`)でスタックが小さくなっていると、深さが `N_nest` 以下のノードでも、処理系の限度として拒否することがある(終了コード 65)。
`--native-stack` に合わせて入れ子の上限を下げる動作は、この例外に該当する。
KIR を処理するスレッドを最も小さいスタックでも作れない場合と、読み込み、検証、LIR への変換の間にメモリを確保できなくなった場合も、同じく処理系の限度として終了コード 65 で終了する。
入力が `.kel` で、同じプロセスの中で作った KIR についてこれらが起きた場合は、言語仕様 §15.5 の表の「型検査と変換での拒否」(終了コード 1)に該当する。

この例外を定めても、バージョンは変えない。
本書 14 節の、バージョンを変えない本文の改訂に該当するからである。
理由は 3 つある。
1 つ目に、既定のサイズのスタックとメモリで実行するリーダが受理するプログラムの集合と、KIR の意味とエンコーディングは変わらない。
2 つ目に、対象外にするのは、スタックやメモリを小さく制限したリーダが上限に達する場合だけである。
これは、本書 1 節が保証の対象外にしている、`N_alloc_max` を超える確保や V8 のヒープの枯渇と同じ種類の、資源の上限による例外である。
3 つ目に、`--native-stack` に合わせて入れ子の上限を下げる動作はリーダの現在の動作であり、この例外を定めてもリーダの動作は変わらない。

ライタは、深さが `N_nest` を超えるノードを持つ KIR を書いてはならない。
そのファイルは、どのリーダも拒否するからである。
ライタは、テキストもバイナリも書かずに、処理系の限度として終了コード 1 で終了する。
その診断は `処理系の限度: KIR の書き出しで入れ子が深すぎます` を含む。
Diktor の `--via-ir` も、評価を始めずに、同じ診断を書いて終了コード 1 で終了する。

`N_nest` の値は、20,000 段の `1 + (...)` の式や 20,000 文のブロックより十分に大きい。
Diktor のライタがこれらから書く KIR の深さは、どちらも 20,001 である。

## 14. バージョン

バージョンは、メジャーバージョンとマイナーバージョンの 2 つの数からなり、「1.0」のように書く。
バイナリではヘッダのオフセット 4 と 6(本書 13.1 節)に、テキストではヘッダの 1 番目と 2 番目の数(本書 12.4 節)に置く。
本書は 1.0 である。

1.0 より前の `0.y` は草稿のバージョンで、リーダはライタと同じ `0.y` だけを受理していた。
1.0 では、Diktor と RustKeleut の両方のライタとリーダが、テストのコーパスの全件でラウンドトリップと差分テストに通ることを確かめて、仕様を確定した。

1.0 より後は、バージョンを次の規則で上げる。

- マイナーバージョンで追加してよいのは、スキップできるセクション(id が 0x80 以上)と、必須機能ビットを立てたときだけ使える新しい命令だけである。
  マイナーバージョンは、すでにあるセクション、命令、フィールドの意味とエンコーディングを変えない。
- 意味やエンコーディングを変えるときは、メジャーバージョンを上げる。
- 各マイナーバージョンのフィクスチャ(そのバージョンの KIR のサンプル)は、`rustkeleut/conformance/kir-fixtures/` のマイナーバージョンごとのディレクトリに置き、新しいバージョンができても消さない。

本文を改訂しても、次の 2 つがどちらも変わらなければ、バージョンを変えない。
1 つは、リーダが受理する KIR の集合、KIR の意味、およびセクション、命令、フィールドのエンコーディングである。
もう 1 つは、ライタとリーダの動作である。
診断のメッセージについてリーダに許す範囲を広げる改訂や、誤記や参照の誤りを直す改訂がこれに該当する。
このような改訂は、バージョンの履歴に日付とともに書く。
意味を変える改訂は、誤りを正すものであっても、上の規則に従ってバージョンを上げる。

ライタとリーダは、バージョンを次のとおりに扱う。

- ライタは、自分が従うバージョンのメジャーバージョンとマイナーバージョンを書く。
  本書に従うライタは 1.0 を書く。
- リーダは、メジャーバージョンが自分のメジャーバージョンと同じファイルを、マイナーバージョンを問わずに受理する。
  マイナーバージョンが自分より新しいファイルも受理する。
  マイナーバージョンが追加するのは、スキップできるセクションと、必須機能ビットを立てたときだけ使える命令だけである。
  そのため、未知のマイナーバージョンのファイルも、立っている必須機能ビットが自分の知っているものだけなら読める。
- リーダは、メジャーバージョンが違うファイルを拒否する。
  1.0 のリーダは、草稿の `0.y` のファイルも拒否する。
- リーダは、自分の知らない必須機能ビットが 1 つでも立っているファイルを拒否する(本書 13.7 節の 1)。
  1.0 は必須機能ビットを 1 つも定義しないので、1.0 のリーダは、必須機能ビットが 0 でないファイルを拒否する。
- テキストのマイナーバージョンは、バイナリのヘッダの `u16le` に収まらなければならない。
- リーダがファイルを読んでそのまま書き戻すとき(`keleut kir dis` と `keleut kir asm`)は、読んだファイルのマイナーバージョンを書く。

| そのほか | `__show_int32`、`__panic` |

`extern "C"` の実装名は `sin`、`cos`、`sqrt`、`exp`、`log` の 5 個で、どれも `(Float64) => Float64` である(§17)。

## 付録 B. 実行時エラーの番号とメッセージ

実行時エラーのメッセージには、Diktor の日本語のメッセージを使う。
実行時エラーが最上位に達したら、リーダは標準エラーに `実行時エラー: ` に続けてメッセージを書く。
番号は、本書の中で場面を指すためのもので、バイナリには現れない。
`<値>` は、Diktor が値を表示するときの形式(`diktor/lib/value.ml` の `show`)で書いた値である。
ただし、レコードの中の、ラベルの異なるフィールドを書く順序は、リーダが決める。
リーダは、同じ値を、値の作り方やプログラムのほかの部分によって違う順序で書いてもよい。
同じラベルのフィールドは、最も外側(言語仕様 §7)のものから順に書く。
ラベルがすべて `_item` のレコードは、タプルの記法(言語仕様 §8)で書く。

| 番号 | 場面 | メッセージ |
| --- | --- | --- |
| 1 | `hole` を評価した | `??? に到達しました` |
| 2 | 初期化の前のグローバルを読んだ | `未束縛の変数: <名前>` |
| 3 | `letpat`、仮引数のパターン、`def_pattern` の照合が失敗した | `パターンに値が一致しません: <値>` |
| 4 | `match` のどの節にも一致しない | `match のどの節にも一致しません: <値>` |
| 5 | 範囲外の数値リテラルを評価した | `数値リテラルが範囲外です: <表記>` |
| 6 | 初期化の前のインスタンスからメソッドを選んだ | `<C>[<T>] のインスタンスは宣言より前の位置では使えません(実行はまだ実体を持ちません。インスタンス宣言を使用より前に置いてください)` |
| 7 | 再開済みの継続を再開した | `resume は高々1回しか呼べません(アフィン)` |
| 8 | 節の外で継続を再開した | `resume を節の外で呼び出しました(second-class)` |
| 9 | ハンドラのどの節にも一致しない | `handle のどの節にも一致しません: <操作><値>` |
| 10 | 整数のゼロ除算 | `ゼロ除算です` |
| 11 | `__f64_to_i32`、`__f64_to_i64` に NaN を渡した | `<実装名>: NaN は整数に変換できません` |
| 12 | `__f64_to_i32`、`__f64_to_i64` の結果が範囲外 | `<実装名>: 変換結果が範囲外です: <値>` |
| 13 | `__string_sub` の範囲外 | `__string_sub: 範囲外です` |
| 14 | `__panic` | `panic: <文字列>` |
| 15 | `Array.get`、`MutableArray.get`、`MutableArray.set` の範囲外 | `配列の範囲外です` |
| 16 | `MutableArray.new` に負の長さを渡した | `MutableArray.new: 長さが負です` |
| 17 | 実装のないプリミティブを呼んだ(表示名と実装名が同じ) | `未実装のプリミティブ: <表示名>` |
| 18 | 実装のないプリミティブを呼んだ(表示名と実装名が違う) | `未実装のプリミティブ: <表示名>(実装名 <実装名> が見つかりません)` |
| 19 | メモリ不足 | `メモリ不足です` |

5 番の `<表記>` は、その `lit_error` に書いたリテラルの表記(本書 10.4 節)である。

9 番の `<操作>` は、エフェクトの表示名と操作の名前を `.` でつないだもので、`<値>` は操作の引数をタプルの記法で書いたものである。
エフェクトの表示名は、エフェクトのシンボルから `単位の鍵/` を取り除いた修飾名である。

2 番の `<名前>` は、読んだグローバルのシンボルから `単位の鍵/` を取り除き、末尾の `#n` も取り除いた修飾名である。
module の中から修飾せずに読んだときも、ソースに書いた名前ではなく修飾名を書く(`main/M.h` なら `M.h`)。
Diktor の構文木の評価器も同じ名前を書く。

17 番と 18 番の `<表示名>` は、その `extern` のグローバルのシンボルから `単位の鍵/` を取り除き、末尾の `#n` も取り除いた修飾名である(`main/__no_such#1` なら `__no_such`、`main/M.__no_such` なら `M.__no_such`)。
どちらのメッセージにするかは、この表示名と `extern` の実装名を比べて決める。
等しければ 17 番、違えば 18 番である。

次のものは実行時エラーではなく、標準エラーに書く抑制の記録である(本書 9.6 節の 4)。

| 場面 | メッセージ |
| --- | --- |
| `cancel` 節の中の脱出を抑制した | `cancel 節で例外が抑制されました: …` |

実行時エラーを抑制したときの記録の「…」は、付録 B のメッセージである(`実行時エラー: ` は付けない)。
その中の `<値>` も、本付録の冒頭に書いた `<値>` の規則(ラベルの異なるフィールドを書く順序はリーダが決める)に従う。

`depth_limit`(本書 11.1 節)のメッセージは `論理的な深さが限度 <L> を超えました` である。
`<L>` は上限 `L` の 10 進表記で、予備の深さ `R`(本書 11.5 節)を足さない値である。
`depth_limit` が最上位に達したら、リーダは、ほかの実行時エラーと同じく、標準エラーに `実行時エラー: ` に続けてこのメッセージを書き、終了コード 3 で終了する。
