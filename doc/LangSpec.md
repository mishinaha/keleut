# Keleut 言語仕様

## 1. 適用範囲

本書は、現在の Keleut の構文、型規則、評価規則および標準環境を定める。
対象は、1 個以上のソースファイルからなるプログラムである。
標準環境は、すべてのソースファイルが暗黙に import する（§15.4）。
まだ使えない構文や実行機能は、各節に制限として書く。
外部関数や穴（§5.6）を含むプログラムは、型検査に通っても最後まで実行できるとは限らない。
`doc/sample.kel` は、言語の設計を注釈つきのプログラムで示す規範であり、まだ実装していない設計（並行処理のエフェクトなど）と未決の点も含む。
本書は、現在の処理系が実装している言語を定め、`doc/sample.kel` が決めていない点も決める。
両者が食い違うときは `doc/sample.kel` を規範とし、本書と処理系を直すか、`doc/sample.kel` を改めて解消する。

**型**：値が属する集合と、その値に許される操作を表すもの。
**エフェクト**：式を評価したときに起きる、出力や可変状態の読み書きなどの作用。
**行**：ラベルとその型を並べたもの。
レコード型、構造的ヴァリアント型、エフェクト行を表すのに使う。
**行変数**：行のうち、まだ決まっていない部分を表す変数。
行変数を持つ行を「開いた行」、持たない行を「閉じた行」と呼ぶ。

## 2. 字句

### 2.1. ソース形式

ソースは UTF-8 で書く。
UTF-8 として正しくないバイト列を含むソースは、字句エラーになる。
改行は LF である。
文字列の外では、空白、タブ、CR を区切りとして扱うので、CRLF も改行として働く。
BOM（U+FEFF）は、文字列とコメントの中を除き、どの位置にあっても字句エラーになる。
ファイルの先頭にある BOM も例外ではない。

ファイルの先頭行に限り、`#!` で始まる行を置ける。
この行はプログラムの意味に影響しない。

`//` から行末までは行コメント、`/*` から `*/` まではブロックコメントである。
ブロックコメントは入れ子にできる。
改行を含むブロックコメントは、文の区切り（§2.3）を判定するときには改行と同じに扱う。

### 2.2. 識別子

識別子は ASCII の英字、数字、アンダースコアからなり、数字では始められない。
大文字と小文字は区別する。

| 用途 | 先頭文字 | 例 |
| --- | --- | --- |
| 値、関数、レコードのラベル | 英小文字または `_` | `value`、`with_file`、`_item` |
| 型、コンストラクタ、モジュール、エフェクト、型クラス | 英大文字 | `List`、`Cons`、`Console` |
| エフェクトの操作 | 英小文字 | `write`、`print` |
| 型パラメータ | 英字または `_` | `A`、`E`、`h` |
| `run` のリージョン変数 | 英小文字または `_` | `h`、`heap` |

単独の `_` は識別子ではない。
パターンではワイルドカードを、型では型構成子の引数の穴（`List[_]` など）を表す。
構造的ヴァリアントのラベルは、`#Even` のように `#` の後ろに大文字で始まる名前を続けて書く。

次の語は予約語であり、レコードのラベルを含め、識別子を書く位置には使えない。

```text
and case class effect else extends extern false fn from handle if
import instance let match module newtype perform pub rec resume run
then true type val with
```

`return`、`cancel`、`Type`、`EffectRow` は予約語ではなく、特定の文脈でだけ特別な意味を持つ。
ただし `return` と `cancel` はハンドラの節の名前と重なるため、エフェクトの操作名には使えない。

### 2.3. 文の区切り

宣言と式文は、セミコロンか改行で区切る。
トップレベルとブロックの中では、改行の直前のトークンが文を終えられ、直後のトークンが文を始められる場合に、その改行を区切りとみなす。
空行や余分なセミコロンを置いてもよい。

文を終えられるトークンは、識別子、リテラル、構造的ヴァリアントのラベル、閉じ括弧、`???` である（付録 A.3）。
次の行が二項演算子、`.`、`\`、`match`、`handle`、`then`、`else`、`and`、`extends`、`|`、`case`、`import` で始まる場合、その改行は区切りにならず、前の行の文が続く。
行頭の `if` は条件式（§5.8）の始まりであり、新しい文を始める。
前の行に続くトークンと、文を始められるトークンの一覧は付録 A.3 にある。
行頭の `(` は、前の行に続く関数呼び出しとは読まず、新しい文の始まりとする。
前置の `-` や負の数値リテラルで新しい文を始めるときは、前の文との間にセミコロンを置く。

丸括弧、角括弧、レコード、レコード型、エフェクト行、`import` の直後の波括弧の中では、改行を文の区切りにしない。
ただし、それらの中にさらにブロックを書いた場合、そのブロックの中では上の規則で改行を区切る。
`case` から節の `=>` までの間（パターンとガード）で改行しても、文は区切られない。

末尾ブロック（§5.5）の `{` は、直前の `)` や名前と同じ行に書く。
トップレベルとブロックの中で `{` を次の行に書くと、改行が文を区切り、`{` は新しい文を始める。
このとき、`{ x => ... }` と `{ case ... }` は構文エラーになり、それ以外の `{ ... }` は §5.4 の表に従って読む独立した式文になる。
丸括弧、角括弧、レコードの中のように改行を文の区切りにしない位置では、`{` を次の行に書いた末尾ブロックは構文エラーになる。

`match` と `handle` の節を並べる波括弧の中でも、改行はブロックの中と同じ規則で区切りとみなす。
節の区切りは `case` 自身であり、節の本体の後ろに区切りは置けないので、節の本体の式の後ろで区切りになる改行は構文エラーになる。
そのため、節の本体に書いた呼び出しの末尾ブロックの `{` を次の行に書くと、中身によらず構文エラーになる。

カンマで区切るリストでは、最後の要素の後にもカンマを置ける。
ただし、`...rest` と `extends R` の後ろには置けない。

## 3. 型

### 3.1. 型の形

基本型は `Boolean`、`Int32`、`Int64`、`Float64`、`String` である。
`Unit` は空レコード型 `{}` の別名であり、その値は `{}` とも `()` とも書ける。
`Never` はコンストラクタを持たない型であり、通常の方法では値を構築できない。
返り値の型が `Never` である操作は、再開しない操作になる（§13.1）。

| 型の形 | 意味 |
| --- | --- |
| `List[Int32]` | 型構成子への型引数の適用 |
| `(A, B) => C @ E` | 引数が 2 個、返り値が `C`、エフェクト行が `E` の関数 |
| `{x: A, y: B}` | 閉じたレコード型 |
| `{x: A extends R}` | 行変数 `R` を持つレコード型 |
| `(A, B)` | 2 要素タプル型 |
| `#Ok(A) \| #Err(String)` | 構造的ヴァリアント型 |

関数の型は引数の個数を含む。
次の 3 つは、上から順に 2 引数の関数、2 要素タプルを 1 個受け取る関数、関数を返す 1 引数の関数であり、互いに異なる型である。

```text
(A, B) => C
((A, B)) => C
(A) => (B) => C
```

型の位置の括弧は、式の `(e)` やパターンの `(p)`（§11.1）と同じく、型をまとめるだけである。
`(A)` は `A` と同じ型を表し、1 要素タプル型は `(A,)` と書く。
矢印型では、`=>` の左の括弧が引数リストを表す。
`@` は最も近い矢印に付く。
外側の矢印に `@` を書くときは、内側の矢印を括弧で囲んで `(A) => ((B) => C) @ E` と書く。
関数束縛の返り値の型に矢印型を書くときも、その矢印に付く `@` と、束縛した関数自身の `@` は別のものである。
`let f(x: A): (B) => C @ E` の `@ E` は返り値の矢印に付き、関数自身の行は `let f(x: A): ((B) => C) @ E` のように返り値の型を括弧で囲んで書く。
処理系が型を表示するときも、外側の矢印の行を表示する場合は、返り値の矢印を括弧で囲む。

### 3.2. 型パラメータ

関数や型の名前の後ろには、`[A, B]` のような型パラメータのリストを書ける。
関数を使うときは、処理系が型引数を推論する。
呼び出しで型引数を明示する構文はない。

型パラメータは、特定の具体型を指定するものではない。
本体は、型パラメータにどの型が入っても型検査に通らなければならない。
たとえば `[A](x: A): A` の本体で、`x` を整数として扱うことはできない。

**カインド**：型や型構成子の種類。
型構成子であれば、どの種類の引数を取り、どの種類の結果を返すかを表す。
値の型のカインドは `Type` であり、行は行のカインドを持つ。
エフェクト行の別名を宣言するときは、カインドを `EffectRow` と注記する（§3.3）。
レコードやヴァリアントの行変数も、カインドの上で値の型と区別する。

`F[_]` は型引数を 1 個取る型パラメータ、`F[_, _]` は 2 個取る型パラメータを表す。
このとき、各引数と結果のカインドは `Type` である。
型パラメータにカインドを直接書く構文は、この形のほかにはない。

`[_]` を付けない型パラメータのカインドは、型注釈や型宣言の中でそのパラメータを使う位置から決まる。
型宣言のパラメータでは、同じ宣言群にある型の本体での使い方も手がかりにする。
値の本体での使い方は考慮しない。
手がかりがなければ `Type` とする。
1 個のパラメータを、値の型の位置と行の位置の両方で使うことはできない。

型引数は、対応するパラメータのカインドに従って読む。
次の例の `Callback` のパラメータ `E` は `@` の右に現れるので、行のカインドを持つ。
そのため `Callback[{}]` の `{}` は空のエフェクト行を、`Box[{}]` の `{}` は空レコード型を表す。

```keleut
newtype Callback[E] = Callback(() => Unit @ E)
newtype Box[A] = Box(A)

let callback: Callback[{}] = Callback(fn() => ())
let box: Box[{}] = Box(())
```

### 3.3. 型エイリアス

`type` は型に別名を付ける。
別名は透過的であり、処理系は別名と、それを展開した型を同じ型として扱う。
別名を使うときは、宣言と同じ個数の型引数を渡す。
型エイリアスは再帰できず、部分適用もできない。

```keleut
type Point = {x: Float64, y: Float64}
type Pair[A, B] = (A, B)
type Output: EffectRow = {Print, Console}
```

エイリアスのカインドは、`type Output: EffectRow` のように名前の後ろに注釈する。
注釈を省略すると `Type` になる。
`EffectRow` の別名を書けるのは、`@` の後ろ、エフェクト行の要素、`EffectRow` の別名の右辺、行を取る型引数の位置に限る。
関数の引数型、返り値型、レコードのフィールド型など、値の型を書く位置には使えない。

### 3.4. 型の一致

2 つの型が一致するのは、型構成子、引数の個数、各引数の型、関数であればエフェクト行がすべて一致する場合である。
ただし、関数を呼び出すとき、関数を名前で参照するとき、関数型を要求する位置に関数を置くときは、閉じたエフェクト行の尾部を開いてから一致させる（§13.2）。
数値型の間の暗黙の変換はない。
レコードの余分なフィールドを捨てて一致させる部分型付けもない。
余分なフィールドを持つレコードを受け取る関数は、行変数を使って書く（§7.1）。

行の比較では、異なるラベルの並び順は問わない。
一方、同じラベルが複数あるときは、その個数と、同じラベルどうしの順序を区別する。
たとえば `{x: Int32, y: String}` と `{y: String, x: Int32}` は同じ型だが、`{x: Int32, x: String}` と `{x: String, x: Int32}` は異なる型である。

## 4. リテラル

### 4.1. 真偽値

`true` と `false` は `Boolean` の値である。
他の型の値を真偽値として暗黙に扱う規則はない。

### 4.2. 数値

整数は、10 進のほか、`0x`（16 進）、`0o`（8 進）、`0b`（2 進）で始まる形でも書ける。
数字の間には、桁の区切りとして `_` を入れられる。
数字の後ろに置いた `_` も、字句としては受ける（付録 A.2）。
浮動小数リテラルは、小数点か、`e` または `E` に続く 10 進の指数を含む。
指数には `+` か `-` を付けられるが、指数の中には `_` を入れられない。

```keleut
let decimal = 1_000
let hexadecimal = 0xff
let octal = 0o17
let binary = 0b1010
let wide = 42i64
let fraction = 1.5
let exponent = 1.5e-3
let trailing_dot = 1.
let negative = -1
```

`.5` のように小数点で始まる形は書けない。
`1.`、`1.e5`、`1.f64` は浮動小数である。
`1.foo` は数値に対するフィールド選択にはならない。
括弧で囲まない数値リテラルに付けた `-` は、そのリテラルと合わせて 1 個の負の数値リテラルになる。
`-` と数値の間に空白を置いても同じである。
すでに負の数値リテラルにさらに付けた `-` は畳まず、前置の演算子として扱う。
それ以外の `-`（括弧で囲んだリテラルや、変数や一般の式の前に書いた `-`）は前置の演算子であり、`Neg.neg` を呼び出す（§12.4）。
たとえば `-2147483648` は `Int32` の最小値を表すが、`-(2147483648)` は範囲を超える 10 進の整数リテラルを含むので、そのリテラルを評価したときに実行時エラーになる。

数値型と、それぞれに対応する接尾辞を次に示す。

| 型 | 表現 | 接尾辞 |
| --- | --- | --- |
| `Int32` | 32 ビット符号付き整数 | `i32` |
| `Int64` | 64 ビット符号付き整数 | `i64` |
| `Float64` | IEEE 754 の 64 ビット浮動小数 | `f64` |

接尾辞のない整数リテラルの型は、文脈によって `Int32` か `Int64` に決まる。
文脈で型が決まらないまま束縛を一般化するときは、`Int32` とする。
トップレベルの宣言と式文の終わりまでに型が決まらない整数リテラルの型も、一般化するかどうかによらず `Int32` とする。
一般化しない束縛（§6.2）の型を通して後の宣言や式文に残ったリテラルの型も、その宣言や式文の終わりで `Int32` に決まる。
この既定化は、制約の付いた型変数を後で決める規則（§6.2）によらず、トップレベルの宣言と式文ごとに行う。
浮動小数リテラルの型は `Float64` である。
数値リテラルの型を決めないまま多相にすることはない。
整数の字面に `f64` を付けることはできる。
逆に、小数点や指数を持つ字面に整数の接尾辞は付けられない。

`Integral` と `Fractional` は、数値リテラルの型に付く組み込みの条件であり、名前は予約されている。
利用者がこれらを型クラスとして宣言したり、制約やインスタンスを書いたりすることはできない。
`Int8`、`Int16`、符号なし整数型、`Float32` はない。
これらの名前は予約しておらず、利用者が型の名前として宣言できる。
表にない接尾辞（`i8`、`u32`、`f32` など）を付けた数値リテラルは、字句としては 1 個の数値に切れるが（付録 A.2）、型検査で拒否する（§15.5）。

10 進の整数リテラルが型の符号付きの範囲を超えると、そのリテラルを評価したときに実行時エラーになる。
2 進、8 進、16 進の整数リテラルでは型のビット幅をすべて使え、最上位ビットを符号ビットとして読む。
たとえば `0xffffffffi32` の値は `-1` である。
2 進、8 進、16 進の整数リテラルが型のビット幅を超える場合も、そのリテラルを評価したときに実行時エラーになる。
パターン（§11.1）に書いた整数リテラルは評価しない。
パターンの整数リテラルが照合する値の型で読めない（10 進では符号付きの範囲を、ほかの基数ではビット幅を超える）ときは、型エラーになる。

### 4.3. 数値演算

整数の加算、減算、乗算、符号反転で桁あふれが起きると、結果は型のビット幅で折り返す。
整数の除算はゼロ方向に切り捨てる。
型の最小値を `-1` で割った結果も、その型の最小値に折り返す。
整数をゼロで割る除算と剰余は、実行時エラーになる。
剰余は `%` で求める（§12.4）。
整数の `a % b` の値は `a - (a / b) * b` であり、0 でなければ符号は `a` と同じになる。

浮動小数の演算は、NaN や正負の無限大を結果として返すことがある。
浮動小数のゼロ除算も、整数と違ってエラーにはならず、これらの値を返す。
比較の一方が NaN のとき、`==`、`<`、`<=`、`>`、`>=` は `false` を、`!=` は `true` を返す。
`0.0` と `-0.0` は等しい。
NaN と無限大を直接書くリテラルはない。

数値型を変換するには、次の関数を明示的に呼ぶ。

| 関数 | 変換 |
| --- | --- |
| `__i32_to_i64` | `Int32` から `Int64` |
| `__i32_to_f64` | `Int32` から `Float64` |
| `__i64_to_i32` | `Int64` から `Int32`。下位 32 ビットを残す |
| `__i64_to_f64` | `Int64` から `Float64`。必要なら丸める |
| `__f64_to_i32` | `Float64` から `Int32` |
| `__f64_to_i64` | `Float64` から `Int64` |

浮動小数から整数への変換は、ゼロ方向へ切り捨てる。
NaN、無限大、および切り捨てた結果が変換先の範囲に収まらない値を変換すると、実行時エラーになる。

### 4.4. 文字列

文字列リテラルは二重引用符で囲む。
改行をそのまま含めてもよい。
文字列の中の CR は、値の一部としてそのまま残る。

使えるエスケープは `\n`、`\t`、`\r`、`\a`、`\b`、`\f`、`\v`、`\\`、`\"`、`\'`、`\uXXXX`、`\UXXXXXXXX` である。
`\uXXXX` と `\UXXXXXXXX` は、コードポイントをそれぞれ 4 桁と 8 桁の 16 進数で指定する。
サロゲートや、U+10FFFF を超える値を指定すると字句エラーになる。
`\uXXXX` と `\UXXXXXXXX` は、指定したコードポイントを UTF-8 で符号化した 1〜4 バイトになる。
`\u0000` は値 0 の 1 バイトになる。
エスケープを使わずに書いた文字は、ソースの UTF-8 のバイト列のまま値になる。

`String` はバイト列として扱い、比較、連結、切り出しもバイト単位で行う。
長さや部分文字列の位置は、Unicode の文字数ではなくバイト数で数える。
切り出す位置は、UTF-8 の文字の境界になくてもよい。
そのため、切り出した結果が UTF-8 として正しくないバイト列になることもあり、そのバイト列も `String` の値である。
`echo` と `echoln`（§16.3）は、文字列のバイト列を検査も変換もせずに標準出力に書く。
1 文字を表す `Char` 型はない。

## 5. 式

### 5.1. 評価順序

Keleut の評価は正格である。
関数を呼び出す前にすべての引数を評価し、`let` の右辺は束縛するときに評価する（使うたびに評価する値束縛は §6.4）。
評価を遅らせるには、引数のない無名関数（§5.3）で包み、必要なときに呼び出す。

関数呼び出しでは、呼び出し先の式を評価し、次に引数を左から右へ評価してから、関数を呼び出す。
二項演算子の両辺、タプルの要素、コンストラクタの引数、レコードのフィールドも、左から右へ評価する。
コンストラクタの名前付き引数は、宣言でのフィールドの順ではなく、呼び出しに書いた順に評価する。

レコードの拡張では、追加するフィールドを先に評価し、`extends` の右の式を最後に評価する。
レコードの更新では、基底のレコードを先に評価し、次に新しい値を書いた順に評価する。
`match` は、照合対象の式を 1 回だけ評価してから節を調べる。
条件式（§5.8）は、条件を 1 回だけ評価し、`then` と `else` の後ろの式のうち選んだ一方だけを評価する。

`&&` と `||` は短絡評価する。
左辺だけで結果が決まる場合、右辺は評価しない。
ただし型検査は、右辺が評価されない場合も含めて両辺に行う。

### 5.2. 演算子

演算子の優先順位を、結合の強い順に示す。

| 優先順位 | 構文 | 結合規則 |
| --- | --- | --- |
| 1 | 呼び出し（末尾ブロック（§5.5）を含む）、`.`、`\` | 左結合 |
| 2 | `!`、前置の `-` | 前置 |
| 3 | `*`、`/`、`%` | 左結合 |
| 4 | `+`、`-` | 左結合 |
| 5 | `==`、`!=`、`<`、`<=`、`>`、`>=` | 連鎖不可 |
| 6 | `&&` | 左結合 |
| 7 | `\|\|` | 左結合 |
| 8 | 後置の `match`、`handle` | 左から適用 |
| 9 | `fn(...) => ...`、`if ... then ... else ...` | 本体、`else` の後ろの式を右に取る |

比較は連鎖できないので、`a < b < c` とは書けない。
`match`、`handle`、条件式は算術演算より結合が弱いため、その結果を算術演算に使うときは括弧で囲む。
利用者が新しい演算子を定義したり、優先順位を変えたりすることはできない。

### 5.3. 関数

無名関数は `fn(x, y) => e` と書く。
引数のない関数は `fn() => e` と書く。
引数にはパターンと型注釈を書ける。
関数の本体に現れる名前は、その関数を定義した位置で有効な束縛を指す。

関数呼び出しは `f(a, b)` と書く。
末尾ブロック（§5.5）を除き、引数を空白で並べる呼び出しはない。暗黙のカリー化や部分適用もない。
関数の引数は位置で対応させる。
`f(x = 1)` のような名前付き引数は、コンストラクタ（§10.2）以外では使えない。

### 5.4. ブロック

ブロックは、波括弧で囲んだ文の並びである。
中には `let`、`let rec`、式文、`with` を書ける。
型、モジュール、エフェクト、型クラスの宣言は書けない。

最後の文が式なら、その値がブロックの値になる。
最後の文が束縛なら、ブロックの値は `Unit` になる。
途中の式文の値は捨てる。
最後の式の後ろにセミコロンを置いても、ブロックの値はその式の値のままである。

式の位置にある `{` がレコードとブロックのどちらを始めるかは、その直後の形で決まる。

| `{` に続く形 | 解釈 |
| --- | --- |
| `}` | 空レコード |
| 識別子の後ろに `=`、`,`、`with`、`extends` | レコード |
| `extends` | レコード |
| フィールド名の後ろに `:` | レコード型の形 |
| それ以外 | ブロック |

このため `{x}` はレコードではなく、変数 `x` の値を返すブロックである。
フィールドが 1 個のレコードは、`{x = x}` か `{x,}` と書く。
型、エフェクト行、宣言の本体、パターンに現れる波括弧は、この表ではなく、それぞれの文脈の規則で読む。

### 5.5. 末尾ブロック

**末尾ブロック**：関数呼び出しの最後の引数を、括弧の外に波括弧で書いた無名関数。
末尾ブロックは、次の 3 つの位置の直後に書ける。

| 位置 | 例 | 意味 |
| --- | --- | --- |
| 呼び出しの `)` | `g(a, b) { ... }` | `g(a, b, 関数)` |
| `.` で選んだ、小文字で始まる名前 | `M.f { ... }`、`r.f { ... }` | `M.f(関数)`、`r.f(関数)` |
| 小文字で始まる識別子 | `f { ... }` | `f(関数)` |

ほかの式の後ろには書けない。
`(g(a)) { ... }` のように括弧で囲んだ式の後ろや、コンストラクタ（§10.2）、構造的ヴァリアント（§9）、`perform`（§13.3）、`resume`（§13.5）の後ろに書くと、構文エラーになる。
1 個の呼び出しに付けられる末尾ブロックは 1 個までで、`f { a } { b }` は構文エラーになる。
末尾ブロックを付けた呼び出しは、§5.2 の優先順位 1 の式である。
そのため、`f(a) { ... }.x` は呼び出しの結果からフィールドを選び、`f(a) { ... }(b)` は呼び出しの結果を `b` で呼び出す。

渡す関数は、波括弧の中身の形で決まる。

| 中身 | 渡す関数 |
| --- | --- |
| `{ 文の列 }` | `fn() => { 文の列 }` |
| `{ x => 文の列 }` | `fn(x) => { 文の列 }` |
| `{ case p => e ... }` | 引数を 1 個受け取り、それを照合対象として節を調べる関数 |

文の列には、ブロック（§5.4）と同じものを書ける。
`{ x => 文の列 }` の文の列は空でもよく、`{ x => }` は本体の値が `Unit` の関数を渡す。
`{ x => 文の列 }` の引数は、小文字で始まる識別子 1 個に限る。
パターン、型注釈、2 個以上の引数は書けない。
`{ _ => e }` とも書けない。
引数のない関数は `{ e }`、受け取った引数を捨てる関数は `{ case _ => e }` と書く。
2 個以上の引数を取る関数や、引数に型注釈を書く関数は、`fn(...) => ...` で書いて括弧の中に渡す。

`{ case ... }` の節には、`match`（§11.2）と同じ規則を適用する。
網羅性の検査と、構造的ヴァリアントの照合対象の行を閉じる規則も、`match` と同じく働く。
`{ case (a, b) => e }` は、2 要素のタプルを 1 個受け取る関数であり、引数を 2 個取る関数ではない（§3.1）。

中身が §5.4 の表でレコードやレコード型に分類される形の末尾ブロックは、構文エラーになる。
空の `{}` もレコードなので、末尾ブロックとしては書けない。
何もしない関数は `{ () }` と書く。
`{ x => ... }` と `{ case ... }` は、§5.4 の表ではブロックに分類されるが、末尾ブロックとしてだけ書ける。
末尾ブロックの位置の外に書くと、構文エラーになる。

末尾ブロックは最後の引数なので、ほかの引数をすべて評価した後に関数の値になる（§5.1）。
末尾ブロックの本体は無名関数の本体であり、`resume` の制限（§13.5）と、`run` の本体から除く規則（§14.1）を受ける。
末尾ブロックを付けた呼び出しは関数呼び出しなので、構文上の値（§6.2）ではない。

`with`（§6.5）は残りの文全体を、末尾ブロックは `}` までを最後の引数にする。
`with` の右辺に末尾ブロックを付けた呼び出しを書くと、`with` が作る無名関数は末尾ブロックの後ろの引数になる。

```keleut
let call_with[A, B, E](x: A, f: (A) => B @ E): B @ E = f(x)
let twice[E](f: () => Unit @ E): Unit @ E = {
  f()
  f()
}
let n = call_with(20) { x => x + 1 }
let s = call_with(Some(n)) {
  case Some(x) => show(x)
  case None => "none"
}
twice { echoln(s) }
```

### 5.6. 穴

**穴**：`???` と書く、どの型にもなれる式。
型検査は穴を周囲が要求する型の式として扱うが、評価が穴に達すると実行時エラーになる。
再開しない操作の `perform` の式も、周囲が要求する型の式として扱う（§13.3）。
関数の本体に書いた穴は、その関数を呼び出すまで評価しない。

### 5.7. 末尾呼び出し

**末尾呼び出し**：関数の本体の末尾位置にある関数呼び出し。
末尾呼び出しでは、呼び出し先の関数が返す値が、そのまま呼び出し元の関数の値になる。
処理系は、末尾呼び出しに入る時点で、呼び出し元の関数の評価のために保持していた情報を捨てる。
そのため、末尾呼び出しを何回続けても、それによって使う領域は増えない。
Keleut には反復の構文がなく、反復は再帰で書く（§6.3）。
末尾呼び出しだけでつながった再帰は、回数によらず一定の領域で評価できる。

関数の本体の**末尾位置**は、次の規則で決まる。

- 関数の本体は末尾位置にある。
  関数の本体には、無名関数（§5.3）、末尾ブロック（§5.5）、関数の定義（§6.1、§6.3）、インスタンスのメソッド（§12.2）の本体を含む。
- 括弧で囲んだ式 `(e)` が末尾位置にあれば、`e` も末尾位置にある。
- ブロック（§5.4）が末尾位置にあり、最後の文が式であれば、その式も末尾位置にある。
  `with`（§6.5）を含むブロックは、§6.5 の書き換えの後の形で判断する。
  書き換えると、`with` の右辺の関数呼び出しが、その位置のブロックの最後の式になる。
- `match`（§11.2）が末尾位置にあれば、各節の本体も末尾位置にある。
- 条件式（§5.8）が末尾位置にあれば、`then` の後ろの式と `else` の後ろの式も末尾位置にある。
- `a && b` や `a || b` が末尾位置にあれば、`b` も末尾位置にある。
- `run h { ... }`（§14.1）が末尾位置にあれば、その本体のブロックも末尾位置にある。
- ハンドラ式（§13.4）が末尾位置にあれば、その `return` 節の本体も末尾位置にある。
- ハンドラ式（§13.4）が末尾位置にあれば、再開しない操作（§13.1）の操作節の本体も末尾位置にある。
  処理系は、その本体を評価する前に中断していた計算を破棄する（§13.6）。
  `return` 節の本体も再開しない操作の節の本体も、同じハンドラの操作節が末尾位置にない `resume` で再開した計算の中で評価されるときは、その `resume` の後ろの計算が残るので、末尾位置にない。

これ以外の位置は末尾位置ではない。
とくに、次のものは末尾位置にない。

- 関数呼び出しの呼び出し先と引数、演算子のオペランド、タプルの要素、コンストラクタの引数、レコードのフィールド、フィールドの選択の対象。
- `match` の照合対象とガード、条件式の条件、`let` の右辺、ブロックの最後でない文。
- ハンドラ式の本体。
  再開する操作の操作節と `cancel` 節の本体の中にも、それを囲む関数に対する末尾位置はない。
- `perform` の引数と、`resume` の引数。

**末尾 `resume`**：操作節の本体を根とし、関数の本体の代わりに上の規則でたどったとき、末尾位置にある `resume`。
操作節の本体そのものが `resume(v)` である場合も含む。
節の本体の中のハンドラ式の本体にある `resume` は、末尾 `resume` ではない。
処理系は、末尾 `resume` で継続を再開する前に、その操作節の評価のために保持していた情報を捨てる。
再開した計算が値を返すと、その値がそのままハンドラ式の値になる。
そのため、操作のたびに末尾 `resume` で再開するハンドラの下では、操作を何回起こしても、それによって使う領域は増えない。

次のものは保証しない。
処理系は、これらを一定の領域で評価してもよい。

- 演算子の適用。
  算術と比較の演算子は型クラスのメソッドを呼ぶ（§12.4）が、末尾位置にあっても末尾呼び出しとはしない。
- ハンドラ式の本体の中の呼び出しと `resume`。
  本体を評価している間、ハンドラは有効なまま残るので、本体の中の呼び出しは、ハンドラ式を囲む関数に対して末尾にならない。
- 再開する操作の操作節の本体の中の関数呼び出し。
  `resume` を呼んだ後の呼び出しも、`resume` を呼ばない節の呼び出しも含む。
  `resume` を呼ばない節では、処理系は節の値が決まってから中断した計算を破棄する（§13.6）ので、節を評価している間は中断した計算を保持する。
  再開しない操作の節の本体は、処理系が中断した計算を破棄してから評価する（§13.6）ので、この制限を受けない。
- 末尾位置にない `resume`。
  たとえば `{ let u = resume(); u }` は、再開した計算が終わった後に節の評価が続くので、末尾 `resume` ではない。
- `cancel` 節の本体の中の呼び出し。
- 標準環境の関数（§14.3、§16、§17）が、引数として受け取った関数を呼ぶ呼び出し。

### 5.8. 条件式

**条件式**：`if e1 then e2 else e3` と書き、`Boolean` の値によって 2 つの式の一方を評価する式。
`e1` を条件と呼ぶ。
条件式は、次の `match`（§11.2）の略記である。

```keleut
e1 match {
  case true => e2
  case false => e3
}
```

`else` とその後ろの式は省略できない。
`e1`、`e2`、`e3` には、条件式や `match` を含む、どの式も書ける。

型、評価、網羅性の検査、末尾位置は、上の `match` の規則で決まる。

- 条件は `Boolean` でなければならない。
  `e2` と `e3` は同じ型でなければならず、その型が条件式の型になる。
- 条件を 1 回だけ評価し、`true` なら `e2` だけを、`false` なら `e3` だけを評価する（§5.1）。
- 上の `match` は網羅的なので、網羅漏れの警告は出ない。
- 条件式が末尾位置にあれば、`e2` と `e3` も末尾位置にある（§5.7）。
  条件は末尾位置にない。
- 条件式は構文上の値（§6.2）ではない。

条件式は、§5.2 の表で `fn(...) => ...` と同じ、最も結合の弱い段にある。
`else` の後ろの式は、できるだけ右まで延ばして読む。
そのため、`if c then a else b + 1` は `if c then a else (b + 1)` と読み、`if c then a else b match { ... }` の `match` は `b` だけに付く。
条件式の値を演算子のオペランドや `match` の照合対象にするときは、`(if c then a else b) + 1` のように括弧で囲む。

`then` と `else` は予約語である（§2.2）。
`then` や `else` で始まる行と、`then` や `else` で終わる行は、前後の行に続く（§2.3）。
`if` で始まる行は、新しい文を始める。

```keleut
let sign(n: Int32): Int32 =
  if n < 0 then -1
  else if n == 0 then 0
  else 1
let rec count_down(n: Int32): Unit =
  if n == 0 then echoln("done")
  else count_down(n - 1)
```

`count_down` の `else` の後ろの呼び出しは末尾呼び出しなので、`n` によらず一定の領域で評価できる。
`match` の節に書くガード（§11.2）の `if` は、条件式とは別の構文であり、`then` と `else` を伴わない。
ガードの式にも条件式を書ける。

## 6. 束縛

### 6.1. 値と関数の定義

値の束縛は `let p = e`、関数の定義は `let f(x, y) = e` と書く。
`let` は文であり、`in` は使わない。
値の束縛には値の型を、関数の定義には引数の型、返り値の型、エフェクト行を注釈できる。

```keleut
let answer: Int32 = 42
let identity[A](x: A): A = x
let add_pair(p: (Int32, Int32)): Int32 = p._0 + p._1
```

ブロックの中の束縛は、同じブロックの中で、その束縛より後ろから参照できる。
同じ名前をもう一度束縛すると、それ以降は新しい束縛が有効になる。
以前の束縛を捕捉した関数は、再束縛の後も以前の束縛を参照し続ける。
変数に代入する構文はない。

### 6.2. 一般化

**一般化**：束縛の型に残った型変数を、使うたびに別の型へ具体化できるようにすること。
処理系は、関数定義と、構文上の値を 1 個の名前に束縛する `let` を一般化する。
構文上の値の式文も一般化する。
**構文上の値**には、リテラル、識別子、無名関数、穴、値だけからなるレコードやコンストラクタ適用、構造的ヴァリアントが含まれる。
値のレコードからフィールドを除く式も含まれる。

関数呼び出しやフィールド選択は、純粋な計算であっても構文上の値ではない。
これらの結果を束縛しても一般化しないので、その型変数を使うたびに別の型へ具体化することはできない。
分解パターンで束縛した変数も一般化しない。
型注釈を書いても、この条件は変わらない。
閉じたエフェクト行を持つ関数を使うときに行の尾部を開く規則（§13.2）は、一般化とは別の規則であり、初期化式が構文上の値でなくても働く。

型クラス制約の付いた型変数は、束縛の型から決まらなければならない。
引数の型にも結果の型にも現れず、具体型も決まらない型変数に制約が付いていると、曖昧性エラーになる。
数値リテラルの条件（§4.2）は既定化によって型が決まるので、この検査の対象外とする。

`pure`（§12.3）のように返り値の型からしかインスタンスが決まらないメソッドの結果は、注釈か、結果を使う位置が型を決める。

```keleut
let a = pure(1)                  // 型エラー。このファイルの中で F が決まらない
let b: Option[Int32] = pure(1)   // F は Option
```

`a` の初期化式は関数呼び出しなので、`a` は一般化しない。
一般化しない束縛と、構文上の値でない式文の型に残った、型クラスの制約が付いた型変数は、同じソースファイルの中のどこかで型が決まればよい。
ファイルの終わりまでに決まらなければ、曖昧性エラーになる。
型が決まる前に、その値にほかの型クラスの制約を要求する位置（`show(a)` など）に置くと、型エラーになる。
型を決める注釈や使用は、そのような位置より前に書く。
対話的な実行では、その入力の終わりまでに決まらなければならない（§6.6）。
数値リテラルの条件（§4.2）は、この規則によらず、既定化で型が決まる。

### 6.3. 再帰

再帰関数は `let rec` で定義し、相互再帰する関数は `and` でつなぐ。
`let rec` と `and` の各束縛は、1 個の名前に関数を束縛するものでなければならない。
値束縛の形で書く場合は、右辺を `fn(...) => ...` にする。
再帰的なデータ値の束縛や、多相再帰はできない。

```keleut
let rec even(n: Int32): Boolean = n == 0 || odd(n - 1)
and odd(n: Int32): Boolean = n != 0 && even(n - 1)
```

同じ再帰群の中の呼び出しにも、使用時の開き（§13.2）を適用する。
処理系は、最外の矢印に書いた行、`pub` の関数の省略した行（`@ {}`）、値束縛の型注釈を、群のどの本体を検査するよりも前に置く。
そのため、注釈した閉じた行のラベルが呼ぶ側の行に含まれていれば、関数を書いた順序によらず呼べる。
各関数がそれぞれ導入した行変数は、綴りが同じというだけでは同じ変数にならない。
行を注釈しない関数の行は本体から推論する。
群の中で前にある束縛から後ろにある束縛への参照は単相なので、互いを呼ぶ関数の推論した行は一致し、後ろの束縛の型パラメータは具体化されない。
そのため、前にある束縛が自分の型パラメータの型の値を後ろの束縛の型パラメータの位置に渡す形は、型検査に通らない（多相再帰を認めないことの帰結である）。
行の型パラメータ（行変数）も同じで、前にある束縛から後ろの束縛を参照するとき、後ろの束縛の行変数は具体化されない。
前の束縛の行変数のうち群のほかの束縛の型に流れ込んだものも、型パラメータと同じく（この節の最後の段落）群の終わりまで一般化されないので、後ろの束縛からの参照でも具体化されない。
具体化されない行変数を何かの行に決めることを型検査が求める形は、型検査に通らない。
例えば次の群は、`a` の本体の呼び出し `b(n)` が `b` の行変数 `F` を `a` の行に決めるので、型検査に通らない。

```keleut
let rec a(n: Int32): Int32 @ Console = b(n)
and b[F](n: Int32): Int32 @ {Console extends F} = { echo("b"); n }
```

同じ 2 本を `b`、`a` の順に書けば、`a` からの参照が `b` の行変数を具体化するので通る。
次の群は、`a` の本体の呼び出しが `F` を決めないので通る。

```keleut
let rec a(n: Int32): Int32 @ Console = b(fn() => n)
and b[F](f: () => Int32 @ F): Int32 @ Console = { echo("b"); 0 }
```

再帰群の関数の型のうち、型パラメータとして宣言していない型変数と、群のほかの関数の型に流れ込んだ型パラメータは、群の終わりまで一般化されない。
群の中の参照がそのような型変数に型クラスの制約を要求するときは、その制約も、参照する側の関数自身の型から決まらなければならない（§6.2）。

### 6.4. 宣言順序

型の宣言群の中では、後ろで宣言する型名も参照できる。
エフェクトの名前も同じで、型を書く位置には、後ろで宣言するエフェクトのラベルも書ける。
再帰するデータ型は `newtype` で定義する。

トップレベルの値を宣言より前から参照できるのは、型検査がそのまま使える完全な署名を、その値が持つ場合に限る。
関数束縛の場合は、各引数と返り値の型を注釈し、最外のエフェクト行も明示する。
`pub` の束縛は、最外の `@` を省略しても完全な署名を持つ（省略の意味は §13.2）。

実行時には、宣言を書いた順に初期化する。
後ろの宣言を参照する関数は、参照先の初期化が済んでから呼び出さなければならない。
初期化の済む前に呼び出すと、実行時エラーになる（§15.5）。
インスタンスのメソッドも、インスタンス宣言を実行する前に呼び出すと実行時エラーになる。
型クラスの制約が付いた型変数を持って一般化した値束縛と式文（§6.2）は、宣言の位置では評価せず、値束縛の初期化式は名前を使うたびに評価する。
インスタンスのメソッドを値束縛で書いたもののうち、インスタンスが前提を持つものと、クラスの宣言でメソッドの型パラメータに制約を付けたものも、メソッドを使うたびに初期化式を評価する。
制約付きで一般化した値束縛と式文は構文上の値なので、停止し、エフェクトを起こさない。
メソッドを使うたびに評価するインスタンスのメソッドの初期化式は、エフェクトを起こせない（§12.2）。
構文上の値でない初期化式は、§12.2 の理由で型検査に通らないことがある（前提を持つインスタンスでは、§12.2 の型注釈の条件も受理の条件の 1 つになる）。
評価の時点の違いが現れるのは、初期化式が穴（`???`）やゼロ除算などで実行時エラーを起こすときや停止しないときに、それが起きるかどうかと、その時点だけである。
ファイルの間の初期化の順は §15.4 で定める。

### 6.5. `with`

`with p = f(a)` は、それより後ろの文をまとめて無名関数にし、`f` の呼び出しの最後の引数として渡す。
無名関数に入る文は、現在のブロックの末尾、またはトップレベルの末尾までである。
右辺は関数呼び出しでなければならない。
次の 2 つは同じ意味である。

```text
with x = f(a)
残りの文

f(a, fn(x) => { 残りの文 })
```

束縛パターンが単独の `_` の場合は、引数のない無名関数を渡す。
引数を 1 個受け取って捨てる関数にはならない。
この `_` は、ほかの位置の `_`（値を受け取って束縛しない。§11.1）と意味が異なる。
`with (_) = f(a)` も、括弧はまとめるだけなので、引数のない無名関数を渡す。
引数を 1 個受け取って使わない関数を渡すには、`with _x = f(a)` のように変数で受ける。
残りの文がなければ、無名関数の返り値は `Unit` になる。

次の例では、`with` で束縛した `x` が `with_value` から値 `21` を受け取る。

```keleut
let with_value[A, B, E](x: A, body: (A) => B @ E): B @ E = body(x)
let doubled(): Int32 = {
  with x = with_value(21)
  x * 2
}
```

### 6.6. 対話的な実行

処理系は、プログラムを入力ごとに型検査して実行する対話的な実行を提供してよい。
入力の区切り方は処理系が定める。
対話的な実行では、各入力を、それより前に受理したすべての入力の後ろに続けて書いたものとして扱う。
ただし、次の点が異なる。

- 前方参照（§6.4）と、型の宣言群の中の相互参照は、1 つの入力の中に限る。
- トップレベルの `with`（§6.5）が無名関数にする文は、その入力の末尾までである。
- 字句と構文の誤りのある入力、型検査に通らなかった入力、実行時エラーで止まった入力は受理しない。
  受理しなかった入力の宣言、束縛、インスタンスと、その入力が一般化しなかった束縛（§6.2）の型変数に決めた型は、後の入力から見えない。
  止まるまでに行った出力は取り消さない。
- 前の入力と同じ名前の型、コンストラクタ、エフェクト、型クラスと、同じクラスと型のインスタンスは宣言できない（§10.1、§12.2）。
  値の再束縛は §6.1 に従う。
- モジュールの中の名前とトップレベルの名前を同名にできない規則（§15.3）は、入力をまたいで適用する。
- トップレベルの評価で行に残せるエフェクトに `Print` を加える（§13.7）。
  トップレベルに残った `Print.print` は、`Console.write` と同じく標準出力に書く。
  この規則は対話的な実行だけのもので、ファイルのトップレベルでは `Print` を処理しなければならない。
- 一般化しなかった束縛（§6.2）の型変数は、後の入力で型が決まることがある。
  決まった型は、受理した入力の間で変わらない。
  ただし、型クラスの制約が付いた型変数は、その入力の中で型が決まらなければならない（§6.2）。

`run` の外へ `Heap[h]` を持ち出せない規則（§14.1）は、対話的な実行でも変わらない。
そのため、参照や可変配列を入力をまたいで持つことはできない。

## 7. レコード

### 7.1. 構築と選択

レコードは、フィールド名と値の組を集めたものである。
型を宣言しなくても構築できる。
`{x, y}` は `{x = x, y = y}` の略記である。
フィールドは `p.x` と書いて選択する。

```keleut
let point = {x = 1.0, y = 2.0}
let x = point.x
let sum_xy[R](p: {x: Float64, y: Float64 extends R}): Float64 =
  p.x + p.y
```

`{x: Float64, y: Float64}` は、書いたフィールドだけを持つレコードの型である。
`extends R` を付けた型は、書いたフィールド以外のフィールドを行変数 `R` で受け取る。
`{extends R}` は、行 `R` 全体をフィールドとするレコード型である。

### 7.2. 拡張と制限

`{x = v extends p}` は、`p` の外側にフィールド `x` を重ねた新しいレコードを返す。
`p` がすでに `x` を持っていても上書きせず、両方を残す。
同じ名前のフィールドが複数あるとき、選択は最も外側の値を返す。

`p \ x` は、最も外側の `x` だけを除いた新しいレコードを返す。
内側に同じ名前のフィールドがあれば、以後はそのフィールドを選択できる。
選択も制限も、対象のラベルを持つことが型で分かるレコードにしか使えない。

```keleut
let p = {x = 1 extends {x = "inner", y = true}}
let outer: Int32 = p.x
let inner: String = (p \ x).x
```

レコード式に書いた異なるラベルの順序は、型の一致には影響しないが、評価の順序を決める（§5.1）。
同じラベルを重ねて書いた場合は書いた順を保存し、最初に書いたフィールドを最も外側とする。

### 7.3. 更新

`{p with x = v}` は、`p` の最も外側の `x` を `v` に置き換えた新しいレコードを返す。
元のレコードは変わらない。
新しい値の型は、元のフィールドの型と違ってもよい。
`p` が `x` を持たなければ型エラーになる。

基底の `p` には、小文字または `_` で始まる識別子を 1 個だけ書ける。
`{p.origin with ...}` や `{f(x) with ...}` とは書けない。
複数のフィールドを更新するときは、左から順に置き換える。

## 8. タプル

タプルは、同じラベル `_item` を要素の数だけ重ねたレコードである。
要素の位置は、重ねた `_item` の順序に対応する。

| 構文 | 等価なレコード |
| --- | --- |
| `(a, b)` | `{_item = a, _item = b}` |
| `(a,)` | `{_item = a}` |
| `()` | `{}` |
| `(A, B)` | `{_item: A, _item: B}` |
| `(A,)` | `{_item: A}` |

`t._0` は 1 番目の要素を、`t._1` は 2 番目の要素を選択する。
一般に `t._N` は、`t` から `_item` を `N` 個除いてから `_item` を選択するのと同じである。
添字は `_` に続けて 0 以上の 10 進整数を書き、全体で 1 個の識別子になる。
`t.0` とは書けない。

閉じたタプル型どうしは、要素数が同じときだけ一致する。
先頭の要素だけを要求する型は `{_item: A extends R}` と書く。
`_item` は普通のラベルでもあるため、この型は `_item` 以外の名前のフィールドを持つレコードも受け取る。

処理系が型や診断を表示するときは、`_item` だけを持つ閉じた行をタプルの記法で表示する。
1 要素のときもカンマを残す。
空の行は、型なら `{}`、値なら `()` と表示する。
開いた行はタプルの記法にせず、`_item` をそのまま表示する。

## 9. 構造的ヴァリアント

**構造的ヴァリアント**：ラベルの付いたいくつかのケースのうち、どれか 1 つを値とする構造的な型。
ラベルはどの型宣言にも属さず、宣言しなくても `#Even` のように使える。

型では、ケースを `|` でつなぐ。
最後に行変数を置くと、書いたケース以外の値も受け取る型になる。
最後以外の位置に型エイリアスを置く場合、そのエイリアスは閉じたヴァリアント型でなければならない。

```keleut
type Result[A] = #Ok(A) | #Err(String)

let describe[R](v: #Even | #Odd | R): String = v match {
  case #Even => "even"
  case #Odd => "odd"
  case _ => "other"
}
```

各ラベルが運ぶ値（**積載値**）は 1 個である。
引数を書かないラベルは、`Unit` の値を積載する。
`#Pair(a, b)` は `#Pair((a, b))` と同じであり、型とパターンでも同じ規則で読む。
引数に名前を付けることはできない。

構築したヴァリアントの型は開いた行を持つ。
文脈の型注釈で、閉じた型にすることもできる。
再帰する型が必要な場合や、利用者が型クラスのインスタンスを定義したい場合は、名目的な型（§10）を使う。

## 10. 名目的な型

### 10.1. 宣言

**名目的な型**：宣言した名前によって、他の型と区別する型。
名目的な型は `newtype` で宣言し、右辺にコンストラクタを `|` で区切って並べる。
この右辺は、型エイリアスの右辺に書く型式とは別の構文である。

```keleut
newtype Tree[A] = Leaf(A) | Branch(left: Tree[A], right: Tree[A])
newtype UserId(Int32)
newtype Empty
```

`newtype UserId(Int32)` は、型名と同じ名前のコンストラクタを 1 個だけ持つ宣言の略記である。
右辺を省略した型は、コンストラクタを持たない。

コンストラクタのフィールドには順序がある。
フィールドには名前を付けても付けなくてもよく、名前のあるフィールドとないフィールドを混ぜてもよい。
1 個のソースファイルで見えるコンストラクタの名前は、一意でなければならない。
見えるコンストラクタは、そのファイルで宣言したもの、import した型のもの（§15.4）、標準環境のものである。
モジュールが違っても、同じファイルの中に同じ名前のコンストラクタは宣言できない。
別のファイルが同じ名前のコンストラクタを宣言することは妨げない。

### 10.2. 構築

コンストラクタを適用するときは、すべてのフィールドをちょうど 1 回ずつ指定する。
名前付き引数は同じ名前のフィールドに対応する。
位置引数は、まだ指定していないフィールドに先頭から順に対応する。
両者を混ぜてもよいが、同じフィールドを 2 回指定することはできない。
引数は書いた順に評価する。

引数のないコンストラクタは、名前だけで値になる。
引数を取るコンストラクタを、名前だけ書いて関数の値として使うことはできない。
関数として渡したいときは、`fn(x) => Some(x)` のように無名関数で包む。

## 11. パターン照合

### 11.1. パターン

パターンは、関数の引数、`let` による分解、`match` の節、ハンドラの節の引数に書く。
1 個のパターンや 1 組の引数の中で、同じ変数名を 2 回以上束縛することはできない。

| 形 | 意味 |
| --- | --- |
| `_` | 値を受け取り、束縛しない |
| `x` | 値を変数 `x` に束縛する |
| `true`、`42`、`"text"` | リテラルと等しいかを調べる |
| `Some(x)` | 名目的なコンストラクタを分解する |
| `#Ok(x)` | 構造的ヴァリアントを分解する |
| `{x, y = p}` | フィールド `x` と `y` を取り出す |
| `{x, ...rest}` | 書いていないフィールドを `rest` に束縛する |
| `(x, y)` | 要素数が一致するタプルを分解する |
| `(x, ...rest)` | タプルを先頭と、残りのレコードに分ける |

数値リテラルのパターンは、照合する値の型で読んだ値と比べる。
たとえば `Int32` の値に対する `case 0xFFFFFFFF` は `-1` に一致する。
その型で読めないリテラルは型エラーになる（§4.2）。

レコードパターンは、書いていないフィールドを持つ値にも一致する。
空のレコードパターン `{}` も余分なフィールドを許すので、空レコードかどうかの判定には使えない。
一方、タプルパターンは `...rest` を含まない限り閉じており、`()` は空タプルにだけ一致する。
`(p)` はパターンを括弧でまとめただけであり、1 要素タプルのパターンは `(p,)` と書く。
式（§8）と型（§3.1）の括弧も同じ規則である。

名前付きのフィールドだけでコンストラクタパターンを書く場合は、一部のフィールドを省略できる。
たとえば `Cons(tail = t)` は先頭要素を束縛しない。
位置で指定するパターンを含める場合は、すべてのフィールドを指定する。

`let` のパターンの最も外側に書けるのは、変数、`_`、名目的なコンストラクタ、レコード、タプルである。
リテラルや `#Case` を最も外側に書くことはできない。
関数の引数や束縛全体には型注釈を書けるが、`case p: T => ...` のように節のパターンに型注釈を書くことはできない。
`p | q` のような選択パターンもない。

### 11.2. `match`

`match` は照合対象の式の後ろに書く。
処理系は節を上から順に調べ、パターンが一致してガードも成り立つ最初の節の本体を評価する。
ガードは `Boolean` を返す式でなければならない。

```keleut
let classify(n: Int32): String = n match {
  case 0 => "zero"
  case x if x < 0 => "negative"
  case _ => "positive"
}
```

すべての節の本体は、同じ型でなければならない。
網羅性の検査では、ガード付きの節がその場合を必ず受け取るとはみなさない。
どの節にも一致しなければ、実行時エラーになる。
`Boolean` の値に対する `match` は、条件式（§5.8）で略記できる。

照合対象が構造的ヴァリアントの場合、残りのケースをまとめて受け取るガードなしの節がなければ、処理系は照合対象の行を閉じる。
そのため、型注釈のない関数の引数を `match` で照合すると、その型は節に挙げたケースだけからなる閉じた和として推論される。
残りを `_` や変数で受け取る節があれば、まだ決まっていない行の尾部は開いたままにする。
利用者が明示した行変数を、この規則で空行に決めることはできない。

処理系は、網羅漏れと到達できない節を検査し、警告（§15.5）を出す。
`let` や関数の引数に書いた、一致しない可能性のあるパターンも検査する。
そのようなパターンが束縛のときに一致しなければ、実行時エラーになる。
コンストラクタを持たない型に対しては、節のない `match {}` が網羅的である。

節のない `match {}` の照合対象の型がまだ決まっていない型変数のとき、処理系はその型を `Never` に決めることがある。
処理系は節のない `match {}` の網羅性を、その `match` を含む式の推論の途中で、ある束縛（式文を含む）の推論を終えた時点に検査する。
以下では、この束縛を検査する束縛と呼ぶ。
どの束縛を検査する束縛にするか（`match` の後の局所の束縛にするか、外側の束縛まで送るか）は処理系が定める。
検査する束縛は、`match` をすぐ外側で囲む束縛とは限らない。
決める条件には次のことが含まれる。
その型変数に制約が付いていないこと、検査する束縛の型に現れないこと、トップレベルの型変数でないことである。
トップレベルの型変数には、前のトップレベルの一般化しない束縛の型に残った型変数と、トップレベルの値でない式文の推論で、局所の束縛と `run` の本体のどちらの中でもなく作られた型変数が含まれる（どの型変数がそれに当たるかは処理系が定める）。
そのような型変数は、決めても検査する束縛の型が変わらない（§6.2 の曖昧な型変数と同じ考え方である）。
`let` で束縛した関数の本体で、再開しない操作（§13.1）の結果を直接照合する `perform throw(m) match {}` は、この規則で網羅的になる。
返り値を注釈しない補助関数の呼び出しの結果を照合する形も、その呼び出しが補助関数を束縛した `let rec` の群の推論の中（群の束縛の右辺と、その中の局所の束縛）になければ同じである。
群の推論の中で呼び出すと、補助関数の返り値がまだ型変数なら、その型変数が群の型に現れるので、型を決めない。
型注釈のない引数 `x` を照合する `let f(x) = x match {}` では、`x` の型変数が検査する束縛 `f` の型に現れるので、型を決めず、網羅性を通常どおり検査する。
前のトップレベルの一般化しない束縛の型に残った型変数の照合、制約が付いた型変数の照合、利用者が明示した型パラメータの値の照合も、型を決めない。
トップレベルの値でない式文に、局所の束縛と `run` の本体のどちらでも包まずに書いた `match {}` も、型を決めない。

## 12. 型クラス

### 12.1. 宣言と制約

**型クラス**：型に要求する操作の署名をまとめたもの。
型クラスはパラメータを 1 個持つ。
そのカインドは `Type` か、`F[_]` のように `Type` を取って `Type` を返す形に限る。

各メソッドの型は矢印型で、クラスパラメータを含まなければならない。
クラスパラメータは、引数の型に現れず、返り値の型にだけ現れてもよい（§12.3 の `pure`）。
メソッド自身の型パラメータに型クラス制約を付けるときは、その型パラメータもメソッドの型に現れなければならない。
`val pp[B: Show]: (A) => String` のように型に現れない型パラメータに制約を付けると、クラスの宣言が曖昧性エラーになる（§6.2）。
異なる型クラスに、同じ名前のメソッドを宣言することはできない。

```keleut
type class Render[A] {
  val render: (A) => String
}

newtype Label(String)
type instance Render[Label] {
  let render(x) = x match { case Label(s) => s }
}

let render_twice[A: Render](x: A): String = render(x) + render(x)
```

型パラメータに複数の制約を付けるときは、`[A: Add + Mul]` のように `+` で並べる。
メソッドは `render(x)` とも `Render.render(x)` とも呼び出せる。
メソッドを使う位置では、その位置でクラスパラメータに決まった型のインスタンスのメソッドを呼ぶ。
どのインスタンスを使うかは型検査が型から決め、実行時の値には依存しない。
`render_twice` のように制約付きの型パラメータを持つ関数は、呼び出しごとに、その呼び出しで `A` に決まった型のインスタンスを使う。
型エイリアスと名目的な型のパラメータには、制約を付けられない。
行変数には型クラス制約を付けられない。
スーパークラス、複数パラメータの型クラス、一般的なランク 2 多相はない。
`Ord` の制約から `Eq` の制約を導く規則もないので、両方が必要なら `[A: Eq + Ord]` と並べて書く。

### 12.2. インスタンス

インスタンスは `type instance C[T] { ... }` と書く。
本体では、クラスのすべてのメソッドを `let` か `let rec` で定義する。
クラスにないメソッドは追加できないので、補助関数はメソッドの中の局所束縛などで定義する。
各メソッドの型は、クラス宣言の署名を満たさなければならない。

メソッドの仮引数のうち、型注釈のない変数と `_` の型は、クラス宣言の署名の対応する引数の型に決まる。
ただし、署名の引数の型のうちメソッド自身の型パラメータの位置は、本体から推論してから署名と照らし合わせる。
`let` の型注釈のない値束縛で書いたメソッドの初期化式が無名関数で、その仮引数がすべて型注釈のない変数か `_` であるときも同じである。
`let rec` の値束縛の形（§6.3）で書いたメソッドの無名関数の仮引数と、仮引数の数が署名と違うメソッドと、それ以外の仮引数の型は、本体から推論してから署名と照らし合わせる。
返り値の型と最外の行は、署名から決めない。
したがって、仮引数の型が署名の型に決まるメソッドでは、本体の数値リテラルの型（§4.2）と網羅性と冗長性の検査（§11.2）は、仮引数に署名の型を注釈した関数と同じ型に基づく。
たとえば署名の引数が `Never` のとき、その仮引数を照合する `match {}` は網羅的であり、`case _` の節には一致する値がないという警告が出る。

インスタンスの実装が起こせるエフェクトは、クラスの宣言のメソッドの最外の行にあるものに限る（§13.2。値束縛で書いたメソッドの初期化式が起こすエフェクトは、この節の後の段落で定める）。
最外の `@` を省略したメソッドの実装は純粋でなければならないので、再開しない操作（§13.1）で失敗することもできない。
標準環境のクラス（`Eq` や `Show` など）のメソッドも最外の行が `@ {}` なので（§16 の冒頭）、そのメソッドの実装はエフェクトを起こせない。
宣言の行が `@ E` のように行変数だけのときは、実装はどの `E` でも通らなければならないので、自分の本体で `Fail` のような特定のエフェクトを起こせない。
引数の関数から届く `E` のエフェクトを通すことはできる（§12.3 の `Functor` の例）。
インスタンスごとに別のエフェクトを足す手段はない。
失敗するメソッドは、次のように宣言の行に失敗のエフェクトを書く。

```keleut
effect Fail = { throw: (String) => Never }

type class Parse[A] {
  val parse: (String) => A @ Fail
}

type instance Parse[Int32] {
  let parse(s) = if s == "0" then 0 else perform throw("not a digit: " + s)
}

let parse_or[A: Parse](s: String, d: A): A = parse(s) handle { case throw(_) => d }
```

失敗しないインスタンスは、同じ宣言の下で純粋な実装として書ける。
閉じた `@ Fail` で宣言したメソッドも、呼び出しと名前の参照で使用時の開き（§13.2）を受けるので、`@ {Fail, Console}` のようにほかのエフェクトも持つ文脈から呼べる。
最外の行が純粋なメソッドで失敗を扱うには、`Option[A]` のような値で返すか、`val mk: (A) => (() => Int32 @ Fail)` のように返り値の関数の行に失敗のエフェクトを書くか、実装の中のハンドラで捕まえる。

値束縛で書いたメソッドの初期化式が起こしてよいエフェクトは、宣言の実行で 1 回だけ評価するものではトップレベルの評価と同じであり（§13.7、§15.4）、メソッドを使うたびに評価するもの（§6.4）では無い。
署名の行と照らすのは初期化式の値の関数の行で、初期化式が起こすエフェクトは含まない。
初期化式が起こしてよいエフェクトの外のエフェクトを起こすインスタンスは、型検査で拒否する。
構文上の値でない初期化式は一般化しない（§6.2）ので、その型に残った型変数は、使うたびに別の型へ具体化できない。
そのため、メソッドの型パラメータを使うたびに別の型へ具体化しなければならないメソッドでは、値でない初期化式は型検査に通らない。
たとえば値の型パラメータ `B` を持つ `val m[B]: (A, B) => B` のメソッドは、`B` に制約が有っても無くても、値でない初期化式では型検査に通らない。
最外の行にだけ現れる行の型パラメータ（`val sz[E]: (A) => Int32 @ E` の `E`）は、署名と照らす包摂で空の行に決まるので、値でない初期化式でも型検査に通る。
前提を持つインスタンスでは、値でない初期化式の型のうちインスタンスの型パラメータに当たる位置を、その型パラメータを書いた型注釈で決めることが、受理の条件の 1 つになる。
たとえば `type instance[A: Show] Show[Box[_]]` の本体で、`let show: (Box[A]) => String = { let q = 1 / 0; fn(b) => "box" }` は型検査を通り、注釈を外した `let show = { let q = 1 / 0; fn(b) => "box" }` は型エラーになる。
型検査を通る値でない初期化式は、ゼロ除算などの実行時エラーを起こすことや、停止しないことがある。
評価の時点は §6.4 で定める。

インスタンスを宣言できる対象は、型構成子である。
レコード、タプル、構造的ヴァリアントに、利用者が直接インスタンスを宣言することはできない。
型エイリアスに対して新しいインスタンスを与えることもできない。

前提を持つインスタンスでは、`instance` の直後に型パラメータのリストを書く。
リストの型パラメータは、対象の型に書いた `_` に左から順に対応する。
次の例では、`[A: Eq]` の `A` が `Seq[_]` の `_` に対応する。

```keleut
newtype Seq[A] = Empty | More(A, Seq[A])

type instance[A: Eq] Eq[Seq[_]] {
  let rec eq(xs, ys) = (xs, ys) match {
    case (Empty, Empty) => true
    case (More(x, xt), More(y, yt)) => x == y && eq(xt, yt)
    case _ => false
  }
}
```

対象の型に書く `_` の数は、その型構成子が取る引数の数と同じにする。
型パラメータの数は、`_` の数を超えてはならない。
型パラメータが対応しなかった右側の `_` は未適用のまま残り、インスタンスの対象は、その数だけ型引数を取る型構成子になる。
残った型構成子のカインドは、クラスパラメータのカインドと一致しなければならない。

インスタンスの型パラメータは、メソッドの型注釈から参照できる。
メソッド自身が同じ名前の型パラメータを持つ場合は、メソッドのものを優先する。
前提は、そのインスタンスを適用できるかどうかを決める条件である。
インスタンスを値として渡し、別のインスタンスに選び直す手段はない。

1 組のクラスと型構成子に対するインスタンスは、プログラム全体で 1 個だけである。
インスタンスは、クラスを宣言したソースファイルか、型構成子を宣言したソースファイルにだけ宣言できる。
標準環境のクラスと型構成子は、標準環境で宣言したものとみなす。
したがって、標準環境のクラスの、標準環境の型構成子に対するインスタンスは、標準環境だけが持つ。
インスタンスには `pub` を付けず、import でも指定しない。
本体の `let` と `let rec` に `pub` を付けると、構文エラーになる。
メソッドは、クラスを import し、クラスのメソッドの名前で使う。
インスタンスは、それを宣言したファイルと、そのファイルを直接または間接に import したファイルから見える。

### 12.3. 高階型パラメータ

型構成子をパラメータに取るクラスでは、`F[_]` のように、そのパラメータが取る引数の数を書く。
メソッドには、値の型やエフェクト行の型パラメータを追加できる。

```keleut
type class Functor[F[_]] {
  val map[A, B, E]: (F[A], (A) => B @ E) => F[B] @ E
}

type instance Functor[List[_]] {
  let rec map[A, B, E](xs: List[A], f: (A) => B @ E): List[B] @ E =
    xs match {
      case Nil => Nil
      case Cons(x, tail) => Cons(f(x), map(tail, f))
    }
}
```

`Functor[List[_]]` では `_` に型パラメータを対応させていないので、`List` を引数 1 個の型構成子として渡している。
エフェクト行を引数に取る型構成子は、カインドが異なるので `F[_]` には渡せない。

返り値の型にだけクラスパラメータが現れるメソッドも宣言できる。
次の `pure` のインスタンスは、引数の型ではなく、結果を受け取る側の型から決まる。

```keleut
type class Applicative[F[_]] {
  val pure[A]: (A) => F[A]
  val ap[A, B, E]: (F[(A) => B @ E], F[A]) => F[B] @ E
}

type instance Applicative[Option[_]] {
  let pure(x) = Some(x)
  let ap(f, x) = (f, x) match {
    case (Some(g), Some(v)) => Some(g(v))
    case _ => None
  }
}

let one: Option[Int32] = pure(1)
```

`let one: Option[Int32] = pure(1)` では、注釈が `F` を `Option` に決める。

標準環境は `Functor`、`map`、`Monad` などを宣言していない。
必要なら、利用者がクラスとインスタンスをプログラムの中で定義する。

### 12.4. 演算子クラス

組み込みの演算子は、次の型クラスのメソッドを呼び出す。

| 演算子 | 操作 | 標準でインスタンスを持つ型 |
| --- | --- | --- |
| `+` | `Add.add` | `Int32`、`Int64`、`Float64`、`String` |
| `-` | `Sub.sub` | `Int32`、`Int64`、`Float64` |
| `*` | `Mul.mul` | `Int32`、`Int64`、`Float64` |
| `/` | `Div.div` | `Int32`、`Int64`、`Float64` |
| `%` | `Rem.rem` | `Int32`、`Int64` |
| 前置の `-` | `Neg.neg` | `Int32`、`Int64`、`Float64` |
| `==` | `Eq.eq` | `Int32`、`Int64`、`Float64`、`String`、`Boolean`、`List[A]`、`Option[A]` |
| `!=` | `Eq.eq` の否定 | `Eq` と同じ |
| `<`、`<=`、`>`、`>=` | `Ord.lt`、`Ord.le`、`Ord.gt`、`Ord.ge` | `Int32`、`Int64`、`Float64`、`String` |

二項の算術メソッドの型は `(A, A) => A`、`Neg.neg` の型は `(A) => A`、比較メソッドの型は `(A, A) => Boolean` である。
これらのメソッドの最外の行は `@ {}` であり（§16 の冒頭）、演算子の位置でも使用時の開き（§13.2）を受けるので、呼ぶ側の行にラベルを要求しない。
括弧で囲まない数値リテラルに付けた `-` は `Neg.neg` を呼ばず、負の数値リテラルになる（§4.2）。
`List[A]` と `Option[A]` の `Eq` は、要素の型 `A` が `Eq` を持つときに使える。
2 つのリストは、長さが同じで、同じ位置の要素がすべて等しいときに等しい。
2 つの `Option` は、どちらも `None` であるか、どちらも `Some` で中の値が等しいときに等しい。
`String` では、`+` は連結を表し、順序の比較はバイト列の辞書順で行う。
`&&`、`||`、`!` は `Boolean` 専用の組み込み演算子であり、型クラスのメソッドではない。

### 12.5. 構造的な等値比較

閉じたレコード、タプル、構造的ヴァリアントは、組み込みの `Eq` によって構造的に比較できる。
そのためには、すべてのフィールドや積載値の型が `Eq` を満たす必要がある。
レコードでは同じラベルの値どうしを比較し、同じラベルが複数あれば、そのラベルの中での順序で対応させる。
ヴァリアントでは、ラベルと積載値を比較する。

行変数を含む型には、この導出を適用しない。
関数どうしの等値比較もない。
名目的な型を比較するには、利用者がその型の `Eq` のインスタンスを定義する。
構造の中に名目的な型があれば、その型の `Eq` のインスタンスで比較する。

構造的な導出を持つのは、標準環境の `Eq` だけである。
利用者が定義したクラスに構造的な導出を与える構文はない。

## 13. エフェクト

### 13.1. 宣言と行

エフェクトの宣言には、操作の名前と型を並べる。
操作の型は矢印型で書く。
返り値の型が `Never`（§3.1）である操作を、**再開しない操作**と呼ぶ。
型エイリアスを展開した結果が `Never` である場合も含む。
`Never` の値はないので、再開しない操作を起こした計算に返す値はなく、その計算は再開されない（§13.5、§13.6）。
ほかの操作は**再開する操作**である。
同じエフェクトに、再開する操作と再開しない操作を混ぜて宣言できる。
利用者が宣言するエフェクトには、型パラメータを付けられない。
同じエフェクトの中で操作名は重複できないが、別のエフェクトには同じ名前の操作を宣言できる。

```keleut
effect Ask = { ask: () => String }
effect Log = { log: (String) => Unit }
effect Fail = { throw: (String) => Never }
type Request: EffectRow = {Ask, Log}
```

関数型では、`@` の右にエフェクト行を書く。

| 記法 | 意味 |
| --- | --- |
| `@ {}` | 空行 |
| `@ Print` | `@ {Print}` の略記 |
| `@ {Print, Console}` | 2 個のラベルを持つ行 |
| `@ E` | 行変数または行の別名 |
| `@ {Print extends E}` | `Print` と行変数 `E` からなる行 |
| `@ Heap[h]` | リージョン `h` の可変状態を扱う行 |

エフェクト行の別名を行の要素として書くと、その位置に別名の中身を展開する。
開いた行の別名も使えるが、展開した結果、独立した尾部の行変数が複数並ぶ書き方はできない。
行の比較は §3.4 に従う。

処理系が関数型を表示するときは、閉じた行を `@ {}` や `@ {Print}` のように書き、行変数だけからなる行は `@` ごと省く。
行変数で終わる行は、`@ {Print extends R1}` のように書く。
表示で `@` を省いた矢印の行は行変数であり、`pub let` の注釈で `@` を省略したとき（`@ {}`）とは意味が違う。
本書が示す標準環境の署名は表示ではなく、§16 の冒頭の読み方で読む。

### 13.2. 注釈の位置

関数型のエフェクト行は、書いたとおりに読む。
閉じた行は、その関数が起こしうるエフェクトの全体を表す。
行変数で終わる行は、その行変数の分だけ、ほかのエフェクトを許す。
2 つの行を一致させる規則は §3.4 のとおりであり、行にラベルを足して暗黙に合わせる一般の規則（サブエフェクティング）はない。
例外は、次に定める使用時の開きだけである。

**使用時の開き**：閉じた行を持つ関数を、呼び出すとき、名前で参照するとき、または関数型を要求する位置に置くとき、その行のラベルが要求する側の行に含まれていればよいとする規則。
処理系は、閉じた行の尾部を新しい行変数として開いてから、要求する側の行と一致させる。
行変数で終わる行は開かず、要求する側の行とそのまま一致させる。
開いた尾部が、それを含む一般化しない束縛（§6.2）の型の最外の行として、束縛の終わりまでほかの行と一致しないまま残ったときは、閉じた行に戻す。
名前で参照するときの開きは、束縛した名前、引数、パターンで束縛した変数、型クラスのメソッドのどれにも、参照した位置ごとに働く。
関数型を要求する位置は、型注釈が関数型である値束縛の初期化式、返り値の型注釈が関数型である関数束縛の本体、仮引数の型が関数型である実引数、操作の型の対応する部分が関数型である `perform` の実引数と `resume` の引数である。
実引数（`perform` の実引数と `resume` の引数を含む）に直接書いた無名関数の本体と、実引数に直接書いたレコード式のフィールドやタプル式の要素も、仮引数の型（`perform` では操作の引数の型、`resume` では操作の返り値の型）のうち対応する部分が関数型なら、関数型を要求する位置にあたる（入れ子になっていてもよい）。
閉じた行で検査した本体が起こすエフェクトはその行に含まれるので、尾部を開いても、型に書かれていないエフェクトが起きることはない。

**最外の矢印**：関数束縛ではその関数自身の矢印、値束縛では型注釈の先頭に直接書いた矢印、型クラスのメソッドと外部関数では宣言した型の先頭の矢印。
型エイリアスを展開して現れる矢印は、最外の矢印に含めない。

最外の矢印の行は、本体を検査する文脈の行になる。
閉じた行を書いた束縛の本体が、その行にないエフェクトを起こすと、型検査に通らない。
最外の `@` を省略したときの意味は、宣言の種類で決まる。

| 宣言 | `@` の省略の意味 |
| --- | --- |
| `pub` のない `let` | 本体から推論する |
| `pub let` | `@ {}` |
| 型クラスのメソッド | `@ {}`。各インスタンスの実装は純粋でなければならない |
| `extern "C"` | `@ Blocking` |
| `extern "prim"` | 新しい行変数。使うたびに別の行へ具体化する |

本書が示す標準環境の署名は、プリミティブを除きこの表の `pub let` と同じく読む（§16 の冒頭）。

インスタンスの実装の最外の行が閉じていれば、尾部を開いてから宣言の行と一致させる。
宣言の行に含まれるラベルだけを起こす実装は、閉じた行の注釈で書ける。

最外以外の矢印では、`@` を省略すると `@ {}` と同じ意味になる。
この規則は、関数の引数や返り値の中の矢印、レコードやタプルの要素、コンストラクタのフィールド、型エイリアスの中の矢印に適用する。
受け取った関数の行を自分の行へ通したいときは、次の `apply` のように行変数を明示する。

```keleut
let apply[A, B, E](f: (A) => B @ E, x: A): B @ E = f(x)
let pure_increment(x: Int32): Int32 = x + 1
let result = apply(pure_increment, 41)
```

使用時の開きには、2 つの制限がある。
1 つ目に、名前の参照でない式（`mk()` のような呼び出しの結果や、`r.go` のようなフィールドの選択）の関数は、関数型を要求する位置に置いたときだけ開く。
コンストラクタの引数、レコードのフィールド、タプルの要素、`match` と条件式の各節の値に置いたときは開かない。
そのような位置で行の違う関数と同じ型にするには、`fn() => mk()()` のように無名関数で包むか、いったん名前に束縛してから置く。
2 つ目に、使用の時点で関数の行や要求する側の型がまだ決まっていないときは、開かずに一致させ、その使用で決まった行がその後の使用に効く。
そのため、注釈のない引数の関数を呼んでから閉じた行の関数と同じ型にする形、行が決まっていない一般化しない束縛（無名関数を引数に渡す呼び出しの結果を束縛し、その無名関数の行がまだ決まっていない値束縛など）を行の違う 2 つの文脈から呼ぶ形、型が型変数である仮引数に名前の参照でない式と行の違う関数を並べて渡す形は、文や実引数の順序によって受理されるかどうかが変わり、どちらの順序でも受理されないこともある。

`pub let n: Int32 = e` のように関数型でない値の初期化式は、その宣言の位置のエフェクト行で評価する。
`pub` が付いていることだけを理由に、初期化式を純粋に制限することはない。

エフェクトの操作の型では、先頭の矢印に `@` を書いても、`perform` の行はその注釈に制約されない。
操作の引数の中に現れる矢印には、最外以外の矢印の規則を適用する。

### 13.3. `perform`

エフェクトの操作は `perform op(args)` の形で呼び出す。
実引数は、操作の型に一致しなければならない。
`perform` の式の型は、操作の返り値の型である。
ただし、再開しない操作（§13.1）の `perform` の式は、穴（§5.6）と同じく、周囲が要求する型の式として扱う。
その式の評価は値を返さず、ハンドラの操作節に移る（§13.6）。
そのため、`case None => perform throw("none")` のように、値が要る位置にそのまま書ける。
任意の型で失敗する関数は、型パラメータを返り値の型にして書く。
`perform` の式は構文上の値（§6.2）ではないので、それを初期化式とする値束縛は、穴と違って一般化しない。

```keleut
effect Fail = { throw: (String) => Never }

let abort[A](message: String): A @ Fail = perform throw(message)
```

操作名が曖昧なときは、`perform Print.print(message)` のようにエフェクト名で修飾できる。

修飾しない操作名は、次の手順で解決する。

1. その操作名を宣言するエフェクトが 1 個だけなら、そのエフェクトを選ぶ。
2. 複数あるときは、その位置のエフェクト行に現れる候補が 1 個だけなら、そのエフェクトを選ぶ。
   行に現れる候補が 1 個もないときと 2 個以上あるときは、修飾を求める型エラーにする。

実引数（`perform` の実引数と `resume` の引数を含む）に書いた無名関数の本体では、仮引数の型（`perform` では操作の引数の型、`resume` では操作の返り値の型）のうち対応する部分が関数型なら、その矢印の行がその位置のエフェクト行になる。
無名関数がタプル式の要素や別の無名関数の本体の中にあってもよい。
そのため、`perform reg(fn() => perform write(s))` の `reg` の引数の型が `() => Unit @ File` なら、本体の `write` は、外側の行に `Console` があっても `File.write` に解決する。
対応する部分が型パラメータのときは、この読み替えは働かない。
実引数でない位置に書いた無名関数にも働かない。
型注釈を持つ値束縛の初期化式や、返り値の型注釈を持つ関数束縛の本体に書いた無名関数がその例である。

同じエフェクトが行に 2 回以上現れても、候補としては 1 個と数える。
行の中のラベルの位置は、解決に使わない。
そのため、ラベルの順序だけが違う行（§3.4 で同じ型になる行）の下では、同じエフェクトを選ぶ。
操作を解決した後は、そのエフェクトを現在の行で扱えることも確かめる。

### 13.4. `handle`

**ハンドラ**：エフェクトの操作を受け取り、中断した計算を再開するか終了するかを決める式。
ハンドラは `body handle { ... }` と書き、1 個のエフェクトを処理する。
本体の行から処理するエフェクトのラベルを 1 個除いた行が、ハンドラの外側の行になる。
操作節、`return` 節、`cancel` 節は、この外側の行で評価する。

```keleut
effect Ask = { ask: () => String }

let greeting(): String =
  ("hello, " + perform Ask.ask()) handle {
    case Ask.ask() => resume("Keleut")
    case return(value) => value
  }
```

処理するエフェクトは、操作節から決まる。
修飾した操作節があれば、その修飾先のエフェクトを処理し、修飾していない操作節も同じエフェクトの操作として読む。
1 個のハンドラの中で、異なるエフェクトへの修飾を混ぜることはできない。

操作節がすべて修飾されていない場合は、次の 2 つを満たすエフェクトを候補とする。
ハンドラに書いたすべての操作を宣言していること、そして宣言したすべての操作がこのハンドラに現れること。
候補が 2 個以上あれば、修飾を求める。
操作節を 1 個も持たないハンドラは書けない。

エフェクトのどの操作にも、ガードがなく、どんな引数にも一致する節が少なくとも 1 個必要である。
節がこの条件を満たすかどうかは、引数の並びを照合対象とし、その節だけを持つ `match` が網羅的かどうか（§11.2）で決める。
変数、`_`、およびそれらだけからなるレコードやタプルのパターンは、この条件を満たす。
コンストラクタを 1 個だけ持つ名目的な型の分解（`newtype UserId(Int32)` に対する `UserId(n)` など）や、ケースが 1 個の閉じた構造的ヴァリアントの分解（`#A(Int32)` に対する `#A(n)`）も、中のパターンがこの条件を満たせば、この条件を満たす。
引数の型がどれも値を持つとき、リテラルのパターンや、コンストラクタやケースを 2 個以上持つ型からその 1 個を選ぶパターンで絞り込む節だけでは、条件を満たさない。
複数の節を合わせるとどんな引数にも一致する場合（`Some(x)` の節と `None` の節など）も、この条件を満たさない。
同じ操作に複数の節を書いてもよいが、どの節にも一致しなかった操作を外側のハンドラへ自動で回す規則はない。
同じ操作について、ガードがなくどんな引数にも一致する節より後ろに書いた節には、操作が届かない。
処理系は、このような節を到達しない操作節として検査し、警告（§15.5）を出す。

`case return(p) => e` は、本体が正常に終了したときの値を `p` に束縛して `e` を評価する。
`return` 節を省略すると、本体の値をそのまま返す。
操作節の値と `return` 節の値は、ハンドラ式全体の型に一致しなければならない。
`return` 節は 1 個までで、ガードも名前の修飾も付けられない。

同じエフェクトのハンドラを入れ子にすると、操作は最も内側のハンドラに届く。
エフェクト名で修飾しても、同じエフェクトの外側のハンドラを選ぶことはできない。
操作節の中で同じエフェクトの操作を起こすと、その節のハンドラの外側にあるハンドラが受け取る。

### 13.5. `resume`

`resume(v)` は、中断していた操作の結果として `v` を返し、その操作の続きの計算（**継続**）を再開する。
`v` の型は、操作の返り値の型に一致させる。
操作が `Unit` を返す場合は、`resume()` と書ける。
引数は 1 個までで、名前付き引数は使えない。

再開した計算の中でも同じハンドラが有効であり、同じ操作が再び起きれば、このハンドラが処理する。
`resume` の返り値の型は、ハンドラ式全体の型である。
そのため、操作節は再開した結果を使って、自分の返り値を組み立てられる。

`resume` は操作節の中でだけ使える専用の構文であり、関数の値ではない。
変数に束縛したり、返り値として外へ持ち出したり、関数の中に閉じ込めたりすることはできない。
操作節の中に書いた無名関数（§5.3）、末尾ブロック（§5.5）、関数の定義（§6.1、§6.3）の本体には、その節の `resume` を書けない。
その関数を節の中で呼び出すだけであっても同じである。
その関数の本体にある別の `handle` の操作節に書いた `resume` は、内側の節の継続を再開するものなので、この制限を受けない。
`with`（§6.5）より後ろの文は無名関数の本体になるので、そこにも `resume` を書けない。
操作節のガード（§13.4）と、`return` 節、`cancel` 節の中でも使えない。
操作節のガードは、操作を処理する節を選ぶための式であり、節の本体には含まれない。
節の中に書いた別の `handle` の操作節のガード、`return` 節、`cancel` 節も同じであり、そこには外側の節の `resume` を書けない。
一方、ガード、`return` 節、`cancel` 節の中に書いた別の `handle` の操作節の `resume` は、内側の節の継続を再開するものなので、書ける。
操作節の本体の中に書いた `match` の節のガード（§11.2）と条件式の条件は本体の一部なので、再開する操作の節では `resume` を書ける。
再開しない操作（§13.1）の操作節にも、`resume` を書けない。
その節の中に書いた無名関数や関数の定義の本体に書いた場合も同じであり、型検査に通らない。
その節の中に書いた別の `handle` の操作節の `resume` は、内側の節の継続を再開するものなので、書ける。
同じ継続を再開できるのは 1 回までであり、2 回目の再開は実行時エラーになる。

操作節の本体の末尾位置にある `resume` は、操作節の評価のために保持していた情報を捨ててから継続を再開する（§5.7）。
そのため、操作のたびにこの形で再開するハンドラの下では、操作を何回起こしても、それによって使う領域は増えない。

### 13.6. 巻き戻し

`resume` を呼ばない操作節では、処理系は中断していた残りの計算を破棄し、その節の値をハンドラ式の値にする。
節の値は、同じハンドラの操作節が末尾位置にない `resume` で再開した計算の中で決まったときは、ハンドラ式の値ではなくその `resume` の返り値になり（§13.5）、保留していた節の評価が続く。
`return` 節の値も同じである。
破棄する計算の中にあったハンドラは、内側から外側の順に巻き戻す。
例外や `defer` のための専用の構文はなく、この動作と後始末の節を組み合わせて書く。
再開する操作の節では、中断していた計算を破棄するのは、節の値が決まった後である。
そのため、再開する操作の節では、`resume` を呼ばない場合も、節の本体の中の関数呼び出しを末尾呼び出しとしては保証しない（§5.7）。
再開する操作の節の本体で、`resume` を呼ぶ前（`resume` の引数の評価中を含む）に実行時エラーが起きた場合と、本体から操作を起こして外側のハンドラが継続を破棄する場合は、継続がまだ生きているので、ハンドラが外側から巻き戻されるときと同じく、そのハンドラ自身の `cancel` 節を実行する。
このとき、節の評価の中で起動したハンドラの `cancel` 節、破棄する計算の中にあったハンドラの `cancel` 節（内側から外側の順）、そのハンドラ自身の `cancel` 節、さらに外側のハンドラの `cancel` 節の順に実行する。
`resume` で再開した計算の中で起きた実行時エラーでは、そのハンドラはまた有効なので、§15.5 のとおりそのハンドラ自身の `cancel` 節を 1 回実行する。
ただし、再開した計算の中で同じハンドラの操作節（ガードを含む）か `return` 節を評価している間（その節自身の `resume` で再開した計算の中にいる間を除く）に起きた実行時エラーには、前の文は当てはまらない。
そのハンドラ自身の `cancel` 節を実行するかどうかは、評価中のそのハンドラの節のうち最も内側のものについて、その節の規則で決まる。
その節が再開する操作の節の本体なら、`resume` を呼ぶ前に起きたときはこの段落の上の規則のとおり 1 回実行し、`resume` が戻った後に起きたときはこの段落の最後の文のとおり実行しない。
操作節のガードと再開しない操作の節の本体では、次の段落による。
`return` 節では実行しない。
`resume` が戻った後に節の本体で起きた実行時エラーと外側による破棄では、継続はもう無いので、そのハンドラ自身の `cancel` 節は実行しない。

再開しない操作（§13.1）の節では、処理系は節の本体を評価する前に、中断していた計算を破棄する。
操作節のガード（§13.4）は、破棄の前に評価する。
破棄が終わってから、ハンドラの外側で節の本体を評価し、その値をハンドラ式の値にする（末尾位置にない `resume` で再開した計算の中では、上のとおりその `resume` の返り値になる）。
そのため、破棄する計算の中にあったハンドラの `cancel` 節は、節の本体より先に実行される。
節の本体で起きた実行時エラーと、本体から操作を起こして外側のハンドラが継続を破棄することは、ハンドラ式の後ろで起きたものとして扱い、そのハンドラ自身の `return` 節と `cancel` 節は実行しない。
ガードの評価で実行時エラーが起きた場合と、ガードから操作を起こして外側のハンドラが継続を破棄する場合は、継続がまだ生きているので、ハンドラが外側から巻き戻されるときと同じく、そのハンドラ自身の `cancel` 節を実行する。
再開する操作の節のガードも同じである。
ハンドラ式が末尾位置にあれば、節の本体も末尾位置にある（同じハンドラの末尾位置にない `resume` で再開した計算の中を除く。§5.7）。
実行時エラーは操作ではなく、ハンドラで捕まえられない（§15.5）。

```keleut
effect Fail = { throw: (String) => Never }

let try_[A, E](body: () => A @ {Fail extends E}): #Ok(A) | #Err(String) @ E =
  body() handle {
    case throw(message) => #Err(message)
    case return(value) => #Ok(value)
  }
```

`case cancel => e` は、ハンドラが外側から巻き戻されるときの後始末を書く節である。
本体の実行時エラーによって巻き戻すときも、この節を実行する。
正常に終了したときの後始末は `return` 節に書く。
操作を処理したハンドラが、節の値を返して自分で継続を破棄して終わる場合、そのハンドラ自身の `cancel` 節は実行しない。
節の評価が実行時エラーや外側による破棄で脱出した場合は、上の規則による。

`cancel` 節は 1 個までで、型は `Unit` である。
省略すると、巻き戻すときに何もしない。
ガード、名前の修飾、巻き戻しの理由を受け取る引数は付けられない。

`cancel` 節は、自分のハンドラの外側で実行する。
そのため、`cancel` 節の中で同じエフェクトの操作を起こしても、自分の操作節には戻らない。
`cancel` 節の実行中に実行時エラーが起きたり、継続の破棄によってさらに脱出しようとしたりした場合、処理系はその `cancel` 節を打ち切る。
このとき脱出は外へ伝えず、診断として記録する。
そのうえで、外側のハンドラの後始末を続ける。
`cancel` 節から再開しない操作（§13.1）を起こした場合も同じである。
その操作のハンドラが行う破棄は、この打ち切りによって `cancel` 節の中で止まり、そのハンドラは操作節の本体を評価しない。
その操作を受け取るハンドラが、破棄を進めている当のハンドラであっても同じである。
打ち切りの後にそのハンドラの本体が値を返せば、その値（`return` 節があれば、それを通した値）がハンドラ式の値になる。

### 13.7. 標準のエフェクト

| 名前 | 操作または用途 | 利用者による `handle` |
| --- | --- | --- |
| `Console` | `write: (String) => Unit` | 不可 |
| `Print` | `print: (String) => Unit` | 可 |
| `Heap[h]` | リージョンの可変状態。操作宣言はない | `run` で処理 |
| `Blocking` | 外部関数のブロッキング。操作宣言はない | `pinned` で除去可能 |

トップレベルの評価で行に残せるエフェクトは、`Console` と `Blocking` である。
`Print` や利用者が定義したエフェクトは、ハンドラで処理しなければならない。
対話的な実行では、トップレベルに `Print` を残せる（§6.6）。

トップレベルの評価の規則は、ソースファイルごとに適用する。
import したファイルのトップレベルの評価も、行に残せるエフェクトは同じである。
そのファイルの初期化（§15.4）で起きるエフェクトは、ファイルの公開署名には現れない。

標準環境は、並行処理のためのエフェクトを持たない。
タスクの切り替え、`scope`、`spawn`、チャネル、期限付きの実行も、標準環境にはない。

## 14. リージョン

### 14.1. `run`

**リージョン**：可変状態を使える範囲を、型で区別するための局所的な領域。
`run h { ... }` は、新しいリージョン変数 `h` を導入して本体を評価し、その `Heap[h]` を外側のエフェクト行から除く。
別々の `run` が導入するリージョン変数は、綴りが同じでも別のものである。
`h` のカインドは `Type` なので、エフェクト行そのものとしては使えない。
`h` のカインドが値の型と同じ `Type` なので、型検査は、`Ref` と `MutableArray` の第 1 引数や `Heap` の引数にリージョン変数でない型を書いたプログラムを拒否しない。
たとえば `Ref[Int32, Int32]` を引数の型とする関数や、`@ Heap[Int32]` と注釈した関数は型検査に通る。
そのような型の値を作る手段はなく、`Heap[Int32]` を行に持つ関数は `run` の本体からもトップレベルからも呼べないので、評価には届かない。

`run` の結果の型に `h` を残すことはできない。
`Ref[h, A]` や `MutableArray[h, A]` を直接返す場合だけでなく、レコード、ヴァリアント、関数の型を通して `h` が残る場合も型検査に通らない。
外側の可変状態に保存するなどして、`h` を外側の型に持ち込むこともできない。

次の関数は、可変参照を使って配列の要素の和を求める。

```keleut
let sum(xs: Array[Int32]): Int32 = run h {
  let acc = Ref.new(0)
  Array.each(xs, fn(x) => Ref.set(acc, Ref.get(acc) + x))
  Ref.get(acc)
}
```

`sum` は内部で可変状態を使うが、外側に `Heap` を要求しない。
`run` が除くのは自分が導入した `Heap[h]` だけであり、出力などのほかのエフェクトは外側の行に残る。

`run h` の本体のエフェクト行は、外側のエフェクト行に `Heap[h]` を加えた行であり、`Heap[h]` は外側の行のどの `Heap` よりも左にある。
行の比較では同じラベルどうしの順序を区別するので（§3.4）、関数の呼び出し（§13.2）に限らず、2 つのエフェクト行を一致させるときは、`Heap` どうしを左から順に対応させる。
ここでの左右は、行を注釈で書いた場合は、注釈に書いた順序で決まる。
参照と可変配列の関数（§14.2、§14.3）は行に `Heap` を 1 個だけ持つので、その `Heap` は呼び出す位置のエフェクト行で最も左にある `Heap` と対応する。
これらの関数で作る参照や可変配列も、読み書きする参照や可変配列も、呼び出す位置で最も左にある `Heap` のリージョンに属する。
関数の本体では、その関数のエフェクト行が位置のエフェクト行になり、その行は、関数を呼び出す位置や、関数を渡す先の型のエフェクト行と一致しなければならない。
そのため、`run` の本体の中に書いた関数の本体、末尾ブロック（§5.5）の本体、`with` が後ろの文から作る無名関数（§6.5）の本体は、次の段落でいう `run` の本体に含めない。
入れ子の `run` の本体も、その `run` の `Heap` が最も左にあるので含めない。

`run h` の本体では `Heap[h]` が最も左の `Heap` なので、本体で作る参照や可変配列は `h` に属する。
ほかのリージョン（外側の `run` が導入したリージョン変数や、関数の型パラメータが表すリージョン）に属する参照や可変配列を本体で読み書きすると、型検査に通らない。
本体で呼び出す関数も、その呼び出しで決まるエフェクト行で最も左の `Heap` がほかのリージョンのものであれば、可変状態を使うかどうかにかかわらず、型検査に通らない。
`run` を囲む関数のエフェクト行にそのリージョンの `Heap` を書いても、その `Heap` は本体のエフェクト行で `Heap[h]` より右にあるので、型検査に通らないことは変わらない。
行に `Heap` を 2 個以上持つ関数を本体で呼び出すと、2 個目以降の `Heap` は `run` で除かれずに外側のエフェクト行に残り、外側の行の `Heap` と左から順に対応する。
2 個目以降の `Heap` のリージョンが `h` であれば、その呼び出しは型検査に通らない。
ほかのリージョンの参照や可変配列を本体の結果として返すことや、本体で作る参照や可変配列に格納することはできる。
それらを読み書きする関数を本体で作り、そのリージョンの `Heap` が最も左にある位置で呼び出すこともできる。

### 14.2. 参照

`Ref[h, A]` は、リージョン `h` に属し、型 `A` の値を保持する可変参照である。
次の署名の `[h, A]` は、型パラメータを示すための説明用の記法である。
この節の各署名は、§16 の冒頭に定める標準環境の署名の読み方で読む。
書いた行は閉じた行で、使うたびに開く。

```text
Ref.new : [h, A] (A) => Ref[h, A] @ Heap[h]
Ref.get : [h, A] (Ref[h, A]) => A @ Heap[h]
Ref.set : [h, A] (Ref[h, A], A) => Unit @ Heap[h]
```

`new` は新しい参照を作り、`get` は現在の値を返し、`set` は保持する値を置き換える。
`set` で値を置き換えても、保持する値の型は変えられない。

### 14.3. 配列

`Array[A]` は不変配列、`MutableArray[h, A]` はリージョン `h` に属する可変配列である。
どちらも添字は `Int32` で、有効な範囲は `0` 以上、長さ未満である。
範囲外の添字は実行時エラーになる。
次の署名も §16 の冒頭の読み方で読むので、`Array.length` と `Array.get` の最外の行は `@ {}` である。

```text
Array.length        : [A] (Array[A]) => Int32
Array.get           : [A] (Array[A], Int32) => A
Array.each          : [A, E] (Array[A], (A) => Unit @ E) => Unit @ E
MutableArray.new    : [h, A] (Int32, A) => MutableArray[h, A] @ Heap[h]
MutableArray.length : [h, A] (MutableArray[h, A]) => Int32 @ Heap[h]
MutableArray.get    : [h, A] (MutableArray[h, A], Int32) => A @ Heap[h]
MutableArray.set    : [h, A] (MutableArray[h, A], Int32, A) => Unit @ Heap[h]
MutableArray.freeze : [h, A] (MutableArray[h, A]) => Array[A] @ Heap[h]
```

`MutableArray.new(n, value)` は長さ `n` の配列を作り、すべての要素を `value` で初期化する。
`value` が可変参照などの場合、すべての要素が同じ値を共有する。
負の長さを指定すると実行時エラーになる。
配列の長さを変える操作はない。
`Array.each` は、添字の小さい順に各要素へ関数を適用する。

`freeze` が返した配列は、その後で元の可変配列に書き込んでも変わらない。
この保証は、要素を格納する配列そのもの 1 段にだけ及ぶ。
要素が可変参照や可変配列であれば、返した配列の要素は元と同じ参照や配列を指す。
要素の型に `h` が残る配列は、`freeze` した後もリージョンの外へ返せない。

不変配列の `length` と `get` は `Heap` を要求しない。
一方、可変配列は、読み取りや長さの取得にも `Heap[h]` を要求する。
配列リテラルや `Array.new` はないので、不変配列は可変配列を `freeze` して作る。

## 15. モジュールとファイル

### 15.1. 名前と可視性

モジュールは、複数の宣言を 1 個の名前の下にまとめる。
モジュールの外からは、中の値や型を `M.name`、`M.Type` のような修飾名で参照する。
モジュールの中では、同じモジュールの名前を修飾せずに参照できる。

```keleut
module Counter {
  pub newtype Counter(Int32)
  pub let initial(): Counter = Counter(0)
  let hidden_value: Int32 = 1
}

type Count = Counter
let count: Count = Counter.initial()
```

モジュールの外から参照させる宣言には `pub` を付ける。
`newtype` の型名とコンストラクタは、同じ可視性を持つ。
コンストラクタの名前は 1 個のソースファイルの中で一意なので（§10.1）、公開したコンストラクタは、モジュールの外でも修飾せずに使える。
モジュールと同じ名前の公開型を**コンパニオン型**と呼ぶ。
コンパニオン型は、`Counter.Counter` の代わりに `Counter` と書いて参照できる。

1 個のソースファイルの中では、可視性を区切るのはモジュールである。
モジュールに `pub` を付けても付けなくても、同じファイルの中から見た各宣言の可視性は変わらない。
ソースファイルの外への公開は §15.4 で定める。

型エイリアスの本体に現れる名前は、エイリアスを宣言したモジュールまたはソースファイルの中で解決する。
非公開の型を指す公開エイリアスを宣言すると、その型を別名を通して公開できる。
ただし、非公開のコンストラクタまで公開されるわけではない。

モジュールの中で修飾せずに書いた型の名前は、同じ名前のトップレベルや標準環境の型と別名より、そのモジュールの宣言を指す。
ただし、エフェクト行を書く位置（§3.3）で、モジュールの宣言が同じ名前を覆うのは、その宣言が `EffectRow` の別名のときだけである。
この別名は、同じ名前の標準環境のエフェクトやトップレベルの別名より優先する。
モジュールの `newtype` や、カインドが `Type` の別名は、エフェクト行を書く位置では何も覆わない。

### 15.2. 公開署名

`pub let` と `pub extern` には、各引数と返り値の型注釈が必要である。
値束縛の場合は、束縛全体の型を注釈する。
注釈の中の入れ子の矢印には、`@` を省略せずに書く。
この要求は、`pub newtype` のフィールドに書く矢印にも適用する。

最外の矢印の `@` だけは省略でき、その意味は §13.2 の省略の表に従う。

### 15.3. 宣言の制限

モジュールの中に書けるのは、`type`、`newtype`、1 個の名前を束縛する `let` と `let rec`、`type instance`、`extern` である。
入れ子のモジュール、エフェクト宣言、型クラス宣言、式文、分解パターンによる `let` は書けない。

モジュール内の値と、同じソースファイルのトップレベルの値（import した値を含む）に、同じ名前は付けられない。
モジュールと同じ名前の型は、`pub` の有無によらず、同じソースファイルのトップレベルの型名（import した型を含む）や、標準環境の型名とエフェクト名と同じ名前にできない。
`Ref.get` や `Eq.eq` のような標準の操作やクラスメソッドと同じ修飾名を、モジュール宣言で作ることはできない。
ただし、モジュール名そのものは予約されていないので、`Array` という名前のモジュールに標準環境にない名前を追加することはできる。

### 15.4. ソースファイルと import

プログラムは、1 個以上のソースファイルからなる。
処理系に渡した 1 個のファイルを**起点**と呼ぶ。

各ソースファイルのトップレベルは、1 個の名前空間である。
ファイルの中で参照できる名前は、そのファイルのトップレベルの宣言、そのファイルが import した名前、標準環境の名前である。
別のファイルの宣言は、import しない限り参照できない。
ファイルを修飾名で指す構文はない。

ファイルの外へ公開されるのは、トップレベルの宣言のうち `pub` を付けたものだけである。
`pub` を付けたモジュールの中の、`pub` を付けた宣言は、そのモジュールを import したファイルから修飾名で参照できる。
`pub` を付けないモジュールは、ファイルの外から参照できない。
ブロックの中の `let` と `let rec`、`type instance` の本体の `let` と `let rec` には `pub` を付けられない。
トップレベルの `with` より後ろの文は無名関数の本体になる（§6.5）ので、その中の宣言は公開できない。

**構文**

```text
from "パス" import 名前
from "パス" import { 名前, 名前, ... }
```

名前は、`x` や `T` のような 1 個の識別子か、`M.x` や `M.T` のように、モジュールの名前とその中の宣言の名前を `.` でつないだものである。
3 段以上の名前は書けない。
モジュールは入れ子にできない（§15.3）ので、指す先がないからである。
波括弧の中には 1 個以上の名前をカンマで区切って書き、最後の名前の後にもカンマを置ける。

import は、ファイルの先頭に、ほかの宣言と式文より前に書く。
`#!` の行とコメントは、import より前に置ける。
パスは文字列リテラルで書く。
計算したパスや、条件付きの import はない。

**束縛する名前**

`from "p" import n` は、パス `p` のファイルのトップレベルで名前 `n` を持つ公開の宣言を、すべて束縛する。
モジュールとそのコンパニオン型のように、1 個の名前が複数の宣言を指すときは、その全部を束縛する。
`from "p" import M.n` は、モジュール `M` の中で名前 `n` を持つ公開の宣言を束縛し、名前 `n` で参照できるようにする。
`M` は束縛しない。

`newtype` を束縛すると、そのコンストラクタも束縛する。
エフェクトを束縛すると、その操作も、同じファイルでエフェクトを宣言した場合と同じく修飾せずに使える。
型クラスを束縛すると、そのメソッドも同じく使える。
モジュールを束縛すると、その中の公開した宣言を修飾名で参照でき、公開したコンストラクタは修飾せずにも使える。

同じファイルに同じ名前の `pub` の値が 2 個以上あるときは、後の宣言が前の宣言を覆うので、最後の宣言を束縛する。
`pub` を付けない宣言は公開されないので、`pub` の値の後ろに同じ名前の `pub` の無い値を宣言しても、import で束縛するのは `pub` の値である。
公開していない宣言と、存在しない名前は import できない。
import した名前を別の名前に改める構文はない。

**パス**

パスの区切りは `/` である。
パスには `\` とコロンを書けない。
コロンは、ソースの種類を表す前置（`"kel:"` など）のために予約する。
`/` で始まる絶対パスは書けない。
処理系は、パスの末尾に `.kel` を付けてファイルを探す。
パスに `.kel` を書くことはできない。

`./` で始まるパスと、`../` を 1 個以上並べて始まるパスは、import を書いたファイルのあるディレクトリからの相対パスである。
それ以外のパスは、処理系に与えた検索パスの各ディレクトリからの相対パスである。
2 個以上の検索パスに該当するファイルがあるときは、誤りとする。
先頭の `./` と `../` を除き、パスの成分には、空の成分、`.`、`..` を書けない。

2 つのパスが同じファイルを指すかどうかは、シンボリックリンクを解決した絶対パスで判定する。

**読み込みと初期化**

処理系は、起点から import をたどり、到達したファイルをすべて読み込む。
同じファイルは、何回 import されても 1 回だけ読み込む。
import の循環は誤りである。
自分自身を import することも循環に含む。

すべてのファイルの型検査が終わってから、初期化を始める。
型の付かないファイルが 1 個でもあれば、どのファイルも初期化しない。
初期化は、各ファイルのトップレベルの式文、値束縛の初期化式、インスタンス宣言の中の値束縛の初期化式を、§6.4 の順に実行することである。
ファイルの初期化の順は、起点から import を書いた順に深さ優先でたどったときの帰りがけ順である。
したがって、import したファイルは、import したファイルより先に初期化する。
各ファイルは 1 回だけ初期化する。
起点は最後に初期化する。

各ファイルのトップレベルの評価の規則は §13.7 で定める。
読み込むファイルの集合と初期化の順は、パスと import の文面だけで決まり、プログラムを実行しなくても求められる。

**名前の衝突**

同じ種類の同じ名前を、異なる宣言を指す 2 つの import で束縛することはできない。
同じ宣言を重ねて束縛することはできる。
import した名前と同じ種類の同じ名前を、そのファイルのトップレベルで宣言することはできない。
import した値とトップレベルの値は、標準環境の同名の値を覆う。
名前の種類は、値、型（型エイリアスとエフェクトを含む。型とエフェクトは 1 つの名前空間を共有する）、コンストラクタ、型クラス、モジュールである。
型クラスを束縛すると、そのメソッドの名前も値の名前として数える。
したがって、同じ名前のメソッドを持つ 2 つの型クラスや、メソッドと同じ名前の値を、別々の import で束縛することはできない。
トップレベルで宣言した値は、ファイルの中で宣言した型クラスの場合と同じく、import した型クラスのメソッドの修飾しない名前を覆える。

**標準環境**

すべてのファイルは、標準環境を暗黙に import する。
標準環境の宣言は、`pub` の有無によらずすべて見える。
標準環境のファイルは import を書けない。

### 15.5. 実行の開始と終了

処理系は、起点から import でたどれるすべてのファイルを読み込んで型検査し、すべてが型検査に通ったときに限り、初期化（§15.4）を始める。
入口を表す関数の宣言はない。
起点の初期化が終わると、プログラムは正常に終了する。

**実行時エラー**：評価をそれ以上続けられない状態。
本書が「実行時エラーになる」と書く場合のほか、評価に要する領域が処理系の限度を超えた場合も実行時エラーとする。
実行時エラーが起きると、処理系は評価を止め、そのとき有効なハンドラを内側から外側の順に巻き戻して、各ハンドラの `cancel` 節を実行する（§13.6）。
実行時エラーが操作節の評価中に起きた場合、その節のハンドラ自身の `cancel` 節を実行するかどうかは §13.6 による。
その後、プログラムは実行時エラーで終了する。
実行時エラーを捕まえて評価を続ける構文はない。

プログラムの終わり方と、処理系が報告する終了状態を次に示す。

| 終わり方 | 条件 | 初期化 | 終了状態 |
| --- | --- | --- | --- |
| 正常終了 | 起点の初期化が終わった | すべて行う | 0 |
| 型検査での拒否 | 型検査に通らないファイルがあるか、import が誤っているか、型検査に要する領域が処理系の限度を超えた | 行わない | 1 |
| 字句と構文の誤り | 読み込んだファイルに字句エラーか構文エラーがあるか、読み込みに要する領域が処理系の限度を超えた | 行わない | 2 |
| 実行時エラー | 初期化の途中で実行時エラーが起きた | 途中まで行う | 3 |

処理系が実装していない機能を使った場合、ファイルを開けない場合、出力に書き出せない場合の終了状態は、処理系が定める。
読み込んだファイルの複数に誤りがあるとき、どの誤りを報告するかと、そのときの終了状態も、処理系が定める。

プログラムが標準出力に書いた内容（§16.3）は、正常終了のときも実行時エラーのときも、終了する前にすべて書き出す。
プログラムを実行するとき、処理系は診断と警告を標準エラーに書く。
診断には、字句エラー、構文エラー、型エラー、実行時エラー、処理系の限度を超えたことの報告と、`cancel` 節の打ち切り（§13.6）の記録を含む。
標準出力と標準エラーを同じ出力先にまとめたとき、診断は、それより前にプログラムが書いた内容の後ろに現れる。
型検査だけを行う機能など、プログラムを実行しない機能の診断の出力先は、処理系が定める。

**警告**：プログラムを拒否せずに、誤りの可能性を知らせる診断。
警告は、網羅漏れと到達できない節（§11.2）、到達しない操作節（§13.4）の 3 種類である。
処理系は、警告を型検査の段階で出し、初期化を始める前に書く。
警告があっても、プログラムは実行する。
処理系は、警告があるときに実行せず、型検査での拒否と同じ終了状態で終わる動作を、選べるようにしてよい。

対話的な実行（§6.6）では、入力が受理されなかったときや実行時エラーで止まったときも、実行は続く。
対話的な実行での診断の出力先は、処理系が定める。

## 16. 標準環境

本書が本文、`text` のブロック、表で示す標準環境の署名（§12.4、§14.2、§14.3、§16、§17 のメソッド、関数、操作、プリミティブの型）は、次のように読む。

- 署名の先頭の `[h, A]` のような角括弧は、型パラメータを示す説明用の記法であり、型式の構文ではない。
  型パラメータは使うたびに具体化する。
- 最外の矢印で `@` を省略した署名は、`@ {}` と書いた署名と同じである。
  `pub let` の注釈と型クラスのメソッドで最外の `@` を省略したとき（§13.2）と同じ読み方である。
- `extern "prim"` で宣言するプリミティブ（§16.4）の署名で最外の `@` を省略したときは、§13.2 の `extern "prim"` の規則に従い、使うたびに新しい行変数になる。
- 最外以外の矢印で省略した `@` は `@ {}` である（§13.2）。

閉じた行を持つ標準環境の関数と型クラスのメソッドは、利用者が宣言した関数と同じく使用時の開き（§13.2）を受ける。
演算子（§12.4）の使用は、対応するメソッドの呼び出しとして開く。
処理系が表示する型（§13.1）では、`@` を省いた矢印の行は行変数を表すので、署名の書き方とは読みが違う。

### 16.1. データ型

標準環境は次の型を含む。

```text
type Unit = {}
newtype Option[A] = None | Some(A)
newtype List[A] = Nil | Cons(head: A, tail: List[A])
newtype Never
```

このほか、基本型、`Ref`、`Array`、`MutableArray`、演算子クラス、標準のエフェクトを提供する。

基本型と、標準環境の型とエフェクトの名前は、トップレベルの型エイリアス、`newtype`、エフェクトの宣言に使えない（名前空間は §15.4）。
標準環境のクラスの名前は、トップレベルのクラスの宣言に使えない（名前空間は §15.4）。
標準環境が持つインスタンスと同じクラスと型構成子の組にも、インスタンスを宣言できない（§12.2）。
利用者が同じ名前空間（§15.4）の名前を重ねて宣言することはできない。
型エイリアス、`newtype`、エフェクトの間で、ある種類の宣言を別の種類の宣言で置き換えることもできない。

### 16.2. 文字列化

`Show[A]` はメソッド `show: (A) => String` を持つ。
`show(x)` と `Show.show(x)` は同じ操作である。

| 型 | 文字列化 |
| --- | --- |
| `Int32`、`Int64` | 符号付き 10 進数。型接尾辞は付けない |
| `Boolean` | `true` または `false` |
| `String` | 内容をそのまま返す。引用符は付けない |
| `Float64` | 下に定める数値表記 |
| `List[A]` | 要素が `Show` を持つとき、`[1, 2]`、空なら `[]` |
| `Option[A]` | 要素が `Show` を持つとき、`Some(1)` または `None` |

有限の `Float64` は、読み戻すと同じ値になる表記で文字列にする。
絶対値が `1e16` 未満の整数値には、小数点表記を使う。
それ以外の値では、有効数字の桁数 `p` を 1 から 17 まで順に増やし、`p` 桁に丸めた 10 進表記を読み戻して元の値になる最初の `p` を使う。
丸めた値の 10 進の指数が `-4` 未満か `p` 以上なら指数表記を、それ以外なら小数点表記を使い、不要な末尾のゼロを除く。
結果に小数点も指数もなければ `.0` を付け、指数からは `+` と先頭のゼロを除く。
たとえば `100000.0`、`0.0001`、`1e-5`、`1e16` のようになる。

非有限値は `nan`、`inf`、`-inf` と表示する。
これらの綴りは、ソースに書けるリテラルではない。
NaN の符号は表示しない。

### 16.3. 出力

```text
echo        : (String) => Unit @ Console
echoln      : (String) => Unit @ Console
println     : (String) => Unit @ Print
with_stdout : [A, E] (() => A @ {Print, Console extends E})
              => A @ {Console extends E}
```

`echo` は文字列を標準出力に書く。
`echoln` は文字列の後ろに LF を付けて書く。
`println` は、LF を付けた文字列で `Print.print` の操作を起こすだけであり、それだけでは標準出力に書かない。
`with_stdout` は、本体で起きた `Print` を処理して `Console` につなぐ。

```keleut
with_stdout(fn() => println("hello"))
```

### 16.4. プリミティブ

数値のプリミティブの名前と署名は、次の規則で決まる。
表の `T` は、名前に対応する数値型を表す説明用の記号である。

| 名前の形 | 対象 | 署名 |
| --- | --- | --- |
| `__int32_add`、`__int64_add`、`__float64_add` など | `add`、`sub`、`mul`、`div` | `(T, T) => T` |
| `__int32_rem`、`__int64_rem` | 整数の剰余 | `(T, T) => T` |
| `__int32_neg`、`__int64_neg`、`__float64_neg` | 符号反転 | `(T) => T` |
| 同じ接頭辞に `eq`、`lt`、`le`、`gt`、`ge` | 数値比較 | `(T, T) => Boolean` |
| `__show_int32` | 整数の文字列化 | `(Int32) => String` |

`%` と前置の `-` の標準のインスタンスは、`rem` と `neg` のプリミティブと同じ値を返す。

文字列には、次のプリミティブがある。

```text
__string_concat : (String, String) => String
__string_eq     : (String, String) => Boolean
__string_lt     : (String, String) => Boolean
__string_le     : (String, String) => Boolean
__string_gt     : (String, String) => Boolean
__string_ge     : (String, String) => Boolean
__string_length : (String) => Int32
__string_sub    : (String, Int32, Int32) => String
__panic         : [A] (String) => A
```

`__string_sub(s, pos, len)` は、`s` の位置 `pos` から `len` バイトを切り出して返す。
位置や長さが負の場合や、文字列の範囲を超える場合は実行時エラーになる。
`__panic` は、メッセージを付けて実行時エラーを起こす。
正常に値を返すことはない。

## 17. 外部関数

外部関数は `extern "C" let ...` か `extern "prim" let ...` で宣言する。
宣言に本体は書かない。
リンケージ名には、この 2 種類しか使えない。

```keleut
extern "C" let sqrt(x: Float64): Float64
extern "C" let sin(x: Float64): Float64 @ {}
let root = sqrt(9.0)
```

`"C"` で呼び出せる名前は `sin`、`cos`、`sqrt`、`exp`、`log` であり、どれも引数を 1 個取り、引数の型と返り値の型は `Float64` である。
これらの名前を、異なる引数型や返り値型で宣言することはできない。
エフェクトの注釈は、型とは別に付けられる。

ほかの名前の外部関数も署名は宣言できるが、呼び出すと実行時エラーになる。
任意の C ライブラリを読み込む機能はない。
モジュールの中で宣言した外部関数も、外部の名前には修飾しない関数名を使う。
標準環境のプリミティブの名前は、モジュールの中であっても `extern` で再宣言できない。

`extern "C"` で最外の `@` を省略したときの意味は、§13.2 の表に従う（`@ Blocking`）。
ブロックしない関数は、上の `sin` のように `@ {}` と書く。
`@ {}` の外部関数は、使用時の開き（§13.2）によって、どの行の文脈からも呼べる。
`extern "prim"` で `@` を省略すると、使うたびに新しい行変数になる（§13.2）。
`Blocking` は呼び出し側の行へ伝わり、トップレベルに残してよい。
`pinned` は、本体の行から `Blocking` を除いて結果を返す。
`Blocking` を含まない行の文脈（`@ {}` や `@ Console` と注釈した関数の本体、最外の `@` を省略した `pub let` の本体など）から `Blocking` の付いた関数を呼ぶには、`pinned` で包む。
`pinned` は `Blocking` を除くだけで、本体が純粋であることは確かめない。

```text
pinned : [A, E] (() => A @ {Blocking extends E}) => A @ E
```

`pinned` は本体を 1 回呼び出す。
外部呼び出しの中断、キャンセルの配送、ほかのタスクの実行は行わない。

## 18. 保存する性質

本節は、プログラムに施しても、受理されるかどうかと評価の結果を変えない変換を定める。
**評価の結果**：プログラムが標準出力に書いたバイト列と、終わり方（§15.5）の組。
処理系が表示する型、診断、警告の文面は、評価の結果に含めない。
これらの文面には名前と位置が現れるので、変換によって変わってよい。

### 18.1. 束縛名の付け替え

束縛の名前と、その束縛を指すすべての出現を一斉に別の名前に付け替えても、受理と評価の結果は変わらない。
対象の束縛は、`let`、`let rec`、`with` で束縛する名前、関数、無名関数、ハンドラの節の引数、パターンの変数、型パラメータ（行の型パラメータを含む）、`run` のリージョン変数である。
新しい名前は、次の 3 つを満たすものに限る。

- その位置に書ける識別子である（§2.2）。
- 付け替える束縛の有効範囲で、ほかの束縛を指していた出現を、新しい名前の束縛が指すようにしない。
- 付け替える束縛を指していた出現を、ほかの束縛が指すようにしない。
- 新しい名前が、モジュールの中の値とトップレベルの値（§15.3）、import した名前（§15.4）の衝突の規則に触れない。

レコードの式とパターンのパンニング（`{a,}`、`{x}`）で書いた出現は、ラベルと変数を兼ねるので、`{a = a,}`、`{x = x}` の形に展開してから変数の側だけを付け替える。
`pub` を付けた宣言の名前は、それを import するファイルの名前でもあるので、import する側の出現も同時に付け替える。
単独の `_` は識別子ではないので、変数を `_` に付け替えることはこの変換に含まない（`with` では渡す関数の引数の個数も変わる。§6.5）。
`extern` で宣言した名前は外部の名前でもある（§17）ので、対象に含まない。

### 18.2. 依存のない宣言の並べ替え

トップレベル、モジュールの本体、ブロックの中で隣り合う 2 つの文が次の 4 つを満たすとき、2 つを入れ替えても、受理と評価の結果は変わらない。

1. 一方が束縛する名前を、他方が参照しない。
   名前には、値、型、コンストラクタ、エフェクトとその操作、型クラスとそのメソッドを含む。
   参照には、文に直接書いた出現のほか、参照する関数の本体と値束縛の初期化式を、くり返したどって現れる出現を含む。
   使うたびに評価する値束縛（§6.4）の初期化式もたどる。
   メソッドの呼び出しや制約の解決で使うインスタンスのメソッドの本体と初期化式も、同じくたどる。
   一方がインスタンス宣言のときは、他方が、上の意味で参照する範囲で、メソッドの呼び出し（演算子を含む。§12.4）や制約の解決（§12.1）によってそのインスタンスを使わないことも求める。
2. 2 つが同じ名前を束縛しない。
3. 少なくとも一方は、初期化で式を評価しない宣言である。
   そのような宣言は、型エイリアス、`newtype`、エフェクト、型クラス、値束縛で書いたメソッドを持たないインスタンス、関数束縛と `let rec` の群、`extern` である。
   そうでなければ、2 つの評価がどちらも終了し、エフェクトを起こさず、実行時エラーにならない。
4. 2 つが、一般化しない束縛（§6.2）と型を注釈していない引数のうち、同じものを条件 1 の意味で参照しない。

次の文は、この変換の対象にしない。

- ブロックの最後の文。その値がブロックの値になる（§5.4）。
- `with` と、その後ろの文。後ろの文は、`with` の右辺の呼び出しに渡す無名関数の本体になる（§6.5）。
- import。その順序はファイルの初期化の順を決める（§15.4）。

`let rec` と `and` でつないだ再帰群の中の束縛の順序を変えても、受理と評価の結果は変わらない。
ただし、群の中のある束縛の本体が、型パラメータを持つ別の束縛を、その型パラメータを何かの型に決める形で使う群は除く（`f[A]` の本体が `g[B]` の `B` を `A` に決める形や、`B` の位置に `Int32` の値を渡す形）。
群の中の参照の一部は単相に扱われる（§6.3）ので、そのような群は、束縛を書いた順序によって型検査に通らないことがある。

4 つ目の条件は、型の決まる順序が受理を変えることがあるので置く。
たとえば、次の 2 つの宣言は互いを参照しないが、一般化しない束縛 `r` を共有する。

```keleut
let idf[A](x: A): A = x
let r = idf(fn(y) => y)
let b: Int64 = r(2)
let a = r(1)
```

この順序では `r` の型が `(Int64) => Int64` に決まり、どちらの宣言も型検査に通る。
`a` と `b` を入れ替えると、`a` の宣言の終わりで `r` の型が `(Int32) => Int32` に決まり（§4.2）、`b` の宣言は型検査に通らない。
§13.2 の制限に書いた、文の順序によって受理されるかどうかが変わる形も、この条件で除く。

### 18.3. ラベルの順序

型に書いた異なるラベルの順序を入れ替えても、受理と評価の結果は変わらない。
対象は、レコード型のフィールド、構造的ヴァリアント型のケース、エフェクト行のラベル（§3.4、§13.1）と、レコードのパターンのフィールドである。

レコード式のフィールドと、コンストラクタの名前付き引数に書いた順序は、評価の順序を決める（§5.1）。
名前付き引数の順序の入れ替えは、入れ替える引数の間に位置で指定する引数が無い場合に限る（位置で指定する引数が埋めるフィールドが変わる。§10.2）。
これらの順序を入れ替えても受理は変わらず、各式の評価が終了し、エフェクトを起こさず、実行時エラーにならないときは、評価の結果も変わらない。

同じラベルどうしの順序（タプルの要素、行に並んだ `Heap`）は型の一致で区別するので（§3.4、§14.1）、この変換に含まない。

### 18.4. 型エイリアスへの置換

型を書く位置で、型式を、それと同じ型に展開される型エイリアスの使用に置き換えても、受理と評価の結果は変わらない。
エイリアスの使用を、それを展開した型式に置き換えても同じである。
展開した型式は、エイリアスの本体の名前を、エイリアスを宣言した位置で解決した型（§15.1）と同じ型を指すように書く。
エフェクト行の別名（§3.3）にも、この性質を適用する。

ただし、次の位置は除く。

- インスタンスの対象。対象は型構成子に限る（§12.2）ので、エイリアスに置き換えられない。
- `pub` の宣言の注釈と `pub newtype` のフィールドの型。§15.2 は、そこに直接書いた矢印に `@` を求めるが、エイリアスの本体の矢印には求めない。
  そのため、`@` を省略した矢印を含む型をエイリアスに置き換えると、拒否していた宣言を受理する。
- `pub` のない値束縛の注釈の先頭の矢印で、`@` を省略したもの。
  この位置で省略した `@` は本体からの推論を表し、エイリアスの本体の矢印で省略した `@` は `@ {}` を表す（§13.2）ので、置き換えると型が変わる。
- エフェクトの操作の型。§13.1 は矢印型を直接書くことを求める。
  操作の引数と返り値の型の中は置き換えられ、再開しない操作の判定（§13.1）も展開した型で行う。
- エイリアスの本体で使わないパラメータに行を渡す形。使わないパラメータのカインドは `Type` になる（§3.2）ので、行変数を渡すと受理が変わる。
- 型の宣言群の中で、後ろで宣言するエイリアスに `{}` を型引数として渡す位置。パラメータのカインドが決まる前なので、`{}` は空のレコード型と読まれる。

### 18.5. 対話的な実行で受理しなかった入力

対話的な実行（§6.6）で、受理した入力の列の間に、受理しなかった入力を挟んでも、受理した各入力の受理、表示、評価の結果は変わらない。
受理しなかった入力が後の入力から見えないこと（§6.6）による。
ただし、実行時エラーで止まった入力が止まるまでに書いた出力は残る（§6.6）。

本付録は、Keleut の字句と構文を定める。
各節の散文は、構文の意味と、この文法が受けても型検査が拒むもの（たとえば §13.1 のエフェクトの型パラメータ）を定める。

### A.1. 記法

| 記法 | 意味 |
| --- | --- |
| `"let"` | その綴りの終端記号 |
| `exp` | 非終端記号 |
| `a b` | 並び |
| `a \| b` | 選択 |
| `a?`、`a*`、`a+` | 省略可、0 回以上、1 回以上 |
| `( ... )` | まとめ |
| `list0(x)` | `( x ( "," x )* ","? )?`。カンマで区切る 0 個以上の並びで、末尾のカンマを許す |
| `list1(x)` | `x ( "," x )* ","?` |

字句の段階で、すべての `{` を §5.4 の表で 3 つに分類する。
表は式の位置について定めたものだが、字句の段階では位置によらず同じ表を当てる。
ただし `import` の直後の `{` はレコードの形とする。
`LBRACE_BLOCK`、`LBRACE_RECORD`、`LBRACE_TYPE` は、それぞれブロック、レコード、レコード型の形に分類した `{` を表す。
`"{"` と書いた位置では、どの分類の `{` でもよい。
型、パターン、宣言の本体の位置では、分類は A.3 の改行の扱いにだけ効く。
`sep` は文の区切り（A.3）である。

### A.2. 字句

```text
lower_ident ::= ( "a"…"z" | "_" ) idchar*     -- 予約語と、単独の "_" を除く
upper_ident ::= "A"…"Z" idchar*
idchar      ::= "a"…"z" | "A"…"Z" | "0"…"9" | "_"
hash_label  ::= "#" upper_ident                -- "#" と名前の間に空白を置かない
number      ::= dec_number | hex_number | oct_number | bin_number
dec_number  ::= digit ( digit | "_" )*
                ( "." ( digit ( digit | "_" )* )? )?
                ( ( "e" | "E" ) ( "+" | "-" )? digit+ )?
                ( ( "i" | "u" | "f" ) digit+ )?
hex_number  ::= "0x" hexdigit ( hexdigit | "_" )* ( ( "i" | "u" ) digit+ )?
oct_number  ::= "0o" octdigit ( octdigit | "_" )* ( ( "i" | "u" ) digit+ )?
bin_number  ::= "0b" bindigit ( bindigit | "_" )* ( ( "i" | "u" ) digit+ )?
text        ::= '"' ( text_char | escape )* '"'
text_char   ::= '"' と "\" を除く任意の文字。改行と CR を含む
escape      ::= "\" ( "n" | "t" | "r" | "a" | "b" | "f" | "v" | "\" | '"' | "'" )
              | "\u" hexdigit hexdigit hexdigit hexdigit
              | "\U" hexdigit hexdigit hexdigit hexdigit hexdigit hexdigit hexdigit hexdigit
```

字句は、最も長く一致する綴りで切る。
そのため `1.foo` は数値 `1.` と識別子 `foo` に、`1u8` は 1 個の数値に切れる。
数値の接尾辞として意味を持つのは `i32`、`i64`、`f64` だけであり、ほかの接尾辞を持つ数値は型検査で拒否する（§4.2）。
16 進、8 進、2 進の数値は、小数点、指数、`f` の接尾辞を持たない。

予約語は §2.2 の表の語である。
記号は次のとおりである。

```text
(  )  [  ]  {  }  ,  ;  :  .  =  =>  @  |  \  ...  ???
+  -  *  /  %  !  ==  !=  <  <=  >  >=  &&  ||
```

改行を含むブロックコメントは、改行として扱う（§2.1）。
それ以外のコメントと、空白、タブ、CR は、トークンを区切るだけである。
改行は、A.3 の規則で文の区切りになるときだけ意味を持つ。
ファイルの先頭の `#!` の行は読み飛ばす。

### A.3. 文の区切り

改行の直前のトークンが次の「終端トークン」で、直後のトークンが次の「始端トークン」であれば、その改行を `sep` とする。
それ以外の改行は捨てる。

- 終端トークン：`)`、`]`、`}`、`lower_ident`、`upper_ident`、`hash_label`、`number`、`text`、`true`、`false`、`???`。
- 始端トークン：`let`、`type`、`newtype`、`effect`、`module`、`pub`、`extern`、`val`、`with`、`perform`、`resume`、`run`、`fn`、`from`、`if`、`lower_ident`、`upper_ident`、`hash_label`、`number`、`text`、`true`、`false`、`???`、`!`、`{`、`(`。

始端トークンに無いトークン（二項演算子、`.`、`\`、`match`、`handle`、`then`、`else`、`and`、`extends`、`|`、`case`、`import` など）で始まる行は、前の行に続く。
次の範囲の中では、改行をすべて捨てる。

- `(` と `)` の間、`[` と `]` の間。
- `LBRACE_RECORD` と `LBRACE_TYPE` で始まる波括弧の中。
- `case` から、その節の `=>` まで。節のガードの中の `fn(...) =>` の矢印は数えて読み飛ばす。

範囲の中にさらにブロック（`LBRACE_BLOCK`）を書くと、そのブロックの中では上の規則で改行を区切る。

```text
sep ::= ";" | 改行
```

### A.4. プログラムと宣言

```text
program      ::= items
               | import_decl ( sep+ import_decl )* ( sep+ items )?
import_decl  ::= "from" text "import" ( import_name | LBRACE_RECORD list1(import_name) "}" )
import_name  ::= ( upper_ident "." )? ( upper_ident | lower_ident )

items        ::= sep* item_seq?
item_seq     ::= item ( sep+ item_seq? )?
               | "with" pat "=" exp ( sep+ items )?
item         ::= decl | exp

decl         ::= "pub"? decl_body
decl_body    ::= "let" binding
               | "let" "rec" binding ( "and" binding )*
               | "type" upper_ident typarams? ( ":" upper_ident )? "=" ty
               | "type" "class" upper_ident typarams class_body
               | "type" "instance" typarams? upper_ident "[" list1(ty_arg) "]" "{" items "}"
               | "newtype" upper_ident typarams? newtype_rhs
               | "effect" upper_ident typarams? "=" "{" list0(eff_op) "}"
               | "module" upper_ident "{" items "}"
               | "extern" text "let" lower_ident typarams? "(" list0(param) ")" sig_tail

binding      ::= lower_ident typarams? "(" list0(param) ")" sig_tail "=" exp
               | bind_pat ( ":" ty )? "=" exp
sig_tail     ::= ( "@" eff )?
               | ":" ty_ret
ty_ret       ::= union_ty ( "@" eff )?
               | arrow_ty
param        ::= pat ( ":" ty )?

class_body   ::= "{" sep* ( class_item ( sep+ class_item )* )? sep* "}"
class_item   ::= "val" lower_ident typarams? ":" ty
newtype_rhs  ::= ( "(" list0(ctor_field) ")" )?
               | "=" ctor ( "|" ctor )*
ctor         ::= upper_ident ( "(" list0(ctor_field) ")" )?
ctor_field   ::= ty | lower_ident ":" ty
eff_op       ::= lower_ident ":" ty

typarams     ::= "[" list1(typaram) "]"
typaram      ::= ( lower_ident | upper_ident ) ( "[" list1("_") "]" )? ( ":" upper_ident ( "+" upper_ident )* )?
```

`pub` は、`type instance`、`type instance` の本体の `let` と `let rec`、式文、ブロックの中の `let` には付けられない。
`with` の右辺は関数呼び出しでなければならない（§6.5）。
`with` は残りの `items` をすべて本体に取るので、同じ並びの最後の文になる。
`import_decl` の前には `sep` を置けない。
`extern` の文字列は `"C"` か `"prim"` に限る（§17）。

### A.5. 式

```text
exp          ::= "fn" "(" list0(param) ")" "=>" exp
               | "if" exp "then" exp "else" exp
               | postfixed
postfixed    ::= postfixed "match" clause_body
               | postfixed "handle" clause_body
               | or_exp
or_exp       ::= or_exp "||" and_exp | and_exp
and_exp      ::= and_exp "&&" cmp_exp | cmp_exp
cmp_exp      ::= add_exp cmp_op add_exp | add_exp
cmp_op       ::= "==" | "!=" | "<" | "<=" | ">" | ">="
add_exp      ::= add_exp ( "+" | "-" ) mul_exp | mul_exp
mul_exp      ::= mul_exp ( "*" | "/" | "%" ) prefix_exp | prefix_exp
prefix_exp   ::= "!" prefix_exp
               | "-" prefix_exp
               | postfix_exp
postfix_exp  ::= postfix_exp "." ( lower_ident | upper_ident )
               | postfix_exp "\" lower_ident
               | postfix_exp "(" list0(arg) ")"
               | tb_call
               | atom
tb_call      ::= postfix_exp "(" list0(arg) ")" trailing_block
               | postfix_exp "." lower_ident trailing_block
               | lower_ident trailing_block
trailing_block ::= block
               | LBRACE_BLOCK lower_ident "=>" items "}"
               | LBRACE_BLOCK clause+ "}"
arg          ::= ( lower_ident "=" )? exp
atom         ::= number | text | "true" | "false" | "???"
               | lower_ident | upper_ident | hash_label
               | "perform" long_id "(" list0(arg) ")"
               | "resume" "(" ( exp ","? )? ")"
               | "run" lower_ident "{" items "}"
               | block
               | record_exp
               | paren_exp
block        ::= LBRACE_BLOCK items "}"
record_exp   ::= LBRACE_RECORD "}"
               | LBRACE_RECORD "extends" exp "}"
               | LBRACE_RECORD list1(field) ( "extends" exp )? "}"
               | LBRACE_RECORD lower_ident "with" list1(field) "}"
field        ::= lower_ident ( "=" exp )?
paren_exp    ::= "(" ")" | "(" exp ")" | "(" exp "," ")" | "(" exp "," list1(exp) ")"
clause_body  ::= "{" clause* "}"
clause       ::= "case" pat ( "if" exp )? "=>" exp
long_id      ::= lower_ident | upper_path | upper_path "." lower_ident
upper_path   ::= upper_ident ( "." upper_ident )*
```

非終端の階層は、§5.2 の表の優先順位を表す。
`fn` と条件式（§5.8）は `atom` に含まれないので、演算子のオペランドや呼び出し先に書くときは括弧で囲む。
後置の `match` の照合対象と `handle` の本体は、直前の `postfixed` 全体（`or_exp` か、それに後置の `match` や `handle` を付けたもの）である。
括弧で囲まない数値リテラルに付けた `-` は、負の数値リテラル（§4.2）として読む。
`tb_call` の 3 つの形のほかに末尾ブロックを書く位置はない（§5.5）。
`LBRACE_BLOCK lower_ident "=>" ...` と `LBRACE_BLOCK clause+ ...` は、`trailing_block` としてだけ書ける。
`perform` と `resume` の後ろ、括弧で囲んだ式の後ろ、コンストラクタと構造的ヴァリアントの後ろに末尾ブロックは書けない。
末尾ブロックの `{` は、直前のトークンと同じ行に書く（§2.3）。A.3 で改行を捨てる範囲の中でも同じである。
`hash_label` の引数にはラベルを付けられない（§9）。
`resume` の引数にはラベルを付けられない。

### A.6. パターン

```text
pat          ::= "_" | "-"? number | text | "true" | "false"
               | long_id ( "(" list0(pat_arg) ")" )?
               | hash_label ( "(" list0(pat_arg) ")" )?
               | record_pat
               | paren_pat
bind_pat     ::= "_" | lower_ident
               | upper_path ( "(" list0(pat_arg) ")" )?
               | record_pat
               | paren_pat
pat_arg      ::= ( lower_ident "=" )? pat
record_pat   ::= "{" ( pat_field "," )* ( pat_field | "..." lower_ident )? "}"
pat_field    ::= lower_ident ( "=" pat )?
paren_pat    ::= "(" ( pat "," )* ( pat | "..." lower_ident )? ")"
```

`long_id` が小文字で始まる 1 個の識別子なら変数、それ以外は引数のないコンストラクタのパターンである。
`pat_field` の `lower_ident` だけの形は、同じ名前のラベルと変数を表す。
`paren_pat` の中身がカンマも `...` も持たない 1 個のパターンなら、括弧でまとめただけである（§11.1）。
`bind_pat` は `let` の束縛にだけ使い、リテラル、構造的ヴァリアント、小文字で始まる名前の呼び出しの形を持たない。

### A.7. 型

```text
ty           ::= union_ty | arrow_ty
arrow_ty     ::= "(" list0(ty) ")" "=>" arrow_ret
arrow_ret    ::= union_ty ( "@" eff )?
               | arrow_ty
union_ty     ::= union_ty "|" app_ty | app_ty
app_ty       ::= atom_ty ( "[" list1(ty_arg) "]" )?
ty_arg       ::= ty | "_"
atom_ty      ::= long_id
               | hash_label ( "(" list0(ty) ")" )?
               | brace_ty
               | "(" ")"
               | "(" ty ")"
               | "(" ty "," list0(ty) ")"
brace_ty     ::= "{" "}"
               | "{" "extends" ty "}"
               | "{" list1(brace_item) ( "extends" ty )? "}"
brace_item   ::= lower_ident ":" ty
               | eff_name
eff          ::= eff_name | brace_ty
eff_name     ::= long_id ( "[" list1(ty_arg) "]" )?
```

`arrow_ty` の `"(" list0(ty) ")"` は引数の並びであり、`=>` が続くかどうかで `atom_ty` の括弧と区別する。
`brace_ty` がレコード型とエフェクト行のどちらを表すかは、要素の形と位置で決まる（§3.1、§13.1）。
`@` は、`arrow_ret` の最初の形でだけ書け、直前の矢印に付く。

### A.8. 文法から読める制限

- 矢印を返す矢印の外側の `@`：`arrow_ret` の 2 つ目の形（返り値がさらに矢印）は `@` を持たない。
  関数束縛でも、`ty_ret` の 2 つ目の形（返り値の型が矢印）は `@` を持たないので、返り値の型の後ろの `@` は返り値の矢印に付く。
  関数自身の行を書くには、返り値の型を省いて `@` だけを書くか、返り値の矢印を括弧で囲む（`(A) => ((B) => C) @ E`、`let f(x: A): ((B) => C) @ E = ...`）。
- 値束縛の型パラメータ：`binding` の 2 つ目の形は `typarams` を持たない。
  型パラメータを書けるのは、関数束縛、型エイリアス、`newtype`、型クラスとそのメソッド（`class_item`）、インスタンスの前提、`extern` である。
- 操作の型パラメータ：`eff_op` は `typarams` を持たない。
  エフェクトの宣言の `typarams` は文法が受けるが、§13.1 が禁じる。
- 型クラスの型パラメータ：`type class` の `typarams` は省略できない。
- 外部関数の形：`extern` は関数束縛の形だけを持ち、値束縛の形を持たない。
- 無名関数の注釈：`exp` の `fn` の形は、返り値の型とエフェクト行を持たない。
- 式の型引数：呼び出しに型引数を書く形はない（§3.2）。
