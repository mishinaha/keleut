## 1: 14 節に足す規則の例示「誤りの訂正」が、すぐ上の「意味や符号を変えるときは、主版を上げる」と衝突しうる

- 観点: spec
- 重さ: medium
- 節: 3.2(D556 の 14 節に足す文)、9 節のリスクの 4 行目

### 根拠

案の文は「KIR の節、命令、欄の意味と符号を変えない本文の改訂(診断の文面について読み手に許す範囲を広げることや、誤りの訂正)では、版を変えない」である。訂正には意味を変えるものもある。前例に挙げた 0.3 の間の改訂には、意味の訂正が入っている(IRSpec 1715 行末尾「レコードのパターンの `open` が書かないフィールドを持つレコードにも一致すること(8 節)を正した」、コミット 405e592)。1.0 の後に同じ種類の訂正をすると、括弧の例示では「版を変えない」、1690-1692 行では「主版を上げる」と読め、どちらの規則に従うのか決まらない。9 節のリスクの対策も「誤りの訂正」に限るとしか書いておらず、この点を防げない。草稿の 0.3 は読み手が同じ 0.y だけを受け付けていたので、版を上げずに直すことができた。1.0 の後の前例としては弱い。

### 直し方

例示を「誤りの訂正のうち、Diktor と RustKeleut の書き手と読み手の振る舞いと、KIR の受理と意味を変えないもの(誤記、参照の誤り、説明の補い)」に限る。あるいは「誤りの訂正」を外し、「読み手に許す診断の文面の範囲を広げる改訂」だけにする。そのうえで「意味を変える訂正は、訂正であっても上の規則に従う」と 1 文足す。3.2 節の理由にある 0.3 の前例は、草稿の版では版の規則が違っていたことを添えて引く。

### 反証者 1: 反証した

指摘の中心は「誤りの訂正」の例示が主版の規則と衝突して、どちらに従うか決まらないという主張である。案の文の書き方からすると、この主張は成り立たない。

計画 doc/log/261104-1-plan.md の 253 行の文は「KIR の節、命令、欄の意味と符号を変えない本文の改訂(診断の文面について読み手に許す範囲を広げることや、誤りの訂正)では、版を変えない」である。括弧の例示は「意味と符号を変えない本文の改訂」を修飾する挿入句で、その類の中の例を挙げている。したがって、意味を変える訂正はこの文の適用範囲に入らない。それは IRSpec 14 節の「意味や符号を変えるときは、主版を上げる」(doc/IRSpec.md、1689-1692 行付近の箇条)にそのまま従う。2 つの規則は適用範囲が重ならず、選ぶ必要が生じない。計画 486 行のリスクの対策も、規則を「読み手に許す範囲を広げる改訂と誤りの訂正」に限る、としか言っていない。これは制限句を外す読みではない。

0.3 の前例についての点も検めた。IRSpec の履歴表の 0.3 の行の末尾に「レコードのパターンの `open` が…一致すること(8 節)を正した」がある。この行は「(草稿)」と明記されている。同じ 14 節の 1685 行には、「0.y は草稿の版で、読み手は書き手と同じ 0.y だけを受け付けた」と書かれている。前例の性質が違うことは、計画が改訂する本文自体に書いてある。計画 3.2 節の理由も、この前例を「版を上げず履歴に書いた」扱いの前例として引いているだけで、意味の訂正を版なしで許す根拠にはしていない。

残る点は文言の明確さだけで、low 相当である。たとえば括弧内を「誤記や参照の誤りの訂正」とすれば紛れはさらに減る。いずれにしても、計画どおりに進めて誤った成果物や受け入れの失敗になる問題ではなく、medium の修正には値しない。

## 2: D555 の文の「外側(後で足したもの)」が、レコードのリテラルについての LangSpec §7 の定義と読み違えを生む

- 観点: spec
- 重さ: medium
- 節: 3.1(1836 行の改訂案の 4 文目)、8 節 D555

### 根拠

LangSpec §7 は「同じラベルを重ねて書いた場合は書いた順を保存し、最初に書いたフィールドを最も外側とする」と書く(`awk` で §7 を抜き出した 38 行目)。リテラル `{x = 1, y = 2, x = 3}` では、最も外側は最初に書き、最初に評価する `x = 1` である。これを「後で足したもの」と呼ぶと、書いた順や評価の順の後と読める。実測では、Diktor も 3 つの後段も `x = 1` を先に書いた(scratchpad verify/spec-text/p1.kel: Diktor `{x = 1, y = 2, x = 3}`、interp/wasm/jit `{x = 1, x = 3, y = 2}`)。p5.kel の更新(`{r with x = 7}`)でも同じだった。言い回しは lir.md:122 から写したものだが、lir.md は内部の文書である。規範の文に置くと読み手の実装者を誤らせうる。

### 直し方

「同じラベルのフィールドどうしは、最も外側(言語仕様 §7。リテラルでは最初に書いたもの、`extends` では左のもの、タプルでは前の要素)から順に書く」と、LangSpec §7 と §8 の定義を指す形に改める。

### 反証者 1: 反証できなかった

反証できなかった。計画 doc/log/261104-1-plan.md:237 の改訂案は「同じラベルのフィールドどうしは外側(後で足したもの)から順に書き」としており、括弧の言い換えは rustkeleut/doc/lir.md:122 の「外側(後で足したもの)を先に置く」を写したものである。規範の側を見ると、LangSpec.md:790 は「同じラベルを重ねて書いた場合は書いた順を保存し、最初に書いたフィールドを最も外側とする」と書いている。IRSpec も 579、655 行などで「外側」とだけ書き、「後で足した」という言い換えは使っていない。つまり、レコードのリテラル `{x = 1, y = 2, x = 3}` で最も外側になるのは、最初に書いた `x = 1` である。拡張(LangSpec.md:775、`{x = v extends p}`)では外側が後で足したものと一致する。しかしリテラルや、関数の引数の `_item` の行(IRSpec.md:505「最初の仮引数を最も外側にする」)では、書いた順の「後」と読める言い換えは逆を指しうる。実物でも確かめた。scratchpad の verify/spec-text/p1.kel を Diktor で実行すると `{x = 1, y = 2, x = 3}` と表示され、最初に書いた x = 1 が先に来る。計画の 3.1 節の理由の箇条(226 行)も同じ言い回しを使っており、この曖昧さには答えていない。付録 B は規範の文書なので、言い換えを外して「外側(LangSpec §7 の定義による)」とするか、指摘のとおり定義を指す形に改める価値がある。誤った成果物は生まないので、重大度は medium から low が妥当である。

## 3: D555 の 3 文目が、Diktor の作った順による違いを明示的には覆わない

- 観点: spec
- 重さ: low
- 節: 3.1(1836 行の改訂案の 3 文目)
