- リストの順は値の作り方で決まる。
  - 拡張は先頭に足す(`value.ml:334`)。
  - 更新はその場で差し替えるので、位置が変わらない(`value.ml:353-358`)。
  - 制限は同名のうち最も左の 1 つだけを消す(`value.ml:337-342`)。
- `ir_eval`(`--run-ir`)の `show` も同じ書き方をする(`diktor/lib/ir_eval.ml:253-264`)。レコードの演算も同じで、拡張は先頭に足し(`ir_eval.ml:777-780`)、更新はその場で差し替える(`ir_eval.ml:303-305`)。22.4 節の冒頭(`ir_eval.ml:282-286`)に「第12章 §12.6 と同じ規則」と書いてある。

- レコードには構造的な `Show` がない。構造的な辞書は `Eq` 専用で、ほかのクラスに使うと内部エラーになる(`interp.ml:526-531`)。したがって、レコードのフィールドの順が見えるのは、実行時エラーの `<値>` と REPL の表示の 2 か所だけである。
- 実測した(diktor は `_build/install/default/bin/diktor`、入力は scratchpad `p253/{a,b,c,d}.kel`)。
  - 木、`--run-ir`、`--via-ir` の 3 つで、`<値>` の綴りはすべて同じだった。
    - a: 型 `{b, a}` の照合に `{a = 1, b = 2}` を渡す → `{a = 1, b = 2}`
    - b: `{c = 3 extends base}` → `{c = 3, a = 1, b = 2}`
    - c: `{base with b = 9}` → `{a = 1, b = 9}`
    - d: `{b = 1, a = 2, c = 3}` → `{b = 1, a = 2, c = 3}`
  - `keleut run --backend interp` は b を `{a = 1, b = 2, c = 3}`、d を `{a = 2, b = 1, c = 3}` と書いた。a と c は Diktor と同じだった。
  - 記録 2100 行付近では、a の形の例で keleut が `{b = 2, a = 1}` を書くとしている。今回の入力では `{a = 1, b = 2}` だった。ラベルの番号の振り方の違いによるものと推測する。記録の例の書き直しは、親の計画で扱う事柄である。
- REPL の比較(入力は `p253/repl.in`)。
  - Diktor は `k : {m: Int32, n: Int32} = {n = 1, m = 2}` と書く。型は行の順、値は作った順で、Diktor の中でも表示の順がそろっていない。`keleut repl` は `{m = 2, n = 1}` と書く。
  - コーパスの `ir_emit/0004-rec.kel` では、両方の REPL の差は `t` の 1 行だけだった。Diktor は `{x = true, x = 1, y = "t"}`、keleut は `{y = "t", x = true, x = 1}` と書く(V221 そのもの)。
- 網羅性の警告の反例(`例えば {b = _, a = 1} が漏れています`)は、型の行の順で書く静的な表示で、Diktor と keleut で一致した。P253 には関わらない。

**2. diktor/test の cram で順に依存するもの**
- 出力の行のうち、ラベルの違うフィールドを 2 つ以上持つレコードの値は、`repl.t:304` の `k : [A: Show] {f: (A) => String, n: Int32} = {f = <fn>, n = 1}` の 1 件だけだった。
  - 探したコマンドは `grep -nE '^  [^>$].*\{[a-z_]* = [^}]*, [a-z]* = ' test/*.t` で、型エラーと警告の行は除いた。
  - この行では書いた順と型の行の順が一致しており、記録も cram に当たるのは `ir_emit/0004-rec.kel` だけとしている(記録 5013 行付近)。
- 実行時エラーにラベルつきのレコードが出る cram はない。`実行時エラー: .*{ラベル = ` は 0 件だった。タプルの例(`typecheck_m5.t:160` の `(false,)`、`:173` の `()`)は、`_item` だけからなるので順が保たれ、影響を受けない。
- Diktor の試験群は、`test/dune` の規則で cram の全体を `DIKTOR_VIA_IR=1`(KIR の経路)でも走らせる(`test/dune:1-21`)。木と `ir_eval` が同じ順で書くことは、この仕組みで保たれている。P253 で変わるのは処理系の間の約束で、Diktor の中の 2 つの評価器の一致は保ったままにすべきである。

**4. 計画に入れる作業の候補と、要らない理由**
- **要らない:Diktor の表示を変えること。** 緩めた付録 B のもとでは、作った順も許される選び方の 1 つである。木、`ir_eval`、REPL はすでにそろっており、`DIKTOR_VIA_IR` の試験がそれを保っている。正準の配置(ラベルの番号の順)に合わせることは、Diktor の値がラベルの番号を持たないので意味をなさない。型の行の順に合わせることは、REPL 以外では型の情報がないので難しい(推測)。
- **要らない:diktor/test の期待値を変えること。** 当たる cram は `repl.t:304` だけで、その行は keleut とも一致している。
- **入れない方がよい:Diktor に順を固定する cram を足すこと。** Diktor の順を固定すると、RustKeleut の組で差が出て、known-diffs への登録が要る。緩めたあとの仕様は順を定めないので、固定する根拠もない。
- **任意:`ir_eval.ml:222` 付近のコメントの推敲。** 書くなら、である調で、番号や経緯を書かない形にする。変えたら `python3 tools/litcheck.py` で確かめる。要らないとする理由は、いまの文も偽ではないことである。
