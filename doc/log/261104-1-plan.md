## 0. 要約

1. 付録 B の 1836 行「`<値>` は、Diktor の値の表示(第12章の `show`)で書いた値である」を、ラベルの違うフィールドどうしの順だけを読み手に任せる文に改める(D555)。
   同じ緩めを、`cancel` 節の打ち切りの記録が実行時エラーを記録するときの `<値>` にも当てる。
2. KIR の版は 1.0 のままにする(D556)。
   付録 B の文面はバイナリに現れず、KIR の節、命令、符号の意味を変えないからである。
   IRSpec 14 節に、版を変えない本文の改訂の扱いを書き、版の履歴に改訂の行を足す。
3. IRSpec 1 節の「同じ出力」の除外の一覧に、レコードのフィールドの順の項目を足す(D557)。
   付録 B だけを直すと、1 節の「次のものを除いて、同じ出力と同じ終了状態を出す」と食い違う。
4. `keleut repl` の値の表示の順(V221)も処理系が決めるものとし、いまの「型の行の順」を保つ(D558)。
   LangSpec は REPL の表示の書式を定めていないので、LangSpec は変えない。
5. 【実測】`keleut repl` は、受理しなかった入力によって、受理した入力の表示を変える(V231)。
   型の配置を使うかどうかを、ラベルと型の通し番号の桁数に依る文字列の長さで決め、使わないときは正準の配置(ラベルの番号の順)で書くからである。
   M104 で、上限を型の構造の大きさで数え、配置を使わないときのレコードをラベルの綴りの順で書くように直す(D559)。
6. 試験の道具に、`<値>` の中のレコードのフィールドをラベルの綴りの順に並べ替える関数を作り、Diktor の出力とバイト列で比べる箇所で使う(D560、D561)。
   使うのは、kconform の正規化(`cancel` 節の打ち切りの記録の行)、`kconform kir-roundtrip`、`tests/run_cmd.rs` と `tests/repl_cmd.rs` のコーパスの比較である。
   `tests/repl_cmd.rs` の「` with ` を含むファイルは標準出力を比べない」という広すぎる除外は、これで置き換える(V233)。
7. `conformance/recshow/` を新設し、レコードを含む `<値>` を書く実行時エラーと `cancel` 節の打ち切りの記録を置く(D562)。
   後段どうしの完全一致の比較で、Rust の `Rt::show` と host の JavaScript の `show` が同じ綴りを書くことを見張る。
8. 記録が「緩めないなら」として挙げていた作業(既知の差の登録、形に印字の順を持たせる改修)は行わない(本計画 2.3 節)。
9. マイルストーンは M102(仕様と文書)、M103(比較の道具と試験)、M104(REPL の表示、V231)、M105(実施記録)の 4 つである(本計画 7 節)。

### 1.2 RustKeleut の綴り

- `keleut run` の 3 つの後段は、レコードのフィールドを正準の配置の順(ラベルの番号の昇順、同じラベルは最も外側から)に書く。
  インタプリタと JIT は `Rt::show`(`rustkeleut/crates/keleut-rt/src/ctx.rs:846-852`、レコードは 922-938 行)を使う。
  WasmGC は host の `show`(`rustkeleut/host/keleut-host.mjs:481-559`)を使い、ラベルの列を rtcore の形の表から取る(475-479 行)。
  印字の実装は Rust と JavaScript の 2 つである(critic.md 2 節)。
- ラベルの番号は、KIR を LIR に下ろすときに初めて出会った順に振る(`rustkeleut/crates/keleut-lir/src/lower.rs:162-171`)。
  そのため、同じ値の綴りが、プログラムのほかの場所に書いたレコードによって変わる。
- 【実測】Diktor と RustKeleut の綴り(`probe/t*.kel`、rk-runtime.md「実測した結果」)。
  終了状態はどれも 3 で、interp、jit、wasm は全件で同じ綴りだった。

  | プログラム | Diktor | keleut run |
  | --- | --- | --- |
  | t1: 型 `{b, a}` の照合の失敗に `{a = 1, b = 2}` | `{a = 1, b = 2}` | `{b = 2, a = 1}` |
  | t2: `{c = 3 extends base}` | `{c = 3, a = 1, b = 2}` | `{a = 1, b = 2, c = 3}` |
  | t3: 前に `let q = {a = 7, b = 8, c = 9}` があり `{b = 1, a = 2, c = 3}` | `{b = 1, a = 2, c = 3}` | `{a = 2, b = 1, c = 3}` |
  | t3b: t3 から `q` を除く | `{b = 1, a = 2, c = 3}` | `{b = 1, a = 2, c = 3}` |
  | t5: ヴァリアントの中 `#P({a = 2, b = 1})` | `#P({a = 2, b = 1})` | `#P({b = 1, a = 2})` |
  | t7: 同じラベル `{x = 1 extends {x = 2, y = 3}}` | `{x = 1, x = 2, y = 3}` | 同じ |
  | t10: タプルの中 | `({a = 1, b = 2}, 3)` | `({b = 2, a = 1}, 3)` |
  | t11: `{z = 3 extends (1, 2)}` | `{z = 3, _item = 1, _item = 2}` | `{_item = 1, _item = 2, z = 3}` |

- 【実測】`cancel` 節の中で t2 の照合を失敗させるプログラム(`probe/gaps/cx.kel`)では、Diktor は `cancel 節で例外が抑制されました: match のどの節にも一致しません: {c = 3, a = 1, b = 2}`、3 つの後段は `{a = 1, b = 2, c = 3}` と書き、どれも 0 で終わった(critic.md 1 節)。
- `keleut repl` は値を `show_value`(`src/repl_cmd.rs:936-1113`、レコードの枝は 1013-1056 行)で書く。
  フロントエンドが作る型の配置 `Layouts`(`rustkeleut/crates/keleut-front/src/types/session.rs:88-118`)が分かれば型の行の順に並べ替え、分からなければ正準の配置のまま書く。
  配置を作る `layout`(`session.rs:517-584`)は、型の鍵を `layout_key`(482-513 行)で作り、鍵の長さが 4096 文字(`LAYOUT_KEY_MAX`、118 行)を超えるか、表の項目が 4096(`LAYOUT_BUDGET`、116 行)に届くと `Layout::Any` にする(529 行)。
  型変数の位置、引数の数が合わない data、data でない型構成子も `Layout::Any` になる(520-524 行、558 行、579 行)。
- `layout_key` は、型構成子を `C{n}`、レコードのラベルを `{l}:` と、綴りでなく通し番号(`Oid`、`rustkeleut/crates/keleut-front/src/types/mod.rs:49`)で書く。
  受理しなかった入力の後の `restore`(`session.rs:309-312`)は通し番号と名前の表を戻さない。
  そのため、鍵の長さ、つまり型が `Layout::Any` になるかどうかは、それまでに振られた通し番号の桁数に依る。
- 【実測】`keleut repl` の表示が Diktor と違う形は、注釈の型とリテラルの順が違う束縛、レコードの更新、`if` の 2 つの枝で違う順に作ったレコードである(入力 `probe/r1.txt`、出力 `probe/r1.dk` と `probe/r1.k`)。
  Diktor の表示は型を行の順、値を作った順で書くので、Diktor の中でも型と値の順がそろわない(`k : {m: Int32, n: Int32} = {n = 1, m = 2}`)。
- 【実測】REPL の実行時エラーの行と `cancel` 節の打ち切りの記録は、Diktor でも keleut でも標準出力に出る。
  keleut ではその `<値>` を `Rt::show` で書くので、前の入力(受理しなかった入力を含む)が振ったラベルの番号で綴りが変わる(`probe/r2.txt`〜`r4.txt`、`probe/gaps/s1.txt`、`s2.txt`)。
  これらの行は §15.5 の診断なので、§18.5 の「表示」には当たらないと読む。

### 1.3 V231 の実測

計画の検証の担当 4 人が、それぞれ独立に再現した(`verify/findings.md` の 16、23、24、29)。

- 【実測】フィールドが約 410 個以上のレコードの型は、型の鍵が 4096 文字を超えて `Layout::Any` になる。
  境はラベルの綴りの長さに依らず、409 個と 410 個の間だった(いまの `Oid` が 4 桁で、1 フィールドが約 10 文字)。
  計画の初稿が測定の例にした「綴りの長いラベル 200 個」では鍵が約 2,000 文字で、上限に届かない。
- 【実測】600 個のラベル `f000`〜`f599` を逆の順で書いたリテラルを受理させると、それだけのセッションでは `{f599 = …`、その前に同じラベルを正の順で使って `1 / 0` で止まる入力を挟んだセッションでは `{f000 = …` と書く。
  `Layout::Any` の値を正準の配置で書き、ラベルの番号の順が受理しなかった入力で決まったからである。
- 【実測】ラベル `f0`〜`f399` のレコードは、それだけなら型の行の順で書く。
  その前に、型エラーで受理しない入力 `let z = {g0 = 1, …, g8999 = 1} + 1` を挟むと、後の入力の通し番号の桁が増えて鍵が上限を超え、正準の配置の順で書く。
  型の行の順で書くかどうかの判定そのものが、受理しなかった入力に依っている。
- 【実測】正則でない再帰型 `newtype T[a] = L(a) | N(T[(a, a)])` の値は、深さ 8〜12 で鍵が上限を超え、同じく表示が変わる。
  表の項目の上限(4096)には、鍵の上限より先に届かない。

## 3. 仕様の改訂

### 3.1 付録 B の `<値>`(D555)

**D555(P253 の答え)**: 付録 B の `<値>` の中のレコードの、ラベルの違うフィールドどうしの順は読み手が決める。
同じラベルのフィールドどうしの順(最も外側から。§7)、ラベルがすべて `_item` のレコードのタプルの記法(§8)、値の綴りは、Diktor の `show` のままとする。
読み手は、同じ値を、値の作り方やプログラムのほかの部分によって違う順で書いてよい。
この規則は、付録 B の 3 番、4 番、9 番の `<値>` に当て、`cancel` 節の打ち切りの記録が実行時エラーを記録するときの `<値>` にも当てる。

理由:

- `<値>` は標準エラーの診断で、LangSpec §18 の評価の結果の外である。
  IRSpec 6.6 節も「レコードの配置は読み手が決め、結果に効かない」としている。
- 同じラベルどうしの順は、どの読み手でも最も外側からに決まっている(Diktor は拡張で先頭に足し、RustKeleut の正準の配置は同じラベルを外側から置く。`rustkeleut/doc/lir.md:122`)。
  【実測】リテラル `{x = 1, y = 2, x = 3}` では、Diktor も 3 つの後段も、最も外側の `x = 1` を先に書いた(`verify/findings.md` の 2)。
  任せる必要が無いので、狭く緩める。
- 「ほかの部分によって違う順」を許すのは、RustKeleut のラベルの番号がプログラム全体で初めて出会った順に振られるからである(本計画 1.2 節の t3 と t3b)。
  「値の作り方によって違う順」は、Diktor が作った順で書くことを指す(t1、t2、t11)。

1836 行の改訂案:

```text
`<値>` は、Diktor の値の表示(第12章の `show`)の綴りで書いた値である。
ただし、レコードの中のラベルの違うフィールドどうしの順は、読み手が決める。
読み手は、同じ値を、値の作り方やプログラムのほかの部分によって違う順で書いてもよい。
同じラベルのフィールドどうしは、最も外側(言語仕様 §7)のものから順に書く。

```

1872 行の表の後ろに足す文:


## 4. REPL の表示

### 4.1 表示の順(D558)

**D558**: P253 の答えは `keleut repl` の値の表示にも及び、レコードのフィールドの順は処理系が決める。
`keleut repl` は、型の配置が使える型の値を、いまの「型の行の順」で書き続ける。

理由:

- LangSpec は REPL の表示の書式を定めていない。
  記録 5684 行は「REPL の表示の順(V221)も同じ答えに従う」としている。
- 型の行の順は、表示の行の型(`名前 : 型 = 値` の型)と同じ順なので、読みやすい。
  注釈の無いリテラルと拡張では、Diktor と同じ綴りになる(`tests/repl_cmd.rs:125-137` の `{z = 4, x = 1, y = 2}`)。
  AGENTS.md は `keleut repl` を「`diktor --repl` と同じ出力」と述べており、一致する場面を減らさない。
- 型の行の順そのものはラベルの番号に依らない。
  ただし、型の行の順を使うかどうかの判定が受理しなかった入力に依る不具合があり(V231)、本計画 4.2 節で直す。

代案 A: `Rt::show`(正準の配置の順)に寄せ、型の配置の機構を消す。
表示がセッションのラベルの番号に依るようになり、受理しなかった入力が残したラベルの番号で受理した入力の表示が変わるので、§18.5 に反する。
採らない。

代案 B: レコードのフィールドをいつもラベルの綴りの順(同じラベルは最も外側から)で書き、型の配置の機構を消す。
綴りの順はセッションの履歴に依らないので §18.5 を満たし、V231 も上限も構造の上から消える。
配置の表(`session.rs` の `Layout`、`Layouts`、上限、`layout_key`、`layout`、約 130 行)と `src/repl_cmd.rs` の並べ替えを消せる。
欠点は、値の順が表示の行の型の順とそろわなくなることと、Diktor と同じ綴りになる場面(注釈の無いリテラル、拡張)が減ることである(`{z = 4 extends {x = 1, y = 2}}` は `{x = 1, y = 2, z = 4}` になる)。
本計画は D558 を推すが、所有者が機構の小ささを取るなら代案 B に替える(P255)。
代案 B に替えるときは、M104 の作業を「機構を消して綴りの順で書く」に改め、`tests/repl_cmd.rs` の表示の期待(125-137 行、153-163 行、549-550 行)を書き直す。

`AGENTS.md:42` の「record fields print in the order of the type's row, not Diktor's construction order (V221)」は、型の行の順で書くこと、順は処理系が決めること(D558)、型の配置が使えない値はラベルの綴りの順で書くこと(D559)、Diktor は作った順で書くことに改める(M102、D559 の部分は M104)。

### 4.2 型の配置を使わない値の表示(D559、V231)

V231 は本計画 1.3 節のとおり実測で起きる。
原因は 2 つある。

1. 型が `Layout::Any` になるかどうかを、通し番号の桁数に依る型の鍵の文字列の長さで決めている。
2. `Layout::Any` のレコードを、セッションのラベルの番号で決まる正準の配置の順で書く。

**D559**: M104 で次のとおりに直す。

1. 上限を、型の鍵の文字列の長さでなく、型の構造の大きさで数える。
   大きさは、`layout_key` がたどる型構成子、レコードとヴァリアントのフィールドの数の和とし、通し番号の綴りの長さを含めない。
   この数え方では、`Int32` のフィールド N 個のレコードの大きさは 2N + 1 である(フィールドと、その型の型構成子を数える)。
   【実測】いまの境は `Int32` のフィールド 409 個と 410 個の間で、大きさでは約 820 に当たる。
   上限の値は 800 を案とし(`Int32` のフィールド約 400 個)、M104 で既存の試験と `KELEUT_DIKTOR` のコーパスの比較が変わらない値を選ぶ。
   境の値は、フィールドの数と大きさの両方で実施記録に書く。
   `layout_key` の中の文字数による打ち切り(`session.rs:484-486`)と `LAYOUT_KEY_MAX` は消す。
   `layout_key` のたどりは大きさの上限で止め、上限の内側の型では鍵を最後まで作る。
   打ち切りを残すと、通し番号が 5 桁になったときに上限の内側の型の鍵が途中で切れ、接頭辞が同じ別の型が同じ `memo` の項目を引く。
   どの型でそれが起きるかは通し番号の桁数で決まるので、V231 と同じ形の履歴への依存が残る。
   `memo` の鍵そのものは通し番号のままでよい(同じ入力の中の同じ型を指すためだけに使い、最後まで作った鍵なら衝突しない)。
2. `Layout::Any` のレコードと、`Layout::Record` でもラベルの集まりが合わないレコード(`src/repl_cmd.rs:1022-1038` の `fs.len() == n`、`v.len() == n`)のフィールドを、ラベルの綴りのバイト列の順(安定、同じラベルは最も外側から)で書く。
   この順はセッションの履歴に依らない。
   表の項目の上限(`LAYOUT_BUDGET`)に届いたときも同じである。

試験(`tests/repl_cmd.rs`)は、次の 2 つのセッションの、受理した入力の表示が同じになることを確かめる。

- 型の鍵の上限の道: 600 個のラベルのレコードを逆の順で書いたリテラル。
  セッション B では、その前に同じラベルを正の順で使って `1 / 0` で止まる入力を挟む。
- 判定の道: 両方のセッションの先頭で、400 個のラベル `f0`〜`f399` を正の順で書いたレコードを受理させ(ラベルの番号を正の順に振る)、そのあとで同じラベルを逆の順で書いたリテラルを受理させる。
  セッション B では、2 つの入力の間に、多くの新しい名前を使う型エラーの入力(`let z = {g0 = 1, …, g8999 = 1} + 1`)を挟む。
- 正則でない再帰型の道: `newtype T[a] = L(a) | N(T[(a, a)])` の深さ 10 の値で、中に `{b = 1, a = 2}` を置く。
  セッション B では、その前に `let w = {a = 1, b = 2}.a / 0`(同じラベルを逆の順で初めて使い、実行時エラーで止まる入力)を挟む。

判定が `Layout::Record` から `Layout::Any` に変わっても、正準の配置の順(ラベルに出会った順)が型の行の順と同じなら、表示は変わらない。
上の道は、どれも正準の配置の順を型の行の順と食い違わせてある。
【実測】正の順のレコードを先に受理させずに、逆の順のリテラルと型エラーの入力だけで試すと、直す前でも 2 つのセッションの表示は同じだった。
再帰型の道で型エラーの入力を挟んでも、表示は変わらなかった(`verify/findings2.md` の 0)。

それぞれ、直す前の `keleut repl` で 2 つのセッションの表示が違うことを確かめてから(試験が働くことの確認)、直した後で同じになることを確かめる。
上限の値を変えるので、上限の近くの型の表示が型の行の順と綴りの順のどちらになるかが変わりうる。
その境の値を実施記録に書く。

代案: 上限を上げる。
上限は正則でない再帰型で表が限りなく伸びるのを止めるためにあり(`session.rs:115`)、上げても超える型は残り、判定が通し番号の桁数に依ることも直らないので採らない。

## 5. 比較の道具と試験

### 5.1 フィールドの順を並べ替える関数と kconform の正規化(D560、V232)

**D560**: kconform に lib の標的を足し、`<値>` の中のレコードのフィールドを並べ替えるモジュールを置く(モジュール名は `fieldsort` を案とする)。
kconform の正規化は、`cancel` 節の打ち切りの記録の行にこのモジュールを当てる。

モジュールの仕様:

- 公開の関数は 2 つである。
  - `sort_value(&[u8]) -> Option<Vec<u8>>`: 値の綴り 1 つを受け取り、レコードのフィールドを並べ替えた綴りを返す。
    字句が読めないときは `None` を返す。
  - `sort_line(&[u8]) -> Vec<u8>`: 1 行を受け取り、次の範囲に `sort_value` を当てた行を返す。
    当てる範囲が無いときと `sort_value` が `None` のときは、行を変えずに返す。
- `sort_line` は、行の中で次の連結が最初に現れる位置を探す(行頭や字下げの後ろに限らず、前の文字も問わない)。
  cram の行は先頭に 2 つの空白を持ち(`cram.rs:262`)、`diktor/test` には `partial実行時エラー: ゼロ除算です` のように改行の無い標準出力の後ろに診断が続く行がある。
  当てる範囲は、`実行時エラー: ` または `cancel 節で例外が抑制されました: ` の直後に、付録 B の 3 番、4 番、9 番の文面の `<値>` の前まで(`パターンに値が一致しません: `、`match のどの節にも一致しません: `、`handle のどの節にも一致しません: `)が続くときの、その連結の直後から行末までである。
  14 番の `panic: <文字列>` のように、利用者の文字列をそのまま書く文面には当てない。
  【実測】`__panic("match のどの節にも一致しません: {b = 1, a = 2}")` を打ち切ると、記録は `cancel 節で例外が抑制されました: panic: match のどの節にも一致しません: {b = 1, a = 2}` になる(`verify/findings.md` の 9)。
  「直後」に限るので、この行は並べ替えない。
- 値の字句は、文字列(`"` で囲み、`\` で次の 1 文字を逃がす)、括弧(`(` `)` `[` `]` `{` `}`)、`,`、` = `、それ以外の文字の並びとする。
  文字列の中の括弧は数えない。
- `{` で始まり、ラベル、` = `、値の組を `, ` で並べて `}` で閉じる部分をレコードとし、フィールドをラベルのバイト列の順に安定に並べ替える。
  安定なので、同じラベルのフィールドは元の順(最も外側から)のまま残る。
  入れ子のレコードもすべて並べ替える。
- 入れ子は作業の列でたどり、再帰でネイティブのスタックを使わない。
  `Rt::show` と host の `show` が同じ理由で作業の列を使っている(`ctx.rs:846-849`)。

単体の試験に入れるもの: 字下げのある行、`partial実行時エラー: …` のように前に文字が続く行、入れ子のレコード、ヴァリアント(`#P({…})`)、コンストラクタ(`Box({…})`)、タプルと 1 要素のタプル、`_item` と普通のラベルが混ざるレコード、同じラベル、`<fn>`、文字列の中の括弧と逃がした `"`、9 番の `<操作><値>`(`E.op({…},)` の形。`effect.rs:143-156`)、上の panic の 2 行(並べ替えないこと)、深さ 100,000 の入れ子の値、読めない綴り(行を変えないこと)。

kconform の正規化(`normalize::line`)の変更:

- `sort_line` を当ててから、種別の語で切る既存の規則を当てる。
  実行時エラーの行はいまも種別の語の後ろで切られるので、変わるのは打ち切りの記録の行だけである。
- レコードを含まない打ち切りの記録の行は、いまと同じく完全に比べる。

理由:

- 打ち切りの記録の行を種別の語に加えて切る代案(critic.md 1 節の (a))は、記録の中身の比較をすべて失う。
  並べ替えなら、レコードを含まない記録の行はいまと同じく完全に比べられ、既存の試験の結果は変わらない。
- 当てる範囲を、診断の文面の決まった連結の直後に限る。
  プログラムが標準出力に同じ形の行を書けば、cram では区別できず並べ替えるが、2 つの処理系の間で順だけが違う文字列をプログラムが書くとは考えにくいので、許す。
  種別の語で切る既存の規則も同じ性質を持つ。
- モジュールを kconform の lib に置くのは、keleut-cli の試験(本計画 5.2 節)からも使うためである。
  kconform はほかの crate に依らないので、keleut-cli の `[dev-dependencies]` に足しても依存は輪にならない。
  `main.rs` の `mod` 宣言のうち `fieldsort` を lib に移し、bin からは `kconform::fieldsort` で使う。

`conformance/README.md:197-198` の正規化の説明に、打ち切りの記録の並べ替えと、その根拠(D555)を書き足す。

## 12. 進め方の原則

- マイルストーンごとに、実装の後で敵対的な検証を行う。
  観点は、仕様の文(付録 B、1 節、14 節が互いに、また LangSpec §7、§8、§15.5、§18、§18.5 と食い違わないか)、道具の正しさ(`fieldsort` が並べ替えてはいけないものを並べ替えないか、許す範囲が D555 を超えないか)、試験の網羅(後段どうしの一致と打ち切りの記録の中身が見張られているか、V231 の試験が直す前に落ちるか)、記録の整合(番号、行番号、台帳)の 4 つを基本とする。
  検証者の指摘ごとに反証者を立て、反証されなかった指摘を直し、直したものを 1 回検証し直す。
- 振る舞いの分類を文書に書くときは、区別する最小の変種を並べて同じ条件で測ってから書く。
  上限に当たる型の大きさのように、内部の表現(通し番号の桁数など)で決まる境は、境の両側で測る。
- 検証者と担当の書き込み先は scratchpad に限り、報告を受けたら親と diktor の `git status --short` を確かめる。
  本計画の作成中に、調査の担当が親の作業木に `rustkeleut/-o`(KIR のバイナリ)を残し、統括者が消した。
- 本文に逆引用符を含むテキストをシェルで書くときは、ヒアドキュメントを `<<'EOF'` と引用する。
- 既存の `doc/log` の記録は書き換えない。
