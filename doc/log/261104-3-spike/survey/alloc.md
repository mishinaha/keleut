# 調査:実行時の確保の制限(計画 261104-3 の項目 (2))

- 日付:2026-11-04
- 対象:V229(形の表)、V230(小さな確保の失敗で 134)、値スタックの塊を回収しないこと(M90 の 4)、`cont_resume` の失敗の後の注入(M89 の残した制限の 1)、V215 と P252(`kw` の V8 のヒープの枯渇)
- 版:親 69febfd、diktor cccd8cb。`rustkeleut/target/release/keleut` は HEAD から作った release の組み
- 材料:測定の台本と小さな結果は `doc/log/261104-3-spike/probe/alloc/` に置いた。数値の一覧は同じ場所の `results.md` にある
- 記号:【実測】は上の台本で測った事実、【推論】は確かめていない判断である

## 0. 要約

5 つの項目のうち、言語仕様からの逸脱は 2 つ(V229 の確保の失敗と V230)で、残りの 3 つは処理系の限度か、計画 6.5 節の規則からのずれである。

- **V229**:形の表の確保は今も `vec!` で、失敗すると Rust の確保の誤りの処理でプロセスが SIGABRT(134)になる。
  `cancel` 節は走らず、それまでに書いた標準出力も失われる【実測】。
  2 乗の大きさは残っており、M90 の GC の後も常駐の大きさのほぼすべてが形の表である【実測】。
  確保を失敗を返すものにする修正は小さく(Rust 側で約 80〜120 行)、先に行うべきである。
- **V230**:`ki` でも 134 になる。
  `ulimit -v 350000` で見つけた失敗の場所は、回収の中の `keleut_lir::live::Points::live` の `Vec` だった【実測】。
  回収はメモリが足りないときに走るので、この場所はほかより失敗しやすい【推論】。
  JIT の段では LLVM の `bad_alloc` と `LLVM ERROR: out of memory` でも 134 になる【実測】。
  回収の中の確保をなくす修正と、大域の確保器に予備を持たせる修正で窓の大部分を閉じられる。
  LLVM の確保の失敗は Rust から捕まえられず、残る【推論】。
- **値スタックの塊**:深い再帰から戻った後も塊は残り、`ulimit -v 1300000` で、深い再帰だけの例とヒープだけの例はどちらも 0 で終わるのに、両方を続けた例は 3 で終わった【実測】。
  仕様には反しないが、メモリの不足が早く来る。
- **`cont_resume` の後の注入**:測った例では再現しなかった【実測】。
  塊を回収しないので、注入が同じ位置に継続を置くときは、前に使った塊が残っていて新しい確保が要らないためである【推論】。
  したがって、塊を回収する修正はこの制限を表に出しうるので、2 つは同じマイルストーンで扱うのがよい。
- **V215**:`kw` は V8 のヒープが尽きると 70 で終わり、`before` も失われた【実測】。
  Node の `Worker` の `resourceLimits.maxOldGenerationSizeMb` を使うと、主スレッドは止まらずに `ERR_WORKER_OUT_OF_MEMORY` を受け取れた【実測】。
  これで「出力を失わずに 3 で終わる」ところまでは近づけるが、`cancel` 節は走らない【推論】。
  直すかどうかは所有者の判断になる。
- 決定的な試験には、確保を N 回目で失敗させる試験用の仕組み(環境変数か隠したオプション)が要る。
  `ulimit -v` の結果は、上限を少し動かしただけで 3、134、70 の間を行き来する(3.2 節の表)【実測】。

## 1. 仕様と計画が求めること

- LangSpec §15.5(`doc/LangSpec.md:1771-1776`)は、「評価に要する領域が処理系の限度を超えた場合も実行時エラーとする」と定める。
  実行時エラーでは、有効なハンドラを内側から巻き戻して各ハンドラの `cancel` 節を実行し、3 で終わる。
  処理系に任せているのは限度の大きさだけで、限度を超えたときの終わり方は任せていない(計画 261024-1 の `doc/log/261024-1-plan.md:789-790` も同じ読み方をする)。
- 同じ節(`doc/LangSpec.md:1790`)は、プログラムが書いた標準出力を、実行時エラーのときも終了する前にすべて書き出すことを求める。
- LangSpec §13.6(`doc/LangSpec.md:1432`、`:1436-1437`)は、破棄する計算の中にあったハンドラを内側から巻き戻すことを求める。
  使われていない継続の中のハンドラの `cancel` 節もこれに当たる。
- IRSpec 1 節(`doc/IRSpec.md:38-43`)が同じ結果の保証から除くのは、`N_alloc_max` を超える確保と、「`N_alloc_max` の検査によらないメモリの不足」のうち `kw` の V8 のヒープの枯渇と Diktor での確保である。
  `ki` と `kj` の小さな確保の失敗による 134 は、この除外に挙がっていない。
  したがって、V229 と V230 は、振る舞いを直すか、IRSpec 1 節と 11.1 節の表と注(`doc/IRSpec.md:962`、`:968-969`)にこの場合を足すかのどちらかが要る。
- 計画 261024-1 の 6.5 節(`doc/log/261024-1-plan.md:785-787`)は、`ki` と `kj` でヒープを広げられないときもプロセスを止めずに `ERROR(OutOfMemory)` にし、予備も尽きたら `cancel` 節からの脱出として打ち切るとしている。
- 計画は Diktor がメモリの不足を 3 にすると書く(`doc/log/261024-1-plan.md:776`)。
  しかし Diktor は、1 回の大きな確保(1 億要素の `MutableArray.new`、`ulimit -v 600000`)では `cancel` を走らせて 3 で終わる一方、ヒープを少しずつ使い尽くす `oomlist.kel` では `Fatal error: allocation failure during minor GC` で 134 になった【実測、`probe/alloc/results.md` の 3 節】。
  この種類のメモリの不足には、試験の基準になる処理系が無い。

## 2. V229:形の表

### 2.1 現状

- `ShapeTable::alloc` は `vec![0u64; …]` で、`grow` は容量の積の溢れを `expect` で panic にする(`rustkeleut/crates/keleut-rtcore/src/lib.rs:193-224`)。
  `intern`、`extend`、`restrict`(同 `:248-302`)は失敗を返さない。
- 形はラベルの列を丸ごと溜め(`rustkeleut/rtcore/shape.c:175-192` の `krt_shape_extend`)、表は回収しない。
  長さ i の形を i 個作る鎖では、ラベルの合計が約 n²/2 になる。
  `grow` は新しい表を取ってから古い表を写すので、広げる瞬間は古い表と新しい表の両方を持つ。
- 呼び出し元は `Rt::rec_extend`、`rec_restrict`(`rustkeleut/crates/keleut-rt/src/ctx.rs:437-457`)、起動のときの登録(同 `:119-123`)、REPL の `Extender::grow`(`rustkeleut/crates/keleut-rt/src/extend.rs:80-86`)である。
  `rec_extend` と `rec_restrict` はすでに `Result<Word, Stop>` を返すので、LIR の意味は変えずに失敗を返せる。
- `rec_fields`(`ctx.rs:431-434`)は、拡張のたびにフィールドを `Vec` に写す。
  これも失敗を返さない確保である。
- `kw` では、形の表は `rt.wasm` の線形メモリにある。
  ホストの `alloc` は線形メモリを広げられないと `内部エラー: 線形メモリを広げられません` を書いて 70 で終わり(`rustkeleut/host/keleut-host.mjs:395-405`)、`shape_op` は `shapes_grow` の失敗を `形の表を広げられません` の内部エラーにする(`rustkeleut/crates/keleut-wasm/src/rt.rs:253-275`)。
  ホストの `alloc` は解放しないので、広げるたびに古い表が線形メモリに残る(`keleut-host.mjs:691-698`)【推論、コードを読んだ】。
  wasm32 の線形メモリは 4 GiB までなので、長い鎖は `kw` で 70 になる【推論】。

### 2.2 実測

`probe/alloc/gen_chain.py` で 3 種類の鎖を作り(`top` は最上位にラベルの違う拡張、`fun` は関数の中で 2 つずつラベルを足す拡張、`same` は同じラベルの拡張)、`run_chain.sh` と `measure.py` で測った【実測】。

| 種類と段の数 | `ki` | `kj` | `kw` | `dk-ir` |
| --- | --- | --- | --- | --- |
| fun 2,000 | 0.13 秒、98 MB | 0.13 秒、133 MB | 0.19 秒、133 MB | |
| fun 4,000 | 0.49 秒、269 MB | 0.47 秒、304 MB | 0.53 秒、358 MB | 0.01 秒、11 MB |
| fun 8,000 | 1.79 秒、944 MB | 1.81 秒、979 MB | 1.77 秒、1,225 MB | 0.01 秒、14 MB |
| top 3,000 / 6,000 / 12,000 | 125 / 399 / 1,482 MB | | | 12 / 15 / 21 MB |
| same 8,000 / 16,000 | 486 / 1,810 MB | | | 17 / 25 MB |

- 段の数が倍になると、常駐の大きさは約 3.5〜3.7 倍になる。
- `KELEUT_GC_STATS=1` で見た GC のヒープの語の数は、fun の 2,000 段、4,000 段、8,000 段で約 140〜160 万語(約 11〜13 MB)で変わらなかった。
  M87 の記録(`doc/log/261024-3-record.md:2150-2160`)のときと違い、途中のレコードの写しは M90 の GC が回収している。
  fun の 944 MB のほとんどは形の表とその広げ直しである。
- `top` の鎖では、すべてのレコードが大域から届くので、平らなレコードのフィールドも合わせて n²/2 語が生きている。
  これは平らなレコード(計画 6.5 節)を選んだ結果で、形の表を直しても残る【推論】。

`gen_chain.py func N` は、同じ鎖を `cancel` 節を持つハンドラの中で呼び、その前に `before` を書く。
§15.5 が求める結果は `before`、`cancel`、`実行時エラー: メモリ不足です`、3 である【実測、`results.md` の 2 節】。

| 入力と条件 | `ki` と `kj` の結果 |
| --- | --- |
| func 8,000、`--native-stack 64m`、`ulimit -v` 1,500,000〜400,000 | 134(`memory allocation of 1207959576 bytes failed` など)、標準出力は空 |
| func 3,000、`--native-stack 64m`、`ulimit -v` 524,288 | 134(`memory allocation of 150994968 bytes failed`)、標準出力は空 |
| func 3,000、同じ条件で `diktor --run-ir` | `before`、`3000`、0 |

gdb の backtrace は `ShapeTable::grow` ← `ShapeTable::extend` ← `Rt::rec_extend` ← `Interp::exec_inner` だった【実測】。
`before` が失われるのは、標準出力のバッファを書き出す前にプロセスが止まるからである。

### 2.3 分類

- 確保の失敗で 134 になり `cancel` が走らないことは、§15.5 からの逸脱で、IRSpec 1 節の除外にも入っていない。
- 2 乗の時間と大きさは、仕様が縛らない処理系の性質である。
  ただし、それがメモリの不足を早める点では、限度の質の問題になる。

### 2.4 直し方

| 案 | 中身 | 規模 | 危険 |
| --- | --- | --- | --- |
| A | `ShapeTable::alloc` を `Vec::try_reserve_exact` にし、`grow`、`retry`、`intern`、`extend`、`restrict` を `Result<_, OutOfMemory>` にする。`rec_extend`、`rec_restrict`、`Extender::grow` から `Stop::OutOfMemory` を返す。`rec_fields` も `try_reserve` にするか、新しい箱へ直に写す | Rust 側で約 80〜120 行。C は変えない | 小さい。`Stop::OutOfMemory` の巻き戻しは既にある道である |
| A' | 形の表のバイト数を、ヒープと同じ予算(V230 の案 C)に数える | 案 A に約 20 行 | 小さい |
| B | `kw` で、ホストの `alloc` と `shapes_grow` の失敗を、70 でなく `N_alloc_max` と同じメモリの不足の状態語にする | ホストと `rt.rs` で約 30〜60 行 | 中くらい。Wasm 側で状態語を立てて伝播する道を `shape_op` に足す |
| C | 形の表を回収する(GC が生きているレコードの形に印を付け、使われない形を空きにする) | C と Rust で約 200〜300 行。`rt.wasm` も同じ C を使う | 中くらい。LIR が定数として持つ形の番号は根にする必要がある |
| D | 形を「親の形と 1 つのラベル」で持ち、ラベルの列を共有する(持続的な順序木など) | `shape.c`(今は 209 行)の書き直しとホスト、`labels()` が列を返す呼び出し元の改修で約 400〜600 行 | 大きい。`find` と位置の計算が対数時間になり、フィールドの読みの速さに効く |

- 案 A は §15.5 の逸脱を閉じる最小の修正で、先に行う。
- 案 C は fun の鎖(途中の形が死ぬ)を線形にするが、top の鎖(すべての形が生きる)は直さない。
- 案 D は top の鎖の形の表を線形にするが、フィールドの写しは平らなレコードのままでは 2 乗のまま残る。
  所有者の判断が要る大きな変更なので、急がない項目(5)の側に置くのがよい【推論】。
- `grow` が古い表と新しい表を同時に持つ点は、広げる比を 2 から下げても峰が少し下がるだけで、本質的な改善ではない。

### 2.5 試験

- `conformance/oom/` か `conformance/gc/` に、func 3,000 の鎖を cram の中で生成し(`seq` か `awk`)、`keleut emit-kir` を制限なしで走らせてから、`ulimit -v 524288` と `--native-stack 64m` の下で `keleut run` する例を置く。
  期待は `before`、`cancel`、`実行時エラー: メモリ不足です`、3 である。
  151 MB の `grow` が決まって失敗する点なので、上限の揺れに強い【推論】。
  `kw` は `gc.t` と同じく `--backend interp` を書いて避ける(Node は 512 MiB の下で起動しない。`doc/log/261024-3-record.md:3702`)。
  フロントエンドは同じ上限で 134 になる(下の 7 節)ので、`.kel` をそのまま `ulimit` の下で走らせてはいけない。
- 試験用の確保の失敗(6 節)があれば、形の表の確保だけを失敗させる決定的な試験を、`ki`、`kj` で置ける。
- `kw` は、線形メモリを 4 GiB まで使う例が重いので、ホストの `alloc` に試験用の上限を渡す形が要る【推論】。

## 3. V230:小さな確保の失敗

### 3.1 現状

- GC のヒープ(`rustkeleut/crates/keleut-rt/src/heap.rs:18-27`)と値スタックの塊(`rustkeleut/crates/keleut-rt/src/stack.rs:23-28`)は、確保の失敗を `OutOfMemory` で返し、それぞれ 1 MiB の予備を持つ。
- それ以外の実行時の確保の多くは Rust の大域の確保器を通り、失敗すると `handle_alloc_error` でプロセスが止まる。
  `vec!`、`to_vec`、`collect`、`Box::new`、`push`、`format!` などの出現は、`keleut-rt` で約 100 か所、`keleut-interp` で約 100 か所あり、`try_reserve` は合わせて 15 か所である【実測、grep で数えた概数】。
- 大域の確保器を差し替えるコード(`#[global_allocator]`)はどの crate にも無い。
- 記録は、M89(`doc/log/261024-3-record.md:2746-2749`)、M90 の 3(同 `:2864-2869`)、M92 の 9(同 `:3360-3370`)でこの窓を挙げている。

### 3.2 実測

`probe/alloc/oomlist.kel` は、`cancel` 節を持つハンドラの中で 20 億要素のリストを作ろうとする。
`sweep_as.sh` で `--native-stack 64m` のまま `ulimit -v` を 25,000 KiB ずつ変えた【実測、`results.md` の 3 節】。
期待は標準出力 2 行(`before`、`cancel`)と 3 である。

| `ulimit -v` | `interp` | `jit-only` | `threshold=1` | `alternating=1` |
| --- | --- | --- | --- | --- |
| 300,000 | 3 | 70 | 70 | 70 |
| 325,000 | 3 | 134 | 134 | 134 |
| 350,000 | 134 | 134 | 134 | 134 |
| 375,000 | 3 | 3(出力なし) | 134 | 3(出力なし) |
| 400,000 | 3 | 3 | 134 | 3 |
| 425,000〜700,000 | 3 | 3 | 3 | 3 |

- 350,000 の `interp` の 134 は `memory allocation of 12 bytes failed` で、backtrace は `RawVec::handle_error` ← `keleut_lir::live::Points::live`(`rustkeleut/crates/keleut-lir/src/live.rs:68`)← `gc::Frames::scan`(`rustkeleut/crates/keleut-rt/src/gc.rs:417-438`)← `Frames::walk` ← `Rt::collect` ← `Rt::alloc` ← `Rt::ctor_new` だった。
  `Points::live` は、回収のたびに走査するフレームごとに新しい `Vec`(と差分を当てるときの `HashMap`)を作る。
- 325,000 の JIT の 134 は `LLVM ERROR: out of memory` と `Buffer allocation failed`、400,000 の `threshold=1` の 134 は C++ の `std::bad_alloc` だった。
- 375,000 の `jit-only` の「3、出力なし」は、`KELEUT_JIT_STATS=1` で翻訳した関数が 1、`interp_stub` からの起動が 0 だった。
  `before` を書く前、ハンドラを置く前の最初のフレームの確保で尽きたと考えられ、正しい結果である【推論】。
- 300,000 以下の 70 と 127 は、スレッドのスタックや共有ライブラリを取れない起動の失敗で、プログラムの評価の前に起こる。
  既定の `--native-stack` では、実行のスレッドが約 1.1 GB のスタックを予約するので、約 1,200,000 KiB 以下で 70 になる【実測】。
- 上限を 25,000 KiB 動かすだけで結果が 3 と 134 の間を行き来するので、`ulimit -v` だけで V230 の修正を決定的に試すことはできない。

### 3.3 分類

`ki` と `kj` のどちらでも §15.5 からの逸脱で、IRSpec 1 節の除外にも入っていない。
Linux の既定の過剰な割り当てでは、`ulimit -v` の無いプロセスの確保はまず失敗せず、OOM killer の SIGKILL(137)になる。
これはどの処理系でも避けられないので、V230 が実際に効くのは `RLIMIT_AS` を絞ったときにほぼ限られる【推論】。

### 3.4 直し方

| 案 | 中身 | 規模 | 危険 |
| --- | --- | --- | --- |
| A | 回収の中の確保をなくす。`Points::live` に出力先の `Vec` を渡す形を足し、`Frames` の `tmp` を使い回す。`FuncRoots::new`(`gc.rs:335`)と `any_slots` の作業域も、回収の前に `try_reserve` で取る | 約 40〜80 行 | 小さい。見つけた失敗の場所そのものである |
| B | 大域の確保器を包み、起動のときに数 MiB の予備を取っておく。確保が失敗したら予備を返してやり直し、「メモリの不足が起きた」印を立てる。実行時は確保の遅い道(`Rt::alloc_obj` の回収の後、`place`)と `krt_*` で印を見て `Stop::OutOfMemory` にする | 約 60〜100 行(`keleut-cli` の `main.rs` に確保器、`keleut-rt` に印の検査) | 小さい〜中くらい。予備を返した後は前と同じく止まる。印を見るまでの間に走るコードはふつうに続く |
| C | `RLIMIT_AS` が有限なら、それから余裕(例えば 1/8 か 64 MiB の大きいほう)と起動の時点の使用量を引いた値を、ヒープ、値スタックの塊、形の表の合計の予算にし、超えたら `OutOfMemory` にする。cgroup の `memory.max` も読める | 約 60〜120 行 | 中くらい。予算の見積もりを誤ると、走れるプログラムをメモリの不足にする |
| D | 残りの確保の場所を 1 つずつ `try_reserve` にする | 約 200 か所。数百行 | 大きい割に、LLVM の確保が残る |
| E | JIT の翻訳の前に、`/proc/self/statm` と `RLIMIT_AS` から残りを調べ、少なければ翻訳せずにインタプリタで続ける | 約 30〜50 行(`keleut-llvm/src/run.rs` の翻訳のスレッド) | 小さい。LLVM の `bad_alloc` と `LLVM ERROR` は Rust からは捕まえられない(C++ の `install_bad_alloc_error_handler` は C API に無い)ので、窓を狭めるだけである |
| F | 直さず、IRSpec 1 節と 11.1 節の注、AGENTS.md に「`ki` と `kj` の小さな確保の失敗は 134 になりうる」と書く | 文書だけ | 無い。§15.5 からの既知の逸脱として残る |

推奨は A と B を行い、C は B の後に要るかを測って決め、E を JIT に足すことである。
D は費用に見合わない。
どれを行っても、LLVM の中での失敗と、物理メモリの枯渇による OOM killer は残るので、F の記述も合わせて要る【推論】。

### 3.5 試験

- 試験用の確保の失敗:大域の確保器の包み(案 B)に、環境変数(例えば `KELEUT_TEST_ALLOC_FAIL=N`、N バイトを超えたら失敗)を読む試験用の道を置く。
  これなら、回収の中、`rec_fields`、`call_clause` の引数の列などの場所で、上限の揺れに依らずに失敗を起こせる。
  ヒープと値スタックの塊は大域の確保器を通らない(`mmap` と `alloc_zeroed`)ので、同じ予算に数えるか、別の印で失敗させる。
- 回帰の試験:`oomlist.kel` を `ulimit -v` 325,000〜425,000 で走らせ、134 が出ないことを確かめる台本(`sweep_as.sh`)を、手で走らせる受け入れの検査に入れる。
  cram の試験にはしない(機械の差で揺れる)【推論】。

## 4. 値スタックの塊を回収しないこと(M90 の 4)

### 4.1 現状

- `ValueStack::place`(`rustkeleut/crates/keleut-rt/src/stack.rs:199-252`)は、今の塊に入らないフレームを次の塊に置き、次の塊があれば使い直す(`:233-234`)。
  新しい塊を取るときだけ、それより後ろの塊を捨てる(`:236-237`)。
- `ptr_at`(`:156-175`)は戻るときに使っている塊を下げるだけで、塊を返さない。
- 塊は `alloc_zeroed` で取る(`:85-94`)。
  glibc の `malloc` は大きな領域の `mmap` の閾値を、解放された大きさに合わせて上げるので、返しても OS に戻らない場合がある【推論】。

### 4.2 実測

`probe/alloc/chunks.kel` で、深さ 1,000 万の末尾でない再帰(MODE 1)、リストの作り直し(MODE 2)、その 2 つを続けたもの(MODE 3)を `--max-depth 20000000` で走らせた【実測、`results.md` の 4 節】。

| MODE | `ki` | `kj` |
| --- | --- | --- |
| 1 | 944 MB | 1,735 MB |
| 2 | 157 MB | 195 MB |
| 3 | 1,072 MB | 1,863 MB |

MODE 3 は MODE 1 と 2 の和に近い。
`ki`、`--native-stack 64m`、`ulimit -v 1300000` では、MODE 1 と 2 は 0、MODE 3 はメモリの不足で 3 だった。
戻った後に生きているのはリストだけなのに、残った塊のためにヒープを広げられなくなった。

### 4.3 分類

メモリの不足は 3 で終わり、`cancel` も走るので、仕様には反しない。
処理系の限度が、生きている量でなく過去の最大の深さで決まる点の、質の問題である。

### 4.4 直し方

| 案 | 中身 | 規模 | 危険 |
| --- | --- | --- | --- |
| A | 回収の終わりに、最上段のフレームを含む塊の次の 1 つ(行き来の振動を避ける)より後ろの塊を捨てる。`ptr_at` では捨てない | 約 20〜40 行と試験 | 小さい〜中くらい。JIT が読む `StackWindow` を書き直すこと、継続の写しが値スタックの外にあること(`cont_make` は写しを取る)を確かめる |
| B | 塊を `mmap` で取り、捨てるときは `munmap` する(ヒープのページと同じ) | 案 A に約 20 行 | 小さい |
| C | 予算(V230 の案 C)に塊を数える | 約 10 行 | 小さい |

案 A を行うと、次の 5 節の制限が起こりやすくなる。
5 節の修正と同じマイルストーンで行い、5 節の例を試験に入れる必要がある。

### 4.5 試験

- `keleut_rt::stack` の単体の試験で、深く置いてから戻り、回収の後の `chunk_count()` が 2 以下になることを確かめる。
- `conformance/gc/` に、`chunks.kel` の MODE 3 を小さくした例(例えば深さ 300 万、`--max-depth` 付き)を `ulimit -v` の下で置く。
  直す前は 3、直した後は 0 になる上限を選ぶが、上限の揺れに弱いので、余裕を大きく取る【推論】。

## 5. `cont_resume` の失敗の後の注入(M89 の残した制限の 1)

### 5.1 現状

- `cont_resume`(`rustkeleut/crates/keleut-interp/src/interp.rs:1588-1660`)は、継続のフレームをすべて置けるまで継続を変えず、置けなければ `used` を立てずにメモリの不足を返す。
  外側の `$rt_handle` は、使われていない継続として、その継続にメモリの不足を注入して中の `cancel` 節を走らせる(記録 `doc/log/261024-3-record.md:2672-2679`)。
- 注入も継続のフレームを値スタックに置き直すので、塊を取れなければ注入も失敗し、継続の中の `cancel` 節は走らない(同 `:2746-2747`)。
- 継続の写しは `cont_make`(`interp.rs:1501`)が `try_reserve_exact` で取った `Vec<u64>` にあり、フレームはそこに連続して並ぶ。

### 5.2 実測

`probe/alloc/continj.kel` は、深さ `DEPTH` の再帰の底で G の節の操作を起こし、節が `resume` の前にヒープを使い尽くす。
§13.6 によれば `inner cancel`、`own cancel`、`outer cancel` の順に走ってから 3 で終わる。
`DEPTH` 1,000 と 3,000,000、`ulimit -v` 800,000 と 1,500,000 の 4 つとも、この期待のとおりだった【実測、`results.md` の 5 節】。

### 5.3 再現しなかった理由と分類

- 注入は、継続を取り出したときと同じ位置(`$rt_handle` のフレームの上)に継続を置く。
  塊は回収しないので、取り出す前に使っていた塊が残っており、`place` は新しい塊を取らずにそれを使い直す(`stack.rs:233-234`)【推論】。
- 節の本体が使い尽くしたヒープは、巻き戻しで節のフレームが消えた後の回収で空く。
- この制限が起こるのは、注入に新しい塊が要り、そのときヒープも塊も取れない場合である。
  今の実装では、継続を作った後に塊が捨てられる場面が少なく、起こりにくい【推論】。
  4 節の案 A で塊を捨てるようにすると、継続を取り出した後に回収が走れば、注入に新しい塊が要るようになる。
- 分類は、§13.6 の「破棄する計算の中にあったハンドラは、内側から外側の順に巻き戻す」からの逸脱である。
  計画 6.5 節の「予備も尽きたら `cancel` 節からの脱出として打ち切る」は `cancel` 節の中の失敗の規則で、注入そのものが失敗する場合を定めていない。

### 5.4 直し方

| 案 | 中身 | 規模 | 危険 |
| --- | --- | --- | --- |
| A | 注入のときは、継続の写しの `Vec<u64>` をそのまま 1 つの塊として値スタックにつなぐ。フレームは写しの中で既に連続しているので、新しい確保が要らない。見出しの 1 番と 3 番の語は今と同じく書き直す | 約 60〜100 行 | 中くらい。`Vec` の容量と長さが違うと `into_boxed_slice` が確保しうるので、`cont_make` で長さちょうどに取る。塊の大きさが `CHUNK_WORDS` より小さい場合の `place` の扱いを確かめる |
| B | 注入では継続を置き直さず、写しの中の `$rt_handle` のフレームを内側から順にたどり、ハンドラ記録から `cancel` 節を直に呼ぶ | 約 100〜200 行 | 大きい。巻き戻しの順序と打ち切りの記録の規則を、注入の道と別に実装し直すことになる |
| C | 塊を捨てるとき(4 節の案 A)、使われていない継続が残っている間は、その大きさ分の塊を捨てずに残す | 約 30 行 | 小さいが、4 節の効果を弱める |

推奨は A である。
A なら、塊を捨てる 4 節の修正と矛盾しない。

### 5.5 試験

- 試験用の確保の失敗(3.5 節)で、注入のときの塊の確保を失敗させ、`inner cancel` が書かれることを確かめる。
- 4 節の修正の後に、`continj.kel` を、継続を取り出した後に回収を起こす形(例えば節の本体で大きなリストを作って捨て、それから使い尽くす)に変えて、`ki`、`kj` と `--gc-stress` で走らせる。

## 6. V215 と P252:`kw` の V8 のヒープの枯渇

### 6.1 現状

- 計画は、V8 のヒープが尽きたとき 70 で終わることを既知の逸脱とし、P252 で受け入れた(`doc/log/261024-1-plan.md:788-797`、`:1484`)。

- `keleut run --backend wasm` は Node を子プロセスで起動し、シグナルによる終わりを 70 にする(`launch.rs:269-279`)。
  ホストには `Worker` で走らせる道があり(`rustkeleut/host/keleut-host.mjs:763-789`)、`resourceLimits` は `stackSizeMb` だけを渡す。
- 標準出力のバッファはホストの JS の側にあり(記録 `doc/log/261024-3-record.md:3785`)、Node が止まると失われる。

### 6.2 実測

- `oomlist.kel` を `keleut run --backend wasm` で走らせると、24 秒後に `FATAL ERROR: Ineffective mark-compacts near heap limit` で Node が止まり、`keleut` は 70 で終わった。

- `probe/alloc/v8worker.mjs` は、`resourceLimits.maxOldGenerationSizeMb: 64` の `Worker` でリストを伸ばし続ける。
  `Worker` がヒープを使い尽くすと、主スレッドは `error` の `ERR_WORKER_OUT_OF_MEMORY` と `exit` の 1 を受け取り、止まらずに走り続けた(Node 26.9.0、0.3 秒)【実測】。

### 6.3 分類

§15.5 からの逸脱で、P252 により既知の逸脱として受け入れ済みである。
IRSpec 1 節が同じ結果の保証から除いているので、IRSpec との矛盾は無い。

### 6.4 直し方

| 案 | 中身 | 規模 | 危険 |
| --- | --- | --- | --- |
| A | 今のまま(文書化した既知の逸脱) | 0 | 無い |
| B | いつも `Worker` で走らせ、`maxOldGenerationSizeMb` を渡す。標準出力のバッファを `SharedArrayBuffer` に置くか、主スレッドに送ってから書く。`ERR_WORKER_OUT_OF_MEMORY` を受け取ったら、主スレッドがバッファを書き出し、`実行時エラー: メモリ不足です` を書いて 3 で終わる | ホストで約 100〜200 行 | 中くらい。`cancel` 節は走らない。`Worker` の起動の費用(記録の `echoln` 1 行の 0.03 秒の中身)と、`--stack-size` で走らせる今の直の道との差を測る必要がある |
| C | 案 B に加えて、Wasm のコードが一定の回数の確保ごとにホストを呼び、`v8.getHeapStatistics()` の使用量が限度に近ければ `gc()`(`--expose-gc`)の後に測り直し、まだ近ければメモリの不足の状態語を立てる | 約 200〜300 行(`keleut-wasm` の生成とホスト) | 大きい。確保の多いプログラムの速さに効く。1 回の大きな確保が閾値を飛び越えると V8 が先に止まる |

- 案 B は「標準出力を失わずに 3 で終わる」ところまで直すが、`cancel` 節は走らないので、§15.5 からの逸脱は残る【推論】。
  `cancel` 節を走らせるには案 C が要る。
- 案 B と C を採るかは、P252 の決定を改めることになるので、所有者への問いにする。

## 7. 範囲の外の気づき

- フロントエンドも拡張の鎖で 2 乗より速く増える【実測】。
  `keleut emit-kir` は top 12,000 段で 226 秒、6.5 GB、`keleut check` は top 6,000 段で 12 秒、1.9 GB だった。
  `diktor --type-check` も top 6,000 段で 27 秒、2.4 GB で、2 つのフロントエンドに共通の性質である。
- フロントエンドの確保の失敗も 134 になる【実測】。

## 8. 計画への提案

順序の提案(番号は計画の作成者が振る):

1. **試験用の確保の失敗の仕組み**を先に作る(3.5 節)。
   以後の修正の試験を決定的にする。
2. **V229 の案 A と B**(形の表の確保を失敗を返すものにし、`kw` も 70 でなくメモリの不足にする)。
   §15.5 の逸脱を閉じる最小の修正である。
   試験は 2.5 節の cram と、試験用の失敗の例。
3. **V230 の案 A、B、E**(回収の中の確保をなくす、大域の確保器の予備、JIT の翻訳の前の残りの検査)と、IRSpec と AGENTS.md への残りの窓の記述(案 F)。
   案 C(`RLIMIT_AS` からの予算)は、3 の後に `sweep_as.sh` で 134 が残るかを測ってから決める。
4. **値スタックの塊の回収(4 節の案 A、B)と、注入の修正(5 節の案 A)を 1 つのマイルストーンで**行う。
   片方だけを行うと、5 節の制限が表に出る。
5. **V215** は所有者への問いにする(案 A のまま、B、C)。
6. 形の表の回収(V229 の案 C)と線形の表現(案 D)は、項目 (5) の急がない設計の側に回す。

所有者への問いの候補:

- V229 と V230 で、直しきれない窓(LLVM の中の失敗、OOM killer)を、IRSpec 1 節の同じ結果の保証の除外に足してよいか。
- `RLIMIT_AS` から予算を決める(V230 の案 C)のように、処理系がメモリの限度を自分で決めて早めにメモリの不足にする振る舞いを入れてよいか。
- V215 で、`cancel` 節は走らないが出力を保って 3 で終わる案 B を入れるか、P252 の決定のまま 70 にしておくか。

受け入れの検査に足すもの:

- `sweep_as.sh oomlist.kir 300000 700000 25000`(手で走らせ、プログラムの評価の中での 134 が無いことを見る)。
- `run_chain.sh` の fun 2,000〜8,000 段(形の表の大きさの回帰を見る)。
