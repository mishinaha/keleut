## 2. V207: 箱に入れない引数の入口

### 2.1 中身

LIR の関数の引数と戻り値はどれも一様な語(`any`)で、`Int64` と `Float64` の引数は箱に入れて渡す(`rustkeleut/doc/lir.md:47-49`、計画 300 行)。
JIT は箱を作るたびに実行時の関数 `krt_box` を呼ぶ(`rustkeleut/crates/keleut-llvm/src/codegen.rs:834-848`)。
`krt_box` は `alloc_with` を通り、`catch_unwind` で包んだ中で安全点を記録してから `Rt::box_i64` か `Rt::box_f64` で確保する(`rustkeleut/crates/keleut-interp/src/native.rs:699-712`、`1213-1248`)。
台帳の V207 は、呼ぶ側と呼ばれる側が引数ごとの形を合わせたレジスタの入口で、箱を作らずに渡す案である(計画 1445 行、記録 5643 行)。
M93 は、インタプリタに移る道とスタブで箱を作り直す仕組み(安全点の外の確保)が要るとして延期した(m93 264-276 行、記録 3532-3535 行)。

### 2.2 測った費用

- `kt1000` で、`Int64` の 2 引数の末尾再帰 1,000 万回 `tail64` は 226 ms、同じ本体を `Int32` で書いた `tail32b` は 44 ms だった【実測】(m93 267-268 行、303 行)。
  `Float64` の `tailf64` は 231 ms、`kw` の `tail64` は 83 ms だった【実測】(m93 303-304 行)。
- 既定の段の `tail64` の内訳は、`krt_box` 17 %、`Rt::box_i64` 13 %、`Heap::try_alloc` 12 %、`Rt::alloc` 10 %、`Heap::sweep` 15 %、JIT のコード 15 % だった【実測】(`probe/perf.txt`)。
  確保の道(`krt_box` から `try_alloc` まで)が約 52 %、掃除が約 15 % で、合わせて約 67 % になる。
  m93 の 78 %(m93 269 行)と同じ向きである。
  `tailf64` もほぼ同じ内訳だった【実測】(`probe/perf.txt`)。
- `tail64` の回収は 38 回で、回収の時間の合計は、時間を測った 3 回で 0.15〜0.24 秒だった(負荷の平均 20〜37 のとき)【実測】(本調査の走らせ直し。`probe/gcstats.txt` の 1 回は 0.08 秒)。
  同じ回の経過時間は 0.65〜0.92 秒だったので、回収は全体の 2〜3 割である。
  残りの多くは、空きリストから 1 区画を取る速い道そのものではなく、そこへ着くまでの呼び出しの道だと考える【推論】。
  `try_alloc` の速い道は空きリストの先頭を外すか切り出しの位置を進めるだけである(`rustkeleut/crates/keleut-rt/src/heap.rs:329-349`)。

### 2.3 見込める効果と代案

V207 の入口を入れれば、末尾再帰の `Int64` と `Float64` の引数は箱を作らない。
`kw` が局所変数を `i64` のまま渡して `tail32b` と `tail64` の差がほとんど無いこと(m93 270-271 行)から、`tail64` は `tail32b` に近づくと見込む【推論】。
ただし、効くのは JIT の関数どうしの呼び出しで、引数の Rep が呼ぶ側に分かっている場合だけである。
多相の関数やクロージャを通す呼び出し、戻り値(D503 で一様)、データとレコードのフィールドの箱は残る【推論】。

V207 より小さい代案が 2 つある。

1. **JIT の中の確保の速い道**: 空きリストか切り出しの位置から 1 区画を取る処理を JIT のコードの中で行い、取れないときだけ実行時の関数を呼ぶ。
   M93 のフレームを置く速い道(V214、m93 3.1 節)と同じ形である。
   呼び出しの規約を変えず、インタプリタに移る道で箱を作り直す必要もない。
   `tail64` の確保の道の約 5 割のうち、呼び出しの分を減らせる【推論】。
   箱だけでなく、`rec_new`、`ctor_new` などの確保にも効く。
   `records` の内訳にも `krt_rec_new` と `try_alloc` と `Rt::alloc` が合わせて 1 割ほどある【実測】(`probe/perf.txt`)。
   安全点の記録(`at_safepoint`)と `--gc-stress` の確保の場所の数え方(`rustkeleut/crates/keleut-rt/src/gc.rs:617-660`)を JIT の側で再現する必要がある。
   `--gc-stress` のときだけ実行時の関数を通せば、`--gc-stress` の振る舞いは変わらない【推論】。
2. **自己末尾呼び出しの箱を外す**: JIT の関数の中で、自分への `tail_call_direct` を、入口の `unbox` の後への枝にし、生の値のまま回す。
   LIR は非巡回と定めている(`rustkeleut/doc/lir.md:34-37`)ので、LIR ではなく LLVM への翻訳の中で行う。
   1 つの関数の中で閉じるので、入口の表と呼び出しの規約は変わらない。
   `tail64` と `tailf64` の形(1 つの関数のループ)はこれで箱が消える【推論】。
   入口で行う検査(ネイティブのスタックの下限、`alternating` の段の選び直し、`depth_enter`)を枝の先でどう扱うかを決める必要がある。
   `ka` の組は、段を選び直す回数が減るので、試す境目が減る。

### 2.4 規模、危険、依存、仕様

- V207 の入口は、レジスタの入口(V206、m93 3.2 節)を引数の形ごとに分け、スタブ、`krt_fx`、`interp_stub_r` の道で箱を作り直す。
  作り直しは安全点の外の確保になり、根の規則(`rustkeleut/doc/lir.md` 1.8 節)を広げる必要がある【推論】。
  記録は、M93 の変更より大きいと見積もった(記録 3532-3535 行)。
- 計画 1408 行は、V207 を全組の差 0 を条件に入れるとしている。
- 仕様への影響は無い。
  KIR は変わらず、LIR の文書(`rustkeleut/doc/lir.md`)と `native.rs` の冒頭の説明が変わる。

### 2.5 推奨

先に試作して測る。
順は、(1) JIT の中の確保の速い道、(2) 自己末尾呼び出しの箱を外す、(3) 残った差を見て V207 の入口を入れるか決める、とする。
(1) と (2) はどちらも呼び出しの規約を変えないので、全組の差 0 の関門(`kconform --pairs ki,kj,kt,ka,km --suite all` と `--suite depth`、`--extra=--gc-stress`)で確かめやすい【推論】。
測る対象は `bench/programs/` の `tail64`、`tailf64`、`records`、`typecheck` と、`probe/livegc.kel` でよい。

## 3. V225: JIT のエフェクトの命令の費用

### 3.1 中身

JIT はエフェクトの命令の被演算子をスロットに書き、`krt_fx` を呼んでインタプリタの同じ命令を 1 つ走らせる(`rustkeleut/crates/keleut-interp/src/native.rs:48-54`、`1658` 行、`rustkeleut/crates/keleut-llvm/src/codegen.rs:1537-1610`)。
継続の再開(`cont_resume`)は、写し戻した区間を `krt_fx` の中のインタプリタで走らせる(`rustkeleut/crates/keleut-interp/src/interp.rs:1692-1745` の `FxCall::Resume` の枝)。
したがって、再開した継続の中のコードは、JIT 済みの関数のものでもインタプリタで走る(記録 5617 行)。

### 3.2 測った費用

- `gen`(G の節の生成器)は `ki` 639 ms、`kt1000` 627 ms、`kw` 146 ms だった【実測】(m93 306 行)。
  `tailresume`(T の節の末尾 `resume`)は `ki` 867 ms、`kt1000` 549 ms、`kw` 154 ms だった【実測】(m93 305 行)。
  本調査の負荷の高い計測でも、`gen` は `kt1000` と `ki` がほぼ同じで、`kw` が約 4 分の 1 だった【実測】(`probe/bench.txt`)。
- 既定の段の `gen` の内訳は、libc 20 %、`Interp::native_fx` 13 %、`Interp::fx` 12 %(中の閉包を含む)、`Interp::code` 7 %、`krt_fx` 7 %、`Interp::fx_call` 4 %、`Rt::cont_new` 3 %、JIT のコード 2 % だった【実測】(`probe/perf.txt`)。
  `tailresume` は libc 32 %、`Interp::native_fx` 11 %、`Interp::fx_call` 9 %、`krt_fx` 6 %、`Rt::hr` と `hr_index` 6 %、`Vec` の作成と伸長 4 % だった【実測】(同)。
  libc の内訳は記号が引けていない。
  M93 は libc の確保と解放だとしている(m93 283 行)。
- `gen` の回収の統計では、継続の表(`gc.rs:109-115` の `Table::Cont`)の項目が 216,000 個まで溜まり、回収で 784,784 個外れた【実測】(`probe/gcstats.txt`)。
  `perform` のたびに継続の表の項目と Rust の `Vec` を作っていると考える【推論】。

### 3.3 見込める効果と規模

改め方は 2 段に分けられる【推論】。

1. **`krt_fx` の中の確保を減らす**: 継続の作成と再開、ハンドラの記録の引き当て(`Rt::hr`)で毎回作る `Vec` を、使い回す領域か値スタックの上の領域にする。
   インタプリタの `ki` にも同じだけ効く。
   `tailresume` で libc と `Vec` が 3 割を超えるので、その一部を減らせる。
   変えるのは `keleut-rt` と `keleut-interp` の中だけで、JIT の翻訳は変わらない。
2. **エフェクトの命令を LLVM の命令にし、再開した継続を JIT で走らせる**: WasmGC の後段が関数ごとの再開の入口(`br_table` で呼び出しの後のブロックへ移る)で継続を再開している形(AGENTS.md の WasmGC の項)を、JIT にも作る。
   JIT の関数のすべての再開点に入口を作り、値スタックのフレームから生きているレジスタを読み直す。
   `gen` の時間の大半を占めるインタプリタの実行(`Interp::code`、`exec_inner`、`fx`)が JIT のコードになるので、`kw` との差の多くはここにある【推論】。
   規模は大きく、`alternating` と `mixed` の段の組み合わせ、`--gc-stress` の根、G の節の継続の写しの規則(`rustkeleut/doc/lir.md` 1.8 節、1.9 節)のどれにも触れる。

G と T の節を多く使う実際のプログラムの比重は、まだ分からない(m93 285 行)。
`bench/programs/typecheck.kel` は N の節(脱出)だけを使い、`abort` の脱出の費用は `kt1000` で 1 フレーム約 40 ns と小さい(m93 257-262 行)。

### 3.4 仕様への影響

無い。
LIR の意味、KIR、§13 の意味論は変わらない。

### 3.5 推奨

先に試作して測る。
まず 1(`krt_fx` の中の確保を減らす)を行い、`gen` と `tailresume` を `ki`、`kt1000`、`kw` で測り直す。
そのうえで、`kt1000` と `kw` の差がまだ 2 倍を超えるなら、2 の設計を別の計画で起こす【推論】。
2 を本計画に入れるなら、受け入れの関門は全組の差 0 と `--suite depth`(`conformance/depth/gresume.t` を含む)にする。

## 4. V208: 参照カウントと追跡型 GC の比較

### 4.1 中身

Koka や Lean 4 のように、LIR の下ろしで `dup` と `drop` を入れ、その場で再利用する方式(Perceus)と、いまの動かさないマークスイープを比べる案である(`doc/log/261024-1-spike/survey/tiering-gc.md:234-253`、計画 1372 行と 1446 行)。
計画は v1 をマークスイープで作り、比較を延期した(D526)。

### 4.2 測った費用

- `records` の回収は 26 回、0.045〜0.050 秒、`typecheck` は 29 回、0.025 秒だった(負荷の平均 20〜37 のとき)【実測】(`probe/gcstats.txt`)。
  m93 の `kt1000` の経過時間(`records` 292 ms、`typecheck` 324 ms。m93 312 行、314 行)に比べると、それぞれ 1〜2 割と 1 割以下である。
  ただし負荷の違う回の値どうしの比なので、目安にとどめる。
- `records` の内訳では、`Heap::sweep` が 7 %、確保の道(`try_alloc`、`Rt::alloc`、`krt_rec_new`、`rec_new`)が合わせて約 15 % で、レコードのフィールドの引き当て(`rec_field`、`krt_shape_find`、`ShapeTable::labels`、`krt_rec_field`)が約 21 % だった【実測】(`probe/perf.txt`)。
- `probe/livegc.kel` は、生きているリストを持ったまま、すぐ死ぬ 2 フィールドのレコードを 2,000 万個作る。
  リストの長さを 1、10 万、100 万、400 万にすると、JIT の回収は 76、76、22、9 回で、回収の時間は 0.08、0.11、0.22、0.20 秒だった【実測】(`probe/livegc.txt`)。
  経過時間は 1.11、1.14、1.41、1.65 秒で、400 万の長さのリストを作る時間も含む。
  ヒープが生きている量に応じて大きくなるので、回収の回数が減り、印を付け直す費用が時間に比例して増えることはなかった。
  同じ試料で、V8 の世代別 GC を使う `kw` は 0.95、0.90、1.09、1.65 秒だった【実測】(同)。

### 4.3 判断

参照カウントで得られるのは、回収の時間と、確保の道の一部までである【推論】。
測った範囲では、回収は全体の 1〜3 割だった。
一方で作業は、LIR の全関数に増減の命令を入れる解析のパス、インタプリタと JIT と WasmGC の 3 つの後段、`Ref` と `MutableArray` と `let rec` の環境を通した循環の扱い、継続の区間の写しの扱いに及ぶ(`tiering-gc.md:234-253`)。
WasmGC の後段は V8 の GC を使い続けるので、後段の間で回収の方式が分かれる。
比べるための試作だけでも、LIR の下ろしの大きな改修になる【推論】。

### 4.4 推奨

行わないで閉じる。
理由は、測った回収の費用が小さいこと、作業が全後段に及ぶこと、比べる対象の負荷(コンパイラのような確保の多い処理)で回収が支配していないこと(`typecheck` で 1 割以下)である。
将来、確保と回収が支配するプログラムが現れたら、V209 と合わせて台帳に戻す。

## 5. V209: 世代別 GC か MMTk

### 5.1 中身

いまの GC は、動かさないマークスイープを全体を止めて行う(計画 D526、`tiering-gc.md:278-288`)。
世代別にするには、書き込みの障壁が `Ref.set`、`MutableArray.set`、`let rec` の環境の差し替えの 3 か所に要る(`tiering-gc.md:299-302`、計画 1447 行)。
MMTk に乗り換えれば Immix や世代別の計画を使えるが、動かす計画には、箱を動かせることが前提になる(`tiering-gc.md:303-306`)。

### 5.2 測った費用と見込める効果

4.2 節の値がそのまま当てはまる。
世代別にして減らせるのは、若い世代の外の箱に印を付け直す費用と、掃除の費用である【推論】。
`probe/livegc.kel` で、生きている量を 400 万要素まで増やしても回収の時間は 0.2 秒台で、全体の 15 % 前後だった【実測】(`probe/livegc.txt`)。
`tail64` の掃除(15 %)は、箱がすぐ死ぬ形なので若い世代の回収で減る見込みがある【推論】。
ただし、2.3 節の代案や V207 で箱そのものを作らなくすれば、掃除の分も消える。

### 5.3 規模、危険、依存

- 世代別にするだけでも、障壁を JIT とインタプリタの 3 か所に入れ、記憶集合を根に加える。
  `--gc-stress` の規則(`rustkeleut/crates/keleut-rt/src/gc.rs:617-660`)も若い世代と古い世代に分けて決め直す必要がある【推論】。
- MMTk の動かす計画を使うなら、JIT のレジスタと Rust の側が持つ箱の番地を、回収の後に読み直す規則が要る。
  いまの根の規則(`rustkeleut/doc/lir.md` 1.8 節)は、箱が動かないことを前提にしている【推論】。
- MMTk の版は計画のときに mmtk 0.33.0(rust-version 1.84)を確かめただけである(`tiering-gc.md:303`)。
  本調査では版を確かめ直していない。

### 5.4 推奨

行わない。
回収が支配するプログラムが無く、得られる時間の上限が 1〜3 割で、2 節の確保の道の改め方のほうが小さい作業で同じ箇所に効くからである【推論】。
閉じるか延期のまま残すかは、計画の書き手に任せる。
残すなら、戻す条件を「回収の時間が全体の 3 割を超えるプログラムを `bench/programs/` に足せたとき」のように測れる形で書くことを勧める。

## 6. V210: 単位ごとの `.kir` と結合

### 6.1 中身

いまの `.kir` は、プレリュードを含む全単位を初期化の順に並べた自己完結のプログラムである(計画 326 行、D505 は計画 1351 行、`doc/IRSpec.md:80-91`)。
IRSpec 2.1 節は、単位ごとの `.kir` と結合を 1.0 では定めないとしている(`doc/IRSpec.md:91`)。
V210 は、単位ごとに `.kir` を書き、後で結合する分割コンパイルである(計画 1448 行、記録 5646 行)。

### 6.2 測った費用

- `keleut run --backend interp` で、`hello` は `.kir` から 10.2 ms、`.kel` から 12.3 ms だった【実測】(`probe/frontend.txt`)。
  前置きの型検査と KIR の書き出しを含むフロントエンドの費用は、1 回あたり約 2 ms である。
- `keleut emit-kir` は、`hello` で 11.5 ms、`bench/programs/typecheck.kel` で 15.0 ms だった【実測】(同)。
- `typecheck` の実行は `.kir` から 918 ms、`.kel` から 869 ms で、差は負荷の揺れの中にある【実測】(同)。

分割コンパイルで省けるのは、変わらない単位(主にプレリュード)の型検査と書き出しで、測った範囲では 1 回あたり数 ms である。
いまのリポジトリに、複数のファイルからなる大きな Keleut のプログラムは無い。

### 6.3 仕様への影響

IRSpec 14 節は、副版で足してよいものを、読み飛ばせる節(id が 0x80 以上)と、必要な機能のビットで守る新しい命令に限り、意味や符号を変えるときは主版を上げるとしている(`doc/IRSpec.md:1691-1700`)。
単位だけを持つ `.kir` は自己完結のプログラムでないので、1.0 の読み手が読み飛ばして走らせると、意味が変わる。
したがって、副版にするなら、単位のファイルであることを必要な機能のビットで示し、1.0 の読み手に拒否させる(`doc/IRSpec.md:1711-1712`)【推論】。
さらに、単位どうしの記号の解決の規則が要る。
いまの記号はリンクと診断にだけ使い、実行時の意味に使わない(計画 4.3 節)ので、結合の規則を新しく書くことになる【推論】。
Diktor と RustKeleut の両方の書き手と読み手、`conformance/kir-fixtures/` の副版ごとの見本(`doc/IRSpec.md:1696`)、`kconform kir-roundtrip` が変わる。

### 6.4 推奨

行わない。
得られる時間は 1 回あたり数 ms で、作業は KIR の版の改訂と 2 つの実装に及ぶからである。
台帳には KIR 1.x の候補として残し、複数のファイルからなる大きなプログラムを扱う必要が出たときに計画を起こす。

## 7. V211: WasmFX

### 7.1 中身

WasmGC の後段の G の節を、スタック切り替えの提案(WasmFX)の `cont.new`、`suspend`、`resume` で実装する案である(計画 937 行、1449 行)。
いまの `kw` は、継続を関数ごとのフレームの記録の列として取り出し、再開の入口から戻す(AGENTS.md の WasmGC の項)。
そのため、深さ `d` からの yield の費用は `d` に比例し、`kw` で 1 段約 33 ns である【実測】(m93 238-255 行)。

### 7.2 Node 26.9.0 の状態

計画のときの試作をそのまま走らせ直した【実測】(`probe/node-flags.txt`)。

- フラグなしでは `CompileError: ... core stack switching not enabled (enable with --experimental-wasm-wasmfx)` で拒まれる。
- `--experimental-wasm-wasmfx` を付けると、`cont.new`、`suspend`、`resume`、`cont.bind`、`resume_throw` は動く。
- `switch` を使うモジュールは、`WebAssembly.validate` が true を返した後、コンパイルで `# Fatal error in , line 0 / # unimplemented code` を出してプロセスが落ちる(`fx2.mjs`、`fx3.mjs`)。
- `node --v8-options` では、`--experimental-wasm-wasmfx` の既定は無効、JSPI の伸びるスタック `--experimental-wasm-growable-stacks` の既定も無効、`--wasm-stack-switching-stack-size` の既定は 984 KB だった。

計画のとき(`doc/log/261024-1-spike/survey/spike-wasm.md:78-92`、計画 182 行の E9)から変わっていない。

### 7.3 規模と危険

`kw` に WasmFX を入れると、WasmGC の後段の中に継続の機構が 2 つになる。
計画は脱出と継続の機構を 1 つにすることを決めている(計画 230 行、D531、D532)。
フラグが要るので、`keleut run --backend wasm` の既定の起動の仕方を変えるか、実験の道として分けることになる。
`switch` がプロセスを落とし、事前に調べる手段も無いので、使う命令を限っても、V8 の版が変わると落ちる危険が残る【推論】。
フラグつきの道の差分試験を組むなら、`kw` と同じく全組の差 0 が要る。

### 7.4 推奨

行わない。
戻す条件は、Node の出荷の版で `--experimental-wasm-wasmfx` が既定で有効になり、`switch` を含む命令が落ちずにコンパイルできることとする。
そのときも、深い G の yield(`gdepth100`、`gdepth1000`)が実際のプログラムで効くかを先に測る。

## 8. V212: `wasm:text-decoder`

### 8.1 中身

i8 の配列を UTF-8 として解いて JS の文字列にする組み込み `decodeStringFromUTF8Array` を使う案である(計画 192 行の E19、1450 行)。
計画は、使わないとして延期した(記録 5648 行)。

### 8.2 Node 26.9.0 の状態

フラグなしでは `Import #0 "wasm:text-decoder": module is not an object or function` で失敗し、`--experimental-wasm-imported-strings-utf8` を付けると `"Kあ"` を得た【実測】(`probe/node-flags.txt`)。
計画のときと同じである(`spike-wasm.md:67`)。

### 8.3 使い道

いまの host は、Keleut の文字列を JS の文字列にしない。
標準出力は、wasm が線形メモリのバッファに写したバイト列を `Uint8Array` で受け取り、`fs.writeSync` で書く(`rustkeleut/host/keleut-host.mjs:200-264`、`653` 行)。
診断の文面も、文字列の値をバイト列として読み出して連結する(`rustkeleut/host/keleut-host.mjs:463-473`、`657-667`)。
バイト列のまま出すのは、UTF-8 として正しくない文字列もそのまま出す必要があるからだと考える【推論】。
UTF-8 として解く組み込みは、正しくない列を置き換え文字にするので、この規約に合わない【推論】。

### 8.4 推奨

使い道が無いので閉じる。
フラグが外れても、出力の道を変える理由にならない。
