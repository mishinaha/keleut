## 2. 事実の誤りと不正確な記述

1. **alloc.md 3.5 節**:「ヒープと値スタックの塊は大域の確保器を通らない(`mmap` と `alloc_zeroed`)」は、塊について誤りである。
   `keleut-rt/src/stack.rs:31` は `std::alloc::{Layout, alloc_zeroed}` を使い、`:88` で塊を取る【確認】。
   `std::alloc::alloc_zeroed` は `#[global_allocator]` を通るので、V230 の案 B(大域の確保器を包んで予備を持つ)を入れると、塊の確保もその予備と試験用の失敗(`KELEUT_TEST_ALLOC_FAIL`)の対象になる。
   ヒープ(`heap.rs` の `mmap`)だけが外にある。
   計画では、案 B の予備を塊の確保が使い切る順序と、試験用の失敗で塊だけを失敗させる方法を決め直す必要がある。
2. **records.md 1.2 節の A**:「計画 261024-1 と記録はこの番号を一度も引かない(grep で該当は無い)」は、文字どおりには誤りである。
   報告の grep の型 `V1[5-9][0-9]` は V190〜V199 にも当たり、`261024-1-plan.md:61` は V190 を続番の出典として引き、記録も V191〜V199 を引く【確認】。
   結論(V149〜V190 の項目がその後の計画に入っていない)は変わらないが、「どれも未着手」は M100 の REPL の作業(V151 の shebang など)と照らしていないので【推論】である。
3. **records.md 1.1 節の表**:(3) の `conformance/float/` の出典 `記録 :5455-5459` は誤りで、M101 の 10 は 5461〜5464 行である【確認】(`small.md` の行番号が正しい)。
   V218 の出典 `:2313-2350` は登録の作業の行で、台帳の番号を立てた文は 2387〜2392 行である(`decide.md` が正しい)。
4. **small.md 1 節**:宣言 160,000 個の `keleut check` の最大 606 MB を、M98 の 541 MB と「ほぼ同じ」とするのは言い過ぎである(約 12 % 大きい)。

## 3. 報告どうしの依存と食い違い

1. **番号の候補の衝突**。
   `gaps.md` は (a) に V234 を、`records.md` 2.3 節は 1.2 節の B〜D の番号の無い項目に V234 からを勧める。
   `alloc.md`、`decide.md`、`small.md` も台帳と所有者への問いの候補を出す。
   4 節の表に集めたので、計画の書き手が一度に振る。
2. **V230 の案 B はフロントエンドにも効く**。
   案 B の確保器は `keleut-cli` のプロセス全体に掛かるので、`alloc.md` 7 節のフロントエンドの 134(`Tc::extend`)と、`small.md` 1 節の `ulimit -v 1,200,000` の 134 も変わる。
   どちらの報告もこれに触れていない。
   フロントエンドの中の確保の失敗は、§15.5 の表では「型検査に要する領域が処理系の限度を超えた」の 1 になるはずで、実行時の `Stop::OutOfMemory`(3)とは違う道が要る。
   案 B の印を実行のスレッドとフロントエンドのスレッドのどちらで見るかを決めないと、フロントエンドの失敗が 3 になるか、実行の失敗が 1 になりうる【推論】。
   LLVM の翻訳のスレッドでの確保の失敗も同じ印を立てうる(案 B の印はプロセスに 1 つ)ので、翻訳の失敗をプログラムのメモリの不足と取り違えない規則も要る【推論】。
3. **`ulimit -v` の下の 70 は 2 種類ある**。
   `small.md` は「KIR の処理のスレッドを作れません」(`.kel` で `forget` のとき 1,250,000〜1,350,000 KiB)を、`alloc.md` 7 節は実行のスレッドの約 1.1 GB の予約(`.kir` で約 1,200,000 KiB 以下)を挙げる。
   仕組みが違い(前者はフロントエンドの常駐が残すメモリの不足、後者はスタックの予約の大きさ)、`small.md` はどちらも (2) に引き渡すとし、`alloc.md` は範囲の外の気づきとして番号を求めていない。
   AGENTS.md は、`RLIMIT_AS` が有限のときにフロントエンドのスレッドのスタックだけを縮めると書く(V226)。
   実行のスレッドと KIR のスレッドに同じ扱いをするかを、計画で 1 つの項目にする必要がある。
   70 は内部の誤りの終了状態なので、型検査を通ったプログラムが 70 で止まる点は §15.5 の表に当てはまらない【推論】。
4. **LangSpec §15.5 の表の 1 の行を 2 つの報告が触る**。
   `decide.md` 1.6 節は、`keleut run` の書き出しの限度(1)を入れるために条件を「型検査か、実行の前の変換」に広げる案を出す。
   上の 2 のフロントエンドの確保の失敗と、3 の KIR のスレッドの 70 も、同じ行の「実行の前」の失敗である。
   LangSpec の改訂は 1 回にまとめ、3 つの場合の終了状態を同時に決めるのがよい【推論】。
5. **small.md 1 と alloc.md の `ulimit -v` の試験の順序**。
   `forget` を `drop` にすると、`.kel` から走らせる場合の通る上限が約 200 MB 動く【実測、small.md】。
   `alloc.md` の試験は `.kir` から走らせるので直接は変わらないが、`.kel` を `ulimit -v` の下で走らせる試験(`gc.t` の形)を足すなら、small 1 を先に行ってから上限を決める必要がある。
6. **perf.md と alloc.md が同じ確保の道を触る**。

   `alloc.md` の V230 の案 C(`RLIMIT_AS` からの予算)と V229 の案 A'(形の表を予算に数える)を採ると、速い道もその予算を見なければならない。

7. **alloc.md 6.4 節の案 B と gaps.md (a) の測り方**。
   V215 の案 B は `kw` をいつも `Worker` で走らせる。

8. **decide.md の V224 と records.md 1.2 節の C**。
   `records.md` は、構文解析の限度を木の深さで数えるために 10 万段の `id(...)` と `else if` の鎖で Diktor が 0、keleut が 2 で終わる差(記録 4564〜4566 行、M98 の 5)を、V224 と同じ扱いで台帳に載せることを勧める。
   `decide.md` は V224 に「構文解析の 20 万段の限度も書き添える」とするだけで、この差を扱わない。
   `probe/decide/v224.out` の 199,999 段の行(`入れ子の限度 200000 を超えました`)も、入れ子の段の数と木の深さが違う数え方であることを示す。

   これは REPL の限度ではなく、`keleut run` と `keleut check` の差なので、V224 とは別の番号にするのがよい【推論】。

## 5. 漏れ

1. **V229 の新しい cram に要る既知の差**。
   `alloc.md` 2.5 節の cram(`ulimit -v 524288` で func 3,000 の `.kir`)は、組 `dk`、`dk-ir`、`kf`、`x-ir` では shim が Diktor で走らせ、Diktor は 0(`before`、`3000`)で終わる(`probe/alloc/results.md` 2 節の表の最後の行)。
   記録(3)と違うので、V215 の `oom.t` の項目(`known-diffs.toml:532-563`)と同じ形で、`against = "record"` と `against = "pair"` の項目をコマンドごとに 2 つ足す必要がある。
   報告はこれに触れていない。
2. **LLVM の組での V229 の cram**。
   LLVM の組は shim がコマンドの `--backend interp` を除いて JIT で走らせる(`gaps.md` 2.2 節の `組の後段の上書き`)。
   `alloc.md` 3.2 節の表では、JIT は `ulimit -v` の上限によって 134 になる窓が interp より広い。
   V230 を直す前に V229 の cram を足すと、`kj` から `km` の組で 134 が出て、後段の組の間の差(既知の差で許せない)になりうる【推論】。
   V229 と V230 のマイルストーンの順か、cram の上限の選び方で避ける必要がある。
3. **形の表には予備が無い**。
   ヒープと塊は 1 MiB の予備を持ち、`cancel` 節がそこにフレームを積める(`stack.rs:23-28`)。
   V229 の案 A は形の表の確保を失敗を返すものにするだけで、メモリの不足の後に `cancel` 節が `rec_extend` を行うと、また失敗する。
   計画 261024-1 の 6.5 節の「予備も尽きたら `cancel` 節からの脱出として打ち切る」が形の表でも成り立つかを試験に入れる必要がある。
4. **gaps.md の回帰の試験の費用**。
   `cancelg.t` の深いコマンドは 1 回 5〜10 秒で、`--suite all` では `ka` の 8 回と `km` の 4 回を含む 36 の組の実行になる。
   `kw` の 1 回は約 1.6 GB のスタックを取る。
   `conformance/depth/` に置いて `--jobs 6` で走らせるか、時間とメモリを計画で見積もる必要がある。
5. **gaps.md (a) は LLVM の組を測っていない**。
   本点検で `jit-only` と `alternating=3` は通った【実測】が、`kt`、`km`、`--gc-stress` は試していない。
   直し方の候補 3(`B_wasm` を上げる)を採ると、受け付ける L の最大が下がるので、`AGENTS.md` と IRSpec の L の記述も変わる。
6. **gaps.md の時間の値は使えない**。
   1.3 節の時間の欄と 2.2 節の 954 秒と 849 秒は、`--suite all`(既定の 32 並列)と探りを同時に走らせた値である。
   `small.md` と `perf.md` の負荷の平均 9〜38 も、同じ時刻の作業による【推論】。
   M101 の締めは `--jobs 16` だった(記録 5477 行)。
   計画の受け入れの時間の見積もり(「合わせて約 32 分」)は、負荷の低いときに測り直す必要がある。
7. **decide.md 4.2 節の文字列の引用の不揃い**。
   トップレベル、タプル、レコードの中では引用符付き、`List` と `Option` の中では引用符無しで書くことは、両処理系で一致する。
   `decide.md` は表示の書式を定める案(表示-B)の論点にしているが、`show` の綴りの一貫性の問い(§16.2 の `Show` のインスタンス)でもありうる。
   計画では、表示-A を採っても、この不揃いを台帳か問いに 1 行で残すのがよい【推論】。
8. **decide.md の V223 の新しい cram と既知の差の数**。
   `diktor/test/repl_stdin.t` を足すと、`conformance/corpus/` に `.kel` は増えないが、`--suite all` の試験の数とコマンドの数が増え、V217 の項目が増える。
   記録の台帳の V217 の件数(31 項目)と、V218 を消したときの既知の差の数(1,508 件から変わる)を、計画の受け入れの数に書き直す必要がある。

10. **small.md 2 の `keleut dump bytecode` は AGENTS.md に無い**。
