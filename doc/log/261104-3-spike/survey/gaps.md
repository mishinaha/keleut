## 1. (a) cancel 節の中のハンドラ式と B_wasm

### 1.1 記録の記述とコードの所在

- 記録 261024-3-record.md の 3968 行(M95 の「計画から外れたこと」の 2)は、`cancel` 節の中に直に書いたハンドラ式が同じ深さで `$rt_handle` と `cancel` 節を重ねると、予算を引いても 1 段が `B_wasm` に収まらないことがあると書く。
  3999 行と 5677〜5678 行は、M95 の検証の後の修正の後では試していないと書く。
- `B_WASM = 1536`(`rustkeleut/crates/keleut-wasm/src/lib.rs:35`)。
  Node のスタックは `stack_size_kib`(`lib.rs:58`)が `(L + R) × B_wasm + 32 MiB`、`R = max(1024, L / 64)` で決める。
  既定の L では 1,630,208 KiB(約 1.669 × 10^9 バイト)である。
- 関数ごとの予算は `budget_of`(`crates/keleut-wasm/src/func.rs:445`)が決める。
  `$rt_handle` を末尾でなく呼ぶ関数と `cancel` 節は `B_wasm − E_rth − E_rres = 1,040`、`$rt_handle` は `E_rth = 320`(`func.rs:432`)、ほかは `B_wasm` である。
  予算は「論理的な 1 段に `$rt_handle` と `rt_resume` が 1 つずつ重なる」ことだけを見込む。
- 大きなフレームの形の関数の部分の重さは `piece_max_big`(`func.rs:122`)が決める。
- G の節がプログラムのどこかにあると、すべての関数が取り出しの区切りと記録を作る命令を持つ(`lib.rs:171` と `lib.rs:350` の `has_g`)。

`doc/lir.md` の 16.2〜16.4 節では、ハンドラ式の `$rt_handle` は `depth_push` で囲まずに呼ばれ、`cancel` 節は防壁の中で `call_cancel` により深さ `h` で呼ばれる。
したがって `cancel` 節の中に直に書いたハンドラ式では、深さ `h` に「ハンドラ式を書いた関数、外側の `$rt_handle`、`cancel` 節、内側の `$rt_handle`」の 4 つの Wasm のフレームが重なる。
予算の上限を足すと `1,040 + 320 + 1,040 + 320 = 2,720` バイトで、`B_wasm` の 1.8 倍である。

### 1.2 探りのプログラム

`probe/gen.py MODE NV N` がプログラムを書き出す。
どの形も、最も外側の `Stop` の N の節(`resume` しない)が捨てる伝播で、途中のハンドラの `cancel` 節が走り、その `cancel` 節がさらに深く再帰する。
`NV` 個の値(`let a0 = n * 3; …`)を呼び出しの後で使い、呼び出しをまたいで生かす。
環境変数 `GADD=1` は、G の節のハンドラ式を 1 つ足す(`echoln(show((perform ask()) handle { case ask() => { let r = resume(1); r + 1 } }))`)。

| 形 | 中身 | 1 つの N の論理的な段の数【実測】 |
| --- | --- | --- |
| a | `go` が末尾でハンドラ式(`cancel` 節つき)を書き、`cancel` 節が値を生かして N の節のハンドラ式を直に書き、その本体が `go(n − 1)` を呼ぶ | 2 |
| b | a の `cancel` 節の本体の中に、さらに `cancel` 節つきのハンドラ式を直に書く | 1.5 |
| c | a に加え、`go` もハンドラ式を末尾でなく書いて値を生かし、本体も値を生かして `go` を末尾でなく呼ぶ(重なるフレームのすべてを重くする) | 2 |
| d | `lv` が値を生かして N のハンドラ式を書き、本体が値を生かして `cancel` 節つきのハンドラ式を書き、`cancel` 節が `lv(n − 1)` を末尾で呼ぶ | 2 |
| e | 対照。c から `cancel` 節を除き、本体が直に `go` を呼ぶ | 2 |

段の数は、`--max-depth 1000` の `ki` で `cancel 節で例外が抑制` か 3 にならない最大の N(a は 498、b は 665、c は 498、d は 499、e は 498)から求めた。

`probe/run1.sh MODE NV N BACKEND [選択肢]` は `keleut run` を 1 回走らせる。
`probe/bytes.sh MODE NV` は、M95 の測り方(記録 4030 行)に合わせて、`keleut build --target wasm --max-depth 100000000` の出力を `ulimit -s 300000; KELEUT_WASM_DIRECT=1 node --stack-size=102400` で走らせ、`RangeError` にならない最大の N を二分探索し、`102,400 KiB / N` を出す(誤差は約 0.5%)。

### 1.4 原因の分析

- 関数ごとの推定(`frame_estimate` と `budget_of`)はどれも予算に収まっている【実測】。
  外れているのは、論理的な 1 段に重なる Wasm のフレームの数の見込みである【推論】。
  `budget_of` は「`$rt_handle` を末尾でなく呼ぶ関数か `cancel` 節」の 1 つと `$rt_handle` と `rt_resume` が 1 段に重なると見込む。
  `cancel` 節の中に直に書いたハンドラ式では、深さ `h` に予算 1,040 の関数が 2 つ(ハンドラ式を書いた関数と `cancel` 節)と `$rt_handle` が 2 つ重なる。
  形 c では、その上の深さ `h + 1` の本体が 1 つの関数だけなので、2 段の平均で `B_wasm` を少し超える。
- G の節があると、取り出しの区切りと記録を作る命令がフレームを大きくする(c の 0 と 1 の比べ合わせで約 1.6 倍)【実測】。
  推定はこの局所を数えている(M95 の「記録を作る命令の重さを分けるかの判断と区切りの重さに足した」)が、V8 の実際のフレームとの比は G の有無で変わる【推論】。
- 既定の L で失敗するには、値を 85 個ほど以上生かす関数を論理的な 1 段に 3 つ重ねる必要がある(c)。
  ふつうのプログラムで起こりやすい形ではない【推論】。
  ただし `kw` の結果が `ki` と違い、後段の組の間の差は既知の差として登録できない(記録 3911 行、M95 の kconform の変更)ので、仕様からの逸脱である。

### 1.5 直し方の候補(新しい計画で選ぶ)

1. `budget_of` で、`cancel` 節のうち中にハンドラ式を末尾でなく持つものの予算から、さらに `E_rth + E_rres` と「呼び出し元の関数の予算」を見込んで引く。
   呼び出し元の予算はプログラムの解析なしには分からないので、`cancel` 節が `$rt_handle` を呼ぶなら `(B_wasm − 2 × (E_rth + E_rres)) / 2` 程度にする案である【推論】。
2. `cancel` 節の中に直に書いたハンドラ式を下ろすとき、`cancel` 節の本体を別の関数に移して深さを 1 つ足す。
   仕様の深さの数え方(IRSpec 11 節)を変えるので採りにくい【推論】。
3. `stack_size_kib` の `B_wasm` の見込みを上げる(例えば 2,048)。
   `--stack-size` の上限 2,097,151 KiB(V203)の下で、受け付ける L の最大が下がる。
4. 推定と V8 のフレームの比を、G の有無と大きなフレームの形の境目(NV が 90〜95)で測り直し、`frame_estimate` の係数を改める。

どれを採っても、`probe/cancelg.t` を `conformance/effects/` か `conformance/depth/` に置く回帰の試験にできる(1 回 10 秒ほど)。

### 1.6 測り方の注意

- 探りの多くは、下の (b) の `--suite all --extra=--gc-stress` と同時に走らせた。
  バイト数はスタックの大きさで決まるので負荷に依らないが、時間の欄は揺れを含む。
- G の節の継続の再開(`rt_resume` が同じ段に加わる形)と `cancel` 節の重なりを組み合わせた形は試していない。
  `budget_of` は `rt_resume` の分も引いているので、その形は c より厳しくはならないと考えている【推論】。
