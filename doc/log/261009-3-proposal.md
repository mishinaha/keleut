## 3. 調査：呼び出し時に閉じた行を開く規則（§13.2）

### 3.1 規則

**呼び出し時の開き**：関数を呼び出すとき、呼び出し先の型の行が閉じていれば、その行の尾部に新しい行変数を足してから、呼び出す位置の行と一致させる。
呼び出し先の行が行変数で終わるときは、今までどおり一致させる。

この規則で、呼び出し先の行のラベルが呼び出す位置の行に含まれていれば呼べる。
ラベルの照合は今までどおり左から順に行い、足した尾部は右端に付くので、`Heap` の左右の対応（§14.1）は変わらない。

現在の仕様は、束縛の最外の矢印に閉じた行を書いたときだけ、公開する型の尾部を開く（§13.2 の表、`publish_open`）。
入れ子の矢印（引数、返り値、フィールド）、型エイリアスを展開して現れる矢印、再帰群で後ろにある関数の注釈、構文上の値でない初期化式の行は開かない。
提案する規則は、この区別を呼び出しの時点で無くす。
公開する型の開き（`publish_open`）は残す。
関数を値として渡すときには要るからである（本書 3.8 節）。

### 3.2 健全性の根拠

閉じた行 `R` を持つ関数は、本体を `R` の文脈で検査している。
したがって、その関数が起こすエフェクトは `R` のラベルに限られる。
`R` のラベルをすべて含む行 `C` の文脈で呼んでも、`C` に無いエフェクトは起きない。
これは、§13.2 がすでに公開する型の開きの根拠としている論法（994〜995 行）と同じである。

行変数で終わる行を開かないのは、その行変数が別の場所と共有されていることがあるからである。
共有された行変数の尾部を勝手に開くと、別の場所の行が変わる。

r1 は渡す側の規則が変わらないこと、r2 と r3 は閉じた文脈に無いラベルを持ち込めないこと、r4 は互いに矛盾する注釈を受理しないことを確かめている。

o1、o2、o3 は、残る順序依存を示す。
o2 では、`f` の型が `Cons(f, Cons(r.k, Nil))` で `() => Unit @ {}` に決まった後に `f()` を呼ぶので、閉じた行を開いて受理する。
o1 では、`f()` を呼ぶ時点で `f` の行は未定の変数なので、本体の行と一致させる。
その後で `f` の行が `{}` に決まり、本体の行も `{}` になって、`echoln` で落ちる。
現在の規則では o1 も o2 も拒否するので、提案する規則が受理する集合は現在の集合を含む。
しかし、受理するかどうかが文の順序に依存する形が残る。

この順序依存は、「呼び出しの時点で閉じていると分かっている行」だけを開くことから来る。
消すには、呼び出し先の行が未定のときに「含まれていればよい」という制約を覚えておき、束縛の終わりに解くことになる。
制約を型と一緒に持ち回る仕組みが要るので、本書では提案しない。
順序依存が現れるのは、注釈のない引数の関数を先に呼び、その後で閉じた行の関数と同一視する形と、値制限で一般化しない束縛を行の違う 2 つの文脈から呼ぶ形に限られる。
§13.2 に制限として書けば足りると判断する。

### 3.6 再帰群：署名を先に置く

変更 1 だけでは、a2_rec_fwd は拒否のままだった。
エラーの位置は `g` の宣言（2 行 5 桁）で、呼び出しの位置ではない。
原因は、再帰群の各束縛が、本体を検査する前は型変数 `pre` としてだけ環境に入ることにある（`elab_rec_bindings` の `names`）。
`f` の本体が `g()` を呼ぶ時点で `g` の型は未定の変数なので、変更 1 は働かず、`pre` は `f` の行 `{Print}` の矢印と単一化される。
その後で `g` の注釈 `{}` と `pre` を単一化して落ちる。
これは本書 3.5 節の o1 と同じ順序依存である。

変更 2 は、型パラメータが無く、`@` を書いたか `pub` の関数束縛について、`pre` を型変数ではなく「引数と返り値は新しい型変数、行は注釈の閉じた行」の矢印にする。
先行する本体が呼ぶ時点で行が閉じていると分かるので、変更 1 が働く。
`pre` の行は書き換えないので、後で本体の型と単一化しても食い違わない。
この変更で a2、a3、recandfwddiff が受理され、r4 は拒否のままだった。

写しの変更 2 は、型パラメータを持つ束縛を扱っていない。
型パラメータの剛定数は束縛ごとにループの中で作るので（`make_rigids`）、署名を先に置くには剛定数の生成をループの前に出す必要がある。
実装するときは、§11.29 の「相手の `pre` に入り込んだ剛定数の解放を群の終わりまで遅らせる」規則をそのまま使えるかどうかを、recandtp と recandpoly で確かめる。

### 3.10 追記（2026-10-10）：使用時の開きに一本化する案 U

利用者から、純粋な関数や限定されたエフェクトを持つ関数を広い文脈で呼べることを保ったまま、§13.2 をさらに単純にできないかと問われた。

**規則**

## 4. 型クラスの辞書渡し（決定済み）

### 4.1 現状

`diktor` は、メソッドの呼び出しで引数の値のタグを見てインスタンスを選ぶ（`lib/interp.ml` 105 行 `tycon_of_value`、483 行 `dispatch_positions`、85 行 `user_instances`）。

そのため §12.1 は、クラスパラメータが引数の頭に現れることを求め、`pure: (A) => F[A]` を拒む（`lib/elab.ml` 3631 行からの説明）。

### 4.2 設計

**辞書**：1 つのインスタンスのメソッドの実装を集めたレコードの値。
**辞書渡し**：型検査で決めたインスタンスの辞書を、実行時に関数へ渡す方式。

型検査では、次の 3 点を足す。

1. 制約付きのスキーマを具体化する時点（`Unify.instantiate`、895 行。`new_class_var` を通る）で、木に「証拠の穴」（クラスと型変数の組）を記録する。
   メソッドの参照 `show`、`Show.show`、演算子の `+` はメソッドのスキーマの具体化なので、同じ穴を持つ。
2. 束縛の終わりに、台帳の項目を 4 つに分ける。
   一般化される変数は、その束縛の辞書パラメータにする（スキーマの制約と同じ順）。
   具体型に決まった変数は、インスタンス表から辞書を組み立てる。前提（`ii_premises`）は型引数の辞書から再帰的に組み立てる。
   数値リテラルの変数は、既定化した型の辞書にする。
   どれでもない変数は、現在と同じく曖昧性エラーにする。
   結果を穴に書き込む。`ROp` や `RCtor` と同じく、評価器は再解決しない。
3. 構造的な `Eq`（§12.5）は、閉じた行の各フィールドの辞書から辞書を組み立てる関数として表す。

実行では、次の 4 点を変える。

1. 辞書パラメータを持つ束縛は、辞書を引数に取る閉包になる。
   評価器は、穴に書かれた辞書を引数レコードに加えて呼ぶ。
2. インスタンス宣言は辞書の値になる。前提付きのインスタンスは、前提の辞書を受け取って辞書を返す関数になる。
3. 組み込みのインスタンス（`lib/builtin.ml` 365〜396 行の 39 項目）は、同じ表から辞書を作る。
4. `user_instances`、`dispatch_positions`、`tycon_of_value`、`resolution_cache`、`positions_cache` を消す。

対話的な実行では、インスタンスの登録を取り消す処理が宣言表の側にすでにある。
辞書は値なので、束縛の取り消しと同じ扱いになる。

## 5. 条件式 `if e1 then e2 else e3`（決定済み）

### 5.1 意味

`if e1 then e2 else e3` は、`e1 match { case true => e2 case false => e3 }` の略記である。
`else` は省略できない。
評価の順序（§5.1）、両節の型が一致すること（§11.2）、両節が末尾位置にあること（§5.7）は、`match` の規則から従う。
実測では、`true` と `false` のリテラルパターンの 2 節を処理系が網羅的と判定し、片方だけでは「false が漏れています」と警告した。
したがって、脱糖した `match` に網羅性の警告は出ない。

### 5.2 構文

- `then` と `else` を予約語にする（§2.2 の表）。
  `doc/sample.kel`、`lib/prelude.kel`、テストに、この 2 語を識別子として使う箇所は無い。
- 優先順位は §5.2 の表の 9（`fn`）と同じ段に置く。
  `if c then a else b + 1` は `else (b + 1)` と読む。
  算術の項に置くときは `(if c then a else b) + 1` と括弧で囲む。
  `e1`、`e2`、`e3` には、入れ子の `if` や `match` を含むどの式でも書ける。
- 文の区切り（§2.3）では、`then` と `else` で始まる行は前の行に続く。
  70 行の一覧に 2 語を足す。
  `if` で始まる行は新しい文を始める。
  ガードの `if` は `case` のパターンの後ろにだけ現れるので、衝突しない。

### 5.3 実装

- `lib/lexer.ml` の予約語の表に `then` と `else` を足す（241 行から）。
- `lib/parser.mly` の `exp` 規則に、`IF exp THEN exp ELSE exp` を 1 本足し、`PBool` の 2 節を持つ `Match` を作る。
  構文木のノードは足さない。
  末尾位置の判定（`eval_clause_tail`、`spine_has_resume`）と型検査は `match` のものがそのまま働く。
- テスト：構文、型、評価、末尾位置（`if` の節での末尾呼び出し）、`then` や `else` を識別子に使ったときの診断。
- 仕様：§2.2、§2.3、§5.2、§5.7、§11.2 788〜789 行（「単独の条件式の構文はない」を削る）と、新しい節「条件式」を §5 に足す。
