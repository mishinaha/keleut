#### `return` 節の重なり

形 R は、`go` が値を生かしてハンドラ式 `(m) handle { case zz() => resume(()) case return(x) => { … let z = go(x - 1); … } }` を末尾でなく書き、`return` 節が値を生かして `go` を末尾でなく呼ぶ形である。
`$rt_handle` は手順 3 で `return` 節を `tail_call_value` で呼んで自分を置き換える(`rustkeleut/doc/lir.md` 16.3 節)。
そのため論理的な深さ `h` に、予算 1,040 の `go` と予算 `B_wasm` の `return` 節が重なり、`return` 節の呼ぶ `go` が深さ `h + 1` になる。
1 つの N が論理的な 1 段で、間に軽い段を挟まない。
重なりの上限は `1,040 + 1,536 + 176 = 2,752` バイトで、`B_wasm + (B_wasm − E_rth)` に等しい。

#### 節の鎖

`return` 節の本体に直に書いたハンドラ式の `return` 節も、`$rt_handle` が末尾で呼んで置き換えるので、同じ深さ `h` に載る。
外側の `return` 節は内側の `$rt_handle` を末尾でなく呼ぶので、外側の節のフレームは残る。
そのため `return` 節を `r` 段重ねると、深さ `h` には `go`、`r` 個の `return` 節、最後の節の呼ぶ `$rt_handle` と `rt_resume` が重なる。
分類 N の操作節も、本体の `perform` の `DISCARD(NeverBody)` で `$rt_handle` が `tail_call_never` で節を呼ぶので、同じ形で重なる。
重なりの上限は `1,040 + r × 1,536 + 176` で、`B_wasm + r × B_wasm − E_rth` に等しい。
2 つ目からの節は前の節が呼んだ `$rt_handle` の場所に載り、その `$rt_handle` は `go` の予算に入っていないので、節ごとに `B_wasm` を足す。
`r = 1` では前と同じ 2,752 である。

#### 交互の鎖

`cancel` 節は、ハンドラ式を書いた関数が末尾でなく呼んだ `$rt_handle` と同じ深さで走る。
`return` 節と N の節は、`$rt_handle` が末尾で呼んで自分を置き換えるので、やはりハンドラ式を書いた関数と同じ深さで走る。
そのため、`cancel` 節の中に N の節を持つハンドラ式を直に書き、その N の節の中に `cancel` 節を持つハンドラ式を直に書く、という交互の鎖でも、鎖の節はすべて同じ深さに重なる。
初めの版の `cancel_nest` は `cancel` 節が直に作る `cancel` 節だけを、`clause_chain` は `return` 節と N の節が直に作る同じ種類の節だけをたどり、`k` と `r` を別々に最大にした。
交互の鎖ではどちらの鎖も 1 段で切れるので、鎖の長さによらず `k = 1`、`r = 0` だった。
そこで 3 つの種類の節を 1 つのグラフにまとめ、1 本の道に沿って `k` と `r` を数えるようにした(`clause_path`)。
道の重みは `b_prog(k, r) − B_wasm` で、`cancel` 節 1 つが `B_wasm − E_rres`、`return` 節と N の節 1 つが `B_wasm` で、道に `return` 節か N の節があれば全体から `E_rth` を 1 回引く。
道の 2 つ目からの節は、前の節が末尾でなく呼んだ `$rt_handle` の上(`cancel` 節)か、その `$rt_handle` の場所(`return` 節と N の節)に載る。
どちらの場合も前の節のフレームは残るので、`cancel` 節の重なりと節の鎖の重なりの和が上限になる。

#### 形 f

形 f は、形 c の `cancel` 節の中のハンドラ式に G の節 `ask` を足し、そのハンドラ式の本体が `ask` を `perform` してから `go` を呼ぶ形である。
エフェクトは `Stop = { stop: () => Int32, ask: () => Int32 }` とし、内側のハンドラ式が `stop` と `ask` の両方を処理する。
G の節は `if m < 0 then { let t = resume(1); t } else resume(2)` で、末尾でない `resume` を持つので分類は G になり、走るのは末尾の `resume(2)` の枝である。
`keleut dump lir` で、`cancelclause` の関数 `main/go$h0.cancel` の中に `handler_new "main/Stop" [... ("main/Stop" ask G)]` があること、`tail_resume` があることを確かめた。
探りの `gen.py` の写しにモード `f` として足した(写しは scratchpad に置き、リポジトリには入れていない)。

### 計画から外れたことと、その理由

1. 計画 3.1 節は、gaps.md の形 a〜e で `k` が 1(形 b は 2)になることを試験に求めた。
   実装では形 a、b、c が 1、形 d と e が 0 になり、単体の試験もその値を確かめる。
   形 e は `cancel` 節を持たない対照で、形 d の `cancel` 節の本体は `lv(n - 1)` を呼ぶだけでハンドラ式を持たないので、D564 の `k` の定義(`cancel` 節の本体の中に関数の本体を挟まずに書いたハンドラ式の入れ子)では 0 である。
   形 b の内側の `cancel` 節つきのハンドラ式は、外側のハンドラ式の本体(種類 `handlebody` の関数)の中にある。
   本体は `$rt_handle` の手順 1 で `depth_push` の後に走る(`rustkeleut/doc/lir.md` 16.3 節)ので、内側の組は 1 つ深い段に重なり、どの段にも組は 1 つしか重ならない。
   そこで本体の中のハンドラ式は数えず、形 b は 1 とした。
   2 になる形は `n2`(`cancel` 節の中に直に書いた `cancel` 節つきのハンドラ式の `cancel` 節に、さらにハンドラ式を書く)で確かめる。
2. 単体の試験の入力に、gaps.md の形のほかに `n0`(`k = 0`)と `n2`(`k = 2`)を足した。
   1 の理由で、`k = 2` を確かめる形がほかに無いからである。
3. 計画 3.1 節は、`(L + R) × B_prog + 32 MiB` が `STACK_CAP` を超えたら `STACK_CAP` で走らせるとした。
   実装では、切るときも `k = 0` の大きさ(`(L + R) × B_wasm + 32 MiB`)より小さくはしない。
   そのまま切ると、`k = 0` のプログラムでも L が 10,991,229 以上だとスタックが 16 GiB に切られ、前は起動のときに 70 で終わった `--max-depth 100000000` の浅いプログラムが `kw` だけ 0 で終わった。
   既存の試験 `取れないスタックの深さの限度は_70_になる`(インタプリタと同じく 70 になること)がこれで落ちた。
   計画 3.1 節は `k = 0` のプログラムのスタックをいまと同じにするとし、候補 3 を `k = 0` のプログラムの起動の道が変わることを理由に退けているので、`k = 0` の振る舞いを変えない形にした。
   host の `Worker` の経路も同じ下限を使うので、host に `B_WASM` の定数を残した。
   `KELEUT_WASM_STATS` には、`STACK_CAP` で切ったときは「スタックを STACK_CAP で切った」、`k = 0` の大きさで切ったときは「スタックを k = 0 の大きさで切った」と書く。
4. 形 f の 1 段あたりのバイト数は約 1,642 で 1.73 KB を下回ったので、計画 3.1 節のとおり、形 f の `Worker` の経路の試験には直す前に落ちることを求めない。
   実際に直す前の `keleut` でも通った。
   計画 3.1 節は形 f の 1 段を約 2,896 バイトと見込んだが、この値は深さ `h` に重なるフレームの和の上限である。
   形 f の 1 つの N は 2 段で、深さ `h + 1` にはハンドラ式の本体だけが載るので、1 段あたりの平均は上限より小さくなる。
   そのため形 f の値は、式が小さすぎないこと(1 段あたりが `B_prog` 以下であること)は示すが、式が上限に近いことは示さない。
   計画が「式の確かめは形 f の値で行う」とした確かめは、この意味で弱い。
5. host の `KELEUT_WASM_STATS` の行は、`node DIR/main.mjs` だけでなく `KELEUT_WASM_STATS=1 keleut run --backend wasm` でも出る(`keleut` は環境変数を子に引き継ぐ)。
   測定用の環境変数なので、そのままにした。
6. `AGENTS.md` の `--backend wasm` の項と `kconform --pairs ki,kw` の項は、計画 3.1 節の「スタックを広げて `Worker` で走る」をそのまま書かず、既定の L では `Worker` の経路に移ると書いた。
   `k = 1` でも L = 600,000 のスタック(1,756,157 KiB)は V8 の `--stack-size` の上限より小さく、直の経路を通るからである(`wasm_cmd.rs` の形 c の試験)。
   スタックを `STACK_CAP` で切る文には、外れたことの 3 のとおり `k = 0` の大きさを下回らないことを書いた。
   全組の項には、締めの受け入れを extra なし、`--extra=--gc-stress`、`--extra=--no-yield-prune` の 3 通りで走らせることを書いた(D565)。
7. D564 の `B_prog` は `cancel` 節の重なりだけを見込み、`return` 節と種類 N の操作節の重なりを見込んでいなかった。
   形 R(測った値)は `k = 0` で `B_prog = B_wasm` になるが、1 段が最大で約 1,801 バイトになり、既定の L の内側の深さ 1,000,000 で `kw` だけが 70 になった。
   計画 3.1 節の「プログラムごとに 1 段の上限を求める」という意図に合わせ、`B_prog` に節の重なりの項を足した。
   `return` 節の予算を `cancel` 節と同じ 1,040 に下げる案は採らなかった。
   ハンドラ式を書いた関数の予算 1,040 に足すと `1,040 + 1,040 + 176 = 2,256` で、やはり `B_wasm` を超えるからである(計画 3.1 節の候補 1 と同じ算術)。
   初めの版は、`return` 節が深い再帰の道に届くかを真偽で数え、`r = 1` なら `B_wasm − E_rth` を足した。
   2 回目の検証が、この版で落ちる 2 つの形を見つけた(測った値の「節の鎖」の項目)。
   1 つは `return` 節の鎖 6 段で、`r = 1`、`B_prog = 2,752` のまま、既定の L の N = 1,000,000 で `kw` だけが 70 になった。
   もう 1 つは分類 N の操作節の鎖 6 段(G の節あり)で、`k = r = 0` のまま直の経路を通り、同じく 70 になった(直す前の `keleut` も 70)。
   初めの版の記録は、`return` 節の入れ子を測っていないと書き、N の節は測った 1 段が `B_wasm` に収まったので数えないと書いていた。
   N の節の測定は入れ子にしない形だけで、鎖には当てはまらなかった。
   そこで `r` を、`return` 節と分類 N の操作節の鎖の長さ(`clause_chain`)にした。
   1 つだけの N の節は、測った 1 段が `B_wasm` に収まったので、前と同じく数えない。
   N の節が 1 つだけのプログラムを `Worker` の経路に移さないためである。
   検証の指摘は `B_prog = B_wasm + k × (B_wasm − E_rres) + r × (B_wasm − E_rth)` を挙げたが、実装は `r ≥ 1` で `r × B_wasm − E_rth` を足す。
   鎖の 2 つ目からの節は、前の節が呼んだ予算の外の `$rt_handle` の場所に載るので、節のフレームの上限 `B_wasm` から導ける和は `B_wasm + r × B_wasm − E_rth` である(上の「節の鎖」)。
   指摘の式は `r` 段で `320 × (r − 1)` バイト小さく、測った値は下回ったが、上限としては導けない。
   `r = 1` では 2 つの式は同じ 2,752 である。
   既定の L で `k = 0` なら、`r` が 9 までは `STACK_CAP` で切らない。
   `r` の条件は、コーパスで `Worker` の経路に移るプログラムを減らすため、節から直の呼び出しの循環か値の呼び出しなどに届くことにした(測った値の 4 個)。
   `k` と `META` の `cancelNest` の意味は D564 のままで、`r` は `META` に書かない(host は `bProg` だけを使う)。
   N の節の鎖の `wasm_cmd.rs` の試験は、既定の L では `kw` で約 60 秒かかるので、`--max-depth 400000`、N = 399,000 で走らせる。
   この L でも、直す前の `keleut` は 70 になり、`r` を数えない版(`B_prog = B_wasm`)と同じスタックなので、試験は直したことを見分ける。
   計画 9 節は、`k` の求め方が鎖を見落とすおそれに「見落としが見つかったら台帳に載せる」とした。
   そこで、`return` 節と分類 N の操作節の重なりの見落とし(形 R、`return` 節の鎖、N の節の鎖)を台帳の V245 とした。
   V245: 初めの `B_prog` は `return` 節と分類 N の操作節が同じ深さに重なることを見込まず、`kw` は既定の L の内側で 70 になった(直す前の `keleut` も 70)。
   M106 で `r` の項(`b_prog` の `R(r)`)を足して直し、閉じた。
   3 回目の検証が、`cancel` 節と N の節(または `return` 節)が交互に重なる鎖を見つけた(測った値の 3 回目の検証の項目と、行ったことの「交互の鎖」)。
   2 回目の検証の後の版は、`k` を `cancel` 節だけの鎖(`cancel_nest`)、`r` を `return` 節と N の節だけの鎖(`clause_chain`)で別々に求めたので、交互の鎖では鎖の長さによらず `k = 1`、`r = 0` になった。
   `cancel` 節と N の節を交互に 4 組重ねた形は、既定の L の内側の深さ 1,000,000 で `kw` だけが 70 になった。
   2 回目の検証の後の記録は、`cancel` 節と節の鎖が混じる形を `k` と `r` の項を足し合わせて見込むが測っていない、と書いていた。
   実際には `k` と `r` を別々の鎖で数えていたので、混じる形を足し合わせてもいなかった。
   そこで 3 つの種類の節を 1 つのグラフにまとめ、1 本の道に沿って `k` と `r` を数える `clause_path` にした(行ったことの「交互の鎖」)。
   この見落としも計画 9 節の見落としなので、台帳の V246 とした。
   V246: `k` と `r` を別々の鎖で数えたので、`cancel` 節と `return` 節や N の節が交互に重なる鎖の `B_prog` が足りず、`kw` は既定の L の内側で 70 になった(直す前の `keleut` も 70)。
   M106 で `clause_path` にして直し、閉じた。
   次に空いている台帳の番号は V247 である。
   `return` 節も N の節も無い道の `k` と、`cancel` 節の無い道の `r` は、前の `cancel_nest` と `clause_chain` の値と同じである。
   コーパスの書けた 555 個の `k`、`r`、`B_prog` も変わらなかった(測った値)。

#### 印を見る場所

- 実行の役割の印は、`Rt::alloc`(`gc.rs`)の入口と、その中の 2 回の回収の後と、値スタックの `take_mem` と最初の予備の塊を取る道(`stack.rs`)で、`alloc::take_flag` の不可分の `swap(false)` で見て下ろす。
  立っていれば `Stop::OutOfMemory` を返す。
  JIT のコードの確保もいまは `Rt::alloc` を通る(JIT の中の速い道は M115 で作る)。
- 値スタックの塊は、失敗を自分で扱う範囲の外で取る。
  塊の確保が失敗すると、包みが大域の予備を返してやり直し、印を立てる。
  `take_mem` は確保の成否にかかわらず印を見て下ろし、確保が通っていれば取れた塊を次に使える塊(`armed`)にしてメモリの不足を返す。
  確保が通らなければ、値スタックの予備の塊を次に使える塊にしてメモリの不足を返す。
  これで、予備の使われ方の順は、大域の予備、大域の予備を返した後に取れた塊、値スタックの予備の塊となり、1 回のメモリの不足に印が 2 回応えることも無い。
  計画の順(大域の予備、値スタックの予備の塊)の間に、取れた塊を使う段が 1 つ入る。
- 変換の役割の印(`alloc::conv_checkpoint`)を見る場所は次のとおりである。
  - 型検査の後: `check_cmd.rs` の `run_check`(型の行を書く前)と、`emit_kir_cmd.rs` の `build`(`check_program` の直後)、`build_on_front_stack` の終わり。
  - KIR の書き出しの後: `emit_kir_cmd.rs` に足した `encode`(`keleut emit-kir` と `keleut run --frontend rust` の `write_kir`)。
  - KIR の読み込み、検証、下ろしの後: `run_cmd.rs` の `load` と `verify_and_lower`、`kir_cmd.rs` の `run`(読み込みと検証の後)、`lir_cmd.rs` の `run`(読み込み、検証、下ろしの後)。
- 翻訳の役割の印は、翻訳のスレッドが関数を翻訳した後に見る。
  入口の表を書く前に `flagged` で見て、立っていれば入口を書かずに番地 0 を結果にする。
  そのあと `take_flag` で下ろし、以後の翻訳をやめ、`alloc::reacquire` で大域の予備を取り直す。
  取れなければ予備なしで続ける。
  やめた後の待つ頼みには番地 0 を返し、`keleut-interp` の `native_target` は番地 0 を受け取った関数をインタプリタに残す(計画から外れたことの 6)。
  待たない頼み(`threshold=N`)では入口の表を書き換えないので、関数はインタプリタで続く。
  やめる前に翻訳した関数は、JIT のコードのまま走る。
  検証の指摘を受けて、翻訳の前に大域の予備が無く取り直せないときも、同じようにやめるようにした(下の「検証の指摘による直し」)。
- `keleut repl` は、各入力を読む前に予備を取り直す(計画から外れたことの 5)。

#### 試験(`crates/keleut-rt/tests/alloc_wrap.rs`)

包みを `#[global_allocator]` に宣言し、5 つの試験を置いた。
予備、印、指定はプロセスに 1 つなので、静的な錠で 1 つずつ走らせる。

1. 範囲の中の失敗(`exec:collect:hard:0` で `site(Collect)` の中の `handled` の `try_reserve`)は、失敗を返し、予備が残り、印が立たない。
2. 範囲の外の `soft` の失敗(`exec:rec_fields:soft:1`)は、2 回目の確保で予備を返して印を立て、やり直しが通る。
   印は `take_flag` で 1 回だけ応え、指定はその後の確保を失敗させず、`reacquire` で予備が戻る。
3. 役割か場所の違う確保は失敗させない。
4. 掃除の `keep` の確保が範囲の中で失敗しても(`exec:collect:hard:0`)、その場で掃除する道で続き、生き残りの語の数が合い、予備が残り、印が立たない。
5. 読めない指定は文面を返す。

#### JIT の翻訳の前の検査(D568 の 4、`crates/keleut-llvm/src/run.rs`)

- 翻訳のスレッドは、起動のときに `getrlimit` で `RLIMIT_AS` の軟らかい上限を 1 回だけ読む。
  上限が無限なら、以後の検査をしない。
- 上限が有限なら、関数ごとの翻訳の前に `/proc/self/statm` の最初の欄(ページの数)を読み、`sysconf(_SC_PAGESIZE)` を掛けて仮想の大きさにする。
  上限との差が 64 MiB(`JIT_AS_ROOM`)を下回れば、その関数を翻訳しない。
  待つ頼みには番地 0 を返し(包みの部分が `native_target` に足した、インタプリタに残す道を使う)、待たない頼みでは入口の表を書き換えない。
  どちらもその関数はインタプリタで続く。
- 翻訳しなかった後も翻訳のスレッドは止めず、次の頼みでまた調べる。
  予備を使ったとき(`gave_up`)と違い、確保は失敗しておらず、ほかの関数は残りが戻っていれば翻訳できるからである。
  翻訳しなかった関数そのものは、その実行の間インタプリタに残る(`jit-only` と `alternating` では `native_target` が番地 0 でインタプリタに残す印を付け、`threshold=N` では頼み済みの印のまま頼み直さない)。
- `/proc/self/statm` は残りが少ないときに読むので、スタックの 128 バイトの領域に読み、ヒープに確保しない。
  読めなければ今までどおり翻訳する。
- 単体の試験を `run.rs` に 3 つ置いた(`statm` の最初の欄の読み、64 MiB の境の判定、試験のプロセス自身の仮想の大きさを読めること)。
  `RLIMIT_AS` を下げる試験はプロセスの全体に効くので、単体の試験には置かず、`ulimit -v` の掃引で確かめた(測った値)。

#### 回収の中の確保(D568 の 3、`crates/keleut-rt/src/gc.rs`、`crates/keleut-lir/src/live.rs`、`ir.rs`)

- `Rt::collect` は `Result<(), Stop>` を返す形にし、本体の全体を `alloc::handled` の範囲で走らせる。
  `Rt::alloc` の回収の時機の呼び出しは、失敗を `?` でそのまま `Stop::OutOfMemory` にする。
  ヒープから取れなかった後の呼び出しは、打ち切ったときも、回収を終えても取れなかったときと同じく `Heap::exhausted` で GC のヒープの予備に切り替えてから `Stop::OutOfMemory` にする(下の時機の扱い)。
- `keleut-lir` の `Points` に `live_into(i, out, work)` を足した。
  出力先の `Vec<Reg>` と作業域 `LiveWork` を受け取り、どちらの領域も `try_reserve` で取って、取れなければ `TryReserveError` を返す。
  中の `HashMap` をやめ、差分の当て方を(レジスタ、点、足すか)の組で作業域に並べて整列し、各レジスタの最初の組を効く当て方とした。
  `i` に最も近い点の当て方が効き、同じ点では除くほうが効くので、いまの `live` と同じ集合になる。
  `live` は `live_into` を包む形にし、`keleut-llvm` の `codegen.rs` と試験はそのまま使う。
  単体の試験 `差分から集合を作り直す` で、出力先と作業域を使い回した `live_into` が `live` と同じ集合を返すことも確かめる。
- `Inst::uses` と `Term::uses` は新しい `Vec` を返すので、確保をしない `for_each_use(f)` を足し、`uses` はそれを集める形にした(被演算子の順は変えていない)。
  回収は `perform` の被演算子、`PHASE` の行の呼び出しの被演算子、末尾の形の行のブロックの終わりの被演算子を `for_each_use` で読む。
- 回収の中の確保は次のとおりで、どれも範囲の中の `try_reserve` か `try_reserve_exact` である。

  | 確保 | 後退の道 | 失敗したとき |
  | --- | --- | --- |
  | 印付けの列(`Marker::word`) | ある | 溢れの印を立てて走査し直す(いままでどおり) |
  | 掃除の `keep` と手元のページの列(`Heap::sweep`) | ある | その場で掃除する、ページをシステムへ返す(いままでどおり) |
  | `FuncRoots::new` の末尾の形の行の列と、行と `PHASE` の行の溜めの列 | ない | 印付けを打ち切る |
  | 行と `PHASE` の行のスロットの箱(`boxed`。長さちょうどの `try_reserve_exact` で取り、`into_boxed_slice` が取り直さないようにした) | ない | 印付けを打ち切る |
  | 行を作る作業域 `tmp`、生きているレジスタの出力先 `live`、`LiveWork` | ない | 印付けを打ち切る |

  作業域の 3 つは `GcState` に置いて回収のたびに使い回し、`gc::Frames` が `Work` にまとめて持つ。
  `FuncRoots` は作り終えたときだけ関数の表に入れ、行と `PHASE` の行の箱も作り終えたときだけ覚える。
  途中まで作った行を覚えると、次の回収がその行の根を見落として生きている箱を外すからである。
- 後退の道を持たない確保が失敗したら、`Marker` の `failed` を立てる。
  フレームの走査、継続の写しの走査、表の項目の走査、印付けの列を空にする繰り返し、溢れの後の走査し直しは、どれも `failed` を見て止まる。
  止まった後は、`Heap::for_each_object` で全部の箱の `MARK` を消し、3 つの表の印付け済みの項目を生きている状態に戻し、掃除をせずに `Stop::OutOfMemory` を返す。
  どちらの走査も確保をしない。
  ヒープの中身と表は回収の前と同じなので、`cancel` 節はいまのメモリの不足と同じく走る。
- 打ち切った後に `cancel` 節の確保がまた回収を起こすときの扱いは、回収の時機をずらすほうに決めた。
  打ち切ると掃除をしないので、ヒープの前の回収の後に確保した量(`since_gc`)は回収の時機を超えたままになり、`cancel` 節の最初の確保がすぐまた回収を起こす。
  回収の中の確保がまだ取れなければ、その回収もまた打ち切られて `cancel` 節がメモリの不足で止まる。
  そこで、打ち切ったときに `Heap::defer_collect` で `since_gc` を 0 にし、次の回収を前の掃除で決めた間隔(最小でも `MIN_TRIGGER_WORDS`、8 MiB)の後にずらす。
  `--gc-stress` の規則 1(初めて通る確保の場所で回収する)も、`GcState::aborted` を立てて、次に回収を終えるまで止める。
  規則 2 の回数(`allocs_since`)も 0 にする。
  回収の時機に起こした回収を打ち切ったときは、GC のヒープの 1 MiB の予備を先に使う案は採らなかった。
  打ち切りはヒープのページが尽きたことを意味せず、ヒープにはまだ空きがありうる。
  予備を先に使うと、後で本当にページが尽きたときに使える予備が無くなる。
  一方、ヒープから取れなかった後に起こした回収を打ち切ったときは、ヒープは尽きている。
  時機をずらすだけでは、`cancel` 節の最初の確保がまたヒープから取れずに回収を起こし、打ち切られる。
  そこで、この場合は、回収を終えても取れなかったときと同じく `Heap::exhausted` で予備に切り替える。
  D568 の 3 の前は、この道の回収は必ず終わって `exhausted` に届いていたので、`cancel` 節から見た振る舞いは変わらない。
  `Heap::exhausted` が予備を 1 回だけ使う、いまの形も変わらない。
  `cancel` 節がずらした間隔より多く確保すると、また回収が起こり、確保がまだ取れなければ `cancel` 節がメモリの不足で止まる(`cancel 節で例外が抑制されました: メモリ不足です`)。
  これは包みだけの構築の 370,000 KiB の点と同じ種類の残りである。
- 打ち切った回収の回数は `GcState::aborts` に数え、`KELEUT_GC_STATS=1` の行の終わりに「打ち切った回収 N」として足した。
  この行を読む試験は無い(`grep` で確かめた)。

#### 検証の指摘による直し

M108 の検証が、`cancel` 節が走らない道と、翻訳のスレッドの 134 の窓を見つけたので、次のように直した。

- 退避した状態語の表(`crates/keleut-rt/src/ctx.rs`、`gc.rs`)。
  直す前は、ヒープのメモリの不足を巻き戻す途中の `pending_box` が、表と `TableGc` の記録を広げられずに状態語を失い、`cancel` 節を走らせずに 3 で終わることがあった。
  原因は 2 つある。
  1 つは、`table_push` と `TableGc::next_index` の確保を失敗を自分で扱う範囲に入れたことで、予備が残っていても失敗が null になる。
  もう 1 つは、範囲から出しても、予備を使った確保が立てた実行の役割の印を、同じ `pending_box` の中の箱の確保(`index_box` から `Rt::alloc` の入口)が下ろしてメモリの不足を返すことである。
  そこで、表にいつも 1 個分の空きを置くことにした。
  `Rt::new` が `saved`、`TableGc` の `state` と `free` の 3 つに 1 個分の容量を範囲の中で取る(`keep_pending_spare`、`TableGc::keep_spare`)。
  メモリの不足の状態語(`Pending::Error(Stop::OutOfMemory)`)を退避するときは、空けておいた項目に置いて表を広げず、箱の確保では入口の印を見ずに下ろす(`Rt::alloc` を、入口の印の検査と、その後の `alloc_after_flag` に分けた)。
  置いた後で空きを取り直し、取れなくてもその退避は失敗にしない。
  ほかの状態語を退避するときは、置いた後の 1 個分の空きまで先に取り(`table_push` と `next_index` の `ahead`)、取れなければ置かずにメモリの不足を返す。
  これで、メモリの不足を巻き戻すときの最初の退避は表を広げない。
  巻き戻しの途中に `cancel` 節を持つハンドラが 2 つ以上あると、2 つ目からの退避は、前の退避の後に空きを取り直せたときだけ広げずに済む。
  取り直せなければ表を広げる確保が要り、それが失敗すると状態語を失う(計画から外れたことの 18)。
  ハンドラ記録と継続の表は変えていない(`ahead` は 0)。
  表を広げる確保と空きを取り直す確保は、試験用の場所 `pending`(`Site::Pending`)で行う。
- 翻訳のスレッドの予備(`crates/keleut-rt/src/alloc.rs`、`crates/keleut-llvm/src/run.rs`)。
  直す前は、実行の役割が大域の予備を使った後に翻訳のスレッドの Rust の確保が失敗すると、包みは予備が無いので null を返し、プロセスは 134 で止まった。
  `threshold=N` では `cancel` 節が走る間も翻訳が続くので、`cancel` 節と 3 の代わりに 134 になる。
  逆の順(翻訳の役割が予備を使い、取り直す前に実行の確保が失敗する)でも 134 になった(測った値)。
  そこで、包みの失敗の道で、翻訳の役割は予備が無ければ `reacquire` で新しく取ってから返してやり直し、やり直しの後には通ったかどうかによらずすぐ `reacquire` で取り直すようにした。
  `reacquire` は `mmap` を呼ぶだけで Rust の確保をしないので、包みの中で呼べる。
  翻訳のスレッドは、関数ごとの翻訳の前にも予備があるかを見て、無ければ取り直し、取れなければ印が立ったときと同じく以後の翻訳をやめる。
- `keleut repl` の実行の役割の印(`crates/keleut-cli/src/repl_cmd.rs`)。
  直す前は、ヒープの確保の入口を通らない確保(`call_args` など)が予備を使って印を立てても、その入力の中で `Rt::alloc` も塊の確保も起きなければ、印は残ったままだった。
  `exec:call_args:soft:0` では、失敗はプレリュードの後、1 つ目の入力の実行の前に起きる。
  入力 `1` だけなら失敗は報されずに 0 で終わり、`let a = 1`、`let a2 = 2` と続けると、関わりの無い後の入力がメモリの不足になって束縛を失った。
  後の入力が関数を定義すると、`Rt::grow` の箱の確保が残った印を見てメモリの不足を返し、セッションは 70 で終わった。
  そこで、`run_job` は単位を下ろした後、表を伸ばす前に印を下ろし、立っていればその入力を実行せずにメモリの不足の実行時エラーにする(プレリュードなら 3 で終わる)。
  `exec` は、初期化の関数を呼び終えた後と束縛を表示し終えた後にも印を見て、立っていればメモリの不足を返す。
  ほかの停止で終わった入力の後に残った印は、その入力とともに下ろす。
  これで、印はメモリの不足 1 回に 1 度だけ答え、表を伸ばす確保が残った印で止まることは無い。
  `tests/oom_cmd.rs` に、この形の例を足した(`repl_で予備を使った入力だけがメモリの不足になり次の入力は続く`。直す前の構築では 70 で落ちる)。
- 試験。
  `tests/oom_cmd.rs` に、`exec:pending:hard:0` の 2 つの例(`PEND`、両方の段)と、`jit:jit:soft:200,exec:call_args:soft:0` の例(`slow_cancel`、`--tier threshold=1`)を足した。
  `threshold=1` の例は、試験の行の順が翻訳のスレッドの進み方で変わりうるので、2 つの試験の行を含むことと、標準エラーが 3 行でメモリの不足で終わることを確かめる。
  `exec:chunk:hard:2` の例は、`cancel` 節が値スタックの予備の塊を使わずに 1 つ目の塊の中で走っていた(測った値)。
  `cancel` 節で末尾でない再帰を 16,000 段続ける形(`deep_spare`)にし、試験の名前を「値のスタックの塊がすべて失敗しても予備の塊で `cancel` 節が走る」に改めた。
  `crates/keleut-rt/tests/alloc_wrap.rs` に、実行の役割が予備を使った後の翻訳の役割の `soft` の失敗が、予備を取り直してやり直し、翻訳の役割の印を立て、やり直しの後に予備を戻すことを確かめる試験を足した(6 つになった)。
- rustdoc と `AGENTS.md`。
  `LOOP` の説明(`rec_fields` は起こらない)、`Site::Kir`(KIR の書き出しを含む)、`alloc` のモジュールの説明の表(実行の役割は回収の後にも印を見る)、`Translator::request`(番地 0 を返す 2 つの場合)、`ValueStack::take_mem`(取れなければ印の有無によらず予備の塊を次に使える塊にする)を、コードに合わせて正した。

### 計画から外れたことと、その理由

1. KIR の処理のスレッド(crate `kir` と `keleut-lir` の `on_stack`)には役割を書いていない。
   2 つの crate は `keleut-rt` に依らず(`keleut-rt` が `keleut-lir` に依る)、スレッドを作る閉包もその crate の中で作るので、作った直後に書けないからである。
   そこで、役割を書かないスレッドの既定の値を変換の役割にし、主のスレッドは `alloc::init` でそのほかの役割にした。
   同じ理由で、KIR の処理のスレッドでは場所もスレッド局所の値で書けない。
   主のスレッドが KIR の処理を呼ぶ間に書くプロセスの場所(`alloc::conv_site`)を足し、変換の役割のスレッドがスレッド局所の場所を持たないときに使う。
   変換の役割のスレッドは主のスレッドが `join` で待つ間だけ走るので、プロセスに 1 つの場所で足りる。
2. KIR の書き出し(`write_kir`)も KIR の処理のスレッドで走るので、場所を `kir` にした。
   計画の `kir` の説明は「KIR の読み込み、検証、下ろし」である。
3. 試験の行は、指定ごとに最初に失敗させたときだけ書く。
   `hard` は失敗させる確保がいくつも続くので、失敗のたびに書くと行の数が確保の数で変わるからである。
4. 入力の種類は、プロセスの起動のときでなく、各コマンドが入力を決めたときに書いた。
   `keleut run`、`keleut build`、`keleut dump bytecode|llvm` は `run_cmd::load` の頭で `.kir` か `.kel` かを書き、`keleut check` と `keleut emit-kir` は `.kel`、`keleut kir verify|dis|asm` と `keleut dump lir` は `.kir` を書く。
   `.kel` か `.kir` かは `run_cmd::load` の `--source-only` の扱いを見ないと決まらず、`main.rs` で同じ判断を繰り返さないためである。
   どれも変換の役割の確保より前に書く。
   `keleut repl` と `keleut dump tokens|ast` は書かないので、変換の役割の終え方を通らない。
   `dump tokens|ast` は出力を流しながら書くので、途中で限度の行に替えると出力が途切れるからである。
   `compat-diktor` は振り分けた先のコマンドの関数が書く。
5. `keleut repl` は、実行時エラーの後だけでなく、各入力を読む前に予備を取り直す(すでにあれば何もしない)。
   予備を使ったのが実行時エラーで止まった入力か、メモリの不足にならずに終わった入力かで分けなくてよく、取り直す処理は予備があれば 1 回の読みで終わるからである。
6. 計画は翻訳をやめたときの実行のスレッドへの知らせ方を決めていない。
   いまの `native_target` は、待つ頼みに番地が返らないと内部の誤りにする。
   そこで、翻訳のスレッドは番地 0 を返し、`native_target` は番地 0 を受け取った関数をインタプリタに残すようにした(`keleut-interp` の `native.rs` の 5 行)。
   印は入口の表を書く前に見るので、LLJIT に足した関数のコードは使われずに残る。
7. 包みだけの構築で、`sweep_interp.sh` の 360,000 KiB の点は、`cancel` 節を走らせずに 3 で終わった(測った値)。
   M108 の全部を入れた構築でも、370,000 KiB の 2 回が同じく `before` だけで 3 だった。
   直す前の構築は同じ点で 134 だった。
   前の版のこの項は、原因を「包みも D568 の 3 も扱わない」と書いたが、誤りだった。
   検証が gdb でたどると、原因は D568 の作り方の 2 点にあった。
   1 つは、`table_push` と `TableGc::next_index` の確保を失敗を自分で扱う範囲に入れたことで、予備が残っていても、表を広げる確保の失敗は予備を使わずに null になる。
   もう 1 つは、範囲から出しても、予備を使った確保が立てた実行の役割の印を、同じ `pending_box` の中の箱の確保(`index_box` から `Rt::alloc` の入口)が下ろし、メモリの不足を返すことである。
   §15.5 は `cancel` 節を走らせることを求めるので、これを台帳の V247 とした。
   V247: ヒープのメモリの不足を巻き戻す途中の状態語の退避(`Rt::pending_box` の `TableGc::next_index`)が失敗しうるので、`cancel` 節を走らせずに 3 で終わった(包みだけの構築の 360,000 KiB、M108 の全部を入れた構築の 370,000 KiB の各 2 回。直す前の `keleut` はどちらの点も 134)。
   M108 の全部を入れた構築の 370,000 KiB の点は gdb でたどっていないが、直した後は `before` と `cancel` の 2 行になった(測った値)。
   M108 で、表にいつも 1 個分の空きを置き、メモリの不足の状態語の退避では表を広げず印も見ないようにして直し、閉じた(行ったことの「検証の指摘による直し」)。
   次に空いている台帳の番号は V248 である。
8. `Rt::alloc` は、入口に加えて、中の回収の後にも実行の役割の印を見る。
   回収の中の確保が予備を使ったときに、その確保の結果を待たずにメモリの不足にするためである。
9. 計画は範囲に入れる確保を挙げるが、いまの `try_reserve` の呼び手 15 か所のうち `heap.rs:265`、`:291`、`:294`、`:365`、`gc.rs:141`、`:145`、`ctx.rs:726`、`interp.rs:1603` と、大きな箱の確保は挙げていない。
   どれも失敗をすぐメモリの不足にするので、計画の範囲の規則に当たるとして入れた。
   範囲に入れないと、これらの失敗が大域の予備を使い、後の印が `cancel` 節の最初の確保を打ち切りうる。
10. `chunk` の場所は値スタックの予備の塊も数える。
    最初の `place` が予備の塊と最初の塊の 2 回を確保するので、`chunk` の `SKIP` は 0 が予備の塊、1 が最初の塊、2 が 2 つ目の塊である。
11. 計画 4.2 節は、翻訳の役割が予備を使ったら、その関数の翻訳を捨てて翻訳をやめた後に予備を取り直すとした。
    検証の指摘による直しでは、これに加えて、包みの失敗の道で翻訳の役割がやり直しのすぐ後に予備を取り直し、予備が無ければ先に新しく取ってからやり直すようにした。
    翻訳の後に取り直すだけでは、翻訳の間に実行の役割が予備なしで失敗する窓と、実行の役割が予備を使った後に翻訳の確保が失敗する窓が残り、どちらも 134 になったからである(測った値)。
    残る 134 の窓は 3 つある。
    LLVM の中の確保の失敗、新しい 8 MiB の写像も取れないときの翻訳のスレッドの Rust の確保の失敗(範囲の外の `Points::live` の `handle_alloc_error` を含む)、翻訳の役割が予備を返してからやり直しの後に取り直すまでの間の実行の確保の失敗である。
    3 つ目の間は 1 回の確保のやり直しの長さで、測った掃引と試験用の失敗では現れなかった。
    同じ長さの窓がもう 1 つある。
    予備が無いときに翻訳の役割が `reacquire` で取った写像を、`release_reserve` で返す前に実行の役割の失敗が先に使うと、翻訳の役割は予備を得られずに null を受け取り、134 になる。
    翻訳のスレッドを止めて待たせる案は、`jit-only` と `alternating` のミューテータが翻訳の返事を待って止まりうるので採らなかった。
12. JIT の翻訳の前の検査(D568 の 4)について、計画が決めていない 2 点を次のように決めた。
    残りが足りずに翻訳しなかった後も、翻訳のスレッドを止めずに次の頼みでまた調べる(行ったこと)。
    翻訳のスレッドの起動(LLJIT とスタブの翻訳)の前には調べない。
    起動はプログラムが走り始める前か直後で、仮想の大きさが最も小さいときであり、起動を省くと `threshold=N` の起動を待つ道も変えることになるからである。
13. D568 の 3 の部分で、計画が挙げていない `keleut-lir` の `ir.rs` を変えた(`Inst` と `Term` の `for_each_use`)。
    回収は行の根を作るときに `perform` と呼び出しの被演算子を `uses` で読んでいたが、`uses` は失敗を返さない `Vec` を作るので、範囲の中で取れないと 134 で止まるからである。
    `uses` は `for_each_use` で集める形にし、返す列は変えていない。
14. 計画は打ち切った後の回収の扱いを 2 つの案(回収の時機をずらす、GC のヒープの 1 MiB の予備を先に使う)から M108 で決めるとした。
    時機をずらすほうに決め、`--gc-stress` の規則 1 も次に回収を終えるまで止めた(行ったこと)。
    計画は `--gc-stress` の扱いを書いていないが、規則 1 は `cancel` 節の中の初めて通る確保の場所ごとに回収を起こし、ずらした時機を無にするからである。
15. `soft` の `collect` の例の `SKIP` を 6 にした。
    計画 4.2 節は、`soft` の `collect` の例が D568 の 3 の前は予備の道で 3 になると見ていたが、包みの部分で回収の中の確保を最初から失敗を自分で扱う範囲に入れたので、`SKIP` 0〜5 は後退の道を持つ確保に当たって 0 で終わる(測った値)。
    計画のとおり `soft` の `collect` の例は D568 の 3 を入れたかどうかを見分けないので、印付けを打ち切る確保に当たる `SKIP` を選び、標準エラーの試験の行で当たりを確かめる形にした。
    確保の数が変わると当たる確保が動くので、この例が 0 で落ちたら `SKIP` を選び直す。
16. `exec:collect:hard:0` が D568 の 3 の前の構築で 134 になることは、本部分では走らせ直していない。
    D568 の 3 の部分が、その前の構築(scratchpad の `work/gc/keleut-before3`)で `c1.kel` と `t1.kel` の両方の段について確かめている(測った値)。
    `oom_cmd.rs` の例は `cancel` 節を軽くした `LOOP` で、`c1.kel` と同じく `cancel` 節は `cancel` を書くだけである。
17. 前の版の締めの受け入れの `bench/run.py` の比べは、計画の条件(負荷の平均 1 以下)から外れて判断した。
    1 回目と 2 回目はどちらも 17 のベンチマークのすべてを、1 分の負荷の平均が 1 以下のときに始めたので、計画の条件を満たしていた。

18. 退避した状態語の表に置く空きは 1 個で、メモリの不足の巻き戻しの途中の最初の退避だけが表を広げないことを確かめられる(行ったことの「検証の指摘による直し」)。

    巻き戻しの途中の 2 つ目からの退避は、前の退避の後に空きを取り直せなかったときだけ表を広げる確保に当たる。
