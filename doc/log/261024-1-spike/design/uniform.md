# RustKeleut の設計案(観点: 意味の一様性と移植性を先に置く)

- 日付: 2026-10-24
- 決定: 仕様の所有者は、Keleut の主な実装を Diktor と別に Rust で作ると決めた。
  名前は RustKeleut、コマンドは `keleut` である。
  理由は、Keleut が GC 言語で GC を減らす仕組みが少なく、コンパイラ自身を GC の無い言語で書くほうがコンパイルの速さで有利だからである。
  所有者は、Diktor と RustKeleut の両方が扱う中間言語(IR)とそのバイナリ表現、WasmGC とバイトコードインタプリタと LLVM(ORCv2)の 3 つのバックエンド、インタプリタと LLVM のコードの相互の飛び移り、Node.js で動く WasmGC を求め、判断事項には推奨案を置いて計画をそのまま実行できる形にするよう求めた。
- 対象: 親リポジトリ `keleut`(ブランチ `ja/bleeding`、HEAD bcb16f1)と、サブモジュール `diktor`(HEAD 6e49bbb)。
  仕様は `doc/LangSpec.md`(2316 行)である。
- 前提(実測): rustc 1.98.1、LLVM 22.1.8(共有ライブラリ)、llvm-sys 221.1.1 で LLJIT が動く。
  Node 26.9.0(V8 14.6)は WasmGC、`return_call`、exnref、JSPI をフラグなしで動かし、WasmFX はフラグが要り一部で落ちる。
  試作は `doc/log/261024-1-spike/llvm` と `doc/log/261024-1-spike/wasm` にある。
- 観点: 3 つのバックエンドが LangSpec §18 の意味での評価の結果(標準出力のバイト列と終わり方)を同じにすることを最優先にする。
  そのために、バックエンドの差をできるだけ小さくし、意味を決める処理を 1 か所の共有の下ろし(lowering)に集める。
  IR は Diktor が無理なく出力し解釈できる形に保つ。
- 番号: 裁定は D499 から、台帳は V191 から、マイルストーンは M79 から、所有者への問いは P232 から使う。
- 読み方: 
  - 本書の節は「本書 6.6 節」と書く。`§` を付けた番号は `doc/LangSpec.md` の節である。
  - 調査報告は次の略称で引く。
    `tree`(diktor-tree.md)、`fid`(spec-fidelity.md)、`fx`(effects-impl.md)、`sl`(spike-llvm.md)、`sw`(spike-wasm.md)、`fp`(frontend-port.md)、`tg`(tiering-gc.md)。
    たとえば「fx §6.0」は effects-impl.md の 6.0 節である。
  - 【実測】は報告か本書の作成で測った事実、【推論】は判断である。

## 0. 要約

1. Diktor と RustKeleut が共有する IR を **KIR**(Keleut Intermediate Representation)とする。
   KIR は精緻化の後、クロージャ変換と辞書渡しを明示した木の形の IR で、型は表現の種類(Rep)だけを持つ。
   バイナリ(`.kir`)とテキスト(`.kirt`)の 2 つの形を持ち、仕様は `doc/IRSpec.md` に置く。
2. RustKeleut は KIR を読んで検証し、**共有の下ろし**で内部の低水準 IR(**LIR**)に変える。
   評価順序、数値の検査、パターンの照合、レコードの形、初期化の検査、エフェクトの規約、論理的なスタックの深さは、すべて LIR の命令として明示する。
   3 つのバックエンドは LIR を機械的に訳すだけにする。
3. エフェクトは、節を静的に N(再開しない操作)、T(末尾 resume だけ)、G(それ以外)に分ける(fx §6.0)。
   全バックエンドで、制御の脱出(継続の破棄、実行時エラー)と継続の取り出し(G)を、1 つの**状態語の伝播**で実装する。
   ネイティブの例外(LLVM の landingpad、Wasm の exnref)と、ネイティブのスタック切り替え(fiber、WasmFX、JSPI)は v1 で使わない。
4. G の継続は **yield bubbling** で、フレームを `(関数 id、再開点、スロットの写し)` のヒープの記録として取り出す。
   この記録は段(インタプリタと JIT)に依らないので、どちらの段が取り出したフレームもどちらの段でも再開できる。
5. スタックの限度は**論理的な深さ**(非末尾の呼び出しの入れ子の数)で決め、既定を 1,000,000 とする。
   全バックエンドが同じ位置で限度に達し、同じ順序で `cancel` 節を走らせ、終了状態 3 で終わる。
6. 浮動小数の文字列化、`sin cos exp log`、文字列の比較などの実行時の核は、Rust の 1 つの crate(`keleut-rt-core`)に書く。
   ネイティブにも wasm32 にもコンパイルし、WasmGC のプログラムから別モジュールとして呼ぶ。
7. Diktor は KIR の書き出し(`--emit-ir`)と、KIR の参照インタプリタ(`--run-ir`)を持つ。
   Rust のフロントエンドは、バックエンドが Diktor の KIR で適合した後に移植し、Diktor と同じ KIR を出すことで検証する。

## 1. 裁定(D499 から)

本文に現れる順に番号を振った。各裁定の根拠と代案は、括弧の中の節に書く。

- **D499(観点)**: 設計の判断が割れるときは、バックエンドの間の意味の一致を速さより先に置く。
  速さのための最適化は、LIR の段で全バックエンドに等しく効くものから入れる(本書 0 節)。
- **D500(IR の層)**: Diktor と RustKeleut の間の交換形式は KIR だけとする。
  LIR は RustKeleut の内部の形で、互換性を約束しない。
  バイトコードは LIR の符号化であり、KIR のバイナリとは別物である(本書 2 節、6.7 節)。
- **D501(KIR の水準)**: KIR は精緻化の後の、脱糖を済ませた木である。
  局所変数はスロット、自由変数は明示の捕獲の列、辞書は明示の式、演算子はメソッドの呼び出し、`run` は消去する。
  ANF にはしない。
  子の評価順序は、符号化に現れる順とする(本書 3.1 節、3.5 節)。
- **D502(型)**: KIR が持つ型は、束縛と関数の署名の Rep(`bool i32 i64 f64 str any`)と、関数型のエフェクト行の要約の 1 ビットだけとする。
  完全な型は任意の Debug 節に文字列で置く(本書 3.2 節)。
- **D503(安定な名前)**: 大域の実体は `単位の鍵/修飾名#n` の記号で名指す。
  単位の鍵は、プレリュードが `prelude`、利用者のファイルが起点の所在からの相対パスである(本書 3.3 節)。
- **D504(プログラムの単位)**: `.kir` の 1 ファイルは、プレリュードを含む全単位を初期化の順に並べた自己完結のプログラムとする。
  単位ごとの節を持つので、分割コンパイルへ後で広げられる(本書 3.4 節)。
- **D505(パターン)**: パターンは、節の順とガードを保った `match` のまま KIR に置く。
  決定木は LIR の段で作る(本書 3.9 節)。
- **D506(末尾の印)**: 末尾呼び出しと末尾 resume の印を KIR に書き、検証器が §5.7 の規則で再計算して一致を確かめる(本書 3.10 節)。
- **D507(節の分類)**: 操作節ごとに N、T、G の分類を KIR に書き、検証器が再計算して確かめる(本書 3.11 節)。
- **D508(脱出の規約)**: 継続の破棄、実行時エラー、継続の取り出しを、全バックエンドで同じ状態語の伝播で実装する。
  ネイティブの例外機構は v1 で使わない(本書 6.6 節)。
- **D509(G の継続)**: G の継続は yield bubbling で取り出し、段に依らないフレームの記録で持つ。
  tg の推奨のネイティブ fiber は採らず、測定で必要になったときの LLVM だけの最適化として残す(本書 6.6 節、P238)。
- **D510(ハンドラの実行時の部品)**: ハンドラの起動と再開の論理は、`keleut-lir` が LIR で組み立てる共有の組み込み関数 `rt_handle` と `rt_resume` にする。
  これらは KIR の外にあり、Diktor の参照インタプリタには要らない。
  取り出した継続の破棄は、保留中の状態を注入した再開として実装する(本書 6.6 節)。
- **D511(入れ子の resume)**: `resume(e)` は、引数を評価してから再開済みかを調べる。
  Diktor の短い経路(fx R1 の測定)をこれに合わせる(本書 4 節、P235)。
- **D512(論理的な深さ)**: 評価に要する領域の限度は、論理的な深さで決める。
  既定は 1,000,000 で、`--max-depth` で変えられる。
  Diktor の `--run-ir` も同じ数え方をする(本書 3.13 節、P234)。
- **D513(浮動小数のパターン)**: `Float64` のリテラルパターンは IEEE の `==` で照合する(本書 4 節、P236)。
- **D514(使うたびに評価する値)**: 辞書を受け取る値束縛は、KIR の意味では使うたびに評価する。
  実装は、観測できない場合に限って結果を覚えてよい(本書 4 節)。
- **D515(実行時の核)**: 浮動小数の文字列化、libm、文字列の操作、レコードの形の表を `keleut-rt-core` に 1 回だけ書き、ネイティブと wasm32 の両方で使う(本書 6.5 節、P239)。
- **D516(値の表現)**: ネイティブの一様な語は 64 ビットで、最下位ビットが 1 なら即値、0 ならポインタとする。
  Int64 と Float64 は一様な位置でだけ箱に入れる(本書 6.5 節)。
- **D517(GC)**: v1 の GC は動かさないマークスイープで、根は共有の値スタックと実行時の表からだけ得る。
  LLVM のステートポイントは使わない(本書 6.5 節)。
- **D518(呼び出し規約)**: JIT の全関数を `tailcc i64 @f(ptr %ctx)` の 1 つの型にし、引数とスロットは ctx が指す値スタックに置く。
  境目のスタブは起動時に作る LLVM のモジュールに置く(本書 6.8 節)。
- **D519(段の切り替え)**: 段の切り替えは関数単位で、呼び出し回数を数え、入口の表の 1 語を書き換える。
  OSR と逆最適化は作らない(本書 6.9 節)。
- **D520(WasmGC の制御)**: WasmGC でも状態語の伝播を使い、exnref を制御に使わない。
  関数本体の制御は非巡回なので、構造化した `block` と前向きの `br` で出し、再開は入口の `br_table` で行う(本書 6.10 節)。
- **D521(Node の実行)**: 出力は線形メモリのバッファを経て `fs.writeSync(1, …)` で書く。
  Node は子プロセスで起動し、RLIMIT_STACK と `--stack-size` で論理的な深さの限度に足るスタックを与える(本書 6.10 節、P245)。
- **D522(Diktor の役割)**: Diktor は KIR の書き出しと、KIR の参照インタプリタを持つ(本書 5 節)。
- **D523(フロントエンドの移植)**: Rust のフロントエンドは M90 から移植し、手書きの再帰下降で構文解析を書く。
  検証の基準は、正規化した KIR のテキストが Diktor の出力と一致することである(本書 7 節)。
- **D524(CLI と終了状態)**: `keleut` はサブコマンドの形とし、終了状態は Diktor の 0/1/2/3/4/64/74 に合わせ、内部エラーを 70 とする(本書 6.2 節、P244)。
- **D525(差分試験)**: 適合試験は、Diktor を基準にした差分試験の実行器 `kconform` で行い、段とバックエンドの組を総当たりで比べる(本書 8 節)。
- **D526(yield の刈り込み)**: エフェクト行が閉じていて利用者が処理できるエフェクトを含まない呼び出しでは、再開点を作らない。
  判定は LIR の段で行い、全バックエンドに同じに効く。
  検査用に `--no-yield-prune` を持つ(本書 6.4 節)。
- **D527(外部関数)**: `extern "C"` の 5 関数は、全バックエンドで Rust の `libm` crate の実装を使う。
  Diktor(glibc)との最下位ビットの差は既知の差として扱う(本書 4 節、P237)。
- **D528(版の方針)**: KIR の版は 1.0 までは `0.y` で、読み手は同じ `0.y` だけを受け付ける(本書 3.16 節、P241)。
- **D529(仕様の置き場所)**: KIR の仕様は親の `doc/IRSpec.md` に置く。
  RustKeleut が使う組み込みの KIR ライブラリ(`Array.each` と `pinned`)は `rustkeleut/lib/rt.kirt` に置く(本書 3.17 節)。
- **D530(REPL)**: RustKeleut の対話的な実行は本計画の範囲の外に置く(本書 9 節、P242)。
- **D531(文書の記述)**: 「セルフホストのブートストラップ」の記述を、「Diktor は参照実装でテストの基準、主な実装は RustKeleut」に改める。
  過去の `doc/log` は書き換えない(本書 9 節 M79、P233)。
- **D532(置き場所)**: RustKeleut は親リポジトリの `rustkeleut/` に cargo の workspace として置く。サブモジュールにしない(本書 6.1 節、P232)。
- **D533(利用者の関数を呼ぶ組み込み)**: `Array.each` と `pinned` は、RustKeleut では `rt.kirt` に KIR で書く(本書 3.12 節)。
- **D534(Console)**: `Console.write` は実行時の直接の呼び出しにし、標準出力をバッファする。
  標準エラーへ書く前と終了の前に flush し、書き込みの失敗は実行時エラーと同じ巻き戻しを経て終了状態 74 にする(本書 6.5 節)。
- **D535(初期化の検査)**: 大域の実体は初期化済みの印を持ち、読むたびに検査する。
  参照を含む最も外側のトップレベルの実体の初期化の手順が後にあるときだけ、静的に検査を省く(本書 6.4 節)。

## 2. 全体の構成

```
              Diktor (OCaml)                         RustKeleut (Rust)
 .kel ─ lexer/parser/elab ─┐                .kel ─ keleut-front (M90〜M92) ─┐
                           ▼                                                ▼
                    KIR writer ── prog.kir / prog.kirt ──► kir: 読み込み + 検証
                           │                                                │
               KIR 参照インタプリタ                     keleut-lir: 共有の下ろし(KIR → LIR)
              (diktor --run-ir)                      意味を決める処理はすべてここ
                                                        │            │             │
                                              bytecode + interp   LLVM ORCv2    WasmGC(+ rt.wasm)
                                                        └─ 段の切り替え ─┘         Node.js
                                                  keleut-rt(GC、値スタック、ハンドラ記録)
                                                  keleut-rt-core(float show、libm、文字列、形の表)
```

- 交換するのは KIR だけである(D500)。
  KIR を Diktor に近い高さに置き、意味の細部の決定(パターンの照合の手順、レコードの配置、数値の検査、エフェクトの規約)を LIR へ下ろす処理を RustKeleut の 1 か所にまとめる。
  こうすると、Diktor は木をほぼ 1 対 1 に写すだけで済み(tree §1.4)、3 つのバックエンドは同じ LIR を訳すだけになる。
- 代案 A: KIR を LIR の水準まで下げ、Diktor がエフェクトの下ろしまで行う。
  Diktor の書き出しが重くなり(tree §5.2 の見積もりの 2 倍を超える)、Diktor の参照インタプリタが OCaml のエフェクトを使えなくなるので採らない。
- 代案 B: バックエンドごとに KIR から直接下ろす。
  fid §15 の表の「重い項目」をバックエンドの数だけ書くことになり、差が生じやすいので採らない。

## 3. KIR の設計

### 3.1 名前と水準

- 名前は KIR、拡張子はバイナリが `.kir`、テキストが `.kirt` である。
- 水準は精緻化の後で、次のものを済ませた形である(D501)。
  - 構文の脱糖(`if`、タプル、`with`、末尾ブロック。tree §1.1 の後半)
  - 名前の解決(大域は記号、局所はスロット)
  - クロージャ変換(関数ごとの捕獲の列)
  - 辞書渡しの明示(証拠の平坦化、インスタンスの頭の解決、メソッドの辞書の位置。tree §2、§3)
  - 数値リテラルの確定(値か「評価したら実行時エラー」の命令。§4.2、fid §1)
  - 末尾呼び出し、末尾 resume、節の分類の印
  - module の平坦化(Diktor の elab §11.42 の結果をそのまま使う)
  - `run` の消去と、`BinOp` と `Neg` のメソッド呼び出しへの書き換え(tree §1.4)
- 木のままにする理由: Diktor の `Tree` を再帰でたどる書き出しがそのまま書け、Diktor の参照インタプリタは現在の `interp.ml` の構造を流用できる。
  評価順序は「子を符号化に現れる順に評価する」の 1 規則で決まる。
  ソースの順と格納の順が違うもの(名前付きのコンストラクタ引数。§5.1、fid §4)は、子に格納先の番号を添えて、評価の順に並べる。
- 代案: ANF。
  評価順序が名前の束縛で明示される利点はあるが、Diktor の書き出しに正規化の段が増え、`match` と `handle` の値を受ける合流の表現が要る。
  ANF は LIR の段で作れば足りるので、KIR では採らない。

### 3.2 型の扱い

- Rep は `bool`、`i32`、`i64`、`f64`、`str`、`any` の 6 種である(D502)。
  `any` は一様な表現(多相の型パラメータ、レコード、データ、ヴァリアント、クロージャ、辞書、参照、配列、Unit)である。
- Rep を付ける場所は、局所の束縛(let、パラメータ、パターンの変数)、関数の結果、大域の実体である。
  Diktor の書き出しは、ノードの `ty_field` を `repr` した結果の `TCon` の頭が Int32、Int64、Float64、Boolean、String なら対応する Rep を、それ以外(`Generic` を含む)なら `any` を書く(tree §3 の「ノードごとの型」)。
- 関数の型のエフェクト行の要約として、呼び出しと関数に `may_yield` の 1 ビットを付ける。
  行が閉じていて、要素が `Console`、`Heap`、`Blocking` だけなら 0、そうでなければ 1 である(fx §6.4 の短所の項)。
  この印は最適化(D526)にだけ使い、意味を変えない。
  印が誤っていて yield が再開点のないフレームに届いたときは、実行時が内部エラー(終了状態 70)として検出する。
- 完全な型(行、行変数、型パラメータ)は、任意の Debug 節に Diktor の `Show` の文面で置く。
  検証器は使わない。
- 根拠: tg §2.2 は、箱なしの数値と WasmGC の型付けに Rep が要ると結論した。
  一方、完全な型を IR に置くと、検証器が行多相とスコープ付きラベルの型検査を再実装することになる(fp §1.3 の規模)。
  Rep は Diktor の `repr` を 1 回呼ぶだけで書け、検証器はプリミティブの演算の型を Rep で検査できる。
- 代案: 型なしの KIR。
  関数の結果の Rep が分からず、箱なしの数値を LIR で推論できないので採らない。

### 3.3 安定な名前

- Diktor の同一性(`Type.intern` の oid、束縛ノードの oid、`h_id`、ハンドラの起動ごとの `inst`)はプロセスの中でしか通用しない(tree §0 の 4)。
  KIR は独自の名前を持つ(D503)。
- 記号の形は `単位の鍵/修飾名` で、同じ単位で同名の大域を再束縛したときは 2 つ目から `#1`、`#2` を付ける(§6.1 の再束縛は別の実体である)。
  単位の鍵は、プレリュードが `prelude`、組み込みが `builtin`、利用者のファイルが起点のディレクトリからの相対パス(区切りは `/`)である。
  Diktor の `%N.` の印(tree §6.2)は単位の番号から鍵へ写す。
- 型、コンストラクタ、エフェクト、操作、クラス、メソッド、インスタンスも記号を持つ。
  インスタンスの記号は `単位の鍵/instance:クラス[頭]#n` とする。
- レコードとヴァリアントのラベル、操作の短い名前は、文字列表の添字である。
- 記号はリンクと診断にだけ使い、実行時の意味に使わない(§18.1)。

### 3.4 プログラムの構成と初期化

- `.kir` の 1 ファイルは、単位を初期化の順(§15.4 の帰りがけ順、起点が最後)に並べた自己完結のプログラムである(D504)。
  先頭はプレリュードの単位である。
- 単位ごとに、宣言の表(型、エフェクト、クラス、インスタンス、大域)と、初期化の手順の列を持つ。
  初期化の手順は次の 5 種である(tree §1.3、§6.3)。

  | 手順 | 意味 |
  |---|---|
  | `def_value g f` | 0 引数の関数 `f` を評価し、結果を `g` に置いて初期化済みにする |
  | `def_fns [g…]` | 関数の大域(let rec の群を含む)を初期化済みにする |
  | `def_dictabs g` | 辞書を受け取る値束縛を初期化済みにする(評価はしない。§6.4) |
  | `def_instance i` | インスタンスを初期化済みにし、前提もメソッドの制約も持たない値束縛のメソッドを宣言の順に 1 回だけ評価する(fid §8 の inst2) |
  | `run_exp f` | 式文を評価する。辞書を受け取る式文は書き出さない(§6.4) |

- 大域の実体の種類は `fn`、`value`、`dictabs`、`extern`、`builtin` の 5 つである。
  どれも初期化済みの印を持ち、初期化の前に読むと実行時エラー(未束縛の変数)になる(fid §10 の fwd.kel)。
  インスタンスも印を持ち、宣言の前に選ぶと実行時エラーになる(fid §8 の inst.kel)。
- 代案: プレリュードを別の `.kir` にして RustKeleut に埋め込む。
  Rust のフロントエンドができるまでは Diktor が必ず KIR を作るので、毎回プレリュードを含めれば埋め込みは要らない。
  埋め込みの版ずれの危険を避けるために採らない。

### 3.5 式

式の種類と、子の評価の順を示す。
「末尾」の欄は `tail` の印を持てる式である。

| 式 | 子の評価の順と意味 | 末尾 |
|---|---|---|
| `lit(bool\|i32\|i64\|f64\|str)` | 定数。`str` はバイト列表の添字 | |
| `lit_error(kind, text)` | 評価したら実行時エラー(範囲外の数値リテラル。§4.2) | |
| `local(s)` / `env(i)` / `dparam(i)` | スロット、捕獲、辞書パラメータを読む | |
| `global(g)` | 大域を読む。初期化済みでなければ実行時エラー | |
| `dictapp(e, [d…])` | `e`、辞書を左から。辞書を受け取る値を評価する(3.7 節) | |
| `ctor0(T, c)` | 引数のないコンストラクタ | |
| `construct(T, c, [(field, e)…])` | `e` を並びの順(ソースの順)に評価し、`field` の位置に格納する | |
| `variant(label, e)` | | |
| `call(f, [a…])` | `f`、引数を左から、呼ぶ | ✓ |
| `method(C, m, d, [own…])` | `d`、`own` を左から、インスタンスの初期化を検査してメソッドの値を選ぶ | |
| `opcall(C, m, d, [a…])` | `d`、引数を左から、メソッドを選び、呼ぶ。常に末尾でない(§5.7) | |
| `not(e)` / `and(a, b)` / `or(a, b)` | 短絡 | `b` の中 |
| `closure(fn, [cap…])` | 捕獲を左から評価してクロージャを作る | |
| `dictabs(fn, [cap…])` | 辞書を受け取る値を作る(評価はしない) | |
| `let(s, rep, e1, e2)` / `letpat(p, e1, e2)` | `e1`、照合、`e2`。照合の失敗は実行時エラー | `e2` の中 |
| `letrec([(s, fn, [cap…])…], e)` | クロージャをすべて作ってから捕獲を埋める | `e` の中 |
| `seq([e…])` | 左から。最後だけ末尾 | 最後 |
| `match(e, [clause…])` | `e` を 1 回、節を上から。どれにも合わなければ実行時エラー | 節の本体 |
| `rec_empty` / `rec_extend(l, v, r)` | `v`、`r` の順(fid §4 の yzext) | |
| `rec_select(l, r)` / `rec_restrict(l, r)` | 最も左の同名ラベル | |
| `rec_update(l, r, v)` | `r`、`v` の順(fid §4 の order2) | |
| `perform(E, op, [a…])` | 引数を左から、最も内側の E のハンドラへ | |
| `handle(E, body, [opclause…], ret?, cancel?)` | 3.11 節 | ✓ |
| `resume(e, tail)` | `e`、再開済みかの検査、再開(D511) | `tail` の印 |
| `hole` | `???`。実行時エラー | |

- `opcall` と `call(method(…), …)` を分けるのは、メソッドを選ぶ時点が観測できるからである。
  Diktor は演算子で辞書を作り、オペランドを評価してからメソッドを選ぶ(interp.ml:340-345【実測】)。
  関数の形で書いたメソッド(`show(x)`)は、呼び出し先として先に選ぶ。
  インスタンスの宣言の前の選択は実行時エラーなので、オペランドの出力との前後が評価の結果に効く。
- `!=` は `not(opcall(Eq, eq, …))` にする(fid §8)。

### 3.6 関数、クロージャ、自由変数

- KIR の関数は、プログラムの関数表の 1 項目で、次の欄を持つ。
  `kind`(`lambda`、`opclause`、`retclause`、`cancelclause`、`handlebody`、`thunk`、`dictabs`)、パラメータの Rep の列、辞書パラメータの数、捕獲の数、スロットの数と Rep、本体。
- 別のフレームで走りうる本体は、すべて関数にする。
  無名関数と関数の定義に加えて、`handle` の本体と各節の本体も関数である。
  `handle` の本体を関数にするのは、継続の取り出しがフレームの境目でしか切れないからである(本書 6.6 節)。
- `closure(fn, caps)` の捕獲は、外側の関数の `local`、`env`、`dparam` を並べた列で、内側では `env(i)` で読む。
  辞書パラメータも捕獲の対象である(tree §3 の「自由変数」の注意)。
- `letrec` は、クロージャをすべて作った後で捕獲を埋める(tg §1.1 の `mutable c_env` に当たる)。
- 根拠: tree §3 は、自由変数の計算を局所のスロット化と同じ走査で求められる中程度の作業(300〜500 行)と見積もった。
  Rust 側で捕獲を計算する案もあるが、KIR に明示すれば検証器が範囲と数を確かめられ、Diktor の参照インタプリタも平坦な環境で書ける。

### 3.7 辞書と型クラス

- 辞書の式は次の 5 種である(tree §2 の証拠)。
  `dinst(I, [前提…])`、`dparam(i)` か `env(i)`、`drecord([(l, d)…])`、`dvariant([(l, d)…])`、`dbuiltin(C, 頭)`。
  `drecord` と `dvariant` のラベルは、型の行の順に並べる(構造的な等値。§12.5、fid §8)。
- インスタンスの定義は、クラス、頭(解決済み。tree §3 の「インスタンスの頭」)、前提の数、メソッドの実装の列を持つ。
  実装は `(メソッドの番号、自分の辞書の数、関数)` で、関数は `前提の辞書 ++ メソッド自身の辞書` を受け取る(tree §4.2 の ABI)。
- `method(C, m, d, own)` の意味は次のとおりである。
  1. `d` が `dinst(I, ps)` なら、`I` の初期化済みの印を調べ、なければ実行時エラーにする。
  2. 実装が前提も自分の辞書も持たない値束縛なら、`def_instance` で評価した値を返す。
  3. そうでなければ、実装の関数を `ps ++ own` で評価する(使うたびに評価。§6.4、§12.2)。
  4. `dbuiltin` は組み込みの表(fid §13.4)を、`drecord` と `dvariant` は構造的な `Eq.eq` を引く。
- 辞書を受け取る値束縛(Diktor の `DAbs` 付きの束縛。tree §4.3)は `dictabs` の大域か局所にし、使う位置で `dictapp` する。
  本体が無名関数の束縛も同じ形にする。
  クロージャを作るだけの評価は観測できないので、LIR は `dictapp(global(f), ds)` の直後の呼び出しを直接呼び出しに変えてよい。

### 3.8 レコード、ヴァリアント、名目的な型

- レコードはラベルで操作する命令のまま残す(tree §3 の「レコードの配置」)。
  スコープ付きラベルと行多相のため、静的な配置は一般には決まらない。
  閉じた行で単相な箇所の配置の確定は LIR が行う(本書 6.4 節)。
- ヴァリアントはラベル(文字列表の添字)と積載値 1 個である。引数のないヴァリアントは Unit を積む(§9)。
- 名目的な型は、型の記号とコンストラクタの番号(宣言の順)で表し、フィールドは宣言の順に格納する。
  コンストラクタは第一級の値ではない(tree §7 の p2)。

### 3.9 パターン

- パターンは `wild`、`bind(s)`、`lit(…)`、`record([(l, p)…], closed|open|rest(p))`、`ctor(T, c, [(field, p)…])`、`variant(l, p)` の 6 種である。
  `PAnnot` は消す。
- 数値のリテラルパターンは、照合する列の型で読んだ値として書き出す(`case 0xFFFFFFFF` は Int32 の -1。§11.1)。
  型検査の後は読めない字面は残らない(tree §1.2)。
- `match` は節の順とガードを保つ(D505)。
  ガードは、その節のパターンが合ったときだけ、上から順に評価する(§11.2、fid §7)。
- 根拠: tree §3 は決定木を IR に要らないと判断した。
  ガードが出力を起こしうるので、決定木を作る段は 1 か所(LIR)にまとめ、評価の順を守る手順をそこだけで確かめる。

### 3.10 末尾呼び出しと末尾 resume の印

- `call` と `handle` は `tail` の印を、`resume` は `tail` の印を持つ(D506)。
- 書き出しは §5.7 の規則で印を付ける。
  検証器は、関数の本体を根にして同じ規則で末尾位置を再計算し、印と一致しなければ拒否する。
  `resume` の末尾は、操作節の本体を根にし、`handle` と `lambda` に入らない背骨でたどる(tree §2 の「末尾 resume」の行)。
- `opcall` は末尾にしない(§5.7 の「保証しない」)。
- `return` 節の本体と N の節の本体の末尾性は動的に決まる(§5.7 の最後の箇条)。
  これは KIR の印ではなく、実行時の仕組み(本書 6.6 節)で満たす。

### 3.11 エフェクト

- `handle` は、対象のエフェクト、本体の関数、操作節の列、`return` 節(任意)、`cancel` 節(任意)を持つ。
- 操作節は、操作の番号、引数のパターン、ガード(任意)、本体、分類 `N|T|G` を持ち、1 つの `opclause` 関数にまとめる。
  パターンの変数は、ガードと本体が共有するスロットである。
- 分類は次の規則で決まる(fx §6.0、D507)。
  - N: 操作の返り値の型が `Never`(Diktor の `RNeverOp`)。
  - T: 節の本体の `resume` がすべて末尾 resume である(`resume` の無い枝を含んでよい)。
  - G: それ以外。
- 検証器は、操作の宣言の `never` の印と、`resume` の `tail` の印から分類を再計算する。
- `cancel` 節と `return` 節には `resume` もガードも無い(§13.5)。
- `Console.write` の `perform` は、KIR ではほかの操作と同じに書く。LIR が実行時の直接の呼び出しに変える(D534)。

### 3.12 リージョン、extern、組み込み

- `run` は消す(tree §1.4。安全性は型が保証する)。
- `Ref` と `Array` と `MutableArray` の操作は、`builtin` の大域(記号 `builtin/Ref.new` など)である。
  一覧は fid §13.2 の 12 個である。
- `extern "prim"` は 48 個(fid §13.1。`grep -c '^extern "prim"' diktor/lib/prelude.kel` → 48【実測】)で、`extern(abi, 名前)` の大域にする。
  実装の無い名前は、読み込みでは拒否せず、呼んだときに実行時エラーにする(§17、fid §12)。
  制約付きの extern が受け取る辞書は捨てる(tree §4.8)。
- RustKeleut では、利用者の関数を呼ぶ組み込み(`Array.each`、`pinned`)を `rt.kirt` に KIR で書く(D533)。
  こうすると、その中の呼び出しも再開点を持ち、継続の取り出しと段の切り替えが組み込みでも同じに働く(fid §9 の最後の段落)。
  Diktor は OCaml のエフェクトで取り出せるので、これまでどおり OCaml で実装してよい。

### 3.13 実行時エラーと論理的な深さ

- 実行時エラーの種類は、KIR の仕様で列挙する(ゼロ除算、数値リテラルの範囲、変換の範囲、文字列と配列の範囲、照合の失敗、未束縛の変数、宣言前のインスタンス、`???`、`__panic`、2 回目の resume、深さの限度、出力の失敗、未実装の外部関数)。
  文面は D の分類(fid §0)なので仕様にしない。
- **論理的な深さ**を次のように定める(D512)。
  - 末尾でない `call` と `opcall`、`perform` の節の起動、組み込みが利用者の関数を呼ぶ呼び出しは、それぞれ深さを 1 増やし、戻ったら 1 減らす。
  - 末尾呼び出しと末尾 resume は深さを変えない。
  - 末尾でない `resume` は、取り出したときの継続のフレームの数だけ深さを増やす。
  - 深さが限度を超える呼び出しは、その呼び出しに入る前に実行時エラーにする。
- 根拠: §15.5 は限度の大きさを処理系に任せるが、限度を超えたときの振る舞い(`cancel` を走らせて終了状態 3)は評価の結果に効く(fid §5)。
  ネイティブのスタックの大きさで限度を決めると、フレームの大きさがバックエンドごとに違うので、深い再帰で終わり方が分かれる(fid §5 の推論)。
  論理的な深さなら全バックエンドが同じ位置で限度に達する。
  V8 のスタックあふれは wasm の中で捕まえられない(fx §4、sw §2)が、論理的な限度がそれより先に来れば問題にならない。

### 3.14 テキスト形式

- `.kirt` は S 式で、バイナリと 1 対 1 に対応する(往復で同じバイト列になる)。
- 例(`let rec loop(n, acc) = if n == 0 then acc else loop(n - 1, acc + 1)` の本体の一部):

```
(fn 7 lambda (params (n i32) (acc i64)) (dicts 0) (caps 0) (slots (n i32) (acc i64)) (yield 0)
  (match (opcall Eq eq (dbuiltin Eq Int32) (local 0) (lit i32 0))
    (clause (lit bool true) (local 1))
    (clause (lit bool false)
      (call tail (global "main.kel/loop")
        ((opcall Sub sub (dbuiltin Sub Int32) (local 0) (lit i32 1))
         (opcall Add add (dbuiltin Add Int64) (local 1) (lit i64 1)))))))
```

- 正準形(空白、並び、数の綴り)を仕様で定め、`keleut kir dis` と `diktor --emit-ir-text` は同じ正準形を出す。
  cram と差分試験はこの正準形を比べる。

### 3.15 バイナリ形式

- 先頭の 16 バイトは、マジック `00 4B 49 52`(`\0KIR`)、主版 u16、副版 u16、必要な機能のビット u32、節の数 u32(どれもリトルエンディアン)である。
- 続いて節が並ぶ。各節は `id: u8`、`size: uLEB128`、中身である。
  id は昇順で、`0x00〜0x7F` は必須の節、`0x80〜0xFF` は任意の節である。
- 整数は、非負を uLEB128、符号付きを sLEB128 で書く。
  `f64` は IEEE のビットを 8 バイトのリトルエンディアンで書く(NaN の積載を保つ)。
- 節の一覧:

  | id | 節 | 中身 |
  |---|---|---|
  | 0x01 | strings | 名前の文字列(UTF-8 であること) |
  | 0x02 | blobs | `String` のリテラルのバイト列(不正な UTF-8 も NUL も許す。§4.4) |
  | 0x03 | units | 単位の鍵、元のパス、初期化の順 |
  | 0x04 | types | 名目的な型、コンストラクタ、フィールド名 |
  | 0x05 | effects | エフェクト、操作、引数の数、`never` の印 |
  | 0x06 | classes | クラス、メソッド、メソッドの辞書の数 |
  | 0x07 | instances | 3.7 節 |
  | 0x08 | globals | 記号、種類、単位、辞書の数、Rep |
  | 0x09 | functions | 3.6 節。本体は前順の木で、各ノードは 1 バイトの命令と欄 |
  | 0x0A | init | 単位ごとの初期化の手順 |
  | 0x80 | producer | 書き手の名前と版、元のファイルのハッシュ |
  | 0x81 | locations | ノードの前順の番号から `(ファイル, 行, 桁)` への表 |
  | 0x82 | types-debug | 3.2 節の完全な型の文面 |

- 読み手は、マジック、版、必要な機能のビット、節の順と大きさ、添字の範囲を検査し、満たさないものを拒否する。
  任意の節は読み飛ばせる。

### 3.16 互換性の方針

- 1.0 までは、形式を変えるたびに副版を上げ、読み手は同じ `0.y` だけを受け付ける(D528)。
  Diktor と RustKeleut は同じリポジトリの木で一緒に進むので、厳密な一致で困らない。
- 1.0 の後は、任意の節と、必要な機能のビットで守る新しい命令の追加を副版の変更とし、意味を変える変更を主版の変更とする。
- `doc/IRSpec.md` の末尾に版ごとの変更の記録を置く。

## 4. KIR の意味で決めること(Diktor との既知の差の裁定)

| 項目 | 現状【実測】 | 裁定 | 理由 |
|---|---|---|---|
| `resume(resume(n))` | Diktor の短い経路は外側の使用済みの印を先に立て、内側の再開の前に落ちる。背骨の経路は内側を再開してから落ちる(fx R1) | 引数を先に評価してから検査する(D511)。Diktor の短い経路(interp.ml:1064 付近)を M80 で合わせる | §5.1 の評価順序と、§13.5 の「2 回目の再開は実行時エラー」に素直に従う |
| `Float64` のリテラルパターン | Diktor は OCaml の `=` で比べる(interp.ml:164)。NaN は合わず、`0.0` は `-0.0` に合う | IEEE の `==` とする(D513) | Diktor と同じで、`==` 演算子(§4.3)とも一致する。LangSpec §11.1 に 1 文を足す(P236) |
| 使うたびに評価する値の覚え込み | Diktor の `apply_dicts` は、直前と同じ辞書の列なら前の結果を返す(interp.ml:465-470) | KIR の意味は毎回評価とし、覚え込みは観測できないときに限って許す(D514) | 初期化式はエフェクトを起こせず(§6.4)、1 回目が実行時エラーか非停止なら 2 回目に到達しない。したがって覚え込みは観測できない |
| `sin cos exp log` | Diktor は glibc、RustKeleut は `libm` crate | RustKeleut の 3 バックエンドは同じ `libm` crate を使う(D527)。Diktor との差は既知の差として試験から外す | 1 つの実装を共有すれば RustKeleut の中では一致する(fid §12)。Diktor に Rust の libm を結合するのは依存が重い |
| 深さの限度 | Diktor は OCaml のスタック(`OCAMLRUNPARAM=l=…`)で決まる | KIR の論理的な深さ(D512)。Diktor の木の評価器は変えない | §15.5 の限度は I。論理的な深さは RustKeleut と Diktor の `--run-ir` で一致させる |

### 5.2 差し込む位置と旗

- `driver.ml` の `run_with` の `Run` の分岐(driver.ml:1196-1197【実測】)で、`type_check_files` の後、`Interp.run_units` の前に書き出しを差し込む(tree §5.1)。
- 旗は 4 つ足す。
  - `--emit-ir FILE`: 型検査の後に KIR のバイナリを書き、実行しない。
  - `--emit-ir-text FILE`: 正準のテキストを書く。
  - `--run-ir FILE`: KIR を読み、検証し、`ir_eval` で実行する。型検査はしない。
  - `--max-depth N`: `--run-ir` の論理的な深さの限度。
- 環境変数 `DIKTOR_VIA_IR=1` のとき、`Run` の分岐は書き出し、バイナリへの符号化、読み込み、検証、`ir_eval` をプロセスの中で続けて行う。
  既存の cram をこの経路でも走らせ、書き出しの正しさを Diktor の中で確かめるためである。
- `usage` の文面を変えるので、`test/smoke.t` の期待値を別のコミットで更新する(tree §5.1)。

### 5.3 cram との結合

- 新しい cram は 3 本である。
  - `test/ir_emit.t`: 小さいプログラムの正準テキストを固定する(式の種類ごと、印ごと)。
  - `test/ir_run.t`: `--run-ir` の結果が通常の実行と一致することと、壊れたバイナリの拒否(マジック、版、範囲)の終了状態。
  - `test/ir_depth.t`: `--max-depth` の限度で `cancel` が内側から走り、終了状態 3 になること。
- dune の別名 `@runtest-via-ir` を足し、評価を含む cram(eval、run_exit、tail_calls、never_ops、effect_order、runtime_effects、resume_guard、instance_init、region、extern_c ほか)を `DIKTOR_VIA_IR=1` で走らせる。
  `OCAMLRUNPARAM=l=100k` で OCaml のスタックの限度を試すブロックは、限度の決め方が違うので除外の一覧に載せる。
- `ir_eval` は末尾位置を OCaml の末尾呼び出しに保つ(interp.ml の冒頭の規約 1 と同じ)。
  `tail_calls.t` の一定空間の検査は、via-IR の経路でも通ることを受け入れの条件にする。

### 6.3 KIR の読み込みと検証

- 読み込みは 3.15 節の検査を行い、関数表と記号表を作る。
- 検証器は次を確かめる。
  1. 添字(スロット、捕獲、辞書パラメータ、大域、型、コンストラクタ、ラベル、操作)が範囲にある。
  2. Rep が合う(プリミティブの引数と結果、`let` の Rep と初期化式)。
  3. 末尾の印と末尾 resume の印が、§5.7 の規則の再計算と一致する(D506)。
  4. 節の分類が再計算と一致する(D507)。
  5. `resume` が操作節の本体の中にだけあり、N の節に無い(§13.5)。
  6. 初期化の手順が各大域をちょうど 1 回定義する。
- 検証の失敗は終了状態 70 である。
  KIR を作るのは型検査を通ったプログラムだけなので、失敗は書き手の不具合を意味する。

### 6.4 共有の下ろし(KIR → LIR)

LIR は関数ごとの基本ブロックのグラフで、仮想レジスタは Rep を持つ。
Keleut には反復の構文が無い(§5.7)ので、どの関数の制御フローも**非巡回**である。

パスの順:

1. 環境の配置: 捕獲と辞書パラメータを `env` の位置に、局所をレジスタに写す。
2. パターンの照合: 節の順を保ち、ガードはパターンが合った節だけ評価する、後戻りのある照合の手順に下ろす。
   照合の失敗は `rt_error(MatchFail)` にする。
3. A 正規化: 評価順序を命令の順として固定する。
4. Rep の推論と箱: Rep の違う位置で `box`、`unbox` を入れる。関数の境目は v1 ではすべて `any` とし、型付きの入口は後で足す(tg §2.2)。
5. 辞書の定数化: 辞書が `dbuiltin` に確定する `opcall` を、プリミティブの命令(`i32.add` など)に置き換える。
6. レコードの形: 閉じた行で単相な箇所の形と位置を定数にする。ほかは実行時の形の表(本書 6.5 節)を引く。
7. 数値の検査の明示: `div_s`、`rem_s` はゼロで `rt_error(DivZero)`、`MIN / -1` は `MIN`、`MIN % -1` は 0 を返す分岐を明示する。
   `f64` から整数への変換は、NaN と範囲(`t >= -2^31 && t < 2^31` など)を先に検査する(fid §1)。
   どのバックエンドの命令も、未定義の動作や trap に頼らない。
8. エフェクトの下ろし(本書 6.6 節)。
9. 初期化の検査の省略(D535): 大域 `g` の参照を含む**最も外側のトップレベルの実体**(大域、インスタンス、式文)の初期化の手順が `g` の手順より後にあるか、両者が同じ `def_fns` の群にあるときだけ、検査を省く。
   その実体のコードは、その手順が始まった後でしか走らないからである。
   「`g` より後に定義される関数」と言い換えると誤りになる。
   前の `def_value` の中で作った無名関数(`let p = {f = fn(x) => h(x)}` で `h` が後の宣言)は、`h` の初期化の前に呼べるので、検査を残す。
   この反例を `conformance/` の試験に置く。
10. 深さの命令: 末尾でない呼び出しの前後に `depth_inc`(限度の検査つき)と `depth_dec` を置く(3.13 節)。
11. yield の刈り込み(D526): `may_yield = 0` の呼び出しは再開点を持たない。
12. 生存区間と再開点: 末尾でない呼び出しのうち再開点を持つものに番号を振り、その後で生きているレジスタを値スタックのスロットに割り当てる。
    スロットは `any` の区画(GC が走査する)と生の区画に分ける。

LIR の命令のうち、意味の一致に効くものの一覧(定数、移動、プリミティブ、確保、フィールド、形の操作、大域の読み、呼び出し、戻り、分岐、`rt_error`、深さ、ハンドラ)は `rustkeleut/doc/lir.md` に書き、各命令の意味を「trap せず、未定義の動作を持たない」形で定める。

### 6.5 実行時

**値の表現(ネイティブ)**(D516、tg §2)

- 一様な語は 64 ビットである。最下位ビットが 1 なら即値、0 なら 8 バイト境界のポインタである。
- 即値は Int32(`(n << 1) | 1`)、Boolean、Unit、引数のないコンストラクタ(番号)である。
- 箱は Int64、Float64(一様な位置に置くときだけ)、文字列(長さ付きのバイト列。NUL を終端にしない。§4.4)、レコード(形の id とフィールドの配列)、データ(コンストラクタの番号とフィールド)、ヴァリアント(ラベルと積載値)、クロージャ(関数 id と捕獲)、辞書、参照、配列、ハンドラ記録、継続、フレームの記録である。
- 見出しの 1 語に、種類、フィールドの数、GC の印を置く。

**GC**(D517、tg §4 案 A、§5)

- 動かさないマークスイープを、大きさの種類ごとのページで行う。ミューテータは 1 本である(§13.7 の最後の文)。
- 根は、値スタックの `any` の区画(実行中のフレームと、継続に取り出したフレームの記録)、大域の表、ハンドラの連鎖、保留中の状態語の積載値、Rust 側の明示のハンドルの枠である。
- 安全点は確保と呼び出しだけである。反復の構文が無いので後ろ向きの枝の検査は要らない。
- ステートポイントは使わない。tg §5.4 は、LLVM 22 の `rewrite-statepoints-for-gc` が `musttail` を壊すことを測った。
- 共有の値スタックがそのまま shadow stack の役を果たす(呼び出しと確保の前にスロットへ明示的に書く)。
  LLVM の `gc "shadow-stack"` の戦略は sl の gc の実験で JIT でも動き、根の鎖を Rust に置けると分かったが、インタプリタのフレームと継続のフレームの記録は別に走査することになるので採らない。
- 世代別 GC と MMTk は本計画の範囲の外に置く(tg §5.3)。

**文字列と出力**(D534)

- 文字列はバイト列で、比較は符号なしバイトの辞書順、長さはバイト数である(fid §3)。
- 標準出力は実行時のバッファに貯め、標準エラーへ書く直前と終了の前に flush する(§15.5、fx R9)。
- 書き込みの失敗は `rt_error(Io)` として巻き戻し(`cancel` 節が走る)、終了状態 74 にする(Diktor の sinkfail.kel と同じ。fx R9)。

**数と文字列化**(D515)

- `keleut-rt-core` に、§16.2 の `show(Float64)` を書く。
  NaN と無限大、`1e16` 未満の整数値の `%.1f`(`-0.0` を含む)、それ以外は有効数字 `p` を 1 から 17 まで増やし、`format!("{:.*e}", p - 1, x)` で正しく丸めた表記を読み戻して元の値になる最初の `p` を使い、指数と末尾のゼロを整える。
  fid §2 は、この探索が glibc の `%.*g` の探索と 2,000,000 件で差 0 件だったことを測った(Rust の最短の往復表記は 522 件違った)。
- `sin cos exp log` は `libm` crate、`sqrt` は IEEE の `sqrt` である。
- 同じソースを wasm32 にもコンパイルするので、WasmGC でも同じ字面と同じビットになる。
  JS の `toPrecision` などは使わない(fid §2 の測定で 113 件の差と `-0.0` の欠落)。

**スタック**

- ミューテータは専用のスレッドで走らせ、スタックを `64 MiB + 限度 × 1 KiB` の仮想領域で確保する(既定で約 1.06 GiB、実メモリは使った分だけ)。
- 論理的な深さの検査(3.13 節)が先に限度を知らせる。
- 予備として、JIT の関数とインタプリタの入れ子の入口でスタックポインタを ctx の下限と比べ、超えたら `rt_error(NativeStack)` にする。
  これが論理的な限度より先に起きたら一様性の違反なので、`kconform` は警告として報告する。

**実行時エラーと終了**

- 実行時エラーは状態語 `ERROR(kind, 文面)` を立て、伝播でハンドラを内側から巻き戻す(本書 6.6 節)。
- 最上位に届いたら、標準出力を flush し、診断を標準エラーに書き、終了状態 3(出力の失敗は 74)で終わる。

### 6.6 エフェクトの実装(全バックエンドで共通の規約)

#### 6.6.1 実行時のデータ

- **ハンドラ記録** `HR`: 起動ごとの 64 ビットの単調増加の id(fx R8)、エフェクト、節の表(`opclause` 関数のクロージャ)、`return` 節と `cancel` 節、親へのポインタ(再開で付け替える)。
- **ハンドラの連鎖** `ctx.handlers`: 有効なハンドラの単方向リスト。最も内側が先頭である。
- **状態語** `ctx.pending`: `NONE`、`YIELD(hr, 節, 束縛)`、`DISCARD(hr, Value(v) | NeverBody(節, 束縛))`、`ERROR(kind, 文面)` のどれかである。
- **フレームの記録**: `(関数 id、再開点、スロットの写し)`。取り出しの途中では `ctx.yield_frames` に内側から積む。
- **継続** `K`: フレームの記録の列、連鎖の切り取り(perform の位置の連鎖の先頭から `HR` まで)、`HR`、深さの差、`used` と `alive` の印。

#### 6.6.2 伝播の規則

末尾でない呼び出しから戻ったとき、`ctx.pending != NONE` なら次のようにする。
これは LIR の命令で書かれ、インタプリタ、JIT、Wasm のどれでも同じである(D508)。

- 普通のフレーム: `YIELD` なら自分のフレームの記録を `ctx.yield_frames` に積んで戻る。それ以外ならそのまま戻る(フレームは捨てる)。
- 戻り値は使わない。状態語だけが意味を持つ。

#### 6.6.3 `handle` と `rt_handle`

`handle` は、ハンドラ記録を作り、組み込み関数 `rt_handle(hr, body)` を呼ぶ。
`handle` が末尾位置にあれば、この呼び出しを末尾呼び出しにする(D510)。
`rt_handle` は `keleut-lir` が LIR で組み立てる組み込み関数(KIR には現れない)で、次の手順を持つ。

1. `hr.parent = ctx.handlers`、`ctx.handlers = hr` とし、本体の関数を末尾でなく呼ぶ。
2. 本体が値 `x` で戻った: `ctx.handlers = hr.parent` とし、`return` 節を `x` で**末尾呼び出し**する(無ければ `x` を返す)。
3. `DISCARD(hr, Value(v))`(自分宛て): 連鎖から外し、`v` を返す。`return` 節も `cancel` 節も走らせない(fx R2)。
4. `DISCARD(hr, NeverBody(c, b))`(自分宛て): 連鎖から外し、N の節の本体を**末尾呼び出し**する(fx R4、§5.7)。
5. `YIELD(hr, c, b)`(自分宛て): `K` を作り、連鎖から外し、G の節を `K` とともに末尾でなく呼ぶ(6.6.5 節)。
6. 自分宛てでない `DISCARD` と `ERROR`: 連鎖から外し、`cancel` 節を**防壁**の中で走らせ、同じ状態語で戻る(伝播を続ける)。
7. 自分宛てでない `YIELD`: 自分のフレームの記録(`hr` を含む)を積んで戻る。

**防壁**は次のとおりである(§13.6 の最後の段落、fx R5)。
保留中の状態語 `P` を退避して消し、`cancel` 節を呼ぶ。
戻ったときに `DISCARD` か `ERROR` が立っていれば、それを打ち切って診断に記録し(標準出力を flush してから標準エラーへ)、消す。
`YIELD` が立っていれば、`P` を生きている値に含めて自分のフレームを積んで戻る(再開されたら続きから同じ処理をする)。
最後に `P` を戻して伝播を続ける。

#### 6.6.4 `perform`

1. `ctx.handlers` を先頭からたどり、エフェクトが一致する最も内側の `hr` を探す。
2. `saved = ctx.handlers`、`ctx.handlers = hr.parent` とする(節とガードの中の操作は外側へ届く。§13.4)。
3. `hr` の節を上から試す。パターンを照合し、合えばガードを評価する。これは perform の位置で走る LIR のコードである。
4. 選んだ節の分類で分ける。
   - T: 節の本体を末尾でなく呼ぶ。本体は末尾 resume `resume(v)` を「`v` を返す」に、`resume` しない値 `v` を `DISCARD(hr, Value(v))` を立てて戻るに下ろしてある。
     値で戻ったら、その値が `perform` の値になる。
     値で戻ったときも状態語が立って戻ったときも、`ctx.handlers = saved` に戻す。
   - N: `ctx.handlers = saved`、`DISCARD(hr, NeverBody(c, b))` を立てて戻る。
   - G: `ctx.handlers = saved`、`YIELD(hr, c, b)` を立て、連鎖の切り取りの先頭として `saved` を記録して戻る。

T の節の本体で `resume` の前に起きた実行時エラーは、節のフレームから perform の位置のフレームを通り、間のハンドラの `rt_handle`(`cancel` を走らせる)、`hr` の `rt_handle`(継続はまだ生きているので `cancel` を走らせる)、外側の順に伝わる。
これは §13.6 の順序(節の中で起動したハンドラ、破棄する計算の中のハンドラを内側から、そのハンドラ自身、外側)と一致する(fx §6.0 の T の項)。

#### 6.6.5 G の節と `rt_resume`

- `rt_handle` の手順 5 で、G の節を `(束縛, K)` で呼ぶ。
- 節の中の末尾でない `resume(v)`: `v` を評価し、`K.used` なら実行時エラー、そうでなければ `K.used = true` とし、`rt_resume(K, v)` を末尾でなく呼ぶ。
- `rt_resume(K, v)` は `rt_handle` と同じ手順 2〜7 を持ち、本体の代わりに `K` のフレームの記録を内側から順に再開する。
  再開の前に `K.hr.parent = ctx.handlers`、`ctx.handlers = K の切り取りの先頭` とし、深さに `K` のフレームの数 n を足す。
  再開したフレームが 1 つ終わるたびに深さを 1 減らす。
  こうすると、最も内側のフレームが走っている間の深さは「`rt_resume` の位置 + n」、それが戻った後は「+ n − 1」となり、OCaml のファイバーで本当に入れ子にする Diktor の `ir_eval` の深さと一致する。
  フレームを順に再開する手順は、LIR の関数本体が非巡回(本書 6.4 節)なので、自分を末尾呼び出しする形で書くか、実行時のループとして持つ。
  各フレームは「再開点の呼び出しが前のフレームの値で戻った」として続きを走る。
  最も外側のフレーム(`handle` の本体)が値を返せば、手順 2 の `return` 節に進む。
  したがって、再開した計算の中の `return` 節の値と、`resume` しない節の値は、ハンドラ式の値ではなくこの `resume` の返り値になる(§13.6 の第 1 段落)。
- 再開の途中で `YIELD` が立てば、`rt_resume` はまだ再開していない `K` のフレームを `ctx.yield_frames` の後ろに足して戻る。
  `DISCARD` か `ERROR` が立てば、残りのフレームも状態語を注入して順に再開し、その中のハンドラの `cancel` を走らせる。
- 節の末尾 resume(G の節の中の末尾の `resume(v)`): 節は「`K` を `v` で末尾再開せよ」という印を立てて戻り、節を呼んだ `rt_handle` または `rt_resume` のフレームが、自分を `rt_resume(K, v)` の末尾呼び出しで置き換える。
  末尾 resume を何回続けても領域は増えない(§13.5、Diktor の `Clause_resume`。fx R6)。
- 節が値 `r` で戻り、`K` を再開済み(`K.used`)なら: `r` がハンドラ式の値であり、ほかに何も走らない。
- 節が値 `r` で戻り、`K` を再開していなければ: 継続を破棄する。
  `rt_resume` を「`DISCARD(hr, Value(r))` を注入した再開」として末尾呼び出しする。
  `K` の中のハンドラの `cancel` が内側から外側へ走り、再び連鎖に付けた `hr` の手順 3 が `r` を返す(§13.6 の「節の値が決まった後で破棄」)。
- 節が `resume` の前に `ERROR` か自分宛てでない `DISCARD` で戻ったら: 同じ状態語を注入した `rt_resume` を末尾呼び出しする。
  `K` の中のハンドラの `cancel`、`hr` 自身の `cancel`(手順 6)、外側の順になる(fx R3 の resumeinnerpre)。
- 節が `resume` の後に脱出したら: `K` はもう無く `hr` は連鎖にいないので、そのまま伝播する(自分の `cancel` は走らない。§13.6)。

#### 6.6.6 難しい場合の照合

| テスト(fx の表) | この規約での動き |
|---|---|
| cancelperform | 実行時エラーの伝播の途中の `cancel` が N の操作を起こし、その `DISCARD` が防壁で打ち切られる。元の `ERROR` が続く |
| cancelsame | 破棄を進めている `H` への 2 つ目の `DISCARD` が防壁で打ち切られ、1 つ目の伝播が続く |
| cancelresume | 防壁の中の `cancel` が `H`(まだ連鎖にいる)の G の操作を起こす。防壁のフレームは退避した `P` を持って取り出され、`resume(5)` で再開されると `cancel` の続きを走らせ、`P` の伝播を続ける。`P` は再び付けた `H` の `rt_resume` に届き、throw の節の値 7 が `resume(5)` の値になる |
| resumeinner* | 再開した計算の中のエラーは、連鎖に付け直した `hr` を通るので `cancel` が 1 回走る。`resume` が戻った後のエラーでは `hr` は連鎖に無い |

#### 6.6.7 選択の根拠と代案

- 採る案は、fx §6.4 の (d)「N と T は直接の呼び出し、G は yield bubbling」を、脱出まで状態語の伝播にそろえたものである。
  fx §6.5 の表で、(d) だけが「Node 26 でフラグなし」と「全バックエンドで共通」を両方満たす。
- 代案 1: ネイティブ fiber(tg §6、fx §6.2)。
  切り替えは往復 1.8 ns と安い(tg §6.2)が、WasmGC では使えない(WasmFX がフラグつきで、`switch` で落ちる。sw §6)。
  インタプリタと LLVM だけ fiber にすると、エフェクトの実装が 2 系統になり、cancel の順序の細部(fx R5 の 5 テスト)を 2 回作ることになる。
  さらに、fiber の上の JIT のフレームと Wasm のフレームで継続の形が違うので、段の間で継続を受け渡せない(fid §6.2 の階層化の推論)。
  本計画では採らず、M89 の測定で G の費用が問題と分かったときに、LLVM の後段だけの最適化として検討する(P238)。
- 代案 2: 選択的 CPS(fx §6.1)。行多相の高階関数がほぼすべて CPS 側に入る(tg §6.1)ので採らない。
- 代案 3: 脱出を LLVM の Itanium の巻き戻しと Wasm の exnref で行う。
  状態の検査が要らない分速いが、ORC での eh_frame の登録を試していない(sl の「分からないこと」)。
  また cancelresume では、landingpad の途中のフレームを取り出す必要があり、例外の途中の状態をフレームの記録に写す規約が別に要る(fx §6.4 の Q5 の行)。
  検査の費用は呼び出し 1 回あたり読み込み 1 回と分岐 1 回で、v1 では一様性を優先する。
- tg §6.3 の「1 つのハンドラに種類の違う節が混ざれば最も重い種類に合わせる」は、本規約では要らない。
  分類は節ごとに効き、G の節を選んだ perform だけが取り出しの費用を払う。

### 6.7 バイトコードとインタプリタ

- バイトコードは LIR の関数を 1 対 1 に符号化したもので、関数を最初に呼ぶときに作る。
  KIR のバイナリとは別物で、ファイルに書かず、互換性を約束しない(D500)。
- 形式はレジスタ機械である。命令は 1 バイトの命令番号と、u16 のスロット番号、u32 の定数・関数・ラベルの番号、i32 の分岐の差分からなる可変長である。
- フレームは共有の値スタックに置く。見出しは `(関数 id、戻り先、再開点)` で、続くスロットは `any` の区画と生の区画に分かれる。
  JIT のフレームと同じ形である(tg §3.2)。
- インタプリタの中の呼び出しはネイティブのスタックを使わず、フレームを積んでループの先頭へ戻る。
  末尾呼び出しはフレームを再利用する。
- 再開点は命令の位置である。フレームの記録からの再開は、スロットを写し戻して再開点へ飛ぶだけである。
- 実装は Rust の `match` によるディスパッチの平坦なループである(Rust の安定版には `become` も computed goto も無い。sl の Rust 側の末尾呼び出し、tg §3.1)。

### 6.8 LLVM ORCv2 の後段

- llvm-sys 221.1.1 を薄く包む自作の層(`keleut-llvm::sys`)を置く。
  LLVM 21 以降の C API には `LLVMOrcThreadSafeContextGetContext` が無いので、`LLVMContextCreate` で作った文脈を `LLVMOrcCreateNewThreadSafeContextFromLLVMContext` で包み、1 つのモジュールに 1 つの文脈を使う(sl)。
- IR は IRBuilder の C API で組み、LLJIT に足す(sl の callback)。
- 呼び出し規約(D518): 全関数を `tailcc i64 @f(ptr %ctx)` にする。
  引数は呼ぶ側が値スタックの先頭に書き、`ctx->sp` が呼ばれた側のフレームの底を指す。
  戻り値は一様な語で、状態語は `ctx->pending` にある。
  全関数の型が同じなので、間接呼び出しを含むすべての末尾呼び出しを `musttail` にできる(sl の tail と sig、tg §3.3)。
- 再開: `ctx->resume_frame` が null でなければ、入口でスロットを写し戻し、再開点の番号で `switch` して呼び出しの直後のブロックへ飛ぶ。
- 生きている `any` の値は、呼び出しと確保をまたぐ前に値スタックのスロットに書く。
  GC が動かさないので、呼び出しの後に読み直さない(tg §4 案 A)。
- Rust の実行時の関数(確保、形の表、文字列、エラー)は ccc の普通の呼び出しで呼ぶ。
- スタブ: Rust は `tailcc` の関数を書けない(`become` が安定版に無い。sl)ので、起動時に小さな LLVM モジュールとして作る。
  - `interp_stub`(tailcc): Rust の `interp_run(ctx)`(ccc)を呼び、戻りが「末尾呼び出しの依頼」なら入口の表の先を `musttail` で呼ぶ。
  - `enter_tailcc`(ccc): Rust から tailcc の関数を呼ぶ入口。
  tailcc から ccc への `musttail` は検証器に拒まれる(sl の tail の最後の行)ので、末尾の境目はすべて tailcc のスタブを通す。
- IR の最適化は、段を上げた関数に `default<O2>` をかける。
  1 関数の翻訳は IR の最適化なしで約 0.9 ms、`default<O2>` で約 1.9 ms だった(sl の時間の表)。

### 6.9 段の切り替え

- 関数 id ごとに、入口の表 `entry[id]` と呼び出しの回数を持つ(D519)。
  `entry` は最初 `interp_stub` を指し、JIT の翻訳が済んだら 1 回だけ書き換える(sl の tier)。
- JIT から JIT への呼び出しも `entry` を通す。翻訳が済んだ関数への直接呼び出しは、後の最適化とする。
- インタプリタは関数の入口で回数を 1 増やし、しきい値を超えたら翻訳を依頼する。v1 は同期で翻訳する。
- 移り方:
  - インタプリタ → JIT(末尾でない): インタプリタが `enter_tailcc` で `entry[id]` を呼ぶ。
  - インタプリタ → JIT(末尾): `interp_run` が「`id` へ末尾呼び出し」を返し、呼び出し元のスタブが `musttail` する。最上位では Rust の駆動のループがトランポリンになる。
  - JIT → インタプリタ: `entry[id]` の `interp_stub` を `musttail` か普通に呼ぶ。
  - tg §3.3 は、この形で交互の末尾呼び出し 1e8 回が `ulimit -s 512` の下で完走し、`musttail` を外すと SIGSEGV になることを測った。
- 継続のフレームの記録は段に依らない(6.6 節)。
  インタプリタが取り出したフレームを JIT の入口が再開することも、その逆もできる。
  再開は `resume_frame` を立てて `entry[id]` を呼ぶだけで、段を問わない。
- OSR と逆最適化は作らない。JIT は投機をせず、熱い反復は必ず関数の入口を通る(tg §3.6)。
- 試験のための `--tier alternating=SEED` は、関数の呼び出しごとに種から決まる擬似乱数で段を選ぶ(翻訳は事前に全関数で済ませる)。

### 6.10 WasmGC の後段

**値の表現**

| Keleut | WasmGC |
|---|---|
| 一様な値 | `eqref` |
| Int32 | 局所では `i32`。一様な位置では、31 ビットに入れば `i31ref`、入らなければ `(struct i32)` |
| Boolean、Unit、引数のないコンストラクタ | `i31ref` |
| Int64、Float64 | 局所では `i64`、`f64`。一様な位置では `(struct i64)`、`(struct f64)` |
| String | `(array (mut i8))`。JS の文字列に写さない(fid §3) |
| レコード | `(struct i32 (ref $AnyArr))`(形の id とフィールド) |
| データ | `(struct i32 (ref $AnyArr))`(コンストラクタの番号とフィールド) |
| ヴァリアント | `(struct i32 eqref)` |
| クロージャ | 引数の数ごとの部分型 `$CloN <: $Clo`。`(struct i32 (ref $FnN) (ref $AnyArr))` |
| 参照、配列 | `(struct (mut eqref))`、`(array (mut eqref))` |
| フレームの記録 | `(struct i32 i32 (ref $AnyArr) (ref $I64Arr))`(関数 id、再開点、`any` と生の値) |

sw §1 は、構造体、i8 の配列、i31ref、`ref.test`、`br_on_cast` がフラグなしで動くことを測った。

**関数と制御**(D520)

- 関数の型は `(func (param (ref null $Clo)) (param eqref)×N (param (ref null $Frame)) (result eqref))` で、最後の引数が null でなければ再開である。
  `call_ref` は引数の数まで一致する型を求めるので、再開のときは引数の位置に null を N 個渡して同じ型で呼ぶ(再開の表を引数の数ごとに持つ)。
- 関数本体の制御は非巡回なので、ブロックを位相順に並べ、入れ子の `block` と前向きの `br` だけで出せる。
  再開の入口は、関数の先頭の `br_table` で再開点のブロックへ前向きに飛び、局所をフレームの記録から戻してから合流する。
  ループによるディスパッチは要らない。
- 末尾呼び出しは `return_call` と `return_call_ref` である(sw §2 で 1e9 回まで溢れないことを測った)。
- 状態語は大域変数 `$pending`(i32)と積載値の大域に置き、末尾でない呼び出しの後で検査する。
- trap になりうる命令(`i32.div_s`、`i32.rem_s`、`i32.trunc_f64_s`、`array.get`、`ref.cast`、null の参照)の前には、LIR が明示の検査を置いてある(本書 6.4 節の 7)。
  wasm の trap は `catch_all` で捕まえられず `cancel` 節が走らない(fx §4 の測定)からである。
  それでも trap が起きたら、JS が `WebAssembly.RuntimeError` を受けて終了状態 70 にする(実装の不具合の印)。
- exnref は使わない。sw §3 で使えることは確かめてあるが、状態語の伝播と 2 系統にしない(D508)。

**実行時の核と入出力**(D515、D521)

- `keleut-rt-core` を `wasm32-unknown-unknown` にコンパイルした `rt.wasm`(線形メモリを持つ)を、プログラムのモジュールの横に置く。
  プログラムは `rt` のメモリと関数(float show、libm、形の表、文字列の比較)を import する。
- `show(Float64)` は、`rt.f64_show(x)` が線形メモリのバッファに字面を書き、プログラムがそれを i8 の配列に写す。
- 出力は、プログラムが i8 の配列を線形メモリのバッファへ写し、`host.write(ptr, len)` を呼ぶ。
  JS は `fs.writeSync(1, new Uint8Array(mem.buffer, ptr, len))` で書く(sw §4 の方法 B)。
  バッファは満ちたとき、標準エラーへ書く前、終了の前に flush する。
- Node の起動: `keleut run --backend wasm` は `program.wasm` と `rt.wasm` と `run.mjs` を一時の場所に書き、`node` を子プロセスで起動する。
  子の RLIMIT_STACK を `64 MiB + 限度 × 1 KiB` に上げ、`--stack-size` をその 9 割(KB)にする。
  sw §2 は、既定のスタックで非末尾の再帰が約 15,689 段、`--stack-size=7800` で約 126,952 段、`--stack-size=65500` で SIGSEGV(OS のスタックを超えたため【推論】)を測った。
  RLIMIT_STACK を上げた状態で大きな `--stack-size` が効くかは未確認なので、M79 の試作で確かめる(V198)。
  効かない場合の代案は、`Worker` の `resourceLimits.stackSizeMb` で走らせることである(P245)。
- Node の版は 26.9.0 以上を求める。`run.mjs` は起動時に `process.versions.v8` を確かめる。

### 6.11 バックエンドごとの実装の対応

| 仕組み | インタプリタ | LLVM | WasmGC |
|---|---|---|---|
| 状態語の検査 | 呼び出しの戻りで `ctx.pending` | 呼び出しの後の読み込みと分岐 | 呼び出しの後の `global.get` と `br_if` |

## 7. Rust のフロントエンド

- **時期**: M90 から M92 で移植する(D523)。
  それまでは `--frontend diktor` で Diktor の KIR を使い、バックエンドを先に固める。
  バックエンドの差分試験で見つかる不具合を、フロントエンドの差と切り分けるためである。
- **順序**(fp §2): 基盤、字句解析、構文解析と脱糖、宣言表、単一化と表示、elab(型式、パターン、式、let、let rec、宣言、module、import)、網羅性、ドライバの終了状態、KIR の書き出し。REPL は範囲の外である(D530)。

  文法は LALR(1) で衝突が無く、優先順位は非終端の階層で表してある(fp §3.1)。
  受理のずれが差分試験で収束しないときは、`.mly` を lalrpop に写して受理の基準にする。
- **型の表現**: 型は arena と添字の Union-Find、ノードの注釈は `NodeId` で引く別表、大域の状態は 1 つの文脈の構造体に集める(fp §1.3)。
- **検証**(価値の高い順。fp §4.2):
  1. 終了状態の一致(cram の全入力)。
  2. `--dump-tokens` と `--dump-ast` の一致(字句と構文)。
  3. `check` の型の行(933 行)の一致。
  4. 正準化した KIR のテキストの一致(Diktor の `--emit-ir-text` と `keleut emit-kir --text`)。
     KIR の名前は 3.3 節の記号で安定しているので、正準化は空白と並びの規則だけで足りる。
  5. 診断の種別と位置の一致。日本語の文面は §18 の外なので、最初は Diktor の文面を写すが、一致を必須にしない。

## 8. テスト計画

### 8.1 差分試験の実行器 `kconform`

- 入力は 3 つの源から集める。
  1. Diktor の cram を無改変で流す: PATH の先頭に `diktor` という名前の shim を置き、`keleut compat-diktor "$@"` を exec させる(fp §4.2 (c) で shim が 102 回呼ばれ差分 0 を測った)。
  2. cram のヒアドキュメントから抜き出した `.kel`(fp §4.2 (d) で 1,046 本)。
  3. `rustkeleut/conformance/` の新しい試験(エフェクト、数値、Float64、深さ、文字列のバイト)。
- 比べるもの: 標準出力のバイト列と終了状態(§18)。
  標準エラーは、`: 型エラー: ` などの種別の語の後ろを切り、警告は件数だけ残す正規化をしてから、標準出力との前後関係を比べる(fp §4.2 (c) の規則、§15.5)。
- 基準は Diktor の木の評価器である。期待値はリポジトリに置き、Diktor の版とともに更新する。
- 既知の差の一覧(`conformance/known-diffs.toml`)に、V191(M80 で直すまで)、V193、深さの限度の違う試験を理由つきで載せる。

### 8.2 組み合わせ

| 名前 | フロントエンド | 実行 |
|---|---|---|
| `dk` | Diktor | Diktor の木の評価器(基準) |
| `dk-ir` | Diktor | `diktor --run-ir` |
| `ki` | Diktor | `keleut --backend interp` |
| `kj` | Diktor | `keleut --backend jit --tier jit-only` |
| `kt` | Diktor | `keleut --backend jit --tier threshold=1` |
| `ka` | Diktor | `keleut --backend jit --tier alternating=1..8`(種 8 個) |
| `kw` | Diktor | `keleut --backend wasm` |
| `kr-*` | Rust | 上の各組(M92 から) |
| `x-ir` | Rust | `diktor --run-ir`(Rust の KIR を Diktor が実行する) |

- `ki` と `kj` と `ka` と `kw` は、既知の差の一覧に関係なく、互いに完全に一致しなければならない(D499)。
  同じ LIR から作るので、差はバックエンドの不具合である。
- `--gc-stress` と `--no-yield-prune` の組も、夜間の試験で回す。

### 8.3 深さの限度の固定

- 限度を超える試験は `--max-depth` を小さく(例 10,000)固定し、`dk-ir` と RustKeleut の全組で、`cancel` 節の出力の順と終了状態 3 の一致を求める。
  `dk`(木の評価器)は OCaml のスタックで決まるので、この試験では比べない。
- 限度に触れない試験は既定の限度で走らせる。
  ネイティブの予備の検査(`NativeStack`)が論理的な限度より先に起きたら失敗とする。
- `tail_calls.t` の一定空間の試験は、`--max-depth 1000` の下で 100,000 回の末尾呼び出し、末尾 resume、N の節の再試行が完走することで固定する。
  深さの増えない実装でなければ、限度で落ちる。

### 8.4 そのほか

- `keleut-rt-core` の float show は、fltcmp の 2,000,000 件(fid §2)をネイティブと wasm32(Node で実行)の両方で glibc の結果と比べ、差 0 件を求める。
- KIR の読み書きは、Diktor の出力の全件で `keleut kir dis` と `diktor --emit-ir-text` の一致、バイナリ→テキスト→バイナリの往復の一致を求める。
- 壊した KIR(ビット反転、切り詰め)を読ませ、終了状態 70 で拒否し落ちないことを確かめる(fuzz の簡易版)。
