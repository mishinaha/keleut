# 261024-1: RustKeleut と中間言語 Kerno の実装計画(ネイティブ性能と段の切り替えを優先する案)

## 0. 要約

1. IR の名前は **Kerno** とする。
   精緻化の後の水準で、辞書渡しを明示し、A 正規形(ANF)で評価順序を固定し、末尾位置を構文の形で表す。
   型は「表現の型」(`bool`、`i32`、`i64`、`f64`、`w`)だけを持ち、利用者の型の全体は持たない。
   パターンは `match` のまま残し、決定木は RustKeleut の下位の段で作る。
   エフェクトは `handle`、`perform`、`resume`、`tailresume` を高水準の形で残し、操作節に分類 N、T、G を付ける。
2. バイナリ形式は、マジック `7F 4B 45 52 4E 4F 00 0A`(`\x7fKERNO\0\n`)、版(主、副)、LEB128 の節の列で構成する。
   テキスト形式は S 式で、バイナリと 1 対 1 に往復する。
   仕様は `doc/IRSpec.md` に置き、プリミティブと組み込みインスタンスの表をデータとして載せる。
3. Diktor には、IR の書き出し(`--emit-ir`)、読み込み、参照用の IR 評価器(`--run-ir`)を足す。
   コード行で 2,700〜4,300 行と見込む(調査 樹 §5.2)。
4. RustKeleut は親リポジトリの `rustkeleut/` に cargo のワークスペースとして置く。
   主な crate は `kel-ir`、`kel-lir`、`kel-rt`、`kel-interp`、`kel-llvm`、`kel-jit`、`kel-wasm`、`kel-front`、`kel-cli`(バイナリ `keleut`)である。
5. 値は 64 ビットの語で表し、最下位ビットが 1 なら即値、0 ならポインタとする。
   単相の箇所の Int32、Int64、Float64 は箱に入れない。
   関数の戻り値だけは常に一様な語にする(末尾呼び出しの領域の保証を守るため。本計画 2.3 節)。
6. GC は動かさないマークスイープで、根はファイバーごとの値スタックから正確に得る。
   LLVM のステートポイントは使わない(LLVM 22.1.8 で `musttail` を壊す。調査 段 §5.4)。
7. すべての Keleut 関数と、インタプリタへの入口のスタブは、同じプロトタイプ `tailcc i64 (ptr ctx, ptr env, i64 x0, i64 x1, i64 x2, i64 x3)` を持つ。
   関数ごとの入口の表を 1 語書き換えて段を上げる。
   JIT からインタプリタへは `musttail`、インタプリタから JIT へは呼び出しとトランポリンで移る。
   OSR と逆最適化は作らない。
8. 巻き戻し(実行時エラー、継続の破棄、再開しない操作)は、戻り値の番兵 `0x2` と `ctx` の中の巻き戻しの記録で伝える。
   どの段のフレームも、番兵を受けたらそのまま返すだけでよい。
9. エフェクトは、ネイティブ(インタプリタと JIT)では、G の節を持つハンドラの本体だけをプールしたファイバーで走らせる。
   T の節はその場で呼び、N の節と継続の破棄は巻き戻しで実装する。
   WasmGC では、N と T と破棄を exnref で、G を JSPI のスタックで実装する。
   JSPI が要件を満たさなければ、G に届く関数だけを状態機械に変える yield bubbling に切り替える。
10. フロントエンドは、後段が Diktor の出す IR で動いた後に Rust へ移す。
    手書きの再帰下降で構文解析し、Diktor の cram を shim で流用し、IR のテキストの一致で突き合わせる。
11. マイルストーンは M79〜M95 の 17 個である。

## 2. 中間言語 Kerno

### 2.1 名前と位置づけ

**Kerno** は、型検査を終えたプログラムを、実行系が意味を変えずに実行できる形に表した言語である。
Diktor と RustKeleut のフロントエンドが書き出し、RustKeleut の 3 つの後段と Diktor の参照用の評価器が読む。
仕様は `doc/IRSpec.md` に日本語で書き、`doc/LangSpec.md` と同じく規範とする(D499)。

代案として、Diktor の精緻化木をそのまま直列化する案を考えた。
しかし、精緻化木は評価器が木の外から引く事実(インスタンスの頭、メソッドの辞書の位置、局所の名前)を含まず、同一性の値はプロセスの中でしか通用しない(調査 樹 §0 の 3 と 4)。
そのため、直列化だけでは RustKeleut が Diktor の表の計算を再実装することになり、採らない。

### 2.2 水準(D500)

Kerno は次の変換を済ませた水準とする。

| 変換 | 内容 | 根拠 |
| --- | --- | --- |
| 辞書渡しの明示 | 証拠(`EvParam`、`EvInst`、`EvRecord`、`EvVariant`)を、辞書の値の構築と辞書の引数に書き換える | 評価器は今、証拠を読んで辞書を作る(調査 前 §1.3)。後段ごとに書き直させない |
| 名前の解決 | 局所の名前を関数ごとの番号に、大域の名前を表の添字にする | Diktor の局所は文字列で引かれている(調査 樹 §2) |
| 演算子の除去 | `BinOp` と `Neg` をメソッドの呼び出しに、`&&`、`||`、`!` を `match` と組み込みに下ろす | §5.7 は演算子の適用を末尾呼び出しとして保証しないので、下ろしても意味は変わらない(調査 樹 §1.4) |
| A 正規形 | 演算の被演算子を変数か定数に限る | 評価順序(§5.1、名前付きのコンストラクタ引数は書いた順)を、命令の並びとして固定できる(調査 忠 §4) |
| 自由変数 | 無名関数が捕まえる変数(辞書を含む)を列挙する | Diktor のクロージャは環境の全体を捕まえている(調査 樹 §3) |
| インスタンスの頭とメソッドの辞書の位置 | 書き出す段で解決して書く | Diktor は実行時に `Decls` で引き直している(調査 樹 §2) |
| 数値リテラル | 型で読んだ値を定数にする。範囲外の字面は「評価したら実行時エラー」の命令にする | §4.2 は範囲外を評価時の実行時エラーと定める(調査 忠 §1) |
| `run` の除去 | 恒等なので消す | リージョンの安全性は型が保証する(調査 樹 §4.7) |

A 正規形にする代わりに、式の木を残す案もある。
木のほうが Diktor の書き出しは小さいが、RustKeleut の後段 3 つがそれぞれ評価順序と末尾位置を計算し直すことになる。
A 正規形への変換は 1 回の走査で済み、Diktor の側で 200〜300 行と見込む。
そこで A 正規形を採る。

### 2.3 型(D501、D502)

Kerno の変数と関数の引数は、次の**表現の型**を 1 つ持つ。

| 表現 | 中身 | 使う型 |
| --- | --- | --- |
| `bool` | 0 か 1 | Boolean |
| `i32` | 符号付き 32 ビット | Int32 |
| `i64` | 符号付き 64 ビット | Int64 |
| `f64` | IEEE 754 binary64 | Float64 |
| `w` | 一様な語(即値かヒープへの参照) | それ以外のすべて(型パラメータ、レコード、ヴァリアント、名目的な型、関数、文字列、辞書、Unit) |

表現の型は、Diktor のノードの型(`ty_field`)を `repr` した結果から決める(調査 樹 §3)。
単相で頭が Int32、Int64、Float64、Boolean の型だけが箱に入らない表現を持ち、型変数(`Generic`)を含む位置はすべて `w` である。
表現が異なる位置の間には、書き出す側が `box` と `unbox` の命令を明示的に入れる。

利用者の型の全体(行、エフェクト行、型スキーム)は、IR の意味には含めない。
省略してよいデバッグ用の節(本計画 2.8 節の節 12)に文字列として載せる。
全体を持つ案は、IR の検証器が行多相とスコープ付きラベルの型検査を再実装することになるので採らない。
検証器は表現の型の一貫性と構造だけを調べる(本計画 2.10 節)。

関数の戻り値の表現は常に `w` とする(D502)。
理由は末尾呼び出しの領域の保証である。
末尾呼び出し `f(x) = g(x)` で、`f` の戻り値が `i64`、多相な `g` の戻り値が `w` だと、`f` は `g` の結果を箱から出してから返すことになり、呼び出しが末尾でなくなる。
クロージャを通した呼び出しでも、一様な入口が戻り値を箱に入れる必要があり、同じ問題が起きる。
戻り値を常に `w` にすれば、この不一致は起きない。
費用は、Int64 と Float64 を返す関数の箱の割り当てである。
Int32、Boolean、Unit は即値なので割り当てない(本計画 4.4 節)。
箱に入らない戻り値の入口を足す最適化は台帳 V193 に残す。

引数は箱に入らない表現を持ってよい。
クロージャを通した呼び出しは常に `w` の引数で行い、後段は引数を箱から出して直接の入口へ `musttail` する一様な入口を関数ごとに作る。
この包みは末尾呼び出しを壊さない(戻り値に手を加えないため)。

### 2.4 項の形

関数の本体は**ブロック**であり、ブロックは束縛の列と 1 つの**終端**からなる。
終端の位置が、§5.7 の末尾位置にそのまま当たる。

- 束縛 `let x : rep = op` の右辺 `op` は、末尾でない計算である。
  入れ子のブロック `let x = block { … }` の中の終端は、そのブロックの値を返すだけで、関数の末尾にはならない。
- 終端は `ret a`、`tailcall f args`、`tailresume a`、`match`、`handle`、`fail kind` のどれかである。
  `match` と `handle` の枝のブロックは、その終端と同じ末尾性を受け継ぐ。

この形により、末尾呼び出しと末尾 `resume` の印は構文から読める(D510)。
Diktor は今、末尾位置の印を持たず、末尾 `resume` を起動のたびに `spine_has_resume` で調べている(調査 樹 §2、調査 効 R6)。
書き出す段で §5.7 の規則を 1 回たどって、末尾の呼び出しを `tailcall` に、末尾の `resume` を `tailresume` にする。
演算子から下ろしたメソッドの呼び出しは、末尾位置にあっても `tailcall` にしなくてよい(§5.7 が保証しない)。
書き出す側は、`tailcall` にしないことを選ぶ(Diktor の振る舞いと同じ)。

`op` の主な形を次に示す。
完全な一覧と符号は `doc/IRSpec.md` で定める。

| 分類 | 形 |
| --- | --- |
| 定数 | `const.bool`、`const.i32`、`const.i64`、`const.f64`、`const.str`(バイト列)、`const.unit` |
| 表現の変換 | `box.i32`、`box.i64`、`box.f64`、`box.bool`、`unbox.*` |
| 呼び出し | `call g args`(大域の関数)、`callc c args`(クロージャ。引数は `w`)、`prim p args`、`extern.c name args` |
| 大域 | `global.get g`(初期化の検査つき)、`dictapp g ds`(辞書を受け取る値を、使うたびに評価する) |
| 構築 | `ctor D.k [(field, a)…]`(書いた順に並べ、格納の位置を明示)、`variant l a`、`closure fid [captures]`、`closures [(x, fid, captures)…]`(let rec の群) |
| レコード | `rec.empty`、`rec.extend l a r`、`rec.select l n r`、`rec.update l r a`、`rec.restrict l r` |
| 辞書 | `dict.inst I [ds]`、`dict.record [(l, d)…]`、`dict.variant [(l, d)…]`、`method C.m d` |
| エフェクト | `perform op a`、`resume a`(G の節の中だけ) |
| 入れ子 | `block { … }` |
| 失敗 | `fail kind`(終端としても書ける) |

`fail` の種類は、`hole`(`???`、§5.6)、`lit_range`(範囲外のリテラル、§4.2)、`match`(どの節にも一致しない、§11.2)、`panic` である。
定数の畳み込みで `fail lit_range` を消したり前へ動かしたりしてはならない(D517)。

### 2.5 各機能の表し方

**辞書と型クラス(D503)。**
辞書は `w` の値である。
辞書を受け取る関数は、辞書を先頭の普通の引数として受け取る。
並びは Diktor の正準順(`Unify.constraints_of`、型を左から深さ優先にたどった順。調査 樹 §2)に従う。
`dict.inst I [ds]` は、インスタンス `I` に前提の辞書 `ds` を添えた辞書を作る。
`method C.m d` は、辞書 `d` からメソッドの値を取り出す。
取り出した値は、メソッド自身の辞書を受け取ってから普通の引数を受け取る関数である。
これは Diktor の `select_method` の並び(前提の辞書、次にメソッド自身の辞書)と同じである(調査 樹 §4.2)。
利用者のインスタンスは、宣言を実行した時点で初期化済みになるセルを持つ。
`method` は初期化済みでないインスタンスに対して実行時エラーを起こす(`inst.kel` の振る舞い。調査 忠 §8)。
検査を `dict.inst` ではなく `method` に置くのは、Diktor が辞書の構築ではなくメソッドの選択で誤りにするからである。
組み込みのインスタンス(Add Int32 など。メソッドの実装の表は Diktor で 44 行。調査 樹 §4.2、調査 忠 §13.4)は `doc/IRSpec.md` の表で番号を固定し、常に初期化済みとする。
閉じた行のレコードとヴァリアントの構造的な等値は、`dict.record` と `dict.variant` で、型の行の順にラベルと辞書を並べる(調査 樹 §2)。

**辞書を受け取る値と、使うたびの評価(D504)。**
制約付きで一般化した値束縛と式文(Diktor の `DAbs` 付きの値)は、大域の種類 `dictfun` にする。
`dictapp g ds` は使うたびに初期化式を評価する(§6.4、`peruse.kel`)。
Diktor の `VDictAbs.da_last` は、直前と物理的に同じ辞書の列で呼ばれたら前の結果を返す 1 件の記憶である(interp.ml:462-470 を読んで確かめた)。
初期化式はエフェクトを起こせないので、評価を省いても標準出力と終わり方は変わらない。
そこで IRSpec は「使うたびに評価する。ただし、同じ辞書の列に対する結果を記憶してよい」と書く。
最初の評価が実行時エラーで終わった場合は記憶しない(Diktor は例外を記憶しない)。

**レコードとスコープ付きラベル(D505)。**
IR はラベルで操作する命令のまま残す。
行多相があるので、フィールドの位置は一般には静的に決まらない(調査 樹 §3、調査 段 §2.2)。
`rec.select l n r` は、ラベル `l` の n 番目(0 が最も外側)のフィールドを選ぶ。
普通の選択は `n = 0` で、タプルの `t._N` は `_item` の `n = N` である(§8)。
`rec.restrict` は最も外側の 1 つだけを除き、`rec.update` は最も外側の位置を保って置き換える(§7.2、§7.3、調査 樹 §4.4)。
実行時の表し方は本計画 4.4 節で決める。

**構造的ヴァリアント(D506)。**
`variant l a` のラベル `l` はラベル表の添字である。
実行時の番号は読み込みの時点でプログラム全体で一意に振る(調査 忠 §4 の §9 の行)。

**名目的な型(D507)。**
コンストラクタはデータ型の表の中の番号で表す。
引数の無いコンストラクタは即値である。
フィールドの表現は宣言の型から決め、宣言の型が Int32、Int64、Float64、Boolean なら箱に入れない。
型パラメータのフィールドは `w` である。
コンストラクタは第一級の値ではない(`let f = Some` は型エラー。調査 樹 §7)ので、コンストラクタ関数は要らない。

**クロージャと自由変数(D508)。**
`closure fid [captures]` は平坦なクロージャを作る。
捕まえる変数には辞書の引数も含める。
`closures` は let rec の群をまとめて作り、互いの参照を埋めてから束縛する(Diktor §14.8 の 3 段のバックパッチに当たる)。
大域の let rec は大域の表を通して参照するので、`closures` を使わない(Diktor と同じ。調査 樹 §1.3)。

**パターン(D509)。**
`match` は節の列のまま残す。
節はパターン、省略できるガードのブロック、本体のブロックからなる。
パターンの形は `_`、変数、`bool`、`i32`、`i64`、`f64`、`str`、レコード(閉じる、開く、`...rest`)、コンストラクタ(フィールドの番号つき)、ヴァリアントの 10 種類で、Diktor の 9 種類から `PAnnot` を除き、数値を表現ごとに分けたものである(調査 樹 §1.2)。
数値のパターンは定数に確定させる(型検査の後は読めない字面が残らない。調査 樹 §1.2)。
`f64` のパターンの照合は IEEE の `==` とする(D509)。
したがって `0.0` のパターンは `-0.0` に一致し、NaN にはどのパターンも一致しない。
これは Diktor の interp.ml:163 が OCaml の `=` で比べている振る舞いと同じである(調査 忠 §7 が残した問いをここで閉じる)。
決定木は RustKeleut の `kel-lir` が 1 回だけ作り、3 つの後段で共有する。
ガードは書いた節の順に評価し、一致しない節のガードは評価しない(§11.2。決定木もこの順序を守る)。
決定木を IR に載せる案は、Diktor の書き出しを重くし、IR の版を最適化の都合で動かすので採らない。

**エフェクト(D511)。**
`handle` は終端で、次のものを持つ。
エフェクトの番号、本体のブロック、操作節の列、省略できる `return` 節、省略できる `cancel` 節。
操作節は、操作の番号、引数のパターン、ガード、本体、分類を持つ。
分類は調査 効 §6.0 の 3 種である。

- **N**: 再開しない操作(返り値の型が `Never`)の節。
- **T**: `resume` が `tailresume` としてだけ現れる節。`resume` の無い枝を含んでよい。
- **G**: それ以外。本体に `resume`(末尾でない)を含む。

書き出す側が分類を書き、検証器が構造から計算し直して一致を確かめる。
`resume` はアフィンで second-class なので、継続を値として表す形は IR に無い(§13.5)。
`perform op a` は束縛の右辺で、N の操作も同じ形である(値は返らない)。

**`resume(resume(x))` の観測(D512)。**
Diktor では、節の本体が `resume` そのものである短い経路だけ、外側の `resume` が引数の評価より先に継続を消費済みにする(調査 効 R1 の nest_short2 と nest_spine)。
Kerno は A 正規形なので、`resume` の引数が先に評価される(背骨の経路の振る舞い)。
§13.5 は 2 回目の再開を実行時エラーとだけ定め、評価順序は §5.1 に従うので、背骨の経路を正とする。
Diktor の短い経路を背骨の経路にそろえる修正を台帳 V191 に載せ、差分試験ではそれまで既知の差として扱う。

**リージョン(D513)。**
`run` は消し、`Heap` のエフェクトは実行時に何もしない。
`Ref`、`Array`、`MutableArray` の 11 の操作と `pinned` は `prim` にする(調査 忠 §13.2)。
`freeze` は写しを作る(Diktor と同じ)。
`Array.each` と `pinned` は利用者の関数を呼ぶので、後段はこれらを継続の捕獲に対応した形で実装する(本計画 4.9 節)。

**外部関数(D514)。**
`extern "prim"` は `doc/IRSpec.md` のプリミティブの表(48 個)の名前で引く。
`extern "C"` は名前を IR に残し、`sin`、`cos`、`sqrt`、`exp`、`log` 以外は**呼んだ時点で**実行時エラーにする(§17、調査 忠 §12)。
読み込みの時点で未解決の名前を誤りにしてはならない。

**モジュールと単位(D515)。**
1 つの Kerno のファイルは、プレリュードを含むプログラム全体の単位を、初期化の順に並べたもの(プログラムの像)とする。
単位の順は、起点から import をたどった帰りがけ順で、起点が最後である(§15.4、調査 樹 §6.1)。
module は平坦化の後の形で、修飾した名前だけを残す。
単位ごとに別のファイルにする分割コンパイルは台帳 V199 に残す。
バイナリの形式は単位の節を持つので、後で分割しても形式を変えずに済む。

**初期化の順(D516)。**
単位は `init` の文の列を持ち、宣言を書いた順に並べる。
文は `global.def g = block`、`instance.def I`、`exp block` の 3 種である。
大域のセルは未初期化の印を持ち、`global.get` は印を見て「未束縛の変数」の実行時エラーを起こす(`fwd.kel`。調査 忠 §10)。
関数の大域も、宣言を実行するまでは未初期化である。
後段は、初期化がすべて済んだ後に検査を省いてよい(省けるのは、未初期化を観測できる時点が初期化の途中に限られるため)。

### 2.6 安定した名前(D518)

Diktor の oid、`GDecl` の束縛ノードの oid、穴の `h_id` は、プロセスの中でしか通用しない(調査 樹 §0 の 4)。
Kerno の名前は次の規則で作る。

- 単位の鍵: プレリュードは `prelude`、起点は `main`、それ以外は起点のディレクトリからの相対パス(区切りは `/`)。
- 大域の鍵: `単位の鍵#宣言の序数.名前`。
  宣言の序数は単位の中の宣言の位置(0 から)で、同名の再束縛を区別する。
  module の中の宣言は `M.T` の修飾した名前を使う。
- 型、コンストラクタ、エフェクト、操作、クラス: 単位の鍵と修飾した名前。
  Diktor の `%N.` の印(調査 樹 §6.2)は、単位の番号が import の順で変わるので使わない。
- ラベル: 綴りそのもの。
- 局所の変数: 関数の中の番号。
  名前はデバッグ用の節にだけ載せる。

書き出しは決定的でなければならない。
同じ入力から、プロセスが違っても同じバイト列を出す(本計画 6 節の試験 C1)。

### 2.7 テキスト形式(D520)

テキスト形式は S 式で、拡張子は `.kerno.txt` とする。
バイナリと 1 対 1 に往復し、`keleut ir dump` と `diktor --emit-ir=text` が同じ文字列を出す。
例を示す。

```text
(kerno 1 0
  (unit main
    (func main#0.loop (params (n i32) (acc i64)) (ret w)
      (let c bool (prim __int32_eq n (const.i32 0)))
      (match c
        (case (pbool true) (let r w (box.i64 acc)) (ret r))
        (case (pbool false)
          (let n1 i32 (prim __int32_sub n (const.i32 1)))
          (let a1 i64 (prim __int64_add acc (const.i64 1)))
          (tailcall (global main#0.loop) n1 a1))))
    (init
      (global.def main#0.loop (closure main#0.loop))
      (exp (let v w (call (global main#0.loop) (const.i32 10000000) (const.i64 0))) ...))))
```

テキスト形式は、cram の期待値と、Diktor と RustKeleut の出力の比較に使う。

### 2.8 バイナリ形式(D519)

ファイルの先頭は次のとおりである。

| 位置 | 大きさ | 内容 |
| --- | --- | --- |
| 0 | 8 | マジック `7F 4B 45 52 4E 4F 00 0A` |
| 8 | 2 | 主版(リトルエンディアンの u16) |
| 10 | 2 | 副版(u16) |
| 12 | 4 | 旗(u32。ビット 0 はデバッグの節を含むこと。ほかは 0) |
| 16 | — | 節の列 |

節は `id: u8`、`len: uleb128`、`payload` の 3 つ組である。
節の番号は昇順に 1 回ずつ現れ、番号 0(独自の節)だけはどこに何回現れてもよい。
数は、符号なしを ULEB128、符号付きを SLEB128 で書く(Wasm と同じ規則で、最長の符号化を超えたら誤り)。
`f64` は 8 バイトのリトルエンディアンで、NaN のビット列もそのまま保つ。

| 番号 | 節 | 内容 |
| --- | --- | --- |
| 1 | strings | 文字列の表。個数、各要素は長さとバイト列。0 番は空文字列。UTF-8 である必要はない(§4.4) |
| 2 | labels | ラベルの表(文字列の添字の列) |
| 3 | datas | 名目的な型。名前、型パラメータの数、コンストラクタの列(名前、フィールドの名前と表現) |
| 4 | effects | エフェクトと操作。操作の名前、引数の数、`Never` の印 |
| 5 | classes | クラスとメソッドの名前、メソッド自身の辞書の数 |
| 6 | instances | 利用者のインスタンス。クラス、頭の型、前提の辞書の数、メソッドの実装(大域の添字) |
| 7 | globals | 大域の表。種類(`value`、`func`、`dictfun`、`prim`、`extern_c`)、鍵、辞書の数 |
| 8 | prims | このファイルが使うプリミティブの名前。読み込む側は IRSpec の表と照合する |
| 9 | funcs | 関数の本体。引数と捕まえる変数の表現、局所の数、本体のブロック |
| 10 | units | 単位の列(初期化の順)と、それぞれの `init` の文の列 |
| 11 | srcmap | 省略できる。命令から位置(ファイル、行、桁)への対応 |
| 12 | debug | 省略できる。局所の名前と、大域の型の表示 |

命令は 1 バイトの命令の番号に、決まった並びの被演算子を続けて書く。
変数は関数の中の番号(ULEB128)、文字列とラベルは表の添字である。

**互換性の方針。**
主版が違うファイルは読まない。
副版が新しいファイルは、知らない命令か知らない節(0 以外)があれば「版が新しすぎます」で拒む。
副版を上げるのは、命令や節を足すときだけである。
命令の意味を変えるとき、番号を詰めるとき、節の中身の並びを変えるときは、主版を上げる。
番号 11 と 12 の節は読み飛ばしてよい。
版 1.0 を M79 で凍結し、それまでは主版 0 として自由に変える。

### 2.9 実行時の規約として IR に書くこと

IRSpec は、意味を次の抽象機械で定める(本計画 4.9 節の実装はすべてこの機械に従う)。

- 評価は値を返すか、**巻き戻し**で終わる。
  巻き戻しの種類は、実行時エラー、宛先つきの値(継続の破棄)、宛先つきの節の本体(再開しない操作)の 3 つで、Diktor の `Runtime_error` と `Unwind (inst, UValue v | UClause f)` に当たる(調査 効 R2〜R4)。
- ハンドラの起動ごとに、単調に増える 64 ビットの番号を振る(調査 効 R8)。
- 操作節の選択、3 つの経路と自分の `cancel` 節の有無、`cancel` 節の中の脱出の抑制と記録は、調査 効 §5 の要件 Q1〜Q10 をそのまま規範の文にする。
- 自分の `cancel` 節の規則は次の 1 文で書く。
  本体の側から届いた巻き戻しがそのハンドラの起動を宛先としていなければ、そのハンドラの `cancel` 節を 1 回走らせる。
  G の節を評価している間に、継続を消費する前に誤りが起きた場合は、継続を破棄してから自分の `cancel` 節を走らせ、消費した後なら走らせない(本計画 4.9 節)。
- `Console.write` は実行系が処理する唯一の操作で、利用者は `handle` できない(調査 効 R9)。

### 2.10 検証器

RustKeleut の `kel-ir` は、読み込んだファイルを実行の前に検証する。
調べるのは、変数の有効範囲、表現の型の一貫性(`prim` の引数、`box` と `unbox`、フィールドの表現)、引数の数、辞書の数、`tailcall` と `tailresume` が終端の位置にあること、`resume` が G の節の中にしか無いこと、節の分類、`init` の文の形、表の添字の範囲である。
検証に通らないファイルは終了状態 65 で拒む(I。Diktor に IR を読ませた場合も同じ値にする)。
検証器は型の健全性を保証しない。
信頼の根は、型検査を済ませたフロントエンドである。

文芸的な注釈を含めると 6,000〜9,300 行になる。
書き出しを差し込む位置は、driver.ml の `run_with` の中の `type_check_files` と `Interp.run_units` の間である(調査 樹 §5.1)。
ここでは Decls の表がそろっているので、インスタンスの頭とメソッドの辞書の位置を計算できる。

### 3.2 参照用の評価器を Diktor に持たせる理由

持たせない案では、Diktor は書き出すだけになり、1,300 行ほど少なく済む。
しかし、その場合は RustKeleut ができるまで IR の意味を試験できず、IR の誤りと RustKeleut の誤りを分けられない。
持たせれば、Diktor の既存の cram 全体を、木の評価器と IR の評価器の 2 通りで走らせて比べられる(本計画 3.3 節)。
そこで持たせる(D521、P234)。

### 3.3 cram との結合

- `test/smoke.t` は `usage` の全文を期待値に持つので、旗を足すコミットとは別のコミットで期待値を更新する(調査 樹 §5.1)。
- `test/kerno_emit.t`: 小さなプログラムのテキスト形式を固定する(20〜40 ブロック)。
- `test/kerno_run.t`: `--emit-ir=bin -o p.kerno` の後に `--run-ir p.kerno` を走らせ、出力と終了状態を固定する。
  効果の難所(never_ops.t の cancelresume の系列、tail_calls.t の retry の系列)を最初から入れる。
- 環境変数 `DIKTOR_EXEC=ir` を足す。
  これが立っていると、実行のモードは型検査の後に IR へ下ろし、バイナリに書いてから読み直し、IR の評価器で実行する。
  `DIKTOR_EXEC=ir dune runtest` で既存の cram を IR の経路で走らせ、差分が V191 の既知の差だけであることを M81 の受け入れ条件にする。

## 4. RustKeleut の構成

### 4.1 ディレクトリと crate(D522)

```text

  crates/
    kel-ir/             Kerno の型、バイナリとテキストの読み書き、検証器
    kel-lir/            下位の IR。決定木、クロージャの配置、表現の確定、スロットの割り当て

    kel-rt-core/        no_std。show_f64 と数値の検査。kel-rt と試験が使う
    kel-interp/         バイトコードの生成とインタプリタ
    kel-llvm/           llvm-sys 221 の薄い安全な包み(LLJIT、IRBuilder、絶対記号)
    kel-jit/            LIR から LLVM IR への生成、段の切り替え、翻訳のスレッド

  runtime/

```

`kel-llvm` と `kel-jit` は cargo の feature `llvm` の下に置き、`llvm-config` の無い環境でもインタプリタと WasmGC だけで組めるようにする(試作 L の示唆)。
`kel-wasm` は feature `wasm` の下に置く。
既定ではどちらも有効にする。
親リポジトリに置き、サブモジュールにしない。
親と別に版を進める必要が無く、IRSpec と同じコミットで変えられるからである(P233)。

### 4.2 コマンド `keleut`(D523)

| 形 | 動作 |
| --- | --- |
| `keleut run [opts] FILE.kel…` | 型検査し、IR に下ろし、実行する(フロントエンドの移植の後。M93) |
| `keleut run [opts] FILE.kerno` | IR を読んで実行する(M84 から) |
| `keleut check FILE.kel…` | 型検査だけ。Diktor の `--type-check` と同じ出力 |
| `keleut ir emit [--text] -o OUT FILE.kel…` | IR を書き出す |
| `keleut ir dump FILE.kerno` | テキスト形式で印字する |
| `keleut ir verify FILE.kerno` | 検証だけ行う |
| `keleut wasm -o DIR FILE.kerno` | `DIR/main.wasm` と `DIR/kel_rt.mjs` を書き出す |
| `keleut tokens FILE.kel`、`keleut ast FILE.kel` | Diktor の `--dump-tokens` と `--dump-ast` と同じ形式 |
| `keleut repl` | 対話的な実行(M94) |

`run` の主な選択肢は次のとおりである。

- `--backend=native|wasm`(既定 `native`)。
- `--tier=auto|interp|jit|alternate[:SEED]`(既定 `auto`)。
- `--jit-threshold=N`(既定 1000。P240)。
- `--depth-limit=N`(本計画 4.4 節の決定的な深さの限度)。
- `--stack-size=BYTES`(主スタックの大きさ。既定 1 GiB)。
- `--strict-exhaustive`、`--prelude FILE`、`--no-prelude`、`--import-path DIR`(Diktor と同じ)。

試験で使う shim `diktor` は、Diktor の旗をこの形に書き換えて `keleut` を呼ぶ(本計画 6 節)。

### 4.3 読み込み

`kel-ir` はファイル全体を読み、検証してから、文字列とラベルを実行時の表に intern する。
関数の本体はこの時点ではバイトコードにしない。
関数を初めて呼んだときに LIR とバイトコードを作る(本計画 4.5 節)。
読み込みの費用を関数の数ではなく実際に走る関数の数に比例させるためである。

### 4.4 実行時(`kel-rt`)

**値の表現(D524)。**
一様な語 `w` は 64 ビットである。

- 最下位ビットが 1: 即値。
  Int32 は `(n << 1) | 1`、Boolean は 1 と 3、Unit は 1(Int32 の 0 と同じビット列でよい。型が混ざらないため)、引数の無いコンストラクタは `(番号 << 1) | 1`。
- 最下位 3 ビットが 0: ヒープへのポインタ(8 バイト境界)。
- `0x2`: 巻き戻しの番兵。
  値としては現れず、戻り値の位置にだけ使う(本計画 4.4 節の実行時エラー)。

Int64 と Float64 は、`w` の位置に置くときだけ箱に入れる。
NaN ボックス化は採らない。
Int64 はどちらの方式でも箱に入るので得が小さく、WasmGC の表現との差が大きくなるからである(調査 段 §2.2)。

ヒープのオブジェクトは 1 語の頭部を持つ。
頭部は、種類(8 ビット)、GC の印(8 ビット)、配置の番号(16 ビット)、大きさ(32 ビット)である。
種類は、レコード、コンストラクタ、ヴァリアント、クロージャ、文字列、Int64 の箱、Float64 の箱、`Ref`、`Array`、`MutableArray`、辞書、継続、形の記述子である。

- **レコード**: 形の記述子へのポインタと、`w` のフィールドの列。
  形は、ラベルの番号の昇順に並べ、同じラベルの重複は外側から順に並べた列で、プログラムの中で intern する。
  §18.3 によりラベルの順序は結果に効かないので、この正準の配置でよい。
  閉じた行で形が静的に決まる箇所では、`kel-lir` が位置を定数にする。
  開いた行の箇所は、呼び出し箇所ごとのインラインキャッシュ(形のポインタと位置の組)で引く。
  インタプリタと JIT は同じキャッシュの形を使う。
- **コンストラクタ**: 頭部の配置の番号が (データ型、コンストラクタ) を指し、フィールドは宣言の型が単相のプリミティブなら生の値、そうでなければ `w` である。
  GC は配置の番号から、どのフィールドが `w` かを引く。
- **ヴァリアント**: ラベルの番号とペイロード(`w`)。
  ペイロードが Unit のものは読み込みの時点でラベルごとに 1 つ作って使い回す。
- **クロージャ**: 関数の番号、捕まえた値の列。
  大域の関数には、読み込みの時点で作った静的なクロージャを使う。

**GC(D525)。**
v1 は、動かさないマークスイープを 1 スレッドで、全体を止めて行う。
大きさの種類ごとのページに分け、空きリストで割り当てる。
根は次の 4 つである。

1. すべてのファイバーの値スタック(走っているものも、継続として止まっているものも)。
2. 大域の表とインスタンスの表。
3. ハンドラの記録(値スタックの上のハンドラのフレームにある)。
4. Rust のコードが一時的に持つ値の枠(`Root<'_>` の型で、値スタックに積む)。

安全点は割り当てだけにする。
Keleut には反復の構文が無いので、後ろ向きの枝の検査は要らない(調査 段 §5.1)。
ネイティブのスタックを保守的に走査する案は採らない。
箱に入れない Int64 と Float64 がポインタに見えて誤って保持すること、内部ポインタの判定が要ること、動かす GC へ移れなくなることが理由である(調査 段 §5.2)。
LLVM のステートポイントも採らない(E7)。
書き込みの障壁が要る箇所は `Ref.set`、`MutableArray.set`、let rec の群の環境の埋め込みの 3 つだけなので、世代別 GC(台帳 V207)へは後で移れる。
参照カウント(Perceus)は v1 では採らず、追跡型の GC と比べる試作を台帳 V195 に残す(P239)。

**文字列(D526)。**
文字列は、長さ(u32)とバイト列を持つ不変のオブジェクトである。
UTF-8 である必要はなく、NUL を含んでよい(§4.4)。
比較は符号なしバイトの辞書順で、`memcmp` と長さで比べる。
リテラルは読み込みの時点で GC の外の静的な領域に置き、頭部の印で GC の対象から外す。
長さが 2^31 - 1 バイトを超える文字列を作ろうとしたら、処理系の限度として実行時エラーにする(`__string_length` の型が Int32 のため)。

**Float64 の表示(D527)。**
`kel-rt-core::show_f64` は §16.2 の 3 規則を実装する。
有効数字 `p` を 1 から 17 まで増やし、`format!("{:.*e}", p - 1, x)` を読み戻して元の値に戻る最初の `p` を使う。
この探索は glibc の `%.*g` と 2,000,000 件で一致した(E16)。
`-0.0` は `-0.0`、NaN は符号なしの `nan` にする。
2,000,000 件の試験の入力と期待値(Diktor の出力)を `kel-rt-core` の試験に入れる。

**数値の検査(D529)。**
整数の `+ - *` と符号反転は折り返す(Rust の `wrapping_*`。LLVM では `nsw` を付けない)。
除算と剰余は、ゼロの検査と `MIN / -1` の分岐を、`sdiv`、`srem`、`i32.div_s`、`i32.rem_s` の前に置く。
`MIN / -1` は `MIN`、`MIN % -1` は `0` である。
`__f64_to_i32` と `__f64_to_i64` は、NaN、無限大、範囲外(`t >= -2^31 && t < 2^31`、上端は開区間)の検査を変換の前に置く。
Rust の `as` は飽和し、LLVM の `fptosi` は範囲外で poison になるので、検査を省いてはならない(調査 忠 §1)。

**外部関数 `extern "C"`(D528)。**
ネイティブの後段は `sin`、`cos`、`exp`、`log` を Rust の `libm` crate(musl の移植)で計算し、システムの libm と LLVM の組み込み関数を使わない。
LLVM が `llvm.sin` などに置き換えないよう、呼び出しは実行時の関数への普通の呼び出しにする。
`sqrt` は IEEE で正しく丸めるので、`llvm.sqrt` を使ってよい。
WasmGC は本計画 4.10 節で扱う。

**スタックの限度(D530)。**
§15.5 は、評価に要する領域が限度を超えたら実行時エラーとし、`cancel` 節を走らせて終了状態 3 にすると定める。
限度の大きさは処理系が決めてよい(I)。

- プログラムは、ガードページ付きで 1 GiB を予約した主ファイバーの上で走らせる(`--stack-size` で変える)。
  Diktor が 100 万段の非末尾再帰を通す(調査 忠 §5)ので、それより浅い限度にはしない。
- JIT の関数は入口で、ネイティブのスタックポインタと、ファイバーの値スタックの先頭を、`ctx` の限度と比べる。
  超えたら実行時エラーを起こして番兵を返す。
- インタプリタはフレームを積むときに値スタックの限度を、ネイティブの入れ子(JIT を呼ぶたびに深くなる)のときにスタックポインタを調べる。
- 限度は予備の 256 KiB を残した位置に置く。
  スタックあふれの巻き戻しの間だけ予備を使えるようにして、`cancel` 節を走らせる余地を作る(調査 効 R7)。
  予備も溢れたら、その `cancel` 節の打ち切りとして記録する。
- `--depth-limit=N` を指定すると、インタプリタ、JIT、WasmGC のどれも、末尾でない Keleut の呼び出しの深さを数え、N を超えたら実行時エラーにする。
  これは試験のための決定的な限度で、後段によって結果(0 か 3)が分かれないようにする(本計画 6 節)。
  既定では JIT は数えない(入口の 1 回の比較だけにするため)。

**実行時エラーと巻き戻し(D531)。**
巻き戻しを始める側は、`ctx.unwind` に種類(実行時エラー、宛先つきの値、宛先つきの節、書き出しの失敗)と、宛先のハンドラの起動の番号と、ペイロードを書き、番兵 `0x2` を返す。
呼び出し元は、末尾でない呼び出しの後に戻り値を `0x2` と比べ、一致したら自分も `0x2` を返す。
JIT では `cmp rax, 2; je` の 1 組で、`ctx` を読み直さない。
戻り値を常に `w` にした(D502)ので、`0x2` は値と衝突しない。
後始末を持つのはハンドラのフレームだけである(本計画 4.9 節)。
メモリは GC が回収するので、ほかのフレームは何もしない。

代案として、LLVM の例外表(`landingpad`)と Rust の `panic` で巻き戻す案を考えた。
正常な経路の費用は 0 だが、DWARF の巻き戻しは 1 回に数 µs かかり、再開しない操作を反復に使うプログラム(retry.kel の 10 万回)で遅くなる。
また、`extern "C-unwind"` と JIT の巻き戻し情報の登録を、インタプリタとの境目ごとに正しく保つ必要がある。
比較 1 回の費用は分岐予測が当たれば 1 サイクル程度で、段の境目に特別な規則が要らないので、番兵を採る。
`setjmp` と `longjmp` で飛ぶ案は、Rust のフレームを飛び越えることになるので採らない。

最も外側では、実行時エラーの記録を受けたら、標準出力を書き出してから標準エラーに診断を書き、終了状態 3 で終わる。
書き出しの失敗は終了状態 74、未実装の機能は 4、使い方の誤りは 64 で、Diktor と同じ値にする(I。cram を流用するため。P247)。

**Console(D549)。**
`Console.write` は実行時の組み込みで、T の節と同じくその場で呼ぶ。
標準出力は 64 KiB でバッファし、標準エラーへ書く前と終了の前に必ず書き出す(§15.5、調査 効 R9)。
書き出しに失敗したら、巻き戻しの種類「書き出しの失敗」で `cancel` 節を走らせ、終了状態 74 で終わる(eval.t の sinkfail.kel)。

### 4.5 下位の IR とバイトコード(D532)

Kerno のバイナリはバイトコードではない。
Kerno は Diktor と共有する安定した形式で、バイトコードは RustKeleut の内部の形式で、版の約束を持たない。
`kel-lir` は Kerno の関数を次の順に下ろす。

1. `match` を決定木にする(ガードの順序を守る)。
2. レコードの操作のうち形が静的に決まるものを、位置の定数にする。
3. クロージャの捕獲の配置と、一様な入口の包みを作る。
4. 操作節を、節の選択の関数と本体の関数に分ける(本計画 4.9 節)。
5. スロットを割り当てる。
   スロットは関数の中で表現が 1 つに決まり、GC 用に「`w` のスロットの集合」を関数ごとに持つ。

バイトコードはこの LIR から作るレジスタ機械の命令列である。
命令は 32 ビットの固定長で、命令の番号 8 ビットと被演算子(A 8 ビット、B と C 8 ビットずつ、または Bx 16 ビット)からなる。
スロットが 256 を超える関数は、被演算子を後続の 32 ビットに置く wide 形を使う。
Lua 5 と同じ形で、命令の数が少なく、命令の取り出しが単純である。
スタック機械の案は、命令の数が多くなり、Rust の `match` による振り分けの回数が増えるので採らない。

### 4.6 インタプリタ(D533)

インタプリタは Rust の平坦なループと `match` である。
安定版の Rust では `become` も計算 goto も使えない(E10)ので、命令ごとの振り分けは `match` の飛び先の表になる。
フレームはファイバーの値スタックに置き、頭部(前のフレーム、関数の番号、戻り先の命令の位置、戻り値を書くスロット)とスロットの列からなる。

- 呼び出し先がインタプリタの関数なら、ネイティブの再帰をせずにフレームを積んでループを続ける。
- 自己と相互の末尾呼び出しは、フレームを再利用してループの先頭へ戻る。
- 呼び出し先が JIT のコードなら、ネイティブの呼び出しをする(本計画 4.8 節)。
- `0x2` の戻り(または自分で起こした巻き戻し)を受けたら、ハンドラのフレームに当たるまでフレームを外す。

### 4.7 LLVM ORCv2 の後段

**包み(D534)。**
`kel-llvm` は llvm-sys 221.1.1(`prefer-dynamic`)を直接包む。
inkwell 0.11.0 は LLJIT を包まず(MCJIT と旧 ORCv1 だけ)、模塊の所有権の受け渡しが ORC と衝突する(試作 L)。
LLVM 21 以降の C API には `LLVMOrcThreadSafeContextGetContext` が無いので、`LLVMContextCreate` で作った文脈を `LLVMOrcCreateNewThreadSafeContextFromLLVMContext` で包む(試作 L)。
実行時の関数(割り当て、巻き戻しの開始、`perform`、ファイバーの操作)は、`LLVMOrcAbsoluteSymbols` で絶対記号として登録する(試作 L の callback)。

**呼び出し規約(D535)。**
すべての Keleut 関数とインタプリタへの入口のスタブは、次のプロトタイプを持つ。

```llvm
tailcc i64 @f(ptr %ctx, ptr %env, i64 %x0, i64 %x1, i64 %x2, i64 %x3)
```

`env` はクロージャへのポインタで、大域の関数には静的なクロージャを渡す。
引数は 4 個までをレジスタで渡し、5 個目からは `ctx.xargs[]` に置く(呼び出された側は入口で読む)。
`f64` の引数は `bitcast` で `i64` にして渡す。
戻り値は 1 語の `w` である。
試作の 2 語の構造体の戻り値は SysV の ABI に頼った書き方なので、規約にしない(調査 段 §3.3)。
全関数が同じプロトタイプなので、どこからでも `musttail` で呼べる(E2、E4)。
`ctx` と `env` と 4 つの引数が x86-64 の引数のレジスタ 6 つに収まると見込むが、試作が確かめたのは 8 引数の `musttail` が検証を通ることだけで(E4)、レジスタの割り当ては確かめていない。
M87 の測り直しで、`llc -O2` の出力を見て確かめる。

代案は、調査 段 §3.2 の `tailcc i64 (ptr ctx)` で、引数をすべて値スタックに置く形である。
交互の末尾呼び出しを測ったのはこの形である(E6)。
本計画はネイティブの性能を優先してレジスタで渡す形を採るが、同じ測定をこの形でやり直すことを M87 の最初の作業にし、通らなければ値スタックの形に戻す(D535 の条件)。

インタプリタへの入口のスタブは、Rust の `extern "C"` にできない。
`tailcc` から `ccc` への `musttail` は検証器が拒むからである(E3)。
スタブは起動のときに小さな LLVM の模塊として作る。
スタブは `env` から関数の番号を読み、Rust の `kel_interp_enter(ctx, env, args…)` を普通に呼ぶ。

**GC の根(D525 の続き)。**
JIT の関数は入口で値スタックに自分の退避の領域を確保し、割り当てを起こしうる呼び出しをまたいで生きている `w` の値を、その領域に書く。
ここでの「割り当てを起こしうる呼び出し」には、`perform` と、ファイバーを切り替えうる実行時の関数をすべて含める。
このフレームが止まっている間に、ほかのファイバーが GC を起こすからである。
退避するのは `w` の値だけである。
`w` は即値かポインタかを最下位ビットで見分けられるので、退避の領域は配置の表なしで正確に走査できる。
GC は動かさないので、呼び出しの後に読み直さない。
JIT の出口(戻りと `musttail` の前)で値スタックの先頭を戻す。
`gc "shadow-stack"` は鎖を 1 フレームずつつなぐ費用があり、Rust の値スタックと 2 本の根の仕組みになるので使わない(E8 は代案として動くことだけを確かめた)。

**翻訳(D536 の一部)。**
関数ごとに 1 つの模塊を作る(相互再帰の群は 1 つにまとめる)。
最適化は `default<O2>` とする。
1 関数の費用は約 1.96 ms で、最適化なしの約 0.90 ms の 2 倍だが、翻訳は別のスレッドで行うのでインタプリタを止めない(E1)。

### 4.8 段の切り替え(D536、D537)

**入口の表。**
`ctx.entry[fid]` は関数ごとに 1 語の入口で、最初はインタプリタへの入口のスタブを指す。
翻訳が済んだら、原子的な 1 回の書き込みで JIT のコードを指すように書き換える(E5)。
JIT のコードから別の関数への呼び出しも、この表を通す。
ORC の遅延再輸出(`LLVMOrcLazyReexports`)と間接スタブの管理器は使わない。
自前の表のほうが、インタプリタも同じ表を読めるので単純である(調査 段 §3.2)。

**数え方と閾値。**
インタプリタは関数の入口で `ctx.counter[fid]` を 1 増やし、`--jit-threshold`(既定 1000)に達したら翻訳のスレッドの待ち行列に積む。
自己の末尾呼び出しでフレームを再利用する場合も入口として数える。
そのため、1 回の呼び出しの中で末尾再帰が長く回る関数も段が上がる。
既定の 1000 は根拠のない初期値で、M88 でインタプリタの速さと翻訳の費用(E1)を測って決める(P240)。

**インタプリタから JIT へ。**
インタプリタは呼び出しの命令で `entry[fid]` を読み、スタブでなければネイティブの関数を普通に呼ぶ。
末尾呼び出しの場合は次のように分ける。

- 呼び出し元がインタプリタのこの起動の最も下のフレームなら、`kel_interp_enter` は「この入口へ末尾呼び出しせよ」という要求を返す。
  呼び出し元のスタブ(JIT から入った場合)はそれを `musttail` で呼び、最上位の駆動ループ(主ファイバーの底から入った場合)はトランポリンとして呼ぶ。
- それ以外の場合は、フレームを外してから JIT の関数を普通に呼び、結果を外したフレームの呼び出し元へ返す。
  この呼び出しは、その先で再びインタプリタに入ったときに最も下のフレームになるので、交互の末尾呼び出しでもネイティブのスタックは 1 段しか伸びない。

**JIT からインタプリタへ。**
JIT のコードは `entry[fid]` を `musttail` で呼ぶだけで、相手がスタブでも JIT のコードでも同じである。
この組み合わせで、交互の末尾呼び出しが一定のスタックで走ることを測った(E6)。

**OSR と逆最適化(D537)。**
作らない。
JIT は投機をしないので逆最適化は要らない。
反復は必ず関数の入口を通るので、関数単位の切り替えで足りる(調査 段 §3.6)。

**ファイバーとの関係。**
インタプリタも JIT もネイティブのスタックの上で走るので、ファイバーはどちらのフレームを積んでいるかを区別しない。
G のハンドラの継続には、インタプリタのフレームと JIT のフレームが混ざってよい。
段を上げても、止まっている継続の中の古いフレームはそのまま動く(入口の表を次に通ったときに新しいコードへ移る)。

### 4.9 エフェクトの実装(D538、D539)

**静的な分類。**
本計画 2.5 節の N、T、G をそのまま使う。

| 分類 | ネイティブ(インタプリタと JIT) | WasmGC |
| --- | --- | --- |
| N | `perform` の位置でガードを評価してから、宛先つきの節の巻き戻しを起こす。ハンドラのフレームが受けて、本体を末尾で呼ぶ | 例外の tag で投げ、ハンドラの `try_table` で受けて `return_call` |
| T | `perform` の位置で節を普通の関数として呼ぶ。`tailresume v` は節の関数が `v` を返すこと。`resume` の無い枝は宛先つきの値の巻き戻し | 同じ(例外で巻き戻す) |
| G | ハンドラの本体をファイバーで走らせ、`perform` は親のファイバーへ切り替える | JSPI のスタック(本計画 4.10 節) |

1 つのハンドラに分類の違う節が混ざってよい。
ファイバーを立てるのは G の節を 1 つでも持つハンドラだけで、そのハンドラでも T と N の節はその場で処理する。
tail_calls.t が一定の領域を要求する形はすべて T か N であり、G の形は仕様が領域を保証しない(調査 効 §6.0)。
したがって、ファイバーを立てる範囲と仕様の保証の境界が一致する。

**ハンドラのフレーム。**
`handle` の終端は、値スタックにハンドラの記録を積む。
記録は、起動の番号、エフェクトの番号、節の選択の関数と捕まえた値、`cancel` 節、親の記録、ファイバーを持つかどうかである。
`ctx.handler_top` は最も内側の記録を指し、`perform` はここから同じエフェクトの記録を探す。
1 回の探索はハンドラの入れ子の深さに比例するが、普通は数段である。
探索の結果を `perform` の位置で記憶する最適化は台帳 V205 に残す。

**T の節の罠。**
T の節はその場で呼ぶが、節を評価している間はハンドラの継続がまだ生きている。
節の中で実行時エラーが起きたとき、または節の中の操作で外側のハンドラが継続を破棄したときは、`perform` の位置からハンドラまでの間のハンドラの `cancel` 節を内側から走らせ、その後にそのハンドラ自身の `cancel` 節を走らせる(§13.6、調査 効 R3 の clauseerr と clausestop、調査 段 §6.3)。
その場で呼ぶ方式では、巻き戻しが節のフレームから `perform` の位置へ戻り、そこから間のハンドラのフレームを通ってハンドラのフレームに着く。
節のフレームは物理的にはハンドラの本体の呼び出しの内側にあるので、次の 1 つの規則で足りる。

> 本体の側から(ハンドラのフレームか、G のハンドラの本体のファイバーの底に)届いた巻き戻しが、このハンドラの起動を宛先としていなければ、このハンドラの `cancel` 節を 1 回走らせてから巻き戻しを続ける。
> 宛先がこのハンドラの起動なら(T の節の `resume` しない値、N の節の本体)、`cancel` 節を走らせずに受け取る。

これは Diktor の `exnc` が行っていることと同じで(調査 効 R2、R3)、本体の中の普通の実行時エラー(so.kel の `cancel ran`。調査 効 R7)、その場で呼んだ T の節の中の誤り(clauseerr)、外側のハンドラによる破棄の通過(clausestop)を同じ規則で扱う。
節が評価中かどうかの印は要らない。
G の節を親の側で評価している間の誤りは、この規則とは別の経路で扱う(下の「G のハンドラ」)。
節を選ぶ間(パターンとガード)と節を評価する間は、`ctx.handler_top` をそのハンドラの親に付け替え、節の中の操作が外側へ届くようにする(§13.4)。
巻き戻しが `perform` の位置を通るときに `ctx.handler_top` を元へ戻す。

**G のハンドラ。**
OCaml 5 と同じ形にする(調査 効 §3)。

- ハンドラの本体を新しいファイバーで走らせる。
  ファイバーは親(最後にこのファイバーへ切り替えた側)を覚える。
- G の節に当たる `perform` は、本体のファイバーからハンドラの親のファイバーへ、途中のファイバーの鎖ごと止めて切り替える。
  親の側で待っている位置(`handle` の位置か、前の節の中の `resume`)が、節を選んで評価する。
- `resume v` は継続の鎖の先頭へ切り替え、`perform` の位置に `v` を返す。
  継続は使用済みの印を持ち、2 回目の `resume` は実行時エラーにする(Q1)。
- 本体のファイバーが値を返したら、親の待っている位置へ戻り、`return` 節を親の側で評価する。
- 節が `resume` せずに値を返したら、止まっている継続へ宛先つきの値の巻き戻しを送り込み、継続の中の `cancel` 節を内側から走らせてから、待っている位置の値にする(Q2)。
- 節の中で `resume` の前に実行時エラーが起きたら、継続へその誤りの巻き戻しを送り込み、次に自分の `cancel` 節を走らせる。
  これで `preresume.kel` の順序(節の中、継続の中、自分、外側)になる(調査 忠 §6.1)。
- `cancel` 節は自分のハンドラの外(親の記録を `handler_top` にした状態)で走らせる。
  中の脱出はすべて打ち切り、標準出力を書き出してから標準エラーに記録し、元の巻き戻しを続ける(Q5)。
  巻き戻しの記録は入れ子にできるよう、`cancel` 節を呼ぶ前に退避して後で戻す。

この形は Diktor の `match_with`、`continue`、`discontinue` と同じ構造なので、never_ops.t の cancelresume、cancelresumevia、cancelresumetwo(破棄の途中に G の節を呼ぶ形)も同じ論理で通ると見込む(調査 効 R5)。
この 3 つを M85 の最初の回帰試験にする。

**ファイバーの実装(D539)。**
corosensei 0.3.4 の切り替えを使い、スタックは自前のプールから渡す(corosensei はスタックの型を差し替えられる)。
スタックは 64 MiB を `MAP_NORESERVE` で予約し、先頭にガードページを置き、実メモリは触れた分だけ使う。
プールは最大 64 本を保持し、返すときに 64 KiB より深い部分を `madvise(MADV_DONTNEED)` で手放す。
毎回 mmap すると 7.1 µs かかる(E9)ので、プールは必須である。
値スタックもファイバーごとに 1 本を同じプールから組で渡す。
ファイバーの切り替えでは、`ctx` の値スタックの先頭と限度を差し替える。
`extern "C"` の呼び出しは `libm` の葉の関数だけなので、ファイバーの上でそのまま呼ぶ。

**ファイバーを選んだ理由。**
代案は、調査 効 §6.4 が推す yield bubbling である。
この方式は継続のフレームを段に依らない形にできるが、エフェクトを起こしうる末尾でない呼び出しのたびに分岐が 1 つ要り、関数ごとに再入の入口が要るのでコードが大きくなる。
ファイバーの往復は 1.8 ns で(E9)、G の節を持たないハンドラの下ではまったく費用がかからない。
さらに、ファイバーはインタプリタと JIT のフレームを区別せずに止められるので、両段が共有する継続のフレームの形を決める必要が無い。
Rust で書いた組み込み(`Array.each`、`pinned`)が利用者の関数を呼び、その中で G の操作が起きても、Rust のフレームごと止められる。
代わりに次の費用を受け入れる。

- スタックのプールとガードページの管理。
- GC の根が、止まっている継続の値スタックすべてに及ぶこと。
- G のハンドラの本体の中の深い再帰は、64 MiB の限度で実行時エラーになること(I)。
- G のハンドラを再帰の段ごとに立てると、実メモリをファイバーあたり最低 1 ページ(4 KiB)使うこと。
  10 万段なら約 400 MiB になる。
  活性なファイバーの数に限度(既定 100,000)を置き、超えたら処理系の限度の実行時エラーにする(台帳 V208)。

分割スタック(LLVM の `split-stack`)も考えたが、`__morestack` の実行時を自作する必要があり、境界をまたぐ呼び出しが熱いと遅くなる問題があるので採らない。

### 4.10 WasmGC の後段(D540〜D543)

WasmGC はネイティブと同じ LIR から、別の下ろし方で作る。
メモリは V8 の GC に任せ、`kel-rt` の GC と値スタックは使わない。

**値(D540)。**
箱に入らない表現 `i32`、`i64`、`f64`、`bool` は Wasm の `i32`、`i64`、`f64`、`i32` にする。
一様な語 `w` は `(ref null eq)` にする。
Int32 を `w` に入れるときは、31 ビットに収まれば `ref.i31`、収まらなければ `(struct (field i32))` に入れる。
取り出しは `br_on_cast` で i31 かどうかを分ける(E11)。
Int32 は 31 ビットに収まらないので、i31 だけで表すことはできない(P242)。
文字列は `(array i8)`、レコードは `(array (mut eqref))` で 0 番に形の記述子を置く。
コンストラクタは配置ごとの struct 型にし、単相のプリミティブのフィールドは生の型にする。
クロージャは、関数への参照と捕まえた値の struct である。

**末尾呼び出し。**
`tailcall` は `return_call` と `return_call_ref` にする。
1e9 回の相互再帰がフラグなしで完走した(E11)ので、トランポリンは要らない。

**巻き戻し(D541 の一部)。**
実行時エラー、宛先つきの値、宛先つきの節は、1 つの例外の tag `$kunwind (param i64)`(起動の番号。0 は実行時エラー)で投げ、種類とペイロードはグローバルの変数に置く。
ハンドラは `try_table` と `catch_ref` で受け、宛先が自分でなければ `cancel` 節を走らせてから `throw_ref` する(E11)。
トラップとスタックあふれは Wasm の中で捕まえられない(E14)。
そのため、ゼロ除算、`MIN / -1`、`trunc`、配列の範囲外、null の参照、`ref.cast` の失敗になりうる箇所は、すべて明示の検査にして tag を投げる。

**スタックの深さ(D543)。**
末尾でない呼び出しの深さを、グローバルの変数で常に数える。
E15 の約 15,689 段は局所の少ない最小のフレームの値で、局所の多い関数ではもっと浅く溢れる。
そこで、深さの限度を固定せず、`kel_rt.mjs` が起動のときに測る。
起動の時点で、生成したモジュールの中で最も大きなフレームを持つ関数の形を真似た探査の関数を再帰させ、`RangeError` になる深さを求め、その半分を限度にする。
探査が失敗したときの既定は 4,000 段である。
`--stack-size` を渡すと、`kel_rt.mjs` は Node の `Worker` を `resourceLimits.stackSizeMb` 付きで起動し、限度をそれに合わせて上げる。
`Worker` で大きなスタックが得られるかは測っていないので、M89 の最初に測る(台帳 V202)。
`--stack-size=65500` が SIGSEGV になった(E15)ので、主スレッドのスタックを旗で大きくする方法は使わない。

**G の節(D541)。**
JSPI のスタックをファイバーの代わりに使う。
G のハンドラの本体は、`WebAssembly.promising` で包んだ export を JS の実行時から呼んで、新しいスタックで走らせる。
`perform` は `WebAssembly.Suspending` で包んだ import を呼んで子のスタックを止め、親のスタックは待っている約束が解決するまで同じく止まる。
`resume` は子の約束を解決し、継続の破棄は子の約束を `WebAssembly.Exception($kunwind, …)` で拒否する(E11 で JS からの例外の作成と照合を確かめた)。
プログラム全体を `promising` の中で走らせ、出力は `fs.writeSync` で同期に書くので、出力の順序は変わらない。
1 回の切り替えは約 63 ns(E13)で、ネイティブの 1.8 ns より遅いが、G の節は末尾でない `resume` に限られる。
JSPI の採否は M90 の試作で決める。
確かめることは、例外が `promising` の境目をまたいで tag を保つこと、JSPI のスタックの大きさ(既定 984 KB で伸びない)で足りること、never_ops.t の cancelresume の系列が通ることの 3 つである。
どれかが満たされなければ、G に届く関数(閉じた行で利用者が handle できるエフェクトを含まない関数を除く)を状態機械に変え、継続のフレームを GC の struct に積む yield bubbling に切り替える(調査 効 §6.4)。
全面的な CPS は、末尾でない呼び出しのたびに継続のクロージャを割り当てるので採らない。
WasmFX は、フラグが要り `switch` でプロセスが落ちる(E12)ので、既定にならない限り使わない(台帳 V197)。
Wasm の中で利用者の関数を呼ぶ組み込み(`Array.each`、`pinned`)は、JS のフレームが間に入ると JSPI が止められないので、Wasm の関数として生成する。

**入出力(D542)。**
`Console.write` は、文字列を線形メモリの 64 KiB のバッファに写し、`(ptr, len)` を JS の import に渡す(E17 の方法 B)。
64 KiB より長い文字列は 64 KiB ずつに分けて import を繰り返し呼ぶ(文字列は 2^31 - 1 バイトまでありうる。D526)。
JS はバイト列を `fs.writeSync(1, …)` でそのまま書く。
UTF-8 の文字列への変換はしない(§4.4。`wasm:text-decoder` はフラグが要る。台帳 V198)。
書き込みに失敗したら、JS は巻き戻しの種類「書き出しの失敗」で `$kunwind` を投げ、終了状態 74 で終わる。

**Float64 の表示と libm(D527、D528)。**
JS の `toPrecision` と `toFixed` は使えない(E16)。
`kel_rt.mjs` に、double の正確な 10 進展開を BigInt で求め、p 桁に偶数丸めして読み戻す `show_f64` を書く。
ネイティブの `show_f64` と同じ 2,000,000 件の入力で一致を確かめる。
Rust の wasm32 の標準ライブラリはこの機械に無いので、`libm` crate を wasm にはできない。
代わりに musl の `sin`、`cos`、`exp`、`log` の C ソースを `runtime/node/libm/` に置き、clang 22.1.8 の `--target=wasm32` で `libm.wasm` を作る(本計画の作成中に、clang と wasm-ld で C から wasm を作れることを確かめた)。
`libm.wasm` は線形メモリの別のモジュールで、WasmGC のモジュールから import で呼ぶ。
`Math.sin` などは V8 の実装なので使わない。
Rust の `libm` crate と musl の C の結果が一致するかは、乱数の 1,000,000 件で確かめる(台帳 V203)。

## 5. フロントエンドの移植(D544、D545)

**時期。**
後段(M84〜M90)が Diktor の出す IR で動いた後に始める(P244)。
所有者の動機はコンパイルの速さだが、意味の誤りを後段とフロントエンドに分けて探せるよう、後段を先に固める。
フロントエンドを移す間も、Diktor の `--emit-ir` が IR の基準になる。

**方法。**
調査 前 §2 の順(基盤、字句、構文、宣言表、単一化と表示、elab、網羅性、ドライバ、IR の書き出し、REPL)で移す。

- 構文解析は手書きの再帰下降にする。
  文法は LALR(1) で衝突が無く、優先順位の宣言も無い(E20)ので、非終端の階層をそのまま関数にできる。
  lalrpop 0.23.2 への機械的な移植は、差分が収束しないときの保険に残す(調査 前 §3.2)。
- 型は arena(`Vec<TyNode>` と `TyId`)に置き、型変数は添字の Union-Find にする。
  REPL の取り消しは `ena` の snapshot と rollback で行う。
- Diktor の大域の可変状態 81 か所を、1 つの `Session` の構造体に集める(調査 前 §1.3)。
- 位置の桁はコードポイントで数える(調査 前 §4.3)。
  字句解析はバイトで進め、表示のときだけ数え直す。
- 型の表示(show.ml、コード行 189)は規則をそのまま移し、`--type-check` の 933 行の `名前 : 型` を一致させる。
- `keleut tokens` と `keleut ast` は Diktor の `--dump-tokens` と `--dump-ast` と同じ形式にする(P248)。

**突き合わせ。**
1. 終了状態の一致: shim で cram を無改変で流す(E19)。
2. 型の行の一致: 933 行。
3. 字句と構文の一致: `tokens` と `ast` の出力。
4. IR の一致: cram から抜き出した 1,046 ファイル(調査 前 §4.2 (d))と cram の全入力について、`keleut ir emit --text` と `diktor --emit-ir=text` の出力をバイト単位で比べる。
   名前は安定しているので(本計画 2.6 節)、正規化は要らない。

診断の本文の一字一句は §18 の評価の結果に含まれないので、一致させなくてよい。
ただし、終了状態、位置、種別の語(型エラー、構文エラー、字句エラー、実行時エラー)、警告の件数は一致させる(調査 前 §5)。

## 6. 試験の方針(D546)

### 6.1 適合の試験の駆動器 `kel-conform`

`kel-conform` は、入力の `.kel` ごとに次の実行系で走らせ、標準出力のバイト列と終了状態を比べる(§18 の評価の結果)。

| 記号 | 実行系 |
| --- | --- |
| D | `diktor`(木の評価器) |
| DI | `diktor --emit-ir` の後に `diktor --run-ir` |
| KI | `keleut run --tier=interp` |
| KJ | `keleut run --tier=jit`(すべての関数を読み込みの時点で翻訳) |
| KA | `keleut run --tier=alternate:SEED`(関数の番号と種から、半分を JIT にする。種は 3 通り) |
| KT | `keleut run --jit-threshold=1`(実行の途中で段が上がる) |
| W | `keleut run --backend=wasm` |

期待値は D の結果とする。
D と DI が違うのは IR の誤り、DI と K* が違うのは RustKeleut の誤りである。
標準エラーは比べないが、診断が標準出力の後ろに出ること(§15.5)を、2 本の出力を 1 本にまとめた実行で確かめる。

### 6.2 入力

- Diktor の cram を shim で無改変で流す。
  shim は `diktor` という名前で PATH の先頭に置き、旗を `keleut` の形に書き換える(E19)。
  診断の本文は、`: 型エラー: ` などの後ろを切ってから比べる(調査 前 §4.2 (c))。
- cram から抜き出した 1,046 ファイルを D、DI、K* で比べる。
- 本計画で足す試験: 数値の境界(調査 忠 §1 の全行)、Float64 の表示の 2,000,000 件、評価順序(`order.kel`、`order2.kel`)、初期化の順(`fwd.kel`、`inst.kel`、`imp/`)。

### 6.3 スタックの限度

Diktor の tail_calls.t は `OCAMLRUNPARAM=l=100k` で、末尾の形が 10 万回を通り、末尾でない形が落ちることを確かめている。
OCaml の語数と RustKeleut の深さは同じ尺度ではないので、`kel-conform` は次の 2 つの条件で比べる。

- 限度に触れない条件: Diktor は既定、keleut は既定。
  深い再帰の試験は 100 万段までにする。
- 限度を絞った条件: Diktor は `OCAMLRUNPARAM=l=100k`、keleut と W は `--depth-limit=10000`。
  末尾の形の試験は 10 万回で通り、末尾でない形は終了状態 3 になることだけを比べる。

`--depth-limit` は全段で同じ数え方をするので、KI、KJ、KA、W の結果が分かれない。
加えて、`ulimit -s 512` の下で KA を走らせ、段の境目の末尾呼び出しがネイティブのスタックを伸ばさないことを見張る(E6 の再現)。

### 6.4 先に移す試験

never_ops.t(80 コマンド)、tail_calls.t(42)、eval.t の effects 系、run_exit.t を、M85 の受け入れ条件にする。
とくに、cancelresume の系列は破棄の途中に G の節を呼ぶ形で、最も壊しやすい(調査 効 R5)。

## 12. 進め方の原則

- マイルストーンは本計画 7.2 節の依存の順に逐次で進め、各マイルストーンの後に、観点ごとの検証者と指摘ごとの反証者による検証を行う。
  検証者の書き込み先は一時領域に限り、リポジトリの編集と git の書き込みを禁じる。
- コミットは論理単位で細かく分ける。
  ブランチが `ja/` で始まるので、メッセージは日本語で書く。
  コンパイルの通らない状態ではコミットしない。
  `--no-verify` と `--no-gpg-sign` は使わない。
- Diktor では、コードの修正と cram の期待値の更新(`dune promote`)を別のコミットにする。
  `test/smoke.t` の `usage` の更新も旗を足すコミットと分ける。
- Diktor のコメントを変えたら `python3 tools/litwrap.py <file>` と `python3 tools/litcheck.py` を走らせる。
  コメントには裁定、台帳、マイルストーンの番号と経緯を書かない。
  `ocamlformat` と `dune fmt` は使わない。
- サブモジュールの変更は `diktor/` の中でコミットしてから、親で版を進めるコミット(`diktor:`)を置く。
  版は `git -C diktor rev-parse --short HEAD` で埋める。
- RustKeleut のコミットの scope は `rk:`(crate 名を本文に書く)、IRSpec は `ir:`、文書は `doc:` とする。
- Diktor の参照用の評価器(`kernoeval.ml`)は、実行時エラーの文面と「cancel 節で例外が抑制されました」の文面を interp.ml と builtin.ml と同じ文字列で出す(関数を共有する)。
  cram は標準エラーも比べるので、文面が違うと M81 の受け入れで差分になる。
- 既存の `doc/log` の記録は書き換えない。
  本計画からの乖離は実施記録に書く。
- push はしない。
