# 261024-1: RustKeleut と中間言語 KIR の実装計画(統合案)

- 日付: 2026-10-24
- 決定: 仕様の所有者は 2026-10-24 に、Keleut のコンパイラと実行系の主な実装を、Diktor とは別に Rust で keleut リポジトリの中に作ると決めた。
  名前は RustKeleut、コマンドは `keleut` である。
  理由は次のとおりである。Diktor はセルフホストのコンパイラを動かすためのブートストラップとして作った。しかし Keleut は GC 言語で、GC を減らす仕組みが少ない。そのため、コンパイラを GC の無い言語で書くほうがコンパイルの速さで有利である。

  (3) できればインタプリタと LLVM のコードが、段階的コンパイルのように互いに飛び移れるようにする。
  (4) WasmGC は当面 Node.js で動けばよい。
  判断事項には推奨案を置き、推奨案で計画を確定する(所有者の指示)。

## 0. 要約

1. Diktor と RustKeleut が共有する IR を **KIR** と名付ける。拡張子はバイナリが `.kir`、テキストが `.kirt` である。
   KIR は精緻化の後の木の形をしている。名前の解決、クロージャ変換、辞書渡し、末尾の印、節の分類 N/T/G は済ませてある。
   型は表現の種類(Rep)だけを持つ。名前は、プロセスに依らない記号で付ける。仕様は `doc/IRSpec.md` に置く。
2. 意味を決める処理は、RustKeleut の**共有の下ろし**(KIR → LIR)に集める。評価順序、パターンの照合、数値の検査、初期化の検査、エフェクトの規約、論理的な深さがこれに当たる。
   LIR の命令は「trap せず、未定義の動作を持たない」と定める。インタプリタ、LLVM、WasmGC は LIR を機械的に訳すだけにする。
3. 関数の戻り値は、どの後段でも常に一様な語とする。これで、表現の違う関数の間でも末尾呼び出しが `musttail` のまま保てる(§5.7)。
4. 制御の脱出(継続の破棄、実行時エラー)と G の継続の取り出しは、全後段で 1 つの**状態語の伝播**で行う。ネイティブでは戻り値の番兵 `0x2` を併用する。
   ハンドラの論理は LIR の組み込み関数 `rt_handle`、`rt_resume`、防壁(barrier)として 1 回だけ書く。
   v1 では、ネイティブの例外、ファイバー、JSPI、WasmFX、exnref を使わない。
5. ネイティブ(インタプリタと JIT)のフレームは、分割した共有の値スタックの上に同じ形で並ぶ。
   G の継続の取り出しは、値スタックの区間の写しで行う。再開したフレームはインタプリタが続ける(取り出しがそのまま脱最適化になる)。
   WasmGC はフレームを GC の構造体に写す。関数の先頭の `br_table` から再開点へ前向きに飛ぶ。
6. 評価に要する領域の限度は、KIR の水準で定めた**論理的な深さ**で決める。既定は 2^20 = 1,048,576 である。
   Diktor の `--run-ir` と RustKeleut の全後段が同じ位置で限度に達し、`cancel` 節を走らせて終了状態 3 で終わる。
   物理的なスタック(ネイティブのスレッド、Node の子プロセス)は、測った 1 段あたりのバイト数から大きさを決める。
7. 実行時の核は、自立した C の 1 つのソース(`rustkeleut/rtcore/`)に書き、clang でネイティブと wasm32 の両方にコンパイルする。
   中身は `show(Float64)`(正確な多倍長の探索)、musl から取り込んだ `sin cos exp log`、バイト列の比較、レコードの形の表である。
   Rust の `{:.*e}` と glibc は試験の基準にだけ使う。
8. Diktor には、KIR の書き出し、バイナリ、検証器、参照の IR 評価器(`--run-ir`、`--via-ir`)を足す。
   最初に Diktor の `resume(resume(x))` の不一致(V191)を単独で直す。
9. 試験は差分試験の実行器 `kconform` で行う。kconform は cram の `.t` を自分で読み、`diktor` の shim を通して Diktor の cram を無改変で流す。
   組み合わせは interp、jit、threshold、alternating:SEED、mixed:SEED、wasm で、RustKeleut の中ではバイト単位の一致を求める。
   Diktor との差は `known-diffs.toml` に登録したものだけを許す。
10. マイルストーンは M79〜M101 の 23 個で、3 つの系統を並行して進める。Diktor の系統(M80〜M83)、後段の系統(M84〜M95)、フロントエンドの系統(M96〜M99)である。
    フロントエンドは kir crate(M84)だけに依存し、コンパイルの速さの関門を持つ。REPL(M100)と KIR 1.0 の凍結(M101)は最後に置く。

## 3. 中間言語 KIR

### 3.1 名前と水準(D500、D501)

- 名前は KIR(Keleut Intermediate Representation)、拡張子は `.kir` と `.kirt` である。
  LIR とバイトコードは RustKeleut の内部の形で、ファイルに書かず、互換性も約束しない。
- 水準は精緻化の後である。KIR を作る段で、次のものを済ませる。
  - 構文の脱糖(`if`、タプル、`with`、末尾ブロック。tree §1.1)
  - 名前の解決(大域は記号、局所はスロット)
  - クロージャ変換(関数ごとの捕獲の列。辞書の引数も捕獲する。tree §3)
  - 辞書渡しの明示(証拠の平坦化、インスタンスの頭の解決、メソッドの辞書の位置。tree §2、§4.2)
  - 数値リテラルの確定と module の平坦化
  - 末尾の印と節の分類
  - `run` の消去と、`BinOp` と `Neg` のメソッド呼び出しへの書き換え
- KIR は木で、子は符号化に現れる順に評価する。ANF にはしない。
  木にする理由は、Diktor の書き出しが `Tree` をほぼ 1 対 1 にたどる形で書け(tree §1.4)、Diktor が ANF の正規化も box の挿入も書かずに済むことである。
  そうすれば Rust のフロントエンドも同じ軽い KIR を出せばよい。ANF は LIR で作る。
  代案の ANF(incremental、native)は、Diktor の書き出しを重くし、2 つの書き手がずれうる箇所を増やすので採らない。

### 3.2 型(D502、D503)

- Rep は `bool`、`i32`、`i64`、`f64`、`str`、`any` の 6 種である。
  付ける場所は、局所の束縛(let、引数、パターンの変数)、関数の結果、大域である。
  Diktor の書き出しは、`ty_field` を `repr` した結果の頭が Int32、Int64、Float64、Boolean、String ならその Rep を、ほか(`Generic` を含む)なら `any` を書く。
- 関数と呼び出しには `may_yield` の 1 ビットを付ける。値が 0 になるのは、エフェクト行が閉じていて、要素が `Console`、`Heap`、`Blocking` だけのときである。
  この印は最適化(D534)にだけ効く。
- 完全な型は、読み飛ばせる節 0x82 に文面で置く。検証器はこれを使わない。
  完全な型を持たせない理由は、持たせると検証器が行多相とスコープ付きラベルの型検査を再実装することになるからである(fp §1.3)。
- **戻り値は一様**(D503): KIR が持つ結果の Rep は検証と最適化のためのものである。LIR の呼び出し規約では、どの関数の戻り値も `any`(一様な語)とする。
  そうしないと、`f(x): Int64 = g(x)`(`g` は多相で `any` を返す)や、クロージャを通す末尾呼び出しで、呼び出しの後に unbox が要る。呼び出しは末尾でなくなり、§5.7 を破る(native 2.3)。
  v1 では引数も境目で `any` にする。箱に入れない引数の入口は、戻り値に手を加えない包みで後から足せる(V207)。
  代案の incremental D510/D545(宣言の Rep で生のビットを返す)は、§5.7 の hof と dict の場合を壊すので採らない。

### 3.3 安定な名前(D504)

- Diktor の oid、`h_id`、ハンドラの起動の番号はプロセスの中でしか通用しない(tree §0 の 4)ので、KIR には書かない。
- 単位の鍵は次のとおりである。
  - プレリュードは `prelude`、組み込みは `builtin`、コマンド行の起点(複数のファイルを連結した 1 単位)は `main`。
  - ほかの単位は、起点のディレクトリからの相対パス(区切りは `/`)。`--import-path` の i 番目の下にあるファイルは `@i/相対パス` とする。
- 大域の記号は `単位の鍵/修飾名` である。同じ単位で同じ名前を再び束縛したときは、2 つ目から `#1`、`#2` を付ける(§6.1 の再束縛は別の実体である)。
- 型、コンストラクタ、エフェクト、操作、クラス、インスタンスにも記号を付ける。インスタンスは `単位の鍵/instance:クラス[頭]#n` である。
- 持ち上げた関数は、持ち主の記号に `$` と、持ち主の本体の前順の番号を付けて名指す(例 `main/loop$3`)。
  ハンドラの本体と節は `$h<n>.body`、`$h<n>.op.<名前>`、`$h<n>.return`、`$h<n>.cancel` とする。
- ラベルと操作の短い名前は文字列表の添字で表す。局所は関数の中の番号で表す。
- 書き出しは決定的にする。同じ入力からは、プロセスが違っても同じバイト列を出す(M81 の受け入れの `cmp`)。
  記号はリンクと診断にだけ使い、実行時の意味には使わない(§18.1)。
  代案の走査の順の添字(incremental D505)は、Rust のフロントエンドに Diktor の走査の順を一字一句再現させることになるので採らない。

### 3.4 プログラム、初期化、使うたびの評価(D505、D506、D507)

- `.kir` の 1 ファイルは、プレリュードを含む全単位を初期化の順(§15.4。起点が最後)に並べた、自己完結のプログラムである。
  単位ごとに節を分けて持つので、後で分割コンパイルへ広げられる(V210)。
- 単位の初期化の手順は 5 種である。

  | 手順 | 意味 |
  |---|---|
  | `def_value g f` | 0 引数の関数 `f` を評価して `g` に置き、初期化済みにする |
  | `def_fns [g…]` | 関数の大域(let rec の群を含む)を初期化済みにする |
  | `def_dictabs g` | 辞書を受け取る値束縛を初期化済みにする(評価はしない。§6.4) |
  | `def_instance i` | インスタンスを使える状態にし、前提も自分の制約も持たない値束縛のメソッドを、宣言の順に 1 回だけ評価する(fid §8 の inst2) |
  | `run_exp f` | 式文を評価する。辞書を受け取る式文は書き出さない |

- 大域とインスタンスは、初期化済みの印を持つ。初期化の前に読むと実行時エラーになる(fid §10 の fwd.kel、§8 の inst.kel)。
- **検査を省いてよい条件**(D506): 大域 `g` の参照を含む最も外側のトップレベルの実体の手順が、`g` の手順より後にあるとき、または両者が同じ `def_fns` の群にあるときだけ省く。
  反例は `let p = {f = fn(x) => h(x)}` で、`h` が後に宣言されている形である。ここで作った無名関数は `h` の初期化の前に呼べるので、検査を残す。この反例を `conformance/init/` に置く。
- 範囲外の数値リテラルは `lit_error(lit_range, 字面)` とする。これは評価したときに初めて実行時エラーになる。下ろしも最適化も、これを畳み込んだり、前へ動かしたり、消したりしてはならない(§4.2、fid §1)。
- **使うたびの評価**(D507): 辞書を受け取る値束縛は、KIR の意味では使うたびに初期化式を評価する(§6.4、§12.2)。
  RustKeleut が結果を保存してよいのは、初期化式が構文上 `closure` のときだけである。
  Diktor の `da_last`(同じ辞書の列なら前の結果を返す)は観測できないので許す、と IRSpec に書く。理由は、初期化式がエフェクトを起こせず、1 回目が誤りか停止しないなら 2 回目に届かないことである(V197)。

### 3.5 式と評価順序(D508)

| 式 | 子の評価の順と意味 | 末尾の印 |
|---|---|---|
| `lit(bool\|i32\|i64\|f64\|str)` | 定数。`f64` はビット列、`str` は blobs の添字 | |
| `lit_error(kind, text)` | 評価したら実行時エラー | |
| `local(i)` `env(i)` `dparam(i)` `global(g)` | 読む。`global` は初期化の検査を伴う(D506) | |
| `ctor0(T,c)` / `construct(T,c,[(field,e)…])` | `e` を**書いた順**に評価し、`field` の位置(宣言の順)に格納する | |
| `variant(l, e)` | 引数が無ければ Unit を積む | |
| `call(f,[a…])` | `f` を先に、次に引数を左から評価して呼ぶ(§5.1、fid §4 の `F12`) | ✓ |
| `method(C,m,d,[own…])` | `d` と `own` を評価し、**この時点で**インスタンスの初期化を検査してメソッドを選ぶ | |
| `opcall(C,m,d,[a…])` | `d` と引数を左から評価し、**その後で**メソッドを選んで呼ぶ。常に末尾ではない | |
| `not` `and` `or` | 短絡する | `and` と `or` の右辺 |
| `closure(fn,[cap…])` `dictabs(fn,[cap…])` `dictapp(e,[d…])` | 捕獲と辞書を左から評価する | |
| `let(i,rep,e1,e2)` `letpat(p,e1,e2)` `letrec([(i,fn,[cap…])…],e)` `seq` | 照合が失敗したら実行時エラー。`letrec` はクロージャをすべて作ってから捕獲を埋める | `e2`、`e`、`seq` の最後 |
| `match(e,[clause…])` | `e` を 1 回評価し、節を上から試す。ガードは、パターンが合った節だけで評価する | 節の本体 |
| `rec_empty` `rec_extend(l,v,r)` `rec_select` `rec_restrict` `rec_update(l,r,v)` | 拡張は `v` を先に、`r` を後に評価する。更新は `r` を先に、`v` を後に評価する。対象は最も外側の同名ラベル(fid §4 の yzext、order2) | |
| `perform(E,op,[a…])` | 引数を左から評価し、最も内側の E のハンドラへ送る | |
| `handle(E,body,[opclause…],ret?,cancel?)` | 本書 3.8 節 | ✓ |
| `resume(e, tail)` | `e` を評価してから再開済みかを調べ、再開する(D514) | `tail` |
| `hole` | `???` で、実行時エラーになる | |

- `opcall` と `call(method(…))` を分けるのは、メソッドを選ぶ時点が観測できるからである。
  Diktor は、演算子の場合はオペランドを評価してから選ぶ(interp.ml:340-345)。関数の形で書いたメソッド(`show(x)`)は、呼び出し先として先に選ぶ。
  インスタンスの宣言の前に選ぶと実行時エラーになるので、オペランドの出力との前後が結果に効く(inst.kel)。
- `!=` は `not(opcall(Eq, eq, …))` にする。辞書の式は `dinst(I,[前提…])`、`dparam/env`、`drecord([(l,d)…])`、`dvariant(…)`、`dbuiltin(C,頭)` の 5 種である(tree §2)。

### 3.6 関数、クロージャ、辞書、データ

- 関数の表の各項目は、次の欄を持つ。
  `kind`(`lambda opclause retclause cancelclause handlebody thunk dictabs`)、引数の Rep、辞書の引数の数、捕獲の数、スロットの数と Rep、本体。
  ハンドラの本体と節も関数にする。継続はフレームの境目でしか切れないからである(本書 5.6 節)。
- インスタンスは、クラス、頭、前提の数、`(メソッドの番号、自分の辞書の数、関数)` の列を持つ。
  実装の関数は `前提の辞書 ++ メソッド自身の辞書` を受け取る(tree §4.2 の ABI)。
- 名目的な型は、記号とコンストラクタの番号で表す。フィールドは宣言の順に置く。コンストラクタは第一級の値ではない(tree §7)。
- レコードはラベルで操作する命令のまま残す。形の確定は LIR が行う。ヴァリアントはラベルと積載値 1 個である。

### 3.7 パターンと末尾の印(D509、D510)

- パターンは `wild`、`bind(i)`、`lit`、`record([(l,p)…], closed|open|rest(p))`、`ctor(T,c,[(field,p)…])`、`variant(l,p)` の 6 種である。
  数値のパターンは、照合する列の型で読んだ値として書く(`case 0xFFFFFFFF` は Int32 の -1)。
  `match` は節の順とガードを保つ。決定木は LIR で 1 回だけ作る。
- `call`、`handle`、`resume` は `tail` の印を持つ。検証器は §5.7 の規則で末尾位置を計算し直し、印と違えば拒否する。
  `resume` の背骨は節の本体から始まり、`handle` と `lambda` の中には入らない(tree §2)。
  戻り値が一様(D503)なので、末尾の印は Rep に依らない。

### 3.8 エフェクトと節の分類(D511)

- `handle` は、エフェクト、本体の関数、操作節の列、`return` 節(省略可)、`cancel` 節(省略可)を持つ。
  操作節は、操作、引数のパターン、ガード(省略可)、本体、分類 `N|T|G` を 1 つの `opclause` 関数にまとめたものである。
- 分類の規則は次のとおりである(fx §6.0)。
  - N: 返り値の型が `Never` の操作。
  - T: 本体の `resume` がすべて末尾 resume である(`resume` の無い枝を含んでよい)。
  - G: それ以外。
  検証器は、操作の `never` の印と `resume` の `tail` の印から分類を計算し直す。
- `resume` が書けるのは T と G の節の本体の中だけである。ガード、`return`、`cancel`、N の節、ラムダには書けない。
- `Console.write` の `perform` は KIR ではほかの操作と同じに書く。LIR がこれを実行時の直接の呼び出しに変える(D530)。

### 3.9 リージョン、extern、組み込み(D533)

- `run` は消す。`Ref`、`Array`、`MutableArray` の 12 個の操作(fid §13.2)は `builtin/…` の大域にする。
- `extern "prim"` の 48 個(`grep -c '^extern "prim"' diktor/lib/prelude.kel` → 48【実測】)と `extern "C"` は、`extern(abi, 名前)` の大域にする。
  実装の無い名前は読み込みでは拒否しない。呼んだときに実行時エラーにする(§17、fid §12)。
- RustKeleut では、利用者の関数を呼ぶ組み込み(`Array.each`、`pinned`)と `with_runtime` の結線を、`rustkeleut/lib/rt.kirt` に KIR で書く。
  中の呼び出しも再開点を持つので、継続の取り出しも段の切り替えも組み込みの中で同じに働く(fid §9)。
  `Array.each` は内側のループを末尾呼び出しで書く。こうすると、利用者の関数は呼び出しの位置 + 2 の深さで走り、OCaml で書いた Diktor の `Array.each` と深さが一致する(3.10 節)。

### 3.10 論理的な深さ(規範。D513)

§15.5 は、限度の大きさを処理系に任せている(I)。一方で、限度を超えたときの振る舞い(`cancel` を走らせて終了状態 3)は結果に効く(fid §5)。
IRSpec は、評価の各文脈に整数の深さ `d` を定め、すべての実装が同じ値を数えるようにする。
Diktor の `ir_eval` は OCaml のファイバーの上で動くので、自分のスタックからは深さを得られない。そのため、規則は「どの境目で数がどの値になるか」の形で書く。

| 場面 | 深さ |
|---|---|
| 最上位の初期化の手順 | 0 |
| 深さ `d` の文脈での末尾でない `call`、`opcall`、`dictapp`、組み込みが利用者の関数を呼ぶ呼び出し | 呼ばれた側は `d+1` |
| 末尾呼び出し、末尾 resume | 呼び出し元の深さを引き継ぐ(増えない) |
| 深さ `h` の `handle` の本体 | `h+1` |
| 深さ `p` の `perform`。節の選択(パターンとガード)と T の節の本体 | `p+1` |
| G の節の本体(宛先のハンドラの深さ `h`) | `h+1` |
| G の節の中、深さ `c` での末尾でない `resume`。継続の深さの差 `Δ = p − h` | 再開した `perform` は深さ `c+Δ` で値を返す |
| N の節の本体、`return` 節 | `h`(ハンドラ式の位置を引き継ぐ) |
| `cancel` 節 | 巻き戻されるハンドラの `h` |

- 呼ばれた側の深さが限度 `L` を超えるときは、その呼び出しに入る前に実行時エラー `depth_limit` にする。
- **予備**: `depth_limit` の誤りが伝播している間は、限度を `L + R`(`R = max(1024, L / 64)`)とする。誤りが最上位に届いたら元に戻す(REPL では入力の終わり)。
  予備の中でさらに限度を超えたら、その `cancel` 節からの脱出として打ち切り、記録する(§13.6)。
- **実装の不変条件**(RustKeleut): 各フレームは、入口で自分の深さを値スタックのフレームの見出しに書く。
  末尾でない呼び出しが戻ったら、正常に戻っても番兵で戻っても、`ctx.depth` を自分の深さに書き戻す。こうして巻き戻しの経路でも数が正しく減る。
  `rt_resume` は、写し戻したフレームの深さを `c − h` だけずらす。
  LIR が内部で使う呼び出し(`rt_handle` から本体への呼び出し、`rt_resume` のフレーム、インライン展開)は、上の表のとおりに数え、LIR の呼び出しの数では数えない。
- 既定は `L = 2^20 = 1,048,576` である。fid §5 の `nontail.kel`(深さ 1e6 の非末尾の再帰。Diktor は 0 で終える)が既定で通るよう、1e6 より少し大きい 2 の冪にした。`keleut --max-depth N` と `diktor --run-ir --max-depth N` で変えられる。Diktor の木の評価器は OCaml のスタックに従う(V196)。
- 深さが L を超えるが Diktor の木の評価器では通るプログラムは、設計による既知の差である(限度は I)。`known-diffs.toml` に理由「限度は I」で登録し、不具合として扱わない。

### 3.11 抽象機械の規範の文(D512)

IRSpec の 9 節は、fx §5 の Q1〜Q10 を規範の文にする。中でも次の文を明記する。

1. 本体の側から届いた巻き戻しの宛先がこのハンドラの起動でないときは、このハンドラの `cancel` 節を 1 回走らせてから巻き戻しを続ける。宛先がこの起動なら、走らせない(native 4.9)。
2. `return` 節は、ハンドラを連鎖から外した後で評価する。そのため、return 節の中の誤りでは自分の `cancel` を走らせない。
   N の節の本体も、継続を破棄してハンドラを外した後で評価する。
   G の節の中で `resume` が戻った後のコードも、そのハンドラが連鎖にいない文脈で走る(§13.6)。
3. 節の選択とガードと T の節の本体では、ハンドラの連鎖をそのハンドラの親に付け替える。節の中の操作は外側へ届く(§13.4)。
4. `cancel` 節は自分のハンドラの外で走る。中で起きた脱出(実行時エラー、破棄、`depth_limit`)はすべて打ち切る。標準出力を flush してから標準エラーに記録し、元の巻き戻しを続ける(fx R5)。
5. ハンドラの起動の同一性は、64 ビットの単調に増える番号で表す(fx R8)。

### 3.12 テキストとバイナリ(D516、D517)

- `.kirt` は S 式で、バイナリと 1 対 1 に往復する。正準の印字(字下げ、表の並び、数の綴り、バイト列は `\xHH`)は IRSpec が定める。
  `keleut kir dis`、`diktor --emit-ir-text` はどちらもこの正準形を出し、比較はバイト単位で行う。テキストを読む機能は RustKeleut の `keleut kir asm` だけが持つ。

```
(fn "main/loop" lambda (params (n i32) (acc i64)) (result i64) (dicts 0) (caps 0) (yield 0)
  (match (opcall Eq eq (dbuiltin Eq Int32) (local 0) (lit i32 0))
    (clause (lit bool true) (local 1))
    (clause (lit bool false)
      (call tail (global "main/loop")
        ((opcall Sub sub (dbuiltin Sub Int32) (local 0) (lit i32 1))
         (opcall Add add (dbuiltin Add Int64) (local 1) (lit i64 1)))))))
```

- バイナリの先頭 16 バイトは次のとおりである(リトルエンディアン)。
  マジック `00 4B 49 52`(`\0KIR`)、主版 u16、副版 u16、必要な機能のビット u32、節の数 u32。
  その後に節 `id: u8, size: uLEB128, payload` が id の昇順に並ぶ。
  整数は uLEB128 と sLEB128(Wasm と同じく最長の符号化を超えたら誤り)、`f64` は 8 バイトで、NaN の積載も保つ。

  | id | 節 | 中身 |
  |---|---|---|
  | 0x01 | strings | 名前(UTF-8 であること) |
  | 0x02 | blobs | `String` のリテラル(任意のバイト列。NUL と不正な UTF-8 も許す。§4.4) |
  | 0x03 | units | 単位の鍵、元のパス、初期化の順 |
  | 0x04 | types | 名目的な型、コンストラクタ、フィールド |
  | 0x05 | effects | エフェクト、操作、引数の数、`never` の印、実行時が処理する印 |
  | 0x06 | classes | クラス、メソッド、メソッドの辞書の数 |
  | 0x07 | instances | 本書 3.6 節 |
  | 0x08 | prims | このファイルが使うプリミティブの名前(読み手は IRSpec の付録 A と照合する) |
  | 0x09 | globals | 記号、種類(`fn value dictabs extern builtin`)、単位、辞書の数、Rep |
  | 0x0A | functions | 関数の表。本体は前順の木で、各ノードは 1 バイトの命令とその欄 |
  | 0x0B | init | 単位ごとの初期化の手順 |
  | 0x80 | producer | 書き手の名前と版、元のファイルのハッシュ |
  | 0x81 | locations | ノードの前順の番号から(ファイル、行、桁)への表 |
  | 0x82 | types-debug | 完全な型の文面 |

- 読み手は、マジック、版、機能のビット、節の順と大きさ、添字の範囲を検査する。0x80 以上の節は読み飛ばしてよい。

## 5. RustKeleut の構成

### 5.1 workspace と crate(D521)

RustKeleut は親の `rustkeleut/` に cargo の workspace として置く(resolver 3、edition 2024、rust-version 1.98)。サブモジュールにはしない(P232)。

```

  lib/rt.kirt                KIR で書いた組み込み(Array.each、pinned、with_runtime の結線)
  host/keleut-host.mjs       Node 側の実行時(起動、入出力、rt.wasm の結線)
  crates/
    kir/            KIR の型、バイナリとテキストの読み書き、検証器
    keleut-rtcore/  rtcore を cc と clang で x86_64 の静的ライブラリと rt.wasm にする build.rs と FFI
    keleut-lir/     共有の下ろし(KIR → LIR)、LIR の検証器、組み込み関数 rt_handle/rt_resume/barrier
    keleut-rt/      値、ヒープと GC、分割値スタック、ctx、ハンドラ記録、継続、出力、終了
    keleut-interp/  バイトコードの符号化とインタプリタ、interp_continue
```

### 5.3 読み込みと検証

検証器(`kir` crate)は次のことを確かめる。失敗したら 65 で終わる。
1. 添字が範囲にあること。
2. Rep が合うこと(プリミティブ、let、init)。
3. 末尾の印と背骨が、計算し直した結果と一致すること。
4. N/T/G が、計算し直した結果と一致すること。
5. `resume` が許された位置にだけあること。
6. 初期化の手順が各大域をちょうど 1 回定義すること。
7. プリミティブの名前が付録 A にあること。

検証器は型の健全性を保証しない。信頼の根は、型検査を済ませたフロントエンドである。

### 5.4 共有の下ろし KIR → LIR(D524)

LIR は、関数ごとの基本ブロックのグラフで、仮想レジスタは Rep を持つ。Keleut には反復の構文が無い(§5.7)ので、どの関数の制御も**非巡回**になる。
パスは次の順に行う。
1. 環境の配置。
2. パターンの照合を、後戻りを伴う照合の手順に下ろす。ガードの順を保ち、照合の失敗は `rt_error(MatchFail)` にする。
3. A 正規化(評価順を命令の順にする)。
4. Rep と箱。関数の境目は v1 では引数も戻り値も `any` にする(D503)。
5. 辞書の定数化(`dbuiltin` の `opcall` をプリミティブにする)。
6. レコードの形(閉じた行で単相の箇所は位置を定数にし、ほかは rtcore の形の表を引く)。
7. 数値の検査の明示。ゼロで割ったら `rt_error(DivZero)`。`MIN / -1` は `MIN`、`MIN % -1` は 0。f64 から整数への変換は NaN と範囲(`t >= -2^31 && t < 2^31` など。上端は開区間)を先に検査する。
   整数の `+ - *` は折り返す(LLVM では `nsw` を付けない)。
8. エフェクトの下ろし(本書 5.6 節)。
9. 初期化の検査の省略(D506)。
10. 深さの命令(本書 3.10 節。入口で深さを書き、戻ったら書き戻す。限度の検査)。
11. yield の刈り込み(D534)。
12. 生存区間、再開点の番号、スロットの割り当て(スロットは `any` の区画と生の区画に分ける)。

LIR の各命令の意味は `rustkeleut/doc/lir.md` に、「trap せず、未定義の動作を持たない」形で定める。LIR の検証器は、各パスの後に Rep、非巡回であること、再開点の一貫性を確かめる。

### 5.5 実行時(D525〜D530)

- **値の表現**(ネイティブ): 一様な語は 64 ビットである。
  - 最下位ビットが 1 なら即値である。Int32 は `(n<<1)|1`。Boolean、Unit、引数の無いコンストラクタも即値にする。
  - 下位 3 ビットが 0 なら、8 バイト境界のポインタである。
  - `0x2` は巻き戻しの番兵で、値としては現れず、戻り値の位置にだけ使う。
  箱は Int64、Float64(一様な位置だけ)、文字列(長さ付きのバイト列で、NUL を終端にしない)、レコード(形の id とフィールドの配列)、データ、ヴァリアント、クロージャ、辞書、`Ref`、配列、ハンドラ記録、継続である。
  見出しの 1 語に、種類、GC の印、配置の番号、大きさを置く。NaN ボックス化は採らない(tg §2.2)。
- **分割値スタック**(D527): フレームは、1 MiB の塊をつないだ値スタックに置く。
  形は「見出し(関数 id、再開点、深さ、`any` と生の区画の大きさ、呼び出し元のフレームへの相対の位置)とスロット」で、インタプリタと JIT で同じである。
  見出しは番地ではなく区間の底からの相対の位置を持つ。区間を別の番地へ写し戻したときは、`rt_resume` が深さの欄と一緒にこれをずらす。
  入口で塊の残りが足りなければ、実行時が次の塊をつなぐ。値スタックの大きさは限度にならない(限度は論理的な深さ)。
- **GC**(D526): 動かさないマークスイープで、ミューテータは 1 本である(§13.7)。大きさの種類ごとのページと空きリストを使う。
  - 根は、値スタックの `any` の区画、継続の中の区間、大域、インスタンス、ハンドラの連鎖、状態語の積載値、Rust の `Root` のハンドルの枠である。
  - マークは明示のマークスタックで反復し、ネイティブのスタックを使わない(深いリストで落ちない)。
  - 安全点は確保の中だけである。JIT は、末尾でない呼び出しと確保の前に、生きている値をすべて(`any` も生の値も)スロットに書く(D538。インタプリタが続きを実行するためでもある)。
  - Rust の実行時の関数は、確保をまたいで値を持つときは `Root` を使う。
  - ステートポイントは使わない(E6)。
- **rtcore**(D528): 自立した C99 で 1 回だけ書く。
  - `f64show.c` は §16.2 を実装する。nan、inf、-inf、`1e16` 未満の整数値は `%.1f`(`-0.0` を含む)。それ以外は p を 1 から 17 まで増やす。
    p 桁の候補は、2 進の値の正確な 10 進展開から多倍長の整数(基数 10^9)で偶数丸めして作る。
    「読み戻して元の値になる」ことは、「候補が x の丸めの区間(半 ulp。2 の冪では下側が半分。端を含むかは仮数の偶奇で決まる)にある」ことと同値なので、strtod なしに正確な比較で判定する。
  - `musl/` は musl 1.2.5 の `sin cos exp log` とその依存を取り込む(P239)。
  - `shape.c` はレコードの形の intern、拡張、制限、位置の検索を扱う。ラベルの番号の昇順に並べ、同名は外側から並べる正準の配置にする(§18.3 により結果に効かない)。
  - `bytes.c` は符号なしバイトの辞書順の比較を行う。
  - 組み方は `clang -std=c99 -O2 -ffreestanding -fno-builtin -ffp-contract=off -fno-math-errno` で、x86_64(`cc` crate で静的ライブラリ)と `--target=wasm32 -nostdlib`(`wasm-ld --no-entry` で `rt.wasm`)の両方を作る。
  - ネイティブの全後段と WasmGC が同じソースの結果を使う。clang で組んだ musl が x86_64 と wasm32 でビット一致し、libc に依存しないことは、まだ確かめていない。【推論・要検証 M79、M85】
  - 試験の基準は 3 つである。glibc の `%.*g`(fid §2 の fltcmp の 2,000,000 件)、Rust の `{:.*e}`(E13)、Diktor の出力。
- **libm**(D529): `sin cos exp log` は rtcore の musl を不透明な記号 `krt_sin` などで呼ぶ。LLVM は意味を知らないので、畳み込みも組み込み関数への置き換えもしない。
  `sqrt` は IEEE の命令(`llvm.sqrt`、`f64.sqrt`)を使う。Diktor の glibc との最下位ビットの差は既知の差とし、LangSpec §17 に「結果の最下位のビットは処理系定義」と書く(P237、V193)。
- **出力**(D530): `Console.write` は実行時の直接の呼び出しで、64 KiB でバッファする。
  flush するのは、満ちたとき、標準エラーへ書く直前、終了の前である。
  書き込みは短い書き込みを繰り返す。`EAGAIN`(非ブロッキングのパイプ)は待ってから再試行する。
  失敗(`EPIPE`、`EBADF` など)は `ERROR(Io)` として巻き戻し、`cancel` を走らせてから 74 で終わる(eval.t の sinkfail.kel)。
  実行時エラーが最上位に届いたら、標準出力を flush し、文面を標準エラーに書き、3 で終わる。

### 5.6 エフェクトの規約(全後段で共通。D531、D532)

**データ**

| 名前 | 中身 |
|---|---|
| ハンドラ記録 `HR` | 起動ごとの 64 ビットの番号、エフェクト、節の表、`return` と `cancel`、親、本体を呼んだときの深さ `h` |
| `ctx.handlers` | 有効なハンドラの単方向の連鎖(最も内側が先頭) |
| 状態語 `ctx.pending` | `NONE`、`YIELD(hr, 節, 束縛)`、`DISCARD(hr, Value(v) \| NeverBody(節, 束縛))`、`ERROR(kind, 文面)` |
| 継続 `K` | フレームの列(ネイティブは値スタックの区間の写し、Wasm はフレームの構造体の列)、連鎖の切り取り、`HR`、`Δ`、`used`、`alive` |

**伝播**: 末尾でない呼び出しが戻ったら、ネイティブでは戻り値が `0x2` か(`cmp rax, 2; je`。ctx を読み直さない)、Wasm では大域 `$pending` が 0 でないかを調べる。
状態が立っていれば、普通のフレームは次の LIR 命令を実行して自分も戻る。
- `YIELD` なら `yield_save(再開点)`。ネイティブでは何もしない(フレームはすでに値スタックにあり、再開点も呼び出しの前に書いてある)。Wasm では生きている局所を構造体に詰めて `ctx.yield_frames` に積む。
- `DISCARD` と `ERROR` なら、フレームを捨てて戻る(値スタックの先頭は受け手が戻す)。
フレームの表現が後段で違うのはこの 1 命令だけである。`rt_handle`、`rt_resume`、防壁は、どの後段でも同じ LIR の文面である。

**`handle` と `rt_handle(hr, body)`**(`handle` が末尾なら、この呼び出しも末尾にする)
1. `hr.parent = ctx.handlers`、`ctx.handlers = hr` とし、本体を末尾でなく呼ぶ。
2. 値 `x` で戻ったら、`ctx.handlers = hr.parent` とし、`return` 節を `x` で**末尾呼び出し**する(省略なら `x` を返す)。
3. 自分宛ての `DISCARD(Value v)` なら、連鎖から外して `v` を返す。`return` も `cancel` も走らせない。
4. 自分宛ての `DISCARD(NeverBody)` なら、連鎖から外し、N の節の本体を**末尾呼び出し**する(retry.kel が一定の領域で走る。§5.7)。
5. 自分宛ての `YIELD` なら、`K` を作り、連鎖から外し、G の節を `(束縛, K)` で末尾でなく呼ぶ。
6. 自分宛てでない `DISCARD` と `ERROR` なら、連鎖から外し、**防壁**の中で `cancel` を走らせ、同じ状態語で戻る。
7. 自分宛てでない `YIELD` なら、自分のフレームも継続に含めて戻る。

**防壁**: 保留中の `P` を退避して消し、`cancel` を呼ぶ。戻ったときの扱いは次のとおりである。
- `DISCARD` か `ERROR` が立っていれば、打ち切る。標準出力を flush し、標準エラーに「cancel 節で例外が抑制されました: …」を記録して、状態を消す。
- `YIELD` が立っていれば、`P` を生きている値に含めたまま自分のフレームも継続に含めて戻る。再開されたら同じ処理を続ける。
最後に `P` を戻して伝播を続ける。

**`perform`**
1. 連鎖から、エフェクトが一致する最も内側の `hr` を探す。
2. `saved = ctx.handlers`、`ctx.handlers = hr.parent` とする。
3. 節を上から試す(パターンを照合し、合えばガードを評価する。深さは `p+1`)。
4. 選んだ節の分類で分ける。
   - T: 本体を末尾でなく呼ぶ。末尾 resume の `resume(v)` は「`v` を返す」に、`resume` しない値 `v` は「`DISCARD(hr, Value v)` を立てて戻る」に下ろしてある。戻ったら、どちらの場合も `ctx.handlers = saved` にする。
   - N: `ctx.handlers = saved` にし、`DISCARD(hr, NeverBody)` を立てて戻る(ガードは先に評価してある。Q4)。
   - G: `ctx.handlers = saved` にし、切り取りの先頭として `saved` と `Δ = p − h` を記録して、`YIELD` を立てて戻る。

**`rt_resume(K, v)`**: 節の中の末尾でない `resume(v)` は、`v` を評価し、`K.used` なら実行時エラーにする。そうでなければ `used` を立てて `rt_resume` を末尾でなく呼ぶ。
- 写し戻す前に `K.hr.parent = ctx.handlers`、`ctx.handlers = 切り取りの先頭` とする。
- ネイティブでは、区間を値スタックに写し戻し、各フレームの深さを `c − h` だけずらし、最下段に「ネイティブの呼び出し元へ戻る」印を置いて `interp_continue(ctx)` を呼ぶ。
  インタプリタは最上段のフレームの再開点から続け、印に達したら戻る。こうして、取り出したフレームはインタプリタで最後まで走る(脱最適化)。新しい呼び出しは入口の表を通って JIT に戻る。
  `--tier jit-only` でもこの経路を通る(P251)。
- Wasm では、構造体の列の内側から順に、再開の入口で各関数を呼ぶ。
- 写し戻した計算は `rt_handle` の手順 2〜7 で終わる。再開した計算の中の `return` 節の値や、`resume` しない節の値は、ハンドラ式の値ではなく、この `resume` の値になる(§13.6)。
- 再開の途中で `YIELD` が立ったら、まだ走らせていないフレームを継続の後ろに足して戻る。`DISCARD` か `ERROR` が立ったら、残りのフレームにも状態を注入して順に巻き戻し、その中の `cancel` を走らせる。
- G の節の中の末尾の `resume(v)` は、「`K` を `v` で末尾再開せよ」という印を立てて戻る。呼んだ側の `rt_handle` または `rt_resume` は、自分を `rt_resume(K, v)` の末尾呼び出しで置き換える(一定の領域。fx R6)。
- 節が値 `r` で戻ったときは次のとおりである。
  - `K` を使っていれば、`r` がハンドラ式の値になる。
  - 使っていなければ、`DISCARD(hr, Value r)` を注入した `rt_resume` を末尾呼び出しする。`K` の中の `cancel` が内側から走り、付け直した `hr` の手順 3 が `r` を返す(§13.6 の「値が決まった後で破棄」)。
- 節が `resume` の前に脱出したら、同じ状態を注入した `rt_resume` を末尾呼び出しする。順序は `K` の中の `cancel`、`hr` の `cancel`(手順 6)、外側である(fx R3 の resumeinnerpre、fid §6 の preresume.kel)。
- 節が `resume` の後に脱出したら、`hr` はもう連鎖にいないので、そのまま伝播する。

**難しい場合の照合**(どれも既存の cram が固定している。下の動きは規約から推論したもので、まだ実行していない。【推論・要検証 M89】)

| 試験 | この規約での動き |
|---|---|
| cancelperform | 実行時エラーの伝播中の `cancel` が N を起こし、その `DISCARD` を防壁が打ち切る。元の `ERROR` が続いて 3 で終わる |
| cancelnormal / cancelsame | 2 つ目の `DISCARD` を防壁が打ち切り、1 つ目の伝播が続く |
| cancelresume / via / two | 防壁の中の `cancel` が、まだ連鎖にいる `H` の G を起こす。防壁のフレームは `P` を持ったまま取り出される。`resume(5)` で再開すると `cancel` の続きが走り、`P` が付け直した `H` の `rt_resume` に届く。throw の節の値 7 が `resume(5)` の値になる |
| resumeinner* / clauseerr / clausestop | 付け直した `hr` を通るかどうかで、`cancel` が 1 回走るか走らないかが決まる |
| retry / retrycancel* | N の本体と `handle` が末尾呼び出しなので、一定の領域で走る |

**採らなかった案**
- ネイティブのファイバー(tg、native): 往復は 1.8 ns と安い(E20)。しかし WasmGC では使えず、`cancel` の順序の実装と継続の形が 2 系統になる。G のハンドラの中の深い再帰の限度も後段で変わる。M93 の測定で必要と分かったときだけ、LLVM の後段の最適化として検討する(P240、V204)。
- exnref、landingpad: 機構が 3 つになり、cancelresume には例外の途中の状態をフレームに写す別の規約が要る(V205)。
- JSPI(native D541): 非同期で、最も近い `promising` の境目までしか止まらない。スタックは 984 KB で伸びず、深さの計数が守れない(E9)。
- WasmFX: フラグが要り、落ちる(E9。V211)。
- 選択的 CPS: 行多相の高階関数がほぼすべて CPS 側に入る(fx §6.1)。

### 5.7 バイトコードとインタプリタ(D535)

- バイトコードは LIR の関数を 1 対 1 に符号化したもので、関数を最初に呼ぶときに作る。ファイルには書かない。
- レジスタ機械で、命令は 32 ビットの語の列である(命令番号 8 ビットと被演算子)。スロットが 256 を超える関数には wide 形を使う。
- フレームは分割値スタックに置き、JIT と同じ形にする。インタプリタの中の呼び出しはネイティブのスタックを使わない。
- 末尾呼び出しはフレームを再利用する。再開点の番号から命令の位置への表を持つので、JIT が作ったフレームもインタプリタが続けられる。
- 振り分けは Rust の `match` の平坦なループで行う(E7)。レコードの選択と更新は、呼び出しの位置ごとのインラインキャッシュで速くする。

### 5.8 LLVM ORCv2(D536、D537、D538)

- `keleut-llvm::sys` は llvm-sys の薄い包みである。文脈は `LLVMContextCreate` で作り、`LLVMOrcCreateNewThreadSafeContextFromLLVMContext` で包む(LLVM 21 以降は `GetContext` が無い。sl)。
  模塊 1 つに文脈 1 つを使い、IRBuilder の C API で組む。段を上げた関数には `default<O2>` をかける(E1)。
  実行時の関数は `LLVMOrcAbsoluteSymbols` で登録する。
- 呼び出し規約は `tailcc i64 @f(ptr %ctx)` の 1 つの型にする。測ったのはこの形である(【実測】E2〜E4)。
  - 呼ぶ側は、引数を値スタックの次のフレームの位置に書き、`ctx->callee = fid` を書き、`ctx->entry[fid]` を間接に呼ぶ。末尾なら `musttail` にする。
  - 戻り値は一様な語か `0x2` である。
  - 全関数が同じ型なので、間接呼び出しを含むすべての末尾呼び出しを `musttail` にできる。
- スタブ: Rust は `tailcc` の関数を書けない(E7)。そのため、起動時に小さな LLVM の模塊として次の 2 つを作る。
  - `interp_stub`(tailcc): `ctx->callee` を読んで Rust の `interp_run(ctx)`(ccc)を呼ぶ。戻りが「末尾呼び出しの依頼」なら、`entry[依頼先]` を `musttail` する。
  - `enter_tailcc`(ccc): Rust から tailcc の関数を呼ぶ入口。
  `tailcc` から `ccc` への `musttail` は拒まれる(E3)ので、末尾の境目はすべて tailcc のスタブを通す。
- フレーム: JIT の関数は、末尾でない呼び出しの前に、生きている値を**すべて**スロットに書き、再開点の番号を見出しに書く(D538)。
  戻った後は、インタプリタと同じ形の値スタックのフレームが残る。
  費用(スロットへの書き込み、呼び出しごとの番兵の比較と深さの書き戻し、境目での Int64 と Float64 の箱)は v1 で受け入れ、M91 と M93 で測る(V214)。
  レジスタで引数を渡す案(native D535)は、M93 で交互の末尾呼び出しを測り直したうえで採る。通らなければ今の形に留める(V206)。
- shadow stack: 共有の値スタックが shadow stack の役を果たす。LLVM の `gc "shadow-stack"` の戦略は JIT でも動くと測った(【実測】sl の gc)。しかし使わない。インタプリタのフレームと継続の区間に、2 つ目の根の仕組みが要るからである。
- JIT には landingpad も eh_frame の登録も要らない。再開点の入口の `switch` も要らない(再開はインタプリタが行う。D532)。
- 予備の検査: JIT の入口と、インタプリタの入れ子の入口で、ネイティブのスタックポインタを `ctx` の下限と比べる。超えたら 70 で終わる(論理的な限度より先に起きるのは不具合の印。D546)。

### 5.9 段の切り替え(D539、D540)

- 関数 id ごとに、入口の表 `entry[id]` と呼び出しの回数を持つ。`entry` は最初 `interp_stub` を指し、翻訳が済んだら原子的に 1 回だけ書き換える(E5)。
  翻訳は別のスレッドで行ってよい。段がいつ上がっても結果は変わらないからである(論理的な深さは段に依らない)。
- インタプリタは関数の入口で回数を 1 増やす。自己の末尾呼び出しでフレームを再利用する場合も数える。
- 移り方は次のとおりである。
  - インタプリタ → JIT(末尾でない): `enter_tailcc` で `entry[id]` を呼ぶ。
  - インタプリタ → JIT(末尾):
    - 呼び出し元のフレームが、この `interp_run` の起動の**最下段**なら、「`id` へ末尾呼び出し」を返す。スタブが `musttail` するか、最上位の駆動ループがトランポリンになる。
    - 最下段でなければ、フレームを外してから JIT を普通に呼ぶ。その先で再びインタプリタに入れば最下段になるので、交互の末尾呼び出しでもネイティブのスタックは 1 段しか伸びない(native 4.8)。
  - JIT → どちらでも: `entry[id]` を `musttail` するか、普通に呼ぶ。
- OSR と逆最適化(投機の取り消し)は作らない。JIT は投機をせず、熱い反復は必ず関数の入口を通る(tg §3.6)。
- 試験の段の設定は次のとおりである。
  - `interp-only`。
  - `jit-only`: 対象の関数をすべて事前に翻訳する。
  - `threshold=N`。
  - `alternating=SEED`: 呼び出しごとに、種から決まる擬似乱数で段を選ぶ。全関数を事前に翻訳しておく。
  - `mixed=SEED`: 種で決まる半分の関数だけを翻訳する。
  組み合わせの試験には、取り出しと再開が必ず段をまたぐ形を `conformance/effects/` に置く。

### 5.10 WasmGC(D541〜D545)

**値**

| Keleut | WasmGC |
|---|---|
| 一様な値 | `eqref` |
| Int32 | 局所では `i32`。一様な位置では、31 ビットに収まれば `i31ref`、収まらなければ `(struct i32)` |
| Boolean、Unit、引数の無いコンストラクタ | `i31ref` |
| Int64、Float64 | 局所では `i64`、`f64`。一様な位置では `(struct i64)`、`(struct f64)` |
| String | `(array (mut i8))`(JS の文字列には写さない) |
| レコード、データ | `(struct i32 (ref $AnyArr))`(形の id か、コンストラクタの番号) |
| ヴァリアント | `(struct i32 eqref)` |
| クロージャ | `(struct i32 (ref $FnN) (ref $AnyArr))`。引数の数ごとの部分型 |
| `Ref`、配列 | `(struct (mut eqref))`、`(array (mut eqref))` |
| フレームの記録 | `(struct i32 i32 (ref $AnyArr) (ref $I64Arr))`(関数、再開点、`any` の値、生の値) |

**制御**: 関数の型は `(func (param (ref null $Clo)) (param eqref)×N (param (ref null $Frame)) (result eqref))` で、最後の引数が null でなければ再開である。
- 非巡回の LIR を位相順に並べ、ブロックごとの入れ子の `block` と前向きの `br` で出す。
- 再開の入口は、関数の先頭の `br_table` で再開点のブロックへ前向きに飛ぶ。局所はフレームの記録から戻す。relooper もループも要らない。
  この配置と、Wasm の `rt_resume` が構造体の列を順に再開する手順は、まだ試作していない。【推論・要検証 M95】ブロックの入れ子が深くなる関数を V8 が受け付けるかも同じである。【推論・要検証 M94】
- 末尾呼び出しは `return_call` と `return_call_ref` で行う(【実測】E8)。状態語は大域 `$pending` に置く。exnref は使わない。

**trap しないこと**(D543): trap しうる命令は、モジュールの中の許可した補助関数だけに置く。
- 許可した命令は `i32/i64.div_s|rem_s|div_u|rem_u`、`trunc_f64_s`、`array.get/set` の添字。補助関数は先に検査し、失敗なら `ERROR` を立てる。
- `ref.cast`、`ref.as_non_null`、`unreachable` は型の健全性の上では失敗しないので、残してよい。それが trap したら不具合の印で、70 で終わる。
- `keleut-wasm` の試験の検査器は、wasmparser で全関数の命令を走査する。そのうえで、許可した補助関数の外に上の命令が無いことを確かめる。

**フレームの大きさ**(D544): 局所は生存区間で色分けして使い回す。
推定したフレームの大きさ(局所の数 × 8 + 定数)が予算 `B_wasm` を超える関数は、超えた局所を入口で確保する GC の構造体に置く(大きなフレームの形)。
`B_wasm` の初期値は 2 KiB で、M79 の測定で決める(V198)。【推論・要検証 M79】予算を超えた関数を大きなフレームの形にするしきい値も M79 と M94 で決める。【推論・要検証 M94】

**Node の起動**(D545): `keleut run --backend wasm` は `program.wasm`、`rt.wasm`、`main.mjs` を一時の場所に書き、`node` を子プロセスで起動する。
- `pre_exec` の中で `setrlimit(RLIMIT_STACK, S)` を呼ぶ。`S = (L+R) × B_wasm + 64 MiB` である。`--stack-size` には `S` の 90%(KB)を渡す。
  軟らかい限度は硬い限度までしか上げられないので、先に `getrlimit` で硬い限度を調べる。足りなければ Worker の経路を使う。
  起動の前に、`keleut` 自身の標準出力を flush する。
- 【実測】E12 は、`ulimit -s 2000000` と `--stack-size=1500000` で 1e7 段を測った。L と `B_wasm` から決まる `S` を V8 の `--stack-size` が受け付けるか(上限)は、まだ確かめていない。【推論・要検証 M79】
- `--stack-size` に上限があってこの方法が使えないときは、`Worker` の `resourceLimits.stackSizeMb` で走らせる(E12 で 1024 MB を確かめた。P248)。
- `stdio` は `'inherit'` にし、子のバイト列と終了状態をそのまま返す。子がシグナルで終わったら 70 にする。
- `main.mjs` は `process.versions.v8` を確かめ、Node は 26.9.0 以上を求める。
- 最上位で `RangeError` か `WebAssembly.RuntimeError` を受けたら、標準出力を書き終えてから 70 で終わる(不具合の印)。

**入出力と rtcore**: 出力は、i8 の配列を `rt.wasm` の線形メモリの 64 KiB のバッファに写し、`host.write(ptr, len)` を呼ぶ形にする(sw §4 の方法 B)。
- JS は `fs.writeSync(1, new Uint8Array(mem.buffer, ptr, len))` を、短い書き込みと `EAGAIN` に対して繰り返す。`EAGAIN` は `Atomics.wait` で 1 ms 待ってから再試行する。失敗は `ERROR(Io)` で、74 になる。
- `show(Float64)`、libm、形の表、バイト列の比較は、`rt.wasm` の export を import して使う。JS の数値の整形と `Math.sin` は使わない(E13)。

### 5.11 物理的なスタック(D546)

- ネイティブ: ミューテータは専用のスレッドで走らせる。スタックは `S_native = (L+R) × B_native + 64 MiB` を予約する。
  `B_native` は、1 段あたりの最大のバイト数である。内訳は、JIT のフレーム、スタブ、非末尾で段を交互にまたぐときの `interp_run` のフレームである。
  初期値の 1 KiB は推論で、M91 で測って決める(V201)。【推論・要検証 M91】1 GiB 級のスタックを WSL2 で予約できるかは M87 で確かめる。【推論・要検証 M87】インタプリタ同士の呼び出しはネイティブのスタックを使わない。
- `--native-stack BYTES` で変えられる。tg の `ulimit -s 512` の試験は、専用のスレッドでは効かないので、`--native-stack 512k` で行う。
- 予備の検査(5.8 節)が論理的な限度より先に起きたら、70 と kconform の失敗にする。

## 6. Rust のフロントエンド(D547、D548)

- **時期**: 独立した系統として、kir crate(M84)の直後から M96〜M99 で移す。LLVM と WasmGC の完了を待たない。
  所有者の動機はコンパイルの速さなので、この系統を後段の最も難しい部分の後ろに置かない(審査 3)。
- **順序**(fp §2): 字句と ASI → 構文と脱糖 → 宣言表、単一化、型の表示 → elab(型式、パターン、式、let、let rec、宣言、module、import) → 網羅性 → ドライバの終了状態 → KIR の書き出し。
- **構文解析**: 手書きの再帰下降にする。文法は LALR(1) で衝突が無く、優先順位は非終端の階層で表してある(fp §3.1)。
  受理のずれが収束しなければ、`.mly` を lalrpop 0.23.2 に写して受理の基準にする。
- **型**: arena と添字の Union-Find にする。ノードの注釈は `NodeId` で引く別表に置き、大域の状態 81 か所は 1 つの文脈の構造体に集める(fp §1.3)。REPL の取り消しは snapshot で行う。
- **検証**(価値の高い順。fp §4.2):
  1. 終了状態(cram の全入力)。
  2. `keleut dump tokens|ast` と `diktor --dump-tokens|--dump-ast` の一致。
  3. `check` の型の行(933 行)の一致。
  4. 正準化した KIR のテキストのバイト単位の一致。記号名が安定しているので、正規化は要らない。
  5. 診断の種別、位置(コードポイントで数える)、警告の件数。日本語の文面は Diktor のものを写すが、比較では正規化する(§18 の外。P245)。
- **速さの関門**(D548): M98 で次の 3 つを `hyperfine` か 10 回の中央値で測り、実施記録に書く。
  - `keleut check` と `diktor --type-check` を、`test/sample/stubs.kel test/sample/sample.kel` で比べる。
  - コーパスの 1,046 本の合計で比べる。
  - sample.kel を module で 100 回複製した合成の大きな入力で比べる。
  受け入れの条件は、3 つとも `keleut check` が `diktor --type-check` 以下の時間であることである(P250)。

## 7. 試験(D549)

### 7.1 kconform

- kconform は cram の `.t` を自分で読む(`  $ ` のコマンド、`  > ` の続きの行、期待の出力、`[N]`)。
  各ファイルを一時のディレクトリで実行し、PATH の先頭に `diktor` の shim を置く。dune の cram は差をファイル単位でしか報せないので、コマンド単位の比較と既知の差の照合のために自前で読む。
- shim の振り分けは次のとおりである。

  | 呼び出し | 最初 | 切り替えた後(切り替えるマイルストーン) |
  |---|---|---|
  | 実行(旗なし、`--prelude`、`--no-prelude`、`--import-path`) | M84〜M87 は本物の diktor。M88 から、本物の `diktor --emit-ir` が 0 なら `keleut run FILE.kir`、0 でなければその出力と終了状態をそのまま返す | `keleut compat-diktor`(M99) |
  | `--type-check`、`--strict-exhaustive` | 本物の diktor | `keleut check`(M97 から部分ごと、M98 で全部) |
  | `--dump-tokens`、`--dump-ast` | 本物の diktor | `keleut dump`(M96) |
  | `--repl` | 本物の diktor | `keleut repl`(M100) |

- `OCAMLRUNPARAM=l=…` を使うブロックは語数を写さない。理由「限度は I(§15.5)」で `known-diffs.toml` に登録して除外する(V213)。
  同じ意図の試験は `conformance/depth/` に `--max-depth` で作り直す。例えば `--max-depth 10000` の下で、末尾呼び出し、末尾 resume、N の再試行は 100,000 回完走し、非末尾の再帰と非末尾の resume は 3 で終わる。
- `known-diffs.toml` の各項目には、ファイル、コマンドの行、組み合わせ、理由、台帳の番号を書く。登録の無い差が 1 件でもあれば失敗にする。
- 比べるのは、標準出力のバイト列と終了状態(§18)である。標準エラーは、種別の語の後ろを切り、警告は件数だけを残して、標準出力との前後関係を比べる(fp §4.2 (c))。

### 7.2 組み合わせ

| 名前 | 書き手 | 実行 |
|---|---|---|
| `dk` | Diktor | 木の評価器(基準) |
| `dk-ir` | Diktor | `diktor --run-ir` |
| `ki` | Diktor | `keleut --backend interp --tier interp-only` |
| `kj` | Diktor | `--backend jit --tier jit-only` |
| `kt` | Diktor | `--tier threshold=1` |
| `ka` | Diktor | `--tier alternating=1..8` |
| `km` | Diktor | `--tier mixed=1..4` |
| `kw` | Diktor | `--backend wasm` |
| `kr-*` | Rust | 上の各組(M99 から) |
| `x-ir` | Rust | `diktor --run-ir`(Rust が書いた KIR を Diktor が実行する) |

- `ki kj kt ka km kw` は、既知の差の一覧に関係なく、互いに完全に一致しなければならない(D499)。
- 夜間の試験では、`--gc-stress` と `--no-yield-prune` の組み合わせも回す。
- 深さの試験(`conformance/depth/`)は `dk-ir` と RustKeleut の全組で比べる。`dk` とは比べない。
  限度に触れない試験は既定の L で走らせる。予備の検査(70)が出たら失敗にする。
  深い非末尾の再帰(L − 10 段)を、既定の L で `ki kj ka kw` が 0 で終えることも求める。

### 7.3 そのほか

- float show: fltcmp の 2,000,000 件(522 件の 2 の冪の付近と、ちょうど中間の値を含む)と、`-0.0`、NaN、`1e16` の境目、非正規化数を、rtcore の x86_64 版と wasm32 版(Node で実行)で glibc と比べ、差 0 件を求める。
- libm: 1,000,000 件の乱数と特殊値で、x86_64 版と wasm32 版のビット一致を求める(V200)。
- KIR: コーパスの全件で `keleut kir dis` と `diktor --emit-ir-text` が一致し、テキスト → バイナリ → テキストの往復が一致すること。
  同じ入力を 2 つのプロセスで書き出したバイト列が `cmp` で一致すること。
  `kir-bad/`(ビット反転、切り詰め、範囲外、背骨の外の `resume tail`)が 65 で、落ちずに拒否されること。
- Wasm: 全出力が wasmparser の既定の機能集合(GC、tail_call、exceptions。stack_switching は無し)で検証に通ること。trap の検査器に通ること。
- 出力: `conformance/bytes/` に、不正な UTF-8、NUL、1 MiB を超える文字列、非ブロッキングのパイプ(`| (sleep 1; cat)`)、閉じた標準出力(74)の試験を置く。
