# RustKeleut の実行時：段階的コンパイルとメモリ管理の設計案

調査日 2026-10-24。対象は親リポジトリ ja/bleeding（bcb16f1）、diktor（6e49bbb）。
追跡対象のファイルは変更していない。
試作はすべて `doc/log/261024-1-spike/probe/tg/` に置いた。

各節では、**計測**（自分で実行して得た事実）、**仕様**（LangSpec と Diktor のソースから読める事実）、**背景知識**（既存の処理系についての知識。今回は確かめていない）、**推測**（設計上の判断）を分けて書く。

## 0. 結論

- 推奨は **案 A**：インタプリタと JIT が共有する、ファイバーごとの**値スタック**を中心にした構成である。
  値スタックは、インタプリタのレジスタ、JIT コードが GC の根を退避する場所、引数を渡す場所を兼ねる。
  GC は動かさないマークスイープで、根は全ファイバーの値スタックをたどって正確に得る。
  LLVM の関数はすべて同じプロトタイプ `tailcc i64 (ptr ctx)` を持たせ、間接呼び出しのどこでも `musttail` が使えるようにする。
  段の切り替えは関数単位で行う。呼び出しの回数を数え、入口の表の 1 語を書き換える。
- 逆最適化と OSR は**作らない**。
  JIT コードが投機をしないので逆最適化は要らない。
  Keleut には反復の構文がなく反復は再帰で書く（§5.7 冒頭、§6.3）ので、熱い反復は必ず関数の入口を通り、関数単位の切り替えで足りる。
- インタプリタから JIT へ、JIT からインタプリタへの末尾呼び出しを交互に 1e8 回続けても、`ulimit -s 512` の下でスタックが伸びないことを確かめた（§3.3）。
  `musttail` を外すと SIGSEGV（終了状態 139）になる。
- LLVM のステートポイントは v1 では使わない。
  LLVM 22 の `rewrite-statepoints-for-gc` は `musttail` の呼び出しを壊すことを確かめた（§5.4）。
  回避策はあるが、ステートポイントで見つかるのは JIT のフレームだけで、インタプリタのフレームとファイバーの根は別の仕組みが要る。
- エフェクトの継続には、プールしたネイティブスタック（ファイバー）を使う。
  `resume` は 1 回までしか呼べず、値として持ち出せない（§13.5）ので、継続は複製の要らないスタック片で表せる。
  切り替えの往復は 1.8 ns だったが、mmap でスタックを毎回作ると 1 回 7.1 µs かかった（§6.2）。スタックはプールする。
- WasmGC のバックエンドは、ホストの GC と `return_call` をそのまま使い、Rust 側の GC は要らない（§7）。
  ただし Node 26 では、標準のままではスタック切り替えが使えない（wasmfx は実験フラグ）。
  一般の `resume` は、このバックエンドだけ CPS か状態機械に変換する必要がある。
- 値の表現は、型付きの IR を前提にする。
  単相の箇所では Int32、Int64、Float64 を箱に入れずに扱う。
  一様な語が要る箇所（多相の引数、ヒープのフィールド）だけ、最下位ビットのタグを使う。
  タグが 1 なら即値（Int32、Boolean、Unit、引数のないケース）、0 ならポインタである。
  NaN ボックス化は採らない（§2）。

## 1. 仕様から来る制約

### 1.1 仕様（LangSpec と Diktor のソース）

| 制約 | 根拠 | 実行時への帰結（推測） |
| --- | --- | --- |
| 反復の構文がなく、末尾呼び出しは一定の領域で評価しなければならない | §5.7 冒頭（「Keleut には反復の構文がなく、反復は再帰で書く」「末尾呼び出しだけでつながった再帰は、回数によらず一定の領域で評価できる」） | 段の境目をまたぐ末尾呼び出しも一定の領域で行う。OSR は要らない |

### 1.2 Diktor の現状（仕様に準じる事実）

- 値の型は `diktor/lib/value.ml:81-96`。
  レコードは `(oid * t) list` で、スコープ付きラベルにより重複してよく、順序があり、先頭が最新である。
  `Unit = VRecord []` である。
- エフェクトは OCaml 5 の `Effect.Deep` に写している（`interp.ml:20-35`）。
  プロトコルは `type _ Effect.t += Op : oid * t -> t Effect.t`（`value.ml:261`）と、`exception Unwind of oid * unwind`（`value.ml:267`）である。
  ハンドラの活性化ごとに id を振る。
- 末尾呼び出しは、評価器の末尾位置を OCaml の末尾呼び出しに保つ規約で守っている（`interp.ml:43-54`）。
  操作節の本体、ガード、`cancel` 節は例外ハンドラで包むので末尾にならない。末尾の背骨にある `resume` だけは包みを抜けてから発行する。
- 回帰テストは `diktor/test/tail_calls.t` にある（retry、retrycancel、retrycancelvia）。
  RustKeleut でも、同じ観点のテストを最初の段から持つべきである。

## 2. 一様な値の表現

### 2.1 選択肢

| 方式 | 即値にできるもの | 箱が要るもの | GC と参照カウントでの判定 | WasmGC との対応 |
| --- | --- | --- | --- | --- |
| NaN ボックス化 | Float64、Int32、Boolean、ポインタ（48 ビット） | Int64 | 上位 16 ビットのマスクと比較 | 対応しない（WasmGC にはこの表現がない） |
| 最下位 1 ビットのタグ（OCaml と同じ） | 63 ビットの整数（Int32 を含む）、Boolean、Unit、引数のないケース | Int64、Float64 | `w & 1` の 1 命令 | `i31ref` が近い。ただし 31 ビットである |
| 1 語に複数ビットのタグ（下位 3 ビット） | 上と同じものに加えて、種類の区別 | 同上 | 少し複雑 | 同上 |
| 型付き IR と箱なし（推奨と組み合わせる） | 単相の箇所の Int32、Int64、Float64 は機械の型のまま | 多相の箇所に渡すときだけ箱に入れる | 型から静的に分かる | WasmGC の `i32`、`i64`、`f64`、`(ref $T)` にそのまま写せる |

### 2.2 推測と推奨

- Keleut は静的に型付けされ、辞書渡しを使い、実行時に型で分岐しない（§1.1 の最後の行）。
  そのため、一様な語が要るのは、多相の型パラメータの位置、ヒープのフィールド、クロージャの環境だけである。
  IR に型（少なくとも表現の種類：`i32`、`i64`、`f64`、`word`）があれば、単相の関数の中の数値は箱に入れずに済む。
  **値の表現をどうするかは、IR が型を持つかどうかに従属する。** この点は IR の調査担当と合わせる必要がある。
- 推奨：IR を型付きにする。`word` は 64 ビットで、最下位ビットが 1 なら即値、0 ならポインタとする。
  - Int32 は `(n << 1) | 1` とする。Boolean、Unit、引数のないケースのタグも即値にする。
  - Int64 と Float64 は、`word` の位置に置くときだけ箱に入れる。
  - ポインタは 8 バイト境界にそろえる。ヘッダの 1 語に、種類、フィールド数、GC の印を置く。
- NaN ボックス化を採らない理由（推測）：
  1. コンパイラの処理は、木、写像、文字列、整数が中心で、Float64 は熱い型ではない。
  2. Int64 はどちらの方式でも箱に入るので、NaN ボックス化の得が小さい。
  3. WasmGC の表現との差が大きくなり、IR から下ろす処理が 2 系統に分かれる。
- レコードとスコープ付きラベル（§7）：
  多相の関数ではフィールドの位置が静的に決まらない。
  v1 では、レコードを「形の記述子（ラベルの列）へのポインタとフィールドの配列」で表す。
  選択は記述子を引き、呼び出し箇所ごとのインラインキャッシュで速くする。インタプリタと JIT のどちらでも同じ方法が使える。
  ラベルの位置を証拠として渡す方式（行多相の index passing。背景知識：Gaster と Jones、Leijen の論文）は、IR の型付けと合わせて後で判断する。

## 3. インタプリタと JIT で共有する呼び出し規約と、段の切り替え

### 3.1 制約（計測と仕様）

- **計測**：Rust 1.98.1 の stable では `become` が使えない。

  ```
  $ rustc --edition 2024 become.rs
  error[E0658]: `become` expression is experimental
  ```

  そのため、Rust で書いたインタプリタは平坦なループにするしかない。
  インタプリタからネイティブコードへ末尾呼び出しを「行う」ことはできず、「頼む」ことしかできない。
  Rust では `tailcc` の関数も定義できない。
- **背景知識**：LLVM の `musttail` は、呼び出し元と呼び出し先のプロトタイプが一致することを求める。`tailcc` と `swifttailcc` ではこの条件が緩む。
  そこで推奨案では、すべての関数を同じプロトタイプにして、この問題をなくす。

### 3.2 推奨する規約（推測）

```
ctx:   Ctx*  （値スタックの先頭、限界、ファイバー、入口の表、GC の状態など）
関数:  tailcc i64 @fn(ptr %ctx)    ; 引数は ctx が指す値スタックに積んである
戻り値: i64（一様な word。箱なしの戻り値は、型付きの変種を後で足す）
```

- **インタプリタのフレーム**と**JIT のフレーム**は、同じ値スタックの上に同じ形で並ぶ。
  1 つのフレームは、戻り先の種類、関数の id、スロットの列からなる。
  インタプリタのレジスタはスロットそのものである。
  JIT のコードは、呼び出しや割り当てをまたいで生きる `word` をスロットへ書き出す。
  GC が動かないので、呼び出しの後に読み直す必要はない。
- **入口の表**：関数 id ごとに 1 語の入口を持つ。
  最初は「インタプリタへの入口のスタブ」を指し、コンパイルが済んだら JIT コードを指すように 1 回書き換える。
  JIT から JIT への直接呼び出しも、この表を通す。
  背景知識として、ORC の `LLVMOrcCreateLocalIndirectStubsManager` も同じ役割を果たせる。ただし自前の表のほうが単純である。
- **呼び出し回数**：インタプリタは関数の入口で数を 1 増やし、しきい値（仮に 1000。根拠のない初期値で、計測して決める）を超えたらコンパイルを頼む。
- **末尾呼び出し**：
  - JIT から呼び出し先へ：自分のフレームを捨て、引数を書き、`musttail call tailcc %entry(ctx)` とする。呼び出し先がインタプリタでも JIT でも同じ形である。
  - インタプリタの中で：フレームを再利用し、ループの先頭へ戻る。
  - インタプリタから JIT へ：インタプリタがネイティブのスタブから入った場合は、`interp_run` から「この入口へ末尾呼び出しせよ」という要求を返す。スタブはそれを受けて `musttail` する。最上位の駆動ループから入った場合は、駆動ループがトランポリンとして呼び出す。
  - こうすると、境目を何回またいでもネイティブのフレームは増えない。フレームの並びは「スタブ → `interp_run`（戻る）→ スタブが `musttail` → 呼び出し先」となる。
- **スタブと最上位の入口**：Rust で `tailcc` を書けないので、起動時に小さな LLVM モジュールとして生成するか、ビルドのときに clang か llc で作ったオブジェクトをリンクする。
- **スタックの限界**：JIT の関数は入口で、ネイティブのスタックポインタと値スタックの先頭を、ctx が持つ限界と比べる。超えたら実行時エラーの経路へ進む（§15.5）。

### 3.3 計測：交互の末尾呼び出し

試作 `tg/tier.ll` と `tg/interp.c` を使った。
`f` は JIT コード、`g` は C で書いたインタプリタの代役である。
`f` は `g` を `musttail` で呼ぶ。`g` は「f への末尾呼び出し」を `{0, &f}` として返し、スタブがそれを `musttail` する。

```
$ clang -O2 -c -fPIC interp.c -o interp.o
$ (ulimit -s 512; lli -jit-kind=orc -extra-object=interp.o tier.ll)
result=100000000 interp_steps=50000000          # 0.078 s
$ (ulimit -s 512; lli -O0 -jit-kind=orc -extra-object=interp.o tier.ll)
result=100000000 interp_steps=50000000          # 0.087 s
$ musttail を普通の call に置き換えた notail.ll
no-musttail O0 exit=139                          # SIGSEGV
```

- 事実：1e8 回の交互の末尾呼び出し（そのうちインタプリタの代役を 5e7 回通る）が、512 KiB のスタックで完走した。`-O0` でも完走したので、最適化に頼らずに `musttail` だけで保証できている。
- 注意：試作は 2 語の構造体を返している。これは SysV の ABI に頼った書き方である。本番では、呼び出し先と引数を ctx に置き、1 語だけを返す形にする。
- `lli -jit-kind=orc` は LLJIT と同じ ORCv2 の経路を使う（背景知識）。


- llvm-sys 221.1.1 は、手元の LLVM 22.1.8 でビルドでき、LLJIT を作れた。
- inkwell 0.11.0 には `llvm22-1` の feature がある。ただし公開は 2026-10-20 で、まだ 4 日しか経っていない（crates.io の API で確認）。
  背景知識として、inkwell は ORCv2 をほとんど包んでいない。
  推奨：JIT の部分は llvm-sys を直接使う。IR を組み立てる部分は、llvm-sys の上に薄い包みを自作するか、inkwell が落ち着いてから使う。

### 3.5 背景知識との比較

- **HotSpot**：インタプリタとコンパイル済みコードでは呼び出し規約が違い、i2c と c2i のアダプタで変換する。推奨案は規約を 1 つにするので、アダプタが要らない。
- **V8**：Ignition（レジスタ機械のバイトコード）、Sparkplug（バイトコードを直接機械語にする。フレームの形はインタプリタと同じ）、Maglev、TurboFan の順に上がる。推奨案の v1 は、Sparkplug と同じ「フレームの形を共有する」考え方に近い。
- **LuaJIT**：トレース JIT とスナップショットによる脱出で、投機的である。Keleut の v1 には要らない。
- **JavaScriptCore**：LLInt、Baseline、DFG、FTL の 4 段で、OSR の出入りがある。投機をしないので、ここまでは要らない。
- **OCaml のネイティブ実行時**：根はフレーム記述子（ステートポイントに相当）でたどる。OCaml 5 はファイバーでエフェクトを実装し、スタックあふれを入口の検査で見つける。

### 3.6 OSR と逆最適化（推測）

- 逆最適化：JIT が型や値を推測して特化しない限り要らない。v1 では型付き IR をそのまま下ろすだけにし、投機をしない。
- OSR：反復が必ず関数呼び出しになるので要らない。1 回の呼び出しの中で長く回るのは、`Array.each` のような組み込みの反復か、非常に長い直線の本体だけである。前者は組み込みを JIT 側でも実装すれば済む。
  「やらない」と決めておけば、フレームの形を段ごとに変える自由が後で得られる。

## 4. 候補となる構成

### 案 A：値スタックを共有し、GC は動かさないマークスイープ（推奨）

- 構成：§3.2 の規約。ファイバーごとに、ネイティブスタックと値スタックを 1 組ずつ持つ。
  GC は動かさないマークスイープで、大きさの種類ごとの空きリストか、Immix 風のブロックを使う。
  根は、全ファイバーの値スタック、グローバル、ハンドラの記録である。
- 長所：
  - 根の見つけ方が、インタプリタ、JIT、停止中の継続のすべてで同じになる。
  - LLVM の GC 機能に頼らない。
  - `musttail` と両立することを計測で確かめた。
  - インタプリタと JIT が同じフレームを読むので、デバッガや実行時エラーのスタックトレースを 1 つの仕組みで作れる。
- 短所：
  - JIT のコードはスロットへの書き出しが増え、レジスタを使い切れない。
    背景知識として、LLVM はスロットへの書き込みを消せない。値スタックが外から見えるからである。
  - 動かさない GC は断片化し、割り当てがバンプポインタより遅い。

### 案 B：レジスタで引数を渡し、ステートポイントを使う（案 A の発展）

- 構成：`tailcc i64 (ptr ctx, i64 a0, ..., i64 aN)` のように引数をレジスタで渡す。値スタックへは、呼び出しと割り当ての点で生きている値だけを退避する。
  さらに進めると、LLVM のステートポイントとスタックマップで JIT のフレームを直接たどる。
- 長所：熱い JIT コードが速くなる。動かす GC（コピーする世代別 GC）への道が開く。
- 短所：
  - フレームを見つける仕組みが、インタプリタ、JIT（スタックマップ）、ファイバーの 3 種類になる。
  - `musttail` との組み合わせで LLVM の不具合を踏む（§5.4）。
  - ORC で読み込んだオブジェクトから `.llvm_stackmaps` 節を取り出すには、メモリマネージャのコールバック（`LLVMOrcCreateRTDyldObjectLinkingLayerWithMCJITMemoryManagerLikeCallbacks`）が要る。
- 位置付け：案 A を v1 にし、計測で必要と分かってから B へ進む。引数の数が違うと `musttail` の条件が問題になるので、プロトタイプは「ctx と固定数 N 個の word」に統一する（推測）。

### 案 C：Perceus 型の参照カウントを IR に明示する

- 構成：RustKeleut の内部の下ろし（IR → 低水準 IR）で `dup` と `drop` を挿入する。不要になったセルは、その場で再利用する。
  背景知識：Koka の Perceus と Lean 4 がこの方式である。どちらも、Keleut と同じく正格な関数型言語で、Koka はエフェクトハンドラも持つ。
- Keleut に向いている点（仕様から）：
  - ヒープの書き換えは `Ref.set` と `MutableArray.set` だけで、循環ができるのは参照と可変配列を通したときと、`let rec` のクロージャだけである。
  - `let rec` の束縛群は、環境を 1 つ共有させ、兄弟のクロージャを「コードポインタと共有の環境」から作り直せば、循環を作らない（推測）。
  - 参照と可変配列はリージョン `h` に属し、`h` は `run` の結果の型に残せない（§14.1）。
    したがって `run` を抜けた時点で、`h` の参照はどこからも届かない。
    リージョンが自分の参照と可変配列の一覧を持てば、`run` を抜けるときに中身を `drop` して循環を断てる（推測）。
    ただし、継続を破棄したことによる脱出（§13.6）でも同じ後始末が要る。
  - 根をたどらないので、値スタック、スタックマップ、ファイバーのスタックを GC が走査する必要がない。段の境目との相性がよい。
  - WasmGC のバックエンドは、`dup` と `drop` を無視するだけでよい。
- 短所：
  - 増減の命令が至る所に入る。借用の推論とその場での再利用が効くかどうかは、低水準 IR の質に強く依存する。
  - 長く続く 1 つの `run` の中で作った循環は、`run` を抜けるまで解放されない。必要なら循環回収器を後で足す。
  - 解析のパスを RustKeleut の側に持つ必要がある。
- 位置付け：案 A と並ぶ有力な対抗案である。性能の決め手は「コンパイラのような割り当ての多い処理で、追跡型 GC と Perceus のどちらが速いか」で、これは試作して測るまで分からない。
  案 A の値スタックと規約は、案 C でもそのまま使える（スロットを根として読まないだけになる）。
  そこで、**v1 は案 A で作り、低水準 IR に所有権の注釈を置く余地を残す**ことを推奨する。

### 参考：全面 CPS とヒープのフレーム

すべてを CPS に変換し、フレームをヒープに置く方式もある。
ファイバーが要らず、根の扱いも末尾呼び出しも自明になる。
ただし、ネイティブのバックエンドとしては性能の水準が 1 段落ちる。
この形は WasmGC のバックエンドで、エフェクトを持つコードだけに使う（§7）。

### 比較

| 観点 | A（推奨） | B | C |
| --- | --- | --- | --- |
| v1 の実装量 | 中 | 大 | 大（所有権の解析） |
| 境目の末尾呼び出し | 計測で確認済み | 回避策が要る（§5.4） | A と同じ |
| 根の見つけ方 | 値スタックだけ | 3 種類 | 要らない |
| ファイバーとの相性 | 値スタックを片ごとに持つ | スタックマップをファイバーごとにたどる | 継続も参照カウントで持つ |
| 割り当ての速さ | 空きリスト（後で世代別） | バンプポインタにできる | malloc 相当。再利用で減らせる |
| 停止時間 | 全体を止めるマーク | 世代別なら短い | ほぼない |
| WasmGC との共有 | 低水準 IR より上を共有 | 同左 | `dup` と `drop` を無視すれば共有できる |

## 5. GC の詳細（案 A）

### 5.1 v1

- 動かさないマークスイープを 1 スレッドで、全体を止めて行う。オブジェクトの大きさの種類ごとにページを分ける。
- 根：
  1. すべてのファイバーの値スタック（実行中のものも、継続として止まっているものも）。
  2. グローバルの表。
  3. ハンドラの記録（節のクロージャ、`cancel` 節）。
  4. Rust 側が一時的に持つハンドル。Rust のコードが Keleut の値を持つときは、必ず値スタックか明示のハンドルの枠に置くことを規則にする（推測）。
- 安全点：割り当てと呼び出しだけにする。反復の構文がないので、ループの後ろ向きの枝に検査を置く必要はない。
- **不変条件**：止まっている継続は、走っているファイバーと同じく根の集まりである。

### 5.2 保守的なスタック走査（検討して不採用）

- 背景知識：JavaScriptCore（Riptide）や Boehm GC は、ネイティブのスタックを保守的に走査する。
- 長所：JIT が退避をしなくてよく、LLVM の GC 機能も要らない。
- 短所：
  - タグ付きの整数がポインタに見える。とくに即値の Int32 は下位ビットが 1 なので区別できるが、箱のない Int64 と Float64 はポインタに見える。そのため、オブジェクトを誤って保持し続けることがある。
  - オブジェクトを動かせなくなる。
  - ファイバーのスタックをすべて走査する必要がある。
- 案 A の値スタックがあれば、保守的な走査が得をする点はほとんどない。

### 5.3 後で行うこと

- 世代別 GC（v3）：書き込みバリアが要るのは `Ref.set`、`MutableArray.set`、`let rec` の環境の差し替えの 3 か所だけである（§1.1）。
  ほかのオブジェクトは作った後に変わらないので、若い世代を短く保ちやすい。
  背景知識：OCaml の minor heap も、変更がまれなことに頼っている。
- MMTk（mmtk 0.33.0、rust-version 1.84 を `cargo info` で確認）：
  Immix や世代別の計画をそのまま使える。動かす計画を使うには、正確な根と、オブジェクトを動かせることが前提になる。
  案 A の値スタックは根を正確に出せるので、v2 以降に MMTk へ乗り換えられる（推測）。

### 5.4 計測：ステートポイントと `musttail`

```
$ opt -passes=rewrite-statepoints-for-gc -S sp.ll        # 普通の呼び出しは正しく書き換わる
  %statepoint_token = call token ... @llvm.experimental.gc.statepoint.p0(...) [ "gc-live"(ptr addrspace(1) %x) ]
  %x.relocated = call coldcc ptr addrspace(1) @llvm.experimental.gc.relocate.p1(...)
$ llc -O2 sp2.ll -filetype=obj ; readelf -S sp.o
  [ 4] .llvm_stackmaps   PROGBITS
$ opt -passes=rewrite-statepoints-for-gc -S tc.ll        # musttail tailcc を含む関数
cannot guarantee tail call due to mismatched varargs
LLVM ERROR: Broken module found, compilation aborted!   (exit=134)
$ 呼び出しに "gc-leaf-function" を付けた tc2.ll
exit=0 ; %r = musttail call tailcc ... #1 ; llc の結果: jmp g@PLT  # TAILCALL
```

- 事実：LLVM 22.1.8 では、ステートポイントへの書き換えが `musttail` の呼び出しを可変長引数の `gc.statepoint` に変えてしまい、検証で落ちる。
  末尾呼び出しの箇所に `"gc-leaf-function"` を付ければ書き換えの対象から外れ、末尾呼び出しが保たれる。
- 推測：末尾呼び出しの後には呼び出し元のフレームが残らないので、その箇所は安全点でなくてよい。
  動かさない GC では、引数の値は呼び出し先の最初の安全点で根になるので、これで正しい。
  動かす GC でも、呼び出し先の入口より前に GC が起きないなら同じことが言える。
  とはいえ回避策に頼る形なので、案 B に進むときの危険として記録しておく。

## 6. エフェクト、ファイバー、GC の根

### 6.1 実装の選択肢

1. **ネイティブのファイバー**（推奨）：ハンドラごとに、ネイティブスタックと値スタックを組にした片を持つ。
   `perform` は、ハンドラの片へ切り替える操作である。
   `resume` は、止めておいた片の連鎖へ戻る操作である。
   `resume` を呼ばずに節を抜けたら、片の連鎖を内側から外側の順に巻き戻し、それぞれの `cancel` 節を走らせてから解放する。
   背景知識：OCaml 5 では、最も内側でないハンドラへ `perform` すると、片の**連鎖**が止まる。継続はその連鎖で、`resume` で付け直す。Wasmtime も、ホストの非同期処理にファイバー（wasmtime-fiber）を使っている。
2. 選択的 CPS：エフェクト行が空の関数は直接形式のままにし、それ以外を CPS にする。
   ただし Keleut は行多相を多用する（例：`Array.each : [A, E] (..., (A) => Unit @ E) => Unit @ E`、§14.3）。行変数を持つ関数はすべて CPS になり、ネイティブでは損が大きい。WasmGC のバックエンドで使う。
3. JSPI やスタックのコピー：Keleut の継続は節の外へ出ないので、コピーは要らない。

### 6.2 計測：corosensei 0.3.4

```
$ cargo run --release          # tg/fib/src/main.rs
acc=50000005000000 rounds=10000000
round trip ns = 1.8                       # 停止と再開の往復
create+run+drop ns = 7083.4               # 64 KiB のスタックを毎回 mmap で作って捨てる
```

- 事実：切り替えそのものは安い。スタックを毎回作ると、1 回あたり約 7 µs かかる。
- 推測：§13.6 の `try_` のように、呼び出しのたびにハンドラを立てる書き方が普通なので、スタックのプールは必須である。
  仮想アドレスを大きく予約し、ガードページを置き、実メモリは使った分だけ割り当てる。
  こうすれば、ハンドラの本体の中で深く再帰しても実メモリをあまり使わない。
  ガードページは最後の守りで、普通は入口の限界検査（§3.2）が先に実行時エラーにする。
- 依存の選択：corosensei は x86_64 と AArch64 に対応している（背景知識）。
  JIT コードもファイバーの上で走るので、ファイバーの実装は「ネイティブスタックを切り替える」だけを担えばよい。
  自作の切り替えでも数十行で済む。

### 6.3 静的に分類して、ファイバーを立てない（推測）

ハンドラの節は構文上すべて見えるので、コンパイル時に次のように分類できる。

| 種類 | 判定 | 実装 |
| --- | --- | --- |
| 再開しない操作の節（§13.1） | 返り値の型が `Never` | ファイバーを立てない。巻き戻しは、実行時エラーと同じ脱出の仕組みで行う |
| 末尾 `resume` だけの節（§5.7） | 節の本体の末尾の背骨にしか `resume` がない | 操作を起こした側のスタックの上で、節を普通の呼び出しとして走らせる。ハンドラの連鎖の指す位置を、節のあいだだけ外側へずらす（§13.4 末尾の「節の中の操作は外側が受け取る」を守るため） |
| 一般の節 | 上のどれでもない | ファイバーを立てる |

- 1 つのハンドラに種類の違う節が混ざるときは、最も重い種類に合わせる。
- 末尾 `resume` だけの節には注意が要る。
  節を評価しているあいだに、その節の中から再開しない操作が起きた場合や、実行時エラーが起きた場合は、§13.6 の「継続がまだ生きている」規則が適用される。
  そのハンドラの `cancel` 節を走らせる必要がある。
  分類の正しさは、`diktor/test/tail_calls.t` と `never_ops.t` と同じ観点の差分テストで確かめる。

### 6.4 末尾性とハンドラの境目（推測）

- ハンドラ式が末尾位置にあるとき、`return` 節と再開しない操作の節の本体も末尾位置にある（§5.7）。
  そのため、ハンドラの片を解放してから、その節の本体を親の片の上で `musttail` で始める必要がある。
  `return` 節は、本体の片が終わった後に親の片で走らせる。
  これは Diktor の `retc` が親のスタックで走る（`interp.ml` の対応表）のと同じ形である。
- 末尾 `resume`：節のフレームを捨ててから、止めておいた片へ切り替える。切り替え先で `resume` の値を戻り値として受け取る。
  再開した計算がハンドラ式の値を返すと、その値はハンドラ式の呼び出し元へ直接返る。
- ハンドラ式の本体の中の呼び出しは末尾にならない（§5.7）。片の境目で末尾呼び出しを保つ必要はない。

### 6.5 GC から見た継続（推測）

- 止まっている片の連鎖は、それを指すハンドラの記録から根としてたどる。
- 片ごとの値スタックは、片と一緒にプールへ返す。
- 案 C を採る場合、継続は片の連鎖への参照カウント付きの参照になる。ワンショットなので、`resume` のときに所有権が移るだけで済む。

## 7. WasmGC のバックエンド

### 7.1 計測：Node v26.9.0（V8 14.6.202.34）

```
# 手で符号化したモジュール。f(n) は return_call で自分を呼ぶ
return_call loop 1e8 -> 0
# struct.new と struct.get。フラグなし
struct.new -> object [object Object] struct.get -> 7
1e7 allocs ok 70000000 heapUsed MB 4.8
$ node -e '... typeof WebAssembly.Suspending ...'
Suspending: function promising: function Tag: function JSTag: object
$ node --v8-options | grep wasmfx
  --experimental-wasm-wasmfx (enable core stack switching for Wasm (experimental))  default: --no-...
```

- 事実：
  - 末尾呼び出し（`return_call`）は、フラグなしで 1e8 回の自己末尾呼び出しを完走した。
  - WasmGC の構造体は、フラグなしで作れ、V8 の GC が回収する。1e7 個作った後のヒープは 4.8 MB だった。
  - 例外のタグ（`WebAssembly.Tag`）がある。
  - JSPI（`Suspending`、`promising`）がある。
  - コアのスタック切り替え（wasmfx）は実験フラグで、既定では無効である。

### 7.2 推測

- Rust の GC も、根の管理も要らない。
  RustKeleut は WasmGC の型（`struct`、`array`、`i31ref`、関数への参照）を出力するだけで、メモリはホストが持つ。
  案 C の `dup` と `drop` は、このバックエンドでは捨てる。
- 一様な語は `eqref` か `anyref` にする。
  Int32 は 31 ビットに収まらないので、`i31ref` に入る値だけ即値にし、入らない値は `struct { i32 }` に入れる。
  文字列は `(array i8)` にする（§4.4 のバイト列。JS の文字列には写さない）。
- 末尾呼び出しは `return_call` と `return_call_ref` で、そのまま保証できる。
- 再開しない操作と実行時エラーは、Wasm の例外（タグ）で巻き戻せる。
- 末尾 `resume` だけの節は、§6.3 と同じく、その場で呼び出せる。
- 一般の `resume` が問題になる。
  JSPI は JS の Promise へ止まる仕組みで、呼び出しを非同期に染めるので、Keleut の深いハンドラには重すぎる。
  v1 では、一般の節を含むハンドラの本体（と、そこから呼ばれる行多相の関数）だけを CPS か状態機械に変換する。
  wasmfx が既定で有効になったら、ファイバーと同じ形へ移る。
  この変換を下ろしのどの段に置くかは、IR の調査担当と合わせる必要がある。

## 8. 推奨する段取り

### v1（最初に動かすもの）

1. 値スタックと ctx、入口の表、`tailcc i64 (ptr ctx)` の規約。境目のスタブと最上位の入口を、起動時に生成する LLVM モジュールとして用意する。
2. バイトコードのインタプリタ（Rust の平坦なループ）。フレームは値スタックの上に置く。末尾呼び出しはフレームの再利用か、スタブへの要求の返却で行う。
3. 動かさないマークスイープ。根は値スタック、グローバル、ハンドラの記録、Rust のハンドルの枠。
4. ファイバーのプール（ガードページ付き）と、片の連鎖による深いハンドラ。`cancel` の巻き戻し、実行時エラー、スタックの限界検査を 1 つの脱出の仕組みにまとめる。
5. ORCv2 の LLJIT（llvm-sys 221）による関数単位のコンパイル。呼び出し回数で切り替え、入口を 1 語書き換える。コンパイルは別スレッドで行ってよい（32 コアあり、ミューテータは 1 本。入口の書き換えは原子的な 1 回の書き込み）。
6. テスト：§5.7 と §13.5、§13.6 の観点で、インタプリタだけ、JIT だけ、交互の 3 つの設定で同じ出力になることを確かめる差分テスト。`diktor/test/tail_calls.t` と `never_ops.t` の内容を移植する。`ulimit -s` を小さくした実行も入れる。

### v2

- §6.3 の静的分類（再開しない操作と、末尾 `resume` だけの節はファイバーを立てない）。
- 案 B の「ctx と固定数 N 個の word」によるレジスタ渡し。退避を呼び出しと割り当ての点だけに減らす。
- レコードの選択のインラインキャッシュ。単相の箇所の数値を箱に入れないこと。
- 案 C の試作と、案 A との比較の計測（Diktor のソースのようなコンパイラの処理を負荷にする）。

### v3 以降

- 世代別 GC（バリアは 3 か所）か MMTk。必要ならステートポイント（`gc-leaf-function` の回避策つき）。
- WasmGC のバックエンドを wasmfx へ移すこと（Node で既定になった後）。

### 作らないもの

- OSR、逆最適化、投機的な最適化。
- 保守的なスタック走査。

## 9. 確認事項と推奨案

| 確認事項 | 推奨案 | 理由 |
