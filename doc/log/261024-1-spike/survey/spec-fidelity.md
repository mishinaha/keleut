# 実行系が一致させる意味規則の目録(spec-fidelity)

調査日 2026-10-24。対象は親 bcb16f1、diktor 6e49bbb。
`doc/LangSpec.md` のうち実行時に観測できる規則を集め、どのバックエンド(Diktor、RustKeleut のバイトコードインタプリタ、LLVM ORCv2、WasmGC on Node.js)も同じに再現しなければならないものを並べる。
標準環境の在庫(プリミティブ、組み込み値、組み込みインスタンス)も示す。

表記の約束は次のとおり。

- **測定**：コマンドを実行して得た事実、またはリポジトリのファイルの記述。コマンドと出力(抜粋)を添える。
- **推論**：測定から筆者が導いた判断。根拠を書く。
- 難所の列は (a) WasmGC on V8、(b) LLVM のネイティブコード、(c) バイトコードインタプリタの 3 つ。`-` は特段の難しさがないことを表す。

実験に使ったファイルはすべて `doc/log/261024-1-spike/probe/fid/` と同じ階層の `fltcmp/` にある。
Diktor は `diktor/_build/default/bin/main.exe`(`dune build` 済み、以下 `$D`)で実行した。

## 0. 一致の基準(§18)と規則の 3 分類

§18 冒頭(LangSpec.md:1951 付近)の定義：

> **評価の結果**：プログラムが標準出力に書いたバイト列と、終わり方(§15.5)の組。
> 処理系が表示する型、診断、警告の文面は、評価の結果に含めない。

終わり方は §15.5 の表で、正常終了 0、型検査での拒否 1、字句と構文の誤り 2、実行時エラー 3 である。
この定義に従い、規則を 3 つに分ける。

| 分類 | 意味 | バックエンド間の要求 |
| --- | --- | --- |
| **R(結果)** | 標準出力のバイト列か終わり方(0/1/2/3)を変えうる | ビット単位で一致させる |
| **D(診断)** | 標準エラーの文面と、標準出力との相対順序 | 文面は自由。順序(§15.5「診断は、それより前にプログラムが書いた内容の後ろ」)だけは守る |
| **I(処理系定義)** | 仕様が処理系に任せている | 一致は不要。RustKeleut 側で決めて文書にする |

I に当たるものの例(測定と仕様)：

- 未実装の機能の終了状態。Diktor は 4(driver.ml:777-778 `e_exit = 4`)。
- 出力に書けないときの終了状態。Diktor は 74(driver.ml:222 `safe_exit 74`)。
- 対話的な実行の入力の区切りと診断の出力先(§6.6、§15.5)。Diktor の `--repl` は結果も診断も標準出力に出す(test/repl.t:1-2)。
- 複数のファイルに誤りがあるときにどれを報告するか(§15.5)。
- 「処理系の限度」の大きさ(§15.5)。ただし限度を超えたときの扱い(実行時エラーとして `cancel` 節を走らせ、終了状態 3)は R である(5 節)。

## 2. Float64 の文字列化(§16.2)

規則(§16.2)：

1. NaN は `nan`(符号を出さない)、`inf`、`-inf`。
2. 絶対値が `1e16` 未満の整数値は小数点表記(`%.1f`)。
3. それ以外は、有効数字 `p` を 1 から 17 まで増やし、**p 桁に正しく丸めた表記**を読み戻して元の値になる最初の `p` を使う。指数が `-4` 未満か `p` 以上なら指数表記。末尾のゼロを除き、小数点も指数もなければ `.0` を足し、指数から `+` と先頭のゼロを除く。

Diktor の実装は value.ml:441 の `float_repr`(C の `%.*g` を OCaml の `Printf` 経由で呼ぶ)。

測定(`num.kel`)：

```text
0.1 + 0.2 -> 0.30000000000000004   100000.0 -> 100000.0   0.0001 -> 0.0001
0.00001  -> 1e-5                    1e16     -> 1e16       1e15   -> 1000000000000000.0
-0.0     -> -0.0                    -(0/0)   -> nan        5e-324 -> 5e-324
123456789012345680000.0 -> 1.2345678901234568e20           1.5e300 -> 1.5e300
```

**この規則は「最短の往復表記」ではない**(測定)。
`fltcmp/src/main.rs` で、2,000,000 個の乱数ビット列と 2 の冪(2^54〜2^1023)と境界値について比べた。

```text
$ ./target/release/fltcmp
short-diff 6.189700196426902e26: C=6.1897001964269014e+26 shortest=6.189700196426902e26
...
tested=1998964 diff_vs_rust_precision_e=0 diff_vs_rust_shortest=522
```

- Rust の `format!("{:.*e}", p-1, f)` で同じ探索を組むと、glibc の `%.*g` の探索と 0 件の差だった(経験的な一致で、証明ではない)。
- Rust の `{:e}`/`Display`(最短往復)は 522 件で桁が違った。差はすべて 2 の冪の付近(上の 2^89 など)で、正しく丸めた p 桁が往復せず p+1 桁が要る値である。

JS で同じ探索を組んだ場合(測定、`fltcmp/js.mjs`、C の結果 399,620 件と比較)：

```text
$ node js.mjs cases.txt
toPrecision diff 43179085685d83c9 1658206780088562.2 1658206780088562.3
n=399620 toPrecision_loop_diff=113 String(f)_diff=22
```

`toPrecision` は 2 進の値がちょうど中間にあるとき大きい側へ丸め(ECMAScript の規定)、glibc と Rust は偶数側へ丸める。
`1658206780088562.25` は 2 桁目の候補 `.2` と `.3` がどちらも同じ値に読み戻るので、ここで字面が分かれる。
また `node -e 'console.log((-0).toFixed(1), String(-0))'` は `0.0 0` を出し、仕様どおりの `-0.0` にならない。

| § | 検査できる規則 | (a) | (b) | (c) |
| --- | --- | --- | --- | --- |
| 16.2 | 上の 3 規則で `show(Float64)` の字面が一意に決まる | **難**：`Number.prototype.toString`/`toPrecision`/`toFixed` はどれも使えない(測定)。正確な 10 進変換を wasm 内に持つか、BigInt で組んだ JS の import を書く | Rust ランタイムで `{:.*e}` の探索 + 整形(推論：測定の 0 件差による) | 同左 |
| 16.2 | `-0.0` は `-0.0`(`%.1f` の結果) | 測定 `-0.0`。**難**：JS の `toFixed` は符号を落とす | Rust の `{:.1}` は `-0.0`(推論、Rust ≥1.53 の仕様) | 同左 |
| 16.2 | NaN の符号は出さない | 測定 `-(0.0/0.0)` → `nan` | - | - |

### 6.2 バックエンド別の難所

- (a) WasmGC：Node 26.9.0 では `--experimental-wasm-wasmfx`(スタック切り替え)が既定で無効、`--experimental-wasm-exnref` は既定で有効だった(測定：`node --v8-options`)。
  推論：ワンショット継続をスタック切り替えなしで実装するには、CPS 変換か、関数を状態機械にして継続のフレームを GC のヒープに置く変換が要る。
  末尾 `resume` の一定領域(§13.5)と末尾呼び出し(§5.7)を、その変換の後も保つ必要がある。
  `cancel` の順序と打ち切り(6.1 の表)は、wasm 例外(exnref)で巻き戻すと素直に書ける。
  ただし、wasm の trap(ゼロ除算、`trunc`、配列の範囲外、null 参照、`unreachable`)と V8 のスタック溢れは wasm の `catch` で受けられない(推論：trap は JS の `WebAssembly.RuntimeError` として wasm の外へ出る)。
  そのため、実行時エラーになりうる箇所はすべて明示の検査にし、wasm の例外タグで投げる必要がある。
  そうしないと `cancel` 節が走らず、終了状態 3 の前に出るはずの出力が欠ける。
- (b) LLVM：ワンショット継続には、独立したスタック(セグメント)の切り替えか CPS が要る。
  巻き戻しで `cancel` 節を走らせるには、C++ 式の例外(`landingpad`)か、自前の巻き戻し表が要る。
  推論：Diktor が OCaml 5 のエフェクトに任せている部分(interp.ml:949 `eval_handle` の `Effect.Deep.match_with`、`discontinue`)を、すべて自前のランタイムで持つことになる。
- (c) インタプリタ：継続をヒープのフレームで表せば、捕捉、破棄、`cancel` の順序はどれも実装できる(推論)。
- 階層化(インタプリタと LLVM コードの相互の飛び移り)：推論として、継続とハンドラのスタックの表現を IR の層で一本に決め、両方の階層が同じ形のフレームを読み書きする必要がある。
  片方の階層だけが独自のスタックに継続を持つと、もう片方から `resume` できない。

### 13.3 プレリュードで Keleut で書いた定義(prelude.kel)

`Never`(コンストラクタなし)は decls.ml の `register_builtins` が登録する。
測定 `show(Cons(1, Cons(2, Nil)))` → `[1, 2]`。

### 13.4 組み込みのクラスとインスタンス(decls.ml の `register_builtins`、builtin.ml:351-403)

| クラス | メソッド | インスタンス | 実体 |
| --- | --- | --- | --- |
| `Add` | `add: (A, A) => A` | Int32 Int64 Float64 String | `__*_add`、String は `__string_concat` |
| `Sub` `Mul` `Div` | 同形 | Int32 Int64 Float64 | `__*_sub/mul/div` |
| `Rem` | `rem` | Int32 Int64 | `__*_rem` |
| `Neg` | `neg: (A) => A` | Int32 Int64 Float64 | `__*_neg` |
| `Eq` | `eq: (A, A) => Boolean` | Int32 Int64 Float64 String Boolean(+ 構造的導出、List、Option) | `__*_eq`。Boolean は直接実装(builtin.ml:398) |
| `Ord` | `lt le gt ge` | Int32 Int64 Float64 String(Boolean はない) | `__*_lt` など |
| `Show` | `show: (A) => String` | Int32 Int64 Float64 String Boolean(+ List、Option) | Int32 は `__show_int32`、ほかは直接実装(builtin.ml:399-402)。Float64 は `float_repr` |
| `Integral` `Fractional` | なし | Int32 Int64 / Float64 | 予約述語。実行時の実体なし |

### 13.5 外部関数(§17)

`sin cos sqrt exp log : (Float64) => Float64`(builtin.ml:287-294)。

## 14. 保存する性質(§18)が実行系に課すこと

| § | 内容 | 実行系への含意(推論) |
| --- | --- | --- |
| 18.1 | 束縛名の付け替えで結果が変わらない | 名前を実行時の意味に使わない。実行時エラーの文面に名前が出るのは D なので構わない |
| 18.2 | 依存のない宣言の並べ替え(条件付き) | 宣言の位置で起きる副作用の順序は保つ。最適化で初期化を並べ替えるなら、§18.2 の条件(評価が停止しエフェクトなしでエラーなし)を満たすものに限る |
| 18.3 | 型に書いた異なるラベルの順序は結果を変えない。ただしレコード式のフィールドと名前付き引数の順序は評価順を決める | レコードの内部配置はラベルの正規順で決めてよいが、評価は書いた順で行う。構造的等値もラベル単位で比べる(interp.ml:546 の注記どおり、物理順で突き合わせない) |
| 18.4 | 型エイリアスの展開 | 実行系には影響しない |
| 18.5 | 対話的な実行で受理しなかった入力を挟んでも結果が変わらない。ただし止まるまでの出力は残る | 11 節の巻き戻し |

## 15. まとめ：バックエンド別の重い項目

| 項目 | (a) WasmGC | (b) LLVM | (c) インタプリタ |
| --- | --- | --- | --- |
| 実行時エラーを `cancel` 節つきの巻き戻しにする | trap と V8 のスタック溢れを使わず、すべて明示の検査と wasm 例外にする | スタック溢れの検出(ガードページか深さ検査)、div/rem/fptosi の UB の回避 | 容易 |
| ワンショット継続と末尾 `resume` の一定領域 | wasmfx が既定で無効なので CPS か状態機械化 | スタック切り替えか CPS。階層間で共通の継続の形が要る | ヒープのフレームで容易 |
| 末尾呼び出しの保証 | `return_call` は使えるが、CPS と組み合わせる設計が要る | `musttail` と GC、呼び出し規約の両立 | トランポリンで容易 |
| Float64 の `show` | JS の数値整形は使えない(113/399620 件の差を測定)。自前の正確な変換 | Rust の `{:.*e}` の探索(2M 件で glibc と一致を測定) | 同左 |
| 文字列のバイト列 | `(array i8)` と `fs.writeSync` | - | - |
| `sin cos exp log` の再現性 | 共有の libm を wasm に入れる | 同左を静的に結合 | 同左 |
| 初期化前の参照、インスタンスの宣言前使用 | 未初期化の印と検査 | 同左 | 同左 |
| 制約付き値の使うたびの評価 | キャッシュしない | 同左 | 同左 |
