## 0. 要約

1. 【実測】`cancel` 節の中に直に書いたハンドラ式で値を多く生かすと、`kw` は既定の L の内側(論理的な深さ約 993,750)で `RangeError` の内部エラー(70)になる(V234)。
   原因は、論理的な 1 段に Wasm のフレームが 4 つ重なることで、関数ごとの予算では直せない。
   `keleut-wasm` がプログラムごとに 1 段の上限 `B_prog` を静的に求め、スタックの大きさをそれで決める(D564、M106)。
2. 【実測】`--extra=--gc-stress` と `--extra=--no-yield-prune` の全組の受け入れは、`--suite all` と `--suite depth` のどれも差 0 だった(gaps.md 2.2 節)。
   これで閉じ、締めの受け入れの手順に 2 つの extra を加える(D565)。
3. LangSpec §15.5 の表の 1 の行を「型検査か、実行の前の変換に要する領域が処理系の限度を超えた」に広げ、3 の行を「初期化を始めるときか、初期化の途中で」に広げる(D566、P259)。
   IRSpec 1 節の除外に、直しきれないメモリの不足の窓と、スタックを小さくした読み手が `N_nest` の内側で拒否しうることを書く(D567、P260)。
   仕様の文の改訂は M107 にまとめ、V224 の 1 文(D577)、§6.6 の受理しない入力の列挙(D577)、§6.6 の表示の 1 文(D578)もここに入れる。
4. Rust の大域の確保器を包み、予備とスレッドの役割ごとの印を持たせる。
   包みは null を返すだけで、自分では止めない。
   失敗を自分で扱う呼び手は、予備に触れない範囲の印を立てて確保する。
   実行の前の役割(変換)で予備を使い切ったら、限度の行を書いて 1(`.kir` の入力は 65)で終える。
   試験用に確保を場所の名前で失敗させる仕組みもここに置く。
   回収の中の確保をなくし、JIT の翻訳の前に残りのメモリを調べる(D568、V230、M108)。
5. 形の表の確保を失敗を返すものにし、`kw` でも 70 でなくメモリの不足にする(D569、V229、M109)。
   2 乗の大きさは V240 として分け、延期する。

8. V215 は P252 の決定のまま 70 とし、`kw` の有限の `ulimit -v` の振る舞いを文書に書いて閉じる(D572、P261)。

### 1.2 実行時の確保の制限((2))

- LangSpec §15.5(`doc/LangSpec.md:1771-1776`)は、評価に要する領域が処理系の限度を超えた場合も実行時エラーとし、`cancel` 節を走らせて 3 で終える。
  §15.5 の表の 1 の行(1783 行)は「型検査に要する領域が処理系の限度を超えた」を 1 とする。
  IRSpec 1 節(`doc/IRSpec.md:34-49`)が同じ結果の保証から除くのは、`N_alloc_max` を超える確保と、`kw` の V8 のヒープの枯渇と、Diktor での確保である。
  `ki` と `kj` の小さな確保の失敗による 134 は除外に無い。
- V229: `ShapeTable::alloc` は `vec!` で、`grow` は `expect` で止まる(`rustkeleut/crates/keleut-rtcore/src/lib.rs:193-224`)。
  【実測】func 3,000 段の拡張の鎖の `.kir` を `ulimit -v 524288`、`--native-stack 64m` で走らせると、`ki` は `memory allocation of 150994968 bytes failed`、`kj` は `75497496 bytes` で、どちらも 134 になり、`before` も失われる(alloc.md 2.2 節、critic.md 1 節で再現)。
  同じ `.kir` の `diktor --run-ir` は `before`、`3000`、0 で終わる。
  形の表は 2 乗で大きくなり、fun 8,000 段で常駐 944 MB のほとんどを占める(alloc.md 2.2 節)。
  `kw` では、形の表を広げる `shapes_grow` が新しい表を host の `alloc` で取るので、メモリが尽きると `線形メモリを広げられません` の内部エラー(70)になる(`host/keleut-host.mjs:395-405`、`:691-697`)。
  `形の表を広げられません`(`crates/keleut-wasm/src/rt.rs:255`)は、`krt_shapes_copy` が失敗したときだけに出る。
- V230: `#[global_allocator]` はどの crate にも無い【実測、grep】。
  【実測】`oomlist.kel` を `ulimit -v` 300,000〜700,000 KiB で走らせると、`interp` は 350,000 で 134 になった。
  backtrace は `keleut_lir::live::Points::live`(`crates/keleut-lir/src/live.rs:68` の `to_vec`)← `gc::Frames::scan` ← `Rt::collect` で、回収の中の確保だった。
  JIT の段では `LLVM ERROR: out of memory` と `std::bad_alloc` でも 134 になった(alloc.md 3.2 節)。
- 値スタックの塊は `std::alloc::alloc_zeroed` で取る(`crates/keleut-rt/src/stack.rs:31`、`:85-94`)ので、大域の確保器を通る(critic.md 2 節の 1)。
  keleut-rt と keleut-interp の確保のうち大域の確保器の外にあるのは、GC のヒープ(`heap.rs` の `mmap`)だけである。
  LLVM の C++ の確保(翻訳のスレッドの `malloc` と `new`)も大域の確保器を通らない。
  【実測】塊は戻った後も回収されず、`ulimit -v 1300000` で、深い再帰だけの例とヒープだけの例はどちらも 0 なのに、両方を続けた例は 3 で終わった(alloc.md 4.2 節)。
- `cont_resume` の失敗の後の注入: 記録 2744〜2746 行(M89 の残した制限の 1)は、注入も値スタックに継続を置き直すので、塊を取れなければ継続の中の `cancel` 節が走らないとした。
  【実測】測った 4 つの例ではこの制限は現れなかった(alloc.md 5.2 節)。
  塊を回収しないので、注入が前に使った塊を使い直すからだと考えている【推論】。

## 3. 測るだけの残り

### 3.1 `kw` のプログラムごとの 1 段の上限(D564、V234)

**D564**: `keleut-wasm` は、プログラムごとに論理的な 1 段のスタックの上限 `B_prog` を求め、Node のスタックの大きさを `(L + R) × B_prog + 32 MiB` で決める。

- `k` を、ハンドラ式の `cancel` 節の本体の中に、関数の本体を挟まずに書いたハンドラ式が入れ子になる段の数の最大とする。
  ハンドラ式を持たない `cancel` 節だけのプログラムは `k = 0` である。
  `k` は KIR の木の入れ子から求め、下ろしのときに LIR の `Program` に持たせる。
  LIR だけから求めるなら、`$rt_handle` を末尾でなく呼ぶ `cancel` 節の関数を、そのハンドラ式の `cancel` 節の関数へ結ぶ辺の最長の鎖の段の数にする。
- `B_prog = B_wasm + k × (B_wasm − E_rres)` とする。
  `k = 0` のプログラムでは `B_prog = B_wasm` で、スタックの大きさはいまと同じである。
  段が 1 つ増えるごとに重なるのは、予算 1,040 の `cancel` 節と `E_rth = 320` の `$rt_handle` で、合わせて `1,360 = B_wasm − E_rres` である。
- 段が増えても `rt_resume` は 1 つしか重ならないと見る【推論、M106 で測る】。
  `rustkeleut/doc/lir.md` 16.3 節の手順では、`$rt_handle` は手順 2 で `cont_resume` を呼び、それが番兵を返してから手順 4 で `cancel` 節を走らせる。
  そのため `cancel` 節のフレームの下にある `$rt_handle` は、もう `rt_resume` を上に持たない。
  1 つの深さで `rt_resume` を上に持てるのは、最も上の `$rt_handle` だけである。
  最も重い形は、入れ子の `cancel` 節の中のハンドラ式で G の節が末尾で `resume` し、内側の `$rt_handle` が深さ `h` で `rt_resume` を呼ぶ形で、`k = 1` で `1,040 + 320 + 1,040 + 320 + 176 = 2,896 = B_prog` になる。
  この形(形 f と呼ぶ)を M106 の単体の試験と測り直しに入れる。
- スタックの大きさには上限 `STACK_CAP` を置く。
  `(L + R) × B_prog + 32 MiB` が `STACK_CAP` を超えるときは `STACK_CAP` で走らせ、`KELEUT_WASM_STATS=1` に上限で切ったことを書く。
  上限で切ったプログラムは、深く入ると V234 と同じく 70 になりうる。
  【実測、`verify/findings.md` の feasible-8 の反証者の探り】この機械の Node 26.9.0 は `resourceLimits.stackSizeMb` が 32,000 の `Worker` を作れ、64,000 では `EAGAIN` で作れなかった。
  `STACK_CAP` は 16 GiB を案とし、M106 で `Worker` を作れることを確かめて決める。
  既定の L では、16 GiB は `k` がおよそ 10 までの分である。
  上限を置かないと、`k` の大きいプログラムは浅い深さでも起動のときに `Worker` を作れずに 70 になる。
- `stack_size_kib` は `B_prog` を引数に取る。
  `keleut build` の出力の `META` に `B_prog` を書き、host の `Worker` の道(`host/keleut-host.mjs:763-789`)は定数の `B_WASM` でなく `META` の値でスタックを決める。
- `k = 1` のとき既定の L のスタックは約 3,044,608 KiB で、`STACK_SIZE_MAX_KIB`(2,097,151)を超えるので、`stack_plan` は `Worker` の道を選ぶ。
  【実測】`Worker` の道は既定の L の約 2 倍と 4 倍のスタックで深い再帰を走らせた(本計画 1.1 節)。
- `KELEUT_WASM_STATS=1` の出力に `k` と `B_prog` を足す。

試験:

- `crates/keleut-wasm` の単体の試験: `k = 0` のプログラムで `stack_size_kib(1 << 20, B_WASM)` が 1,630,208 のままであること。
  gaps.md の形 a〜e と本節の形 f の小さな版で `k` が 1(形 b は 2)になること。

## 4. 実行時の確保の制限

### 4.1 仕様の文(D566、D567)

**D566(P259)**: LangSpec §15.5 の表の 1 の行の条件を次の文に改める。

```text
型検査に通らないファイルがあるか、import が誤っているか、型検査か実行の前の変換に要する領域が処理系の限度を超えた
```

表の 3 の行の条件を次の文に改める。

```text
初期化を始めるときか、初期化の途中で実行時エラーが起きた
```

表の下に次の 2 文を足す。

```text
実行の前の変換は、型検査の後、評価のための領域(実行のスタックや実行時の表など)を用意する前に処理系が行う処理(中間表現への変換、その読み込みと検証など)であり、その範囲は処理系が定める。
評価のための領域を用意できない場合は、評価に要する領域が処理系の限度を超えた場合にあたり、初期化を始めるときの実行時エラーとする。
```

境は「評価のための領域を用意し始めるとき」である。
その前の失敗は 1 の行、後の失敗は 3 の行に入る。

1 の行に入るのは、次の 4 つである。

1. KIR の書き出しの入れ子の限度(`keleut run` と `diktor --emit-ir` はいまも 1 で終わる。本計画 1.4 節)。
2. フロントエンドの確保の失敗(V236。いまは 134)。
3. 仮想メモリの上限の下で、KIR の処理のスレッドを作れない場合(V235 の一部。いまは 70)。
4. `.kel` から同じプロセスの中で作った KIR を、小さくしたスタックに合わせて下げた入れ子の限度で検証が拒否する場合と、KIR の読み込み、検証、下ろしで確保が尽きた場合。
   【実測、`verify/findings.md` の feasible-6 の反証者の探り】いまは `--native-stack 16m` で深さ 7,000 の `1 + (...)` が、フロントエンドの限度(7,168)を通った後に「KIR の検証で入れ子が深すぎます」で 65 になる。
   65 は §15.5 の表に無い。

3 の行に入るのは、実行のスレッドと構造的な `Eq` が移るスレッドを作れない場合と、起動のときの形の表の登録の失敗である(本計画 4.3 節、4.4 節)。

`.kir` を入力にしたとき(`keleut run FILE.kir`、`keleut kir verify|dis|asm`)は、Keleut の型検査が無いので §15.5 の表でなく IRSpec に従う。
KIR の処理のスレッドを作れない場合、下げた入れ子の限度で拒否する場合、読み込みと検証と下ろしで確保が尽きた場合は、どれも読み手の処理系の限度として 65 で終える(D567)。

理由: 1 の行の 4 つは、どれも評価のための領域を用意する前に処理系の限度に当たる場合である。
いまの文は「型検査」と書くので、KIR の書き出しの限度の 1 は厳密には表に当てはまらない(decide.md 1.4 節)。
4 つを別々に決めると、フロントエンドの失敗が 3 になるか、実行の失敗が 1 になりうる(critic.md 3 節の 2)。
3 の行を広げないと、実行のスレッドを作れない場合と起動のときの登録の失敗が、表のどの行にも当てはまらない(初期化を 1 つも行っていない)。

代案: 表を変えず、3 つを処理系の定める終了状態にする。
§15.5 は「出力に書き出せない場合の終了状態は処理系が定める」と並べて書けるが、型検査を通ったプログラムの終わり方が表の外に出るので採らない。

**D567(P260)**: IRSpec 1 節の除外の「`N_alloc_max` の検査によらないメモリの不足」の項は、総論の文を残す。
読み手ごとにメモリが尽きる点は違い、尽きた読み手はメモリの不足(3)で終わる。
そのうえで、3 で終わらない場合として次の 3 つを挙げる。

1. WasmGC の後段が V8 のヒープを使い尽くす場合と、`keleut run` が仮想メモリの上限の下で Node のスタックやスレッドを取れない場合(70)。
2. RustKeleut のインタプリタと LLVM の後段で、LLVM の中の確保が失敗する場合と、大域の確保器の予備(本計画 4.2 節)を使い切った後に Rust の確保が失敗する場合(SIGABRT、134)。
3. OS が物理メモリの不足でプロセスを止める場合(SIGKILL、137)。
   どの読み手でも起こりうる。

IRSpec は kconform の組の名前(`ki`、`kj` など)を使わないので、文は後段の名前で書く。
Diktor での確保の項はそのまま残す。
11.1 節の表の後ろの注(`doc/IRSpec.md:968-969`)も同じ範囲に改める。

あわせて、13.9 節の「読み手は、深さが `N_nest` 以下のプログラムを受け付け」の除外を 1 項足す。
RustKeleut の読み手は、スタックを `--native-stack` か仮想メモリの上限で小さくしたとき、深さが `N_nest` 以下のノードでも処理系の限度として拒否しうる(65)。
KIR の処理のスレッドを最も小さいスタックでも作れない場合と、読み込み、検証、下ろしで確保が尽きた場合も、同じく処理系の限度として 65 で終える。
いまの `--native-stack` で入れ子の限度を下げる振る舞いも、この項で除外に入る。
版の履歴の表に `1.0(本文の改訂)` の行を足す(計画 261104-1 の D556 の規則。KIR の受理、意味、符号を変えない)。

理由: 本計画 4.2 節の修正の後も、LLVM の C++ の確保の失敗は Rust から捕まえられない(C API に `install_bad_alloc_error_handler` が無い。alloc.md 3.4 節)。
物理メモリの枯渇による SIGKILL は、`ulimit -v` の無いプロセスでどの処理系にも起こる。
これらを除外に書かないと、IRSpec 1 節の「同じ終了状態」の保証が実装と食い違う。
総論の文を残すのは、本計画の `oom/shape.t`(本計画 4.3 節)のように、RustKeleut が 3 で終わり Diktor が 0 で終わる場合を保証から除くためである。
`keleut build` の出力を `node DIR/main.mjs` で直に走らせた場合(512 MiB の上限で 133 になる。記録 3702〜3703 行)は、IRSpec 1 節の読み手(`diktor --run-ir` と `keleut run`)に入らないので、IRSpec には書かず `AGENTS.md` に書く(本計画 4.6 節)。

`doc/sample.kel` に終了状態と処理系の限度と対話的な実行の記述は無い【実測、grep で `終了状態`、`限度`、`対話`】ので、`diktor/test/sample/sample.kel` の同期は要らない。

### 4.2 大域の確保器と試験用の失敗(D568、V230)

**D568**: `keleut` のプロセスの大域の確保器を包み、次の 4 つを行う(alloc.md 3.4 節の案 A、B、E と F)。

1. **予備と役割の印**。
   - 確保器は `std::alloc::System` を包み、起動のときに予備(8 MiB を案とする)を取っておく。
   - 各スレッドは役割(実行、変換、翻訳、そのほか)をスレッド局所の値に持つ。
     実行の役割は、実行のスレッドと、構造的な `Eq` が移るスレッド(`crates/keleut-interp/src/interp.rs:345-372`)である。
     変換の役割は、フロントエンドのスレッドと KIR の処理のスレッド(読み込み、検証、LIR への下ろし)である。
     翻訳の役割は LLVM の翻訳のスレッドである。
     どれも作った直後に役割を書く。
     そのほかは主のスレッドで、引数の解析、ファイルの読み込み、スレッドの起動と後始末だけを行う。
   - 確保が失敗し予備があれば、予備を返して役割ごとの印を立て、確保をやり直す。
   - 包みは失敗した確保に null を返すだけで、自分では `handle_alloc_error` を呼ばない。
     `Vec` などの失敗を返さない呼び手が null を受け取ったときに、標準ライブラリが `handle_alloc_error` で止める(134、D567 の 2)。
   - **失敗を自分で扱う範囲**: 呼び手が失敗の後の道を持つ確保は、スレッド局所の印を立てた範囲で行う。
     この範囲の中の失敗では、包みは予備に触れず印も立てずに、すぐ null を返す。
     範囲に入れるのは、いまの `try_reserve` の後退の道(`heap.rs:393` の `keep`、`gc.rs:314` の印の列、`heap.rs:317`、`:410` の溜め、`gc.rs:654`)と、失敗をすぐメモリの不足にする確保(本計画 4.3 節の形の表、`rec_fields`、本項 3 の回収の作業域、`cont_make` の写し)である。
     これらは回収が続けられるか、`Stop::OutOfMemory` を自分で返すので、予備を使うと後の `cancel` 節の分が減るだけである。
     形の表の 150 MB の広げ直しのように、8 MiB の予備では足りない確保もこの範囲に入る。
     値スタックの塊の確保は範囲に入れず、下の「予備の使われ方の順」に従う。
   - **実行の前の役割で予備を使い切ったとき**: 変換の役割で、やり直しも失敗するか予備が無ければ、包みは標準エラーに限度の行を `write(2)` で書き、`_exit` で終える。
     終了状態は、入力が `.kel` なら 1(D566)、`.kir` なら 65(D567)である。
     変換の役割にはまだ `cancel` 節もプログラムの出力も無いので、ここで止めても失うものは無い。
     入力の種類は起動のときに静的な値に書いておく。
     行の文面は確保をせずに書ける固定の文で、M110 で決める。
     `keleut repl` の変換の役割はこの道を通らず、いまと同じく 134 で止まる(D567 の 2)。
     REPL を 1 つの入力のために終えないためである。
   - 包みと印は `keleut-rt` の小さなモジュールに置き、`#[global_allocator]` の宣言は `keleut-cli` の `main.rs` に置く。
     `kconform` は包まない。
2. **印を見る場所**。
   - 実行の役割の印は、`Rt` のヒープの確保の入口(速い道を含む)と、値スタックの塊を取る道で見る。
     立っていれば `Stop::OutOfMemory` を返し、いまのメモリの不足と同じく `cancel` 節を走らせて 3 で終わる。
     見るときは不可分の `swap(false)` で印を下ろし、1 回のメモリの不足に 1 回だけ応える。
     下ろさないと、`cancel` 節の中の最初の確保がまた印を見て、`cancel` 節が打ち切られる。
     GC のヒープの 1 MiB の予備を 1 回だけ使う、いまの `Heap::exhausted`(`heap.rs:313`)と同じ形である。
     JIT のコードの中の確保の速い道(M115)も同じ印を見る(critic.md 3 節の 6)。
   - 変換の役割の印は、型検査の後、KIR の書き出しの後、KIR の読み込みと検証と下ろしの後に見る(本計画 4.4 節)。
     立っていれば限度の行を書いて、`.kel` なら 1、`.kir` なら 65 で終える。
   - 翻訳の役割の印が立ったら、その関数の翻訳を捨て、それ以後の翻訳をやめる。
     プログラムはインタプリタで続ける。
     翻訳の失敗をプログラムのメモリの不足と取り違えない。
   - そのほかの役割の印は見ない。
     主のスレッドの確保は少なく、そこで予備を使い切った後の失敗は 134 の窓として D567 の 2 に入る【推論】。
   - `keleut repl` は、実行時エラーで止まった入力の後、次の入力の前に予備を取り直す。
     取れなければ予備なしで続ける。
3. **回収の中の確保をなくす**。
   `Points::live` に出力先の `Vec` を渡す形を足し、`gc::Frames` の作業域を使い回す。
   `FuncRoots::new`(`crates/keleut-rt/src/gc.rs:335`)と `any_slots` の作業域は、回収を始める前に `try_reserve` で取り、取れなければ回収を始めずに `Stop::OutOfMemory` を返す。
4. **JIT の翻訳の前の検査**。
   `RLIMIT_AS` が有限なら、翻訳の前に `/proc/self/statm` の仮想の大きさとの差を調べ、64 MiB を下回れば翻訳せずにインタプリタで続ける(`crates/keleut-llvm/src/run.rs` の翻訳のスレッド)。
   LLVM の中の失敗を捕まえる手段は無いので、窓を狭めるだけである。

予備の使われ方の順: 値スタックの塊(1 MiB 以上)の確保は大域の確保器を通るので、塊の確保の失敗では、まず大域の予備を返してやり直し、それも失敗したら値スタックの予備の塊(`stack.rs:23-28`)を使う。
GC のヒープは `mmap` で取り、いまの 1 MiB の予備のまま変えない。

**試験用の失敗**: 環境変数 `KELEUT_TEST_ALLOC_FAIL=ROLE:SITE:MODE:SKIP` を起動のときに読む。

- `SITE` は確保の場所の名前で、呼び手が確保の前後にスレッド局所の値として書く。
  名前は `collect`(回収の中)、`rec_fields`、`call_args`(`call_clause` と `perform` の引数の列)、`chunk`(値スタックの塊)、`cont`(`cont_make` の写し)、`shape`(形の表の広げ直し)、`check`(型検査)、`kir`(KIR の読み込み、検証、下ろし)とし、M108 で決める。
  確保の回数でなく名前で狙うので、M114 と M115 が確保の数を変えても、狙う場所は動かない。
- 役割 `ROLE`(`exec`、`conv`、`jit`。本計画 4.2 節の実行、変換、翻訳)のスレッドの、場所 `SITE` の確保の `SKIP + 1` 回目を失敗させる。
- `MODE` が `soft` なら 1 回だけ失敗させ、失敗は OS の失敗と同じく予備の道を通る。
  印を立てる道を決定的に試せる。
- `MODE` が `hard` なら、`SKIP + 1` 回目から後のその場所の確保をすべて、やり直しも含めて失敗させ、予備には触れない。

## 12. 進め方の原則

- マイルストーンごとに、実装の後で敵対的な検証を行う。
  観点は、仕様の文(§15.5、§6.6、IRSpec 1 節、11.1 節、13.9 節、14 節が互いに、また §8、§13.6、§16.2、§18、§18.5 と食い違わないか)、確保の失敗の道(印を見る場所の漏れ、印を下ろす時、失敗を自分で扱う範囲の漏れ、予備の使われ方、`cancel` 節の中の失敗)、試験の網羅(直す前に試験が落ちるか、後段の組の間の比較が働くか)、記録の整合(番号、行番号、台帳、既知の差の数)の 4 つを基本とする。
  検証者の指摘ごとに反証者を立て、反証されなかった指摘を直し、直したものを 1 回検証し直す。
- 振る舞いの分類を文書に書くときは、区別する最小の変種を並べて同じ条件で測ってから書く。
  `ulimit -v` の境のように機械で揺れる値は、境の両側で測り、余裕を書く。
- 時間を測るときは負荷の平均を添える。
  基準とベンチマークは負荷の平均 1 以下のときに測る(`rustkeleut/bench/README.md`)。
- `kconform --suite all` を同時に 2 つ走らせない。
  `--suite depth` は `--jobs 6` で走らせる(32 並列では OOM killer が `depth/gresume.t` を止める)。
  Diktor の木の評価器で数分を超える入力を `--suite all` の cram に置かない。
- 検証者と担当の書き込み先は scratchpad に限り、報告を受けたら親と diktor の `git status --short` を確かめる。
- 本文に逆引用符を含むテキストをシェルで書くときは、ヒアドキュメントを `<<'EOF'` と引用する。
- 既存の `doc/log` の記録は書き換えない。
