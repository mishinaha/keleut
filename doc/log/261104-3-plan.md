## 0. 要約

1. 【実測】`cancel` 節の中に直に書いたハンドラ式で値を多く生かすと、`kw` は既定の L の内側(論理的な深さ約 993,750)で `RangeError` の内部エラー(70)になる(V234)。
   原因は、論理的な 1 段に Wasm のフレームが 4 つ重なることで、関数ごとの予算では直せない。
   `keleut-wasm` がプログラムごとに 1 段の上限 `B_prog` を静的に求め、スタックの大きさをそれで決める(D564、M106)。
2. 【実測】`--extra=--gc-stress` と `--extra=--no-yield-prune` の全組の受け入れは、`--suite all` と `--suite depth` のどれも差 0 だった(gaps.md 2.2 節)。
   これで閉じ、締めの受け入れの手順に 2 つの extra を加える(D565)。
3. LangSpec §15.5 の表の 1 の行を「型検査か、実行の前の変換に要する領域が処理系の限度を超えた」に広げる(D566、P259)。
   IRSpec 1 節の除外に、直しきれないメモリの不足の窓を書く(D567、P260)。
   仕様の文の改訂は M107 にまとめ、V224 の 1 文(D577)と §6.6 の表示の 1 文(D578)もここに入れる。
4. Rust の大域の確保器を包み、予備とスレッドの役割ごとの印を持たせる。
   試験用に確保を失敗させる仕組みもここに置く。
   回収の中の確保をなくし、JIT の翻訳の前に残りのメモリを調べる(D568、V230、M108)。
5. 形の表の確保を失敗を返すものにし、`kw` でも 70 でなくメモリの不足にする(D569、V229、M109)。
   2 乗の大きさは V240 として分け、延期する。
6. フロントエンドの確保の失敗を 1 に、仮想メモリの上限の下で KIR の処理のスレッドと実行のスレッドを作れないときの 70 を、スタックを縮めて作り直す形にする。
   `keleut run` と `keleut emit-kir` は型検査の文脈を `drop` で捨てる(D570、V235、V236、M110)。
   `drop` は (3) の項目だが、`ulimit -v` の下の試験の境を動かすので、ここで行う。
7. 値スタックの塊を回収し、注入では継続の写しをそのまま塊として使う(D571、V242、V243、M111)。
8. V215 は P252 の決定のまま 70 とし、`kw` の有限の `ulimit -v` の振る舞いを文書に書いて閉じる(D572、P261)。
9. `rt.kirt` と wide 形は作らないと決めて閉じ、取り出しとスロットの試験を足す(D573)。
   `conformance/float/` を作る(D574)。
   `node DIR/main.mjs` が閉じた標準出力を見分けるようにする(D575、V238)。
   この 3 つは M112 で行う。
10. Diktor の V218 を起動時に `O_NONBLOCK` を外す 1 行で、V223 を 3 行と cram 1 本で直す(D576、P257、P258、M113)。
    V224 と V237 は処理系の限度として閉じる(D577)。
    REPL の表示の書式は処理系が定めると §6.6 に書き、表示の順の差の登録の規則を `conformance/README.md` に写す(D578)。
11. 負荷の低いときに基準を測り直し、V225 の段 1(`krt_fx` の中の確保を減らす)と V207 の代案 1(JIT の中の確保の速い道)を試作して測る(D579、M114、M115)。
    V208〜V212 は戻す条件を書いて閉じる(D580、P265)。
12. マイルストーンは M106〜M116 の 11 個で、最後の M116 は実施記録 `doc/log/261104-4-record.md` の締めに当てる(本計画 7 節)。

### 1.2 実行時の確保の制限((2))

- LangSpec §15.5(`doc/LangSpec.md:1771-1776`)は、評価に要する領域が処理系の限度を超えた場合も実行時エラーとし、`cancel` 節を走らせて 3 で終える。
  §15.5 の表の 1 の行(1783 行)は「型検査に要する領域が処理系の限度を超えた」を 1 とする。
  IRSpec 1 節(`doc/IRSpec.md:34-49`)が同じ結果の保証から除くのは、`N_alloc_max` を超える確保と、`kw` の V8 のヒープの枯渇と、Diktor での確保である。
  `ki` と `kj` の小さな確保の失敗による 134 は除外に無い。
- V229: `ShapeTable::alloc` は `vec!` で、`grow` は `expect` で止まる(`rustkeleut/crates/keleut-rtcore/src/lib.rs:193-224`)。
  【実測】func 3,000 段の拡張の鎖の `.kir` を `ulimit -v 524288`、`--native-stack 64m` で走らせると、`ki` は `memory allocation of 150994968 bytes failed`、`kj` は `75497496 bytes` で、どちらも 134 になり、`before` も失われる(alloc.md 2.2 節、critic.md 1 節で再現)。
  同じ `.kir` の `diktor --run-ir` は `before`、`3000`、0 で終わる。
  形の表は 2 乗で大きくなり、fun 8,000 段で常駐 944 MB のほとんどを占める(alloc.md 2.2 節)。
  `kw` では、形の表を広げられないと `形の表を広げられません` の内部エラー(70)になる(`crates/keleut-wasm/src/rt.rs:255`、`host/keleut-host.mjs:404`)。
- V230: `#[global_allocator]` はどの crate にも無い【実測、grep】。
  【実測】`oomlist.kel` を `ulimit -v` 300,000〜700,000 KiB で走らせると、`interp` は 350,000 で 134 になった。
  backtrace は `keleut_lir::live::Points::live`(`crates/keleut-lir/src/live.rs:68` の `to_vec`)← `gc::Frames::scan` ← `Rt::collect` で、回収の中の確保だった。
  JIT の段では `LLVM ERROR: out of memory` と `std::bad_alloc` でも 134 になった(alloc.md 3.2 節)。
- 値スタックの塊は `std::alloc::alloc_zeroed` で取る(`crates/keleut-rt/src/stack.rs:31`、`:85-94`)ので、大域の確保器を通る(critic.md 2 節の 1)。
  大域の確保器の外にあるのは、GC のヒープ(`heap.rs` の `mmap`)だけである。
  【実測】塊は戻った後も回収されず、`ulimit -v 1300000` で、深い再帰だけの例とヒープだけの例はどちらも 0 なのに、両方を続けた例は 3 で終わった(alloc.md 4.2 節)。
- `cont_resume` の失敗の後の注入: 記録 2744〜2746 行(M89 の残した制限の 1)は、注入も値スタックに継続を置き直すので、塊を取れなければ継続の中の `cancel` 節が走らないとした。
  【実測】測った 4 つの例ではこの制限は現れなかった(alloc.md 5.2 節)。
  塊を回収しないので、注入が前に使った塊を使い直すからだと考えている【推論】。
  塊を回収すると、この制限が表に出うる。
- V215 / P252: 【実測】`kw` は V8 のヒープが尽きると 70 で終わり、`before` も失われる(alloc.md 6.2 節)。
  `Worker` の `resourceLimits.maxOldGenerationSizeMb` を使うと、主スレッドは `ERR_WORKER_OUT_OF_MEMORY` を受け取って走り続けた(`probe/alloc/v8worker.mjs`)。
  有限の `ulimit -v` の下では、`kw` は 2 GiB と 4 GiB で `Worker` を作れずに 70 になり、512 MiB では Node が起動しない(記録 3703、3743、3838〜3843 行)。

## 3. 測るだけの残り

### 3.1 `kw` のプログラムごとの 1 段の上限(D564、V234)

**D564**: `keleut-wasm` は、プログラムごとに論理的な 1 段のスタックの上限 `B_prog` を求め、Node のスタックの大きさを `(L + R) × B_prog + 32 MiB` で決める。

- `k` を、ハンドラ式の `cancel` 節の本体の中に、関数の本体を挟まずに書いたハンドラ式が入れ子になる段の数の最大とする。
  ハンドラ式を持たない `cancel` 節だけのプログラムは `k = 0` である。
  `k` は KIR の木の入れ子から求め、下ろしのときに LIR の `Program` に持たせる。
  LIR だけから求めるなら、`$rt_handle` を末尾でなく呼ぶ `cancel` 節の関数を、そのハンドラ式の `cancel` 節の関数へ結ぶ辺の最長の鎖の段の数にする。
- `B_prog = B_wasm + k × (B_wasm − E_rres)` とする。
  `k = 0` のプログラムでは `B_prog = B_wasm` で、スタックの大きさはいまと同じである。
  段が 1 つ増えるごとに重なるのは、予算 1,040 の `cancel` 節と `E_rth = 320` の `$rt_handle` で、合わせて `1,360 = B_wasm − E_rres` である。
- `stack_size_kib` は `B_prog` を引数に取る。
  `keleut build` の出力の `META` に `B_prog` を書き、host の `Worker` の道(`host/keleut-host.mjs:763-789`)は定数の `B_WASM` でなく `META` の値でスタックを決める。
- `k = 1` のとき既定の L のスタックは約 3,044,608 KiB で、`STACK_SIZE_MAX_KIB`(2,097,151)を超えるので、`stack_plan` は `Worker` の道を選ぶ。
  【実測】`Worker` の道は既定の L の約 2 倍と 4 倍のスタックで深い再帰を走らせた(本計画 1.1 節)。
- `KELEUT_WASM_STATS=1` の出力に `k` と `B_prog` を足す。

試験:

- `crates/keleut-wasm` の単体の試験: `k = 0` のプログラムで `stack_size_kib(1 << 20, B_WASM)` が 1,630,208 のままであること。
  gaps.md の形 a〜e の小さな版で `k` が 1(形 b は 2)になること。
- `crates/keleut-cli/tests/wasm_cmd.rs` に、形 c(`NV = 92`、`GADD=1`)のプログラムを試験の中で作り、`--max-depth 600000`、N = 299,000 で `--backend wasm` と `--backend interp` の出力と終了状態が同じ(`2`、`bottom`、`7`、0)であることを確かめる試験を足す。
  feature `llvm` があれば `--tier jit-only` も比べる。
  直す前の `keleut` でこの試験が落ちること(`kw` が 70)を確かめてから直す。
- cram にはしない。
  Diktor はこの入力で 600 秒を超え(本計画 1.1 節)、`--suite depth` の組 `dk-ir` と `x-ir` が基準にならないからである。
  `kconform expect` は `ki` の選択肢で走らせるので、`kw` を見張れない。
- `probe/gaps/bytes.sh` で、形 c、`GADD=1`、`NV` = 60〜100 の 1 つの N あたりのバイト数を測り直し、1 段あたりが `B_prog` 以下であることを実施記録に書く。

## 4. 実行時の確保の制限

### 4.1 仕様の文(D566、D567)

**D566(P259)**: LangSpec §15.5 の表の 1 の行の条件を次の文に改める。

```text
型検査に通らないファイルがあるか、import が誤っているか、型検査か実行の前の変換に要する領域が処理系の限度を超えた
```

表の下に次の 1 文を足す。

```text
実行の前の変換は、型検査の後、初期化を始める前に処理系が行う処理(中間表現への変換、その読み込みと検証など)であり、その範囲は処理系が定める。
```

この行に入るのは、次の 3 つである。

1. KIR の書き出しの入れ子の限度(`keleut run` と `diktor --emit-ir` はいまも 1 で終わる。本計画 1.4 節)。
2. フロントエンドの確保の失敗(V236。いまは 134)。
3. 仮想メモリの上限の下で、KIR の処理のスレッドを作れない場合(V235 の一部。いまは 70)。

実行のスレッドを作れない場合は、評価に要する領域の不足なので 3 とする(本計画 4.4 節)。

理由: 3 つとも、初期化を始める前に処理系の限度に当たる場合である。
いまの文は「型検査」と書くので、KIR の書き出しの限度の 1 は厳密には表に当てはまらない(decide.md 1.4 節)。
3 つを別々に決めると、フロントエンドの失敗が 3 になるか、実行の失敗が 1 になりうる(critic.md 3 節の 2)。

代案: 表を変えず、3 つを処理系の定める終了状態にする。
§15.5 は「出力に書き出せない場合の終了状態は処理系が定める」と並べて書けるが、型検査を通ったプログラムの終わり方が表の外に出るので採らない。

**D567(P260)**: IRSpec 1 節の除外の「`N_alloc_max` の検査によらないメモリの不足」の項を、次の 3 つの場合を挙げる形に改める。

1. WasmGC の後段が V8 のヒープを使い尽くす場合と、Node が仮想メモリの上限の下でスタックやスレッドを取れない場合(70)。
2. RustKeleut の `ki` と `kj` で、LLVM の中の確保が失敗する場合と、大域の確保器の予備(本計画 4.2 節)を使い切った後に Rust の確保が失敗する場合(SIGABRT、134)。
3. OS が物理メモリの不足でプロセスを止める場合(SIGKILL、137)。
   どの読み手でも起こりうる。

Diktor での確保の項はそのまま残す。
11.1 節の表の後ろの注(`doc/IRSpec.md:968-969`)も同じ範囲に改める。
版の履歴の表に `1.0(本文の改訂)` の行を足す(計画 261104-1 の D556 の規則。KIR の受理、意味、符号を変えない)。

理由: 本計画 4.2 節の修正の後も、LLVM の C++ の確保の失敗は Rust から捕まえられない(C API に `install_bad_alloc_error_handler` が無い。alloc.md 3.4 節)。
物理メモリの枯渇による SIGKILL は、`ulimit -v` の無いプロセスでどの処理系にも起こる。

`doc/sample.kel` に終了状態と処理系の限度と対話的な実行の記述は無い【実測、grep で `終了状態`、`限度`、`対話`】ので、`diktor/test/sample/sample.kel` の同期は要らない。

### 4.2 大域の確保器と試験用の失敗(D568、V230)

**D568**: `keleut` のプロセスの大域の確保器を包み、次の 4 つを行う(alloc.md 3.4 節の案 A、B、E と F)。

1. **予備と役割の印**。
   - 確保器は `std::alloc::System` を包み、起動のときに予備(8 MiB を案とする)を取っておく。
   - 各スレッドは役割(実行、フロントエンド、翻訳、そのほか)をスレッド局所の値に持つ。
     実行のスレッド、フロントエンドのスレッド、LLVM の翻訳のスレッドは、作った直後に役割を書く。
   - 確保が失敗し予備があれば、予備を返して役割ごとの印を立て、確保をやり直す。
     やり直しも失敗するか予備が無ければ、いまと同じく `handle_alloc_error` で止まる(D567 の 2)。
   - 包みと印は `keleut-rt` の小さなモジュールに置き、`#[global_allocator]` の宣言は `keleut-cli` の `main.rs` に置く。
     `kconform` は包まない。
2. **印を見る場所**。
   - 実行の役割の印は、`Rt` のヒープの確保の入口(速い道を含む)と、値スタックの塊を取る道で見る。
     立っていれば `Stop::OutOfMemory` を返し、いまのメモリの不足と同じく `cancel` 節を走らせて 3 で終わる。
     JIT のコードの中の確保の速い道(M115)も同じ印を見る(critic.md 3 節の 6)。
   - フロントエンドの役割の印は、型検査と KIR の書き出しの後に見る(本計画 4.4 節)。
   - 翻訳の役割の印が立ったら、その関数の翻訳を捨て、それ以後の翻訳をやめる。
     プログラムはインタプリタで続ける。
     翻訳の失敗をプログラムのメモリの不足と取り違えない。
   - `keleut repl` は、実行時エラーで止まった入力の後、次の入力の前に予備を取り直す。
     取れなければ予備なしで続ける。
3. **回収の中の確保をなくす**。
   `Points::live` に出力先の `Vec` を渡す形を足し、`gc::Frames` の作業域を使い回す。
   `FuncRoots::new`(`crates/keleut-rt/src/gc.rs:335`)と `any_slots` の作業域は、回収を始める前に `try_reserve` で取り、取れなければ回収を始めずに `Stop::OutOfMemory` を返す。
4. **JIT の翻訳の前の検査**。
   `RLIMIT_AS` が有限なら、翻訳の前に `/proc/self/statm` の仮想の大きさとの差を調べ、64 MiB を下回れば翻訳せずにインタプリタで続ける(`crates/keleut-llvm/src/run.rs` の翻訳のスレッド)。
   LLVM の中の失敗を捕まえる手段は無いので、窓を狭めるだけである。

予備の使われ方の順: 値スタックの塊(1 MiB 以上)の確保は大域の確保器を通るので、塊の確保の失敗では、まず大域の予備を返してやり直し、それも失敗したら値スタックの予備の塊(`stack.rs:23-28`)を使う。
GC のヒープは `mmap` で取り、いまの 1 MiB の予備のまま変えない。

**試験用の失敗**: 環境変数 `KELEUT_TEST_ALLOC_FAIL=ROLE:MIN:SKIP` を起動のときに読む。
役割 `ROLE` のスレッドで、`MIN` バイト以上の確保の `SKIP + 1` 回目を 1 回だけ失敗させる。
失敗は OS の失敗と同じく予備の道を通るので、印を立てる道を決定的に試せる。
`MIN` を 1 MiB にすれば値スタックの塊と形の表の広げ直しだけを、`MIN` を小さくして `SKIP` を選べば回収の中や `rec_fields` の確保を狙える(critic.md 2 節の 1)。
変数は試験のためだけのもので、`AGENTS.md` の試験の説明にだけ書く。

案 C(`RLIMIT_AS` から予算を決める)を採らない理由(P262): 予算の見積もりを誤ると、走れるプログラムをメモリの不足にする。
本 D568 の後に `sweep_as.sh` で 134 がどれだけ残るかを測り、残れば次の計画で決める。
案 D(約 200 か所を `try_reserve` にする)は、費用に見合わず、LLVM の確保が残る。

試験(M108):

  どれも `cancel` 節を持つハンドラの中で起こし、`before`、`cancel`、`実行時エラー: メモリ不足です`、3 を `--backend interp` と `--tier jit-only` で確かめる。

**D571**: 値スタックの塊を回収し、注入では継続の写しをそのまま塊として値スタックにつなぐ(alloc.md 4.4 節の案 A と 5.4 節の案 A)。

### 4.6 V215 と P252(D572)

**D572(P261)**: `kw` の V8 のヒープの枯渇は、P252 の決定のまま 70 で終える既知の逸脱とし、V215 を閉じる。
`AGENTS.md` の `--backend wasm` の項に、有限の `ulimit -v` の下では `kw` が 2 GiB と 4 GiB で `Worker` を作れずに 70 になり、512 MiB では Node が起動しないことを書く(M107)。

理由:

- 【実測】`Worker` の `resourceLimits.maxOldGenerationSizeMb` で出力を保って 3 で終える案 B は作れる(alloc.md 6.2 節)が、`cancel` 節は走らないので §15.5 からの逸脱は残る。
- 案 B はいつも `Worker` で走らせることになり、シグナルの転送、`RLIMIT_STACK` を上げる道、起動の時間が変わる(critic.md 5 節の 9)。
  `conformance/bytes/` と `sinkfail` の試験と、本計画 3.1 節の `B_prog` の測り直しが要る。
- `cancel` 節まで走らせる案 C は、確保の多いプログラムの速さに効き、1 回の大きな確保が閾値を飛び越えると V8 が先に止まる。

所有者が案 B を選んだら、M111 の後に 1 つのマイルストーンを足す。
中身は、host をいつも `Worker` で走らせ、標準出力のバッファを主スレッドに送り、`ERR_WORKER_OUT_OF_MEMORY` で `実行時エラー: メモリ不足です` を書いて 3 で終えることと、起動の時間、`bytes/`、`sinkfail`、本計画 3.1 節の試験の測り直しである。

### 5.1 小さな宿題(D573、D574、D575)

**D573**: `rustkeleut/lib/rt.kirt` は作らない。

理由:

## 12. 進め方の原則

- マイルストーンごとに、実装の後で敵対的な検証を行う。
  観点は、仕様の文(§15.5、§6.6、IRSpec 1 節、11.1 節、14 節が互いに、また §13.6、§18、§18.5 と食い違わないか)、確保の失敗の道(印を見る場所の漏れ、予備の使われ方、`cancel` 節の中の失敗)、試験の網羅(直す前に試験が落ちるか、後段の組の間の比較が働くか)、記録の整合(番号、行番号、台帳、既知の差の数)の 4 つを基本とする。
  検証者の指摘ごとに反証者を立て、反証されなかった指摘を直し、直したものを 1 回検証し直す。
- 振る舞いの分類を文書に書くときは、区別する最小の変種を並べて同じ条件で測ってから書く。
  `ulimit -v` の境のように機械で揺れる値は、境の両側で測り、余裕を書く。
- 時間を測るときは負荷の平均を添える。
  基準とベンチマークは負荷の平均 1 以下のときに測る(`rustkeleut/bench/README.md`)。
- `kconform --suite all` を同時に 2 つ走らせない。
  `--suite depth` は `--jobs 6` で走らせる(32 並列では OOM killer が `depth/gresume.t` を止める)。
  Diktor の木の評価器で数分を超える入力を `--suite all` の cram に置かない。
- 検証者と担当の書き込み先は scratchpad に限り、報告を受けたら親と diktor の `git status --short` を確かめる。
- 本文に逆引用符を含むテキストをシェルで書くときは、ヒアドキュメントを `<<'EOF'` と引用する。
- 既存の `doc/log` の記録は書き換えない。
