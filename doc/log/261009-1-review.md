## 1. 要約

仕様は、処理系の挙動を決めきっている節が多い。
評価順序（§5.1）、末尾呼び出しの保証の範囲（§5.7）、`Float64` の表示（§16.2）、import の初期化順（§15.4）、`cancel` 節（§13.6）は、読めば処理系の出力を予測できる。
できないことを制限として各節に書く方針（§1）も守られている。
1,547 行で、行多相のエフェクト、one-shot のハンドラ、リージョン、型クラス、import までを定めた文書として、節どうしの矛盾は見つからなかった。

直す余地は 3 つの系統に分かれる。

第 1 の系統は、型クラスの実装方式が仕様の制約として表に出ている点である（本書 2.1 節）。
`pure` の形のメソッドを宣言できないので、`Applicative` と `Monad` を利用者が書けない。
これは、高階型パラメータを残す理由として利用者が挙げた「`Functor`、`Applicative`、`Monad` を書けること」と食い違う。

第 2 の系統は、エフェクト行の規則の分散である。
「使うたびに尾部を開く」規則とその例外が §6.2、§6.3、§13.2、§15.2、§17 に分かれて書かれ、§6.3 では宣言の順序が型付けの結果を変える（本書 2.2 節）。

第 3 の系統は、日常のコードに要る小さな構文の不在である。
条件式、単項マイナス、剰余の演算子が無く、`match` とプリミティブで代用するので冗長になる（本書 2.4 節、2.5 節）。

## 2. 設計への指摘

### 2.1 返り値だけにクラスパラメータが現れるメソッド（§12.1）

§12.1 は「返り値にだけクラスパラメータが現れるメソッドは宣言できない」と定めるが、理由を書いていない。
理由は実装の方式にある。
`diktor` は型クラスを**タグディスパッチ**（値が持つ型の印を実行時に見てインスタンスを選ぶ方式）で実装しており、`lib/elab.ml` の 3631 行からのコメントがこの制約の根拠をそう説明している。
値を見て選ぶ以上、引数のどれかにクラスパラメータが頭として現れなければ、選びようがない。

この制約で書けなくなるメソッドは、`Applicative.pure: [A](A) => F[A]`、`Monad.return`、`Monoid.empty: () => A`、`Bounded.min_value` である。
実測では、`val pure[A]: (A) => F[A]` を持つクラスの宣言を、処理系が「クラスパラメータが引数の頭に現れないため宣言できません」と拒んだ。
`Functor.map` と `bind` は書けるので、`pure` の無い `Monad` だけが書ける。

同じ方式から来ている制約が、ほかに 3 つある。

- メソッド名はプログラム全域で一意である（§12.1「異なる型クラスに、同じ名前のメソッドを宣言することもできない」）。
- レコード、タプル、構造的ヴァリアントにはインスタンスを書けない（§12.2）。
- インスタンスを値として渡し、選び直すことはできない（§12.2）。

案は、**辞書渡し**（型検査で決めたインスタンスを、メソッドの実装の表として関数に渡す方式）への移行である。
辞書渡しでは、どのインスタンスを使うかが型検査の時点で決まるので、返り値だけにパラメータが現れても選べる。
§6.2 の曖昧性検査は、制約付きの型変数が束縛の型から決まることをすでに求めており、辞書渡しに要る情報はこの検査が保証するものと同じである。
移行すれば、上の 3 つの制約も原理上は外せる。
費用は実装の側にあり、仕様の文面で変わるのは §12.1 の制約と §12.2 のインスタンスの対象の制限である。
移行しない場合でも、§12.1 に制約の理由が実装の方式にあることを書いておかないと、読者は設計上の判断だと読む。

### 2.2 `let rec ... and` の宣言順（§6.3）

§6.3 は、再帰群の中で閉じた行を注釈した関数を「前にある関数から呼ぶ」場合と「後ろにある関数から呼ぶ」場合で、別の規則を定めている。
その結果、同じ群を並べ替えるだけで型付けの結果が変わる。

```keleut
let rec f(): Unit @ Print = { println("a"); g() }
and g(): Unit @ {} = ()
```

`f` は前にある関数から後ろの `g` を呼ぶので、`f` の本体の行 `{Print}` と `g` の注釈 `{}` が一致せず、型エラーになる。
`g` を先に書くと、`g` の尾部が開くので通る。
実測では、上の順序を処理系が「ラベル Print がありません(行は閉じています)」と拒み、入れ替えた順序は `f : () => {} @ {Print extends R1}` と型が付いた。

§6.3 は回避策として「各関数のエフェクト行を注釈せずに推論させる」と書く。
しかし `pub let rec` は注釈が必須で、最外の `@` を省くと `{}` になる（§15.2、§13.2）ので、公開する群ではこの回避策を使えない。
使えるのは並べ替えだけで、互いに呼び合う 2 つの関数の行が違う場合は、どちらの順序でも通らない。

案は、再帰群の中で完全な署名（§6.4）を持つ関数を、群の検査の前に一般化することである。
§6.4 の前方参照と同じ扱いになり、前後の区別が消える。
本体は注釈の閉じた行で検査し、呼ぶ側では尾部を開くので、健全性の議論は §6.4 と同じになる。

### 2.3 入れ子の `run`（§14.1）

§14.1 は、`run` の本体で「ほかのリージョンに属する参照や可変配列を読み書きすると、型検査に通らない」と定める（1192 行）。
外側の `run` が導入したリージョンも「ほかのリージョン」に含むので、次のコードは通らない。

```keleut
let v: Int32 = run outer {
  let acc = Ref.new(0)
  run inner {
    Ref.set(acc, 1)
  }
  Ref.get(acc)
}
```

実測では、処理系が `Ref.set` の位置を「スコープ付きの型が一致しません」と拒んだ。
§14.1 が示す回避策は、読み書きする関数を本体で作って外側で呼ぶことで（1197〜1198 行）、実用上は入れ子の `run` を使えない。
局所的な作業領域のために `run` を使う補助関数が、呼び出し元から受け取った参照を更新できないからである。

原因は、`Heap` を同名ラベルの重複として行に並べ、左から位置で対応させることにある。
`run h` の本体では `Heap[h]` が最も左にあるので、`Heap[g]` を要求する関数の行と照合すると、位置で `Heap[h]` と対応して失敗する。

案は 2 つある。

- (a) `Heap` の対応を位置ではなく、リージョンが一致する最初の `Heap` にする。
  固定されたリージョンどうしが違えば読み飛ばし、リージョンが推論の途中で未定のときは今と同じく左端を選ぶ。
  §3.4 の重複ラベルの順序の規則は残り、`Heap` だけが特別な扱いになるので、仕様にはその旨を書く。
  未定のリージョンを左端に決めた後で、別のリージョンに決まるべきだったと分かる場合があるかどうかは、確かめていない。
- (b) 今の規則を残し、§14.1 の冒頭に「入れ子の `run` の本体は、外側のリージョンの参照と可変配列を読み書きできない」と制限として書く。
  今は節の終わり近くまで読まないと分からない。

### 2.4 条件式（§11.2）

§11.2 は「`if` はガードにだけ使い、単独の条件式の構文はない」と定める。
分岐は `b match { case true => x case false => y }` で書くことになり、`match` の優先順位が `||` より低い（§5.2）ので、結果を算術に使うときは括弧も要る。

案は、`if c then a else b` を `Boolean` に対する `match` の略記として加えることである。
意味規則は増えない。
`IF` はすでにトークンで、ガードでだけ使っている（`lib/parser.mly` 1106 行）。
優先順位は §5.2 の表で `match` と同じ段に置くと一貫する。
`then` と `else` は予約語になるので、§2.2 の表に加える。

### 2.5 単項マイナスと剰余（§4.2、§4.3、§5.2）

§4.2 は「変数や一般の式に付ける単項マイナスはない」と定め、`-x` は `0 - x` か `__int32_neg(x)` と書く。
実測でも、`let y: Int32 = -x` はパースエラーになった。
§4.3 は「剰余の演算子はなく」と定め、剰余は `__int32_rem` で求める。

案は、演算子クラス `Neg`（`neg: (A) => A`）と `Rem`（`rem: (A, A) => A`）を §12.4 の表に加え、前置の `-` と `%` をそのメソッドにすることである。
`neg` は引数の頭にクラスパラメータが現れるので、本書 2.1 節の制約の下でも宣言できる。
負のリテラルの畳み込み（`lib/parser.mly` 880 行）はそのまま残せる。
§5.2 の表の「負の数値リテラル」の行は「前置の `-`」になる。

### 2.6 数値と文字列の API の名前（§4.3、§16.4）

変換関数は `__i32_to_i64`、算術のプリミティブは `__int32_add` で、同じ型の略し方が違う。
`Ref.new` と `Array.get` はモジュールの修飾名なのに、数値と文字列の操作は `__` 付きの自由関数が利用者向けの名前である。

案は、`Int32.to_i64`、`Int32.rem`、`String.length`、`String.sub` のように標準のモジュールに置き、`__` の名前をプレリュードの内部に隠すことである。

### 2.7 エフェクトと操作の型パラメータ（§13.1）

§13.1 は「利用者が宣言するエフェクトには、型パラメータを付けられない」と定める。
`effect State[S]`、`Exn[E]`、`Reader[A]` を書けないので、状態や例外のハンドラは型ごとに書くことになる。
操作にも型パラメータは書けない（`lib/parser.mly` 817 行、`eff_op: lower_id COLON ty`）が、仕様はこれに触れていない。

標準の `Heap[h]` は型パラメータ付きのエフェクトであり、行の仕組みは 1 引数のラベルを扱えている。
案は、利用者のエフェクトにも型パラメータを許すことである。
同名ラベルの重複と順序の規則（§3.4、§14.1）をそのまま適用すれば、新しい規則は要らない。
許さない場合でも、操作に型パラメータを書けないことは明記する。

### 2.8 コンストラクタ名の一意性と import（§10.1、§15.4）

§10.1 は、見えるコンストラクタの名前がソースファイルの中で一意であることを求め、import した型のコンストラクタも含める（§15.4）。
`Leaf`、`Node`、`Empty` のような名前を持つ 2 つの型を、同じファイルに import できない。
import の `as` は延期中だが、入れたとしても型の改名ではコンストラクタの名前は変わらない。

案は、コンストラクタを型名で修飾できるようにし（`Tree.Leaf`）、一意性を型ごとに緩めることである。
修飾せずに使えるのは、見えているコンストラクタの中で名前が一意なときに限る。
コンパニオン型（§15.1）の仕組みと同じ形になる。

### 2.9 モジュール内の値の名前（§15.3）

§15.3 は「モジュール内の値と、同じソースファイルのトップレベルの値に、同じ名前は付けられない」と定める。
一方、型については §15.1 が「モジュールの中で修飾せずに書いた型の名前は、同じ名前のトップレベルや標準環境の型と別名より、そのモジュールの宣言を指す」と定め、同名を許している。
値と型で規則が違う。

案は、値も型と同じく、モジュールの中では自分の宣言が優先するとそろえることである。

### 2.10 `Console` と `Print`（§13.7、§16.3）

`echo` と `echoln` は `Console` に書き、利用者は `Console` を handle できない（§13.7）。
`println` は `Print` の操作を起こし、利用者は handle できる。
`echoln` と `println` の違いは名前から読めず、出力を捕まえるテストは `println` の側でしか書けない。

案は、`Console` を handle できる普通のエフェクトにし、トップレベルに既定のハンドラがあると定めることである。
`Print` と `with_stdout` は消せる。

### 2.11 入力（§16、§17）

標準環境には、標準入力、コマンドライン引数、環境変数を読む関数が無い。
`extern "C"` で呼べる名前も、数学関数 5 つに限られる（§17）。
`#!` の行と import を入れてスクリプトとして使える形にした以上、`read_line` に相当する関数が 1 つは要る。

### 2.12 `Show` と `Eq` の範囲（§12.4、§12.5、§16.2）

`Show` のインスタンスは `Int32`、`Int64`、`Float64`、`String`、`Boolean`、`List`、`Option` にある（§16.2、`lib/builtin.ml` 386〜396 行、`lib/prelude.kel` 435〜453 行）。
`Unit`、タプル、レコード、`Array`、`Never` には無い。
利用者はこれを足せない。
標準のクラスの標準の型構成子に対するインスタンスは標準環境だけが持ち（§12.2）、レコードとタプルはインスタンスの対象にならない（§12.2）からである。
`Eq` も `Array` には無い。

仕様と実装のずれもある。
§12.4 の表は `==` のインスタンスを持つ型を `Int32`、`Int64`、`Float64`、`String`、`Boolean` とするが、プレリュードは `Eq[List[_]]` と `Eq[Option[_]]` を持つ（`lib/prelude.kel` 465 行、478 行）。
§16.2 の `Show` の表は `List` と `Option` を載せているので、§12.4 の表にも載せる。

### 2.13 ハンドラとエフェクトの対応（§13.4）

§13.4 は、処理するエフェクトを操作節から推論する規則を定める。
修飾しない節だけの場合は「ハンドラに書いたすべての操作を宣言していること、そして宣言したすべての操作がこのハンドラに現れること」を満たすエフェクトを候補にする。
`handle Ask { ... }` のようにエフェクト名を書く構文にすれば、この推論の規則は要らない。

同じ節の「どの節にも一致しなかった操作を外側のハンドラへ自動で回す規則はない」は、すべての操作にガードの無い全称の節を要求している（1072 行）以上、起こらない状況の説明なので削れる。

## 3. 仕様文書への指摘

### 3.1 文法の一覧

構文の規則は、各節の散文と表に分かれている。
次の 3 点は仕様を読んでも分からず、`lib/parser.mly` で確かめた。

- 返り値が矢印型のとき、外側の矢印に `@` を書く構文が無い（1243 行のコメント「入れ子の矢印の外側には @ を書けない」）。
  §3.1 は「`@` は最も近い矢印に付く」と書くだけで、外側の矢印には型エイリアスを使うしかないことを書いていない。
  実測では `let k: (Int32) => (Int32) => Int32 @ {} = ...` に型が付き、処理系は `k : (Int32) => (Int32) => Int32 @ {}` と表示した。
  表示も同じ構文を使うので、`@ {}` がどちらの矢印のものかは表示からも読めない。
- 値束縛に型パラメータを書く形 `let x[A]: T = e` は無い（717〜719 行、`bind_pat annot_opt`）。
  §6.1 は「値の束縛には値の型を注釈できる」としか書いていない。
- エフェクトの操作に型パラメータは書けない（本書 2.7 節）。

付録に EBNF を置けば、この種の「書けない形」を仕様から読める。

### 3.2 型位置の括弧（§3.1、§11.1）

式の `(e)` はグループ化、パターンの `(p)` もグループ化（§11.1）だが、型の `(A)` だけが 1 要素タプルである（§3.1）。
3 つの構文範疇で括弧の意味が違う。

案は、型でも `(A,)` を 1 要素タプル、`(A)` をグループ化にすることである。
式とパターンにそろい、本書 3.1 節の外側の矢印の `@` も `(A) => ((B) => C) @ E` と書ける。
パーサは `)` の直後の `=>` で矢印型を見分けている（`doc/sample.kel` の冒頭の表、`lib/parser.mly` 1238 行）ので、曖昧にはならない。

### 3.3 実行時エラーと警告

「実行時エラー」は仕様の中で 14 回使われるが、プログラムがどう終わるかは書かれていない。
決まっているのは、`cancel` 節が実行されること（§13.6）だけである。
終了コード、診断の出力先、それまでに書いた標準出力の扱いが無い。

「警告」も同様である。
§11.2 は「通常は警告を出す」と書くが、「通常」でない条件と、警告があってもプログラムを実行するかどうかを書いていない。

案は、「実行の開始と終了」の節を置き、起点のトップレベルの評価の開始、正常終了、実行時エラー時の挙動、終了コード、警告の扱いをまとめて書くことである。

### 3.4 推論した行の順序（§13.3、§14.1）

§13.3 の操作名の解決と §14.1 の `Heap` の対応は、行の中で「最も左」にあるものを選ぶ。
どちらも「行を注釈で書いた場合は注釈に書いた順序で決まる」と書くが、注釈が無く推論した行での順序を定めていない。
推論した行の順序を定めるか、推論した行では修飾を要求するかのどちらかが要る。

### 3.5 規則の重複（§6.2、§13.2）

「値束縛の最外の矢印の閉じた行は、使うたびに開く」という規則が、§6.2（508 行）、§13.2 の表（980〜981 行）、§13.2 の本文（998〜999 行）の 3 か所にある。
§13.2 は仕様で最も規則が密な節で、表が 2 つ、例外が 6 つある。
行の開閉の規則を 1 つの表にまとめ、`pub`、`extern`、メソッドの既定はその表の「注釈に何を補うか」の行として書くと、例外の数が減って見える。

### 3.6 その他

- §15.4 の複数ファイルの連結は、処理系のコマンドラインの都合である。
  連結すると非公開の名前が衝突し、`pub` の区別が消える。
  仕様から外し、処理系の文書に移す。
- §4.4 は、`\uXXXX` を UTF-8 で符号化すること、切り出しで不正な UTF-8 になりうること、`echo` がバイトをそのまま書くことを書いていない。
- §14.1 は `h` のカインドを `Type` とするので、`Ref[Int32, Int32]` のような型を排除しない。
  `Region` のカインドを足せば、§3.2 のカインド推論で区別できる。
- §6.4 の「参照先の初期化が済んでから呼び出さなければならない」は、違反したときの挙動（実行時エラーかどうか）を書いていない。
- §6.5 の `with _ = f(a)` だけ、`_` が「引数なし」を意味する。
  ほかの位置の `_` は「受け取って捨てる」である。
  `with f(a)` のように束縛を省く形にすると一貫する。
- §5.1 は、正格評価であることを書いていない。
  呼び出しの手順から推測するしかない。
- §1 は `doc/sample.kel` との関係を書いていない。
  `AGENTS.md` は `doc/sample.kel` を仕様と呼び、`doc/sample.kel` には `Nursery` や `Async` のような将来の設計が含まれる。
  どちらが規範かを書く。

## 4. 優先順位の案

1. 本書 2.1 節（辞書渡しへの移行）。
   利用者の方針と食い違っている。
2. 本書 2.2 節（再帰群の順序依存）。
   同じプログラムの型付けが並べ替えで変わる。
3. 本書 3.1 節と 3.3 節（文法の付録、実行時エラーと警告の定義）。
   文書の穴であり、実装を変えずに直せる。
4. 本書 2.4 節と 2.5 節（`if`、`Neg`、`Rem`）。
   小さく、互いに独立している。
5. 本書 2.3 節と 2.7 節（入れ子の `run`、エフェクトの型パラメータ）。
   行の照合の規則に触れるので、変更が大きい。
