## 2. 末尾ブロック引数

### 2.1 提案

Scala のように、最後の引数を括弧の外にブロックとして書けるようにする。

```text
f { x => value }
g(x) { case (y, z) => value }
```

Keleut はカリー化しないので、「最後の引数」を分離して書く形にする。

### 2.2 構文の空き

現在の文法では、式の直後に `{` を置く規則がない。
後置の規則は `.`、`\`、`(...)` の 3 つだけである（`lib/parser.mly:831-836`）。
`run h {` の `h` は式ではなく（`lib/parser.mly:854`）、`x match {` と `x handle {` はキーワードが間に入る（`lib/parser.mly:786-789`）。

実測では、`f {x => 1}`、`f { x }`、`g(1) { case (a, b) => a }`、`f {}` はどれもパースエラー（終了コード 2）になった。
したがって、新しい規則を足しても既存のプログラムの意味は変わらない。

### 2.3 付けられる位置と menhir の衝突

末尾ブロックを付けられる位置を、次の 3 つに限る規則を試した。

```text
postfix_exp LPAREN call_args RPAREN block   (* g(x) { ... } *)
postfix_exp DOT lower_id block              (* M.f { ... } *)
lower_id block                              (* f { ... } *)
```

作業用のコピーにこの 3 規則（ブロックの中身は文の列だけ）を足すと、menhir（`--explain --strict`）の衝突は 0 件で、`dune runtest` にも差分が出なかった（実測）。
本書 2.4 節の 3 形をこの 3 つの位置と組み合わせた文法は、まだ確かめていない。

一方、任意の後置式の後ろに `block` を付ける規則は避けたほうがよい。
括弧 `( e )` は構文木にノードを残さないので（`lib/parser.mly:929`）、意味アクションで「左辺が呼び出しなら引数の行に足す」と書くと、`(g(1)) { k }` と `g(1) { k }` を区別できない。
前者は「`g(1)` の結果に `k` を渡す」意味であるべきで、後者と混同すると誤った呼び出しになる。
素朴に「任意の後置式の後ろ」と「呼び出しの後ろ」の両方を入れた変種では、shift/reduce の衝突が 1 件出た（実測）。

### 2.4 ブロックの中身の形

ブロックの中身として衝突なく足せる形は、次の 3 つである（実測）。

| 形 | 意味 |
|---|---|
| `f { 文の列 }` | 引数のない関数 `fn() => { 文の列 }` を渡す |
| `f { x => 文の列 }` | 引数 1 個の関数を渡す。引数は識別子 1 個に限る |
| `f { case p => e ... }` | 引数 1 個の照合関数 `fn(v) => v match { case ... }` を渡す |

`case` で始まる文はないので、`{ case ... }` は文の列と LR(1) で区別できる。
節の文法と網羅性の検査、構造的ヴァリアントの行を閉じる規則（§11.2）は、`match` のものをそのまま使える。

括弧で囲んだ引数リスト `{ (a, b) => ... }` は、この 3 形と一緒には入れられない。
`{ (a, b) => ... }` と、タプルを返すブロック `{ (a, b) }` は、`)` の後の `=>` を見るまで区別できないからである。
実測では、文の列と `{ パターン => ... }` を併用すると 12 状態で衝突した。
文の列、`{ x => ... }`、`{ (引数) => ... }` の 3 つを併用すると 13 状態で衝突し、任意に解決された衝突は shift/reduce 4 件と reduce/reduce 28 件だった。
回避するには、字句解析で対応する `)` まで先読みして別のトークンを出す必要があり、`{` の分類を 2 トークンの先読みで決める現在の設計（`lib/lexer.ml:648-656`、`:671-675`）が崩れる。

`{ x: T => ... }`（型注釈付き）と `{ x, y => ... }` も書けない。
字句解析が前者を `LBRACE_TYPE`、後者を `LBRACE_RECORD` に分類するからである（`lib/lexer.ml:706-715`）。

### 2.5 利用者の例と引数の個数

関数の型は引数の個数を含み、`(A, B) => C` と `((A, B)) => C` は別の型である（§3.1）。
本書 2.4 節の 3 形の下では、`{ case (y, z) => value }` は「2 要素タプルを 1 個受け取る関数」になる。
そのため、利用者の例 `g(x) { case (y, z) => value }` は、`g` の最後の引数の型が `((Y, Z)) => R` のときにだけ型検査に通り、`(Y, Z) => R` のときには通らない。

2 引数の関数を末尾ブロックで渡す方法は 2 つ考えられるが、どちらも勧めない。

- 括弧の引数リスト `{ (y, z) => ... }` を入れる。
  本書 2.4 節のとおり字句解析の先読みが増え、括弧が「引数リスト」と「タプルパターン」の 2 通りの意味を持つ。
- 期待される型が 2 引数なら、タプルのパターンを自動で分解する。
  型推論が期待される型に依存するようになる。

2 引数以上の関数は、従来どおり `fn(y, z) => ...` で書けば足りる。

### 2.6 改行の扱い

トップレベルとブロックの中では、識別子と `)` が文を終えられ、`{` が文を始められる（§2.3、`lib/lexer.ml:828-841`）。
そのため、`f` の次の行に書いた `{ ... }` は、末尾ブロックではなく独立した文になる。
実測では、`let r = f` の次の行に `{ 1 }` を書くと、エラーにならずに 2 つの文として型検査を通った。

利用者が末尾ブロックのつもりで `{` を次の行に書くと、エラーにならずに別の文になる。
Scala にも同じ種類の誤りがある。
仕様に「末尾ブロックは同じ行に書く」と定め、後置の位置以外に現れた `{ x => ...}` や `{ case ...}` には専用の診断を出すのがよい。
これらは単独では式にならないので、構文エラーとして検出できる。

丸括弧や角括弧の中では改行を区切りにしない（§2.3、`lib/lexer.ml:861`）ので、括弧の中に限り、改行を挟んでも末尾ブロックとして読まれる。
同じ行に限る規則を括弧の中でも強制するなら、字句解析が「直前に改行があった」ことを `{` に記録する必要がある。

### 2.7 `with` との関係

`with`（§6.5）は「残りの文全体を最後の引数にする」糖衣である。
末尾ブロックは「`}` で区切った範囲を最後の引数にする」糖衣で、式の途中にも置ける（`let ys = map(xs) { x => x + 1 }` など）。
入れ子の深さの点で、両者は互いを置き換えない。
`with` の連鎖を末尾ブロックで書くと入れ子が深くなり（`doc/sample.kel:633-637` の `Parser.bind` の連鎖など）、末尾ブロックを `with` で書くと残りの文全体を包んでしまう。

実装では、末尾ブロックは `with` の脱糖関数 `with_splice` の、引数の行の末尾に継続を足す処理（`lib/parser.mly:338-350`）を共有できる。

ただし `doc/sample.kel:614-617` には、関数を渡す糖衣は `with` だけで表し、別の構文は用意しないという趣旨の設計メモがある。
末尾ブロックを入れるなら、この文を書き直す必要がある。

### 2.8 ほかの構文との関係

- `perform op(a) { k }` は、`perform` がアトムとして自分の引数を持つ（`lib/parser.mly:845` 付近）ので、本書 2.3 節の規則のままでは書けない。
- 末尾ブロックの本体は関数の本体なので、§13.5 の「操作節の中の関数には `resume` を書けない」規則と、§14.1 の「`run` の本体に含めない関数の本体」の列挙に、末尾ブロックを加える必要がある。
- `f {a} {b}` は、カリー化しない方針に合わせて 1 個までとし、2 個目はエラーにするのが妥当である。

### 2.9 利用者が決める点

| 判断 | 選択肢 | 推奨 |
|---|---|---|
| 2-1 ブロックの中身の形 | 本書 2.4 節の 3 形だけ / `{ (a, b) => }` も入れる | 3 形だけ。2 引数は `fn(a, b) =>` で書く |
| 2-2 `{ case (y, z) => }` の意味 | タプル 1 個を受け取る関数 / 2 引数の関数 | タプル 1 個。利用者の例の意図と合うかを確認したい |

## 3. import とロード時エフェクト

### 3.1 提案

外部のソースをロードする `import` 文を入れる。

```text
from "path_searched/dir/base_name" import A
from "path_searched/dir2/base_name2" import A.b
from "kel:path_searched/dir3/base_name3" import { A, B.c, D.E.f, }
```

- `"kel:"` はソースの種類を表し、省略すると `"kel:"`（Keleut のソース）になる。
  当面は `"kel:"` だけを扱う。
- import はコンパイル時に解決する。
- import したソースのロード時に起きるエフェクトは、ロードした側のロード時のエフェクトに加わる。
- 積み重なったエフェクトは、処理系が最後にロード時に実行する。
  許すエフェクトは処理系が決め、当面は任意の標準エフェクトを許す設定だけを扱う。

利用者の問い：将来 AOT を扱うとき、コード生成はコンパイル時に、エフェクトの実行は起動時に行いたい。
この構想でそれは可能か。

### 3.2 AOT の可否

**条件付きで可能である。**
可能な理由は 3 つある。

1. 型検査は評価から分かれていて、何も実行しない（`lib/driver.ml:512-524`）。
2. 利用者の `handle` は式なので、継続はその式の中で閉じる。
   トップレベルの `with` が作るのも、そのファイルの中のブロック式である（`lib/parser.mly:562-563`）。
   そのため、継続がファイルの境界や、コンパイル時と起動時の境界をまたぐことはなく、継続を直列化する必要もない。
3. トップレベルに残せるエフェクトは `Console`、`Async`、`Fs`、`Blocking` の 4 つに限られ（§13.7）、利用者はこのうち `Console`、`Async`、`Fs` を `handle` できない。
   `Blocking` を外す `pinned` は関数を受け取り、宣言は受け取らない（§17）。
   したがって、どのファイルのロード時の行もこの 4 つの部分集合になり、「積み重ねる」処理はその和集合を取ることに当たる。

起動時に行うのは、各ファイルの初期化（トップレベルの式文と、値束縛の初期化式）を、ランタイムのハンドラの下で依存の順に 1 回ずつ実行することだけである。

AOT のための条件は次のとおりである。

- パスは文字列リテラルに限る。
  計算したパスや条件付きの import は認めない。
- 検索パスとソースの種類はコンパイル時に確定する。
  起動時にソースを探さない。
- import はファイルの先頭にだけ書ける。
- import の循環を禁止する。
  循環を許すと、§6.4 の「書いた順に初期化する」がファイルの間で意味を持たない。
- 同じファイルを複数の経路から import しても、正規化したパスで同一視して 1 回だけ初期化する。
  初期化の順は、依存の深さ優先の帰りがけ順（依存される側が先）に固定する。
- 依存先の型検査に要るのは公開署名だけにする（本書 3.3 節の案 B）。
  ただしコード生成で単相化やインライン化を行うなら、依存先の本体か中間表現も要る。
  これは import の可否ではなく、コード生成の方式の選択である。

本書 4 節の真正末尾呼び出しを保証する場合は、バックエンドの選び方も縛られる（4.6 節）。

### 3.3 ファイルの意味

ファイルの扱いには 2 案がある。

**案 A：ファイルを暗黙のモジュールにする。**
§15.3 はモジュールの中で、エフェクト宣言、型クラス宣言、式文、入れ子のモジュールを禁じている。
このままでは、ライブラリのファイルがエフェクトも型クラスも宣言できず、ロード時のエフェクトの出どころである式文も書けない。
制限を外せば成り立つが、`diktor` ではこれらが未実装（`noimpl`、終了コード 4。`lib/elab.ml:5029-5032`）で、作業量が大きい。

**案 B：ファイルのトップレベルを 1 つの名前空間にし、`pub` を付けた宣言だけを公開する。**
ファイルの中には今と同じく何でも書ける。
`pub let` と `pub extern` には完全な型注釈が要る（§15.2）ので、依存先の公開署名は本体を推論しなくても構文から決まる。
`diktor` の型検査も、注釈の完全な束縛の署名を本体の推論の前に登録している（`lib/elab.ml:4607-4634`）。
この性質は、分割コンパイルと AOT に向いている。

本書は案 B を推す。
案 B を採ると、§15.1 の「トップレベルの非公開宣言を別のファイルから隠す規則はない」を改めることになる。

案 B にも注意点がある。
トップレベルの `with` は、それより後ろの文をすべて無名関数の本体にする（§6.5）。
そのため、ファイルの途中の `with` より後ろにある `let` は局所束縛になり、公開できない。
このことを仕様に書いておく必要がある。

### 3.4 import が束縛する名前

`import A.b` は、最後の要素 `b` を束縛するのが自然である。
`A` を束縛して `A.b` と書かせたいなら、`import A` で足りる。

`D.E.f` は、今の仕様では指す先がない。
入れ子のモジュールは禁止されており（§15.3）、型クラスもモジュールの中に置けないので、`D.Eq.eq` のような形も生じない。
`D.E.f` を許すかどうかは、入れ子のモジュールを入れるかどうかの判断と同じである。

`newtype` の型名とコンストラクタは可視性を共有する（§15.1）。
型を import したときはコンストラクタも一緒に入る、と決めるのが簡単である。
ただしその場合、表現を隠した抽象型を作る手段がない。
`newtype X = ???`（§10.1）を削除するかどうか（本書 7.2 節）と合わせて決める必要がある。

### 3.5 プログラム全体を範囲とする規則

次の規則は、全ファイルを連結した 1 プログラムを前提にしている。
import を入れると、互いに無関係なライブラリを推移的にロードしただけで衝突が起き、利用者には直す手段がない。

| 規則 | 根拠 | 提案 |
|---|---|---|
| コンストラクタ名はプログラム全体で一意 | §10.1、`lib/decls.ml:772-775` | 一意性の範囲をファイル単位にする |
| インスタンスは (クラス, 型構成子) ごとに 1 個で、大域から見える | §12.2、`lib/decls.ml:1009-1025` | **孤児規則**（インスタンスを、クラスを宣言したファイルか型を宣言したファイルにしか置けない規則）を入れる。衝突を import の閉包の中で静的に検出できる |
| モジュール内の値とトップレベルの値の同名禁止 | §15.3、`lib/elab.ml:4909-4941` | ファイル単位にする |
| 標準宣言の再宣言は名前ごとに 1 回まで | §16.1 | 再宣言そのものを削除する（本書 7.1 節） |
| 修飾名 `M.x` を大域の名前空間に置く | `lib/elab.ml` の module の平坦化 | 内部の名前をファイルの識別子で修飾する |

実装には、もう 1 つの前提がある。
`diktor` では、型検査は宣言の時点の環境で、評価器は呼び出しの時点の大域の束縛で、同じ名前を引く。
その結果、両者が同じ名前から別の実体を選ぶ穴が、プレリュードと利用者プログラムの間にすでにある（`lib/interp.ml` の §14.15、`lib/interp.ml:1386-1407`）。
ただし、この穴が起きるのは `--prelude` で module を含むプレリュードに差し替えた場合で、同梱のプレリュードでは起きない。
ファイルごとに名前空間を作れば、この穴がすべての import の境界に広がる。
型検査が解決した名前を構文木に書き、評価器が修飾のない名前を引かないようにすることが、import の前提になる。

### 3.6 構文と字句

- `from` と `import` は現在予約語ではない（§2.2）。
  テストとプレリュードに識別子としての使用はなく、今なら予約語にしても既存のコードは壊れない。
- `from "p"` の直後で改行し、次の行を `import` で始めると、§2.3 の規則で 2 つの文に分かれる。
  文字列リテラルが文を終えられ、識別子が文を始められるからである。
  `import` を予約語にして、文の継続トークンに加える必要がある。
- `import { ... }` の波括弧は、今の分類では中身によってレコードにもブロックにもなる（`lib/lexer.ml:706-714`）。
  `import` の直後の `{` を専用に分類し、改行を区切りにしない括弧の一覧（§2.3）に加える必要がある。
- `"kel:"` の前置は、`"C:/x"` のような Windows のドライブ文字と区別できない。
  当面は `"kel:"` しかないので、前置は構文として予約するだけにし、パスにコロンを書けないことにする案を推す。

パスの検索規則として、次の点を決める必要がある。

- `./` と `../` で始まるパスを、import するファイルのディレクトリからの相対パスにするか。
- それ以外を、コンパイル時に与える検索パスから探すか。
- 拡張子 `.kel` を自動で付けるか。
- 区切りを `/` に固定するか。
  絶対パスを禁止するか。
- 複数の候補が見つかったとき、先勝ちにするかエラーにするか。

プレリュードが暗黙に import されることも、§1 と §15 に書く必要がある。

### 3.7 既存のテストとの関係

`test/typecheck_sample.t:7` は `diktor --type-check sample/stubs.kel sample/sample.kel` の形で、複数ファイルを連結する現在の CLI に依存している。
`test/sample/sample.kel` は手で編集できない（`AGENTS.md`）ので、連結の機能を廃止するとこのテストの組み方を変える必要がある。
当面は連結の機能を残すのが安全である。

## 4. 真正末尾呼び出し

### 4.1 提案

真正末尾呼び出しを仕様で保証し、`diktor` で実装する。

### 4.2 仕様の現状

`doc/LangSpec.md` と `doc/sample.kel` には、末尾呼び出しの記述がない。
Keleut には `while` がなく、反復は再帰で書くので、仕様が保証しなければ、別の処理系や AOT で普通のループがスタックを使い尽くしうる。
`diktor` は、`eval` の末尾位置を OCaml の末尾呼び出しに保つことを、実装の規約 1 として定めている（`lib/interp.ml:40-47`）。

### 4.3 実装の現状

`diktor` の評価器は直接再帰の木の評価器で、CPS ではない（`lib/interp.ml:285` の `eval`、`:430` の `apply`）。
エフェクトは OCaml 5 の `Effect.Deep` に写している。
`handle` は `Effect.Deep.match_with` に（`lib/interp.ml:883`）、`resume` は `Effect.Deep.continue` に対応する。

実測は、最大 RSS の測定と、OCaml のスタック上限を `OCAMLRUNPARAM=l` で絞った実行の 2 通りで行った。
OCaml 5 は利用者のコードをヒープ上で伸びる fiber のスタックで動かすので、`ulimit -s` は効かない。
既定の設定では、末尾でない再帰でも 1000 万段が 1.4GB と約 5 分を使って通ってしまうため、`Stack_overflow` が出ないことは末尾呼び出しの証拠にならない。
本書では、RSS が一定であることを判定の基準にした。
スタックを絞っても通ることは、`match` の腕からの自己再帰、`even` と `odd` の相互再帰、`with` を通る再帰、操作節が `resume()` だけの perform ループの 4 つで確かめた。

| 形 | 回数 | 最大 RSS | 判定 |
|---|---|---|---|
| `match` の腕からの自己再帰 | 1000 万 | 11MB | 有界 |
| `even` と `odd` の相互再帰（`&&` と `\|\|` の右辺） | 1000 万 | 11MB | 有界 |
| ブロックの `let` の後、ガード付きの腕 | 100 万 | 11MB | 有界 |
| `with` を通る再帰 | 100 万 | 11MB | 有界 |
| `handle` の本体の中の自己再帰 | 1000 万 | 11MB | 有界 |
| `run` を含むループ | 100 万 | 11MB | 有界 |
| 型クラスのメソッドの再帰 | 100 万 | 11MB | 有界 |
| `return` 節からの再帰 | 100 万 | 11MB | 有界 |
| 高階関数を通る再帰 | 300 万 | 11MB | 有界 |
| 操作節が `resume()` だけの perform ループ | 1000 万 | 11MB | 有界 |
| 操作節が `{ Ref.set(...); resume() }` の perform ループ | 100 万 | 322MB | **伸びる** |
| 操作節の `match` の腕で `resume(...)` | 100 万 | 323MB | **伸びる** |
| resume しない操作節の本体からの再帰 | 10 万 | 133MB | **伸びる** |
| 対照：末尾でない再帰 `n + sum(n - 1)` | 100 万 | 104MB | 伸びる（想定どおり） |

### 4.4 穴：操作節の末尾 `resume`

操作節の本体が構文上 `resume(...)` そのものなら、`diktor` は高速経路を通り、`continue` を末尾で発行する（`lib/interp.ml:949-969`）。
本体がそれ以外の形なら、本体全体を `match ... with exception` で包む一般経路を通り（`lib/interp.ml:970-983`）、本体の中の `continue` は末尾にならない。
この挙動は `lib/interp.ml:775-778` に既知の制約として書かれている。

状態を更新してから `resume` を呼ぶジェネレータ風の書き方は普通に現れるので、実用上の影響はこの穴がいちばん大きい。
`resume` は値ではなく、節の中の関数にも書けない（§13.5）ので、節の本体の末尾にある `resume` は、本体の末尾の背骨（ブロックの最後、`match` の腕、`let` の続き、`run` の本体）にしか現れない。
したがって末尾 `resume` は構文から静的に判定できる。
一般経路に「非末尾の部分は例外の捕捉の内側で評価し、末尾の `resume` に着いたら引数の値を返す」評価関数を足し、捕捉を抜けた後で `continue` を末尾で発行すれば塞げる。
見積もりは 50〜80 行と、回帰テスト 1 本である（推測）。

`{ let u = resume(); u }` のような非末尾の `resume` は、この修正の後も呼び出しのたびに空間を使うので、保証の対象外とする。

### 4.5 保証の対象外とするもの

resume しない操作節の本体の中の末尾呼び出しは、保証の対象外とするのが妥当である。
この本体は、捨てる前の継続を抱えたまま評価され、継続を破棄するのは本体の値が出た後である（`lib/interp.ml:976-977`）。
末尾にするには本体の評価より先に継続を巻き戻す必要があり、そうすると §13.6 の「節が終わってから、内側から巻き戻して `cancel` 節を実行する」順序が変わる。

ほかに、次のものも末尾位置としない。

- `handle` 式そのもの。
  本体の中の末尾呼び出しは本体に対して末尾だが、ハンドラの枠が残るので、`handle` 式は外側の関数に対して末尾にならない。
- 演算子のオペランド。
  算術と比較はクラスのメソッドの呼び出し（§12.4）で、`!=` は結果を反転する処理が残る。
- 関数の引数、コンストラクタ、レコード、タプルの要素、`match` の照合対象とガード。
- `cancel` 節。

プリミティブのコールバック（`Array.each`、`par_map`、`par`、`pinned` など。`lib/interp.ml:1045-1120`）を経由する末尾呼び出しは、まだ測っていない。
OCaml 側の実装が閉包を末尾で呼んでいるかどうかで結果が変わるので、保証の範囲を決める前に確かめる必要がある。

### 4.6 仕様の書き方と AOT

仕様の §5 に節を設け、次の内容を書くことを提案する。

- 末尾位置にある関数呼び出しと、操作節の末尾位置にある `resume` は、呼び出し元の評価文脈を保持しない。
- 末尾位置の帰納的な列挙：関数の本体、ブロックの最後の式、`match` の腕の本体、`&&` と `||` の右辺、`run` の本体、`return` 節の本体、操作節の本体の末尾位置にある `resume`。
  `with` より後ろの文は無名関数の本体なので、関数の本体の規則から導ける。
- 本書 4.5 節の対象外の列挙。

AOT で保証を守ることはできるが、バックエンドの選び方を縛る。
C の関数呼び出しへ素直に写すと、C は末尾呼び出しを保証しないので守れない。
自己再帰のループ化とトランポリンの併用、CPS 変換、LLVM の末尾呼び出しの指定、WebAssembly の末尾呼び出し拡張のいずれかが要る。
エフェクトハンドラを別スタックで実装する方式なら、末尾 `resume` はスタックを切り替えて戻らない跳躍になり、保証できる。

### 4.7 利用者が決める点

| 判断 | 選択肢 | 推奨 |
|---|---|---|
| 4-1 保証の範囲 | 自己再帰だけ / すべての末尾呼び出し | すべて。`diktor` はすでに満たしている |
| 4-2 操作節の末尾 `resume` | 保証に含める / 含めない | 含める（本書 4.4 節） |
| 4-3 `run` の本体 | 末尾位置にする / しない | する。参照を GC で管理する前提に立つ。リージョンを一括で解放する実装を将来選ぶなら見直す |
| 4-4 resume しない節の本体、`handle` 式 | 対象外 / 対象 | 対象外（本書 4.5 節） |
| 4-5 適合性のテスト | 小さい `OCAMLRUNPARAM=l` を付けた cram で固定する / しない | 固定する |

## 5. 注釈のない外部関数の Blocking 既定

### 5.1 提案

`@` を付けない外部関数を `Blocking` にし、ノンブロッキングの関数は `@ {}` などで明示させる。

### 5.2 現状と変更後の意味

現在、最外の `@` を省略した `extern` は、使うたびに行多相になる（§13.2 の省略の表、`lib/elab.ml:4727`）。
`extern "C" let sin(x: Float64): Float64` は純粋で、`par_map` にも `@ Console` の文脈にも渡せる。

変更後は、省略が `@ Blocking` と同じ意味になる。
`@ Blocking` は閉じた空でない行なので、使うたびに尾部が開き（§13.2 の注釈の表の 2 行目）、型は `(Float64) => Float64 @ {Blocking extends R}` になる。
`Blocking` はトップレベルに残してよい（§13.7）ので、§17 の例 `let root = sqrt(9.0)` は通る。

一方、次の文脈から呼ぶと型エラーになる（今の `diktor` で `@ Blocking` を明示した宣言を使って実測）。

| 文脈 | 結果 |
|---|---|
| `par_map(xs, fn(x) => sqrt(x))` | 「ラベル Blocking がありません(行は閉じています)」 |
| `@` を省略した `pub let` の本体 | 「pub な宣言はエフェクトを起こせません」 |
| インスタンスのメソッドの本体 | 「型クラスのメソッドの実装は純粋でなければなりません」 |
| `@ Print` や `@ Console` で行を閉じた関数の本体 | 「注釈で固定された行変数なので、ラベル Blocking を足せません」 |
| `par_map(xs, fn(x) => pinned(fn() => sqrt(x)))` | 通る |

### 5.3 `@ {}` でノンブロッキングを表す案

この案は、今の §13.2 の規則のままでは成り立たない。
`@ {}` と明示した関数は、空でない行の文脈から呼べないからである（§13.2）。
実測でも、`extern "C" let cos(x: Float64): Float64 @ {}` は、`@ Console` の関数からも、`@` を省略した `pub let` からも呼べなかった。
最もよくある「出力の途中で数学関数を呼ぶ」使い方が壊れる。

今の規則のままで純粋な外部関数を書く綴りは、行変数を明示する次の形である。

```keleut
extern "C" let sin[E](x: Float64): Float64 @ E
```

この形は今の既定と同じ型になり、`pub` を付けても通る（実測）。
欠点は 2 つある。
綴りが長いことと、表示器が `@ E` と `@ {}` をどちらも `(Float64) => Float64` と表示するので、読み手が区別できないことである。
後者は、表示器が開いた行と閉じた空の行を区別すれば解消でき、この提案とは別に直してよい。

`@ {}` をそのまま使いたいなら、2 つの道がある。

- `extern` に限り `@ {}` を行多相と読む特例を設ける。
  同じ綴りの意味が宣言の種類で変わるので勧めない。
- §13.2 の注釈規則そのものを単純化し、`@ {}` を「純粋で、どの行からでも呼べる」意味にする（本書 7.3 節の単純化案）。
  大きな変更で、健全性はまだ確かめていない。

### 5.4 `"C"` と `"prim"`

`"C"` だけを Blocking 既定にし、`"prim"` は今の既定のままにすることを推す。

- `"prim"` は処理系が実装を持つ組み込みで、プレリュードの `"prim"` 52 本のうち 48 本は `@` を書いていない（`lib/prelude.kel:306-359`）。
  `"prim"` も変えると、この 48 本をすべて書き換えることになる。
- §16.4 はこれらを純粋な署名として説明している。
- プレリュードの prim は利用者が再宣言できない（`lib/decls.ml:185`）ので、`"prim"` の既定が効くのはプレリュードの作者と `--no-prelude` の利用者だけである（推測）。
- `@` の省略の意味が宣言の種類で変わる前例は §13.2 にすでにある（`let`、`pub let`、型クラスのメソッド、`extern`）。
  リンケージで既定を分けても、新しい種類の規則を持ち込むことにはならない。

### 5.5 影響範囲

- コード：`lib/elab.ml:4727` の `None -> (new_row_var lvl, [])` を、`"C"` のときに `Blocking` だけの閉じた行を作って `open_explicit_eff` に通す処理に替える。
  数行の見込みである。
- テストの期待出力：`test/extern_c.t:86` と `test/typecheck_sample.t:66` の型の表示が変わる。
- 仕様：§13.2 の省略の表の `extern` 行と、§17 の「ブロックする可能性のある関数には `@ Blocking` を付ける」段落を書き直す。
- サンプル：`doc/sample.kel:494` の省略の表の `extern` 行を書き直す。
  `doc/sample.kel:793` の `extern "C" let sin(x: Float64): Float64  // ブロックしない` は、コメントが誤りになる。`sin[E] … @ E` に書き換え、写しの `test/sample/sample.kel` を `test/sample/README.md` の手順で同期する。
- 実装のコメント：`lib/elab.ml:549`、`lib/decls.ml:193-207`、`lib/builtin.ml:118-120`、`lib/prims.ml:172`、`lib/syntax.ml:612-613`。

### 5.6 得られるもの

`Async.yield_` と `Async.sleep` はすぐに戻り、実行時の `pinned` は何もしない（§13.7、`lib/builtin.ml:120`）。
そのため、今のところ実行時の利点はない。
得られるのは、ブロックしうる関数に印を付け忘れても、その事実が黙って消えないという安全側の既定である。

既定を変えると、`Blocking` の外部関数を純粋な文脈へ持ち込む正規の手段が `pinned` になる。
`pinned` は「本体の行から `Blocking` を除く」もので、純粋であることを保証しない（§17）。

### 5.7 利用者が決める点

| 判断 | 選択肢 | 推奨 |
|---|---|---|
| 5-1 適用範囲 | `"C"` だけ / `"prim"` も | `"C"` だけ |
| 5-2 純粋な外部関数の綴り | `[E] … @ E` / `extern` での `@ {}` の特例 / §13.2 の単純化 / 新しい綴り | 当面は `[E] … @ E`。§13.2 の単純化を採るなら `@ {}` |
| 5-3 `pinned` の位置づけ | 純粋な文脈へ持ち込む正規の手段と認める / 制限する | 認める |
| 5-4 型の表示 | 開いた行と閉じた空の行を区別する / しない | 区別する（この提案とは別に直してよい） |

## 6. REPL

### 6.1 提案

REPL を実装する。
REPL では型検査と実行が交互に起き、Algorithm W の挙動が見えてもかまわない。

### 6.2 実装の現状

型検査も評価も、宣言を 1 つずつ畳み込む形になっている。
型検査の入口 `Elab.process_decls` は最後に `List.fold_left step env decls` を行い（`lib/elab.ml:4785`）、型の環境は不変の Map である。
評価は `Interp.exec_decl` を畳み込み（`lib/interp.ml:1357`）、同じ名前を束縛し直す処理もある（`lib/interp.ml:1214-1227`）。
型変数のレベルは大域変数でなく引数で渡している。

新しく要るものは 4 つある。

1. 初期化と 1 入力分の処理の分離。
   型検査の入口は呼ぶたびに警告、単一化、網羅性の検査の状態を初期化して最終の環境を捨て（`lib/elab.ml:4796-4814`）、評価の入口も呼ぶたびに大域の束縛を作り直す（`lib/interp.ml:1345-1360`）。
   見積もりは 100〜200 行である（推測）。
2. 失敗した入力の取り消し（本書 6.4 節）。
   最大の工数である。
3. 複数行の入力の終わりの判定（6.5 節）。
4. 結果の表示の方針。

ほかに、クラスのメソッドのラッパは評価の開始時に 1 回だけ作る（`lib/interp.ml:1155`）ので、後の入力で宣言したクラスにも作る処理が要る。
module の平坦化が集めるトップレベルの名前（`lib/elab.ml:4909-4941`）も、入力をまたいで持ち越す必要がある。
持ち越さないと、本書 3.5 節の型検査と評価器の食い違いを入力ごとに作り直すことになる。

### 6.3 仕様の制約が見える点

- 前方参照と型の相互再帰は、1 回の入力の中に限られる。
  前方参照を可能にする署名の登録が、1 回に渡した宣言列の中でしか働かない（`lib/elab.ml:4462-4635`）。
- トップレベルの `with` の範囲は、その入力の末尾までになる。
- `Ref` を入力をまたいで持てない。
  `run` の外へ `Heap` を出せない（§13.7、§14.1）。
  実測では `let r = run h { Ref.new(0) }` が型エラーになった。
- `println` はトップレベルで使えない。
  `Print` をトップレベルに残せない（§13.7）。
- 型、コンストラクタ、インスタンスを再定義できない。
  実測では `newtype T = A` の後に `newtype T = B` を入力すると「二重に宣言されています」になった。

Algorithm W の挙動は、たとえば次の形で見える（実測）。

- `let f = id(fn(x) => x)` は値制限（§6.2）で一般化されず、`f : (_A) => _A` と表示される。
  次の入力 `let g = f(1)` で `_A` が `Int32` に決まり、その後の `f("a")` は型エラーになる。
- `let v = id(#A)` は `v : #A | _R1` と表示され、`#A` だけを扱う `match` の関数に渡した時点で行が閉じる（§11.2）。
- トップレベルで呼んだ関数の行は、トップレベルの行と単一化される。
  `let h = f` が `(Int32) => Int32 @ {Console, Async, Fs, Blocking}` と表示される例がある。
- 整数リテラルの `Int32` への既定化（§4.2）は宣言ごとに行うので、ファイルと違いは出ない。

### 6.4 失敗した入力の取り消し

型の環境は不変なので、入力の前の値に戻すのは簡単である。
一方、宣言の表への書き込みは型エラーの後も残る。
たとえば `add_data` はコンストラクタの重複を検査する前に型を表に登録する（`lib/decls.ml:763-770`）。
実測では、`newtype T = A | Nil` が「コンストラクタ Nil が二重に宣言されています」で落ちた。
この後で `T` が表に残り、打ち直した入力が「T が二重に宣言されています」になるはずだが、これはコードからの推論で、確かめていない。
単一化による型変数の書き換えも戻らないので、一般化されなかった変数が、失敗した入力で決まったまま残りうる。

取り消すには、宣言の表のスナップショットか取り消しの記録と、単一化の束縛の記録が要る。

実行時エラーでは、同じ入力の中で先に済んだ宣言がすでに大域の束縛に入っており、出力は取り消せない。
成功した宣言までを残すと、入力全体で通った型の環境と実行の環境が食い違うので、入力の単位で戻すのがよい。

### 6.5 入力の終わりの判定

括弧やブロックの中なら、字句解析の領域のスタック（`lib/lexer.ml:841-889`）で「まだ続く」と判定できる。
一方、§2.3 の改行の規則は次の行の先頭のトークンを見る（`lib/lexer.ml:849-852`）。
Enter を押した時点では次の行がないので、次の行が二項演算子や `and`、`match` で始まる継続は判定できない。
パーサの開始記号も `program: items EOF` だけで（`lib/parser.mly:555`）、menhir の incremental API も使っていない。

### 6.6 利用者が決める点

| 判断 | 選択肢 | 見解 |
|---|---|---|
| 6-1 入力の終わり | パースが通った時点 / 空行 / `;;` のような明示の終端 | パースが通った時点が最も簡単。ただし `let rec ... and` の継続は 1 行に書く必要がある |
| 6-2 `Print` | REPL だけトップレベルの行に `Print` を足す / 式を `with_stdout` で包む / 何もしない | どれにも代償がある。1 つ目はファイルの規則と食い違い、2 つ目は `let` に効かない |
| 6-3 失敗した入力 | 型エラーは全部戻す、実行時エラーは入力の単位で戻す / 成功した宣言まで残す | 前者 |
| 6-4 結果の表示 | `Show` があれば使い、なければ構造に沿って表示 / 常に構造に沿って表示 | 前者。弱い型変数 `_A` はそのまま表示する |
| 6-5 型の再定義 | 拒否して `:reset` を用意する / 世代を分けて許す | 当面は拒否する。本書 3 節の単位の仕組みができてから世代を分ける |
| 6-6 入力をまたぐ可変状態 | §13.7 の制約を受け入れる / REPL に例外を設ける | 決めていない |
| 6-7 REPL の意味の記述 | 仕様に 1 段落書く / 処理系の文書に留める | 仕様に書く。`with` の範囲と前方参照の範囲を定める |

REPL の各入力を「それより前の入力をすべて import した、名前のない単位」とみなせば、REPL と import を同じ仕組みで扱える（推測）。
型の再定義も、この単位の仕組みの上で世代を分ければ扱える。

## 7. 機能の削除と単純化

`doc/sample.kel` は仕様の例であると同時に、将来の設計（`doc/sample.kel` の §11 の並行性など）を記した文書でもある。
以下の削除候補は、標準環境と `doc/LangSpec.md` から外すものを指し、`doc/sample.kel` の側は設計メモ（`???` のスタブか利用者の宣言）として残す余地がある。
`doc/sample.kel` を変える削除は、写しの `test/sample/sample.kel` の同期を伴う。

### 7.1 安く、独立に消せるもの

| 候補 | 仕様 | 理由 |
|---|---|---|
| 標準の型、エフェクト、クラスの再宣言 | §16.1、§12.2 の末尾 | 「名前ごとに 1 回まで」「構造の一致」「種別の置き換え禁止」の 3 規則が消える。import と REPL の両方の前提になる（本書 3.5 節、6.3 節）。`doc/sample.kel` の再宣言（59、238-240、372-389、463-465、731 行付近）はコメントにすれば足りる |
| `derive structural` | §12.5 | 書いて意味があるのは `Eq` の再宣言だけで、再宣言の削除と一緒に消える。予約語 `derive` も消える |
| `par` と `par_map` | §16.6 | 並列に実行せず（§16.6）、配列の map と変わらない。`doc/sample.kel:723-724` は同名の関数を自分で定義して組み込みを覆っている |

### 7.2 他の判断と組で決めるもの

| 候補 | 仕様 | 組になる判断 |

### 7.3 大きいか、まだ確かめていないもの

- **§13.2 の注釈規則の単純化。
  **
  案は次の 3 点からなる。
  最外の矢印に書いた行は `@ {}` を含めて閉じた行のまま本体を検査し、公開する型でだけ尾部を開く。
  `@ {}` を「純粋で、どの行からでも呼べる」意味にする。
  `pub` で `@` を省略したら `@ {}` と同じにする。
  これで §13.2 の禁止事項の多くと §15.2 の `let rec` の特例が消え、本書 5.3 節の `@ {}` の問題も解ける。
  ただし健全性は推測で、`test/annot_rows.t`（553 行）での回帰の確認が要る。
- **整数型を 1 つにする。
  **
  文脈による整数リテラルの型の決定、`Integral` の述語、接尾辞 `i32` と `i64` が消えるが、テストのほぼ全体を書き換えることになる。
- **高階型パラメータ `F[_]`（§12.3）。
  **
  標準環境は高階のクラスを宣言しておらず、使用は sample の `Functor` とテストだけである。
  消すとカインドの矢印とインスタンスの頭部のカインド照合が消える。

  消すにはタプルとリージョンを両方作り直す必要がある。

## 8. 実施順序

次の 4 つは互いに独立しており、並行して進められる。

- 真正末尾呼び出し：仕様の §5 に節を設け、操作節の末尾 `resume` の穴を塞ぎ、回帰テストを足す。
  プリミティブのコールバックを経由する経路もここで確かめる。
- 外部関数の Blocking 既定：`"C"` だけ。
- 末尾ブロック引数：パーサの変更と、`doc/sample.kel:614-617` の書き直し。
- 本書 7.1 節の削除。

import と REPL は次の順に進める。

1. 下地：宣言の表を単位ごとに持つこと、型検査が解決した名前を構文木に書くこと、段階的に処理する入口と失敗した入力の取り消し。
2. 最小の REPL：型の再定義は拒否して `:reset` を用意し、入力の終わりはパースが通った時点で確定する。
   仕様をほとんど変えずに、下地の仕組みを試せる。
3. import：先に仕様（一意性の範囲、孤児規則、§15.1 の書き換え、パスの規則）を改め、その後で実装する。
   仕様への影響がいちばん大きいので最後に置く。
