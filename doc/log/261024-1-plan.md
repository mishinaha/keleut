# 261024-1: RustKeleut と中間言語 KIR の実装計画

- 日付: 2026-10-24
- 決定: 仕様の所有者は 2026-10-24 に、Keleut のコンパイラと実行系の主な実装を、Diktor とは別に Rust で keleut リポジトリの中に作ると決めた。
  名前は RustKeleut、コマンドは `keleut` である。
  所有者が挙げた理由は次のとおりである。
  Diktor は、セルフホストのコンパイラを動かすためのブートストラップとして作った。
  しかし Keleut は GC 言語で、GC を減らす仕組みが少ない。
  そのため、コンパイラを GC の無い言語で書くほうが、コンパイルの速さで有利である。
  所有者の要求は次の 4 つである。
  1. Diktor と RustKeleut の両方が扱う中間言語(IR)と、そのバイナリ表現を定める。
  2. RustKeleut の後段を、WasmGC、バイトコードインタプリタ、LLVM(ORCv2)の 3 つにする。
  3. できれば、インタプリタと LLVM のコードが、段階的コンパイルのように互いに飛び移れるようにする。
  4. WasmGC は当面 Node.js で動けばよい。

  要求と本計画の対応は次のとおりである。

## 0. 要約

1. Diktor と RustKeleut が共有する IR を **KIR** と名付ける。
   拡張子はバイナリが `.kir`、テキストが `.kirt` である。
   KIR は精緻化の後の木の形をしている。
   名前の解決、クロージャ変換、辞書渡し、末尾の印、節の分類 N/T/G は済ませてある。
   型は表現の種類(Rep)だけを持つ。
   名前は、プロセスに依らない記号で付ける。
   仕様は `doc/IRSpec.md` に置く。
2. 意味を決める処理は、RustKeleut の**共有の下ろし**(KIR → LIR)に集める。
   評価順序、パターンの照合、数値の検査、初期化の検査、エフェクトの規約、論理的な深さがこれに当たる。
   LIR の命令は「trap せず、未定義の動作を持たない」と定める。
   インタプリタ、LLVM、WasmGC は LIR を機械的に訳すだけにする。
3. 関数の戻り値は、どの後段でも常に一様な語とする。
   これで、表現の違う関数の間でも末尾呼び出しが `musttail` のまま保てる(§5.7)。
4. 制御の脱出(継続の破棄、実行時エラー)と G の継続の取り出しは、全後段で 1 つの**状態語の伝播**で行う。
   ネイティブでは戻り値の番兵 `0x2` を併用する。
   ハンドラの論理は、LIR の組み込み関数 `rt_handle`、`rt_resume`、防壁(barrier)として 1 回だけ書く。
   v1 では、ネイティブの例外、ファイバー、JSPI、WasmFX、exnref を使わない。
5. ネイティブ(インタプリタと JIT)のフレームは、分割した共有の値スタックの上に同じ形で並ぶ。
   G の継続の取り出しは、値スタックの区間の写しで行う。
   再開したフレームはインタプリタが続ける(取り出しがそのまま脱最適化になる)。
   WasmGC はフレームを GC の構造体に写し、関数の先頭の `br_table` から再開点へ前向きに飛ぶ。
6. 評価に要する領域の限度は、KIR の水準で定めた**論理的な深さ**で決める。
   既定は 2^20 = 1,048,576 である。
   Diktor の `--run-ir` と RustKeleut の全後段が同じ位置で限度に達し、`cancel` 節を走らせて終了状態 3 で終わる。
   物理的なスタック(ネイティブのスレッド、Node の子プロセス)は、測った 1 段あたりのバイト数から大きさを決める。
7. 実行時の核は、自立した C の 1 つのソース(`rustkeleut/rtcore/`)に書き、clang でネイティブと wasm32 の両方にコンパイルする。
   中身は、`show(Float64)`(正確な多倍長の探索)、musl から取り込んだ `sin cos exp log`、バイト列の比較、レコードの形の表である。
   Rust の `{:.*e}` と glibc は試験の基準にだけ使う。
8. Diktor には、KIR の書き出し、バイナリ、検証器、参照の IR 評価器(`--run-ir`、`--via-ir`)を足す。
   最初に、Diktor の `resume(resume(x))` の不一致(V191)を単独で直す。
9. 試験は差分試験の実行器 `kconform` で行う。
   kconform は cram の `.t` を自分で読み、`diktor` の shim を通して Diktor の cram を無改変で流す。
   組み合わせは interp-only、jit-only、threshold=N、alternating=SEED、mixed=SEED、wasm で、RustKeleut の中ではバイト単位の一致を求める。
   Diktor との差は、`known-diffs.toml` に登録したものだけを許す。
10. マイルストーンは M79〜M101 の 23 個である。
    系統は、Diktor の系統(M80〜M83)、後段の系統(M84〜M95)、フロントエンドの系統(M96〜M99)の 3 つである。
    前提の試作と文書(M79)の後は、Diktor の M80〜M82 と rtcore(M85)を並行して進める。
    後段の残り(M84 から)とフロントエンドは、バイナリの形式と検証器ができる M82 の後に始める。
    フロントエンドの M96〜M98 は kir crate(M84)だけに依存し、コンパイルの速さの関門(M98)を持つ。
    KIR の書き出しと全組の比較(M99)は、受け入れで kr-kj、kr-ka、kr-kw を流すので、M92 と M95 も待つ。
    REPL(M100)と KIR 1.0 の凍結(M101)は最後に置く。
11. Diktor は、Keleut の参照インタプリタ、RustKeleut の試験の基準、KIR の参照実装になる。
    Diktor の上でセルフホストのコンパイラを動かす構想は棚上げにし、主な実装は RustKeleut とする(本計画 1 節)。

## 1. 役割の変更(D551)

本計画の決定で、Diktor と RustKeleut とセルフホスト版の位置づけは次のように変わる。

| 対象 | これまで | 本計画の後 |
|---|---|---|
| Diktor | Keleut のブートストラップインタプリタで、将来のセルフホスト版のコンパイラのテストオラクルを目指す(diktor/README.md:3-5、AGENTS.md:6、diktor/diktor.opam:4) | Keleut の参照インタプリタである。RustKeleut の試験の基準(テストオラクル)と、KIR の参照実装(書き手、読み手、検証器、参照の IR 評価器)を兼ねる |
| RustKeleut | 無い | Keleut のコンパイラと実行系の主な実装である。コマンドは `keleut` |
| セルフホスト版 | Keleut で書き、Diktor をテストオラクルにするコンパイラの構想。計画文書はまだ無い(`doc/log/260912-1-status.md` の未決事項 8) | 棚上げにする。本計画は Diktor を足場にしたセルフホストの手順を立てない |

- Diktor の試験の基準としての働きは、cram を通して保つ。
  kconform が Diktor の cram を無改変で RustKeleut に流し、Diktor との差は `known-diffs.toml` に登録したものだけを許す(本計画 8 節)。
- KIR の参照実装としての働きは、`--emit-ir`、`--run-ir`、`--via-ir` と検証器で持つ(本計画 5 節)。
  Rust のフロントエンドが書いた KIR を Diktor が実行する組 `x-ir` で、2 つの書き手と読み手を突き合わせる(本計画 8.2 節)。
- セルフホストを棚上げにする理由は、所有者の判断(GC の無い言語でコンパイラを書くほうがコンパイルの速さで有利)である。
  Keleut で書いたコンパイラを再び検討するときは、KIR を出せば RustKeleut の後段に載る【推論】。
  その計画は本計画の範囲に入れない。
- 現在の状態を述べる文書を改める。
  - M79 で、AGENTS.md:6、diktor/README.md:3-5、diktor/diktor.opam:4 の役割の文を改める。
  - M96 で、diktor/README.md:23-25 の「他の実装との読み合わせには使えません」を、RustKeleut との読み合わせに使う趣旨に改める(V195)。
  - diktor/README.md:109-111 の名前の由来の段落は残す(M101)。
- 過去の `doc/log` の記録は書き換えない。
  diktor/README.md:18-21 は、過去の記録の行番号を当時のまま残すと定めている(fp §6)。
  過去の記録が延期の条件に書いた「セルフホスト版まで」は、「RustKeleut まで」と読み替える(fp §6)。
  `doc/log/260912-1-status.md:643-644` の未決事項 8(セルフホスト版の計画)は、本計画で閉じる(V199)。
- 役割の文面は P233 の推奨案のとおりにする。

## 3. 全体の構成と 3 案からの取捨

### 3.1 構成

Diktor と RustKeleut は KIR のファイルだけでつながる。
RustKeleut の中では、3 つの後段が共有の下ろしの出す LIR を受け取る。

```
 Diktor (OCaml)                                    RustKeleut (Rust + rtcore の C)
 .kel → lexer/parser/elab ─┐               .kel → keleut-front(M96〜M99)─┐
                           ▼                                              ▼
              KIR writer → prog.kir / .kirt ─────────────────→ kir: 読み込み + 検証(終了状態 65)
                           │                                              │
             ir_eval(--run-ir / --via-ir)              keleut-lir: 共有の下ろし KIR → LIR
             Effect.Deep + 明示の深さの計数              (評価順、照合、検査、エフェクトの規約、深さ)
                                                     ┌───────────┼──────────────┐
                                                 bytecode     LLVM ORCv2      WasmGC(+ rt.wasm)
                                                 + interp  ⇄ 入口の表 ⇄ JIT     Node の子プロセス
                                                 keleut-rt: GC、分割値スタック、ハンドラ記録、出力
                                                 rtcore(C): float show、libm、バイト比較、形の表
```

## 4. 中間言語 KIR

### 4.1 名前と水準(D500、D501)

- 名前は KIR(Keleut Intermediate Representation)、拡張子は `.kir` と `.kirt` である。
  LIR とバイトコードは RustKeleut の内部の形で、ファイルに書かず、互換性も約束しない。
- 水準は精緻化の後である。
  KIR を作る段で、次のものを済ませる。
  - 構文の脱糖(`if`、タプル、`with`、末尾ブロック。tree §1.1)
  - 名前の解決(大域は記号、局所はスロット)
  - クロージャ変換(関数ごとの捕獲の列。辞書の引数も捕獲する。tree §3)
  - 辞書渡しの明示(証拠の平坦化、インスタンスの頭の解決、メソッドの辞書の位置。tree §2、§4.2)
  - 数値リテラルの確定と module の平坦化
  - 末尾の印と節の分類
  - `run` の消去と、`BinOp` と `Neg` のメソッド呼び出しへの書き換え
- KIR は木で、子は符号化に現れる順に評価する。
  ANF にはしない。
  木にする理由は、Diktor の書き出しが `Tree` をほぼ 1 対 1 にたどる形で書け(tree §1.4)、Diktor が ANF の正規化も box の挿入も書かずに済むことである。
  そうすれば Rust のフロントエンドも同じ軽い KIR を出せばよい。
  ANF は LIR で作る。
  代案の ANF(incremental、native)は、Diktor の書き出しを重くし、2 つの書き手がずれうる箇所を増やすので採らない。

### 4.2 型(D502、D503)

- Rep は `bool`、`i32`、`i64`、`f64`、`str`、`any` の 6 種である。
  付ける場所は、局所の束縛(let、引数、パターンの変数)、関数の結果、大域である。
  Diktor の書き出しは、`ty_field` を `repr` した結果の頭が Int32、Int64、Float64、Boolean、String ならその Rep を、ほか(`Generic` を含む)なら `any` を書く。
- 関数と呼び出しには `may_yield` の 1 ビットを付ける。
  値が 0 になるのは、エフェクト行が閉じていて、要素が `Console`、`Heap`、`Blocking` だけのときである。
  この印は最適化(D534)にだけ効く。
- 完全な型は、読み飛ばせる節 0x82 に文面で置く。
  検証器はこれを使わない。
  完全な型を持たせない理由は、持たせると検証器が行多相とスコープ付きラベルの型検査を再実装することになるからである【推論】。
  再実装することになる型検査器の構造と規模は fp §1.3 にある。
- **戻り値は一様**(D503): KIR が持つ結果の Rep は検証と最適化のためのものである。
  LIR の呼び出し規約では、どの関数の戻り値も `any`(一様な語)とする。
  そうしないと、`f(x): Int64 = g(x)`(`g` は多相で `any` を返す)や、クロージャを通す末尾呼び出しで、呼び出しの後に unbox が要る。
  呼び出しは末尾でなくなり、§5.7 を破る(native 2.3)。
  v1 では引数も境目で `any` にする。
  箱に入れない引数の入口は、戻り値に手を加えない包みで後から足せる(V207)。
  代案の incremental D510/D545(宣言の Rep で生のビットを返す)は、§5.7 の hof と dict の場合を壊すので採らない。

### 4.3 安定な名前(D504)

- Diktor の oid、`h_id`、ハンドラの起動の番号はプロセスの中でしか通用しない(tree §0 の 4)ので、KIR には書かない。
- 単位の鍵は次のとおりである。
  - プレリュードは `prelude`、組み込みは `builtin`、コマンド行の起点(複数のファイルを連結した 1 単位)は `main`。
  - ほかの単位は、起点のディレクトリからの相対パス(区切りは `/`)。
    `--import-path` の i 番目の下にあるファイルは `@i/相対パス` とする。
- 大域の記号は `単位の鍵/修飾名` である。
  同じ単位で同じ名前を再び束縛したときは、2 つ目から `#1`、`#2` を付ける(§6.1 の再束縛は別の実体である)。
- 型、コンストラクタ、エフェクト、操作、クラス、インスタンスにも記号を付ける。
  インスタンスは `単位の鍵/instance:クラス[頭]#n` である。
- 持ち上げた関数は、持ち主の記号に `$` と、持ち主の本体の前順の番号を付けて名指す(例 `main/loop$3`)。
  ハンドラの本体と節は `$h<n>.body`、`$h<n>.op.<名前>`、`$h<n>.return`、`$h<n>.cancel` とする。
- ラベルと操作の短い名前は文字列表の添字で表す。
  局所は関数の中の番号で表す。
- 書き出しは決定的にする。
  同じ入力からは、プロセスが違っても同じバイト列を出す(M81 の受け入れの `cmp`)。
  記号はリンクと診断にだけ使い、実行時の意味には使わない(§18.1)。
  代案の走査の順の添字(incremental D505)は、Rust のフロントエンドに Diktor の走査の順を一字一句再現させることになるので採らない。

### 4.4 プログラム、初期化、使うたびの評価(D505、D506、D507)

- `.kir` の 1 ファイルは、プレリュードを含む全単位を初期化の順(§15.4。起点が最後)に並べた、自己完結のプログラムである。
  単位ごとに節を分けて持つので、後で分割コンパイルへ広げられる(V210)。
- 単位の初期化の手順は 6 種である。

  | 手順 | 意味 |
  |---|---|
  | `def_value g f` | 0 引数の関数 `f` を評価して `g` に置き、初期化済みにする |
  | `def_pattern [g…] p f` | 0 引数の関数 `f` を評価し、結果をパターン `p` と照合する。合わなければ実行時エラーにする(文面は `letpat` と同じ)。合えば束縛した各大域に順に置き、初期化済みにする(トップレベルの `let (a, b) = e` や `let Some(c) = e`。§6.1、§11.1) |
  | `def_fns [g…]` | 関数の大域(let rec の群を含む)を初期化済みにする |
  | `def_dictabs g` | 辞書を受け取る値束縛を初期化済みにする(評価はしない。§6.4) |
  | `def_instance i` | インスタンスを使える状態にし、前提も自分の制約も持たない値束縛のメソッドを、宣言の順に 1 回だけ評価する(fid §8 の inst2) |
  | `run_exp f` | 式文を評価する。辞書を受け取る式文は書き出さない |

- 大域とインスタンスは、初期化済みの印を持つ。
  初期化の前に読むと実行時エラーになる(fid §10 の fwd.kel、§8 の inst.kel)。
- **検査を省いてよい条件**(D506): 大域 `g` の参照を含む最も外側のトップレベルの実体の手順が、`g` の手順より後にあるとき、または両者が同じ `def_fns` の群にあるときだけ省く。
  反例は `let p = {f = fn(x) => h(x)}` で、`h` が後に宣言されている形である。
  ここで作った無名関数は `h` の初期化の前に呼べるので、検査を残す。
  この反例を `conformance/init/` に置く。
  同じ場所に、トップレベルのタプルの分解と、照合に失敗する `let Some(c) = None`(先の出力の後に実行時エラーで 3)の試験も置く。
- 範囲外の数値リテラルは `lit_error(lit_range, 字面)` とする。
  これは評価したときに初めて実行時エラーになる。
  下ろしも最適化も、これを畳み込んだり、前へ動かしたり、消したりしてはならない(§4.2、fid §1)。
- **使うたびの評価**(D507): 辞書を受け取る値束縛は、KIR の意味では使うたびに初期化式を評価する(§6.4、§12.2)。
  RustKeleut が結果を保存してよいのは、初期化式が構文上 `closure` のときだけである。
  Diktor の `da_last`(同じ辞書の列なら前の結果を返す)は観測できないので許す、と IRSpec に書く。
  理由は、初期化式がエフェクトを起こせず、1 回目が誤りか停止しないなら 2 回目に届かないことである(V197)。

### 4.5 式と評価順序(D508)

| 式 | 子の評価の順と意味 | 末尾の印 |
|---|---|---|
| `lit(bool\|i32\|i64\|f64\|str)` | 定数。`f64` はビット列、`str` は blobs の添字 | |
| `lit_error(kind, text)` | 評価したら実行時エラー | |
| `local(i)` `env(i)` `dparam(i)` `global(g)` | 読む。`global` は初期化の検査を伴う(D506) | |
| `ctor0(T,c)` / `construct(T,c,[(field,e)…])` | `e` を**書いた順**に評価し、`field` の位置(宣言の順)に格納する | |
| `variant(l, e)` | 引数が無ければ Unit を積む | |
| `call(f,[a…])` | `f` を先に、次に引数を左から評価して呼ぶ(§5.1、fid §4 の `F12`) | ✓ |
| `method(C,m,d,[own…])` | `d` と `own` を評価し、**この時点で**インスタンスの初期化を検査してメソッドを選ぶ | |
| `opcall(C,m,d,[a…])` | `d` と引数を左から評価し、**その後で**メソッドを選んで呼ぶ。常に末尾ではない | |
| `not` `and` `or` | 短絡する | `and` と `or` の右辺 |
| `closure(fn,[cap…])` `dictabs(fn,[cap…])` `dictapp(e,[d…])` | 捕獲と辞書を左から評価する | |
| `let(i,rep,e1,e2)` `letpat(p,e1,e2)` `letrec([(i,fn,[cap…])…],e)` `seq` | 照合が失敗したら実行時エラー。`letrec` はクロージャをすべて作ってから捕獲を埋める | `e2`、`e`、`seq` の最後 |
| `match(e,[clause…])` | `e` を 1 回評価し、節を上から試す。ガードは、パターンが合った節だけで評価する | 節の本体 |
| `rec_empty` `rec_extend(l,v,r)` `rec_select` `rec_restrict` `rec_update(l,r,v)` | 拡張は `v` を先に、`r` を後に評価する。更新は `r` を先に、`v` を後に評価する。対象は最も外側の同名ラベル(fid §4 の yzext、order2) | |
| `perform(E,op,[a…])` | 引数を左から評価し、最も内側の E のハンドラへ送る | |
| `handle(E,body,[opclause…],ret?,cancel?)` | 本計画 4.8 節 | ✓ |
| `resume(e, tail)` | `e` を評価してから再開済みかを調べ、再開する(D514) | `tail` |
| `hole` | `???` で、実行時エラーになる | |

- `opcall` と `call(method(…))` を分けるのは、メソッドを選ぶ時点が観測できるからである。
  Diktor は、演算子の場合はオペランドを評価してから選ぶ(diktor/lib/interp.ml:340-345)。
  関数の形で書いたメソッド(`show(x)`)は、呼び出し先として先に選ぶ。
  インスタンスの宣言の前に選ぶと実行時エラーになるので、オペランドの出力との前後が結果に効く(inst.kel)。
- `!=` は `not(opcall(Eq, eq, …))` にする。
  辞書の式は `dinst(I,[前提…])`、`dparam/env`、`drecord([(l,d)…])`、`dvariant(…)`、`dbuiltin(C,頭)` の 5 種である(tree §2)。

### 4.6 関数、クロージャ、辞書、データ

- 関数の表の各項目は、次の欄を持つ。
  `kind`(`lambda opclause retclause cancelclause handlebody thunk dictabs`)、引数の Rep、辞書の引数の数、捕獲の数、スロットの数と Rep、本体。
  ハンドラの本体と節も関数にする。
  継続はフレームの境目でしか切れないからである(本計画 6.6 節)。
- インスタンスは、クラス、頭、前提の数、`(メソッドの番号、自分の辞書の数、関数)` の列を持つ。
  実装の関数は `前提の辞書 ++ メソッド自身の辞書` を受け取る(tree §4.2 の ABI)。
- 名目的な型は、記号とコンストラクタの番号で表す。
  フィールドは宣言の順に置く。
  コンストラクタは第一級の値ではない(tree §7)。
- レコードはラベルで操作する命令のまま残す。
  形の確定は LIR が行う。
  ヴァリアントはラベルと積載値 1 個である。

### 4.7 パターンと末尾の印(D509、D510、D515)

- パターンは `wild`、`bind(i)`、`lit`、`record([(l,p)…], closed|open|rest(p))`、`ctor(T,c,[(field,p)…])`、`variant(l,p)` の 6 種である。
  数値のパターンは、照合する列の型で読んだ値として書く(`case 0xFFFFFFFF` は Int32 の -1)。
  Float64 のリテラルパターンは、IEEE の `==` で照合する(D515。LangSpec §11.1 に文を足す。P236)。
  `match` は節の順とガードを保つ。
  決定木は LIR で 1 回だけ作る。
- `call`、`handle`、`resume` は `tail` の印を持つ。
  検証器は §5.7 の規則で末尾位置を計算し直し、印と違えば拒否する。
  `resume` の背骨は節の本体から始まり、`handle` と `lambda` の中には入らない(tree §2)。
  戻り値が一様(D503)なので、末尾の印は Rep に依らない。

### 4.8 エフェクトと節の分類(D511)

- `handle` は、エフェクト、本体の関数、操作節の列、`return` 節(省略可)、`cancel` 節(省略可)を持つ。
  操作節は、操作、引数のパターン、ガード(省略可)、本体、分類 `N|T|G` を 1 つの `opclause` 関数にまとめたものである。
- 分類の規則は次のとおりである(fx §6.0)。
  - N: 返り値の型が `Never` の操作。
  - T: 本体の `resume` がすべて末尾 resume である(`resume` の無い枝を含んでよい)。
  - G: それ以外。

  検証器は、操作の `never` の印と `resume` の `tail` の印から分類を計算し直す。
- `resume` が書けるのは T と G の節の本体の中だけである。
  ガード、`return`、`cancel`、N の節、ラムダには書けない。
- `Console.write` の `perform` は KIR ではほかの操作と同じに書く。
  LIR がこれを実行時の直接の呼び出しに変える(D530)。

### 4.9 リージョン、extern、組み込み(D533)

- `run` は消す。
  `Ref`、`Array`、`MutableArray` の 11 個の操作と `pinned`、合わせて 12 個の組み込みの値(fid §13.2)は `builtin/…` の大域にする。
- `extern "prim"` の 48 個(`grep -c '^extern "prim"' diktor/lib/prelude.kel` → 48【実測】)と `extern "C"` は、`extern(abi, 実装名)` の大域にする。
  表示名は、その大域の修飾された記号の名前(`M.__no_such` など)から取る。
  実装の無い名前は読み込みでは拒否しない。
  呼んだときに実行時エラーにする(§17、fid §12)。
  文面は Diktor の形を付録 B に写したもので、「未実装のプリミティブ: <表示名>」である。
  表示名が実装名と違うときは、続けて「(実装名 <実装名> が見つかりません)」を書く(diktor/lib/interp.ml:1393-1396、diktor/test/extern_c.t:100)。
  終了状態は 3 である。
  `conformance/prim/` に、`extern "prim"` と `extern "C"` のそれぞれについて、宣言だけで呼ばない試験(出力の後に 0)と、出力の後に呼ぶ試験(`before` の後に実行時エラーで 3)を置く。
  `module M { pub extern "prim" let __no_such(x: Int32): Int32 }` のように、表示名と実装名が違う場合の試験も置く(extern_c.t:93-101 と同じ形)。
- RustKeleut では、利用者の関数を呼ぶ組み込み(`Array.each`、`pinned`)と `with_runtime` の結線を、`rustkeleut/lib/rt.kirt` に KIR で書く。
  中の呼び出しも再開点を持つので、継続の取り出しも段の切り替えも組み込みの中で同じに働く(fid §9)。
  `Array.each` は内側のループを末尾呼び出しで書く。
  こうすると、利用者の関数は呼び出しの位置 + 2 の深さで走り、OCaml で書いた Diktor の `Array.each` と深さが一致する(本計画 4.10 節)。
  `pinned` は、`rt.kirt` の中で本体を末尾でない呼び出しで呼ぶ。
  そのため本体も呼び出しの位置 + 2 の深さで走り、組み込みの中から `apply` で本体を呼ぶ Diktor の `pinned`(diktor/lib/interp.ml:1208)と深さが一致する。
  IRSpec の付録 A には、利用者のコードを呼ぶ組み込みごとに、その呼び出しの深さを書く。

### 4.10 論理的な深さ(規範。D513)

§15.5 は、限度の大きさを処理系に任せている(I)。
一方で、限度を超えたときの振る舞い(`cancel` を走らせて終了状態 3)は結果に効く(fid §5)。
IRSpec は、評価の各文脈に整数の深さ `d` を定め、すべての実装が同じ値を数えるようにする。
Diktor の `ir_eval` は OCaml のファイバーの上で動くので、自分のスタックからは深さを得られない。
そのため、規則は「どの境目で数がどの値になるか」の形で書く。

| 場面 | 深さ |
|---|---|
| 最上位の初期化の手順 | 0 |
| 深さ `d` の文脈での末尾でない `call`、`opcall`、`dictapp`、組み込みが利用者の関数を呼ぶ呼び出し(組み込みの中で末尾の位置にあっても、この行で数える) | 呼ばれた側は `d+1` |
| 末尾呼び出し、末尾 resume | 呼び出し元の深さを引き継ぐ(増えない) |
| 深さ `h` の `handle` の本体 | `h+1` |
| 深さ `p` の `perform`。節の選択(パターンとガード)と T の節の本体 | `p+1` |
| G の節の本体(宛先のハンドラの深さ `h`) | `h+1` |
| G の節の中、深さ `c` での末尾でない `resume`。継続の深さの差 `Δ = p − h` | 再開した `perform` は深さ `c+Δ` で値を返す |
| N の節の本体、`return` 節 | `h`(ハンドラ式の位置を引き継ぐ) |
| `cancel` 節 | 巻き戻されるハンドラの `h` |

- 限度の検査は、表で深さが増えるすべての境目で行う。
  末尾でない呼び出し、`handle` の本体に入るとき、節の選択、T の節の本体、G の節の本体、末尾でない `resume` である。
  末尾でない `resume` では、再開した `perform` の深さ `c+Δ` を、継続を写し戻す前に `L` と比べる。
  新しい深さが限度 `L` を超えるときは、その境目に入る前に実行時エラー `depth_limit` にする。
- `Console.write` の `perform` は、LIR が実行時の直接の呼び出しに変える(本計画 4.8 節)ので、深さを変えず、限度の検査もしない。
- **再開での深さのずれ**: 深さ `c` で継続 `K` を再開するとき(`K` を取り出したハンドラの深さは `h`)、`K` の中のフレームと、`K` の中で始まったすべてのハンドラの `h` を、`c − h` だけずらす。
  `K` の中で始まったハンドラは、`K` が持つ連鎖の切り取りの中のものだけではない。
  T の節(またはガード)を走らせている間は、そのハンドラと、`perform` の位置からそのハンドラまでのハンドラが連鎖から外れている(本計画 4.11 節の 3)。
  その節の中から外側のハンドラの G を起こすと、これらのハンドラは切り取りに入らず、`K` のフレームからだけ届く(`perform` のフレームが退避した `saved` と、`rt_handle` のフレームが持つ `HR`)。
  これらの `h` もずらす。
  `K` を取り出したハンドラ自身の `h` は `c` になる。
  そのため、付け直したハンドラの `return` 節と、`resume` しない節は深さ `c` で走る。
  これは、§13.6 でそれらの値がこの `resume` の値になることと合う。
- **予備**: `depth_limit` の誤りが伝播している間は、限度を `L + R`(`R = max(1024, L / 64)`)とする。
  誤りが最上位に届いたら元に戻す(REPL では入力の終わり)。
  予備の中でさらに限度を超えたら、その `cancel` 節からの脱出として打ち切り、記録する(§13.6)。
- **実装の不変条件**(RustKeleut): 各フレームは、入口で自分の深さを値スタックのフレームの見出しに書く。
  末尾でない呼び出しが戻ったら、正常に戻っても番兵で戻っても、`ctx.depth` を自分の深さに書き戻す。
  こうして巻き戻しの経路でも数が正しく減る。
  `rt_resume` は、写し戻す前に `c+Δ` を `L` と比べる(上の限度の検査)。
  そのうえで、写し戻したフレームの深さと、`K` の中で始まった各 `HR` の `h` を `c − h` だけずらす(上の「再開での深さのずれ」)。
  そのため `K` を作るときに、切り取りの中の `HR` と、`K` のフレームから届く `HR` を集めて `K` に持たせる。
  LIR が内部で使う呼び出し(`rt_handle` から本体への呼び出し、`rt_resume` のフレーム、インライン展開)は、上の表のとおりに数え、LIR の呼び出しの数では数えない。
- 既定は `L = 2^20 = 1,048,576` である。
  fid §5 の `nontail.kel`(深さ 1e6 の非末尾の再帰。Diktor は 0 で終える)が既定で通るよう、1e6 より少し大きい 2 の冪にした。
  この既定は、M79 の測定で WasmGC の後段に要るスタック `S`(本計画 6.10 節)が確保できると確かめた場合に限る。
  確保できないときの決め方は、本計画 11 節のリスクの表の `--stack-size` の行に書いた。
  `keleut --max-depth N` と `diktor --run-ir --max-depth N` で変えられる。
  Diktor の木の評価器は OCaml のスタックに従う(V196)。
- 深さが L を超えるが Diktor の木の評価器では通るプログラムは、設計による既知の差である(限度は I)。
  `known-diffs.toml` に理由「限度は I」で登録し、不具合として扱わない。
- `conformance/depth/` には、次の試験を置く。
  同じ形のブロックを Diktor の `ir_depth.t` にも置く(M83)。
  - 入れ子の `handle` の中で `c ≠ h` の深さで再開し、内側のハンドラの `return` 節を L の近くで走らせる。
  - T の節の本体が外側のハンドラの G の操作を起こし、外側のハンドラが `c ≠ h` の深さで再開し、内側のハンドラの `return` 節を L の近くで走らせる。
  - 末尾でない `resume` が L を超え、`resume` の直後に出力を書く(出力の前に 3 で終わる)。
  - `pinned` が、L に届く再帰の本体を呼ぶ。

### 4.11 抽象機械の規範の文(D512)

IRSpec の 9 節は、fx §5 の Q1〜Q10 を規範の文にする。
中でも次の文を明記する。

1. 本体の側から届いた巻き戻しの宛先がこのハンドラの起動でないときは、このハンドラの `cancel` 節を 1 回走らせてから巻き戻しを続ける。
   宛先がこの起動なら、走らせない(native 4.9)。
2. `return` 節は、ハンドラを連鎖から外した後で評価する。
   そのため、return 節の中の誤りでは自分の `cancel` を走らせない。
   N の節の本体も、継続を破棄してハンドラを外した後で評価する。
   G の節の中で `resume` が戻った後のコードも、そのハンドラが連鎖にいない文脈で走る(§13.6)。
3. 節の選択とガードと T の節の本体では、ハンドラの連鎖をそのハンドラの親に付け替える。
   節の中の操作は外側へ届く(§13.4)。
4. `cancel` 節は自分のハンドラの外で走る。
   中で起きた脱出(実行時エラー、破棄、`depth_limit`)はすべて打ち切る。
   標準出力を flush してから標準エラーに記録し、元の巻き戻しを続ける(fx R5)。
   標準出力への書き込みがすでに失敗しているときは、この flush は何もしない(本計画 6.5 節の出力の規約)。
5. ハンドラの起動の同一性は、64 ビットの単調に増える番号で表す(fx R8)。

### 4.12 テキストとバイナリ(D516、D517)

- `.kirt` は S 式で、バイナリと 1 対 1 に往復する。
  正準の印字(字下げ、表の並び、数の綴り、バイト列は `\xHH`)は IRSpec が定める。
  `keleut kir dis`、`diktor --emit-ir-text` はどちらもこの正準形を出し、比較はバイト単位で行う。
  テキストを読む機能は RustKeleut の `keleut kir asm` だけが持つ。

```
(fn "main/loop" lambda (params (n i32) (acc i64)) (result i64) (dicts 0) (caps 0) (yield 0)
  (match (opcall Eq eq (dbuiltin Eq Int32) (local 0) (lit i32 0))
    (clause (lit bool true) (local 1))
    (clause (lit bool false)
      (call tail (global "main/loop")
        ((opcall Sub sub (dbuiltin Sub Int32) (local 0) (lit i32 1))
         (opcall Add add (dbuiltin Add Int64) (local 1) (lit i64 1)))))))
```

- バイナリの先頭 16 バイトは次のとおりである(リトルエンディアン)。
  マジック `00 4B 49 52`(`\0KIR`)、主版 u16、副版 u16、必要な機能のビット u32、節の数 u32。
  その後に節 `id: u8, size: uLEB128, payload` が id の昇順に並ぶ。
  整数は uLEB128 と sLEB128(Wasm と同じく最長の符号化を超えたら誤り)、`f64` は 8 バイトで、NaN の積載も保つ。

  | id | 節 | 中身 |
  |---|---|---|
  | 0x01 | strings | 名前(UTF-8 であること) |
  | 0x02 | blobs | `String` のリテラル(任意のバイト列。NUL と不正な UTF-8 も許す。§4.4) |
  | 0x03 | units | 単位の鍵、元のパス、初期化の順 |
  | 0x04 | types | 名目的な型、コンストラクタ、フィールド |
  | 0x05 | effects | エフェクト、操作、引数の数、`never` の印、実行時が処理する印 |
  | 0x06 | classes | クラス、メソッド、メソッドの辞書の数 |
  | 0x07 | instances | 本計画 4.6 節 |
  | 0x08 | prims | このファイルが使うプリミティブの名前。付録 A に無い名前も許す。後段は、そうした名前の呼び出しを、付録 B の「未実装のプリミティブ: <表示名>」(表示名が実装名と違えば「(実装名 <実装名> が見つかりません)」が続く)の実行時エラー(3)にする(本計画 4.9 節) |
  | 0x09 | globals | 記号、種類(`fn value dictabs extern builtin`)、単位、辞書の数、Rep |
  | 0x0A | functions | 関数の表。本体は前順の木で、各ノードは 1 バイトの命令とその欄 |
  | 0x0B | init | 単位ごとの初期化の手順 |
  | 0x80 | producer | 書き手の名前と版、元のファイルのハッシュ |
  | 0x81 | locations | ノードの前順の番号から(ファイル、行、桁)への表 |
  | 0x82 | types-debug | 完全な型の文面 |

- 読み手は、マジック、版、機能のビット、節の順と大きさ、添字の範囲を検査する。
  0x80 以上の節は読み飛ばしてよい。

### 4.13 版の方針と仕様の置き場所(D518、D519)

- 1.0 までは `0.y` とし、読み手は書き手と同じ `0.y` だけを受け付ける。
  1.0 に凍結するのは M101 で、条件は「Diktor と RustKeleut の両方の書き手と読み手が、コーパスの全件で往復と差分試験に通ること」である。
  1.0 の後は次のとおりにする。
  - 副版で許すのは、読み飛ばせる節と、機能のビットで守る新しい命令の追加だけである。
  - 意味や符号を変えるときは主版を上げる。
  - 各副版の見本を `rustkeleut/conformance/kir-fixtures/` に置き続ける。
- 仕様は `doc/IRSpec.md` に日本語で書く。

## 6. RustKeleut の構成

### 6.1 workspace と crate(D521)

RustKeleut は親の `rustkeleut/` に cargo の workspace として置く(resolver 3、edition 2024、rust-version 1.98)。
サブモジュールにはしない(P232)。

```
rustkeleut/
  Cargo.toml / Cargo.lock    版を固定する(llvm-sys =221.1.1 prefer-dynamic、wasm-encoder と wasmparser =0.262.0、cc)
  rtcore/                    自立した C99(libc なし): f64show.c、shape.c、bytes.c、musl/(sin cos exp log と依存。版と LICENSE を添える)
  lib/rt.kirt                KIR で書いた組み込み(Array.each、pinned、with_runtime の結線)
  host/keleut-host.mjs       Node 側の実行時(起動、入出力、rt.wasm の結線)
  crates/
    kir/            KIR の型、バイナリとテキストの読み書き、検証器
    keleut-rtcore/  rtcore を cc と clang で x86_64 の静的ライブラリと rt.wasm にする build.rs と FFI
    keleut-lir/     共有の下ろし(KIR → LIR)、LIR の検証器、組み込み関数 rt_handle/rt_resume/barrier
    keleut-rt/      値、ヒープと GC、分割値スタック、ctx、ハンドラ記録、継続、出力、終了
    keleut-interp/  バイトコードの符号化とインタプリタ、interp_continue
    keleut-llvm/    llvm-sys の薄い包み、LIR から LLVM IR、LLJIT、スタブ、段の切り替え(feature `llvm`、既定で有効)

    keleut-front/   字句、構文、宣言表、単一化、精緻化、網羅性、KIR の書き出し(M96 から)
```

  inkwell は使わない(LLJIT を包まない。sl)。
- Rust のソースは日本語の rustdoc で書き、`cargo fmt` と `cargo clippy -- -D warnings` を使う。
  Diktor の文芸的な配置は求めない(P246)。

### 6.3 読み込みと検証

検証器(`kir` crate)は次のことを確かめる。
失敗したら 65 で終わる。
1. 添字が範囲にあること。
2. Rep が合うこと(プリミティブ、let、init)。
3. 末尾の印と背骨が、計算し直した結果と一致すること。
4. N/T/G が、計算し直した結果と一致すること。
5. `resume` が許された位置にだけあること。
6. 初期化の手順が各大域をちょうど 1 回定義すること。
7. 節 0x08 の各名前が正しい UTF-8 で、`extern(abi, 名前)` の大域から参照されていること。
   付録 A に無い名前は誤りにしない(本計画 4.9 節、§17)。

検証器は型の健全性を保証しない。
信頼の根は、型検査を済ませたフロントエンドである。

### 6.4 共有の下ろし KIR → LIR(D524)

LIR は、関数ごとの基本ブロックのグラフで、仮想レジスタは Rep を持つ。
Keleut には反復の構文が無い(§5.7)ので、どの関数の制御も**非巡回**になる。
パスは次の順に行う。
1. 環境の配置。
2. パターンの照合を、後戻りを伴う照合の手順に下ろす。
   ガードの順を保ち、照合の失敗は `rt_error(MatchFail)` にする。
3. A 正規化(評価順を命令の順にする)。
4. Rep と箱。
   関数の境目は v1 では引数も戻り値も `any` にする(D503)。
5. 辞書の定数化(`dbuiltin` の `opcall` をプリミティブにする)。
6. レコードの形(閉じた行で単相の箇所は位置を定数にし、ほかは rtcore の形の表を引く)。
7. 数値の検査の明示。
   ゼロで割ったら `rt_error(DivZero)`。
   `MIN / -1` は `MIN`、`MIN % -1` は 0。
   f64 から整数への変換は NaN と範囲(`t >= -2^31 && t < 2^31` など。上端は開区間)を先に検査する。
   整数の `+ - *` は折り返す(LLVM では `nsw` を付けない)。
8. エフェクトの下ろし(本計画 6.6 節)。
9. 初期化の検査の省略(D506)。
10. 深さの命令(本計画 4.10 節。入口で深さを書き、戻ったら書き戻す。限度の検査)。
11. yield の刈り込み(D534)。
12. 生存区間、再開点の番号、スロットの割り当て(スロットは `any` の区画と生の区画に分ける)。

LIR の各命令の意味は `rustkeleut/doc/lir.md` に、「trap せず、未定義の動作を持たない」形で定める。
エフェクトを除く命令の節は M86 で書き、`rt_handle`、`rt_resume`、防壁の節は M89 で足す。
LIR の検証器は、各パスの後に Rep、非巡回であること、再開点の一貫性を確かめる。

### 6.5 実行時(D525〜D530)

- **値の表現**(ネイティブ): 一様な語は 64 ビットである。
  - 最下位ビットが 1 なら即値である。
    Int32 は `(n<<1)|1`。
    Boolean、Unit、引数の無いコンストラクタも即値にする。
  - 下位 3 ビットが 0 なら、8 バイト境界のポインタである。
  - `0x2` は巻き戻しの番兵で、値としては現れず、戻り値の位置にだけ使う。

  箱は Int64、Float64(一様な位置だけ)、文字列(長さ付きのバイト列で、NUL を終端にしない)、レコード(形の id とフィールドの配列)、データ、ヴァリアント、クロージャ、辞書、`Ref`、配列、ハンドラ記録、継続である。
  見出しの 1 語に、種類、GC の印、配置の番号、大きさを置く。
  NaN ボックス化は採らない(tg §2.2)。
- **分割値スタック**(D527): フレームは、1 MiB の塊をつないだ値スタックに置く。
  形は「見出し(関数 id、再開点、深さ、`any` と生の区画の大きさ、呼び出し元のフレームへの相対の位置)とスロット」で、インタプリタと JIT で同じである。
  見出しは番地ではなく区間の底からの相対の位置を持つ。
  区間を別の番地へ写し戻したときは、`rt_resume` が深さの欄と一緒にこれをずらす。
  入口で塊の残りが足りなければ、実行時が次の塊をつなぐ。
  値スタックの大きさは限度にならない(限度は論理的な深さ)。
- **GC**(D526): 動かさないマークスイープで、ミューテータは 1 本である(§13.7)。
  大きさの種類ごとのページと空きリストを使う。
  - 根は、値スタックの `any` の区画、継続の中の区間、大域、インスタンス、ハンドラの連鎖、状態語の積載値、Rust の `Root` のハンドルの枠である。
  - マークは明示のマークスタックで反復し、ネイティブのスタックを使わない(深いリストで落ちない)。
  - 安全点は確保の中だけである。
    JIT は、末尾でない呼び出しと確保の前に、生きている値をすべて(`any` も生の値も)スロットに書く(D538。インタプリタが続きを実行するためでもある)。
  - Rust の実行時の関数は、確保をまたいで値を持つときは `Root` を使う。
  - ステートポイントは使わない(E6)。
- **メモリの不足**: §15.5 は、評価に要する領域が処理系の限度を超えたときも実行時エラーとする。
  Diktor はこれを「実行時エラー: メモリ不足です」と終了状態 3 にする(diktor/lib/driver.ml:928、1353)。
  RustKeleut は、状態語の誤りの種類に `OutOfMemory` を足し、`ERROR(OutOfMemory)` をほかの実行時エラーと同じに巻き戻す(`cancel` を内側から走らせて 3)。
  文面は Diktor のものを付録 B に写す。
  - 1 回の確保の要素の数の上限 `N_alloc_max` を IRSpec の 11 節に置く。
    値は処理系定義で、RustKeleut の全後段で同じにする。
    V8 の WasmGC の配列の長さの上限以下にし、その上限は M79 で測って記録する(V215)。
  - 長さを取る確保(`MutableArray.new`、文字列を作るプリミティブ、それらを下ろした Wasm の `array.new` と `array.new_default`)は、先に長さを `N_alloc_max` と比べ、超えたら `ERROR(OutOfMemory)` にする。
    Wasm では、この検査を trap の補助関数(本計画 6.10 節。D543)に置き、V8 に trap させない。
    `ki` と `kj` では、実行時の確保の関数に置く。
  - `ki` と `kj` でヒープを広げられないとき(mmap やページの確保の失敗)も、プロセスを止めずに `ERROR(OutOfMemory)` にする。
    `cancel` 節が走れるよう、小さな予備の領域を残しておく。
    予備も尽きたら、深さの予備と同じに、その `cancel` 節からの脱出として打ち切る(§13.6)。
  - `kw` で V8 のヒープが尽きたときは、Node のプロセスが落ち、`cancel` は走らない。【推論・要検証 M94】
    これは §15.5 からの既知の逸脱である。
    §15.5 が処理系に任せるのは限度の大きさだけで、限度を超えたら `cancel` を走らせて 3 で終わらなければならないが、`kw` は 3 の代わりに 70 で終わる。
    WasmGC には、V8 が止まる前にヒープの枯渇を捉える移植できる手段が無い。
    当面は `N_alloc_max` の検査と、70 で終わることを文書に書くことを緩和とし、V215 に記録して所有者に問う(P252)。
    確保したバイト数を `--max-old-space-size` より小さい予算と比べ、超えたら `ERROR(OutOfMemory)` にする方法は、M94 で費用を測り、安いときだけ採る。
    差分試験が扱うのは `N_alloc_max` を超える確保だけで、ヒープそのものが尽きる場合は既知の逸脱として試験の対象から外す。
    `ki kj kt ka km kw` の完全な一致(D499)は、この試験の対象の中でだけ成り立つ。
  - `conformance/oom/` に、`cancel` 節を持つハンドラの中で `MutableArray.new(N_alloc_max + 1, 0)` を呼ぶ試験を置く。
    期待は `cancel` の出力の後に 3 で、`ulimit` なしに `ki`、`kj`、`kw` で決定的に再現する。
    Diktor には 1 回の確保の上限が無く、この試験の結果は機械の空きに依るので、`dk` と `dk-ir` との差は `known-diffs.toml` に理由「限度は I」で登録する。
- **rtcore**(D528): 自立した C99 で 1 回だけ書く。
  - `f64show.c` は §16.2 を実装する。
    NaN は、符号と積載に依らず常に `nan` と書く(§16.2。diktor/lib/value.ml:443 と同じ)。
    glibc の `%.1f` は符号の立った NaN を `-nan` と書き、Wasm では NaN の結果の符号が決まらないので、NaN は `%.1f` に渡さない。
    `inf` と `-inf` も、`%.1f` の整数の分岐の前に文字列で書く。
    絶対値が `1e16` 未満の整数値は `%.1f`(`-0.0` を含む)。
    それ以外は p を 1 から 17 まで増やす。
    p 桁の候補は、2 進の値の正確な 10 進展開から多倍長の整数(基数 10^9)で偶数丸めして作る。
    「読み戻して元の値になる」ことは、「候補が x の丸めの区間(x の前後の値との中点で区切る区間。下側の幅は (x − pred(x))/2、上側の幅は (succ(x) − x)/2。下側が狭いのは 2^-1022 より大きい正規数の 2 の冪だけである。端を含むかは仮数の偶奇で決まる)にある」ことと同値なので、strtod なしに正確な比較で判定する。
  - `musl/` は musl の最新の安定版の `sin cos exp log` とその依存を取り込む(P239)。
    作成時点で、この機械のパッケージは 1.2.6-2 である(`pacman -Si musl`)。
    上流の最新の安定版を M79 で確かめて版を決め、出所と sha256 を `rtcore/musl/` に記録する。
  - `shape.c` はレコードの形の intern、拡張、制限、位置の検索を扱う。
    ラベルの番号の昇順に並べ、同名は外側から並べる正準の配置にする(§18.3 により結果に効かない)。
  - `bytes.c` は符号なしバイトの辞書順の比較を行う。
  - 組み方は `clang -std=c99 -O2 -ffreestanding -fno-builtin -ffp-contract=off -fno-math-errno` で、x86_64(`cc` crate で静的ライブラリ)と `--target=wasm32 -nostdlib`(`wasm-ld --no-entry` で `rt.wasm`)の両方を作る。
  - ネイティブの全後段と WasmGC が同じソースの結果を使う。
    clang で組んだ musl が x86_64 と wasm32 でビット一致し、libc に依存しないことは、まだ確かめていない。【推論・要検証 M79、M85】
  - 試験の基準は 3 つである。
    glibc の `%.*g`(fid §2 の fltcmp の 1,998,964 件)、Rust の `{:.*e}`(E13)、Diktor の出力。
- **libm**(D529): `sin cos exp log` は rtcore の musl を不透明な記号 `krt_sin` などで呼ぶ。
  LLVM は意味を知らないので、畳み込みも組み込み関数への置き換えもしない。
  `sqrt` は IEEE の命令(`llvm.sqrt`、`f64.sqrt`)を使う。
  Diktor の glibc との最下位ビットの差は既知の差とし、LangSpec §17 に「結果の最下位のビットは処理系定義」と書く(P237、V193)。
- **出力**(D530): `Console.write` は実行時の直接の呼び出しで、64 KiB でバッファする。
  flush するのは、満ちたとき、標準エラーへ書く直前、終了の前である。
  書き込みは短い書き込みを繰り返す。
  `EAGAIN`(非ブロッキングのパイプ)は待ってから再試行する。
  失敗(`EPIPE`、`EBADF` など)は `ERROR(Io)` として巻き戻し、`cancel` を走らせてから 74 で終わる(eval.t の sinkfail.kel)。
  最初の書き込みの失敗で、未出力のバッファを捨て、標準出力に失敗の印を付ける。
  その後の flush は、防壁の中でも、標準エラーへ書く直前でも、終了の前でも、何もせず、誤りも起こさない。
  防壁の「cancel 節で例外が抑制されました」の記録と、最後の「標準出力に書き出せません」の診断は、そのまま標準エラーに書き、終了状態は 74 にする。
  これは Diktor と同じである(OCaml のチャネルは書き込みの誤りでバッファを捨て、`safe_exit` は flush の誤りを無視する)。
  eval.t:845-848 の sinkfail.kel を `conformance/bytes/sinkfail.t` に写し、その中に `$ keleut run sinkfail.kel >&-` の起動と、標準エラーの 2 行と `[74]` の期待を書く(試験の形は本計画 8.1 節)。
  実行時エラーが最上位に届いたら、標準出力を flush し、文面を標準エラーに書き、3 で終わる。

### 6.6 エフェクトの規約(全後段で共通。D531、D532)

**データ**

| 名前 | 中身 |
|---|---|
| ハンドラ記録 `HR` | 起動ごとの 64 ビットの番号、エフェクト、節の表、`return` と `cancel`、親、本体を呼んだときの深さ `h`(再開のたびに `rt_resume` がずらす。本計画 4.10 節) |
| `ctx.handlers` | 有効なハンドラの単方向の連鎖(最も内側が先頭) |
| 状態語 `ctx.pending` | `NONE`、`YIELD(hr, 節, 束縛)`、`DISCARD(hr, Value(v) \| NeverBody(節, 束縛))`、`ERROR(kind, 文面)`(`kind` は実行時エラー、`depth_limit`、`Io`、`OutOfMemory`) |
| 継続 `K` | フレームの列(ネイティブは値スタックの区間の写し、Wasm はフレームの構造体の列)、連鎖の切り取り、`HR`、`K` の中で始まったハンドラの `HR` の列(本計画 4.10 節)、`Δ`、`used`、`alive` |

**伝播**: 末尾でない呼び出しが戻ったら、ネイティブでは戻り値が `0x2` か(`cmp rax, 2; je`。ctx を読み直さない)、Wasm では大域 `$pending` が 0 でないかを調べる。
状態が立っていれば、普通のフレームは次の LIR 命令を実行して自分も戻る。
- `YIELD` なら `yield_save(再開点)`。
  ネイティブでは何もしない(フレームはすでに値スタックにあり、再開点も呼び出しの前に書いてある)。
  Wasm では生きている局所を構造体に詰めて `ctx.yield_frames` に積む。
- `DISCARD` と `ERROR` なら、フレームを捨てて戻る(値スタックの先頭は受け手が戻す)。

フレームの表現が後段で違うのはこの 1 命令だけである。
`rt_handle`、`rt_resume`、防壁は、どの後段でも同じ LIR の文面である。

**`handle` と `rt_handle(hr, body)`**(`handle` が末尾なら、この呼び出しも末尾にする)
1. `hr.parent = ctx.handlers`、`ctx.handlers = hr` とし、本体を末尾でなく呼ぶ。
2. 値 `x` で戻ったら、`ctx.handlers = hr.parent` とし、`return` 節を `x` で**末尾呼び出し**する(省略なら `x` を返す)。
3. 自分宛ての `DISCARD(Value v)` なら、連鎖から外して `v` を返す。
   `return` も `cancel` も走らせない。
4. 自分宛ての `DISCARD(NeverBody)` なら、連鎖から外し、N の節の本体を**末尾呼び出し**する(retry.kel が一定の領域で走る。§5.7)。
5. 自分宛ての `YIELD` なら、`K` を作り、連鎖から外し、G の節を `(束縛, K)` で末尾でなく呼ぶ。
6. 自分宛てでない `DISCARD` と `ERROR` なら、連鎖から外し、**防壁**の中で `cancel` を走らせ、同じ状態語で戻る。
7. 自分宛てでない `YIELD` なら、自分のフレームも継続に含めて戻る。

**防壁**: 保留中の `P` を退避して消し、`cancel` を呼ぶ。
戻ったときの扱いは次のとおりである。
- `DISCARD` か `ERROR` が立っていれば、打ち切る。
  標準出力を flush し、標準エラーに「cancel 節で例外が抑制されました: …」を記録して、状態を消す。
  標準出力がすでに失敗の印を持つときは、flush は何もしない(本計画 6.5 節の出力)。
- `YIELD` が立っていれば、`P` を生きている値に含めたまま自分のフレームも継続に含めて戻る。
  再開されたら同じ処理を続ける。

最後に `P` を戻して伝播を続ける。

**`perform`**
1. 連鎖から、エフェクトが一致する最も内側の `hr` を探す。
2. `saved = ctx.handlers`、`ctx.handlers = hr.parent` とする。
3. 節を上から試す(パターンを照合し、合えばガードを評価する。深さは `p+1`)。
4. 選んだ節の分類で分ける。
   - T: 本体を末尾でなく呼ぶ。
     末尾 resume の `resume(v)` は「`v` を返す」に、`resume` しない値 `v` は「`DISCARD(hr, Value v)` を立てて戻る」に下ろしてある。
     戻ったら、どちらの場合も `ctx.handlers = saved` にする。
   - N: `ctx.handlers = saved` にし、`DISCARD(hr, NeverBody)` を立てて戻る(ガードは先に評価してある。Q4)。
   - G: `ctx.handlers = saved` にし、切り取りの先頭として `saved` と `Δ = p − h` を記録して、`YIELD` を立てて戻る。

**`rt_resume(K, v)`**: 節の中の末尾でない `resume(v)` は、`v` を評価してから `rt_resume` を末尾でなく呼ぶ。
G の節の中の末尾の `resume(v)` も、`v` を評価してから、末尾再開の印(後述)を通って `rt_resume` に届く。
- `rt_resume` は最初に `K.used` を調べ、立っていれば実行時エラーにする。
  立っていなければ `used` を立てる。
  検査が両方の経路で同じ場所にあるので、`resume(resume(x))` や `resume({ let x = resume(1); ... })` の外側の末尾の `resume` も、2 回目の再開として実行時エラーになる(§13.5、D514)。
- 写し戻す前に、再開した `perform` の深さ `c+Δ` を `L` と比べ、超えれば `depth_limit` にする(本計画 4.10 節)。
- 写し戻す前に `K.hr.parent = ctx.handlers`、`ctx.handlers = 切り取りの先頭` とする。
- ネイティブでは、区間を値スタックに写し戻し、各フレームの深さと、`K` の中で始まった各 `HR`(切り取りの中のものと、`K` のフレームから届くもの)の `h` を `c − h` だけずらし(`K.hr.h` は `c` になる)、最下段に「ネイティブの呼び出し元へ戻る」印を置いて `interp_continue(ctx)` を呼ぶ。
  インタプリタは最上段のフレームの再開点から続け、印に達したら戻る。
  こうして、取り出したフレームはインタプリタで最後まで走る(脱最適化)。
  新しい呼び出しは入口の表を通って JIT に戻る。
  `--tier jit-only` でもこの経路を通る(P251)。
- Wasm では、構造体の列の内側から順に、再開の入口で各関数を呼ぶ。
- 写し戻した計算は `rt_handle` の手順 2〜7 で終わる。
  再開した計算の中の `return` 節の値や、`resume` しない節の値は、ハンドラ式の値ではなく、この `resume` の値になる(§13.6)。
- 再開の途中で `YIELD` が立ったら、まだ走らせていないフレームを継続の後ろに足して戻る。
  `DISCARD` か `ERROR` が立ったら、残りのフレームにも状態を注入して順に巻き戻し、その中の `cancel` を走らせる。
- G の節の中の末尾の `resume(v)` は、「`K` を `v` で末尾再開せよ」という印を立てて戻る。
  呼んだ側の `rt_handle` または `rt_resume` は、自分を `rt_resume(K, v)` の末尾呼び出しで置き換える(一定の領域。fx R6)。
- 節が値 `r` で戻ったときは次のとおりである。
  - `K` を使っていれば、`r` がハンドラ式の値になる。
  - 使っていなければ、`DISCARD(hr, Value r)` を注入した `rt_resume` を末尾呼び出しする。
    `K` の中の `cancel` が内側から走り、付け直した `hr` の手順 3 が `r` を返す(§13.6 の「値が決まった後で破棄」)。
- 節が `resume` の前に脱出したら、同じ状態を注入した `rt_resume` を末尾呼び出しする。
  順序は `K` の中の `cancel`、`hr` の `cancel`(手順 6)、外側である(fx R3 の resumeinnerpre、fid §6 の preresume.kel)。
- 節が `resume` の後に脱出したら、`hr` はもう連鎖にいないので、そのまま伝播する。

**難しい場合の照合**

次の試験の結果は、どれも既存の cram が固定している。
ただし retry と retrycancel* のある tail_calls.t のブロックは、どれも `OCAMLRUNPARAM` を使うので kconform では除外し(V213)、`conformance/depth/` に作り直した試験で確かめる(本計画 8.1 節)。
表の動きは規約から推論したもので、まだ実行していない。【推論・要検証 M89】

| 試験 | この規約での動き |
|---|---|
| cancelperform | 実行時エラーの伝播中の `cancel` が N を起こし、その `DISCARD` を防壁が打ち切る。元の `ERROR` が続いて 3 で終わる |
| cancelnormal / cancelsame | 2 つ目の `DISCARD` を防壁が打ち切り、1 つ目の伝播が続く |
| cancelresume / via / two | 防壁の中の `cancel` が、まだ連鎖にいる `H` の G を起こす。防壁のフレームは `P` を持ったまま取り出される。`resume(5)` で再開すると `cancel` の続きが走り、`P` が付け直した `H` の `rt_resume` に届く。throw の節の値 7 が `resume(5)` の値になる |
| resumeinner* / clauseerr / clausestop | 付け直した `hr` を通るかどうかで、`cancel` が 1 回走るか走らないかが決まる |
| retry / retrycancel* | N の本体と `handle` が末尾呼び出しなので、一定の領域で走る |
| resume_guard.t の V191 のブロック(M80 で足す) | 外側の `resume` が末尾で内側が末尾でないので、節は G である。内側の `resume` が `used` を立てる。外側の末尾の `resume` は末尾再開の印を通り、置き換えた `rt_resume` の最初の検査で実行時エラーになる。`resume({ let x = resume(1); x / 0 })` では、継続が `cont saw 1` を出した後、引数の評価がゼロ除算で止まって 3 で終わる |

**採らなかった案**
- ネイティブのファイバー(tg、native): 往復は 1.8 ns と安い(E20)。
  しかし WasmGC では使えず、`cancel` の順序の実装と継続の形が 2 系統になる。
  G のハンドラの中の深い再帰の限度も後段で変わる。
  M93 の測定で必要と分かったときだけ、LLVM の後段の最適化として検討する(P240、V204)。
- exnref、landingpad: 機構が 3 つになり、cancelresume には例外の途中の状態をフレームに写す別の規約が要る(V205)。
- JSPI(native D541): 非同期で、最も近い `promising` の境目までしか止まらない。
  スタックの既定値は 984 KB で、伸びるスタックは既定で無効なので、深さの計数が守れない(E9)。
- WasmFX: フラグが要り、落ちる(E9。V211)。
- 選択的 CPS: 行多相の高階関数がほぼすべて CPS 側に入る(fx §6.1)。

### 6.7 バイトコードとインタプリタ(D535)

- バイトコードは LIR の関数を 1 対 1 に符号化したもので、関数を最初に呼ぶときに作る。
  ファイルには書かない。
- レジスタ機械で、命令は 32 ビットの語の列である(命令番号 8 ビットと被演算子)。
  スロットが 256 を超える関数には wide 形を使う。
- フレームは分割値スタックに置き、JIT と同じ形にする。
  インタプリタの中の呼び出しはネイティブのスタックを使わない。
- 末尾呼び出しはフレームを再利用する。
  再開点の番号から命令の位置への表を持つので、JIT が作ったフレームもインタプリタが続けられる。
- 振り分けは Rust の `match` の平坦なループで行う(E7)。
  レコードの選択と更新は、呼び出しの位置ごとのインラインキャッシュで速くする。

### 6.8 LLVM ORCv2(D536、D537、D538)

- `keleut-llvm::sys` は llvm-sys の薄い包みである。
  文脈は `LLVMContextCreate` で作り、`LLVMOrcCreateNewThreadSafeContextFromLLVMContext` で包む(LLVM 21 以降は `GetContext` が無い。sl)。
  モジュール 1 つに文脈 1 つを使い、IRBuilder の C API で組む。
  段を上げた関数には `default<O2>` をかける(E1)。
  実行時の関数は `LLVMOrcAbsoluteSymbols` で登録する。
- 呼び出し規約は `tailcc i64 @f(ptr %ctx)` の 1 つの型にする。
  E2〜E4 で測ったのは、この形に近い変種である。
  E2 は `tailcc` と `ccc` の `musttail` による相互の末尾呼び出しで、引数を i64 で明示に渡した。
  E3 は呼び出し規約が違うときの拒否と、引数の数が違うときの規則を確かめた。
  E4 の交互の試験(`doc/log/261024-1-spike/probe/tg/tier.ll`)は `tailcc i64 @f(ptr %ctx, i64 %n, i64 %acc)` で、スタブ `@stub_g` も `tailcc i64` である。
  2 語の構造体(値と末尾呼び出しの先)を返したのは、インタプリタの代役 `interp_run`(ccc、C。`doc/log/261024-1-spike/probe/tg/interp.c`)である(tg §3.3 の注意)。
  E5 は Rust の表を介した ccc の間接の `musttail` である。
  引数を値スタックに置き、`ctx->callee` を使い、`interp_run` が 1 語だけを返して末尾呼び出しの求めを `ctx` に置くこの形と、最下段の規則(本計画 6.9 節)は、まだ測っていない。【推論・要検証 M91、M92】
  M92 の受け入れの、`--native-stack 512k` で 1e8 回の交互の末尾呼び出しを完走させる試験が、本番の型でこれを確かめる。
  - 呼ぶ側は、引数を値スタックの次のフレームの位置に書き、`ctx->callee = fid` を書き、`ctx->entry[fid]` を間接に呼ぶ。
    末尾なら `musttail` にする。
  - 戻り値は一様な語か `0x2` である。
  - 全関数が同じ型なので、間接呼び出しを含むすべての末尾呼び出しを `musttail` にできる。
- スタブ: Rust は `tailcc` の関数を書けない(E7)。
  そのため、起動時に小さな LLVM のモジュールとして次の 2 つを作る。
  - `interp_stub`(tailcc): `ctx->callee` を読んで Rust の `interp_run(ctx)`(ccc)を呼ぶ。
    戻りが「末尾呼び出しの依頼」なら、`entry[依頼先]` を `musttail` する。
  - `enter_tailcc`(ccc): Rust から tailcc の関数を呼ぶ入口。

  `tailcc` から `ccc` への `musttail` は拒まれる(E3)ので、末尾の境目はすべて tailcc のスタブを通す。
- フレーム: JIT の関数は、末尾でない呼び出しの前に、生きている値を**すべて**スロットに書き、再開点の番号を見出しに書く(D538)。
  戻った後は、インタプリタと同じ形の値スタックのフレームが残る。
  費用(スロットへの書き込み、呼び出しごとの番兵の比較と深さの書き戻し、境目での Int64 と Float64 の箱)は v1 で受け入れ、M91 と M93 で測る(V214)。
  レジスタで引数を渡す案(native D535)は、M93 で交互の末尾呼び出しを測り直したうえで採る。
  通らなければ今の形に留める(V206)。
- shadow stack: 共有の値スタックが shadow stack の役を果たす。
  LLVM の `gc "shadow-stack"` の戦略は JIT でも動くと測った(【実測】sl の gc)。
  しかし使わない。
  インタプリタのフレームと継続の区間に、2 つ目の根の仕組みが要るからである。
- JIT には landingpad も eh_frame の登録も要らない。
  再開点の入口の `switch` も要らない(再開はインタプリタが行う。D532)。
- 予備の検査: JIT の入口と、インタプリタの入れ子の入口で、ネイティブのスタックポインタを `ctx` の下限と比べる。
  超えたら 70 で終わる(論理的な限度より先に起きるのは不具合の印。D546)。

### 6.9 段の切り替え(D539、D540)

- 関数 id ごとに、入口の表 `entry[id]` と呼び出しの回数を持つ。
  `entry` は最初 `interp_stub` を指し、翻訳が済んだら原子的に 1 回だけ書き換える(E5)。
  翻訳は別のスレッドで行ってよい。
  段がいつ上がっても結果は変わらないからである(論理的な深さは段に依らない)。
- インタプリタは関数の入口で回数を 1 増やす。
  自己の末尾呼び出しでフレームを再利用する場合も数える。
- 移り方は次のとおりである。
  - インタプリタ → JIT(末尾でない): `enter_tailcc` で `entry[id]` を呼ぶ。
  - インタプリタ → JIT(末尾):
    - 呼び出し元のフレームが、この `interp_run` の起動の**最下段**なら、「`id` へ末尾呼び出し」を返す。
      スタブが `musttail` するか、最上位の駆動ループがトランポリンになる。
    - 最下段でなければ、フレームを外してから JIT を普通に呼ぶ。
      その先で再びインタプリタに入れば最下段になるので、交互の末尾呼び出しでもネイティブのスタックは 1 段しか伸びない(native 4.8)。【推論・要検証 M92】
  - JIT → どちらでも: `entry[id]` を `musttail` するか、普通に呼ぶ。
- OSR と逆最適化(投機の取り消し)は作らない。
  JIT は投機をせず、熱い反復は必ず関数の入口を通る(tg §3.6)。
- 試験の段の設定は次のとおりである。
  - `interp-only`。
  - `jit-only`: 対象の関数をすべて事前に翻訳する。
  - `threshold=N`。
  - `alternating=SEED`: 呼び出しごとに、種から決まる擬似乱数で段を選ぶ。
    全関数を事前に翻訳しておく。
  - `mixed=SEED`: 種で決まる半分の関数だけを翻訳する。

  組み合わせの試験には、取り出しと再開が必ず段をまたぐ形を `conformance/effects/` に置く。

### 6.10 WasmGC(D541〜D545)

**値**

| Keleut | WasmGC |
|---|---|
| 一様な値 | `eqref` |
| Int32 | 局所では `i32`。一様な位置では、31 ビットに収まれば `i31ref`、収まらなければ `(struct i32)` |
| Boolean、Unit、引数の無いコンストラクタ | `i31ref` |
| Int64、Float64 | 局所では `i64`、`f64`。一様な位置では `(struct i64)`、`(struct f64)` |
| String | `(array (mut i8))`(JS の文字列には写さない) |
| レコード、データ | `(struct i32 (ref $AnyArr))`(形の id か、コンストラクタの番号) |
| ヴァリアント | `(struct i32 eqref)` |
| クロージャ | `(struct i32 (ref $FnN) (ref $AnyArr))`。引数の数ごとの部分型 |
| `Ref`、配列 | `(struct (mut eqref))`、`(array (mut eqref))` |
| フレームの記録 | `(struct i32 i32 (ref $AnyArr) (ref $I64Arr))`(関数、再開点、`any` の値、生の値) |

**制御**: 関数の型は `(func (param (ref null $Clo)) (param eqref)×N (param (ref null $Frame)) (result eqref))` で、最後の引数が null でなければ再開である。
- 非巡回の LIR を位相順に並べ、ブロックごとの入れ子の `block` と前向きの `br` で出す。
- 再開の入口は、関数の先頭の `br_table` で再開点のブロックへ前向きに飛ぶ。
  局所はフレームの記録から戻す。
  relooper もループも要らない。
  この配置と、Wasm の `rt_resume` が構造体の列を順に再開する手順は、まだ試作していない。【推論・要検証 M95】
  ブロックの入れ子が深くなる関数を V8 が受け付けるかも同じである。【推論・要検証 M94】
- 末尾呼び出しは `return_call` と `return_call_ref` で行う(【実測】E8)。
  状態語は大域 `$pending` に置く。
  exnref は使わない。

**trap しないこと**(D543): trap しうる命令は、モジュールの中の許可した補助関数だけに置く。
- 許可した命令は `i32/i64.div_s|rem_s|div_u|rem_u`、`i32/i64.trunc_f64_s|trunc_f64_u`、`array.get/set` の添字、`array.new` と `array.new_default`(長さ)、`array.copy`、`array.fill`、`array.init_data|init_elem`(範囲)である。
  `array.new_fixed` は trap しないので含めない。
  補助関数は先に検査し、失敗なら `ERROR` を立てる。
  `array.new` と `array.new_default` の補助関数は、負の長さに加えて、`N_alloc_max` を超える長さも `ERROR(OutOfMemory)` にする(本計画 6.5 節のメモリの不足)。
- `ref.cast`、`ref.as_non_null`、`unreachable` と、null を取りうる参照(`$Clo`、`$Frame` など)への `struct.get|set`、`array.len`、`call_ref` は、型の健全性の上では失敗しないので、残してよい。
  それが trap したら不具合の印で、70 で終わる。
- `keleut-wasm` の試験の検査器は、wasmparser で全関数の命令を走査する。
  そのうえで、許可した補助関数の外に上の命令が無いことを確かめる。

**フレームの大きさ**(D544): 局所は生存区間で色分けして使い回す。
推定したフレームの大きさ(局所の数 × 8 + 定数)が予算 `B_wasm` を超える関数は、超えた局所を入口で確保する GC の構造体に置く(大きなフレームの形)。
`B_wasm` の初期値は 2 KiB で、M79 の測定で決める(V198)。【推論・要検証 M79】
M79 では、bigframe.mjs が局所の数ごとに測った 1 段のバイト数の表から、局所をすべて Wasm の局所に置いたままにする関数(大きなフレームの形にしない関数)の 1 段のバイト数の最大値を `B_wasm` とする。
そのうえで、`S = (L+R) × B_wasm + 64 MiB`(下の Node の起動)の 90% が、測った `--stack-size` の上限を超えないことを確かめる。
超えるなら、`B_wasm` を下げるか、Worker の経路(D545)を使う。
決めた値と測定の表は M79 の記録に書く(V198)。
フレームの大きさの推定の定数(局所の数 × 8 に足す値)も、M79 の bigframe.mjs の測定から決め、M94 の深さの試験で確かめる。【推論・要検証 M94】

**Node の起動**(D545): `keleut run --backend wasm` は `program.wasm`、`rt.wasm`、`main.mjs` を一時の場所に書き、`node` を子プロセスで起動する。
- `pre_exec` の中で `setrlimit(RLIMIT_STACK, S)` を呼ぶ。
  `S = (L+R) × B_wasm + 64 MiB` である。
  `--stack-size` には `S` の 90%(KB)を渡す。
  軟らかい限度は硬い限度までしか上げられないので、先に `getrlimit` で硬い限度を調べる。
  足りなければ Worker の経路を使う。
  起動の前に、`keleut` 自身の標準出力を flush する。
- 【実測】E12 は、`ulimit -s 2000000` と `--stack-size=1500000` で 1e7 段を測った。
  L と `B_wasm` から決まる `S` を V8 の `--stack-size` が受け付けるか(上限)は、まだ確かめていない。【推論・要検証 M79】
- `--stack-size` に上限があってこの方法が使えないときは、`Worker` の `resourceLimits.stackSizeMb` で走らせる(E12 で 1024 MB を確かめた。P248)。
- `stdio` は `'inherit'` にし、子のバイト列と終了状態をそのまま返す。
  子がシグナルで終わったら 70 にする。
- `main.mjs` は `process.versions.node` を確かめ、Node は 26.9.0 以上を求める(E8 の機能は Node 26.9.0、V8 14.6.202.34 で確かめた)。
- 最上位で `RangeError` か `WebAssembly.RuntimeError` を受けたら、標準出力を書き終えてから 70 で終わる(不具合の印)。
  補助関数が検査する trap(長さが負か `N_alloc_max` を超える確保を含む)は先に `ERROR` になるので、ここに届くのは補助関数の外の trap か、検査の漏れだけである。
  V8 のヒープが尽きてプロセスが落ちた場合は、シグナルの終わりとして 70 になる。
  これは §15.5 からの既知の逸脱である(本計画 6.5 節。V215、P252)。

**入出力と rtcore**: 出力は、i8 の配列を `rt.wasm` の線形メモリの 64 KiB のバッファに写し、`host.write(ptr, len)` を呼ぶ形にする(sw §4 の方法 B)。
- JS は `fs.writeSync(1, new Uint8Array(mem.buffer, ptr, len))` を、短い書き込みと `EAGAIN` に対して繰り返す。
  `EAGAIN` は `Atomics.wait` で 1 ms 待ってから再試行する。
  失敗は `ERROR(Io)` で、74 になる。
- `show(Float64)`、libm、形の表、バイト列の比較は、`rt.wasm` の export を import して使う。
  JS の数値の整形と `Math.sin` は使わない(E13)。

### 6.11 物理的なスタック(D546)

- ネイティブ: ミューテータは専用のスレッドで走らせる。
  スタックは `S_native = (L+R) × B_native + 64 MiB` を予約する。
  `B_native` は、1 段あたりの最大のバイト数である。
  内訳は、JIT のフレーム、スタブ、非末尾で段を交互にまたぐときの `interp_run` のフレームである。
  初期値の 1 KiB は推論で、M91 で測って決める(V201)。【推論・要検証 M91】
  1 GiB 級のスタックを WSL2 で予約できるかは M87 で確かめる。【推論・要検証 M87】
  インタプリタ同士の呼び出しはネイティブのスタックを使わない。
- `--native-stack BYTES` で変えられる。
  tg の `ulimit -s 512` の試験は、専用のスレッドでは効かないので、`--native-stack 512k` で行う。
- 予備の検査(本計画 6.8 節)が論理的な限度より先に起きたら、70 と kconform の失敗にする。
- フロントエンドと KIR の道具: 字句、構文解析、精緻化と、KIR の読み込み、検証、LIR への下ろしも、専用のスレッドで走らせる。
  スタックの大きさは `--native-stack` で変えられる。
  再帰する各パスは入れ子の計数器を持ち、限度を超えたら §15.5 の診断を出して終わる。
  構文解析は 2(診断は「処理系の限度: 構文解析で再帰が深すぎます」で始まる)、型検査は 1(同じく「処理系の限度: 型検査で再帰が深すぎます」)、KIR の読み込みと検証は 65 である。
  プロセスをスタックあふれで落とさない。
  既定の限度は、run_exit.t の `l=8M` のブロック(20,000 段の `1 + (...)` の式が型検査を通り、0 で終わる)が通る値にする。
  run_exit.t:163-219 のこれらのブロックは `OCAMLRUNPARAM` を使うので kconform では除外し(V213)、同じ意図の試験を `conformance/frontend-depth/` に作り直す(本計画 8.1 節)。

## 7. Rust のフロントエンド(D547、D548)

- **時期**: 独立した系統として、kir crate(M84)の直後から M96〜M99 で移す。
  M96〜M98 は LLVM と WasmGC の完了を待たない。
  M99 は、受け入れに kr-kj、kr-ka、kr-kw を含むので、M92 と M95 の後に置く。
  所有者の動機はコンパイルの速さなので、この系統を後段の最も難しい部分の後ろに置かない(審査 3)。
- **順序**(fp §2): 字句と ASI → 構文と脱糖 → 宣言表、単一化、型の表示 → elab(型式、パターン、式、let、let rec、宣言、module、import) → 網羅性 → ドライバの終了状態 → KIR の書き出し。
- **構文解析**: 手書きの再帰下降にする。
  文法は LALR(1) で衝突が無く、優先順位は非終端の階層で表してある(fp §3.1)。
  M96 の受け入れ(本計画 9 節)の各 .t が、見積もりの上限 4,000 行を書き終えても差 0 にならなければ、M97 に入る前に `.mly` を lalrpop 0.23.2 に写して受理の基準に切り替え、その判断を実施記録に書く。
- **型**: arena と添字の Union-Find にする。
  ノードの注釈は `NodeId` で引く別表に置き、大域の状態 81 か所は 1 つの文脈の構造体に集める(fp §1.3)。
  REPL の取り消しは snapshot で行う。
- **検証**(価値の高い順。fp §4.2):
  1. 終了状態(cram の全入力)。
  2. `keleut dump tokens|ast` と `diktor --dump-tokens|--dump-ast` の一致。
  3. `check` の型の行(933 行)の一致。
  4. 正準化した KIR のテキストのバイト単位の一致。
     記号名が安定しているので、正規化は要らない。
  5. 診断の種別、位置(コードポイントで数える)、警告の件数。
     日本語の文面は Diktor のものを写すが、比較では正規化する(§18 の外。P245)。
- **速さの関門**(D548): M98 で次の 3 つを `hyperfine` か 10 回の中央値で測り、実施記録に書く。
  - `keleut check` と `diktor --type-check` を、`test/sample/stubs.kel test/sample/sample.kel` で比べる。
  - コーパスの 1,046 本の合計で比べる。
  - sample.kel を module で 100 回複製した合成の大きな入力で比べる。

  関門の条件は、3 つとも `keleut check` が `diktor --type-check` 以下の時間であることである(P250)。
  M98 は、3 つの入力の表を記録し、cram の型の行と終了状態が差 0 なら終える(関門の成否に依らない)。
  関門の条件を求めるのは、M99 の中の `--frontend rust` を既定にする段だけである。
  1 つでも 1.0 倍を超えたら、原因を測って直し、そのたびに表を記録する。
  この測って直す回を 3 回行っても通らないか、M101 に着いても通らないときは、打ち切る。
  打ち切ったら、その時点の表と原因を実施記録に書き、不足を台帳の新しい項目に載せ、所有者への新しい問いを立てる。
  そのうえで M99〜M101 はそのまま進め、`--frontend rust` は明示の旗として使い、既定は `diktor` のままにする。
  M99 では、参考として `keleut emit-kir` の時間と、KIR から LIR への下ろしの時間も同じ表に記録する(関門の条件にはしない)。

## 8. 試験(D549)

### 8.1 kconform

- kconform のコマンド行は次のとおりである。
  受け入れの欄の `kconform …` はこの形で書く(本計画 9 節)。

  | 形 | 働き |
  |---|---|
  | `kconform [--pairs P,…] [--suite S] [--extra=FLAG…] [FILES…]` | 既定の働き。組み合わせごとに走らせ、組の間で比べ、各組を `.t` に記録した期待とも比べる。`FILES` を与えたときは、`--suite` の代わりにその `.t` と `.kel` を流す |
  | `kconform expect FILES…` | `conformance/` の `.t` を、組の間で比べずに走らせ、`.t` に記録した期待とだけ比べる。`keleut run` の起動には `ki` の選択肢を足す。組がまだ無い M84〜M87 と、Diktor が基準にならない試験(`frontend-depth/`)に使う |
  | `kconform kir-roundtrip` | コーパスの全件で、KIR のテキスト → バイナリ → テキストの往復と、2 つのプロセスの書き出しの `cmp` を確かめる |
  | `kconform extract-corpus` | cram のヒアドキュメントから `.kel` を抜き出し、`conformance/corpus/` に置く |

  | 選択肢と組 | 意味 |
  |---|---|
  | `--pairs` | 本計画 8.2 節の組の名前を並べる。省いたときは、そのマイルストーンで使える全組である |
  | `--suite all` | `diktor/test/*.t` の全ブロック、コーパスの全件、`conformance/` のうち `depth/` と `frontend-depth/` を除く全部 |
  | `--suite depth` | `conformance/depth/` だけ |
  | `--extra=FLAG` | RustKeleut の側のすべての起動に `FLAG` を足す(`--gc-stress`、`--no-yield-prune` など) |

- kconform は cram の `.t` を自分で読む(`  $ ` のコマンド、`  > ` の続きの行、期待の出力、`[N]`)。
  各ファイルを一時のディレクトリで実行し、PATH の先頭に `diktor` の shim を置く。
  dune の cram は差をファイル単位でしか報せないので、コマンド単位の比較と既知の差の照合のために自前で読む。
- `conformance/` の試験(init、prim、bytes、effects、float、depth、frontend-depth、oom)は、どれも cram の形の `.t` で書く。
  `.kel` は `.t` の横か、`.t` のヒアドキュメントに置く。
  コマンドは shim を通さずに `keleut` を直に呼び、リダイレクトとパイプ(`>&-`、`| (sleep 1; cat)` など)もコマンドの中に書く。
  期待には標準出力と `[N]` を書き、標準エラーは本節の最後の正規化した形(種別の語と、標準出力との前後関係)で書く。
  kconform は PATH の先頭に `keleut` を置いて走らせ、記録した期待と比べる。
  組で比べるときは、`.t` の中の `keleut` の各起動に組の選択肢(本計画 8.2 節)を足し、組の間でも比べる。
  組 `dk` と `dk-ir` では、`keleut run` の起動を Diktor の対応する起動(`dk-ir` では `diktor --emit-ir` の後の `diktor --run-ir`)に置き換える。
  `kconform expect` は組の間で比べず、`keleut run` に `ki` の選択肢だけを足して、期待とだけ比べる。
- shim の振り分けは次のとおりである。

  | 呼び出し | 最初 | 切り替えた後(切り替えるマイルストーン) |
  |---|---|---|
  | 実行(旗なし、`--prelude`、`--no-prelude`、`--import-path`) | M84〜M87 は本物の diktor。M88 から、本物の `diktor --emit-ir` が 0 なら `keleut run FILE.kir`、0 でなければその出力と終了状態をそのまま返す | `keleut compat-diktor`(M99) |
  | `--type-check`、`--strict-exhaustive` | 本物の diktor | `keleut check`(M97 から部分ごと、M98 で全部) |
  | `--dump-tokens`、`--dump-ast` | 本物の diktor | `keleut dump`(M96) |
  | `--repl` | 本物の diktor | `keleut repl`(M100) |
  | `--emit-ir`、`--emit-ir-text`、`--run-ir`、`--via-ir`、`--max-depth`、`--dump-ir-tables` のどれかを含む呼び出しと、環境変数 `DIKTOR_VIA_IR` を立てた呼び出し | 本物の diktor | 切り替えない(M99 の後も本物の diktor) |

  2 つ以上の行に当たる呼び出しは、最後の行(Diktor の IR の旗)を先に当てる。
  これらの呼び出しは Diktor 自身の IR の経路を試すもので、shim が自分で行う `diktor --emit-ir` もここに入る。
  `keleut compat-diktor` はこれらの旗を解釈しない。

- kconform は、いま走らせている組の `keleut run` の選択肢(本計画 8.2 節。ka と km の種、すべての `--extra` の旗を含む)を、環境変数 `KCONFORM_PAIR_ARGS` で shim に渡す。
  組 `dk` では、shim はすべての呼び出しを本物の diktor にそのまま渡す。
  組 `dk-ir` では、実行の呼び出しを `diktor --emit-ir` の後の `diktor --run-ir` にする。
  そのほかの組では、`keleut run FILE.kir` に(M99 からは `keleut compat-diktor` に)その選択肢を足す。
- 既定の働きでは、各組のコマンドごとの結果(標準出力のバイト列、`[N]`、正規化した標準エラー)を、既知の差を当てた後で、`.t` に記録した期待とも比べる。
  そのため、M84 の `--pairs dk` のように組が 1 つの実行も、記録との比較として意味を持つ。

- `OCAMLRUNPARAM=l=…` を使うブロックは語数を写さない。
  理由「限度は I(§15.5)」で `known-diffs.toml` に登録して除外する(V213)。
  同じ意図の試験は `conformance/depth/` に `--max-depth` で作り直す。
  例えば `--max-depth 10000` の下で、末尾呼び出し、末尾 resume、N の再試行は 100,000 回完走し、非末尾の再帰と非末尾の resume は 3 で終わる。
- run_exit.t:163-219 の、フロントエンドの限度を固定するブロック(型検査の限度で 1、構文解析の限度で 2、REPL がその後の入力を続けること、`l=8M` で 20,000 段の式が 0 で終わること)も V213 で除外する。
  同じ意図の試験は `conformance/frontend-depth/` に作り直す(本計画 6.11 節)。
  中身は次の 3 本に分け、それぞれを受け入れるマイルストーンを決める。
  - `parse.t`(M96): 限度を超える文の数のブロック(2)。
    `keleut dump ast` で、Rust の構文解析だけを走らせる。
  - `typecheck.t`(M98): `keleut check` で走らせる、限度を超える深い式(1 で終わり、標準出力にはそれまでの型の行に続けて限度の診断を出す。Diktor の `--type-check` と同じ)と、20,000 段の成功の例(0 で終わり、型の行を出す)。
  - `repl.t`(M100): 構文解析の限度と型検査の限度のそれぞれについて、REPL がその後の入力を続けること。
    `keleut repl` は M100 で入るので、それより前には受け入れに使わない。

  `frontend-depth/` は `--suite all` に入れず、各ファイルを受け入れるマイルストーン(M96、M98、M100)から `kconform expect` でだけ走らせる。
  M101 では `kconform expect conformance/frontend-depth/*.t` で 3 本をまとめて確かめる。

  `kir-bad/` には、入れ子の深い KIR(65 で終わる)を置く。
- `known-diffs.toml` の各項目には、ファイル、コマンドの行、組み合わせ、理由、台帳の番号を書く。
  登録の無い差が 1 件でもあれば失敗にする。
- 比べるのは、標準出力のバイト列と終了状態(§18)である。
  標準エラーは、種別の語の後ろを切り、警告は件数だけを残して、標準出力との前後関係を比べる(fp §4.2 (c))。

| 名前 | 書き手 | 実行 |
|---|---|---|
| `dk` | Diktor | 木の評価器(基準) |
| `dk-ir` | Diktor | `diktor --run-ir` |
| `ki` | Diktor | `keleut --backend interp --tier interp-only` |
| `kj` | Diktor | `--backend jit --tier jit-only` |

- 深さの試験(`conformance/depth/`)は `dk-ir` と RustKeleut の全組で比べる。
  `dk` とは比べない。
  限度に触れない試験は既定の L で走らせる。
  予備の検査(70)が出たら失敗にする。
  深い非末尾の再帰(L − 10 段)を、既定の L で `ki kj ka kw` が 0 で終えることも求める。
  深さの試験を回すのは、M89(`dk-ir ki`)、M92(`kj kt ka km` と、L − 10 段の `ki kj ka`)、M94(L − 10 段の `kw`)、M95(`kw`)、M101(`kr-*` を含む全組)である。

### 8.3 そのほか

- float show: 2,000,000 個の乱数ビット列から作る fltcmp の比較対象(1,998,964 件。522 件の 2 の冪の付近と、ちょうど中間の値を含む)と、`-0.0`、NaN、±`1e16` と ±`1e17` の境目、非正規化数、k ≤ -1022 のすべての 2^k、最大の非正規化数を、rtcore の x86_64 版と wasm32 版(Node で実行)で glibc と比べ、差 0 件を求める。
  NaN だけは glibc と比べない。
  符号の立った NaN と積載の違う NaN を含め、§16.2 と Diktor の求める `nan` と比べる(本計画 6.5 節)。
  - 入力は、keleut-rtcore の試験が `doc/log/261024-1-spike/probe/fltcmp/src/main.rs` の候補の生成をそのまま移して作る(同じ xorshift と種、同じ 2 の冪と境界の値、同じ除外)。
    生成した件数が 1,998,964 でなければ、試験を失敗にする。
    `cases.txt` は候補の先頭 400,000 件の表なので、これには頼らない。
  - glibc の基準は、試験のプロセスの中で `snprintf("%.*g")` を呼んで作る(fltcmp と同じ探索)。
  - wasm32 版の確認では、x86_64 の試験が入力と glibc の結果を `target/` の下のファイルに書き、`crates/keleut-rtcore/tests/wasm_check.mjs` がそれを読む。
- libm: 1,000,000 件の乱数と特殊値で、x86_64 版と wasm32 版のビット一致を求める(V200)。
- KIR: コーパスの全件で `keleut kir dis` と `diktor --emit-ir-text` が一致し、テキスト → バイナリ → テキストの往復が一致すること。
  同じ入力を 2 つのプロセスで書き出したバイト列が `cmp` で一致すること。
  `kir-bad/`(ビット反転、切り詰め、範囲外、背骨の外の `resume tail`)が 65 で、落ちずに拒否されること。
- Wasm: 全出力が wasmparser の既定の機能集合(GC、tail_call、exceptions。stack_switching は無し)で検証に通ること。
  trap の検査器に通ること。
- 出力: `conformance/bytes/` に、不正な UTF-8、NUL、1 MiB を超える文字列、非ブロッキングのパイプ(`| (sleep 1; cat)`)、閉じた標準出力(74)の試験を置く。

## 14. 進め方の原則

- 実施は本計画 9 節の依存の順で行う。
  Diktor の系統、後段の系統、フロントエンドの系統は並行してよい。
- 各マイルストーンの後に、観点ごとの検証者と、指摘ごとの反証者を置く。
  検証者には一時領域に写したバイナリだけを使わせ、リポジトリの編集と git の書き込みを禁じる。
- 次のものは、それぞれ 1 本のコミットにする。
  - Diktor の V191 の修正(M80。diktor の中)。
  - LangSpec §11.1 と §17 の文の追加(M79。P236、P237)。
  - LangSpec §13.5 の文の追加(M80。P235)。
    V191 を直した後の振る舞いを書く文なので、Diktor の修正を記録した親のコミットの後に置く。
- コミットの scope とメッセージの言語は D554 に従う。
  期待値の更新は、実装と別のコミットにする。
- 親の `diktor:` のコミットの版は `git -C diktor rev-parse --short HEAD` で埋める。
- 既存の cram の期待値は、RustKeleut のために変えない。
  変えるのは、Diktor の新しい旗(smoke.t)、V191 の回帰のブロック(resume_guard.t。M80)、新しい cram の追加だけである。
- 実施記録は、M101 で `doc/log/` に書く。
  M79 と M93 の測定の記録も `doc/log/` に置く。
