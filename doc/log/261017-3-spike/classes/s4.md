### N.6 V132：型クラスのメソッドと再開しない操作

#### (1) 判定、規模、依存、出典

判定は spec である。
言語の規則(`@` を省略したメソッドは `@ {}`、インスタンスの実装はクラス宣言の行を超えるエフェクトを起こせない)は変えない(D[V132-1])。
台帳の要約「再開しない操作で失敗するメソッドを書けない」は実測と合わない。
クラスの宣言が最外の行に失敗のエフェクトを書けば、インスタンスの実装は再開しない操作で失敗できる((2) の closed.kel と open.kel)。
自分の本体で失敗を起こせないのは、宣言の最外の `@` を省略したメソッドと、標準環境のクラスのメソッドと、宣言の行が行変数だけのメソッドである。
ただし宣言の行が行変数だけのメソッドは、引数の関数から届くエフェクトを通すことはできる(`verify/ex/cb.kel`、`verify/ex/functor.kel`)。
この制限を LangSpec §12.2 に例つきで明記し、回帰の cram を 3 ブロック足す。
処理系のコードは変えない。

規模は S である(LangSpec に 26 行(直前の空行 1 行と挿入する 25 行)、cram に 58 行。コードの変更なし)。

依存:

- V97(N.1)。組み込みのクラスのメソッドのスキーマを閉じると、`Show` のインスタンスで失敗したときの診断の「元の報告」が、HEAD の「行 ς1 は注釈で固定された行変数なので」から「ラベル Fail がありません(行は閉じています)」に変わる。
  V132 の最終稿は推測としていたが、合成で ex/show.kel、ex/eq.kel、verify/ex/addinst.kel の 3 例がこの文面になることを確かめた(実測)。

- V110(N.2)。§12.2 の段落の 1 文目「インスタンスの実装が起こせるエフェクトは…」は値束縛の初期化式にも読めるので、V110 の段落と文面を突き合わせて直した((4))。

#### (2) 現状(根拠つき)

仕様の文面:

- LangSpec §13.2 の表(1151 行)は「型クラスのメソッド | `@ {}`。各インスタンスの実装は純粋でなければならない」とする。
- 同じ節の 1155〜1156 行は「インスタンスの実装の最外の行が閉じていれば、尾部を開いてから宣言の行と一致させる。宣言の行に含まれるラベルだけを起こす実装は、閉じた行の注釈で書ける」とする。
- LangSpec §12.2 の 958 行は「各メソッドの型は、クラス宣言の署名を満たさなければならない」とだけ書く。

````markdown
インスタンスの実装が起こせるエフェクトは、クラスの宣言のメソッドの最外の行にあるものに限る（§13.2。値束縛で書いたメソッドの初期化式が起こすエフェクトは、この節の後の段落で定める）。
最外の `@` を省略したメソッドの実装は純粋でなければならないので、再開しない操作（§13.1）で失敗することもできない。
標準環境のクラス（`Eq` や `Show` など）のメソッドも最外の行が `@ {}` なので（§16 の冒頭）、そのメソッドの実装はエフェクトを起こせない。
宣言の行が `@ E` のように行変数だけのときは、実装はどの `E` でも通らなければならないので、自分の本体で `Fail` のような特定のエフェクトを起こせない。
引数の関数から届く `E` のエフェクトを通すことはできる（§12.3 の `Functor` の例）。
インスタンスごとに別のエフェクトを足す手段はない。
失敗するメソッドは、次のように宣言の行に失敗のエフェクトを書く。

```keleut
effect Fail = { throw: (String) => Never }

type class Parse[A] {
  val parse: (String) => A @ Fail
}

type instance Parse[Int32] {
  let parse(s) = if s == "0" then 0 else perform throw("not a digit: " + s)
}

let parse_or[A: Parse](s: String, d: A): A = parse(s) handle { case throw(_) => d }
```

失敗しないインスタンスは、同じ宣言の下で純粋な実装として書ける。
呼ぶ側のほかのエフェクトも通すには、`val parse[E]: (String) => A @ {Fail extends E}` のように宣言の行を行変数で開く。
最外の行が純粋なメソッドで失敗を扱うには、`Option[A]` のような値で返すか、`val mk: (A) => (() => Int32 @ Fail)` のように返り値の関数の行に失敗のエフェクトを書くか、実装の中のハンドラで捕まえる。
````

#### (3) 判断と確定

判断事項 P[X-D7-1]: D7 をどう閉じるか。

- 推奨案: D190 で前提が消えたものとして、コードを変えずに閉じる。拒否の経路のうち cram が固定していないもの(起点でない単位と `--prelude`)だけを足す。
- 代案 1: 何も足さずに閉じる(doc-only)。トップレベルの拒否は `std_names.t` の s4 と `typecheck.t` の d8 が既に固定している。ただし `add_class_decl` の第 1 の分岐(印を外した綴りで引く)は、どの cram からも通らない。
- 代案 2: 将来、標準環境のクラスの再宣言を「確認のため」に再び許す場合に備えて、型の同型判定(260829-4 の案 A、相互包摂)を入れる。仕様 §16.1 が再宣言を禁じているので、今は使い道が無い。
- 推奨の根拠: 仕様と実装が「名前で拒否」で一致しており、メソッドの型の照合は要らない。一方で import 経由の拒否は 6e0a559 で入ったが cram が無く、退行しても気付けない。

D[X-D7-1]: 組み込みと同名のクラスの宣言は、メソッドの一覧と型を見ずに名前だけで拒否する(D190 の規則のまま)。メソッドの型の照合は入れない。台帳の課題 D7 は D190 により解消とする。
