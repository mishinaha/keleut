#### (2) 現状(根拠つき)

仕様: LangSpec §12.2(958 行)は「各メソッドの型は、クラス宣言の署名を満たさなければならない」とだけ述べ、署名がメソッドの推論の文脈になるかどうかを書かない。
§11.2(916 行)は「コンストラクタを持たない型に対しては、節のない `match {}` が網羅的である」と定める。
§4.2(240〜241 行)は、接尾辞のない整数リテラルの型を文脈で決め、決まらないまま一般化するときは `Int32` とする。

実装(ソースを読んで導いた性質): `lib/elab.ml` §11.38 の `check_instance_bodies`(4488 行)は、各メソッドを `elab_binding env 0 (new_row_var 0) bnode`(4576 行)か `elab_rec_bindings`(4581 行)で期待型なしに推論し、その後で `subsume`(4514 行)が宣言の型と照らし合わせる。
`elab_binding`(3075 行)は仮引数の型を `new_var lvl`(3094 行)で作り、本体を推論したあと、`generalize` の直前に網羅性のキューを drain する(3140 行)。
そのため `n match {}` の照合対象の型は drain の時点で未定の変数のままで、`Never` と決まるのは drain の後の `subsume` である。
`elab_rec_bindings`(定義は 3304 行、仮引数は 3383 行)も同じ順序である。

HEAD での実測(例は `doc/log/261017-3-spike/V136/ex/` と `doc/log/261017-3-spike/V136/verify/ex/`、結果は `doc/log/261017-3-spike/V136/results.head.txt` と `results.compare.txt`):

- `ex/a.kel`(`type instance Describe[Never] { let describe(n) = n match {} }`)は `⚠ match が非網羅的です。例えば _ が漏れています` を出し、`--strict-exhaustive` で終了状態 1 になる。
- 同じ形の値束縛 `let describe = fn(n) => n match {}`(`ex/f.kel`)と `let rec`(`ex/g.kel`)も同じ警告になる。
- 仮引数を `n: Never` と注釈した `ex/b.kel` は警告を出さない。
- 同じ根から、宣言の型を文脈にできないことがほかにも 3 つ見える。
  `type instance Pick[Int64] { let pick(a, b) = if a > 10 then a else b }`(`ex/w.kel`)は、リテラル `10` を `Int32` に既定化してから照らし合わせるので「インスタンスメソッド pick がクラス宣言の型を満たしません(型が一致しません: Int32 と Int64)」で拒否される(`ex/l.kel` も同じ)。
  宣言の引数が閉じた構造的ヴァリアント `#Lo | #Hi` のとき、`case #Lo` だけの実装(`ex/x.kel`)は照合対象の行を `#Lo` に閉じてから照らし合わせるので「ラベル Hi がありません(行は閉じています)」の型エラーになる。
  逆に、宣言の引数が `Never` か `#Lo | #Hi` で、実装の `match` に `case _` を足した形(`verify/ex/` の r01_wild_never、r02_wild_variant、r12_tuplepat、r16_guard)は警告なしに受理される。
  仮引数を注釈した関数で同じ形を書く `verify/ex/r11_annot_never.kel` は、HEAD でも「このパターンには一致する値がありません」と「第 3 節は到達不能です(冗長)」を出し、`--strict-exhaustive` で終了状態 1 になる。
  インスタンスのメソッドだけがこの検査を逃れている。

#### (3) 判断と確定

D[V136-1]: インスタンスのメソッドを推論するとき、宣言の型の引数の型を仮引数に渡す。
渡すのは、関数束縛(`let m(x, y) = …`)と `let rec` の関数束縛の仮引数のうち、型注釈の無い変数かワイルドカードのものである。
値束縛のメソッドは、初期化式が無名関数で、その仮引数がすべて注釈の無い変数かワイルドカードのときに、`elab_check` で引数の型を渡す。
仮引数の数が宣言と違うとき、宣言の引数が閉じた `_item` 行でないときは、何も渡さず HEAD と同じ経路になる。
渡す型は、`expected_of` の結果のうち、メソッドの型パラメータと行変数(`Generic`)を、制約を持たない新しい変数(レベル 1、カインドは保つ)に写したものである。
したがって、メソッド自身の型パラメータ(`val conv[B]: (A, B) => String` の `B`)の位置には新しい変数が入り、その位置の型は本体から推論される(`verify/ex/r15_gen.kel` は両方のビルドで「スコープ付きの型が一致しません: Int32 と ς1」)。
頭の剛定数(前提つきインスタンスの束縛子)はそのまま渡す。
包摂(`subsume`)はこれまでどおり後で走るので、宣言との照らし合わせの規則は変わらない。

判断事項 P[V136-1]: 宣言の型のどこまでを推論に渡すか。

- 推奨案: 仮引数の型だけを渡す(メソッド自身の型パラメータの位置は除く)。
- 代案 1: 返り値の型も渡す(`ex/t.kel` の `let size(s) = 0` が `Int64` に決まって通る)。
- 代案 2: 渡さず、インスタンスのメソッドだけ網羅性の drain を包摂の後へ遅らせる。
- 代案 3: `Never` のようなコンストラクタを持たない型のときだけ渡す。
- 推奨の根拠: 代案 1 を試作すると、返り値の食い違いが `subsume` の言い換えを通らなくなり、`test/typecheck_m7.t` の c3 が「インスタンスメソッド f がクラス宣言の型を満たしません(型が一致しません: Boolean と Int32)」から「型が一致しません: Int32 と Boolean」に後退する(`doc/log/261017-3-spike/V136/runtest.ret.log`)。
  言い換えを保つには `elab_binding` の返り値の単一化に新しい言い換えの分岐が要り、規模に見合わない。
  代案 2 は、drain を `generalize` より前に済ませる制約(§11.14)に反するので採れない。
  代案 3 は V136 の症状だけを直し、`ex/w.kel` と `ex/x.kel` の受理の広がりも構造的ヴァリアントでの `case _` の警告(r02、r12、r16)も起こさない。
  しかし `Never` の側の `case _`(r01)は代案 3 でも警告になるので、変化を避けられるのは構造的ヴァリアントの側だけである。
  また、型の種類で渡すかどうかを分けると、インスタンスのメソッドが注釈した関数と同じ扱いになる型とならない型が生じ、仕様の文面も型の種類を列挙することになる。
  推奨案は、インスタンスのメソッドを「仮引数に宣言の型を注釈した関数」と同じ扱いにする。
  最外の行は渡さない。
  純粋性の規則を名指しする言い換え(§11.38 の `subsume`)と、V110 の初期化式の行の検査(推論の後で照らす)を保つためである。

判断事項 P[V136-2]: 渡した型と本体が食い違うときの診断の文面。

- 推奨案: 本体の中の食い違った位置に、注釈を書いた関数と同じ素の文面で出す(試作のまま)。
- 代案: `check_instance_bodies` で `elab_binding` を `try` で包み、「インスタンスメソッド m がクラス宣言の型を満たしません(…)」に言い換える。
- 推奨の根拠: 仮引数を注釈した `let describe(n: Int32) = …` と同じ文面と位置になり、位置は食い違った式を指す(`ex/s.kel` は 2:37 から 2:67 へ)。
  代案は `Type_error_at` の位置を捨てるか、言い換えの規則を 2 種類にすることになる。
  推奨案の欠点として、文面からメソッドの名前が消える。
  pr7 は「インスタンスメソッド eq がクラス宣言の型を満たしません(…)」が「型パラメータ ς1 は Eq のインスタンスではありません。…」に、`ex/z.kel` は「…(ラベル Mid がありません(行は閉じています))」(2:31)が「ラベル Mid がありません(行は閉じています)」(2:91)に、`ex/u.kel` は「…(型が一致しません: String と Int32)」(2:37)が「型が一致しません: Int32 と String」(2:73)になる。
  合成では、V106 の例 `doc/log/261017-3-spike/V106/ex/alias1.kel`(もともと拒否する形)も「インスタンスメソッド pp がクラス宣言の型を満たしません((ς1, ς1) は Show のインスタンスではありません)」(6:7)から「(_A, _A) は Show のインスタンスではありません」(6:33)に変わった(実測)。
  位置がメソッドの本体の中を指すので、どのメソッドかは位置から辿れると判断する。
  ただし alias1 の `_A` はメソッド自身の型パラメータの位置に置いた新しい変数の表示で、利用者が書いた名前 `B` とつながらない。
  台帳の候補 V[V136-1] に載せる((6))。

D[V136-2]: この変更による受理と診断の変化を、意図した変化として仕様に書き、cram で固定する。
変化は 3 種類である。
受理が広がる形: `ex/w.kel`、`ex/l.kel`(リテラルが宣言の型に決まる)と、`verify/ex/r10_rec_mutual.kel`(`let rec` の相互再帰。HEAD は Int32 と Int64 で拒否し、試作は true を出す)。

3 種類とも、仮引数に宣言の型を注釈した関数と同じ扱いである(r11 で HEAD も同じ警告を出すことを確かめた)。

#### (4) 仕様側の改訂案

LangSpec §12.2 の 958 行「各メソッドの型は、クラス宣言の署名を満たさなければならない。」の直後に、空行を挟んで次の段落を足す(§12.2 のほかの段落との並びは N.z)。

```
メソッドの仮引数のうち、型注釈のない変数と `_` の型は、クラス宣言の署名の対応する引数の型に決まる。
ただし、署名の引数の型のうちメソッド自身の型パラメータの位置は、本体から推論してから署名と照らし合わせる。
値束縛で書いたメソッドの初期化式が無名関数で、その仮引数がすべて型注釈のない変数か `_` であるときも同じである。
仮引数の数が署名と違うメソッドと、それ以外の仮引数の型は、本体から推論してから署名と照らし合わせる。
返り値の型と最外の行は、署名から決めない。
したがって、本体の数値リテラルの型（§4.2）と網羅性と冗長性の検査（§11.2）は、仮引数に署名の型を注釈した関数と同じ型に基づく。
たとえば署名の引数が `Never` のとき、`match {}` は網羅的であり、`case _` の節には一致する値がないという警告が出る。
```

`doc/sample.kel` は変えない。
sample.kel(410〜430 行)はメソッドの推論の文脈を定めておらず、この変更は sample.kel の規則を緩めない。

#### (6) リスク

- 前提つきインスタンスでは頭の剛定数が本体に直接入る。前提のクラスを本体で使う形(`ex/n2.kel`、r04、r05)と、制約を書かずに使う形(`ex/o2.kel`、pr7)を両方のビルドで測った。前者は出力が同じで、後者は pr7 と同じく文面と位置だけが変わる。前提のクラスと違うクラスを本体で使う形は測っていない。
- 組み込みのクラスのメソッドの引数の行変数は、新しい行変数に写して渡す。N.1 でスキーマを閉じた行に変えると、渡す行も閉じるので、実装の引数の矢印の行が早く決まる。合成でこの項目の例 94 回(実行と `--type-check`)を走らせ、試作と同じ結果だった(実測)。
- 受理が広がる(`ex/w.kel`、r10)。型エラーが警告に変わる(`ex/x.kel`)ので、`--strict-exhaustive` を使わない利用者には実行時エラーの可能性が残る。注釈した関数と同じ扱いなので、仕様の文面で明示する。
- 警告なしに受理されていた `case _` の実装が警告になり、`--strict-exhaustive` で拒否される(r01、r02、r12、r16、imp)。既存の利用者のコードを壊す変化である。リポジトリの cram とプレリュードには該当する形が無い(合成の runtest の差分は pr7 だけ)。
- 宣言のメソッドの型パラメータの制約は渡さない。本体が制約を要求すれば推論で付き、包摂で解かれるので、HEAD と同じ辞書の経路になる(既存の dictionary_passing.t が変わらないこと、反証者の r03 で 2 つの制約の辞書の順序が変わらないことで確かめた)。
- 診断の型の名前: メソッド自身の型パラメータの位置に置く新しい変数は、本体の制約の診断で `_A` のように表示される(alias1。合成の実測)。
  利用者が書いた `B` の名前が出ないので、どの型パラメータの話かを読み取りにくい。
