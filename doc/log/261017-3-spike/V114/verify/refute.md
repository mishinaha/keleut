## 4. 退行の探索

HEAD が受理し正しく実行する形として次を書き(`ex/r03`〜`r09`、`r16`、`e08`)、両方で同じ出力と終了状態 0 を得た。

- r03: 型の宣言とジェネリック関数の型パラメータを `Float32`、`UInt64` と名付ける。出力 `3`、`5`。
- r04: 文字列に `Int8 u8 1u8` を含め、`1i32` のレコードを使う。
- r05: クラスの型パラメータを `Int16` と名付ける。
- r06: `newtype Int16[A]` を型引数つきで使う(型適用の経路は HEAD でも受理する)。
- r07: 意味を持つ接尾辞を基数、指数、パターンの位置で使う。
- r08: エフェクトを `UInt32` と名付け、行 `@ UInt32` で使う(行の経路は HEAD でも受理する)。
- r09: ガードの中の `0x10i64` と入れ子のハンドラ。
- r16: 接尾辞の無いプログラム。
- e08: module の中の `pub type Int8` を `M.Int8` で使う。

HEAD が未実装の 4 で拒否し、試作が受理するようになる形は次である(意図した変化)。

- r01: `type Int8 = Int32` のエイリアス。試作は `42`。
- r02: module の中の `pub newtype UInt8` を module の中で素の名前で使う。試作は `7`、`8`。
- r10、r11: import した先のファイルが `Int8` を宣言して使う。HEAD は import 先 `lib/nums.kel:2:17` の未実装で 4、試作は `2` と `5`。
- r12: `type Float32 = Float64` を extern の署名に使う。
- r13: `pub type UInt16`。
- r14: `--prelude` で差し替えたプレリュードが `pub type Int16` を宣言する。HEAD は利用者側の使用で 4、試作は `42`。
- r15(REPL): `type Int8 = Int32` の後の `let z: Int8 = 5` を HEAD は未実装で拒否し、続く `z + 1` が未束縛になる。試作は `z : Int32 = 5`、`_ : Int32 = 6` と表示する。

これらは HEAD が受理していなかった入力なので退行ではない。
ただし r01 の形は、LangSpec §18.4(型式をエイリアスの使用に置き換えても受理が変わらない)を HEAD が破っていた例でもあり、P[V114-2] の根拠に足せる。

- e05: `newtype Int8[A]` を引数なしで書くと、HEAD は未実装の 4、試作は「型構成子 Int8 には型引数が必要です」の 1 である。

## 5. 仕様の文面

§4.2 と付録 A.2 の改訂文は、§15.5 の表(型検査での拒否は 1、初期化を行わない)と合う。
試作で `echoln("before")` の後に `1u8` を書いた形(sfx_late)は何も出力せずに 1 で終わり、「初期化を行わない」と一致する。
§18 の保存する性質に、接尾辞や数値型の名前を扱う規則は無く、矛盾しない。
§16.1 の再宣言の禁止は基本型と標準環境の型の名前が対象で、`Int8` は含まれないので、利用者の宣言を受理する推奨案と合う。

§4.2 の改訂文の「これらの名前は予約しておらず、宣言の無い型の名前として扱う。」は、利用者が宣言すれば型として使える(ty_int8_user、r01、r10)ことを言い切っていない。
「宣言の無い型の名前」は、宣言しても使えないとも読める。
「これらの名前は予約しておらず、利用者が型の名前として宣言できる。」のように、実測(宣言すれば使える)に合わせて書くほうが誤読が少ない。

## 6. 判断事項の推奨案

P[V114-1] の推奨(型検査で拒否、終了状態 1)に異論は無い。
根拠の「`--type-check` がそこまでに確定した型の行を残す」は HEAD の未実装(4)でも同じなので、代案 C との差にはならず、代案 A と B との差だけを支える。

P[V114-2] の推奨にも異論は無い。
根拠に、HEAD が `type Int8 = Int32` の宣言を受理しながら使用を拒否するので §18.4 の置き換えの性質が破れていることを足せる。
数値型の案内は素の名前の位置だけに付き、`Int8[Int32]` には付かない(e01)。
この差を許すなら、検証の観点にそう書いておくのがよい。

`smoke.t` と `typecheck.t` の mix の未実装の例を `cancel(e)` に替える案について。
`(1) handle { case cancel(e) => () }` は操作節を持たないので、`cancel(reason)` の未実装の検査が操作節の数の検査(「handle には少なくとも1つの操作節が必要です」、HEAD で 1)より先に走ることに依存する。
module の入れ子は平坦化の段階で落ちるので、mix の `ok : Int32` の行が出なくなり、代わりにならないことを確かめた(m3)。
操作節を 1 つ持たせた形(m2: `effect E = { op: () => Int32 }` と `case op() => resume(1) case cancel(e) => ()`)でも同じ未実装の 4 と `ok : Int32` を得たので、順序に依存しない例として選べる。
