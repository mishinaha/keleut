## 4. 退行の候補

試作が HEAD の受理を拒否に変える形を 1 種類見つけた。
利用者のクラスのインスタンスで、値束縛の初期化式が、行が Console に決まった一般化しない束縛を呼ぶ形である。

```
type class Sh[A] { val sh: (A) => String }
newtype Foo = Foo
let idf[A](x: A): A = x
let w = idf(fn(x: Int32) => x)
echoln(show(w(1)))
type instance Sh[Foo] {
  let sh: (Foo) => String = { let n = w(2); fn(x) => "foo" }
}
echoln(sh(Foo))
```

HEAD は `1` と `foo` を出して終了状態 0、試作は `7:39` で「ラベル Console がありません(行は閉じています)(この位置の行は空 = 純粋です …)」で終了状態 1 である(ex/r1_weakinit.kel)。
w は実際には何のエフェクトも起こさないが、型は `@ {Console}` に決まっているので、仕様の表(§13.2 の 1151 行)に従えば拒否が正しい。
下書きの (6) は拒否が広がる形として inicon(初期化式が Console を直接起こす形)だけを挙げており、この形を挙げていない。
REPL でも同じ形が拒否に変わる(ex/r10_repl.in)。
インスタンスを `echoln(show(w(1)))` より前に置くと両方とも受理する(ex/r1b_reorder.kel)が、これは §18.2 の条件 4(一般化しない束縛の共有)で除かれる形で、§18.2 には反しない。

REPL の表示も変わる。
`let g = idf(fn(x: Int32) => x + 1)` は HEAD で `g : (Int32) => Int32 = <fn>`、試作で `g : (Int32) => Int32 @ {} = <fn>` と出る(ex/r10_repl.in)。
下書きは --type-check の表示の変化を挙げているが、REPL の応答も同じく変わる。

ほかに境界の形を 15 本書き、HEAD と試作の結果が同じだった。
利用者の型の Add と Show のインスタンスと演算子(r2)、module の中の演算子と pub(r3)、run の中の Ref と MutableArray の操作と演算子(r4)、型エイリアスの注釈(r5)、ガードと入れ子の handle の中の演算子(r6)、前提つきのインスタンス(r7)、import した pub の関数(r9 の import の部分)、プレリュードの差し替え(r11。HEAD と試作で同じ拒否)、--no-prelude(r12。h の表示だけが ` @ {}` に変わる)、インスタンスの let rec(r14)、行変数の関数を呼ぶ初期化式(r16)である。

逆向きの変化(HEAD の拒否が試作で受理になる)は、下書きの記述より広い。
HEAD は組み込みのクラスのインスタンスで、構文上の値でない初期化式をエフェクトの有無によらず拒否する。
`{ let k = 1; fn(v) => "n" }`、`if true then fn(v) => "a" else fn(v) => "b"`、`{ let k = pre; fn(v) => k }`(r18)、`{ let k = 1 + 2; … }`(r17)、run を使う初期化式(r13)のどれも、HEAD は「純粋でなければなりません … スコープ付きの型 ς1 がスコープの外に漏れています」で拒否し、試作は受理して正しく実行する。
`fn(v) => "n"` と `{ fn(v) => "n" }` と `mk()` は HEAD でも通る。
下書きの (6) はこの類をゼロ除算の 3 本(inst_a、inst_b、v9)としてだけ挙げ、P[V97-2] の根拠は HEAD が e8 を「偶然に拒否」したと書くが、HEAD の拒否の理由はエフェクトではなく、値でない初期化式の行が宣言の剛定数の行と出会うことである(実測から導いた性質)。

## 5. 仕様の文面

§12.2 に足す文面の 2 文目「初期化式の評価でゼロ除算などの実行時エラーが起きるときは、インスタンス宣言を実行する時点で起きる(§6.4)」は、前提つきのインスタンスで実測と合わない。
ex/r19_premdiv.kel(組み込みの Show)と ex/r20_premdiv_user.kel(利用者のクラス)は、前提つきのインスタンスの初期化式に `1 / z` を書いた形で、試作は `a`、`b` を出した後、メソッドを使った時点で「実行時エラー: ゼロ除算です」になる(終了状態 3)。
§6.4 の 653 行のとおり、前提つきのインスタンスの初期化式は使うたびに評価するからである。
また §6.4 の 654 行は「これらの初期化式は構文上の値なので、停止し、エフェクトを起こさない」とするが、r20 は HEAD でも値でない初期化式を受理して実行時エラーになる。
§12.2 の文面は、前提の無いインスタンスと前提つきのインスタンス(と制約つきのメソッド)を分けて書き、654 行との食い違いも合わせて扱う必要がある。

§12.4 に足す文面と §13.2 の制限は、試作の実測(bopweak、ordervr_id)と矛盾しない。
§15.5 の終了状態は、inicon と r1 が型検査の拒否(1)、inidiv と r19 が実行時エラー(3)で、分類に合う。
付録 A の文法には触れない。

## 6. 判断事項

P[V97-1] の推奨に異論は無い。
P[V97-2] の推奨(空の行)にも異論は無いが、根拠の「HEAD の組み込みのクラスの結果(e8 を拒否)とも一致する」は誤りに近い。
HEAD は e8 だけでなく純粋な値でない初期化式も拒否しており(r17、r18)、一致しているのは e8 の結論だけである。
見落とした代案として、初期化式を構文上の値に限る案がある。
§6.4 の 654 行は前提つきのインスタンスの初期化式を構文上の値と書いており、この案はその文面に実装を合わせる形になる。
ただし r7 の `{ let base = 2 + 3; fn(x) => x + base }` のような HEAD で受理する利用者のクラスの形を拒否するので、推奨案のほうが受理の変化は小さい。
P[V97-3] の推奨に異論は無い。
