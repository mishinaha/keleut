#### (1) 判定、規模、依存、出典

規模は S である(`lib/elab.ml` のコード 1 か所の並べ替えとコメント、cram 2 ブロック、10 コマンド、5 プログラム)。

V56 と重なるが、順序はどちらでもよい(P[V57-1])。

#### (2) 現状(根拠つき)

仕様: LangSpec §13.1(`doc/LangSpec.md:1105-1116`)は `@ {Print extends E}` の形だけを挙げ、行変数を行の要素に置く形の診断の文面は書いていない。
規範 `doc/sample.kel` にもこの診断の記述は無い(`grep -n "extends の位置"` は 0 行)。
diktor の cram にも、この文面を固定するブロックは無い。

実装(ソースを読んで導いたこと): `lib/elab.ml` §11.6 の `elab_eff` の `EBraceRow` の分岐で、要素 `T.BLabel` の処理(`lib/elab.ml:1211-1236`)は、先に `find_alias n`(`:912-926`)を引き、`None` のときだけ `args = [] && SMap.mem n env.types` を調べて「行変数 n は extends の位置にのみ書けます」を出す(`:1222-1227`)。
`find_alias` は、EffectRow エイリアス、effect の宣言表、行にならないエイリアスの順に引き、見つかったエイリアスに `Decls.check_con_visible` を掛ける。
そのため、型パラメータと同名の行にならないエイリアスが `Decls.resolve_con` か `Decls.resolve_con_global` で見つかると、型パラメータの検査に届く前に、Type エイリアスの誤りか可視性の誤りで落ちる。
一方 `@ E`(`T.EIdent` の分岐、`:1168-1170`)は `env.types` を先に引くので影響を受けない。

HEAD での実測(`doc/log/261017-3-spike/V57/ex/`、入力と出力は `results.head.txt`)。
どの形も終了コード 1 で、受理と拒否は変わらない。

| 例 | 形 | HEAD の診断 |
|---|---|---|
| b0、b7 | 同名の宣言なし(module の中 / トップレベル) | 行変数 E は extends の位置にのみ書けます |
| b1、b8 | 同じ module の `type E = Int32` | エフェクト行に Type エイリアス E は置けません(: EffectRow を付けてください) |
| b2 | `module E { pub type E = Int32 }` の外 | 同上 |
| b3 | `module E { type E = Int32 }` の外 | 型 E.E は module E の外からは参照できません(pub を付けてください) |
| b6 | トップレベルの `type E = Int32` | エフェクト行に Type エイリアス E は置けません(…) |
| b14、b15 | module の EffectRow エイリアスと newtype の型パラメータ `E` を、同名の Type エイリアスのある module で本体に書く | 同上 |
| b4、b5 | 同名の newtype(同じ module / pub のコンパニオン) | 行変数 E は extends の位置にのみ書けます |
| b13 | 別の module(コンパニオンでない)の pub の Type エイリアス | 行変数 E は extends の位置にのみ書けます |
| b11 | 同じ module の `type E: EffectRow = {Print}` | 受理(`M.f : (Int32) => Int32 @ {Print}`。V50) |

台帳の訂正 7 は、変わる形を「同じ module の Type エイリアス」と「module の外から書いた pub の Type エイリアスのコンパニオン」に限っている。
b6 のとおり、トップレベルの Type エイリアスでも同じく変わる(実測)。
原因は同じ `find_alias` で、1 つ目の場所 `Decls.resolve_con` がトップレベルのエイリアスに当たるためである(ソースから)。
b14 と b15 のとおり、関数の型パラメータに限らず、エイリアスと newtype の型パラメータでも起きる(実測)。

#### (3) 判断と確定

D[V57-1]: `T.BLabel` の処理で、引数なしの名前が型パラメータで、同名の EffectRow エイリアスが `find_row_alias` で見つからなければ、`find_alias` を引く前に「行変数 n は extends の位置にのみ書けます」で落とす。
同名の EffectRow エイリアスがあるときは、従来どおりエイリアスを先に展開する(V50 の振る舞いを保つ)。
これで `find_alias` の `None` の分岐の型パラメータの検査は到達しなくなるので、そこから取り除く。
引く順は、EffectRow エイリアス、型パラメータ、effect の宣言表、行にならないエイリアス、未知のエフェクトになる。
型パラメータと effect の宣言表の順は HEAD と同じである(b12 の `let f[Print]` は HEAD でも試作でも行変数の誤り)。

判断事項 P[V57-1]: V56 と 1 つの修正で閉じるか。
- 推奨案: 閉じない。V57 は `T.BLabel` の検査の順を変え、V56 は `find_alias` の可視性の検査を変える、別々の 2 つの修正にする。同じマイルストーンに入れてよく、順序はどちらでもよい。
- 代案: V56 の直し方として、`find_alias` が行にならないエイリアスを引かないようにする(`None` を返す)。そうすれば `T.BLabel` の `None` の分岐の型パラメータの検査に届くので、V57 も同時に閉じる。
- 推奨の根拠: 代案は、module の Type エイリアスを「未知のエフェクトではなく、Type エイリアスとして引いたうえで拒否する」という M36 の設計(`test/visibility.t:342-352` の visrow12 と visrow13 の前書き)を捨てることになり、V57 の範囲を越えて文面を変える。
  逆に、V56 をどう直しても、b1、b2、b6 の Type エイリアスの文面は残るので、V56 の修正だけでは V57 は閉じない(ソースから)。
  V56 の例を合成で走らせると、変わるのは型パラメータを含む `ex/b1.kel`(と反証者の写し)だけである(実測)。
- 採らない代案(反証者の指摘): 波括弧の中でも型パラメータを EffectRow エイリアスより先に引く形。V50 の非対称も閉じるが、b11 と visrow26 の受理を拒否に変えるので、受理と拒否を変えない V57 の範囲を越える。V50 は diktor の `doc/log/260926-1-plan.md:4411` で残すとされている。

#### (4) 仕様側の改訂案

変えない。
LangSpec は行変数を行の要素に置く形の診断の文面を書いておらず、受理と拒否も変わらないからである。

#### (5) diktor 側の変更

コード(`lib/elab.ml`、§11.6 の `elab_eff`、`EBraceRow` の分岐の `T.BLabel`): `match find_alias n with` の前に次の検査を置き、`None` の分岐から型パラメータの検査を除く。

```ocaml
if args = [] && SMap.mem n env.types && Option.is_none (find_row_alias n) then
  type_error ("行変数 " ^ n ^ " は extends の位置にのみ書けます")
else
  match find_alias n with ...
```

cram(`test/visibility.t`、V56 の 2 ブロックの後ろ。単独の試作の visrow16〜visrow16e を、合成では visrow22〜visrow26 に改めた):

| ブロック | プログラム | 期待 |
|---|---|---|
| visrow22 | 同じ module の `type E = Int32` と `@ {E}` | 3:31 行変数 E は extends の位置にのみ書けます |
| visrow23 | トップレベルの `type E = Int32` と `@ {Print, E}` | 2:29 同上 |
| visrow24 | `module E { pub type E = Int32 }` の外で `@ {E}` | 2:29 同上 |
| visrow25 | `module E { type E = Int32 }` の外で `@ {E}` | 2:29 同上 |
| visrow26 | 同じ module の `type E: EffectRow = {Print}` と `@ {E}` | 受理、`M.f : (Int32) => Int32 @ {Print}` |

前書きは 2 つである。
1 つ目(visrow22 から visrow25): 引数なしで行の要素に書いた型パラメータは、同名の Type エイリアスが同じ module やトップレベルにあっても、同名の module の Type エイリアスのコンパニオンが pub でもそうでなくても、行変数の合成として拒否する。
コンパニオンを Type エイリアスに限るのは、pub でない EffectRow エイリアスのコンパニオン(b18)が可視性の誤りのままだからである(実測)。
2 つ目(visrow26): 同名の EffectRow エイリアスは行の要素では型パラメータより先に当たり、`@ E` と `@ {E}` は別のものを指す。これは `doc/sample.kel:467` の略記の規則と食い違う現状の振る舞い(V50)である、と書く。
HEAD の lib では visrow22〜visrow25 の 4 コマンドが落ち、visrow26 は通る(合成の写しで実測)。

ソースコメント: §11.6 の記事(`lib/elab.ml:1072` の行変数の中置の合成の文の後)に、型パラメータの検査の順と visrow22〜visrow25 への参照、同名の EffectRow エイリアスが pub でないコンパニオンなら可視性の誤りになること、`@ W` と `@ {W}` が別のものを指しうること(V50 の事実、visrow26)を足す。
`T.BLabel` の分岐の内側のコメントを、新しい検査の位置へ移して書き足す。

#### (6) リスク

- 受理と拒否が変わる形: 新しい検査は `type_error` を出すだけで、HEAD で `find_alias` が `Some` を返して型エラーになっていた形を別の型エラーに替える。HEAD で `find_alias` が EffectRow エイリアスを返す形は `find_row_alias` が `Some` なので検査に当たらない。HEAD で `None` を返していた形は、HEAD でも同じ検査に当たっていた。したがって受理と拒否は変わらない(ソースから)。sample の型検査(stubs つき)は HEAD と試作で同一(終了コード 0、68 行)だった(実測)。
- `find_row_alias` を 2 回引く: 型パラメータと同名の名前のときだけで、表の引きが 2 回増えるだけである。
- V30 の反証者の r21(`V30/verify/ex/r21_v57_param.kel`)も、合成で「行変数 E は extends の位置にのみ書けます」に変わる(実測)。
- V50 を cram で固定する: visrow26 は V50 の非対称の片側を固定する。V50 を直すときは、このブロックの期待値を改める。
