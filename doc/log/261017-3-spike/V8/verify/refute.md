## 退行の探索

HEAD が受理するプログラムを 15 本書き、両方のビルドで走らせた(`verify/ex/`、出力の全文は `verify/probes.txt`)。

受理と出力が HEAD と同じだったもの:

- `r2_module.kel`: module の中の pub 関数で Int64 の `4294967295` と `0xFFFFFFFFFFFFFFFF` を照合する。どちらも `132`。
- `imp/main.kel`: import 先の pub 関数で Int64 の最大値と最小値を照合する。どちらも `truefalse`。
- `r4_tparam.kel`: 型パラメータ `A` を Int64 に決める呼び出しに、注釈なしの無名関数を渡す。どちらも `1`。
- `r5_guard.kel`: ガードつきの節。どちらも `1`。
- `r6_handlers.kel`: 入れ子のハンドラの操作節で Int64 の引数を照合する。どちらも `0`。
- `r8_letrec.kel`: `let rec` の群。どちらも `1`。
- `r10b_class.kel`: Int64 のインスタンスのメソッド。どちらも `truefalse`。

- `r12_with.kel`: `with` の後ろの照合。どちらも `7`。

- `r14_tuplelet.kel`: `let (4294967295, y) = p` で `p: (Int64, Int32)`。どちらも警告 1 つと `1`。
- `r15_polyint.kel`: 一般化しない局所の束縛が Int64 に決まる。どちらも `3`。

- `r18_repl.in`: 対話的な実行で、範囲外のパターンを積んだまま別の型エラーで落ちた入力の後に、Int64 の照合を受理する。どちらも同じ出力である(§18.5 を保つ。`start_input` が積んだリストを空にする)。

HEAD が受理し、試作が拒否する形は、範囲外の字面を含むもの(意図した変更)のほかに見つからなかった。

出力が変わったが意図どおりのもの(退行ではない):

- `r16_repl.in` の `:type fn(x) => x match { case 4294967295 => 1  case _ => 2 }` は、HEAD では `(Int32) => Int32` を表示し、試作では `! <stdin>:4:31: 型エラー: 数値リテラルのパターン 4294967295 は Int32 の範囲を超えるので、どの値にも一致しません` になる。
  下書きの (6) が実測済みとして挙げる経路で、同じ式を入力すれば拒否されるので整合する。
  cram には固定されていない。
- `r7_toplevel_nongen.kel`(一般化しない `r` に範囲外のパターンを持つ無名関数を入れ、次の宣言で Int64 を渡す)は、どちらも拒否する。
  HEAD は `3:18: 型が一致しません: Int64 と Int32`、試作は `2:36:` の範囲外のパターンを報告する。
  `r` の宣言の終わりに既定化で Int32 に決まる(LangSpec §4.2 の 242 行)ので、先に `r` の宣言が落ちるのは規則どおりである。

観察(直す必要は判断しない):
試作の mask.kel のブロックでは、`--type-check` が `f : (Int32) => Int32` を印字した後に、同じ宣言 `f` の型エラーを出す。
印字(elab.ml 4987 行ほかの分岐)が宣言の終わりの検査より先に走るためである。
拒否された宣言の型が出力に現れる形を cram が固定することになる。
LangSpec §15.5 は型検査だけを行う機能の出力を処理系が定めるとしているので、仕様とは矛盾しない。

## 仕様の文面

§4.2 の改訂案は、§15.5 の終了状態の表(型検査での拒否は 1、初期化を行わない)と合う。
試作でも範囲外のパターンを含むプログラムは何も出力せずに終了コード 1 で終わる(`dead.kel` など)。
§18.2 の並べ替えについては、検査は各宣言の終わりに、その宣言の既定化の後に走る。
リテラルの型はその宣言の終わりまでに決まる(§4.2 の 241-243 行)ので、検査の結果は宣言の順序に依存しない。
§18.4 のエイリアスへの置換は `r1_alias.kel` で、§18.5 は `r18_repl.in` で保たれることを確かめた。
付録 A の文法は変わらない。
§11.1 の追記の例 `Int32` の値に対する `case 0xFFFFFFFF` が `-1` に一致することは、`r13_variant.kel` と litok.kel で実測した。

改訂案の「ほかの基数ではビット幅を超える」は、負の 16 進(`-0xFFFFFFFF` が Int32 で `1`)を説明しない。
これは HEAD の式の位置と同じ性質で、下書きの (6) が書いている。
§4.2 は負の 2 進、8 進、16 進のリテラルを今も定めていないので、この改訂で新たに矛盾は生じない。

## 判断事項

P[V8-1] の推奨(型エラー)に異論は無い。
ただし、代案が 1 つ抜けている。
照合が範囲外のリテラルの節に達したときに実行時エラーにする案である。
interp.ml の `match_pat`(160-165 行)は値の型(`VInt32` / `VInt64`)を見ているので、`None` を返す代わりに「数値リテラルが範囲外です」を投げられる。
これは式の位置の §4.2 の規則と対称になる。
推奨より劣る理由は、節に達しない限り誤りが見えないこと、ガードや前の節の順序で出たり出なかったりすること、`--type-check` で見えないことである。

P[V8-2] の根拠の「パターンは評価されないので、評価時のエラーという選択肢がもともと無い」は誤りである。
上のとおり、照合の時点で実行時エラーにする選択肢はある。
推奨(式の位置は変えない)の結論は変わらない。

## 試験の観点の抜け

旧 mask.kel のブロックは、積の鍵が偽の冗長警告を出さないことを確かめていた。
下書きは、型エラーで警告が捨てられるのでこれを出力から確かめられなくなる、と書く。
しかし、Int64 の列で同じ観点を確かめられる。
`verify/ex/mask64.kel`(Int64 の列に `case 0xFFFFFFFF` と `case -1` を並べる)は、HEAD でも試作でも `21` を出し、`--type-check --strict-exhaustive` の終了コードは 0 である。
2 つの字面は Int32 の読みでは同じ `-1` になり、Int64 では別の値になる。
鍵を Int32 の読みだけにする退行があれば、`case -1` に偽の冗長警告が出る。
mask.kel を型エラーのブロックに変えるなら、このブロックを足して観点を残すべきである。
