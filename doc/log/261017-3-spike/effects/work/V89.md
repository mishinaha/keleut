#### (3) 判断と確定

判断事項 P[V89-1]: §13.5 の「ガード」をどちらに揃えるか。

- 推奨案 A: 操作節自身のガード(入れ子の `handle` の操作節のものを含む)だけを指すと明記する。実装は変えない。
- 代案 B: 操作節の本体の中の `match` のガードでも `resume` を拒否する。`lib/elab.ml` の `match` の節(1857 行)で、`resume_ty` が `Some` のときガードを `resume_ty = None` で推論するように変える。
- 代案 C: 操作節自身のガードでも `resume` を許す。`lib/interp.ml` §14.9 の節の選択で `resume` を渡し、ガードが偽のときの次の節の選び方と、再開しない操作の節の破棄の前に評価する規則(§13.6 の 1293 行)との関係を新たに決める。
- 推奨の根拠:
  - 操作節自身のガードは、どの節で操作を処理するかを選ぶための式であり、§13.6 の 1293 行はこれを「破棄の前に評価する」ものとして扱っている。ここで継続を再開すると、ガードが偽のときに再開済みの継続を持って次の節へ進むことになり、C はその規則を新しく作る必要がある。
  - 本体の中の `match` のガードは、本体の評価の途中にある式であり、条件式の条件や照合対象と同じく継続がすでに節の手にある。`sample.kel` 322 行は条件式を `Boolean` に対する `match` の略記と述べており、B を採ると `if resume(x) then …` は受理し `true match { case _ if resume(x) => … }` は拒否するという切れ目ができる。
  - B は HEAD で受理するプログラム(`g2`、`g9`)を拒否に変える。A は振る舞いを変えない。
  - アフィン性(2 回目の再開)は、本体の中のガードでも実行時の検査で守られる(`g6`、終了状態 3)。ガードだから特別に壊れる性質は見つからなかった。

反証者は推奨案 A に異論を出していない。
推奨案 A で確定する。

D[V89-1]: `resume` を書けない「ガード」は、`case op(...) if g =>` の `g`(操作節自身のガード)である。
節の中に書いた入れ子の `handle` の操作節のガードも含む。
操作節の本体の中の `match` の節のガードは本体の一部であり、本体のほかの位置と同じ規則に従う(再開する操作の節なら書ける、再開しない操作の節や閉包の本体なら書けない)。

D[V89-2]: 同じ段落で、入れ子の `handle` の `return` 節と `cancel` 節にも外側の節の `resume` を書けないことを明記する(HEAD の `g12` の振る舞い)。
診断の文面は変えない(文面の統一は V133 で扱う)。

D[V89-3]: ガード、`return` 節、`cancel` 節の中に書いた別の `handle` の操作節の `resume` は、内側の節の継続を再開するものなので書けることを明記する(HEAD の `b1`〜`b3` の振る舞い)。
1271 行と 1276 行の除外と同じ形の文にする。
