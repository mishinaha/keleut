#### (3) 判断と確定

D[X-perform-1]: 行の失敗の判定を、エラーの文字列ではなく単一化の構造で行う。
`elab_check` に省略可能な引数 `row_note`(添える文言)を足す。
`fallback` は、文言があり、推論した型と期待型がどちらも矢印で、期待型の最外の行が閉じた空の行のとき、引数、返り値、行の順に単一化し、行の単一化の失敗にだけ文言を添える。
`Unify.unify` の矢印の分岐(`lib/unify.ml:561-564`)と同じ順序なので、受理と拒否は変わらない(ソースを読んで導いた性質。cram の差分が文面だけであることで確かめた)。
引数の型の不一致は行より先に報告されるので文言が付かない(`a13`)。
`_item` やレコードのフィールドの誤りは、期待型が矢印でないので文言が付かない(`a6`、`a7`)。
期待型の行が空でない形(`a14`)は、§9 の `@` 省略と関係が無いので付けない。

D[X-perform-2]: 文言は `perform` の引数と `resume` の引数にだけ渡す。
操作の型は型パラメータを持たない(`test/spec_gaps.t` の effopparam、effparam が拒否を固定している)ので、期待型の空の行は、操作の型に書いた `@ {}` か `@` の省略から来る(ソースを読んで導いた性質)。
文言は次のとおりで、`<what>` は `操作 spawnp の引数の型` か `操作の返り値の型` である。

> (<what>が求める関数の行は空 = 純粋です。操作の型の矢印は書いたとおりに読み、@ の省略は @ {} と読みます。エフェクトを起こす関数を通すなら、操作の型のその矢印に @ で行を書いてください。§9)

「行変数を型パラメータに取ってください」は、操作に型パラメータを書けないので使わない。
`resume` は環境に操作名を持たない(`env.resume_ty` は型の組)ので、操作名を書かない。
