### N.4 V101：perform と resume の引数を検査モードに通す(X-perform を吸収)

X-perform はこの項目に吸収する(X-perform の P[X-perform-3] の推奨案)。
X-perform は、V101 が `perform` と `resume` の引数を `elab_check` に通すことを前提に、その `fallback` で行の不一致に §9 の案内を添える。
台帳では V101 と X-perform の両方をこの項目で閉じる。
判断事項と裁定の番号は、それぞれの最終稿のまま残す。
各小見出しの中は、V101 の部分、X-perform の部分の順に書き、分野の合成で分かったことを最後に足す。
コミットは V101 の 3 つの後に X-perform の 3 つを置く。

#### (3) 判断と確定

**V101 の部分。**

判断事項 P[V101-1]: `perform` と `resume` の引数を、関数呼び出しの実引数と同じ検査モードに通すか。

- 推奨案: 通す。2 か所の `Unify.unify (elab_exp …) t` を `elab_check env level eff … t` に置き換える。
- 代案 A: 渡す側の開きだけを足す(`subsume_closed` を挟んで単一化する)。ラムダへの押し込みは入れない。
- 代案 B: 直さず、§13.2 の制限の 1 つ目に書いたままにする。
- 推奨の根拠: 操作の呼び出しは関数呼び出しと同じ形をしており、同じ位置で受理が分かれる理由が利用者から見えない。
  `elab_check` は既に関数呼び出しの全実引数に使っている経路で、失敗する形は `fallback` に落ちるので、受理を狭める経路を持たない(ソースを読んで導いた性質)。
  試作で既存の cram に新しく落ちるブロックは無く、反証者が 25 本余りの境界の例(エイリアス、行のエイリアス、型クラスのメソッド、入れ子のハンドラ、module、import、`--prelude`、REPL、網羅性の警告と `--strict-exhaustive`)で探しても、受理が狭まる形は見つからなかった(実測、`doc/log/261017-3-spike/V101/verify/ex/run1.txt`〜`run10.txt`)。
  代案 A は `p2`、`r2` の操作名の解決を救えず、関数呼び出しとの差が残る。

推奨案で確定する。

D[V101-1]: `perform` の実引数と `resume` の引数は、関数型を要求する位置と同じく検査モードで検査する。
期待型は、`perform` では操作の型の引数行、`resume` では操作の返り値の型である。
名前の参照でない式は、期待型の対応する部分が関数型なら閉じた行を開いてから単一化する。
引数に書いた無名関数の本体は、期待型の対応する部分が関数型なら、その矢印の行の下で推論する(タプルの要素、無名関数の本体の中の無名関数のように入れ子になっていてもよい)。

D[V101-2]: `perform` で引数を検査してから行の単一化をする順序は変えない。
無名関数の本体は期待型の矢印の行で推論するので、外側の `eff` にラベルを足す順序は解決に影響しない(ソースを読んで導いた性質。`p8` の実測で解決と実行を確かめた)。

判断事項 P[V101-2]: §13.3 に、実引数に書いた無名関数の本体の行を書くか。

- 推奨案: 書く。関数呼び出しと `perform`、`resume` をまとめて書き、範囲は 1137 行と同じく入れ子を含め、対応する部分が関数型のときに限る。
- 代案: 書かない。§13.3 の「その位置のエフェクト行」の解釈に任せる。
- 推奨の根拠: この変更で受理が広がる形の半分(`p2`、`r2`、`p8`、`y3`、`y4`)は操作名の解決によるもので、仕様に根拠の文が無いと、受理の理由を仕様から読めない。
  関数呼び出しで同じ振る舞いになることは HEAD で実測した(`c2`、`c3`、`y8calltuple` の 4 行目)。
- 範囲の根拠(実測): 型注釈が関数型である値束縛の初期化式に書いた無名関数(`y8calltuple` の 5 行目 `let anno: () => Unit @ File = fn() => perform write("z")`)と、型パラメータの仮引数に渡す無名関数(`y9generic`)は、HEAD と試作の両方で拒否(5:39、3:41、複数のエフェクトに属する旨)である。
  したがって段落を「関数型を要求する位置」一般には広げず、実引数(`perform` と `resume` の引数を含む)に限る。

推奨案で確定する。

**X-perform の部分。**

D[X-perform-1]: 行の失敗の判定を、エラーの文字列ではなく単一化の構造で行う。
`elab_check` に省略可能な引数 `row_note`(添える文言)を足す。
`fallback` は、文言があり、推論した型と期待型がどちらも矢印で、期待型の最外の行が閉じた空の行のとき、引数、返り値、行の順に単一化し、行の単一化の失敗にだけ文言を添える。
`Unify.unify` の矢印の分岐(`lib/unify.ml:561-564`)と同じ順序なので、受理と拒否は変わらない(ソースを読んで導いた性質。cram の差分が文面だけであることで確かめた)。
引数の型の不一致は行より先に報告されるので文言が付かない(`a13`)。
`_item` やレコードのフィールドの誤りは、期待型が矢印でないので文言が付かない(`a6`、`a7`)。
期待型の行が空でない形(`a14`)は、§9 の `@` 省略と関係が無いので付けない。

D[X-perform-2]: 文言は `perform` の引数と `resume` の引数にだけ渡す。
操作の型は型パラメータを持たない(`test/spec_gaps.t` の effopparam、effparam が拒否を固定している)ので、期待型の空の行は、操作の型に書いた `@ {}` か `@` の省略から来る(ソースを読んで導いた性質)。
文言は次のとおりで、`<what>` は `操作 spawnp の引数の型` か `操作の返り値の型` である。

> (<what>が求める関数の行は空 = 純粋です。操作の型の矢印は書いたとおりに読み、@ の省略は @ {} と読みます。エフェクトを起こす関数を通すなら、操作の型のその矢印に @ で行を書いてください。§9)

「行変数を型パラメータに取ってください」は、操作に型パラメータを書けないので使わない。
`resume` は環境に操作名を持たない(`env.resume_ty` は型の組)ので、操作名を書かない。

- 推奨の根拠: 代案 1 は、仮引数の型が型変数で期待型の空の行が先の引数から決まる形を取り違える。

推奨案で確定する。
