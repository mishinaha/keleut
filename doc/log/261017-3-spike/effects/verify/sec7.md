#### (2) 現状(根拠つき)

仕様の文面。
LangSpec §13.6 は、再開しない操作の節について、節の本体の実行時エラーと外側による破棄ではハンドラ自身の `cancel` 節を実行しない(1296 行)、ガードの実行時エラーと外側による破棄では「継続がまだ生きているので」実行する(1297〜1298 行、再開する操作の節のガードも同じ)と定める。
再開する操作の節の本体(`resume` の引数を含む)が脱出したときの規則は無い。
1313 行は「本体の実行時エラーによって巻き戻すときも、この節を実行する」、1315 行は「自分で継続を破棄して終わる場合」は実行しないと書くだけである。
§15.5 の 1611 行は「そのとき有効なハンドラ」の `cancel` 節を実行するとするが、操作節はハンドラの外側の行で評価する(1216 行)ので、節の評価中にそのハンドラが「有効」かは文面から決まらない(V125 の指摘)。

実装(ソースを読んで導いた性質)。
`lib/interp.ml` §14.9 の `eval_handle`(HEAD の 954〜1117 行)の `effc` は、再開する操作の節が例外で脱出したとき、`r.r_used` が偽(`resume` 前)なら `Effect.Deep.discontinue k ex`(1086、1096、1115 行)、真なら `raise ex` とする。
`discontinue k ex` は継続の fiber に `ex` を送り、捨てる継続の中のハンドラの `exnc` を内側から通った後、自分の `exnc`(995〜1004 行、`run_cancel ()` は 1003 行)に届き、自分宛ての `Unwind` ではないので `run_cancel ()` が走る。
`raise ex` は親のスタックを伝わり、自分の `exnc` を通らない。
記事の表(§14.9「3 つの経路」、670〜674 行)の 3 行目(674 行)がこの経路で、記事は「捨てた継続の中と自分の cancel 節を走らせる」と書いている。
規則として言い直すと、ハンドラ自身の `cancel` 節は「継続が生きている(再開も破棄もしていない)間に、その操作の処理が脱出したとき」に走る。
ガード(1042 行)、`resume` の引数(1086 行)、`resume` 前の本体(1096、1115 行)がこれにあたり、再開しない操作の節は本体の前に継続を捨てる(1060〜1063 行、`discontinue` は 1061 行)ので本体の脱出では走らない。
V137 の後は、再開しない操作の節の本体を自分の `exnc` で評価する形になるが、本体の脱出は `exnc` の外へ出るので、自分の `cancel` 節は走らない(V137 の記事。合成の上での実測で `g_never_body_error` の出力は変わらない)。

#### (3) 判断と確定

判断事項 P[V128-1]: 再開する操作の節が `resume` の前に脱出したとき、ハンドラ自身の `cancel` 節を実行するか。

- 推奨案: 実行する(現状のまま)。規則を「継続が生きている間に操作の処理(ガード、節の本体、`resume` の引数)が脱出したら、ハンドラ自身の `cancel` 節を実行する」の 1 つにまとめ、§13.6 に書く。
- 代案: 再開しない操作に揃えて実行しない。試作 `doc/log/261017-3-spike/V128/V128-alt.patch`(`resume` 前の 3 か所の `discontinue k ex` を、自分宛ての `Unwind` で継続を捨ててから `ex` を送り直す形に替える、44 行)で測ると、cram の差は eval.t の tailresume と never_ops.t の fromclause から `cancel outer`、`cancel ask` の行が消える 2 か所だけで(`doc/log/261017-3-spike/V128/runtest.alt.log`)、例 `a`、`c`、`d`、`e`、`i`、`k_nested_second` から `cancel ask` が消える(反証者の 26 本では、`resume` 前の節の脱出で自分の `cancel` 節が走る 19 本のすべてから消えた)。

推奨の根拠は 4 つある。
1 つ目に、既に §13.6 に書いた規則と同じ原理で説明できる。
1297 行はガードで自分の `cancel` 節を実行する理由を「継続がまだ生きているので」とする。
`resume` 前の再開する操作の節の本体でも継続は生きており、同じ理由があてはまる。
再開しない操作の節の本体(1296 行)と B10(`resume` が戻った後)は、継続が破棄済みか消費済みなので走らない。
代案を採ると、ガードでは走り、同じく継続が生きている本体では走らないという区別を、別の理由で説明しなければならない。
2 つ目に、資源を持つハンドラの後始末が漏れない。
sample.kel の `with_file` の `read` 節が `resume` の前に失敗したとき、推奨案では `cancel` 節の `file_close(h)` が走る。
代案では、節の本体から外側の `throw` を起こしてプログラムが続く形(例 `d`)で、`return` 節も `cancel` 節も走らず、ファイルが閉じられないまま残る。
3 つ目に、処理系を変えない。
代案は `Unwind` の印の扱いを新たに設計する必要がある。
印が戻らない経路で元の例外を失うことを、反証者が `u3_err_in_cancel_clause`(内側のハンドラの `cancel` 節から自分の再開する操作を起こし、その節が `resume` 前に `1 / 0` で脱出する形)で実測した。
HEAD は `cancel 節で例外が抑制されました: ゼロ除算です` と記録し、代案は抑制の原因を `cancel 節から操作の巻き戻しで脱出しようとしました` と取り違える(値はどちらも `5`)。
`u1`(外側の再開しない操作による打ち切り)と `u2`(自分の再開する操作による打ち切り)では、代案でも元の実行時エラーで終わり、この弱点は現れない。
4 つ目に、規範の sample.kel:583 は `cancel` 節を「外側が継続を捨てたことによる巻き戻し」とする。
例 `d` と `e` は、外側のハンドラが自分のハンドラの枠を含む継続を捨てる形なので、文字どおりこの定義にあたる。
代案はこの 2 例でも自分の `cancel` 節を走らせないので、規範の文言と食い違う。

D339 との関係。
261017-1-plan.md の 3 節 (3) は、再開しない操作の節で自分の `cancel` 節を走らせない根拠として、この経路を「仕様に無い実装の都合である」と書いた。
推奨案はこの経路を仕様に上げるので、その記述(279 行)は取り下げる。
あわせて、D339 の根拠 1(278 行、`cancel` 節は外側から巻き戻されるときの後始末で、節の実行時エラーを含まない)も取り下げる。
推奨案の規則では再開する操作の節の実行時エラーでも自分の `cancel` 節が走るので、根拠 1 は一般論として成り立たない。
D339 の結論(再開しない操作の節の本体の脱出では自分の `cancel` 節を走らせない)は変えず、根拠 2 と根拠 3 で支える。
D[V128-2]: D339 の根拠 1 と 261017-1-plan.md:279 の記述を取り下げ、D339 は根拠 2 と 3 で支える。
D339 の根拠 2(再開しない操作の節はどの場合も自分で継続を破棄する)と根拠 3(末尾位置)は、再開しない操作の節に固有で、再開する操作の節にはあたらない。
再開する操作の節は、もともと本体を包みの中で評価し、末尾呼び出しを保証しない(§13.6 1290 行、§5.7)。

B10 との関係。
B10(`resume` 済みの節の脱出では走らない)は、推奨案の規則の「継続が消費済み」の場合にあたり、そのまま残る。
代案を採っても B10 は変わらない。

D[V128-1]: ハンドラ自身の `cancel` 節は、そのハンドラが処理中の操作の継続が生きている間(ガードの評価中、`resume` を呼ぶ前の再開する操作の節の本体と `resume` の引数の評価中)に、実行時エラーか外側のハンドラによる継続の破棄で脱出したときに実行する。
順序は、節の評価の中で起動したハンドラの `cancel` 節、捨てる継続の中のハンドラの `cancel` 節(内側から外側へ)、そのハンドラ自身の `cancel` 節、外側のハンドラの `cancel` 節である。
継続を破棄した後(再開しない操作の節の本体)と消費した後(`resume` が戻った後)の脱出では実行しない。
`resume` の最中(再開した計算の中)の実行時エラーでは、同じハンドラがまた有効なので、§15.5 の一般の規則で自分の `cancel` 節を 1 回実行する。

#### (4) 仕様側の改訂案

LangSpec §13.6、1290 行の後(段落の末尾)に次を足す。

```
再開する操作の節の本体で、`resume` を呼ぶ前（`resume` の引数の評価中を含む）に実行時エラーが起きた場合と、本体から操作を起こして外側のハンドラが継続を破棄する場合は、継続がまだ生きているので、ハンドラが外側から巻き戻されるときと同じく、そのハンドラ自身の `cancel` 節を実行する。
このとき、節の評価の中で起動したハンドラの `cancel` 節、破棄する計算の中にあったハンドラの `cancel` 節（内側から外側の順）、そのハンドラ自身の `cancel` 節、さらに外側のハンドラの `cancel` 節の順に実行する。
`resume` で再開した計算の中で起きた実行時エラーでは、そのハンドラはまた有効なので、§15.5 のとおりそのハンドラ自身の `cancel` 節を 1 回実行する。
`resume` が戻った後に節の本体で起きた実行時エラーと外側による破棄では、継続はもう無いので、そのハンドラ自身の `cancel` 節は実行しない。
```

1297〜1298 行の「再開する操作の節のガードも同じである。」は残す(新しい段落と同じ原理であることが読める)。

1315 行を次に替える。

```
操作を処理したハンドラが、節の値を返して自分で継続を破棄して終わる場合、そのハンドラ自身の `cancel` 節は実行しない。
節の評価が実行時エラーや外側による破棄で脱出した場合は、上の規則による。
```

§15.5 の 1611 行の後に次を足す。

```
実行時エラーが操作節の評価中に起きた場合、その節のハンドラ自身の `cancel` 節を実行するかどうかは §13.6 による。
```
