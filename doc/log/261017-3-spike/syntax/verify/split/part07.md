#### (2) 現状(根拠つき)

仕様: LangSpec §5.5(397〜398 行)は、括弧で囲んだ式、コンストラクタ、構造的ヴァリアントの後ろの末尾ブロックと 2 個目の末尾ブロックを構文エラーとし、411〜415 行は引数を小文字の識別子 1 個に限る。
HEAD の一般のパースエラーも終了状態 2 の構文エラーなので、振る舞いは仕様に反していない。
欠けているのは診断の案内だけである。
§5.5 は `{ x => }` のように文の列が空の形に触れていない(410 行は文の列にブロックと同じものを書けるとだけ言い、421〜422 行は空の `{}` をレコードとする)。
§2.3(84〜87 行)は `{` を次の行に書く形を「トップレベルとブロックの中」と「改行を区切りにしない位置」に分けて書き、`match` と `handle` の節を並べる波括弧の中を扱っていない(付録 A.3 の 1945〜1958 行と A.5 の `clause_body` からは構文エラーと導ける)。

実装: `lib/parser.mly` §3.19 の `tb_call`(979〜990 行)は、呼び出しの 3 つの位置の後ろの `trailing_block` と `record_exp` だけを受ける。
大文字の名前、`M.Foo`、`#Tag`、`paren_exp` の後ろの `{` を受ける規則は無い。
`{ x: T => }` と `{ x, y => }` の `{` は字句の分類(`lib/lexer.ml` §2.9 の `classify_brace`、727〜738 行)で `LBRACE_TYPE` と `LBRACE_RECORD` になるので `trailing_block` に届かず、`record_exp`(1078 行)も `=>` で行き詰まる。
`{ (a, b) => }` は `LBRACE_BLOCK` で、`lambda_block`(996〜1005 行)に対応する規則が無い。
2 個目の末尾ブロックの規則 `tb_call trailing_block`(989 行)は `record_exp` を受けないので、`f { 1 } {}` も一般のパースエラーになる。
`{ x => }` は `lambda_block` の `items` が空を許すので受理する(`--dump-ast` は `fn(x) => {}` と同じ)。

#### (3) 判断と確定

D[V60-1]: 字句の分類は変えず、文法に診断用の規則を足す。
試作では menhir の衝突は 0 件だった(`dune build` は `--strict` で通り、`menhir --explain` を単独で走らせた `.conflicts` も 0 バイト。HEAD も 0 バイト)。
`parser.mly` に優先順位の宣言は無いので、衝突の解決で構文木が黙って変わる経路も無い(ソースを読んで導いた性質)。

- `tb_call` に `upper_id tb_brace`、`postfix_exp DOT upper_id tb_brace`、`HASH_IDENT tb_brace`、`paren_exp tb_brace` を足す。
  `tb_brace` は 3 種の `{` の 1 トークンだけを受け、中身を読まずに診断を出す。
- 呼び出しの 3 つの位置の `record_exp` を `trailing_other` に替える。
  `trailing_other` は `record_exp`、`LBRACE_RECORD field_list EQ_GREATER`、`LBRACE_TYPE lower_id`、`LBRACE_TYPE upper_id` を受け、レコードの形か引数の誤りかを返す。
  `LBRACE_RECORD field_list EQ_GREATER` は、意味動作で並びを調べ、2 個以上の名前だけ(パンニングの形)の並びを引数の誤り、それ以外(`{ x = 1 =>`、`{ x, =>`)をレコードの形とする。
- `tb_call trailing_other` を足し、2 個目の診断を `{}` にも出す。
- `lambda_block` に `LBRACE_BLOCK paren_exp EQ_GREATER` を足す。`=>` まで読んだところで診断を出す。

D[V60-2]: 診断の文面は次のとおりとする。

| 形 | 文面 |
|---|---|
| `Foo { k }`、`M.Foo { k }`、`#Tag { k }`、`Foo {}` | 既存の「コンストラクタと構造的ヴァリアントには末尾ブロックを付けられません」 |
| `(g(1)) { k }` | 括弧で囲んだ式には末尾ブロックを付けられません(関数を括弧の中の引数として渡します) |
| `{ (a, b) => }`、`{ () => }`、`{ (a) => }` | 末尾ブロックの引数は小文字の識別子 1 個です(引数のない関数は { 式 }、タプルを分解する関数は { case (a, b) => 式 } と書きます) |
| `{ x: T => }`、`{ x: T }`、`{ Foo: T => }` | 末尾ブロックの引数に型注釈は書けません(型注釈の要る関数は fn(x: T) => 式 と書いて括弧の中に渡します) |
| `{ x, y => }`(名前だけの 2 個以上の並び) | 末尾ブロックの引数は小文字の識別子 1 個です(2 個以上の引数を取る関数は fn(x, y) => 式 と書いて括弧の中に渡します) |
| `{ x = 1 => }`、`{ x, => }` | 既存の「末尾ブロックの中身にレコードの形は書けません(…)」 |
| `f { 1 } {}` | 既存の「末尾ブロックは 1 つの呼び出しに 1 個までです」 |

`{ _: T => }` と `perform E.op { k }` は表に無く、HEAD と同じ一般のパースエラーのままである(試作の実測)。

D[V60-3]: 位置は、引数の誤り(括弧、型注釈、名前の並び)が既存の `{ _ => }` と同じく引数の先頭を、ほかが `{` を指す。

D[V60-4]: 末尾ブロックの位置の外の `{ x: T => }` と `{ x, y => }`(`annot_out.kel`、`two_out.kel`)は一般のパースエラーのままにする。
位置の外の `{ (a, b) => }`(`tuple_out.kel`)は `lambda_block` を通るので、引数の診断になる。
位置の外でレコードやレコード型に分類される `{` を診断するには式の `record_exp` の側に規則が要り、V60 の範囲を越える。

判断事項 P[V60-1]: `{ x => }`(文の列が空)を受理し続けるか。
推奨案: 受理し、§5.5 に `{ x => 文の列 }` の形に限って「文の列は空でもよく、本体の値は `Unit`」と書く。
代案: `lambda_block` の空の `items` を拒否する専用の診断を足す。
推奨の根拠: 振る舞いを変えずに済み、`fn(x) => {}` と同じ関数になる(`{}` は `Unit` の値。実測で `u == v` は `true`)。
`{ x => }` が誤りの兆候だとする根拠は実測にも報告にも無い。
`{ 文の列 }` の形の空(`f { }`)はレコードの診断のまま変わらない(HEAD でも試作でも終了状態 2)。

判断事項 P[V60-2]: `match` と `handle` の節の本体で `{` を次の行に書く形をどう扱うか。
推奨案: 振る舞いを変えず(一般の構文エラー)、§2.3 に文面を足し、cram で固定する。
代案 1: 節の本体の後ろの改行に続く `{` に専用の診断を出す(文法に `NL` を含む診断用の規則が要り、衝突は未計測)。
代案 2: 節の並びの中で改行を区切りにしない(`armdot.kel` のような折り返しの規則が変わり、互換性を損ねる)。
推奨の根拠: 付録 A.3 と A.5 から構文エラーが導けるので、欠けているのは §2.3 の本文の記述だけである。
節の区切りは `case` 自身なので、`;` を挟んだ形(`armsemi.kel`)も同じく構文エラーで、`{` だけを特別扱いする理由が薄い。

判断事項 P[V60-3]: `=>` の無い `{ x: T }` を末尾ブロックの位置に書いた形を、どの診断にするか。
推奨案: 型注釈の診断にする(D[V60-2] の表のとおり)。
代案: 既存のレコードの形の診断に寄せる(`LBRACE_TYPE lower_id` の規則を `=>` まで読む形に変える)。
推奨の根拠: `LBRACE_TYPE` の規則は名前を読んだ時点で診断を出すので、`=>` の有無を見るには `ty` を読む規則が要り、文法が広がる。
`{ x: T }` を末尾ブロックの位置に書く誤りは、`=>` の書き忘れの方が多いと見るが、これは推測である。
LangSpec §5.5 の 421 行はこの形をレコード型に分類される形とし、構文エラーと定めるだけなので、どちらの文面も仕様に反しない。

推奨案で確定する。

#### (4) 仕様側の改訂案

§5.5 の 410 行(「文の列には、ブロック（§5.4）と同じものを書ける。」)の直後に、次の 1 文を足す。

```
`{ x => 文の列 }` の文の列は空でもよく、`{ x => }` は本体の値が `Unit` の関数を渡す。
```

形を `{ x => 文の列 }` に限るのは、`{ 文の列 }` の形の空の `{}` が 421〜422 行でレコードとされ、末尾ブロックとして書けないからである。

§2.3 の 87 行の直後に、次の段落を足す。

```
`match` と `handle` の節を並べる波括弧の中でも、改行はブロックの中と同じ規則で区切りとみなす。
節の区切りは `case` 自身であり、節の本体の後ろに区切りは置けないので、節の本体の式の後ろで区切りになる改行は構文エラーになる。
そのため、節の本体に書いた呼び出しの末尾ブロックの `{` を次の行に書くと、中身によらず構文エラーになる。
```

§5.5 の 397〜398 行と付録 A.5 の 2069〜2072 行は変えない。
どちらも構文エラーとだけ定め、診断の文面を定めていないからである。

#### (6) リスク

- 診断用の規則が、これまで受理していた入力を拒否する可能性。
  足した規則はどれも、HEAD で一般のパースエラーになる先読み(式の直後の `{`、`=>`、`LBRACE_TYPE`)でだけ働く。
  文法は衝突が無く HEAD の文法を含むので、HEAD が受理する入力の構文木は変わらない(ソースを読んで導いた性質)。
  試作で既存の cram が ctor0、tag0、paren の 3 本を除いて変わらないこと、`recok.kel`、`ctor_ok.kel`、`paren_ok.kel`、反証者の r1〜r10 と `test/sample/sample.kel` の出力が HEAD と同じであることを確かめた。
- REPL の入力の途中の扱い。`=>` や `{` の 1 トークンで診断を出すので、複数行の入力の途中でも診断が早く出る。
  試作の REPL(`doc/log/261017-3-spike/V60/results.txt` の末尾)で、誤りの行の後ろの入力が評価されることを確かめた。
- 同じ行の検査は `trailing_other` と `tb_brace` の規則には働かない(HEAD の `record_exp` の規則と同じ)。
  `(Foo` の次の行の `{ k }`(`ctornl.kel`)は同じ行の診断ではなく構築の診断になる。
- パンニングの判定は値が同名の識別子かを見るので、`{ x = x, y => }` も名前の並びとして引数の誤りになる。文面の案内は外れないので許容する。
- 同じマイルストーンで V88、V118 も `parser.mly` を変えるなら、合わせた文法で `menhir --explain` の衝突の件数を測り直す。分野の合成で測り直し、0 件だった(上の (5))。
- V115 が「パースエラー」の文字列(`lib/driver.ml` の `parse_unit_with`、`try_parse`)を変えると、nlarm と trailing_block.t に残る一般のパースエラーの期待値が変わる。試作の前書きは既に「構文エラー」と呼んでいる。分野の順序では V115 を先に入れるので、本項目の期待値ははじめから V115 の文面で書く。
- 本項目の診断は文法の規則で出すので、V88 の増分 API の駆動では `Syntax_error_at` として `parse_program` の外へ出る。V88 の予約語の判定は `Parser'.Error` の分岐でだけ走るので、本項目の診断とは競合しない(ソースから導いた性質。合成後の trailing_block.t で確かめた)。
