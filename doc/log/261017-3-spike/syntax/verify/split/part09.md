- §4.2 の 223〜225 行は `.5` を書けないこと、`1.` と `1.e5` が浮動小数であること、`1.foo` が数値へのフィールド選択にならないことを書く。
- `doc/sample.kel` の 104〜106 行は「最長一致により、`1._0` や `1.foo` は「数値の後に識別子」と読む」と定める。
- §15.5 の 1621 行は、字句と構文の誤りを終了状態 2 とする。
  パースエラーの文面は仕様に無い。

実装は次のとおりである(ソースを読んで確かめた)。

- `lib/lexer.ml` §2.2(147〜196 行)の正規表現と §2.7 の `read_raw_token` の 507 行は、数値を最長一致で切る。
  数値の直後に英数字が続いても字句エラーにせず、残りは次のトークンになる。
- `lib/driver.ml` §16.3 の `parse_unit_with`(264〜274 行)は、`Parser'.Error` を `パースエラー(付近のトークンを確認してください)` にし(271 行)、位置に `lexer.Lexer'.last_sp` を使う。
  REPL の `try_parse`(769 行)も同じ文面と位置である。
- `last_sp` は menhir が詰まったトークン、つまり数値の後ろのトークンの開始位置である(`lib/lexer.ml` §2.11 の `read`、938〜941 行)。
- `last_ep`(`lib/lexer.ml` 601 行)は HEAD では書くだけで読まれていない(§2.8 の 562〜564 行)。

HEAD での実測は `doc/log/261017-3-spike/X-F5b/results.head.txt` にある(`doc/log/261017-3-spike/X-F5b/ex/lit*.kel`、各プログラムは `let a = <綴り>` と `let b = 2` の 2 行、`doc/log/261017-3-spike/X-F5b/run.sh` で生成)。
要点は次のとおりである。

| 書いたもの | トークン列(`--dump-tokens`) | `--type-check` の診断 |
|---|---|---|
| `1x` | `1` `x` | `1:10: パースエラー(付近のトークンを確認してください)`、終了状態 2 |
| `1.2.3` | `1.2` `.` `3` | `1:13: パースエラー(…)` |
| `0x` / `0x_1` / `0xg` | `0` `x` / `0` `x_1` / `0` `xg` | `1:10: パースエラー(…)` |
| `0b102` | `0b10` `2` | `1:13: パースエラー(…)` |
| `0o8`、`0b2`、`0o`、`0b` | `0` `o8` など | `1:10: パースエラー(…)` |
| `1i`、`1u`、`1f`、`1e`、`1E`、`1e+` | `1` `i` など | `1:10: パースエラー(…)` |
| `1._1`、`1.foo` | `1.` `_1` / `1.` `foo` | `1:11: パースエラー(…)` |
| `1u8x`、`1i32x`、`0xffz`、`1.5e` | `1u8` `x` など | 数値の後ろの位置でパースエラー |
| `1_`、`0xff_`、`1__2`、`1.`、`1.e5` | 1 個の数値 | 受理(`Int32` か `Float64`) |

どの割れ方も受理されずにパースエラーになり、位置は数値の後ろのトークンを指す。
文面は数値に触れないので、利用者は数値の綴りを誤ったことを位置から推し量る必要がある。
`1_` と `0xff_` の受理は付録 A.2 の文法(`digit ( digit | "_" )*`)のとおりであり、本項目の対象外とする。

浮動小数の後ろの `.` はフィールド選択として文法に合う(`1.2.foo` と `1.2._0` は構文を通り、型エラーの終了状態 1 になる。`doc/log/261017-3-spike/X-F5b/results.final.edge.txt` の k9、k10)。
そのため `1.2.` の後ろで詰まるのは、続きが数値(`1.2.3`)か予約語(`1.2.match`、`1.0.if`、`1.2.true`、`1.2.with`)のときである。

#### (3) 判断と確定

判断事項 P[X-F5b-1]: 割れた数値をどの段階でどう報告するか。

- 推奨案: 字句の切り方と受理するプログラムを変えず、パースエラーの報告のときだけ直近のトークンを調べ、数値が隙間なく次のトークンに続いていたら、数値とその直後の綴りを名指す文面にする。終了状態は 2 のまま。
- 代案 A: 260829-4 の (a) のとおり、sedlex に `number, Plus idchar` の長い分岐を足して字句エラーにする。
- 代案 B: 直さない(延期を続ける)。
- 推奨の根拠: 代案 A は、付録 A.2 の 1926 行と sample.kel の 105 行が定める「`1.foo` は数値と識別子に切れる」を字句エラーに変えるので、規範と仕様の両方の改訂が要る。
  さらに、HEAD が受理する `if c then 1else 2` を拒否するようになる(`doc/log/261017-3-spike/X-F5b/ex/e_else.kel`、`doc/log/261017-3-spike/X-F5b/verify/ex/r2`、`r3`、`r6` で受理を実測)。
  推奨案は文法も受理の集合も変えないので仕様の改訂が要らず、260829-4 が挙げた「分岐順を誤ると全数値リテラルを壊す」リスクも生じない。
  代案 B は、試作が S で収まり既存のゴールデンが動かなかったので、延期を続ける理由が弱い。

判断事項 P[X-F5b-2]: 報告の位置をどこにするか。

- 推奨案: 数値の開始位置(`0b102` なら `1:9`)。
- 代案: 従来どおり詰まったトークンの位置(`1:13`)のまま、文面だけで数値を名指す。
- 推奨の根拠: 誤りは数値の綴りにあり、文面が名指すのも数値なので、位置と文面が同じものを指す。
  負の数値リテラル `-0b102` では数値の部分の `1:10` を指す(`-` は別のトークンで、パーサが後で畳むため)。

判断事項 P[X-F5b-3]: 字句解析器の状態をどう持つか。

- 推奨案: `last_ep` を残し、直近 3 個のトークンを新しい順に持つ `recent : entry list` を足す。
- 代案 1: `last_ep`(HEAD では読まれていない)を消し、`recent` に置き換える(下書きの案)。
- 代案 2: V118 の `before_ep` を `recent` から導き、`last_ep` と `before_ep` を足さない。
- 推奨の根拠: V118 は `last_ep` を読んで `before_ep` を控える設計で、V88 も `last_ep` を戻す。
  代案 1 は両者と同じフィールドで衝突し、どちらかの差分を書き直させる。
  代案 2 は V118 の判定を本項目の状態に依存させ、項目の順序を縛る。
  推奨案は 1 フィールドを足すだけで、V118、V88 の差分の行とは独立に当たる。
  状態が 1 個増えるのは、V88 の復元の対象に `recent` を加えることで吸収する(1 節)。

設計上の裁定は次のとおりである。

- D[X-F5b-1]: 文面は `<位置>: 構文エラー: 数値リテラル 0b10 の直後に 2 が続いています(数値リテラルの綴りを確認してください)` とする(最終稿の頭の「パースエラー:」を V115 の形に改めた)。
  数値は `Lexer.show_number` で原文を出し、直後の綴りは (i) では `show_token` の表記、(ii) では `.` とその後ろの数値の表記をつなげたもの(`1.2.3` なら `.3`)にする。
- D[X-F5b-2]: 見分ける形は 2 つに限る。
  (i) 詰まったトークンの直前が数値で、両者の間に隙間が無く、詰まったトークンの表記が英数字か `_` か `.` で始まる。
  (ii) 詰まったトークンが数値で、1 つ前が `.`、2 つ前が数値で、3 つが隙間なく並ぶ(`1.2.3` は `3` で詰まる)。
  (ii) を数値に限るのは、`.` の後ろで詰まるのが数値か予約語のときで、予約語の形は数値の綴りの誤りではないからである。
  隙間の有無は位置の `pos_cnum` の一致で判定する。
  `<NL>`、`<EOF>`、文字列、括弧は表記が記号で始まるので対象外になる。
- D[X-F5b-3]: `last_ep` を残し、`recent` を足す(P[X-F5b-3] の推奨案)。
- D[X-F5b-4]: 受理と終了状態は変えない。空白を挟んだ `1 x`、`1"s"`、`1.2 .3`、浮動小数の後ろの `.` に予約語が続く `1.2.match` は従来の文面のままにする。
