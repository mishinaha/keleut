# V30 の反証

## 方法

試作の差分 `V30.patch` を `verify/diktor` に当てた(当たりはずれ無し。当てた後の差分は元と 411 行で一致)。
`dune build` と `dune runtest` は通った(期待値の差分 0)。
テストの期待値を HEAD のものに戻してコードだけで走らせると、差分は `kinds.t` の specunit2 と speclab の 2 ブロックだけだった(`verify/runtest_codeonly.log`)。
担当の `ex/*.kel` 27 本を HEAD と試作で走らせ直し、`results.head.txt` と同じ出力を得た。
`effect_order.t` の各プログラムを HEAD で走らせ、`effect_order.head.log` のとおりに 5 ブロックで差分が出ることを確かめた(effunknown だけが同じ)。
`tools/litwrap.py` は試作の両ファイルを変えず、`tools/litcheck.py --old` の marker は両ファイルとも 0 件だった。

## 下書きの誤り

1. (2) の「型エイリアスの本体(展開はパス 2)」と、「関数の注釈、型エイリアス、EffectRow エイリアスは 1b の後に読むので通る」は、エイリアスを関数の注釈から使う形にしか当たらない。
   エイリアスを 1b で読む本体(newtype のフィールド、effect の操作)から使うと、HEAD はエイリアスの本体の位置で落ちる(実測)。

   ```
   type W: EffectRow = {Log}
   newtype N = N(() => Unit @ W)
   effect Log = { log: (String) => Unit }
   ```
   HEAD: `r24_rowalias_via_newtype.kel:1:21: 型エラー: 未知のエフェクト: Log`(終了 1)、試作: 出力なしで終了 0。
   `type T = () => Unit @ {Log}` を `newtype N = N(T)` と `effect A = { a: (T) => Unit }` から使う形(r25、r26)も、HEAD は `1:23` で落ち、試作は通る。
   module の中の EffectRow エイリアスを module の newtype から使う形(r20)も同じで、HEAD は `2:27` で落ち、試作は実行して `w` を出す。
   したがって、宣言の種類で分かれていたのではなく、1b で読むかどうかで分かれていた(エイリアスの本体は、使う側のパスで読む)。

2. 試作は、下書きが挙げていない拒否から受理への変化をもう 1 つ持つ(実測)。
   module の中の非公開の Type エイリアスと、後ろで宣言するトップレベルの effect が同名のとき、module の newtype のフィールドの `{Log}` を、HEAD は Type エイリアスとして読んで落とし、試作は effect として読む。

   ```
   module M {
     type Log = Int32
     pub newtype N = N(() => Unit @ {Log})
   }
   effect Log = { log: (String) => Unit }
   ```
   HEAD: `r22_mod_type_alias_same.kel:3:34: 型エラー: エフェクト行に Type エイリアス Log は置けません(: EffectRow を付けてください)`(終了 1)、試作: 終了 0。
   effect を先に置いた形(r23)は HEAD も通るので、試作は宣言順への依存を消す向きである。
   `find_alias`(`elab.ml:912-926`)が effect の表を Type エイリアスより先に引くことによる(ソースを読んで導いた性質)。
   V56 と V57 が同じ関数を扱う。

3. 試作は §11.31 の残りの形の記述(HEAD の 3623-3637)を消したが、それを指す 2 か所が残る。
   `elab.ml:38` の表の「投機が相手のパラメータのカインドを決められない形(§11.31)を除き」と、`elab.ml:4640-4641` の「例外は、§11.31 で述べた、…波括弧で書いた行を前方参照で渡す場合である」である(試作では 4629-4630)。
   (5) のコメントの一覧にもこの 2 か所が無い。
   残りの形が試作の上で残るかどうかは V22 の担当の判断に依るが、どちらにしても参照先と文面を揃える必要がある。
   私が試した 3 本(エイリアス経由の `B[{}]` の両順、深さ 3 の連鎖)は HEAD と試作の両方で通り、残りの形は見つけられなかった。

4. 仕様の改訂案(4)は、ラベルを書ける位置を 3 つに限って名指しする。
   試作の振る舞いはそれより広く、値束縛の注釈、関数の注釈、型エイリアスの本体、インスタンスのメソッドも、後ろの effect のラベルを書ける(t01 で実測。HEAD は `2:40` のクラスのメソッドで落ち、試作は `v 3 w` を出す)。

## 退行の探索

HEAD が受理する形を中心に、境界の形を 25 本書いて両方のビルドで `--type-check` と実行の 2 通りに走らせた(`verify/ex/`、結果は `verify/cmp1.txt` とこの節)。
試作が HEAD の受理を拒否に変えた形と、出力を変えた形は見つからなかった。

- 投機がラベルのフィールドを読むようになる形: r01(先に effect、`{Log extends X}` と前方参照の `B[X]`、実行して `x` と `7`)、r14(specfield を実行)、r15(specinner と同じ相手に `{}` と `{Log extends X}` を渡す)、r06(使わないパラメータ)。
- module と pub: r02、r17、r20、r22、r23。
- 型パラメータと同名の effect: r13(`newtype N[E]` と `effect E`)。
- 入れ子のハンドラとガード: r03(`210`)、r16(ガードの中の `perform`、`1`)。
- エイリアス経由: r05(EffectRow エイリアスを newtype のフィールドと関数の注釈に使い、実行して `a` と `42`)、r24、r25、r26。
- import: r08(`from "./imp/lib" import { Tick, ticker }`、`t`)。
- 名前の衝突: r10、r11(エイリアスと effect の両順。文面と位置が同じ)、r12(クラスと effect の同名。どちらも受理)。
- 操作の索引: r07(非修飾の操作名の解決は変わらない)。
- 対話的な実行: r19(受理しなかった入力の effect を宣言し直す、二重の宣言、実行時エラーで受理しなかった入力の effect を宣言し直す)。出力は一致した。
- プレリュードの差し替え: `--prelude` に HEAD の `prelude.kel` の写しを渡して r05 と r14 を走らせ、一致した。

## 判断事項

P[V30-1] の推奨案(順序の変化を受け入れる)に異論は無い。
ただし、effect の型パラメータの検査は 1b の `register_effect` に残るので、名前の検査とは順序が揃わない(`newtype N = N(() => Unit @ {Nope})` と `effect Log[A] = …` では、試作も `1:28 未知のエフェクト: Nope` を先に出す)。
effname の前書きが型パラメータの検査も名前を置く時点で行うと読めないよう、文を分けるか、検査を `declare_effect` の呼び出し側へ移す代案を挙げるとよい。

P[V30-2] は文を足すことに賛成するが、文面は位置を列挙せずに一般に書くほうがよい(上の 4)。
例: 「エフェクトの名前も同じで、型を書く位置には、後ろで宣言するエフェクトのラベルも書ける。」
