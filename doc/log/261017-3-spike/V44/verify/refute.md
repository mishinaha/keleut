`V44.patch` は合成の木 `all/diktor` に対して取ったもので、HEAD の写し `snap/diktor` には当たらない。
`patch --dry-run` では 8 個の hunk のうち 4 個(#2、#3、#4、#7)が失敗する。
失敗の原因は文脈で、#2 は V111 の `has_sub`、#3 は V117 が変えた `check_pub_annots` の前の記事、#4 は V127 の `check_call_arity` の段落、#7 は V136 の `expected_params` の分岐である。
合成の木の写し(`verify/diktor`)に当てると、`dune build` は通り、`dune runtest` の差分は 0 行だった(`verify/runtest.log`)。
新しい `test/pub_effect_note.t` を合成の木(本項目の前)に置くと、pubvalinner、pubvalrec、pubvalarg、pubvalvariant、pubvalboth、pubrecvalrec、pubrunleak の 7 コマンドが落ちる(`verify/runtest.newfile-on-allbase.log`)。
担当の分類は正しい。
cram は 23 コマンド、cat で作るプログラム 10 本と sed で作る 1 本で、下書きの数と合う。

## 下書きが見落とした形(§11.12 の剛定数の呼び出し先)

§11.12 の言い換えは、呼び出し先が型パラメータの剛定数で、矢印でないときにも掛かる。
失敗の文面「スコープ付きの型が一致しません: ς1 と …」が `row_failure` の「スコープ付きの型」に一致するからである。
この失敗は行の失敗でも脱出でもなく、試作の後も残る(実測)。

```
q7_rigid_callee.kel:
module M {
  pub let f[F](g: F): Int32 = g()
}
HEAD、合成の木、試作のどれも:
! q7_rigid_callee.kel:2:31: 型エラー: pub な宣言はエフェクトを起こせません(@ を明示するか pub を外してください。元の報告: スコープ付きの型が一致しません: ς1 と _A => _B @ {})
pub を外すと:
! q7np_rigid_callee.kel:2:27: 型エラー: スコープ付きの型が一致しません: ς1 と _A => _B
```

run の中でも同じである(q7r、元の報告は `ς1 と _A => _B @ {Heap[ς2]}`)。
pub でなく注釈に `@ {}` を書いた形(q7e、`let f[F](g: F): Int32 @ {} = g()`)では、行が空の位置の言い換えが「この位置の行は空 = 純粋です…」を添える。
これも同じ原因の誤った言い換えだが、下書きの D[V44-3] は行が空の位置の言い換えを変えないとしている。

下書きの D[V44-1] は「スコープ付きの型が一致しません」を除かない理由に c2 を挙げる。
しかし c2 の報告は HEAD でも合成の木でも「は注釈で固定された行変数」を含む文面で、「スコープ付きの型が一致しません」を含まない(実測)。
したがって、その部分一致を残す根拠は c2 からは出ない。
また、「§11.12 の単一化の相手は新しい pvar と tr なので、レコードとヴァリアントの失敗は届かない」は正しいが、呼び出し先そのものが矢印でない形(剛定数)は届く。

直し方の案として、§11.12 の 2 つの言い換え(pub と行が空の位置)を、`open_closed_arrow` の後の `repr tf` が矢印のときに限る試作を作った(`verify/q7-guard.patch`、V44 の試作の上の差分)。
呼び出し先が矢印なら、相手の `pvar` と `tr` は新しい変数なので、落ちるのは行の単一化か脱出だけである(ソースを読んで導いた性質)。
この試作で q7、q7r、q7e は元の報告だけになり、`dune runtest` の差分は 0 行、担当の `ex/` の出力は V44 の試作と同じだった(実測)。

## 退行の探索

HEAD が受理して正しく実行するプログラムを 10 本書き、HEAD、合成の木、試作で走らせた(`verify/ex/`)。
- r01_alias_eff: 矢印のエイリアス(`@ {}` つき)で注釈した pub の値束縛。3 つとも 2。
- r02_rec_val: pub の値束縛と pub の `let rec` の値束縛。3 つとも 42 と 5。
- r03_run_heap: pub の関数と pub の値束縛の中の run と Ref。3 つとも 8。
- r04_tparam_row: 行の型パラメータを取る pub の関数と、入れ子の矢印に `@ {}` を書いた pub の値束縛。3 つとも in、3、20。
- r05_handler_guard: ガードつきの操作節と入れ子のハンドラを含む pub の関数と値束縛。3 つとも 15 と 2。
- r06_poly_val: 多相の関数で作る pub の値束縛、レコードとヴァリアントを返す pub の値束縛。3 つとも 2、7、A。
- r07_eff_explicit: `@ {Console}` を明示した pub の値束縛と `let rec`。3 つとも p と 0。
- r08_handle_in_pubval: pub の値束縛の初期化式の中の handle。3 つとも 101。
- r09_prelude: `--prelude` で差し替えたプレリュードで、run と pub の値束縛。3 つとも 6 と 6。
- imp/main.kel: `pub module` の pub の値束縛と `let rec` と run を import して呼ぶ。3 つとも 2、0、9。
REPL(`r10_repl.txt`)では、受理する行の出力は 3 つで同じで、pub の値束縛のレコードの失敗だけが試作で「注釈された型を満たしません」に変わる(意図どおり)。
退行は見つからなかった。
試作は、失敗した単一化の文言の選び方だけを変え、単一化の組と順序は `Unify.unify` の矢印の分岐と同じなので、受理の集合は変わらない(ソースを読んで導いた性質)。

そのほか、pub の値束縛の入れ子の引数の行に `@ {Console}` を書いた形(q5)は、試作で pub の言い換えから外れる。
`@` を書いた位置の失敗なので、これは意図どおりと読める。
run の中で外側の単相の Console の関数を呼ぶ形(q3、q3b、q3c)は、脱出より先に「ラベル Console」で落ち、試作でも pub の言い換えを保つ(実測)。

## 判断事項について

P[V44-1] の推奨案(両方を直す)に賛成する。
ただし範囲に q7 の形(呼び出し先が矢印でない剛定数)を加えるべきである。
台帳の詳述が求める「`row_failure` の判定と pub の言い換えの条件の両方を見直す」の範囲に入り、同じ箇所(§11.12)で 1 行の条件で直る。

P[V44-2] の推奨案に異論は無い。
見落とした代案として、`Unify` に矢印の頭の行の失敗だけを別の例外で知らせる入口(例えば行の単一化を呼び出し側の関数で包む引数)を足す形がある。
矢印の分岐を `elab.ml` に写さずに済むが、`Unify` の公開の関数が増える。
推奨案のリスク(分岐の写しが古くなる)は下書きが挙げており、ブロック 4 で固定しているので、推奨案のままでよい。
