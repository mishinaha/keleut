## 反証できた点

下書きの (3) は「`ie` が空でない理由は、注釈を書いていればその注釈、書いていなければ本体の推論である」と述べ、試作の記事は「最外の `@` を書いていなければ、実装の行は本体から推論したものなので、空でない行は本体が何かを起こしたことを意味する」と書く。
これは関数束縛では成り立つが、注釈の無い値束縛では成り立たない。
実測(`verify/ex/j1.kel`):

    newtype Box = Box(Int32)
    let sizeP(b: Box): Int32 @ Print = 1
    type class Sizer[T] { val size: (T) => Int32 }
    type instance Sizer[Box] { let size = sizeP }

HEAD と試作のどちらも、`j1.kel:4:32` で「インスタンスメソッド size の本体がエフェクトを起こしています。元の報告: ラベル Print がありません(行は閉じています)」を出し、終了コード 1 である。
`sizeP` の本体も `size` の初期化式も何も起こしていない。
行は `sizeP` の注釈に由来する。
`verify/ex/j2.kel`(`let size = { let g(b: Box): Int32 @ Print = 1; g }`)も同じである。
したがって、試作の後でも V33 と同じ種類の取り違え(何も起こしていないのに「本体がエフェクトを起こしています」)が値束縛に残り、記事の文はこの形で偽になる。
退行ではない(HEAD と同じ出力)。

もう 1 つ、注釈に行変数を書いた形では「空でない行を書いています」が字義どおりではない。
`verify/ex/h2b.kel`:

    newtype Box = Box(Int32)
    type class R4[T] { val r4[E]: (T, () => Unit @ E) => Unit }
    type instance R4[Box] { let r4[F](b: Box, f: () => Unit @ F): Unit @ F = () }

試作は「インスタンスメソッド r4 の注釈が空でない行を書いています。元の報告: 行 ς1 は注釈で固定された行変数なので、この行と一致させられません(注釈を extends 付きの形にしてください)」を出す(HEAD は「本体がエフェクトを起こしています」)。
注釈が書いたのは行変数 `F` で、引数の型を通して宣言の `E` に結ばれたために空にならない。
注釈が原因であることは正しいので、HEAD より改善しているが、「空でない行」という言い方は行変数の形を覆わない。

## 判断事項への意見

P[V33-1]: 推奨案(分岐)に反対はしないが、根拠の「書いていない形の文言は正しい」は値束縛で偽である(j1)。
代案として、`lb_params` が `None`(値束縛)で注釈が無い形を第 3 の文言(例「インスタンスメソッド size の値の型の最外の行が空ではありません」)にする案を挙げるべきである。
採らないなら、記事の文を「関数束縛で最外の `@` を書いていなければ」に狭め、値束縛の残りの形を記事か台帳に残す。

P[V33-2]: h2b のように注釈が行変数のとき「空でない行を書いています」は字義に合わない。
「注釈に `@ {}` 以外の行を書いています」は、ラベル、行変数、エイリアス経由のどれにも当てはまり、`@ {}` に直せることも示す。
推奨案を採るなら、行変数の形が字義から外れることを記事に書く。
