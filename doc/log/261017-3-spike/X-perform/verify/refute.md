## 実測の再現

担当の 16 例を 3 つの処理系で走らせ直した(`verify/ex3.txt`)。
各例の診断の文面と位置は担当の `results.head.txt`、`results.new.txt` と一致した。

ただし、下書きの 2 か所の記述は実測と合わない。

1 つ目は (7) の「`a1`、`r3`、`a8` だけに案内が付き」である。
試作では `a9` と `a15` にも案内が付く。
`a15` はリスクの節で認めているが、`a9` は触れていない。
`a9` の HEAD の出力は次のとおりで、§11.12 の案内は付かない。

```
! a9.kel:4:41: 型エラー: エフェクト Async2 をここでは実行できません(ラベル Async2 がありません(行は閉じています))
```

試作ではこれに「(この位置の行は空 = 純粋です — …§9)」が付く(P[X-perform-2] の分岐による)。

2 つ目は P[X-perform-2] の根拠の「関数呼び出しで同じ形(`a9`、nested2)は、呼び出しなら §11.12 の案内が付き、`perform` なら付かない不揃いが HEAD にある」である。
`a9` と nested2 はどちらも、関数呼び出しの引数の無名関数の本体で `perform` する形で、HEAD では案内が付かない。
HEAD の不揃いは、空の行の位置で「関数を呼ぶ」と案内が付き(`classes.t` の clsrow4 など)、「`perform` する」と付かない点にある。
表の `a9` の欄は「…」で末尾を省いているので、案内の有無が読めない。

## P[X-perform-2] の分岐の届く範囲

分岐は無名関数の本体に限らず、閉じた空の行の下のすべての `perform` に効く(実測、`verify/d.txt` と `verify/ex/d*.kel`)。

- `@ {}` と注釈した関数(efferr、`d4` の pub、`d8` の let rec、`d9` の module の中の pub): 案内が付く。
- `@ {}` の関数の中の handle の節の本体(`d5`): 案内が付く。
- インスタンスメソッドに `@ {}` と書いた形(`d11`): 案内が付く。
- トップレベルの値束縛と式(`d1`、`d2`): 変わらない。
- pub で `@` を省略した形(`d13`)、クラス宣言が純粋なインスタンスメソッド(`d3`): 変わらない(先の分岐が先に効く)。
- 行変数を注釈した形(`d10`): 変わらない。

関数を呼んだ場合の §11.12 の振る舞いとそろうので誤りではない。
下書きの D の文面と §11.15 の記事の最後の段落(「無名関数を引数に書いて、その本体で操作を起こす形がそうである」)は、この範囲を `a8` の形で代表させており、`@ {}` の注釈の形が主であることが読めない。

## litcheck の確かめ方

git archive の写しには `.git` が無いので、`python3 tools/litcheck.py` は全ファイルで「HEAD に同じファイルが無い」を出し、どの検査も走らない。
写しのコメントにわざと二重引用符を入れても、この呼び方では検出されなかった(`verify/lt`)。
したがって「litcheck の出力が V101 を当てた写しと同じ」は、何も検査していない出力どうしの一致である。
`python3 tools/litcheck.py --old <snap>/lib/elab.ml lib/elab.ml` で走らせ直すと、X-perform の写しは code の不一致(コードを変えたので当然)だけで、lex、block、width の失敗は無く、marker は 0 件だった。
二重引用符を入れた写しは、この呼び方で「284 行: コメントの中に " がある」と検出された。
結論は変わらないが、計画には `--old` での手順を書く。
`tools/litwrap.py lib/elab.ml` は X-perform の写しを変えなかった。

## 退行の探索

HEAD が受理する 11 本(`verify/ex/g1`〜`g7`、`g9`〜`g11` と REPL の 1 セッション)を 3 つの処理系で走らせた。
エイリアスで書いた操作の型(`g1`)、module の中の pub 関数とガード(`g2`)、import したエフェクト(`g3`)、関数とレコードを返す操作の `resume`(`g4`、`g10`)、関数のフィールドを持つレコードを引数に取る操作(`g5`、`g11`)、入れ子のハンドラの `resume(fn …)`(`g6`)、プレリュードの差し替え(`g7`)、行多相の関数の名前を `@ {}` の操作に渡す形(`g10`)である。
すべて出力と終了状態が 3 つで一致した。
REPL の `let z = perform p(fn() => echoln("y"))` の診断は V101 で位置と文面が変わるが、X-perform は V101 から変えない。
受理と拒否が変わる形は見つからなかった。
`fallback` の分解が `Unify.unify` の矢印の分岐と同じ順序であることは、`lib/unify.ml` 537〜564 行で確かめた(両辺が矢印なら `unbound_var` の分岐に入らず、矢印の分岐で引数、返り値、行の順に単一化する)。

## 判断事項の推奨案について

P[X-perform-1] の推奨案(関数呼び出しには添えない)に反対はしない。
ただし根拠の「出所を確かめる手段が単一化の後には無い」は、確かめる時点を単一化の前に置く代案を見落としている。
`T.Apply` では、`Unify.unify tf (TArrow (pvar, tr, eff))` の後、`elab_check env level eff arg pvar` の前に、宣言した仮引数の型が `pvar` の行に並んでいる。
この時点で、各 `_item` の型が閉じた空の行の矢印かどうかを記録し、その位置にだけ文言を渡せば、orderargs2(仮引数の型が `A`)は対象から外れる(推測。試作していない)。
`a2` の形(`take(g: () => Unit)`)は高階関数の普通の書き方なので、台帳に残すときは、この代案を添える。

P[X-perform-2] の推奨案に賛成する。
本文には、分岐が `@ {}` と注釈した本体、その中の handle の節、インスタンスメソッドにも効くこと(実測 `d4`、`d5`、`d8`、`d9`、`d11`)を書く。

P[X-perform-3] の推奨案に賛成する。
