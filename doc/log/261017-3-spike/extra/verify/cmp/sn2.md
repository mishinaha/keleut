#### (3) 判断と確定

判断事項 P[V50-1]: 略記の規則どおり `@ W` と `@ {W}` を同じに解決するか、現状を仕様に書くか。
- 推奨案: 型パラメータが、波括弧の中でも同名の EffectRow エイリアスを隠す。`@ W` と `@ {W}` はどちらも型パラメータを指し、後者は行変数を要素に置く形として拒否する。
- 代案 1: 現状を LangSpec §13.1 に書く(「行の要素では、エフェクト行の別名が同名の型パラメータより先に当たる」)。コードは変えない。
- 代案 2: `@ W` と `@ {W}` の両方で、エイリアスを型パラメータより先に引く。略記の規則は満たし、波括弧の中の受理(r01〜r13 など)は保つ。`@ W` の解決は変わる(a03 の `f` が `@ {Print}` になる)。
- 推奨の根拠:
  1. 規範 `doc/sample.kel:469` は `@ X` を `@ {X}` の略記とし、`:470` は行変数を `extends` の右に置くと定める。名前ごとに 2 つの形が同じものを指すことが前提で、代案 1 はこの略記が別名と型パラメータの組でだけ成り立たないと書くことになる。
  2. 型の位置、`@ W`、`@ W[E]` は、どれも型パラメータを先に引く(§11.3 の「内側の `[A]` は外側の型構成子 `A` を隠す」)。LangSpec `:986` と sample.kel `:420` も、型パラメータの名前の衝突では内側を優先すると定める。代案 2 はこの内側優先を、エフェクト位置でだけ外側優先に変える。
  3. 引数なしのエフェクト名では、HEAD でも両方の形で型パラメータが先に当たる(a07、a08)。推奨案はエイリアスをこれと同じ扱いにし、代案 2 は逆にする。引数つきのエフェクト名では両方の形でエフェクトが先に当たる(a15、b09)が、これも 2 つの形が揃っているので略記の規則とは食い違わず、本項では変えない。
  4. 代案 1 のもとでは、1 つの行の中で同じ綴りが別のものを指し(a16)、型パラメータが使われないことでカインドが Type に決まり、利用箇所で無関係な診断になる(a11)。
  受理していたプログラムを拒否する変化である。
  該当するのは、型パラメータと EffectRow エイリアス(またはそのコンパニオン)が同名で、型パラメータの有効範囲の波括弧の中にその名前を書いた形だけである(反証者の 15 本 r01〜r15、b04、b06 はすべてこの形。実測)。
  diktor の cram、`test/sample/sample.kel`、プレリュード、LangSpec の例には、V57 が足した visrow26 のほかに該当が無い(実測: 試作で `dune runtest` の差分は visrow26 の 1 コマンドだけ。LangSpec と sample.kel の EffectRow エイリアスは `Output` と `Request` だけで、プレリュードには無く、同名の型パラメータも無い)。
  回避は、型パラメータの名前を付け替えること(LangSpec §18.1)である。module のエイリアスは修飾名 `M.W` で書けば型パラメータに覆われない(a17、b02、b03、実測)。

D[V50-1]: エフェクト位置で、修飾していない名前が型パラメータなら、引数なしでも引数つきでも、同名のエイリアス(EffectRow エイリアス、Type エイリアス、それらのコンパニオン)を引かない。
`T.BLabel` の処理では、型パラメータで引数なしなら「行変数 n は extends の位置にのみ書けます」で落とし、引数つきなら `find_alias` を飛ばして effect の宣言表へ進む。
effect の宣言表にあればそのエフェクトを指し(a15、b09。HEAD と同じ)、無ければ HEAD で別名の無い `{F[E]}`(a10)と同じく「未知のエフェクト: W」になる。

判断事項 P[V50-2]: `{W}` の診断に、型パラメータが同名のエイリアスを覆っていることの案内を添えるか。
- 推奨案: 添えない。文面は別名の無い形(a09)と同じ「行変数 W は extends の位置にのみ書けます」にする。
- 代案: 同名のエイリアスがあるときだけ「(同名の EffectRow エイリアス W は型パラメータ W に覆われます)」を添える。
- 判断の材料:
  1. 型の位置で型パラメータが型を覆うときも案内は出さない。案内は、エフェクト位置でだけ覆う規則を特別扱いすることになる。
  2. 案内のためには、拒否の経路で `find_row_alias`(またはコンパニオンも含めるなら `find_alias`)を引き直す必要が生じる。推奨案のコードは型パラメータのときにどちらも引かないので、案内はこの経路を足すことになる。
  3. 代案に有利な材料として、本項は受理していたプログラムを拒否に変える(r01〜r15、REPL を含む)。移行の手がかりとしての案内の価値は、振る舞いの変わらない型の位置より高い。
  4. 推奨案に有利な材料として、診断は型パラメータの名前と位置を示し、回避(型パラメータの名前の付け替え)は 1 か所の変更で済む。該当する形は cram、sample、プレリュードに visrow26 のほかに無い(実測)。
- 推奨の根拠は 1、2、4 である。3 は所有者が代案を選ぶ理由になりうるので、判断の材料として残す。代案を採る場合も、規模は S のまま(診断の文字列の分岐と cram の期待値 4 コマンド)と見込む(推測。試作はしていない)。

#### (4) 仕様側の改訂案

LangSpec §13.1 の `doc/LangSpec.md:1116`(「開いた行の別名も使えるが、…」)の後に、次の段落を足す(実測: a03、a04、a07〜a09、a15、a17、b05、b09、visrow26〜visrow30)。

```markdown
型パラメータの有効範囲では、引数を付けずに書いた型パラメータの名前は、`@` の直後でも行の要素でも型パラメータを指し、同じ名前のエフェクトやエフェクト行の別名を指さない。
`W[E]` のように引数を付けて書いた名前は、`W` が型パラメータなら同じ名前のエフェクト行の別名を指さず、同じ名前のエフェクトがあればそのエフェクトを指す。
行変数は行の要素には書けず、`extends` の右に書く。
そのため、型パラメータ `E` を `@ {E}` や `@ {Print, E}` と書くと、同じ名前のエフェクト行の別名があっても型検査に通らない。
この規則は、§15.1 のモジュールの `EffectRow` の別名にも及ぶ。
モジュールで修飾した別名 `M.E` は、型パラメータに覆われない。
```

§15.1(`doc/LangSpec.md:1479-1482`)は、エフェクト行を書く位置でモジュールの `EffectRow` の別名が標準環境のエフェクトとトップレベルの別名より優先すると書く。
新しい段落の 5 文目でその上に型パラメータがあることを示すので、§15.1 の文面は変えない。

規範 `doc/sample.kel` は変えない。
`:469` の略記の規則と `:470` の行変数の書き方を実装が満たすようになるだけで、規範の文面と食い違わない。
`test/sample/sample.kel` の同期も要らない。

#### (6) リスク

- 受理から拒否への変化: (3) の形だけである。反証者が書いた 15 本(import した pub エイリアス、pub な関数、handle、ガード、型クラス、ラムダの引数、module の pub、エイリアスのパラメータ、newtype、引数つき、`extends`、局所関数、pub なコンパニオン、局所の値束縛の注釈、REPL)は、HEAD で正しく実行し、試作で位置つきの型エラーになる(r10 は「未知のエフェクト: W」、ほかは「行変数 W は extends の位置にのみ書けます」)。どれも意図した拒否で、分類の外の退行は見つからなかった。
- REPL では拒否しても終了コード 0 のままで、拒否された宣言の名前を後の入力で使うと「未束縛の変数」が続く(r15)。REPL の既存の振る舞いで、本項では変えない。
- 型パラメータの有効範囲の判定: `env.types` は関数、newtype、エイリアス、型クラスのメソッドの型パラメータを含む。a11(newtype)、a12(エイリアスのパラメータ)、a18(内側の let)、a19(メソッドの型パラメータ)は、どれも新しく行変数の診断になる(実測)。a18 は外側の関数の型パラメータが内側の let の注釈まで届く形で、型の位置と同じ有効範囲である。インスタンスの型パラメータとクラス宣言の `@ {W}` の組(r14)は変わらない(実測)。
