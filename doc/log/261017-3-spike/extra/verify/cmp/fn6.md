#### (3) 判断と確定

判断事項 P[V48-1]:値の無い型を受けるパターンの警告を、どの規則で揃えるか。

- 推奨案(C):行が 1 つのエントリ(関数とラムダの引数、`let` のパターン束縛、return 節、節が 1 つの `match`)は、受ける型に値が無ければ、網羅漏れも一致する値が無いことも報告しない。
  判定は型の側で行い、パターンの形を見ない。
- 代案(A):直さない。224c98c のコメントのまま残す。
- 代案(B):`irrefutable_pat` による選別をやめ、すべての引数パターンを積む。
- 推奨の根拠:C では、行が 1 つの位置に値は来ないので、照合が失敗して実行時エラーになることもない。報告しても利用者が直すべきものが無い。
  C の試作では、`ex/` の 11 本で警告がパターンの形によらず揃い、`run.kel` は `--strict-exhaustive` でも `42` を出して終了状態 0 になる(実測、`results.proto2.txt`。表を足す前の試作の `results.proto.txt` と同一)。
  `irrefutable_pat` を常に偽にして C と組み合わせたビルドでも、`dune runtest` と `ex/` の出力は C と一致した(担当と反証者の実測)。選別は C の後は節約だけになり、警告の有無を変えない。
  A は台帳の非一貫性と、値の無いデータ型を警告なしに消去できないことを残す。
  B は合成の木で 6 ファイル、HEAD の上で 3 ファイル(`typecheck_sample.t`、`typecheck_m5.t`、`typecheck_m7.t`)の cram を落とす(反証者の実測)。`let absurd[A](n: Never): A = n match {}` の引数にも警告が出て(`results.altB.txt`)、しかも変数で受ける `Absurd`(pa)には出ないので、形による差も消えない。

D[V48-1]:値があるかどうかの判定 `inhabited` は、`complete_sig`(§10.7)と `sub_types` で決める。
シグネチャが `None` の型(基本型の `Int32` や `String`、関数型、型変数、型パラメータ、開いた行の構造的ヴァリアント、組み込みの不透明型 `Ref`、`Array`、`MutableArray`)は値があるとみなす。
シグネチャがあれば、どれかのコンストラクタ(レコードは唯一の形、閉じたヴァリアントは各ケース、`Boolean` は 2 つのリテラル)について引数の型すべてに値があるとき、値がある。
再帰するデータ型で同じ名前に戻ったら、値があるとみなして打ち切る(型引数が育つ `newtype N[A] = C(N[(A, A)]) | D(A)` でも停止する。`ex2/grow.kel` で HEAD と同じ出力、実測)。
加えて、1 回の判定の中で調べ終えたデータ型の結果を、型引数まで含めた鍵(`ty_key`)の表に覚え、同じ型を 2 度は開かない。
表が無いと、`T(i) = A(T(i+1)) | B(T(i+1))` の形で段数に対して指数の時間がかかる(反証者の実測で 26 段 28.57 秒)。
表に置く値は、打ち切りで値ありとみなした結果も含む。
値が無いという結果は、仮定を値ありの側に置いても値が無いと出たものなので、文脈によらず正しい。
値ありの結果は、文脈によっては値が無いと言えた型を値ありとすることがあるが、それは警告を出す側に倒れるだけである(ソースから導いた性質)。
代案:宣言表に対して値の有無の不動点を宣言時に求めておく。正確だが、型引数を持つ型は具体化ごとに答えが変わるので、宣言時の表では足りず、引数の具体化の扱いを別に決める必要がある。推奨しない。

D[V48-2]:判定は `close_variant_rows` の後に置く。
行を閉じるのは型推論への副作用なので、警告を出さないエントリでも従来どおり閉じる。

D[V48-3]:節が 2 つ以上の `match` は対象にしない。
値の無い型を照合する節(`k2`)と、ペイロードの型に値の無いケースの節(`k3` の `case #Err(e)`)は、§10.11 のとおり到達できない節と報告する。
V134 の D[V134-3] が前提にする振る舞いと同じである。
判断の材料:このもとでは、`Never` に 2 節を書くと第 1 節も到達不能と報告され(`k2`、`elim.kel` の e6)、1 節なら警告が出ないという差が残る。
節を 1 つ書くのは消去の書き方として意味があり、2 節目を書くのは冗長なので、この差は受け入れる。

D[V48-4]:コンストラクタを持つ値の無い型に対する節のない `match {}`(`k4`)は本項で変えない。
§11.2 の 916 行は、`match {}` を網羅的とする型をコンストラクタを持たない型に限っている。
消去は `case MkA(n) => n match {}` か引数の `MkA(n)` で書け、本項の後はどちらも警告が出ない。

#### (6) リスク

- 警告の減少:値の無い型を受ける 1 つのパターンの警告は、本項の後は出ない。値があると思って書いたフィールドが実は値の無い型だった、という誤りの手掛かりが減る。その型の値を作る式は型エラーになるので、誤りはそちらで見つかる(推測)。
  反証者の 13 本(エイリアス、module、pub、import、型パラメータ、ガード、入れ子のハンドラ、構造的ヴァリアント、リテラルを含むタプル、操作節、インスタンス、`--prelude` の差し替え、REPL)で、警告が消えたのは受ける型に値が無い場合だけだった。表を足した後の試作でも出力は同一である(実測、`x.proto2.txt`)。
- `inhabited` の停止と時間:データ型は名前で打ち切るので停止する。構造的な型(レコード、ヴァリアント)はデータ型を経ずに再帰しない(Keleut に構造的な再帰型は無いとソースから読んだ)。
  時間は表で抑える。反証者の 24 段と 26 段、自作の 26、60、200 段の 3 形(値が無い型で終わる形、値がある型で終わる形、`T0` に戻る形)は、どれも 0.01 秒以下で、出力は HEAD と同じ `ok` だった(実測、`ex2/timing.txt`)。
  表の鍵は判定のたびに型を文字列に書き出すので、大きな型引数を持つ型では鍵の作成に型の大きさに比例する時間がかかる(ソースから導いた性質)。
- 表と打ち切りの組み合わせで、打ち切りの仮定のもとで値ありと出た結果を、別の経路でも使う。これは値ありの側(警告を出す側)への偏りで、値の無い型を値ありとすることはあっても、その逆は起きない(ソースから導いた性質)。
- V136 と V129 との順序:(1) のとおり。後に入れる側が期待値と字下げを合わせる。

#### (7) 検証の観点

- 行が 1 つの位置(関数の引数、`let rec` の引数、ラムダの推論と検査の両方、`let` のパターン束縛、return 節、節が 1 つの `match`)のそれぞれで、値の無い型を変数、`_`、レコード、タプル、コンストラクタ、ヴァリアントで受けても警告が出ないこと。

- 段数の多い型で時間が増えないこと(deep、`ex2/blow_*.kel`)。
- ガード付きの節が 1 つだけの `match` を値の無い型に書いたときに警告が出ないこと(`guard.kel` の g1)と、値のある型では従来の網羅漏れが残ること(g4)。`let rec` の群の引数(g2)も警告が出ないこと。

- 仕様の段落が `results.proto2.txt` と `ex2/valued.out` の実測と合うこと。
