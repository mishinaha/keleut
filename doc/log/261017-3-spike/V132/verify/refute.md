## 1. 行変数だけの宣言の下の実装は純粋ではない(内容の誤り)

下書きの §12.2 案の 4 文目「宣言の行が `@ E` のように行変数だけのときも、実装はどの `E` でも通らなければならないので、エフェクトを起こせない」と、D[V132-1] の「宣言の行が行変数だけのメソッドの実装は純粋である」は、実測と合わない。
実装は、引数で受け取った関数を呼ぶことで `E` のエフェクトを起こせる。
ex/cb.kel(宣言 `val run1[E]: (A, (A) => Int32 @ E) => Int32 @ E`、実装は `f(x)`、呼ぶ側が `perform throw` するラムダを渡す)は HEAD で `caught boom`、`-1`、終了状態 0 である。
ex/functor.kel(LangSpec §12.3 の 1002〜1013 行の `Functor[List[_]]` の例そのもの)でも、`map` の実装が `f` を通して `Fail` を起こし、`caught two`、`[]`、終了状態 0 である。
つまり 4 文目は、同じ LangSpec の §12.3 の例と矛盾する。
言えるのは「実装は自分の本体で特定のラベル(`Fail` など)を起こせず、引数の関数から届く `E` を通すだけである」までである(ex/generic.kel と test/classes.t の clsbarerow、clsargpure)。
D[V132-3] の台帳の要約の言い換えも同じ理由で「自分では失敗を起こせない」と限定する必要がある。

## 判断事項について

P[V132-1] の推奨(緩めない)に異論は無い。
ただし、純粋なメソッドで失敗を扱う回避の形に、ex/inner.kel の形(メソッドの返り値の関数の行に `Fail` を書く)が抜けている。
§12.2 案の最後の文に足すか、足さない理由を書くとよい。
代案 B の根拠の「行変数への制約の禁止を変える」は、関連する行をクラスに持たせる設計が行変数への制約を要するとは限らないので、根拠としては弱い。
「複数パラメータか関連型という新しい機構が要る」で足りる。

P[V132-2] の推奨に異論は無い。
