測った値と決めた値は次のとおりである(詳細は `doc/log/261024-2-m79.md` の 1 節と 2 節)。

- 1 段のバイト数は、引数 1 個の関数では、最悪の層の Liftoff で `8 × K + 64` である(K は局所の数)。
- KIR の WasmGC の関数の型の形(クロージャ、N 個の `eqref`、フレームの P = N + 2 個の引数)で、引数を呼び出しに渡す関数の 1 段は、P が 4 以下では引数 1 個あたり 8 バイト、P が 18 から 66 では 1 個あたり 24 バイト増える。
  測った 14 の組のすべてで、1 段は `8 × K + 24 × P + 64` 以下だった。
- `--stack-size` の上限は 2,097,151 KiB である(V203)。
  2,097,152 KiB 以上は使えない。
  `Worker` の `stackSizeMb` は、試した最大の 16,384 まで使えた。
- `B_wasm = 1536` バイト、`--stack-size = 1,630,208` KiB、`S = RLIMIT_STACK = 1,695,744` KiB、`L = 2^20` である(V198)。
  フレームの大きさの推定は `8 × K + 24 × P + 64` バイトとした。
  推定がちょうど 1,536 バイトの関数(N = 0、10、59)も、すべての層で `L + R` 段に届いた。
- V8 の WasmGC の配列の長さの上限は、i8 で `2^30 − 32`、`eqref` と `i64` で `2^27 − 8` である。
  超えると `RuntimeError: requested new array is too large` で trap する。
  `N_alloc_max = 2^26 = 67,108,864` に決めた(V215)。
  要素の幅ごとに上限を分ける案と、`2^27 − 8` とする案は採らず、所有者が覆す余地として測定の記録に書き残した。

計画からの逸脱は次のとおりである。

- `--stack-size` に渡す値を、計画 6.10 節の `S` の 90% から `(L+R) × B_wasm + 32 MiB` に改め、`S` を `--stack-size + 64 MiB` にした。
  90% の式では、`(L+R) × B_wasm` が 576 MiB を超えると、V8 に渡す限度が `(L+R) × B_wasm` より小さくなる。
  実際に、計画の式で `B_wasm = 2048` とした設定(`ulimit -s 2195456`、`--stack-size=1975911`)では、1 段が 2,048 バイトの再帰が 987,952 段で `RangeError` になり、`L` に届かなかった。
  計画の確かめ方(「`S` の 90% が上限を超えない」)はこの設定で通るので、確かめ方そのものが誤りを見逃す。
  M94 の Node の起動(計画 6.10 節、D545)は、改めた式で実装する必要がある。
- `B_wasm` を、計画 6.10 節の初期値 2 KiB でなく 1,536 バイトにした。
  `(L+R) × 2048 = 2,129,920` KiB だけで `--stack-size` の上限を超えるためである。
  計画 6.10 節の選択肢のうち、`Worker` の経路より先に挙がっている「`B_wasm` を下げる」を採った。
  `Worker` の経路は `stackSizeMb` 2,176 で `B_wasm = 2048` も満たせるので、代わりの経路として残る。
- フレームの大きさの推定を、計画 6.10 節の「局所の数 × 8 + 定数」から `8 × K + 24 × P + 64` に改めた。
  はじめは `8 × (P + K) + 64` としていたが、検証で、引数を呼び出しに渡す関数では引数 1 個が最大 24 バイトを使うことがわかった。
  たとえば P = 18、K = 150 の関数は、元の推定では 1,408 バイトだが、1 段は 1,568 バイトで `B_wasm` を超える。
- 大きなフレームの形(計画 6.10 節)は局所だけを移すので、引数が 62 個以上(N が 60 以上)の関数は、その形でも 1 段が `B_wasm` に収まらない。
  計画はこの場合を扱っていない。
  M94 は、超えた引数を GC の構造体にまとめて渡す形を足す必要がある。

## M80 入れ子の resume の修正(V191)

行ったことは次のとおりである。

- `diktor/lib/interp.ml` の `eval_handle` の `T.Resume` の枝(節本体が `resume` そのものである短い経路)を直した。
  `r` を `r_used = false` で作り、引数を評価した後で `r_alive` と `r_used` を調べてから `r_used <- true` にする。
  順序は `take_resume` と同じである。
  引数が無い `resume()` の枝では、再開の前に `r_used <- true` にする。
- 同じ経路の例外の枝を、背骨をたどる経路と同じ `if r.r_used then raise ex else Effect.Deep.discontinue k ex` に改めた。
  引数の中の入れ子の `resume` が継続を再開した後なら、例外をそのまま送り出す。
- 短い経路の注釈、§14.9 の記事の段落、`take_resume` の注釈、`Resume` の分岐の箇条を、この振る舞いに合わせて書き直した。
- `diktor/test/resume_guard.t` に 2 つのブロックを足した。
  `nestresume.kel`(`case ask(n) => resume(resume(n))`)は `cont saw 1`、アフィン性の実行時エラー、`[3]` を固定する。

  期待値だけの変更はこのファイルだけであり、実装のコミットとは分ける。
- LangSpec §13.5 に「`resume` は先に引数を評価し、その後で継続が再開済みであれば実行時エラーになる」の 1 文を足した(P235)。
- LangSpec §13.6 の、再開する操作の節で `cancel` 節を実行するかどうかの規則を、継続を再開したかどうかで分けるように改めた(下の逸脱を参照)。

測った値は次のとおりである。
fx の試料(`doc/log/261024-1-spike/probe/fx/`)を、修正の前(diktor 7fd4517)と後の Diktor で走らせた。

最後の行の前の振る舞いは、短い経路が内側の `resume` を外側の `r` の消費済みの印で落とし、例外の枝で継続を捨てていたためである。

計画からの逸脱と、計画が決めていなかった点は次のとおりである。

- `nestresumediv.kel` の操作は `ask: () => Int32` と宣言した。
  計画 9 節の M80 の行が書く節の形 `case ask() => …` は引数を持たないので、`nestresume.kel` と同じ `ask: (Int32) => Int32` では「操作 ask は 1 引数です(節には 0 個書かれています)」の型エラーになるためである。
- LangSpec §13.6 の 3 つの文を改めた。
  計画は §13.5 の 1 文だけを足すとしていた。
  §13.6 は「`resume` を呼ぶ前(`resume` の引数の評価中を含む)」の実行時エラーで `cancel` 節を実行するとしていたが、引数の中の入れ子の `resume` が継続を再開した後は、同じ段落の最後の文(`resume` が戻った後は実行しない)とも食い違い、Diktor は後者のとおりに動く。
  そこで、`cancel` 節を実行する条件を「継続を再開する前(`resume` の引数の評価中で、その中の `resume` がまだ継続を再開していない場合を含む)」に狭め、実行しない条件に「外側の `resume` の引数の評価中で、その中の `resume` が戻った後を含む」を足した。
  §13.5 の文と同じコミットに入れる。

### 受け入れの検査の指摘による修正

受け入れの検査が 16 件の指摘を出し、すべて反証されずに残った。
次のとおり直した。
指摘の番号は検査の記録のものである。

1. **単位の鍵の重なり**(accept-1-1、spec-1-1、spec-1-6):起点のファイルのディレクトリが基準のディレクトリ `B` の下に無いと、その綴りがそのまま鍵のディレクトリになり、別のファイルが同じ鍵を持った。
   シンボリックリンクの下の `..` でも、綴りの相殺と OS の解決がずれて同じことが起きた。
   `driver.ml` の `unit_keys` を次のように直し、IRSpec 2.2 節を合わせた。
   - 起点のディレクトリは、`B` からの相対パス(共通の先頭を除き、`B` の残りの数だけ `..` を置く)にした。
     一方だけが絶対パスのときと、`B` の残りに `..` があるときは、両方の `realpath` から同じ規則で作る。
     `diktor a/m.kel c.kel` がどちらも `./w` を import すると、鍵は `w.kel` と `../w.kel` になる。
   - 正規化は先頭の `/` を残さない。
     起点を絶対パスで書いても鍵は変わらず、機械に依存する綴りが記号に入らない。
   - `..` を相殺しない印は、先頭の成分で `@` と数字だけからなるもの(検索パスの印)に限った。
     実在のディレクトリ `@foo` の下の `..` は相殺する。
   - 鍵を決めた後で、別のファイルが同じ鍵になっていないかを調べ、なっていれば「KIR の単位の鍵が重なります」と出して 64 で終える。
     終了状態は、ファイルの配置とコマンド行による誤りなので、使い方の誤りの 64 にした。
     4(未実装)は構文の未対応に使い、この受け入れの「終了状態 4 で拒むものは無い」と混ぜないためである。
2. **`--emit-ir-text` とほかのモードの併用**(accept-1-2):`--type-check` などと併せると、旗が黙って無視されていた。
   `parse_args` で、`Run` 以外のモードとの併用を使い方の誤り(64)にした。
   `driver.ml` の旗の表にも書いた。
3. **`runtime` の印**(fidelity-1-1):`--no-prelude` で起点が宣言した `Console` の `write` に `runtime` を付けていた。

- 既定の限度で、`f(1048575)` と、辞書を受け取る関数の深さ 200 万の再帰は、どちらも OCaml のスタックを使い尽くさずに深さの限度の文面で 3 になった。
  木の評価器は後者を最後まで走らせて 0 で終わる(IRSpec 11.5 節の、処理系に任せた限度の差)。
- 深さ 100 万の非末尾の再帰は、木の評価器の 3.2 秒に対して 4.2 秒、300 万回の末尾呼び出しのループは 1.4 秒に対して 0.6 秒だった。
  非末尾の再帰の時間の大半は、深いスタックを走査する GC である。

計画からの逸脱と、その理由は次のとおりである。

1. 計画 5 節は、`ir_eval` が `value.ml` を共有するとしていた。
   評価器は自分の値の型を持ち、`value.ml` からは `float_repr`、例外、`Op` だけを使う。
   `Value.t` のクロージャは精緻化木の本体と環境を持つので、KIR のクロージャを入れるには `VPrim` に包むしかない。
   包むと、診断の印字が `<fn>` でなく `<prim …>` になり、実行時エラーの文面が木の評価器と食い違う。
   プリミティブは数と文字列しか受け取らないので、`builtin.ml` の表を呼ぶときだけ値を写す。
2. 計画 5 節は、深さを明示の計数器で数えるとしていた。
   評価器は、深さを各フレームの欄に置き、末尾でない呼び出しのたびに 1 つ深いフレームを作る。
   数える境目と値は IRSpec 11 節のとおりで、呼び出しから戻ったときと例外で抜けたときに数を書き戻す処理が要らない。
   `handle` を評価する段では、再開での深さのずれ(IRSpec 11.4 節)のために、フレームの深さを囲むハンドラの起動からの差で持つ形に改める必要がある。
3. IRSpec が決めていない深さの数え方を、次のとおりにした。
   組み込みの値は、それを呼んだ `call` の呼ばれた側の深さで走り、利用者の関数をその 1 つ深いところで呼ぶ。
   付録 A.4 の「呼び出しの位置の深さ + 2」は、組み込みを末尾でない呼び出しで呼んだときにこれと一致する。
   メソッドの値の呼び出しでは、辞書を受け取る実装の本体の評価と、得た値の呼び出しを、どちらも呼ばれた側の深さで行う。
   構造的な `Eq` は、フィールドを比べるたびに、フィールドの辞書のメソッドを末尾でない呼び出しとして呼ぶ。
   `extern` への `dictapp` と、プリミティブへの末尾でない呼び出しも、深さを 1 つ増やして限度と比べる。
   これらは IRSpec に書く問いとして残す。

残したことは次のとおりである。

- `handle` の評価(M83)。
- ドライバの旗の結線と、`test/ir_run.t`、`test/ir_depth.t`、`test/ir_tables.t`、`@runtest-via-ir`、`test/via-ir-exclude.txt` は、ドライバと試験を持つ段が行う。
  dune は環境変数を依存として追わないので、`@runtest-via-ir` の規則に `DIKTOR_VIA_IR` を依存として書かないと、普段の `dune runtest` が `--via-ir` の結果を使い回す(作業領域の写しで起きた)。

計画からの逸脱と、その理由は次のとおりである。

1. 計画 5 節は、`@runtest-via-ir` で cram を `DIKTOR_VIA_IR=1` で走らせ、ブロックを `via-ir-exclude.txt` で除くとしていた。
   dune の cram は `.t` のファイルを単位にしか除けず、規則が作った `.t` も走らせない(`(cram (applies_to …))` を付けても走らないことを確かめた)。
   そこで、別名を cram の stanza でなく規則にし、cram と同じ形で走らせる `via_ir_run.py` を足した。
   除外の単位は、ブロックでなくコマンド(`.t` の中の `  $ ` の行の番号)にした。
   ブロックの境目は cram の文法に無く、同じ `.kel` の名前が別のファイルにも現れるからである。
2. 作業の指示は、除外の一覧に handle に届くブロックだけを載せるとしていた。
   計画 5 節は、`OCAMLRUNPARAM` で OCaml のスタックを絞るブロックも理由つきで除くとしている。
   計画に従って両方を載せ、種類を理由の欄で分けた。
3. 環境変数 `DIKTOR_VIA_IR=1` を `--via-ir` と同じに扱うのは、旗の無い `Run` のモードだけにした。
   別名は全部の `.t` を同じ環境で走らせるので、`--type-check` や `--repl` や `--emit-ir-text` まで切り替えると、KIR の経路と関係の無い差が出るからである。
   旗の `--via-ir` は、ほかのモードの旗と併せると 64 にした。
4. 符号化の誤りのうち UTF-8 でない名前以外のものは、計画にも IRSpec にも終了状態が無く、作業の指示は 70 を勧めていた。
   第16章の終了状態の表には 70 が無く、内部の不具合は 3 に数えるので、`bug` を通して 3 にした。
5. UTF-8 でない名前を 64 で終える経路に CLI から届く入力は無いと考え、cram で確かめなかった。
   この判断は誤りで、2 つ目以降の起点のファイルを UTF-8 でない名前のディレクトリに置くと、そこから import した単位の鍵がディレクトリの綴りを含む(IRSpec 2.2 節)。
   受け入れの検査の指摘で、この入力を `test/ir_run.t` の最後のブロックに足した(下の「受け入れの検査の指摘による修正」)。
6. `--max-depth` は、どのモードでも受け付け、木の評価器では効かない。
   環境変数で `--via-ir` になる実行と、ならない実行で、旗の正しさが変わらないようにするためである。
7. `--run-ir` が読むのはバイナリだけである。
   計画 4.12 節のとおり、テキストを読む機能は RustKeleut の `keleut kir asm` だけが持つ。
   `.kirt` を渡すと、マジックの検査で 65 になる。

残したことは次のとおりである。

- 除外の一覧の `handle` の 106 個と、`stack` の 12 個の「handle にも届く」の印は、M83 で handle を評価できるようにしてから消す。
- `ir_depth.t` の handle を含むブロック(`cancel`、予備、G、`c ≠ h` の再開)は M83 で足す。
- `ir_run.t` の handle に届くブロックは、M83 で期待値が変わる。

### 受け入れの検査の指摘による修正

受け入れの検査は、検証を通った `.kir` が KIR の評価器の内部の不具合の経路(`[BUG]` の文面で 3)に届く例、IRSpec の規則の欠け、文面の誤りを 13 件指摘した。
すべて直した。
行ったことは次のとおりである。

- `diktor/lib/ir_check.ml` の検証に、次の規則を足した。
  どれも型を使わずに名前と個数から計算できる。
  - 組み込みの表:types、classes、globals の表の先頭が付録 A.1、A.2、A.4 の項目をその順に持ち、ほかに単位の鍵が `builtin` の項目と種類が `builtin` の大域が無いこと。
    比べる相手は書き手の `Ir_write.builtin_types`、`builtin_classes`、`builtin_values` そのものである。
    これまでは `builtin/Array.fach` のような記号の組み込みの値が検証を通り、評価器がリンクのときに `[BUG]` で 3 になった。
  - 操作の印:`runtime` の印は `prelude/Console` の引数が 1 個の `write` にだけ、必ず付くこと。
    `runtime` の操作を持つエフェクトを `handle` しないこと。
  - スロットの有効範囲:`local` は、式としても捕獲としても、束縛の有効範囲(IRSpec 6.4 節)の中でだけ読むこと。
    `match` の後の節が、前の節のパターンで束縛したスロットを読むことも拒む。
  - 辞書のクラス:`method` と `opcall` の `d` の `dinst` と `dbuiltin` のクラスがそのクラスと同じで、`drecord` と `dvariant` が `builtin/Eq` の位置にだけあること(構造的な辞書の項目にも同じ規則を当てる)。
    どの位置の `dbuiltin` も、組が付録 A.3 にあること。
    A.3 の組は、評価器が引く第13章の実装の表 `Builtin.builtin_method_table` のキーから作る。
  - `dictapp` の辞書の数:頭が `extern` の大域なら `dicts` の欄が 1 以上でそれと同じ数、`dictabs` の大域か `(dictabs F …)` なら `F` の `dicts` と同じ数であること。
    頭が種類 `fn`、`value`、`builtin` の大域なら拒む。
  - インスタンス:実装がクラスの各メソッドをちょうど 1 回ずつ持つこと。
- `diktor/lib/ir_write.ml` の `runtime` の印の条件に「引数が 1 個」を足した。
  `--prelude` で差し替えたプレリュードの `Console.write` の引数が 1 個でないとき、書き手の出す KIR を検証が拒まないようにするためである。
  同梱のプレリュードの出力は変わらない。
- `diktor/lib/driver.ml` の `--emit-ir-text` は、テキストを書く前にバイナリへ符号化し、UTF-8 でない名前があれば何も書かずに 64 で終える。
  `--emit-ir`、`--emit-ir-text`、`--via-ir` が同じ文面で 64 になる。
- `diktor/lib/ir_check.ml` の章の冒頭の規範の参照を 13.4 節から 13.8 節と 13.9 節に直し、性質の表に新しい規則を足した。
- `diktor/lib/driver.ml` の使い方の `--run-ir` の行の括弧書きを「入力の .kel とは併用できない」に改めた。
  `diktor/test/smoke.t` の同じ行も合わせた(期待値だけの変更)。
- `doc/IRSpec.md` を次のとおりに改めた。
  版と符号化は変えず、14 節の 0.3 の行に書き足した。
  - 6.4 節にスロットの有効範囲を、7.2 節に実装の項目の並びとクラスのメソッドを覆うことを、7.5 節に `dictapp` の辞書の数を書いた。

  - 12.5 節の `runtime` の印に「引数が 1 個の」を足した。

| wasm32 版のバイト列の比較と `Buffer.compare` | 100,000 | 0 |
| 形の表と単純なモデル(Rust / JS) | 200,000 / 20,000 操作 | 0 |

- libm の入力と x86_64 版の結果は、M79 の `inputs.bin` と `native.bin` とバイト単位で一致した。
  glibc との差は M79 と同じく、`sin` 19,378 件、`cos` 17,818 件、`exp` 138 件、`log` 2 件で、どれも 1 ulp である(参考の値で、受け入れの条件ではない)。
- `rt.wasm` は 29,177 バイト、import は 0 個、FNV-1a(64 ビット)は `78b0b281bde17b8a` である。
  x86_64 の静的ライブラリは自身の外の記号を参照せず、定義する大域の記号はすべて `krt_` で始まる。
- debug の `cargo test -p keleut-rtcore` は 3.7 秒、`wasm_check.mjs` は 8.0 秒かかった。
  試験の profile は変えていない。
- 試験が誤りを捕らえることを確かめるため、`f64show.c` を 3 通りに壊して走らせ、元に戻した。

| 故意の誤り | fltcmp の差 | 境界の値の差 |
| --- | --- | --- |
| 下側の狭い区間を使わない | 109 | 510 |
| ちょうど半分を常に切り上げる | 500 | 10 |
| 区間の下端を常に含めない | 224 | 6 |

  2^-1022 を下側の区間が狭い値として扱う誤りは、差を生まなかった。
  この値の最短の表記はどちらの規則でも 17 桁になるので、この試験では 2 つの規則を区別できない。

計画からの逸脱と、計画が決めていなかった点は次のとおりである。

- fltcmp の `2f64.powi(-1074)` は、release では `5e-324` だが debug では `0.0` になる。
  そのまま移すと、生成する件数が release で 1,998,964 件、debug で 1,998,963 件になる。
  2 の冪をビット列から直に作るように移し、どちらの profile でも 1,998,964 件にした。
- glibc の基準は、fltcmp の `%.*g` の出力そのままでなく、Diktor の `float_repr` の手順を glibc で行ったものにした。
  整数には `%.1f`、それ以外は `%.*g` で桁数を探し、指数の `+` と先頭の 0 を落とし、必要なら `.0` を足す。
  LangSpec §16.2 の書式に合わせ、整数の境界の値も覆うためである。
- 旗には、計画 6.5 節のものに、M79 で要ると分かった `-fno-stack-protector`、`-nostdlibinc`、`-I` のパス、`-include shim/krt_names.h` を足した。
  `-O2` は profile に依らず固定する。
  `wasm-ld` には `-z stack-size=1048576` を渡す。
- 計画 6.1 節と 6.5 節は x86_64 の静的ライブラリを `cc` crate で組むとしているが、本実装は `cc` を使わない(下のレビューの指摘による修正を参照)。
- 計画が挙げていない入口を足した。
  `krt_f64_show_bits` は生のビット列を受け取り、NaN の符号と payload を JS の `Number` を通さずに wasm に渡す。
  `krt_scratch` はホストと wasm の間でバイト列を受け渡す 64 KiB の静的な領域を返す。
  `rt.wasm` は `__heap_base` も export する。
- 形の表の API は計画が決めていなかった。
  メモリは呼び出し側が渡し、表が満ちると `KRT_SHAPE_FULL` を返す。
  呼び出し側はより大きな表に写して続け、形の番号は変わらない。
  Rust の `ShapeTable` はこの拡張を自動で行う。
- 記号の試験 `tests/symbols.rs` は、試作の `ld -r` の手順の代わりに静的ライブラリに `nm` をかける。
  そのため PATH に `nm`(binutils)が要る。
- 親のリポジトリがライセンスを定めていないので、`Cargo.toml` に `license` の欄を置いていない。
- wasm32 の libm の比較は値を JS の `Number` で受け渡すので、M79 と同じく NaN はどの NaN とも一致するとみなし、payload が保たれるかは確かめていない。

### レビューの指摘による修正

レビューで確かめた 9 件の指摘を直した。

- x86_64 の静的ライブラリを `cc` crate で組むのをやめ、wasm32 と同じく build.rs から clang を直に呼んで 1 ファイルずつ組み、`llvm-ar crs` で `libkeleut_rtcore.a` にする。
  `cargo:rustc-link-search` と `cargo:rustc-link-lib=static=keleut_rtcore` も build.rs が出す。
  x86_64 の旗は共通の旗に `--target=<対象> -fPIC -fno-stack-protector -ffunction-sections -fdata-sections` を足したものである。
- `shim/krt_names.h` の FMA の検査を `#if defined(__FP_FAST_FMA) || defined(__FMA__)` に広げた。
  `-march=native` では `__FMA__` だけが定義され、元の検査では止まらなかった。
- `rt.wasm` と試験の入力の置き場を、`--target` や profile に依らず `<CARGO_TARGET_DIR か workspace の根の target>/rtcore` にした。
- `fltcmp-meta.json` と新しい `libm-meta.json` に、`rt.wasm` の FNV-1a(64 ビット)、profile、対象を書く。
  `wasm_check.mjs` は置き場とこの記録を毎回表示し、置き場の `rt.wasm` から計算し直した FNV-1a が記録と違えば失敗とする。
- `ShapeTable::with_capacity` が `Vec::as_ptr` の指す先に C から書かせていたのを、`as_mut_ptr` に直した。
- コメントと文書の誤りを直した。
  `ldexp` の n の範囲、`krt_shape_labels` の返すポインタの有効な期間、README の `krt_names.h` の説明、build.rs のスタックの保護の理由、`ShapeTable` が panic する条件である。
  `shim/` の 5 つのヘッダのコメントを日本語に改めた。

#### 計画との違い

計画の 6.1 節と 6.5 節は、x86_64 の静的ライブラリを `cc` crate で組むとしている。
本実装は `cc` crate を使わない。

理由は、`cc` 1.10.0 が環境変数 `CFLAGS`(と `HOST_CFLAGS`、`TARGET_CFLAGS`、対象ごとの `CFLAGS_<三つ組>`)を build.rs の旗の後ろに足し、これを止める設定を持たないことである。
clang は同じ旗の後のものを採るので、`CFLAGS="-O0 -ffp-contract=fast"` は 6.5 節の `-O2` と `-ffp-contract=off` を打ち消す。
wasm32 の側はもともと clang を直に呼んでいて `CFLAGS` を読まないため、2 つの対象の旗が警告なしに食い違う。
レビューでは、`CFLAGS="-march=native -ffp-contract=fast"` で x86_64 の libm の結果が変わり、wasm32 との比較で sin 3101 件、cos 3405 件、exp 138 件の差が出た。
`CFLAGS=-fstack-protector-strong` では、静的ライブラリが `__stack_chk_fail` を参照して記号の試験が落ちた。

6.5 節の旗をどの環境でも守ることが計画の意図に近いと判断し、両方の対象を同じ経路で組むことにした。
`cc` を使う者がいなくなったので、workspace の `Cargo.toml` から `cc = "=1.10.0"` の固定も除いた。
`Cargo.lock` には `keleut-rtcore` だけが残る。
道具は `KELEUT_CLANG`、`KELEUT_AR`、`KELEUT_WASM_LD` で替えられる。
既定の書庫の道具は `llvm-ar` なので、GNU の `ar` しか無い機械では `KELEUT_AR=ar` を渡す。

#### 修正後の確かめ

作業用の写しでは、次も確かめた。

- `CFLAGS="-O0 -ffp-contract=fast -fstack-protector-strong -march=native" HOST_CFLAGS=-fstack-protector-strong TARGET_CFLAGS=-O0 cargo test --release -p keleut-rtcore` が通り、その後の `wasm_check.mjs` も差が 0 件だった。
- clang に `-march=native` を足して組むと、`krt_names.h` の `#error` で止まった。
- `cargo test --target x86_64-unknown-linux-gnu -p keleut-rtcore` の後、置き場は `target/rtcore` のままで、`wasm_check.mjs` が通った。
- `libm-meta.json` の FNV-1a を書き換えると、`wasm_check.mjs` が終了状態 1 で失敗した。
