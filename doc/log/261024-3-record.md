### musl の libm(rtcore)

行ったことは次のとおりである。

- 上流の最新の版が musl 1.2.6 であることを確かめ、配布物の sha256 と署名を確かめた。
- `doc/log/261024-1-spike/rtcore/` に、`sin cos exp log` とその依存の 20 個のソースと、`COPYRIGHT`、`VERSION` を改変せずに写した。
  生成物の `out/` は `rtcore/.gitignore` で除いた。
  版、出所、sha256 は `rtcore/musl/SOURCE.md` に書いた。
- 最小の shim のヘッダ、記号を `krt_` で始まる名前にする `krt_names.h`、試験の駆動部(`test/native.c`、`test/check.mjs`)、`Makefile` を書いた。

### Node のスタックと WasmGC の配列(stack)

行ったことは次のとおりである。

- `doc/log/261024-1-spike/stack/` に、`depth.mjs`、`wk.mjs`、`bigframe.mjs`、`arraylen.mjs`、`wasmgen.mjs`、`README.md` を置いた。
  `depth.mjs` は `wasm/depth.mjs` を元に、`../wasm/out/tail.wasm` を `import.meta.url` からの相対パスで読むようにした。
  `wk.mjs` は `new URL("./depth.mjs", import.meta.url)` を `Worker` の `stackSizeMb: 1024` で走らせる。
- `bigframe.mjs` と `arraylen.mjs` は、Wasm のモジュールを `wasmgen.mjs` で JS のバイト列として組む。
  計画は `.wasm` の作り方を決めて書くよう求めていた。
  `.wasm` を読まないこの作り方にしたので、新しく clone した木からビルドなしで動く。
- 局所の数 64、256、1,024 に、比較のための 0 を足した。
  局所の型は `i64` と `eqref` の 2 つ、層は既定、Liftoff、TurboFan、インライン展開なしの TurboFan の 4 つを測った。
- 配列の長さの上限を測る `arraylen.mjs` を足した。
  計画は測ることだけを定め、置き場所を決めていなかった。
- `doc/log/261024-2-m79.md` に、ヘッダと 1 節と 2 節を書いた。
  3 節は musl の担当が書いた。

測った値と決めた値は次のとおりである(詳細は `doc/log/261024-2-m79.md` の 1 節と 2 節)。

- 1 段のバイト数は、引数 1 個の関数では、最悪の層の Liftoff で `8 × K + 64` である(K は局所の数)。
- KIR の WasmGC の関数の型の形(クロージャ、N 個の `eqref`、フレームの P = N + 2 個の引数)で、引数を呼び出しに渡す関数の 1 段は、P が 4 以下では引数 1 個あたり 8 バイト、P が 18 から 66 では 1 個あたり 24 バイト増える。
  測った 14 の組のすべてで、1 段は `8 × K + 24 × P + 64` 以下だった。
- `--stack-size` の上限は 2,097,151 KiB である(V203)。
  2,097,152 KiB 以上は使えない。
  `Worker` の `stackSizeMb` は、試した最大の 16,384 まで使えた。
- `B_wasm = 1536` バイト、`--stack-size = 1,630,208` KiB、`S = RLIMIT_STACK = 1,695,744` KiB、`L = 2^20` である(V198)。
  フレームの大きさの推定は `8 × K + 24 × P + 64` バイトとした。
  推定がちょうど 1,536 バイトの関数(N = 0、10、59)も、すべての層で `L + R` 段に届いた。
- V8 の WasmGC の配列の長さの上限は、i8 で `2^30 − 32`、`eqref` と `i64` で `2^27 − 8` である。
  超えると `RuntimeError: requested new array is too large` で trap する。
  `N_alloc_max = 2^26 = 67,108,864` に決めた(V215)。
  要素の幅ごとに上限を分ける案と、`2^27 − 8` とする案は採らず、所有者が覆す余地として測定の記録に書き残した。

計画からの逸脱は次のとおりである。

- `--stack-size` に渡す値を、計画 6.10 節の `S` の 90% から `(L+R) × B_wasm + 32 MiB` に改め、`S` を `--stack-size + 64 MiB` にした。
  90% の式では、`(L+R) × B_wasm` が 576 MiB を超えると、V8 に渡す限度が `(L+R) × B_wasm` より小さくなる。
  実際に、計画の式で `B_wasm = 2048` とした設定(`ulimit -s 2195456`、`--stack-size=1975911`)では、1 段が 2,048 バイトの再帰が 987,952 段で `RangeError` になり、`L` に届かなかった。
  計画の確かめ方(「`S` の 90% が上限を超えない」)はこの設定で通るので、確かめ方そのものが誤りを見逃す。
  M94 の Node の起動(計画 6.10 節、D545)は、改めた式で実装する必要がある。
- `B_wasm` を、計画 6.10 節の初期値 2 KiB でなく 1,536 バイトにした。
  `(L+R) × 2048 = 2,129,920` KiB だけで `--stack-size` の上限を超えるためである。
  計画 6.10 節の選択肢のうち、`Worker` の経路より先に挙がっている「`B_wasm` を下げる」を採った。
  `Worker` の経路は `stackSizeMb` 2,176 で `B_wasm = 2048` も満たせるので、代わりの経路として残る。
- フレームの大きさの推定を、計画 6.10 節の「局所の数 × 8 + 定数」から `8 × K + 24 × P + 64` に改めた。
  はじめは `8 × (P + K) + 64` としていたが、検証で、引数を呼び出しに渡す関数では引数 1 個が最大 24 バイトを使うことがわかった。
  たとえば P = 18、K = 150 の関数は、元の推定では 1,408 バイトだが、1 段は 1,568 バイトで `B_wasm` を超える。
- 大きなフレームの形(計画 6.10 節)は局所だけを移すので、引数が 62 個以上(N が 60 以上)の関数は、その形でも 1 段が `B_wasm` に収まらない。
  計画はこの場合を扱っていない。
  M94 は、超えた引数を GC の構造体にまとめて渡す形を足す必要がある。
