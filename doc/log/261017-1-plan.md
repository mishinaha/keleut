## 0. 設計の要約と棚卸し

### 0.1 出発点

Keleut は、専用の例外機構を持たない（LangSpec §13.6）。
例外に相当する動作は、`resume` を呼ばずに操作節を抜ける巻き戻しと、`cancel` 節の後始末の組み合わせで書く。
標準環境は、コンストラクタを持たない型 `Never` を持ち（§3.1、§16.1）、規範の `doc/sample.kel` は 570 行で `effect Fail = { throw: (String) => Never }` を宣言し、572〜576 行の `try_` でそれを `#Ok` と `#Err` に変換している。
したがって、例外を「返り値の型が `Never` の操作」として書くこと自体は、今の言語でもできる。

今の言語で足りないのは、次の 4 点である（HEAD の実測は本計画 3 節 (2)）。

1. `perform throw("none")` の型が `Never` なので、`Int32` などの値が要る位置に置けない。
   `perform throw("none") match {}` と書く回り道が要る。
2. `throw` の節に `resume(???)` と書けてしまい、実行時に穴で落ちる。
3. 節の本体を評価してから中断した計算を破棄するので、内側の `cancel` 節が節の本体より後に走る。
   多くの言語の例外機構は、`finally` に相当する後始末を `catch` の本体より先に走らせる。
4. 節の本体が継続を抱えたまま評価されるので、`case throw(e) => retry(n - 1)` の形の再試行が、再帰の深さに比例して領域を使う。

本計画は、返り値の型が `Never` の操作を「再開しない操作」と定め、その操作にだけ 4 つの規則を足す。
再開しない操作の `perform` の式は穴と同じく周囲が要求する型になり（規則 1）、その操作の節には `resume` を書けず（規則 2）、処理系は節の本体を評価する前に中断していた計算を破棄し（規則 3）、節の本体はハンドラ式の末尾位置にある（規則 4）。
新しい宣言、構文、注釈、標準のエフェクトは足さない。
再開回数が 0 であることは、`resume(v)` の `v` に値がないことから型だけで導かれるので、別の印は要らない。

## 1. 裁定（D336 から）

- **D336（再開しない操作の定義）**：返り値の型が `Never` である操作を再開しない操作と呼ぶ。
  判定は型エイリアスを展開した後の型で行い、操作ごとに行う。
  同じエフェクトに再開する操作と再開しない操作を混ぜて宣言できる。
  `Never` 以外の値を持たない型（コンストラクタを持たない利用者の `newtype`、ケースの無いヴァリアント、`Never` を含むタプル）は判定に含めない。
  含めると、判定が構文ではなく型の性質（値を持つかどうか）に依存し、§18 の保存する性質を調べる範囲が広がるからである。
  印をエフェクト単位にしない理由は、`effect Parser = { next: () => Int32, fail: (String) => Never }` のように失敗を含むエフェクトを 1 つのハンドラで処理できること、`handle` の規則（1 ハンドラ 1 エフェクト、全操作に節が要る）を変えずに済むことである。
- **D337（規則 1。`perform` の式の型）**：再開しない操作の `perform` の式は、穴（§5.6）と同じく、周囲が要求する型の式として扱う。
  実装は、操作の返り値の型の代わりに新しい型変数を返す。
  `Never` を任意の型と一致する型（ボトム型）にはしない。
  一致の規則が対称でなくなり、§3.4 の「型の一致」に部分型付けを持ち込むからである。
  任意の型で失敗する補助関数は、`let abort[A](m: String): A @ Fail = perform throw(m)` のように、型パラメータで書く。
- **D338（規則 2。節の `resume`）**：再開しない操作の操作節には `resume` を書けず、型検査で拒否する。
  節の中の無名関数や関数の定義の本体に書いた場合も拒否する。
  診断は「再開しない操作 throw の節には resume を書けません(操作の返り値の型が Never です)」とし、位置は `resume` の位置とする。
  実装は、節の本体を推論する環境の `resume_ty` を `None` のままにし、診断のために操作名を環境に持つ。
  閉包の中の `resume` を探す静的な検査（`lib/elab.ml` の §11.21）は、この節では呼ばない。
  環境の `resume_ty` が `None` なら、閉包の本体の `resume` も推論の時点で落ちるからである。
- **D339（規則 3。継続を破棄する時点と、ハンドラ自身の後始末）**：再開しない操作の節では、処理系は節の本体を評価する前に中断していた計算を破棄し、破棄が終わってからハンドラの外側で節の本体を評価する。
  破棄する計算の中にあったハンドラの `cancel` 節は、節の本体より先に走る。
  節の本体で起きた実行時エラーや、本体から同じ操作を起こして外側のハンドラへ移ること（再送出）は、ハンドラ式の後ろで起きたものとして扱い、そのハンドラ自身の `return` 節と `cancel` 節は走らせない。
  HEAD は、再開する操作の節が `resume` を呼ばずに実行時エラーで脱出したとき、そのハンドラ自身の `cancel` 節を走らせる（`lib/interp.ml` の §14.9 の 3 つ目の経路）。
  再開しない操作の節にこの経路を残す案は、節の評価を例外の捕捉で包むことになり、規則 4 の末尾位置と両立しないので採らない（本計画 2.3 節）。
  資源を持つハンドラが自分で継続を捨てるなら、後始末はその節の中に書くという現行の規則（§13.6、`lib/interp.ml` の §14.9）は変わらない。
- **D340（規則 4。末尾位置）**：ハンドラ式が末尾位置にあれば、再開しない操作の操作節の本体も末尾位置にあると §5.7 に書く。
  実装は、`Effect.Deep.match_with` の `effc` の中で継続を捨てた後、節の本体をその関数の末尾で評価する。
  `match_with` の呼び出しを `eval_handle` の末尾から外して結果を受け取る形は、`return` 節の経路の末尾性を失い、既存の cram（`test/tail_calls.t` の retc.kel）を落とす（本計画 3 節 (3) の実測）ので採らない。
- **D341（実装の印）**：型検査は、再開しない操作の操作節に `Tree.RNeverOp` の印を付け、評価器はその印だけで経路を分ける。
  評価器が宣言表を引いて判定し直す案は、「評価器は節の種別を判定し直さない」という `lib/tree.ml` の §5.1 の方針に反するので採らない。
- **D342（`match {}` の書き方）**：`perform throw(e) match {}` の形は、規則 1 の後は照合対象の型が決まらないので網羅漏れの警告になる。
  既存の cram と `doc/sample.kel` にこの形は無い（`grep 'match {}'` の結果は `absurd` の 2 か所だけで、どちらも `Never` 型の引数に対するもの）ので、特別な扱いはしない。
  仕様にもこの形は書かない。
- **D343（足さないもの）**：新しい宣言（`exception`）、再開回数の注釈、標準環境の `Fail` エフェクト、操作節を持たないハンドラ（`return` 節と `cancel` 節だけのハンドラ）は、本計画では足さない。
  最後のものは例外とは独立の拡張なので、所有者への問い P83 とし、別の文書で決める。
- **D344（cram の置き場）**：`test/never_ops.t` を新設し、規則 4 の再試行のブロックは `test/tail_calls.t` に置く。
- **D345（マイルストーンの分割）**：型検査の規則（規則 1、2）を M63、評価の規則（規則 3、4）を M64、`doc/sample.kel` の改訂と写しの同期を M65、検証と記録を M66 とする。
  M63 の後の評価器は、再開しない操作の節を再開する操作の節と同じ経路で評価する（HEAD と同じ）ので、M63 だけでも cram は緑である。
- **D346（`doc/sample.kel`）**：568 行、569 行、574 行のコメントを改め、行数 881 は変えない。
  コードは変えない。

### (2) 現状（根拠つき）

#### 仕様

- §3.1 98 行は、`Never` をコンストラクタを持たない型と定め、§16.1 1595 行が `newtype Never` を標準環境に置く。
- §13.1 1079 行は「操作の型は矢印型で書く」とだけ定め、返り値の型による区別はない。
- §13.3 1169 行は「実引数は、操作の型に一致しなければならない」と定め、`perform` の式の型は書いていない。
  実装は操作の返り値の型をそのまま式の型にする（下の実装）。
- §13.5 1245〜1246 行は、`resume` を書けない位置としてガード、`return` 節、`cancel` 節を挙げ、再開回数を高々 1 回と定める。

### (3) 判断と確定

#### 4 つの規則

規則 1（D337）は、`perform` の式の型を新しい型変数にする。
`let abort[A](m: String): A @ Fail = perform throw(m)` は、型変数が `A` と一致して一般化され、呼ぶ側の型に合わせて使える（例 `m_generic`。試作で `abort : (String) => A @ {Fail}` と表示し、`Int32` と `String` の両方の位置で動く）。

規則 2（D338）は、節の `resume` を型検査で拒否する。
直接書いた形（例 `i_resume_static`）も、無名関数の本体に書いた形（例 `j_resume_lambda`）も、同じ診断で落ちる。
節の本体の中に書いた別のハンドラの操作節では、その節の `resume` を書ける（例 `p_nested`）。

規則 3（D339）は、継続を破棄する時点を節の評価の前に動かす。
再開の可能性が型で消えているので、節の終わり方を待たずに破棄できる。
例 `d_order` の出力は `open outer`、`open inner`、`cancel inner`、`cancel outer`、`catch abort` の順になり、多くの言語の `finally` と `catch` の順序に合う。
再開する操作の節では、節が `resume` を呼ぶかどうかは節が終わるまで分からないので、この時点を動かせない。
この違いが、再開回数 0 を型で確定させることの、性能以外の利点である。

規則 4（D340）は、規則 3 の帰結である。
破棄が終わった後の節の本体には、抱えている継続がないので、ハンドラ式の末尾位置に置ける。
例 `f_retry` は、試作で `OCAMLRUNPARAM=l=100k` の下で 10 万回の再試行を通し、`0` を出す。

#### 再開しない操作の節の終わり方

試作の再開しない操作の節は、`effc` の中で次の順に動く。

1. 節を選ぶ（引数の照合とガードの評価。HEAD と同じ）。
2. `discontinue k (Unwind (inst, unit))` で継続を捨てる。
   捨てる継続の中のハンドラは内側から外側の順に `cancel` 節を走らせ、最後に自分の `exnc` が `Unwind` を受け取って `discontinue` が戻る。
   `Unwind` に載せる値は使わないので `unit` でよい。
3. 節の本体を、`effc` の関数の末尾で評価し、その値を `match_with` の値にする。

HEAD の 3 つの経路（`lib/interp.ml` の §14.9 の表）との違いは次のとおりである。

| 節の終わり方 | HEAD（再開する操作と同じ経路） | 試作（再開しない操作） |
|---|---|---|
| 値 `v` を返した | 節の後で `discontinue`。内側の `cancel` 節は節の本体の後に走る | 節の前で `discontinue`。内側の `cancel` 節は節の本体の前に走る |
| 実行時エラーで脱出した | `discontinue k ex`。内側の `cancel` 節と、自分の `cancel` 節が走る | 内側の `cancel` 節は節の前に走り済み。自分の `cancel` 節は走らない（例 `o_clause_error`） |
| 本体から同じ操作を起こした（再送出） | 外側の `Unwind` が自分の `exnc` を通り、自分の `cancel` 節が走る | 自分の `cancel` 節は走らない（例 `e_rethrow`、`s_from_clause`） |

2 行目と 3 行目の違いを D339 で確定した。
根拠は 3 つある。
1 つ目に、§13.6 の `cancel` 節は「ハンドラが外側から巻き戻されるとき」の後始末であり、1260 行が挙げるのは本体の実行時エラーで、節の実行時エラーではない。
HEAD の 3 つ目の経路は、仕様に無い実装の都合である（台帳 V128）。
2 つ目に、§13.6 1262 行は、自分で継続を破棄して終わるハンドラの `cancel` 節を走らせないと定めており、再開しない操作の節は常に自分で継続を破棄するので、節の本体が値を返すときと実行時エラーで脱出するときを揃えるほうが一貫する。
3 つ目に、節の評価を例外の捕捉で包むと、末尾位置（規則 4）を失う（本計画 2.3 節）。

`cancel` 節から再開しない操作を起こした形（例 `t_cancel_perform`）は、外側のハンドラが継続を捨てようとして `cancel` 節の中に `Unwind` を送り、`cancel` 節の打ち切りの規則（§13.6 1270〜1272 行）でそれを抑制する。
試作の出力は `cancel res`、`cancel 節で例外が抑制されました: cancel 節から操作の巻き戻しで脱出しようとしました`、`実行時エラー: ゼロ除算です` で、HEAD の抑制の規則のままである。

#### 末尾位置の実装の形

最初の試作は、`eval_handle` が `match_with` の結果を受け取り、再開しない操作の節の本体を `match_with` の後で評価する形にした。
この形は `test/tail_calls.t` の retc.kel を `実行時エラー: スタックオーバーフロー(再帰が深すぎます)` で落とした。
`match_with` が `eval_handle` の末尾になくなり、`return` 節の経路で `eval_handle` の枠が再帰の段ごとに残るからである。
そこで、節の本体を `effc` の関数の末尾で評価する形に改めた（D340）。
この形は `dune runtest` を 0 差分で通し、例 `f_retry` を `OCAMLRUNPARAM=l=100k` の下で通す。
`effc` の関数が `discontinue` から戻った後の末尾の呼び出しが領域を使わないことは、OCaml 5.2.1 で実測した事実であり、ほかの版での保証は OCaml の処理系に依存する（本計画 8 節）。

#### 判定の位置

`Never` の判定は、操作のスキーマを具体化した返り値の型を `repr` して `TCon (Never, [])` と比べる。
操作の型は `elab_type` が型エイリアスを展開済みなので、`type Boom = Never` を返り値に書いた操作も再開しない操作になる（例 `h_alias`）。
判定は `perform`（§11.15）と操作節（§11.23）の 2 か所で行い、どちらも同じ補助関数 `is_never` を使う。

#### 変わらないこと

- `perform` の引数の型付け、操作名の解決（§13.3）、ハンドラの対象エフェクトの決定と網羅（§13.4）、節の選択（ソースの順、ガード）は変わらない（例 `k_mixed`、`l_guard`）。
- トップレベルに残せるエフェクトの規則（§13.7）は、再開しない操作にも同じに働く（例 `n_stmt`。試作でも型エラー）。
- 再開する操作の 3 つの経路、末尾 `resume`、アフィン性と第二級性の検査は変わらない。
  試作の `dune runtest` は 39 本すべてで 0 差分である。
- HEAD が受理するプログラムで振る舞いが変わるのは、再開しない操作の節の本体が出力した後に内側の `cancel` 節が走る形（順序が入れ替わる）と、節の本体が実行時エラーで脱出する形（自分の `cancel` 節が走らなくなる）の 2 つである。
  既存の cram と `doc/sample.kel` に、この 2 つの形は無い。

## 9. 進め方の原則

- 実装は、マイルストーンの順に逐次で進める。
- 各マイルストーンの後に、敵対的検証を行う。
  検証者は観点ごとに置き、指摘 1 件につき反証者を 1 人置く。
  検証者と反証者には、リポジトリの編集、git の書き込み、リポジトリの中での `dune` の実行を禁じ、一時領域に写した新旧 2 つのバイナリだけを使わせる。
  検証者の書き込み先を一時領域に固定し、報告を受けたら作業ツリーに未追跡のファイルが無いことを確かめる。
- 前の計画の検証で繰り返し出た欠陥の種類を、実装者と検証者の両方に示す。
  1 つ目は、全称や件数の主張（「〜だけ」「N か所」）が偽であること。
  2 つ目は、cram の前書きの主張が、そのブロックの入出力で示されていないこと。
  3 つ目は、修正が、変更前に通っていた正しいプログラムを落とす退行である。
  本計画の作成では、3 つ目が末尾位置の最初の試作で起きた（本計画 3 節 (3)）。
- コミットは項目ごとに細かく分け、コードの修正と期待出力の更新を別のコミットにする。
  ブランチが `ja/` で始まるので、コミットのメッセージは日本語で書く。
  壊れた状態ではコミットしない。
- diktor の中のコミットの scope は `diktor:`、`fix:`、`test:`、`doc:`、`lit:` を使う。
  親では `spec:` と `diktor:` と `doc:` を使う。
  親の `diktor:` のコミットのメッセージの版は `git -C diktor rev-parse --short HEAD` で埋め、手で書かない。
- ソースのコメントは、現状と設計の理由だけを書き、裁定、台帳、マイルストーンの番号、計画への参照、経緯は書かない。
  番号と経緯は、コミットのメッセージと `doc/log` にだけ書く。
- `test/sample/sample.kel` は手で編集しない。
  親の `doc/sample.kel` から `test/sample/README.md` の手順で同期する。
- 既存の `doc/log` の記録は書き換えない。
  本計画からの乖離は、実施記録に書く。
- ヒアドキュメントは `<<'EOF'` で引用する。
  並行する Bash は絶対パスだけを使う。
- `ocamlformat` と `dune fmt` は使わない。
- push はしない。
