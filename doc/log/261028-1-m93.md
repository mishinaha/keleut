# 261028-1: M93 計測と最適化の判断の記録

計画 261024-1(`doc/log/261024-1-plan.md`)の M93 で測った値と、そこから決めたことを記録する。
決めたことの一覧は 1 節にある。
実施の経緯と受け入れの結果は、実施記録 `doc/log/261024-3-record.md` の M93 の節にある。

## 1. 決めたこと

| 項目 | 決定 | 根拠(節) |
| --- | --- | --- |
| フレームを置く速い道(V214) | 採る。呼ばれる側のフレームが値スタックの使っている最後の塊に収まれば、JIT のコードが `krt_prep` を呼ばずにその場で置く | 3.1 |
| レジスタで引数を渡す ABI(V206) | 採る。関門(512 KiB のスタックで 1 億回の交互の末尾呼び出しが完走し、全組で差 0)を通り、引数の多い末尾再帰で 1.65 倍速くなった | 3.2 |

## 2. 測り方

### 2.1 道具

計測のプログラムと走らせる道具は `rustkeleut/bench/` に置いた(使い方は `rustkeleut/bench/README.md`)。
`bench/run.py` は、`bench/programs/` の各プログラムを `diktor --emit-ir` で一時のディレクトリの KIR にし、設定ごとに走らせて経過時間を測る。
経過時間は、子プロセスを作ってから `wait4` で終わりを受け取るまでの `time.perf_counter` の差である。
どの設定の標準出力も最初の設定のものと同じで、終了状態が 0 であることを、すべての回で確かめた。
`bench/corpus.py` は、`conformance/corpus/` の `.kel` のうち KIR にできる 555 個を順に走らせ、設定ごとの合計の時間を出す。

プログラムは次の 17 個である。

| 名前 | 中身 |
| --- | --- |
| `hello` | `echoln("hello")` |
| `fib` | `fib(32)`(`Int32` の末尾でない再帰) |
| `tail32` | 2 引数の末尾再帰 1,000 万回と、相互の末尾再帰 1,000 万段 |
| `tail32b` | `tail64` と同じ本体を `Int32` で書いた 2 引数の末尾再帰 1,000 万回(5.3 節のために後で足した) |
| `args6` | 6 引数の末尾再帰 1,000 万回 |
| `tail64`、`tailf64` | `Int64` と `Float64` の引数の末尾再帰 1,000 万回 |
| `tailresume` | T の節の末尾 `resume`(500 万回の `perform`) |
| `gen` | G の節の生成器(1,000 回の yield を 1,000 回) |
| `gdepth1`〜`gdepth1000` | 深さ 1、10、100、1,000 の再帰の底からの yield を 2 万回 |
| `abort` | N の節への脱出を、深さ 10 で 20 万回、深さ 1,000 で 2,000 回 |
| `records` | 3 フィールドのレコードの作り直しと `with` の更新を 200 万回ずつ、1,000 要素のレコードのリストを 1,000 回走査 |
| `strings` | 文字列の連結と部分文字列と比較を 1,200 回、`show` と比較を 100 万回 |
| `typecheck` | let 多相つきの単一化による型推論器で、型で導いて生成した式 12,000 個を検査する |

`typecheck` は、コンパイラに近い負荷として書いた。
型を `newtype` のコンストラクタで表し、型変数の束縛と水準を 512 要素の可変配列に置き、環境は名前の文字列で引く連想リストにした。
1 回の検査が使う型変数は 256 個に収まり、128 要素では配列の外を指して止まる。
型の誤りは `Never` を返す操作 `fail` で起こし、N の節で受ける。
12,000 個の式のうち 1,200 個に、関数を `Bool` に適用する誤りを入れた。

### 2.2 設定

| 設定 | コマンド |
| --- | --- |
| `ki` | `keleut run --backend interp` |
| `kj` | `keleut run --backend jit --tier jit-only` |
| `ktN` | `keleut run --backend jit --tier threshold=N` |
| `kw` | `keleut run --backend wasm`(Node 26.9.0) |
| `dk` | `diktor FILE.kel`(木の評価器) |
| `dkir` | `diktor --run-ir FILE.kir` |

`dk` は構文解析と型検査を含む。
`diktor --type-check` は、どのプログラムでも 3〜6 ms だったので、`dk` の値の大部分は評価の時間である。
`kw` は、KIR から WasmGC のモジュールへの翻訳と、Node の起動(`hello` で 38 ms)を含む。
`kt1000` は、LLVM の後段を付けて組んだ `keleut run` の既定(`--backend` と `--tier` を省いたとき)と同じである。

### 2.3 機械と回数

機械は AMD Ryzen 9 7950X(16 コア、32 論理コア)、メモリ 31 GB、WSL2(Linux 6.18.54.1)である。
`keleut` は `cargo build --release --features llvm`(rustc 1.98.1、LLVM 22.1.8)で組み、Diktor は diktor 15ddd62 の組みを写して使った。
各設定を 5 回(`dk` と `dkir` は 3 回)走らせ、経過時間の中央値を表に書いた。
多くの設定では、最小値と最大値は中央値から 5 % 以内だった(最適化の前の表で 176 個のうち 128 個、後の表で 144 個のうち 126 個)。
ただし、1 回だけ大きく外れた標本のために 20〜43 % 離れた設定があった。
前の表では `typecheck` の `kw` が 43 %、`gdepth100` の `kj` が 27 %、`args6` の `ki` が 22 % で、10 % を超えた設定は 27 個あった。
後の表では `typecheck` の `kw` が 31 %、`typecheck` の `ki` が 26 %、`args6` の `ki` が 21 % で、10 % を超えた設定は 8 個あった。
1 つの設定の回は続けて走らせ、捨てる回を置かなかったので、そうした設定どうしの 10〜20 % ほどの差は意味のある差とみなさない。

同じ機械で、別の作業がときどき Rust の組み立てを走らせていた。
各表の測定の始めの 1 分の負荷の平均は、最適化の前の表で 0.42、最適化の後の表で 3.26 だった。
後の表は 32 論理コアのうち数個が使われている状態で測ったので、数 % の差は誤差とみなす。
これは、負荷の平均が 1 を超えるときは測り直すという `bench/README.md` の手順に反する。
同時に進む別の作業の組み立てを止められなかったので、全体を測り直さず、負荷を記録して読み方で補った。

`typecheck` は、初めは 1 回の検査ごとに型変数の配列を 20,000 要素で 2 つ作っていた。
検証で、この配列を埋める時間が `kw` の時間の約 4 割を占め、後段ごとに比重が違うことが分かったので、要る大きさの 512 要素に直して測り直した。
直した `typecheck` と、5.3 節の `tail32b` は、2026-10-28 に、各設定を 1 回捨ててから、設定を回ごとに順に回して 9 回(`dk` と `dkir` は 3 回)走らせた(`run.py --interleave --warmup 1`)。
回ごとに回したのは 1 つの組みの中の設定どうしで、前と後の組み(3.2 節と 6 節の前の列)は組みごとに別の回で、同じ指定で測った。
この測定の負荷の平均は、始めに 0.60、終わりに 1.83 だった。
回ごとに回しても、`hello` のような数 ms の計測や、1 回だけ外れた標本で、中央値から 30〜40 % 離れた設定は残った。
3.2 節、4 節、6 節の表の `typecheck` の行は、この測り直しの値である。

## 3. 入れた最適化

### 3.1 フレームを置く速い道(V214)

最適化の前の JIT は、呼び出しのたびに実行時の関数 `krt_prep` を呼んで、呼ばれる側のフレームを値スタックに置いていた。
`perf` で `kj` の `fib(34)` を測ると、時間の 70 % が `krt_prep` とその中の `place` と `ValueStack::place` だった。
`Int32` と `Int64` の末尾再帰(1,000 万回ずつ)と相互の末尾再帰でも、この 3 つが 33 % を占めた。

そこで、値スタック(`keleut_rt::stack::ValueStack`)が、使っている最後の塊の範囲(先頭と終わりの論理的な位置と番地)を `StackWindow` に持つようにした。
値スタックは、使っている塊を変えるたびに(`place` と `ptr_at`)これを書き直す。
JIT の文脈 `NativeCtx` は、この範囲を指す `win` と、関数ごとのフレームの語の数の列 `frames` を持つ。
JIT のコードは、自分のフレームの位置が範囲の中にあり、置く位置に呼ばれる側のフレームの語の数を足したものが範囲の終わりを超えないとき、見出しの 4 語と文脈の欄をその場で書く。
このとき使っている塊は自分のフレームのある塊なので、`krt_prep` の `ValueStack::place` も同じ位置を返す。
収まらないときだけ `krt_prep` を呼ぶ。
直接の呼び出しは翻訳のときにフレームの語の数を知っており、クロージャの呼び出しは `frames` の列から読む。

この道は `krt_prep` の中の `sample` を通らないので、`KELEUT_JIT_STATS` が書くネイティブのスタックの使用量は、末尾呼び出しの多い実行で小さく出る(交互の末尾呼び出しの試験で 808 バイトから 736 バイト)。

### 3.2 レジスタで引数を渡す ABI(V206)

計画 6.8 節は、レジスタで引数を渡す形を、M93 で交互の末尾呼び出しを測り直してから採るとしていた。
3.1 節の速い道の上に試作を作り、測ってから採った。

JIT の関数は、値スタックの入口 `tailcc i64 @kfN(ptr %ctx)` と、レジスタの入口 `tailcc i64 @kfN.r(ptr %ctx, i64 %env, i64 %x0, …, i64 %x3)` の 2 つを持つ。
入口の表は値スタックの入口を指し、新しいレジスタの入口の表がレジスタの入口を指す。
JIT の関数どうしの直接の呼び出しとクロージャの呼び出しはレジスタの入口を呼び、環境と前の 4 個の引数をレジスタで渡す。
`ctx` と環境と 4 個の引数で、x86-64 の引数のレジスタ 6 つを使う。
5 個目からの引数は、これまでどおりスロットに書く。
インタプリタ、スタブ、エフェクトの命令からの呼び出しは、値スタックの入口を通る。
値スタックの入口は、スロットと文脈から引数と環境を読み、レジスタの入口を `musttail` で呼ぶ。
翻訳していない関数のレジスタの入口の表の項目はスタブ `interp_stub_r` を指し、スタブがレジスタの引数をスロットに書いてから `interp_stub` に移る。

レジスタの入口は、引数をスロットに書かずに走る。
GC はどの点でも生きているレジスタのスロットだけを根にし(`rustkeleut/doc/lir.md` の 1.8 節)、JIT のコードは再開点と安全点の前に生きているレジスタをスロットに書くので、引数を入口で書く必要はない。
例外は `$rt_handle` で、0 番のスロットがどの点でも根なので、入口でレジスタの引数をスロットに書く。
入口でインタプリタに移るとき(ネイティブのスタックの下限と `alternating`)は、レジスタの引数をスロットに書いてから移る。

関門の結果は次のとおりである。

- `cargo test --release --features llvm -p keleut-llvm --test tier_alt`(512 KiB のスタックで 1 億回の交互の末尾呼び出し)は完走した。
  時間は 2.81 秒と 2.67 秒で、3.1 節だけの組み(2.65 秒と 2.72 秒)と変わらなかった。
  この試験は、呼び出しのたびにインタプリタとの境目をまたぐので、境目の費用が支配する。
- `kconform --pairs ki,kj,kt,ka,km --suite all` は差 0 件で、`--extra=--gc-stress` と `--extra=--no-yield-prune` も差 0 件だった。
  `kconform --pairs dk-ir,ki,kj,kt,ka,km --suite depth` も差 0 件だった。

速さは、3.1 節だけの組みと比べて次のとおりだった(5 回の中央値、ミリ秒)。

| 計測 | 3.1 節だけ `kj` | 3.2 節も `kj` | 3.1 節だけ `kt1000` | 3.2 節も `kt1000` |
| --- | ---: | ---: | ---: | ---: |
| `args6` | 124 | 83 | 109 | 66 |
| `tail32` | 103 | 106 | 84 | 84 |
| `fib` | 61 | 64 | 46 | 47 |
| `records` | 339 | 342 | 302 | 295 |
| `typecheck` | 536 | 543 | 326 | 320 |

速くなったのは引数の多い関数だけで、6 引数の末尾再帰は 1.65 倍になった。
2 引数の末尾再帰、`fib`、`records`、`typecheck` は誤差の範囲で変わらなかった(`typecheck` の行は 2.3 節の測り直しの値)。
引数が少ないと、スロットへの書き込みと読み出しは L1 キャッシュの中の転送で済むが、引数が多いと書き込みと読み出しが 1 回ごとの依存の鎖に並ぶためだと推測している。
関門を通り、測れる差があったので、計画 6.8 節の条件のとおり採った。

### 3.3 翻訳のスレッドの起動を待たない

最適化の前の `keleut run` は、LLVM の後段の段の設定のどれでも、翻訳のスレッドが LLJIT を作ってスタブを翻訳するのを待ってから走り始めた。
`perf stat` で 30 回測ると、`hello` の経過時間は `--backend interp` が 7.9 ms、`threshold=1000` が 15.5 ms だった。
`corpus.py` で 555 個の小さなプログラムを走らせた合計は、`ki` が 6.78 秒、`kt1`〜`kt10000` が 10.0〜10.8 秒だった。
しきい値に依らず、プログラムごとに約 6 ms 遅かった。
実行の後に翻訳のスレッドを待たずに終えても、`hello` の時間は 15.5 ms のままだったので、遅れの元は起動の待ちである。

そこで、`threshold=N` では、ミューテータが起動を待たずにインタプリタで走り始めるようにした。
入口の表はミューテータの側で 0 で埋めて作り、翻訳のスレッドが起動を終えたときに `interp_stub` で埋める。
ミューテータは、翻訳を頼んだ関数の項目が 0 でなくなったときに初めて起動の結果(スタブと `enter_tailcc` の番地)を受け取る(`Native::set_pending_init`)。
それまでは翻訳済みの関数が無いので、JIT のコードは走らない。
`keleut run` は、この段の設定では実行の後に翻訳のスレッドを待たずにプロセスを終える(標準出力と標準エラーを flush してから `_exit` を呼ぶ。M92 の逸脱の 10 と同じ終え方)。
`jit-only`、`alternating`、`mixed` は最初の呼び出しで翻訳を待つので、これまでどおり起動を待つ。

直した後は、`hello` の `threshold=1000` が 8.9 ms になり、`corpus.py` の合計は次のようになった。

| 設定 | 前(秒) | 後(秒) |
| --- | ---: | ---: |
| `ki` | 6.78 | 6.71 |
| `kt1` | 10.22 | 6.75 |
| `kt10` | 10.60 | 6.03 |
| `kt100` | 10.53 | 6.40 |
| `kt1000` | 10.84 | 6.06 |
| `kt10000` | 10.02 | 6.20 |
| `kj` | 33.27 | (測っていない) |

前の測定の負荷の平均は 8.16、後は 4.80 だった。
後の値が `ki` より小さい理由は測っていない。
`kt1000` は実行の後に `_exit` で終わり、ヒープや LIR のプログラムを捨てる普通の終わりの処理を省くので、その差だと推測している(`ki` は LLJIT を作らない)。

## 4. JIT のしきい値の既定(P249)

しきい値は、短いプログラムでは翻訳の費用を払わず、長く走るプログラムでは早く JIT のコードに移る値がよい。
判断の基準は次のとおりとした。
2.1 節の計測(`tail32b` を除く 16 個)の中央値と `corpus.py` の合計のどれでも誤差を超える差のないしきい値の範囲を求め、その範囲の中で、速さの落ちる両端から対数で最も離れた値を選ぶ。
範囲の中での翻訳する関数の数の違いは、判断に使わない。

最適化の後の組み(3.1〜3.3 節)で、16 個の計測をどれもすべてのしきい値で測った。
次の表は、そのうち、しきい値 1 で 1,000 より 8 % 以上遅かった 8 個の値である(中央値、ミリ秒)。

| 計測 | `kt1` | `kt10` | `kt100` | `kt1000` | `kt10000` | `kt100000` | `kj` |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `abort` | 172 | 152 | 151 | 153 | 151 | 171 | 213 |
| `args6` | 79 | 65 | 66 | 65 | 65 | 70 | 85 |
| `fib` | 59 | 47 | 46 | 46 | 46 | 47 | 66 |
| `gdepth100` | 148 | 125 | 126 | 128 | 125 | 118 | 190 |
| `records` | 316 | 293 | 291 | 292 | 297 | 316 | 339 |
| `strings` | 199 | 178 | 178 | 178 | 177 | 207 | 217 |
| `tail32` | 103 | 83 | 84 | 82 | 82 | 91 | 106 |
| `typecheck` | 384 | 330 | 333 | 324 | 326 | 398 | 547 |

`typecheck` の行は 2.3 節の測り直しの値で、ほかの行とは測った回が違う。

表にない 8 個の結果は次のとおりだった。

- `hello`、`gen`、`gdepth1` は、どのしきい値でも差が誤差の範囲だった。
- `gdepth10` は、100,000 でだけ 1,000 の 45 から 42 にわずかに速くなった。
- `tail64`、`tailf64`、`tailresume` は、1 でだけ 1,000 より 3〜5 % 遅かった(`tail64` が 235 と 226、`tailf64` が 242 と 231、`tailresume` が 568 と 549)。
- `gdepth1000` は、1,000 の 926 に対して 10,000 で 882(5 % 速い)、100,000 で 827(11 % 速い)だった。

両方の結果から、しきい値ごとに次のことが分かる。

- 10 から 10,000 までは、`gdepth1000` を除くどの計測でも差が誤差の範囲だった。
  熱いループは最初の数回の反復でどのしきい値にも届くからである。
  `gdepth1000` は 10,000 で 1,000 より 5 % 速かったが、速くなる向きの差なので、速さの落ちる両端は変わらない。
- 1 は、一度しか呼ばない関数まで翻訳を頼むので、熱い関数の翻訳が待ち行列の後ろに回り、表の 8 個では 8〜28 % 遅かった。
  表にない 8 個では、差がないか 3〜5 % 遅いだけだった。
- 100,000 は、1,000 と比べて 16 個の計測のうち 6 個で 8〜23 % 遅かった(`typecheck` が 23 %、`strings` が 16 %、`abort` が 12 %、`tail32` が 11 %、`records` が 8 %、`args6` が 8 %)。
  `typecheck`、`strings`、`records` は、呼び出しが多くの関数に散らばるので、JIT に移るのが遅れ、翻訳される関数も減る(`typecheck` では 1,000 の 24 個に対して 13 個)。
  `tail32`、`args6`、`abort` は、少数の熱い関数が、翻訳されるまでに約 10 万回をインタプリタで走る。
  `fib` は 46 と 47 で同じだった。
  `gdepth100` は 128 から 118 に、`gdepth1000` は 926 から 827 に速くなった。
- `jit-only` は、走らせるプレリュードの関数まで最初の呼び出しで翻訳を待つので、どの値よりも遅かった。
- `typecheck` で翻訳した関数の数は、しきい値 10 で 23 個、100 と 1,000 で 24 個、10,000 で 21 個、100,000 で 13 個、`jit-only` で 32 個だった。
  1,000 と 10,000 の 3 個の違いは、速さの差にならなかった。
- `corpus.py` の合計(3.3 節)は、3.3 節の後では 10〜10,000 で 6.0〜6.4 秒で、差は負荷の揺れの範囲だった。

10〜10,000 の平らな範囲の中で、速さの落ちる両端(1 と 100,000)から対数で最も離れた 1,000 を既定のままにする。
1,000 は計画 6.9 節の始めの値でもある。

## 5. 採らなかったものと延期したもの

### 5.1 G のためのネイティブのファイバー(P240、V204)

深さ `d` の再帰の底から 2 万回 yield する `gdepth` の時間は次のとおりだった(最適化の後、ミリ秒)。

| 後段 | `d` = 1 | 10 | 100 | 1,000 | 1 段あたり(`d` = 1,000) |
| --- | ---: | ---: | ---: | ---: | ---: |
| `ki` | 27 | 43 | 203 | 1,725 | 85 ns |
| `kt1000` | 28 | 45 | 128 | 926 | 45 ns |
| `kw` | 67 | 77 | 181 | 718 | 33 ns |
| `dkir` | 38 | 91 | 592 | 6,526 | 325 ns |

1 段あたりの値は、`d` = 1,000 の時間から `d` = 1 の時間を引き、2 万 × 999 で割ったものである。
どの後段でも、1 回の yield の費用は深さに比例した。
継続を作るときと再開するときに、区間のフレームを写すからである(計画 6.6 節)。
WasmGC の後段も同じく深さに比例するので、ファイバーを LLVM の後段だけに足しても、後段の間の違いが増えるだけである。
深さ 100 の G の 1 回の yield は、`d` = 100 の時間から 6 節の `hello` の時間を引いて 2 万で割ると、`kt1000` で約 6 µs、`kw` で約 7 µs、`ki` で約 10 µs、`dkir` で約 30 µs である。
`gen`(深さ 1)の費用は、深さでなく 5.4 節のエフェクトの命令の費用が占める。
計画 6.6 節の判断のとおり、ファイバーは採らない。

### 5.2 脱出を exnref と landingpad にする(V205)

`abort` は、深さ 10 と深さ 1,000 からの N の節への脱出で、合わせて約 400 万個のフレームを番兵で巻き戻す。
`kt1000` で 153 ms、`ki` で 352 ms、`kw` で 84 ms だった。
JIT の関数は番兵を戻り値の 1 回の比較で受け取るので、1 個のフレームの巻き戻しは約 40 ns である(153 ms を 400 万で割った値で、`handle` と `perform` の費用も含む)。
巻き戻しの費用は小さく、exnref と landingpad で機構を 3 つに増やす理由にならないので、採らない。

### 5.3 箱に入れない引数の入口(V207)

`Int64` と `Float64` の値は一様な語の中で箱に入るので、それらを引数に渡すたびに箱を確保する。
最適化の後の `kt1000` で、2 引数の末尾再帰 1,000 万回は、`tail64` と同じ本体を `Int32` で書いた `tail32b` が 44 ms なのに対して、`Int64` の `tail64` が 235 ms だった(2.3 節の測り直しの同じ回の値)。
6 節の表では、`tail64` が 226 ms、`Float64` の `tailf64` が 231 ms である。
`perf` で `kj` の `tail64` を測ると、時間の 78 % が箱の確保(`krt_box`、`box_i64`、`Heap::try_alloc`、`Rt::alloc`)と回収の掃除(`Heap::sweep`)だった。
`kw` は、同じ回の測定で `tail32b` が 77 ms、`tail64` が 89 ms で、箱の費用がほとんど無い。
WasmGC の後段は局所変数を `i64` のまま渡すからである。

必要は測れたが、延期する。
箱に入れずに渡すには、呼ぶ側と呼ばれる側が引数ごとの形を合わせたレジスタの入口が要る。
さらに、入口でインタプリタに移る道とスタブで箱を作り直す必要があり、その確保は安全点の外で起きる。
3.2 節のレジスタの入口は、この入口の土台になる。

### 5.4 エフェクトの命令の費用(V225)

`gen` と `tailresume` は、`kt1000` が 627 ms と 549 ms だった。
`ki`(639 ms と 867 ms)と比べると、`gen` はほぼ同じで、`tailresume` は約 1.6 倍速いだけである。
`kw`(146 ms と 154 ms)と比べると、経過時間で 3.6〜4.3 倍、`hello` の時間を引いた計算の時間で 4.7〜5.7 倍遅い。
`perf` で `kj` の `gen` を測ると、時間は `Interp::native_fx`、`Interp::code`、`krt_fx`、`Interp::fx_call`、libc の確保と解放に分かれていた。
JIT はエフェクトの命令を 1 つずつ `krt_fx` でインタプリタの命令として走らせ(M92 の逸脱の 1)、継続の作成と再開でも Rust の `Vec` を確保する。
命令をその場の LLVM の命令にするか、`krt_fx` の中の確保を減らすかは、G と T の節を使う実際のプログラムの比重が分かってから決める。
台帳に次の項目を載せる。

**V225: JIT のエフェクトの命令は `krt_fx` でインタプリタの命令を走らせるので、G と T の節の多いプログラムで WasmGC の後段の約 4 分の 1 の速さである(Node の起動を含む経過時間の比で、起動の時間を引くと約 5 分の 1)。**
扱いは延期である。

- `kw` の値は、KIR からの翻訳と Node の起動(`hello` で 38 ms)を含む。
  後段の速さは、`hello` の時間を引いた計算の時間で比べる。
- 計算の時間で `kt1000` が `kw` より速いのは `args6`(58 ms と 189 ms)と `gdepth1`(21 ms と 29 ms)で、`gdepth10` は同じ(38 ms と 39 ms)である。
  `fib` と `tail32` の経過時間は `kt1000` が `kw` と同じか速いが、計算の時間では `kw` が速い(`fib` で 39 ms と 21 ms、`tail32` で 75 ms と 47 ms)。
  `typecheck` は、`kw` が経過時間で 1.5 倍、同じ回の `hello`(`kt1000` 12 ms、`kw` 51 ms)を引いた計算の時間で 1.8 倍速い。

- エフェクト(`gen`、`tailresume`)と `Int64` と `Float64` の引数(`tail64`、`tailf64`)では、`kw` が `kt1000` より経過時間で 2.6〜4.3 倍、計算の時間で 4.3〜5.7 倍速い(5.3 節、5.4 節)。
- `kj` 後の `hello`、`gdepth1`、`typecheck` が前より遅いのは、2 つの入口の分だけ翻訳する文面が増え、`jit-only` が最初の呼び出しで翻訳を待つからだと推測している。
  `kj` は試験の組で、既定の段ではない。
- `ki` の `args6` は前の測定で 825 ms、後で 916 ms だったが、この差はどちらの標本の幅(798〜1,008 ms と 779〜1,107 ms)の中にもある。
  2026-10-28 に負荷の小さいとき(負荷の平均 1.2〜1.6)、前と後の組みの `ki` を交互に 2 回ずつ、各 5 回測り直した。
  `args6` は前が 769 ms と 847 ms、後が 785 ms と 797 ms で、差は分からなかった。
  `fib` は後が約 2 % 速く(前 407 ms と 400 ms、後 395 ms と 395 ms)、`tail32` は後が約 8 % 遅かった(前 941 ms と 933 ms、後 1,016 ms と 1,011 ms)。
  `typecheck` も、設定を回ごとに回した 9 回の測定で、後が約 6 % 遅かった(前 770 ms、後 821 ms)。
  後の組みは、値スタックの範囲の書き直し(3.1 節)のほかに、同時に進む M100 の後の作業の変更を含むので、`tail32` と `typecheck` の遅れがどちらによるかは測っていない。

## 7. 再現の手順

```sh
cd rustkeleut
cargo build --release --features llvm
python3 bench/run.py --diktor ../diktor/_build/install/default/bin/diktor \
  --configs ki,kj,kt1,kt10,kt100,kt1000,kt10000,kt100000,kw,dk,dkir,dktc --repeat 5
python3 bench/corpus.py --diktor ../diktor/_build/install/default/bin/diktor \
  --configs ki,kt1,kt10,kt100,kt1000,kt10000
python3 bench/run.py --diktor ../diktor/_build/install/default/bin/diktor \
  --bench typecheck,tail32b,tail32,tail64,hello \
  --configs ki,kj,kt1,kt10,kt100,kt1000,kt10000,kt100000,kw,dk,dkir --repeat 9 --warmup 1 --interleave
```

1 つ目のコマンドが 2.3 節の始めの測り方で、3 つ目が `typecheck` と `tail32b` の測り直しである。

`perf` の内訳は、`perf record` の後に、`perf report --sort dso,symbol` の番地を `nm` の記号に写して数えた(`keleut` は PIE なので、`perf` が記号を引けない)。
