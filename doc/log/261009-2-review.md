## 1\. 小さくできている部分は、かなりよい

まず、レコード、タプル、関数の引数列を行の機構で扱う設計を評価する。

タプルを \_item ラベルの重複したレコードとし、多引数関数の引数も閉じた \_item 行で表すため、要素数や引数個数の不一致を、別々の専用機構ではなく行の単一化で検出できる。() と空レコードと Unit の関係も、この設計から自然に出てくる。単なる内部表現の節約ではなく、構築、選択、分解、型検査の規則を共用している点がよい。

Scoped Labelsの採用にも筋が通っている。同じラベルを禁止するための追加制約を持ち回らず、重複を認め、最も外側の値を選び、一つ取り除けば内側の値が現れる。この選択には通常の「レコードの更新」と異なる振る舞いが伴うが、仕様は拡張と更新を区別している。利用者の直観と違うところを、曖昧なまま隠してはいない。

構造的な型と名目的な型の役割分担も明瞭だ。名前を付けなくても扱えるデータにはレコードや構造的ヴァリアントを使い、再帰データや利用者定義インスタンスの単位には newtype を使う。透過的な型エイリアスの再帰や、一般的な型レベルのラムダを入れないため、型の等価性や高階型の単一化に際限のない仕事を負わせずに済んでいる。高階型パラメータを残すこと自体を、ただちに「巨大化」と見なす必要はない。

可変状態の扱いも、言語の方向に合っている。run h の内部では可変参照や可変配列を使えるが、リージョンが結果や外側の型へ漏れることは許さない。不変配列と可変配列を分け、freeze の保証を配列一段のスナップショットとして明記し、要素の参照共有とは区別している。この程度まで契約を具体化してあるのは重要だ。region.t も、単純な脱出だけでなく、配列の入れ子や浅いコピーを通じた場合を扱っている。

継続を第一級にしない判断も支持する。resume を操作節の中に限定し、関数へ閉じ込めたり外へ持ち出したりできなくすることで、自由な継続の保存・複製に伴う問題を持ち込まずに、ハンドラの主要な用途を得ている。ただし、再開が高々一回であることは実行時に検査される。この点は「静的なアフィン型システムを持つ」こととは別であり、現在の割り切りとして理解すべきだ。

したがって、予定されている if then else の追加を、小ささへの脅威とは考えない。問題は構文の個数ではなく、その追加が独立した意味論や例外規則を要求するかどうかである。真偽値に対する分岐として既存の核へ落とせるなら、利用者の負担を減らすための有益な糖衣になる。

## 2\. 最大の設計課題は、エフェクトの「型」と「注釈」の境界にある

現在の仕様で最も重い部分は、§13.2だと判断する。

関数を呼ぶ際に、呼び出される関数のエフェクト行と、その位置のエフェクト行を一致させる。サブエフェクティングは持たない。その代わり、束縛の最外に書いた閉じた行は、本体を閉じた行で検査した後、使用時には尾部を開く。一方、入れ子の矢印は開かず、型エイリアスを展開して現れる矢印も最外とは見なさない。

この設計の動機は理解できる。単一化を中心に据えたまま、純粋な関数や限定されたエフェクトを持つ関数を、より広い文脈でも呼びたい。そのための仕組みである。しかし、その代償として「同じ関数型を書いたつもりでも、書いた場所と書き方で扱いが変わる」という学習負担が生じている。

### 型エイリアスへの置き換えが、受理性を変える

これは抽象的な懸念ではなく、既存テストに明確な対照例がある。

直接矢印を書いた次の束縛は、Console の文脈から使える。

keleut

`let k: (Int32) => Int32 = fn(x) => x let use(): Int32 @ Console = k(1)`

ところが、その関数型に別名を付けると、同じ呼び出しが拒否される。

keleut

`type F = (Int32) => Int32 let k: F = fn(x) => x let use(): Int32 @ Console = k(1)`

test/annot\_rows.t の val2 と alval が、この違いを記録している。後者では、エイリアス内の矢印が閉じた純粋な行のまま公開されるためである。型クラスのメソッド署名でも、矢印を直接書くか、エイリアスで書くかによって同種の差がある。

これは実装が仕様に反している例ではない。仕様と実装が一致して、そのように定めている。しかし、設計上の代価は大きい。

型エイリアスは型として透過的でも、束縛注釈のエラボレーションにおいては、単純な置換に対して透明ではない。利用者は「この関数は純粋か」という性質だけでなく、「矢印が表層構文に直接現れているか」まで考えなければならない。共通する型に名前を付けるという普通の整理が、プログラムの受理性を変える。

小ささを追求するなら、ここは構文を一つ削るよりも重要な整理対象だ。必ずしも全面的なサブエフェクティングを導入するという話ではない。束縛の署名と、第一級の値としての関数型とで、何を表し、どの段階で行多相を与えるのかを、より一様に説明できることが重要である。

### 相互再帰の宣言順が、エフェクト注釈の扱いに影響する

§6.3は、同じ再帰群でも、前の関数から後ろの関数を呼ぶ場合と、その逆で扱いが違うことを明記している。後ろにある閉じた行の注釈付き関数を呼ぶ場合には行の一致が必要で、すでに検査を終えた前の関数を呼ぶ場合には、公開用に開いた行を使える。

elab\_rec\_bindings でも、この性質を確認できる。検査済みの束縛について publish\_open を行い、env\_now をその公開型に更新してから、後続の本体を検査している。したがって、これは単なる説明の不備ではなく、逐次的な処理構造が言語の受理規則に現れたものだ。

この非対称性は、小さな言語の規則としてはかなり高価である。let rec ... and ... を一つの相互再帰群として理解した読者に、群の内部の検査順序まで理解させるからだ。

必ずしも、あらゆる相互再帰を最大限に受理する必要はない。少し制限が強くても、群内参照の扱いが一様で、順序に依存しない規則の方が、小さな言語には適する場合がある。ここでは「受理するプログラムの数」と「規則の予測可能性」を、別々に評価すべきだ。

### 等しいエフェクト行の並べ替えが、操作の意味を変える

もう一つ、より意味論に近い問題がある。

異なるラベルの順序は行の型の一致に影響しない。一方、未修飾の操作名が複数のエフェクトに属する場合には、その位置の行で最も左にある候補を選ぶ。明示的な注釈があれば、その記述順を使う。

たとえば、仕様の規則からは次の二つで ask の解決先が異なる。

keleut

`effect A = { ask: () => Int32 } effect B = { ask: () => Int32 } let first(): Int32 @ {A, B} = perform ask() let second(): Int32 @ {B, A} = perform ask()`

first は A.ask、second は B.ask を選ぶ。しかし、行の型としては {A, B} と {B, A} は等しい。

これは型安全性の破れとは別の問題である。Diktorは解決済みの操作を木の ROp に記録して実行時まで運ぶので、静的な選択と実行時の操作は一致する。問題は、型として等しい注釈の並べ替えが、プログラムの意味を変えることだ。

この箇所については、曖昧な場合に修飾を要求する方が、言語全体を単純にできると考える。同じラベルの重複に順序があることと、異なるエフェクトが同名の操作を持つ場合に、行の表示順で一方を選ぶことは、分けて考えられる。現在の規則は、便利な省略のために、型の等価性と名前解決の間へ特別な関係を持ち込んでいる。

## 3\. 型クラスは簡潔だが、目標とする抽象の範囲を再確認する必要がある

Diktorの型クラスは、辞書を渡す代わりに、引数の実行時タグからインスタンスを選ぶ。これは動的型付け化ではなく、静的に制限された多相呼び出しの実装方式である。その制限として、クラスパラメータが少なくとも一つのメソッド引数の型の先頭に現れることを要求している。インスタンスを型構成子単位で一意にし、孤児インスタンスも制限するため、実行時に選ぶものと静的に認めたものを対応させやすい。

この方式は、Eq、Show、算術演算、Functor.map のような操作にはよく合っている。しかし、その制限は「型クラスの少し特殊な書き方」では済まない。

設計記録では、Functor、Applicative、Monad のような型クラスを書けるようにすることが、F\[\_\] を残す理由になっている。ところが、現在の規則では、次のような慣用的な pure は宣言できない。

keleut

`type class Applicative[F[_]] { val pure[A]: (A) => F[A] }`

引数の型の先頭は A であって、クラスパラメータ F ではない。F は返り値側にしか現れないからだ。これは仕様から直接導かれる制限であり、read のような結果側だけにクラスパラメータが現れるメソッドについても、テストの説明で同じ制約を認めている。

したがって、「高階型パラメータを持つので、通常の意味でのApplicativeやMonadをそのまま定義できる」とは言えない。map や、既存の F\[A\] を受け取る操作が書けることと、任意の値から F\[A\] を生成する操作を過負荷にできることは、別の能力である。

ここは、型推論を少し改善すれば済む問題でもない。実行時に選択の根拠となる値がない呼び出しへ、どのインスタンスを使うかという情報をどう伝えるか、という実装方式の問題につながる。

現在の型クラスを「引数の値の型に基づく、制約付きの過負荷」と位置付けるなら、かなりよい限定だ。一方、一般的な型クラスによる抽象化を目標にするなら、この境界は重要な設計判断になる。F\[\_\] 自体を削る必要はないが、それによって何が書けるようになったのかは、代表的な抽象を完全な形で記述して評価する必要がある。

## 4\. リージョンとモジュールには、実装の簡潔さの代価が現れている

リージョンの脱出検査そのものは評価したい。しかし、現在の Heap の扱いには、脱出防止から必然的に出てくるわけではない制限がある。

内側の run では、そのリージョンの Heap が最も左に置かれる。Ref.get などの関数にある一個の Heap は、その最も左のものと対応する。このため、内側の run の本体で、外側の参照を直接読み書きすることができない。参照を外へ漏らさない読み取りでも、リージョンの不一致として拒否される。仕様はこの点を詳しく記述している。

これは保守的な制限であり、ただちに欠陥ではない。ただし、利用者に見える性質は「局所状態が外へ漏れない」だけではなく、「その位置で直接操作できるヒープが最左のものに限定される」である。二つを同じ安全性の説明で済ませない方がよい。Scoped Labelsをヒープにも使ったことによる、表現力との交換条件として説明する方が正確だ。

モジュールについても、入れ子がないこと以上に、名前の衝突規則が気になった。

コンストラクタ名は、モジュールが違っても一つのファイルで見える範囲で一意でなければならない。型クラスのメソッド名にも制限がある。モジュール内の値とトップレベルの値を同名にできず、import時の別名付けもない。モジュールをimportして修飾して利用するつもりでも、公開コンストラクタは非修飾名として見える。

これらが重なると、独立に書いた小さな部品を組み合わせるだけで、各部品の内部命名にまで注意を払う必要が出てくる。小さな言語に高度なモジュールシステムは必須ではないが、名前空間には、部品どうしを不用意に干渉させない役割がある。現在の制限の一部は、その役割を弱めている。

一方、抽象化の道がまったくないわけではない。非公開の名目的な型を公開エイリアスで露出させ、コンストラクタは非公開のままにできる。ここはよい工夫だ。問題は抽象型が表現できるかどうかより、名前空間の規則をどこまで局所的に理解できるかにある。

## 5\. Diktorは、参照実装としても教材としても評価できる

Diktorで最もよいのは、コードの意図だけでなく、誤った実装をしたときに何が壊れるかを説明していることだ。

たとえば unify.ml は、行を伸ばす際の新しい型変数を「現在のレベル」ではなく「伸ばす行変数のレベル」で作る理由を、誤って一般化してしまう例で説明している。bind も、カインド検査、occurs checkとレベル調整、制約伝播、リンクの設定という順序を、入れ替えてはいけない理由とともに示している。さらに、行の書き換えに伴う無限行を、通常のoccurs checkとは別に検出している。ここは教材の中核としてよくできている。

エラボレーションで解決結果を木に書き込む方針もよい。操作名、コンストラクタ引数の格納位置、パターンのフィールド対応、トップレベルの束縛の実体などを、評価器が再解決しない。名前のシャドーイングやモジュールが入ると、型検査器と評価器が同じ文字列を別のものとして扱う事故が起こりうるが、それを構造的に減らしている。

評価器では、左から右の評価順序を明示的な let で固定している。名前付きコンストラクタ引数も、評価はソース順、格納は宣言されたフィールド順として分離している。run 自体は実行時には本体の評価へ消去される。このように、静的に保証する部分と、実行時に実現する部分を切り分けた実装は読みやすい。

ハンドラの実装も、既存ランタイムに任せたから簡単、という説明で終わっていない。Effect.Deep に継続を対応づけつつ、再開しない場合には中断された計算へ discontinue を送り、巻き戻しを通して後始末を実行する。ハンドラ起動ごとに識別子を付け、自分宛ての巻き戻しと外側へ向かう巻き戻しを区別している。この部分は、例外とエフェクトと後始末が交差する実装例として価値が高い。

### 末尾呼び出しを言語の保証として扱っている点がよい

反復を再帰で書く言語では、末尾呼び出しは単なる性能改善ではない。Keleutの仕様は、どこを末尾位置とし、何を一定領域で実行するか、何を保証しないかまで明記している。ハンドラ本体と return 節、操作節の通常の呼び出しと末尾 resume を区別している点も適切だ。

Diktorも、評価器全体を安易に try ... with で包まず、末尾 resume については、操作節の評価の包みを抜けてから継続を発行する専用経路を持つ。tail\_calls.t には、小さなスタック上限の下で十万回の末尾呼び出しを行う期待結果だけでなく、同条件の非末尾再帰が失敗する対照例がある。単に大きな回数を回して「落ちなかった」とするより、よい検証方法だ。

ただし、保守上の注意点はある。末尾位置に関する構造が、通常の eval、eval\_clause\_tail、spine\_has\_resume に現れる。新しい式を追加する際に、これらの対応を崩す可能性がある。予定されている if を既存の分岐へ脱糖できれば、この種の更新箇所を増やさずに済む。独立したASTノードを設ける場合には、通常の評価が正しいだけでは十分ではない。

### 「安全側の保険」と呼ばれている箇所には、修正した方がよいものがある

具体的なコードレビュー上の指摘として、interp.ml のディスパッチのフォールバックを挙げる。

説明では、メソッドのクラスパラメータが現れる引数位置だけを使わなければ、Pick\[A\] のようなクラスで静的検査と実行時が違うインスタンスを選ぶ、と正しく説明している。ところが、dispatch\_positions が位置を返さなかった場合には、すべての引数を探索する分岐が残され、それを「安全側の保険」としている。

現在の受理規則では、この分岐には到達しないとされている。したがって、現時点で利用者のプログラムから誤選択を再現した、という指摘ではない。しかし、不変条件が破れたときの処理としては、方向が逆だ。

参照実装では、もっともらしい別の結果を返すより、内部不変条件の違反として停止する方が安全である。全引数探索は、直前の説明が排除した誤選択を再導入しうる。この分岐は、教育上も「不変条件が満たされない場合には、意味を推測して続行しない」とした方が一貫する。

これは小さな箇所だが、コーディングエージェントによる保守では重要になる。到達不能な分岐は、後の機能追加で到達可能になることがある。そのとき、即座に異常を示す分岐と、誤った意味を黙って補う分岐では、発見の難しさが大きく違う。

### 読める実装ではあるが、入門用の最小実装ではない

elab.ml は、式の型推論だけでなく、注釈の解釈、カインド、宣言登録、インスタンス検査、公開署名、モジュールの平坦化、対話的入力など、多くの責務を持つ。宣言処理も、型の頭、投機的なカインド推論、コンストラクタ等、前方参照用署名、本体検査という段階に分かれている。

説明が丁寧なので追うことはできる。しかし、「HM型推論の最初の教材」として読むには重い。むしろ、「小さな処理系が、行多相、エフェクト、モジュール、REPLを備えるまでに、どこで複雑になるかを学ぶ教材」として優れている。

ここはファイルを機械的に分割すれば解決する問題ではない。単一化、式の推論、宣言処理、セッション管理の間で、何を渡し、何を不変条件とするかが読み取れることの方が重要だ。とくに unify.ml は、外から見えるが外向けではないと説明される関数もあるため、説明上の境界を小さなインターフェースとして固定する価値がある。

また、逐次的なラベル探索に基づく行単一化には、幅の広い行で最悪二次の仕事になる形がある。これはコードから導ける計算量上の性質であり、性能測定の結果ではない。参照・教育用実装としては、現時点で複雑な表現へ置き換える理由にはならない。短く検証しやすい実装を選び、その代償を明記する方が、この実装の目的に合っている。

## 6\. テストと開発記録は強みだが、規範と観測の関係が重要になる

テストは、機能の成功例を並べただけではない。

エフェクトを高階関数やコンストラクタのフィールドへ通して隠してしまう経路、リージョンの脱出、浅い freeze、末尾呼び出し、公開型の注釈、名前解決など、機能どうしの交点を意識した回帰例がある。REPLについても、失敗した入力の束縛を消すだけでなく、その入力中に具体化された弱い型変数を戻すことや、登録したインスタンスが残らないことまで扱っている。ここはよくできている。

spec\_gaps.t が「望ましい挙動」ではなく「未決事項の現在の挙動」を監視するものだと明示し、裁定後に通常の回帰テストへ移す方針もよい。現在の出力をすべて正解として固定してしまう危険を、少なくとも認識している。

さらに設計記録には、LangSpec.md を現在の実装の振る舞いを記述する仕様、sample.kel を規範として扱う区別があり、規範が決めていない事項は裁定として残す、説明とテストの前書きは実測から起こす、といった方針もある。これは、エージェントが実装に合わせて仕様を黙って書き換えることへの防波堤になっている。

そのうえで、二点を重視したい。

第一に、この区別は、設計ログを読み込まなくても最初に分かる必要がある。「現在動くもの」「規範上要求するもの」「将来案」「未決の観測」を、読者が容易に区別できることが望ましい。とくに現在の extern "C" は、実際に呼べる関数が限られ、任意のCライブラリを読み込むものではない。pinned も、現在はスケジューラや外部呼び出しのキャンセルを実現するものではない。こうした境界は、言語の意味論と参照処理系の実装範囲を分けて示した方が誤解されにくい。

第二に、ゴールデンテストの充実とは別に、守りたい不変性を明示する価値がある。

たとえば、束縛名のα変換、依存関係のない純粋な宣言の並べ替え、異なるレコードラベルの順序、型エイリアスへの置換、失敗した対話入力を挟んだ場合の状態、といった変換に対して、何が変わってよく、何が変わってはいけないかである。

現在の実装には、その一部を個別例として扱うテストがすでにある。重要なのは、さらに例を増やすことだけではない。「既存実装がこの結果を返す」という観測から独立して、言語として保存したい性質を定めることだ。今回指摘した、エイリアスへの置換や相互再帰の順序は、まさにその性質をどこまで約束するかという問題である。

参照実装が将来の処理系の比較基準になるなら、値、出力順序、ハンドラの捕捉先、後始末の順序、受理・拒否といった言語上の観測と、Diktor固有の型表示や診断文面を、概念的にも区別しておく方がよい。内部表現を変えた処理系にも引き継ぐべき契約が、そこで明確になる。

文書の保守にも小さなずれはある。DiktorのルートREADMEにあるサンプルの来歴と、test/sample/README.md の記録は一致していない。ただし、後者の記録するサンプルのblobは親の doc/sample.kel と一致しており、サンプル自体が未同期なのではない。この区別は重要だ。問題は主に、読者を正しい現状へ導く入口の説明にある。

文芸的な本文に現れる裁定番号、過去の修正番号、古いサンプルの行番号も、開発者には有益だが、初めて読む者には負荷になる。長く残る本文には原理と現在の契約を置き、来歴は注記やログへ分離する方が、教材としての寿命は長くなる。

## 結論

Keleutの方針は、失敗しているとは考えない。少なくとも現在の仕様と実装には、機能を無造作に積み上げた形跡よりも、複数の用途を少数の機構で扱おうとする明確な意図がある。Diktorにも、型推論の不変条件、評価順序、継続の巻き戻し、静的解決と実行時ディスパッチの一致を、具体的に守ろうとする仕事がある。参照・教育用実装として、十分に価値のある内容だ。

ただし、「実装を短くするための制限」が、必ず「言語を小さくする制限」になるわけではない。

現在もっとも注意すべきなのは、機能の数よりも、型エイリアスを使ったか、矢印を直接書いたか、再帰群のどちら側に宣言したか、エフェクト行をどの順で書いたか、といった事情を利用者が覚えなければならない部分である。また、型クラスの引数側ディスパッチという制限が、目標とする抽象の範囲と一致しているかは、明確にしておく必要がある。

if then else を一つ加えても、この言語の小ささは失われない。むしろ、利用者に処理系の検査順序や表層構文の事情を意識させる例外規則を減らせるかどうかが、Keleutを「小さく、しかも使える言語」にする分岐点だと評価する。
