# Repository Guidelines

## Project Structure & Module Organization

- `doc/sample.kel` is the Keleut language specification: its comments define syntax and semantics. `doc/log/` records design and status notes.
- `diktor/` is a Git submodule containing Diktor, the OCaml reference interpreter of Keleut. It serves as the test oracle for RustKeleut, the main implementation, and as the reference implementation of KIR. Core modules live in `lib/`, the CLI entry point in `bin/main.ml`, and Cram tests in `test/*.t`. Keep implementation logic in the library.
- `diktor/lib/prelude.kel` provides the prelude; `diktor/test/sample/` holds specification fixtures and stubs.
- `rustkeleut/` is the Cargo workspace of RustKeleut, the main implementation (edition 2024, resolver 3, `rust-version = "1.98"`, members `crates/*`; versions are pinned in `Cargo.toml`). `crates/kir` reads, verifies and writes KIR (binary `.kir` and text `.kirt`, byte-compatible with Diktor's `--emit-ir` and `--emit-ir-text`; spec in `doc/IRSpec.md`); `crates/keleut-rtcore` builds `rtcore/` (freestanding C) for x86_64 and wasm32; `crates/keleut-lir` lowers verified KIR to LIR, the shared trap-free CFG that the interpreter, LLVM and WasmGC backends translate (instruction semantics in `rustkeleut/doc/lir.md`); `crates/keleut-rt` is the runtime (tagged 64-bit words, non-moving mark-sweep GC with precise roots (root rules in `rustkeleut/doc/lir.md` 1.8), split value stack, 64 KiB stdout buffer, runtime errors and exit statuses); `crates/keleut-interp` encodes LIR to register bytecode and interprets it on a dedicated thread (`src/native.rs` is the boundary with native code: the `NativeCtx` layout, the entry table, the `krt_*` runtime functions called by JIT code); `crates/keleut-llvm` (cargo feature `llvm`, off by default; links the LLVM 22 shared library through `llvm-sys = 221.1.1`) translates LIR functions, including those with `handle`/`resume`/`perform` (effect instructions call `krt_fx`, which runs the interpreter's instruction on the spilled frame; resumed continuations run in the interpreter), to LLVM IR (one module per function, `default<O2>`; each function has a value-stack entry `tailcc i64 @kfN(ptr %ctx)` in the entry table and a register entry `@kfN.r(ptr %ctx, i64 %env, i64 ×4)` in a second table that JIT-to-JIT direct and closure calls use, passing the environment and the first four arguments in registers; callee frames that fit in the value stack's current chunk are placed inline without calling `krt_prep`) and runs them with LLJIT on a separate compile thread that patches the entry table when a function is ready (tiering in `keleut-interp`'s `native.rs`); `crates/keleut-wasm` translates LIR to a WasmGC module with wasm-encoder, validates every output with wasmparser, runs the trap checker (instructions that can trap may only appear in functions named `safe.*`) and launches Node; `host/keleut-host.mjs` is the Node-side runtime (startup, the stdout convention, diagnostics); `crates/keleut-cli` is the `keleut` binary; `crates/kconform` is the differential test runner. `bench/` holds the backend benchmarks (`programs/*.kel`, the runner `run.py` and the corpus timer `corpus.py`; results in `doc/log/261028-1-m93.md`). `conformance/` holds `known-diffs.toml`, the generated `corpus/` (`.kel` files extracted from `diktor/test/*.t`), `kir-bad/` (malformed KIR that must be rejected with exit 65) and the other cram-form conformance tests.
- `reference/` contains ignored local reference material, including `MiniLang.scala` when available; a fresh clone does not supply it.

## Build, Test, and Development Commands

Initialize the interpreter from the repository root:

```sh
git submodule update --init --recursive
cd diktor
```

Use an opam switch with OCaml >= 5.2. Run these commands inside `diktor/`:

- `opam install dune menhir sedlex` — install build dependencies (Dune >= 3.0).
- `dune build` — compile the interpreter and library.
- `dune runtest` — run the Cram golden tests.
- `dune exec diktor -- path/to/program.kel` — execute a Keleut file; add `--type-check` before the path to check types only.
- `awk -f tools/weave.awk lib/unify.ml > /tmp/unify.md` — render a literate source chapter as Markdown.
- `python3 tools/litwrap.py lib/unify.ml` — wrap long lines in literate article blocks after Japanese commas.
- `python3 tools/litcheck.py` — after comment-only edits, confirm that the code tokens still match `HEAD` and that the comments keep the literate conventions (no `"` or unpaired `(*`, block indentation, line width).

Run these commands inside `rustkeleut/` (no rustup is needed; only the x86_64 standard library):

- `cargo build --release`, `cargo test`, `cargo clippy -- -D warnings`, `cargo fmt --check`, `cargo build --no-default-features` — the checks every change must pass; also run `cargo test --features llvm` and `cargo clippy --features llvm --all-targets -- -D warnings`, which build the LLVM back end (`llvm-config` of LLVM 22 must be on PATH).
- `target/release/keleut dump llvm FILE` — print the LLVM IR the JIT makes for every eligible function (needs `--features llvm`).
- `cargo test -p kir` — KIR reader, writer and verifier tests; set `KIR_CORPUS_DIR` or `KIR_DIKTOR` for the optional corpus and Diktor cross-checks.
- `target/release/keleut kir verify|dis|asm FILE`, `target/release/keleut kir tables` — KIR tools: `verify` reads and verifies (exit 65 when invalid), `dis` prints canonical text, `asm FILE.kirt -o OUT.kir` writes canonical binary, `tables` prints the builtin tables like `diktor --dump-ir-tables`. `--max-nest N` and `--native-stack BYTES` change the nesting limit and the stack of the KIR thread (a stack too small for the limit lowers the limit).
- `target/release/keleut dump lir [--check] [--unassigned] FILE` — lower KIR to LIR, verify it and print it (`--check` prints nothing; exit 65 for invalid KIR, 70 when lowering or LIR verification fails). `cargo test -p keleut-lir` lowers the KIR fixtures and depth-100,000 chains; set `KELEUT_DIKTOR` to also emit and lower every corpus program, or `KIR_CORPUS_DIR` for a directory of `.kir` files.
- `target/release/keleut run [--max-depth N] [--native-stack BYTES] [--gc-stress] [--no-yield-prune] FILE.kel... | FILE.kir` — run a program (on the interpreter by default; in a `--features llvm` build on the LLVM JIT with `--tier threshold=1000`, see below; `--gc-stress` collects garbage at the first allocation of every allocation site (top frame's function and point), then about every W/64 allocations, where W is the work of the previous collection, with a pseudo-random jitter; it does not collect at every allocation, and caller frames' roots are exercised only when a collection happens while they are suspended; `KELEUT_GC_STATS=1` prints collection counts and time to stderr; `.kel` goes through the Rust front end keleut-front by default, and with `--frontend diktor` through `$KELEUT_DIKTOR --emit-ir`, else `diktor` on PATH; `--backend jit` (only in a build with `--features llvm`, else exit 4; the default backend in such a build, and selected when `--backend` is omitted and `--tier` is not `interp-only`) runs with the LLVM JIT: `--tier threshold=N` (default `threshold=1000`) counts interpreter entries and compiles a function in the background after N calls, `jit-only` compiles each eligible function on its first call, `alternating=SEED` also does so and picks the tier at every JIT function entry with a seeded xorshift, `mixed=SEED` compiles only a seed-chosen half of the functions, and `interp-only` interprets everything; functions whose estimated translation cost exceeds `JIT_COST_MAX` in `keleut-interp`'s `native.rs` stay in the interpreter under every tier; with `threshold=N` the program starts on the interpreter without waiting for LLJIT and the stubs to be ready, and `keleut run` exits without waiting for the compile thread; when the program ends while a background translation is in progress, `keleut run` exits without waiting for it; `--backend interp` and `--backend wasm` accept and ignore `--tier`; when the native stack gets within 64 KiB of the reserve check, JIT functions fall back to the interpreter at entry, so deep non-tail recursion still reaches the logical limit with a small `--native-stack`; `KELEUT_JIT_STATS=1` prints compiled-function counts and native stack use; `--backend wasm` runs the WasmGC backend under Node 26.9.0 or later (`$KELEUT_NODE`, else `node` on PATH) with a raised `RLIMIT_STACK` and `--stack-size`; when V8's own heap runs out, Node aborts (SIGABRT) and keleut exits 70 instead of 3, `cancel` clauses do not run, and stdout still held in the host's buffer is lost (only allocations over `N_alloc_max` become `ERROR(OutOfMemory)` with exit 3, which `conformance/oom/` tests; a known deviation from §15.5, P252/V215, not registered as a known diff); signals that were ignored when keleut started (`nohup`, background jobs) stay ignored and are not forwarded to Node; `--gc-stress` and `--native-stack` affect only the interpreter and the JIT, and `--backend wasm` accepts and ignores them; `--no-yield-prune` turns off pass 11: by default a yield that reaches a resume point marked `noyield` is an internal error with exit 70, while with the flag no resume point is marked, so such a program runs normally). Set `KELEUT_DIKTOR` for `cargo test -p keleut-cli --test run_cmd` to also compare every corpus program with Diktor.
- `target/release/keleut build --target wasm -o DIR [--frontend diktor|rust] FILE.kel... | FILE.kir` — write `program.wasm`, `rt.wasm` and `main.mjs` to `DIR` (`.kel` is read as in `keleut run`); `node DIR/main.mjs` runs the program on its own (a `Worker` provides the stack). `KELEUT_WASM_STATS=1` prints translation statistics. Set `KELEUT_DIKTOR` for `cargo test -p keleut-wasm` to translate, validate and trap-check every corpus program, and for `cargo test -p keleut-cli --test wasm_cmd` to compare the large-frame and many-block cases with the interpreter.
- `target/release/keleut run [--frontend rust|diktor] FILE.kel...` — `rust`, the default since M99, type-checks and writes KIR in-process with keleut-front instead of `diktor --emit-ir` (same diagnostics and exit codes as `diktor --emit-ir`; accepts `--no-prelude`, `--prelude`, `--import-path` and `--strict-exhaustive`; the front-end thread gets the default 8 GiB stack, and `--native-stack` stays the interpreter's; under a finite `RLIMIT_AS` (`ulimit -v`) `keleut run`, and `keleut emit-kir` without `--native-stack`, cap that stack at a quarter of the limit, halve it down to 16 MiB while the thread cannot be created, and lower the nesting limit to what fits, e.g. 63488 under `ulimit -v 524288`); `diktor` runs `$KELEUT_DIKTOR --emit-ir` as a child process.
- `target/release/keleut repl [--no-prelude | --prelude PATH] [--max-nest N] [--native-stack BYTES] [--max-depth N] [--gc-stress] [--no-yield-prune]` — interactive session with the same output as `diktor --repl` (keleut-front type-checks each input; each accepted input becomes one KIR unit; the prelude runs once at start and after `:reset`, and a runtime error there exits 3 like Diktor; the session keeps one live interpreter heap: each input's KIR unit is verified on its own (`kir::verify_extension`), lowered and appended to the LIR program (`keleut_lir::Extender`), and only its top-level code runs, and rejected inputs are undone through change logs rather than copies, so the time per input does not depend on the number of earlier inputs, apart from work proportional to the number of declared classes and module values (as in Diktor); memory still grows by about 11 KB per input, against about 2 KB in Diktor, because every unit's code is kept; a runtime error discards the input's names and the values of its globals and instances but keeps the unit's code in the program; `KELEUT_REPL_STATS=1` prints the KIR and LIR functions added per input to stderr; `--native-stack` here is the front-end stack, as in `keleut check`; `--max-depth`, `--gc-stress` and `--no-yield-prune` work as in `keleut run`; `--backend`, `--tier`, `--frontend` and `--strict-exhaustive` are accepted and ignored; record fields print in the order of the type's row, not Diktor's construction order (V221)). Set `KELEUT_DIKTOR` for `cargo test -p keleut-cli --test repl_cmd` to feed every corpus program to both REPLs and to compare `keleut run --frontend rust` with Diktor.
- `python3 bench/run.py --diktor PATH [--keleut PATH] [--configs ki,kj,kt1000,kw,dk,...] [--repeat N] [--warmup N] [--interleave] [--bench NAME,...] [--json OUT]` — time the programs in `bench/programs/` on each configuration (`--interleave` runs every configuration once per round instead of all repeats back to back; `--warmup N` discards N runs per configuration first) (`ki` interpreter, `kj` jit-only, `ktN` threshold=N, `kd` default, `kw` WasmGC, `dk` Diktor's tree evaluator, `dkir` `diktor --run-ir`, `dktc` `diktor --type-check`); KIR is written to a temporary directory, and the run fails if any configuration's stdout differs. `python3 bench/corpus.py --diktor PATH` sums the time of every `conformance/corpus/` program per configuration (the short-program cost of a tier setting).
- `target/release/kconform --pairs dk,kr-ki,kr-kj,kr-kt,kr-ka,kr-km,kr-kw,x-ir --suite all` — compare the Rust front end feeding each backend (`kr-ki` interpreter, `kr-kj` JIT, `kr-kt` `--tier threshold=1`, `kr-ka` alternating tiers with seeds 1..8, `kr-km` `mixed=1..4`, `kr-kw` WasmGC; `kr-kj`, `kr-kt`, `kr-ka` and `kr-km` need a `--features llvm` build and are not default pairs) against Diktor; the pairs whose KIR Diktor writes (`ki`, `kj`, `kt`, `ka`, `km`, `kw` and `kconform expect`) pass `--frontend diktor` to `keleut run`, and the `kr-*` pairs pass `--frontend rust`; like `ki kj kt ka km kw`, the `kr-*` pairs must agree exactly with each other; in every RustKeleut backend pair (`ki`, `kj`, `kw`, `kr-ki`, ...) the shim routes `diktor --repl` to `keleut repl`, which always runs on the interpreter, so the backend pairs agree on REPL blocks. `target/release/kconform expect conformance/frontend-depth/repl.t` checks that the REPL continues after the parse and type-check limits.
- `target/release/kconform --pairs ki,kw --suite all` — compare the WasmGC backend (`kw`) with the interpreter; RustKeleut backends must agree exactly (no known-diff entry applies to a difference between backend pairs). G clauses are captured as lists of per-function frame records and resumed through each function's resume entry (`br_table` to the block after the call); `conformance/effects/` and `conformance/depth/gresume.t` test them.
- `target/release/kconform --pairs ki,kj --suite all` — compare the LLVM JIT (`kj`) with the interpreter; needs a `keleut` built with `cargo build --release --features llvm` (kconform runs the `keleut` next to itself), so `kj` is not in the default pair set; `--extra=--gc-stress` also stresses `kj`. The same holds for the tiering pairs `kt` (`--tier threshold=1`), `ka` (`alternating=1..8`, eight runs) and `km` (`mixed=1..4`): `kconform --pairs ki,kj,kt,ka,km --suite all` and `--suite depth` compare all of them. For the LLVM pairs (`kj`, `kt`, `ka`, `km`, `kr-kj`, `kr-kt`, `kr-ka`, `kr-km`; the shim recognises them from the pair's options, not the pair's name) the shim drops a command's own `--backend` so that the pair's backend runs; for other pairs a command's own `--backend` wins, and kconform prints a `組の後段の上書き` line for every command whose `--backend` differs from the pair's. Under memory exhaustion (`ulimit -v`, Rust or LLVM heaps) the JIT pairs can abort with SIGABRT (exit 134) instead of exiting 3 (a known deviation like V215, recorded in M92). `cargo test --release --features llvm -p keleut-llvm --test tier_alt` runs 1e8 tail calls alternating between the interpreter and the JIT on a 512 KiB stack.
- `target/release/kconform --pairs dk-ir,ki --suite depth` — run the logical-depth tests in `conformance/depth/` (they pass `--max-depth` to `diktor --run-ir` for `dk-ir`); add `--extra=--no-yield-prune` or `--extra=--gc-stress` to any run to repeat it without yield pruning or with frequent collection (see `--gc-stress` above; `--gc-stress` stresses `ki`, `kj`, `kt`, `ka`, `km`, `kr-ki`, `kr-kj`, `kr-kt`, `kr-ka` and `kr-km`; `kw` and `kr-kw` ignore it; `conformance/gc/` holds the collector tests: a 10^6-element list under `--native-stack 512k` and programs that must stay under `ulimit -v 524288`).
- `target/release/kconform --pairs dk ../diktor/test/*.t` — run Diktor's cram tests through the PATH shim and compare each command with the recorded expectation (add `--check-shim` to fail when a `diktor` call bypasses the shim).
- `target/release/kconform expect conformance/kir-bad/*.t` — run conformance tests against their recorded expectations only; `--promote` rewrites them with the actual results (review the diff).
- `target/release/kconform kir-roundtrip` — on every corpus program, compare `keleut kir dis` and `asm` with Diktor's text and binary output and check the text → binary → text round trip.
- `target/release/kconform extract-corpus [--check]` — regenerate (or check) `conformance/corpus/` after `diktor/test` changes.
- kconform finds the real Diktor through `--diktor`, then `KELEUT_DIKTOR`, then `../diktor/_build/install/default/bin/diktor`, and the `keleut` next to itself, so build both with `cargo build --release` first.

## Coding Style & Naming Conventions

Follow existing OCaml code: two-space indentation, `snake_case` values and filenames, and capitalized modules and constructors. Preserve Japanese literate explanations and column-zero `(* ... *)` article blocks. Do not run `ocamlformat` or `dune fmt`; they break that layout despite the existing `.ocamlformat` file. In `rustkeleut/`, write rustdoc comments in Japanese, and format with `cargo fmt`; the literate layout does not apply there. Follow nearby `.kel` examples when editing the specification.

## Testing Guidelines

Add focused regression cases to descriptive `test/*.t` files such as `trailing_comma.t`. Cover successful behavior and relevant diagnostics or exit codes. No numeric coverage threshold is configured.

RustKeleut conformance tests are cram-form `.t` files under `rustkeleut/conformance/`, with their `.kel`, `.kir` or `.kirt` inputs beside them; they call `keleut` directly, and `kconform expect` compares them with the recorded output. Never change `diktor/test` expectations for RustKeleut's sake; record unavoidable differences in `conformance/known-diffs.toml` with a ledger number.

Review golden-output differences before `dune promote`; commit expectation updates separately from implementation changes. Never hand-edit `test/sample/sample.kel`: synchronize it from the parent specification using `test/sample/README.md`, updating provenance and affected source references together.

## Commit & Pull Request Guidelines

Use small logical commits with `scope: summary` subjects; history uses `spec:`, `diktor:`, `test:`, and `doc:`. Follow `.claude/rules/commit.md`: Japanese messages on `ja/` branches, English elsewhere; never bypass hooks or signing.

PR descriptions should explain behavior changes, cite affected specification sections or issues, and report validation commands and results. Commit submodule changes within `diktor/`, then record its updated revision in the parent repository.
