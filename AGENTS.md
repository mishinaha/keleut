# Repository Guidelines

## Project Structure & Module Organization

- `doc/sample.kel` is the Keleut language specification: its comments define syntax and semantics. `doc/log/` records design and status notes.
- `diktor/` is a Git submodule containing Diktor, the OCaml reference interpreter of Keleut. It serves as the test oracle for RustKeleut, the main implementation, and as the reference implementation of KIR. Core modules live in `lib/`, the CLI entry point in `bin/main.ml`, and Cram tests in `test/*.t`. Keep implementation logic in the library.
- `diktor/lib/prelude.kel` provides the prelude; `diktor/test/sample/` holds specification fixtures and stubs.
- `rustkeleut/` is the Cargo workspace of RustKeleut, the main implementation (edition 2024, resolver 3, `rust-version = "1.98"`, members `crates/*`; versions are pinned in `Cargo.toml`). `crates/kir` reads, verifies and writes KIR 1.0 (binary `.kir` and text `.kirt`, byte-compatible with Diktor's `--emit-ir` and `--emit-ir-text`; spec in `doc/IRSpec.md`, whose section 14 gives the version rules: writers write 1.0, and both Diktor's and RustKeleut's readers accept every minor version of major 1, reject any other major (including the draft 0.y versions) and reject any required-feature bit, since 1.0 defines none; a minor version may only add skippable sections and instructions guarded by a feature bit, and a change of meaning or encoding raises the major); `crates/keleut-rtcore` builds `rtcore/` (freestanding C) for x86_64 and wasm32; `crates/keleut-lir` lowers verified KIR to LIR, the shared trap-free CFG that the interpreter, LLVM and WasmGC backends translate (instruction semantics in `rustkeleut/doc/lir.md`); `crates/keleut-rt` is the runtime (tagged 64-bit words, non-moving mark-sweep GC with precise roots (root rules in `rustkeleut/doc/lir.md` 1.8), split value stack, 64 KiB stdout buffer, runtime errors and exit statuses); `crates/keleut-interp` encodes LIR to register bytecode and interprets it on a dedicated thread (`src/native.rs` is the boundary with native code: the `NativeCtx` layout, the entry table, the `krt_*` runtime functions called by JIT code); `crates/keleut-llvm` (cargo feature `llvm`, on by default in `keleut-cli` and `keleut-llvm`, and left out by `cargo build --no-default-features`; links the LLVM 22 shared library through `llvm-sys = 221.1.1`) translates LIR functions, including those with `handle`/`resume`/`perform` (effect instructions call `krt_fx`, which runs the interpreter's instruction on the spilled frame; resumed continuations run in the interpreter), to LLVM IR (one module per function, `default<O2>`; each function has a value-stack entry `tailcc i64 @kfN(ptr %ctx)` in the entry table and a register entry `@kfN.r(ptr %ctx, i64 %env, i64 ×4)` in a second table that JIT-to-JIT direct and closure calls use, passing the environment and the first four arguments in registers; callee frames that fit in the value stack's current chunk are placed inline without calling `krt_prep`) and runs them with LLJIT on a separate compile thread that patches the entry table when a function is ready (tiering in `keleut-interp`'s `native.rs`); `crates/keleut-wasm` translates LIR to a WasmGC module with wasm-encoder, validates every output with wasmparser, runs the trap checker (instructions that can trap may only appear in functions named `safe.*`) and launches Node; `host/keleut-host.mjs` is the Node-side runtime (startup, the stdout convention, diagnostics); `crates/keleut-front` is the Rust front end (lexer, an LR(1) parser driven by tables that `tools/gen_tables.ml` generates with menhir from Diktor's `lib/parser.mly` (steps at the top of that file; never edit `src/tables.rs` by hand), desugaring, type checker, exhaustiveness check and KIR writer; it aims at Diktor's output, diagnostics and exit codes and serves `keleut check`, `keleut emit-kir`, `keleut dump tokens|ast`, `keleut repl` and, by default, `keleut run`); `crates/keleut-cli` is the `keleut` binary; `crates/kconform` is the differential test runner. `bench/` holds the backend benchmarks (`programs/*.kel`, the runner `run.py` and the corpus timer `corpus.py`; results in `doc/log/261028-1-m93.md`). `conformance/` holds `known-diffs.toml`, the generated `corpus/` (`.kel` files extracted from `diktor/test/*.t`), `kir-bad/` (malformed KIR that must be rejected with exit 65), `kir-fixtures/` (valid KIR samples, one directory per minor version, now `1.0/`, that both readers must read), `depth/` (logical-depth tests, run by `--suite depth`), `frontend-depth/` (nesting limits of keleut-front, run only by `kconform expect`), `recshow/` (runtime-error values that contain records, each written both as a top-level runtime error and as a `cancel`-suppression record line; IRSpec appendix B leaves the order of fields with different labels to the reader, so kconform sorts the fields of suppression record lines before comparing them with the record and with Diktor, while the RustKeleut backend groups must agree byte for byte; expectations in RustKeleut's spelling; case 9 runs a hand-written `nomatch.kirt` assembled into `nomatch.kir`) and the other cram-form conformance tests (the table in `conformance/README.md`).
- `reference/` contains ignored local reference material, including `MiniLang.scala` when available; a fresh clone does not supply it.

## Build, Test, and Development Commands

Initialize the interpreter from the repository root:

```sh
git submodule update --init --recursive
cd diktor
```

Use an opam switch with OCaml >= 5.2. Run these commands inside `diktor/`:

- `opam install dune menhir sedlex` — install build dependencies (Dune >= 3.0).
- `dune build` — compile the interpreter and library.
- `dune runtest` — run the Cram golden tests.
- `dune exec diktor -- path/to/program.kel` — execute a Keleut file; add `--type-check` before the path to check types only.
- `awk -f tools/weave.awk lib/unify.ml > /tmp/unify.md` — render a literate source chapter as Markdown.
- `python3 tools/litwrap.py lib/unify.ml` — wrap long lines in literate article blocks after Japanese commas.
- `python3 tools/litcheck.py` — after comment-only edits, confirm that the code tokens still match `HEAD` and that the comments keep the literate conventions (no `"` or unpaired `(*`, block indentation, line width).

Run these commands inside `rustkeleut/` (no rustup is needed; only the x86_64 standard library):

- `cargo build --release`, `cargo test`, `cargo clippy --all-targets -- -D warnings`, `cargo build --no-default-features`, `cargo test --no-default-features`, `cargo fmt --check` — the checks every change must pass; the default build includes the LLVM back end, so `llvm-config` of LLVM 22 must be on PATH, and `--no-default-features` builds the interpreter and WasmGC back ends only (`cargo clippy --no-default-features --all-targets -- -D warnings` checks that configuration).
- `target/release/keleut dump llvm FILE` — print the LLVM IR the JIT makes for every eligible function (needs the default feature `llvm`; a `--no-default-features` build exits 4).
- `cargo test -p kir` — KIR reader, writer and verifier tests; set `KIR_CORPUS_DIR` or `KIR_DIKTOR` for the optional corpus and Diktor cross-checks.
- `target/release/keleut kir verify|dis|asm FILE`, `target/release/keleut kir tables` — KIR tools: `verify` reads and verifies (exit 65 when invalid), `dis` prints canonical text, `asm FILE.kirt -o OUT.kir` writes canonical binary, `tables` prints the builtin tables like `diktor --dump-ir-tables`. `--max-nest N` and `--native-stack BYTES` change the nesting limit and the stack of the KIR thread (a stack too small for the limit lowers the limit).
- `target/release/keleut dump lir [--check] [--unassigned] FILE` — lower KIR to LIR, verify it and print it (`--check` prints nothing; exit 65 for invalid KIR, 70 when lowering or LIR verification fails). `cargo test -p keleut-lir` lowers the KIR fixtures and depth-100,000 chains; set `KELEUT_DIKTOR` to also emit and lower every corpus program, or `KIR_CORPUS_DIR` for a directory of `.kir` files.
- `target/release/keleut check [--no-prelude | --prelude PATH] [--import-path DIR] [--strict-exhaustive] [--quiet] [--max-nest N] [--native-stack BYTES] FILE.kel...` — type-check with keleut-front (same output and exit codes as `diktor --type-check`; `--native-stack` sets the checker thread's stack, default 8 GiB, and lowers `--max-nest` to what fits). `target/release/keleut emit-kir [--text] [-o OUT] [same front-end options] FILE.kel...` writes KIR 1.0 (binary, or canonical text with `--text`; standard output without `-o`), byte-identical with `diktor --emit-ir` and `--emit-ir-text` on every corpus program. `target/release/keleut dump tokens|ast FILE.kel...` prints Diktor's `--dump-tokens` and `--dump-ast` formats. Set `KELEUT_FRONT_DIKTOR` (and optionally `KELEUT_FRONT_CORPUS`, default `conformance/corpus`) for `cargo test -p keleut-front` to compare tokens, ASTs, type-check output and written KIR with Diktor on every corpus program.
- `target/release/keleut run [--max-depth N] [--native-stack BYTES] [--gc-stress] [--no-yield-prune] FILE.kel... | FILE.kir` — run a program (on the LLVM JIT with `--tier threshold=1000` by default, see below, and on the interpreter in a `--no-default-features` build; `--gc-stress` collects garbage at the first allocation of every allocation site (top frame's function and point), then about every W/64 allocations, where W is the work of the previous collection, with a pseudo-random jitter; it does not collect at every allocation, and caller frames' roots are exercised only when a collection happens while they are suspended; `KELEUT_GC_STATS=1` prints collection counts and time to stderr; `.kel` goes through the Rust front end keleut-front by default, and with `--frontend diktor` through `$KELEUT_DIKTOR --emit-ir`, else `diktor` on PATH; `--backend jit` (only in a build with the default feature `llvm`, else exit 4; the default backend in such a build, and selected when `--backend` is omitted and `--tier` is not `interp-only`) runs with the LLVM JIT: `--tier threshold=N` (default `threshold=1000`) counts interpreter entries and compiles a function in the background after N calls, `jit-only` compiles each eligible function on its first call, `alternating=SEED` also does so and picks the tier at every JIT function entry with a seeded xorshift, `mixed=SEED` compiles only a seed-chosen half of the functions, and `interp-only` interprets everything; functions whose estimated translation cost exceeds `JIT_COST_MAX` in `keleut-interp`'s `native.rs` stay in the interpreter under every tier; with `threshold=N` the program starts on the interpreter without waiting for LLJIT and the stubs to be ready, and `keleut run` exits without waiting for the compile thread; when the program ends while a background translation is in progress, `keleut run` exits without waiting for it; `--backend interp` and `--backend wasm` accept and ignore `--tier`; when the native stack gets within 64 KiB of the reserve check, JIT functions fall back to the interpreter at entry, so deep non-tail recursion still reaches the logical limit with a small `--native-stack`; `KELEUT_JIT_STATS=1` prints compiled-function counts and native stack use; `--backend wasm` runs the WasmGC backend under Node 26.9.0 or later (`$KELEUT_NODE`, else `node` on PATH) with a raised `RLIMIT_STACK` and `--stack-size`; the stack is `(L + R) × B_prog + 32 MiB` with `R = max(1024, L / 64)`, where `B_prog = B_wasm + k × (B_wasm − E_rres) + (r × B_wasm − E_rth if r ≥ 1)` (1,536 bytes at `k = r = 0`, 2,896 at `k = 1`, 2,752 at `r = 1`, 10,432 at `r = 6`), `k` and `r` are counted along the heaviest single chain of clauses in which each clause writes the next one's handler expression directly in its body (no function body in between): the chain may mix `cancel` clauses, `return` clauses and `Never`-returning (class N) operation clauses, `k` counts its `cancel` clauses that contain a handler expression, and `r` counts its `return` and class-N clauses that can reach, through direct calls, a function on a call cycle or one that calls a value, a method, `perform` or `$rt_handle` (a `cancel` clause runs at the depth of its `$rt_handle`, and `$rt_handle` replaces itself with a `return` or class-N clause by a tail call, so every clause of the chain sits at the logical depth of the function that wrote the outermost handler expression; a class-N clause that is the only `return` or class-N clause of its chain, whose measured frames fit in `B_wasm`, is not counted; `KELEUT_WASM_STATS=1` prints the chain's `k`, `r` and `B_prog`, e.g. `k = 5`, `r = 4` and 14,160 bytes for four alternating pairs of `cancel` and class-N clauses); a program with `k ≥ 1` or `r ≥ 1` gets a larger stack, which at the default L exceeds V8's `--stack-size` limit and moves it to the `Worker` path (`keleut build` writes `bProg` and `cancelNest` into `main.mjs`'s `META`, and the host sizes the `Worker` stack from `bProg`); the stack is cut at `STACK_CAP` (16 GiB), never below the `k = r = 0` size; `KELEUT_WASM_STATS=1` adds `k`, `B_prog`, `r` and the cut (`STACK_CAP` or the `k = 0` size) to the statistics line, and the host prints `keleut-host: path=worker stackSizeMb=N` or `keleut-host: path=direct` to stderr before starting; when V8's own heap runs out, Node aborts (SIGABRT) and keleut exits 70 instead of 3, `cancel` clauses do not run, and stdout still held in the host's buffer is lost (only allocations over `N_alloc_max` become `ERROR(OutOfMemory)` with exit 3, which `conformance/oom/` tests; a known deviation from §15.5, P252/V215, not registered as a known diff, and kept at 70 by P261, which closes V215); under a finite `ulimit -v` (`RLIMIT_AS`), `keleut run --backend wasm` exits 70 in each of these measured cases: at 512 MiB Node does not start (V8 cannot reserve its `CodeRange`, SIGTRAP), at 2 GiB the host cannot create the `Worker` (the run thread) with its stack of about 1.6 GiB (`EAGAIN`), and at 4 GiB the `Worker` stops with `ERR_WORKER_OUT_OF_MEMORY`; the program runs at 8 GiB (measured at the default L with `B_wasm`; programs with `k ≥ 1` or `r ≥ 1` get a larger stack (`B_prog` > `B_wasm`), which is expected to move these bounds up; IRSpec section 1 lists these exits); signals that were ignored when keleut started (`nohup`, background jobs) stay ignored and are not forwarded to Node; `--gc-stress` affects only the interpreter and the JIT, and `--native-stack` sets the stack of the interpreter and the JIT, of the Rust front end and of KIR reading and verification (plan 6.11; the KIR nesting limit drops to what fits, so a deep `.kir` exits 65 rather than overflowing); `--backend wasm` accepts both and ignores them for the back end; `--no-yield-prune` turns off pass 11: by default a yield that reaches a resume point marked `noyield` is an internal error with exit 70, while with the flag no resume point is marked, so such a program runs normally). Set `KELEUT_DIKTOR` for `cargo test -p keleut-cli --test run_cmd` to also compare every corpus program with Diktor.
- `target/release/keleut build --target wasm -o DIR [--frontend diktor|rust] FILE.kel... | FILE.kir` — write `program.wasm`, `rt.wasm` and `main.mjs` to `DIR` (`.kel` is read as in `keleut run`); `node DIR/main.mjs` runs the program on its own (a `Worker` provides the stack); run that way under `ulimit -v 524288` (512 MiB), V8 cannot reserve its `CodeRange` and Node ends with 133 (SIGTRAP) before the program starts (outside IRSpec section 1, whose readers are `diktor --run-ir` and `keleut run`). `KELEUT_WASM_STATS=1` prints translation statistics. Set `KELEUT_DIKTOR` for `cargo test -p keleut-wasm` to translate, validate and trap-check every corpus program, and for `cargo test -p keleut-cli --test wasm_cmd` to compare the large-frame and many-block cases with the interpreter.
- `target/release/keleut run [--frontend rust|diktor] FILE.kel...` — `rust`, the default since M99, type-checks and writes KIR in-process with keleut-front instead of `diktor --emit-ir` (same diagnostics and exit codes as `diktor --emit-ir`; accepts `--no-prelude`, `--prelude`, `--import-path` and `--strict-exhaustive`; `--native-stack BYTES` sets the front-end thread's stack as well as the interpreter's and the JIT's (V227; the parse nesting limit drops to what fits, e.g. 128 levels at 512k in a release build, and a value below the front end's minimum (about 384 KiB in a release build, 2.3 MiB in a debug build) is raised to it; KIR reading, verification and lowering use the same stack size); without `--native-stack` the front-end thread gets the default 8 GiB stack, and under a finite `RLIMIT_AS` (`ulimit -v`) `keleut run` and `keleut emit-kir` cap that stack at a quarter of the limit, halve it down to 16 MiB while the thread cannot be created, and lower the nesting limit to what fits, e.g. 63488 under `ulimit -v 524288`); `diktor` runs `$KELEUT_DIKTOR --emit-ir` as a child process.
- `target/release/keleut compat-diktor [RUN-OPTIONS --] DIKTOR-ARGS...` — interpret Diktor's options the way `diktor` does (the last of `--type-check`, `--repl`, `--dump-tokens`, `--dump-ast` wins; `--no-prelude`, `--prelude`, `--import-path`, `--strict-exhaustive`; every input file is read as Keleut source, even one named `.kir` or `.kirt`) and run the matching command in-process: no mode → `keleut run` with RUN-OPTIONS (`--backend`, `--tier`, `--max-depth`, `--native-stack`, `--frontend`, `--gc-stress`, `--no-yield-prune`), `--type-check` → `keleut check` (with `--native-stack` only, so parsing has the same limit as in a run), `--dump-tokens`/`--dump-ast` → `keleut dump tokens|ast`, `--repl` → `keleut repl`; RUN-OPTIONS placed before a `--` apply, and after `--` come only Diktor's arguments (still parsed as options); without `--`, RUN-OPTIONS other than `--max-depth` may be mixed with Diktor's options; Diktor's IR options (`--emit-ir`, `--emit-ir-text`, `--run-ir`, `--via-ir`, `--dump-ir-tables`, and `--max-depth` among Diktor's arguments, which Diktor's tree evaluator ignores), `--help`/`-h` and other usage errors exit 64 with a keleut message. kconform's shim sends Diktor's run invocations of the pairs `ki` ... `kw` and `kr-*` here as `compat-diktor PAIR-OPTIONS -- ARGS`; invocations with an argument that is not valid UTF-8 go to the real diktor.
- `target/release/keleut repl [--no-prelude | --prelude PATH] [--max-nest N] [--native-stack BYTES] [--max-depth N] [--gc-stress] [--no-yield-prune]` — interactive session with the same output as `diktor --repl` (keleut-front type-checks each input; each accepted input becomes one KIR unit; the prelude runs once at start and after `:reset`, and a runtime error there exits 3 like Diktor; the session keeps one live interpreter heap: each input's KIR unit is verified on its own (`kir::verify_extension`), lowered and appended to the LIR program (`keleut_lir::Extender`), and only its top-level code runs, and rejected inputs are undone through change logs rather than copies, so the time per input does not depend on the number of earlier inputs, apart from work proportional to the number of declared classes and module values (as in Diktor); memory still grows by about 11 KB per input, against about 2 KB in Diktor, because every unit's code is kept; a runtime error discards the input's names and the values of its globals and instances but keeps the unit's code in the program; `KELEUT_REPL_STATS=1` prints the KIR and LIR functions added per input to stderr; an input whose nesting reaches the KIR writer's limit (100,000 levels) is not accepted: it gets the KIR writer's limit line (`処理系の限度: KIR の書き出しで入れ子が深すぎます`), as `diktor --emit-ir` does, and an input nested deeply enough to reach keleut-front's parser limit (counted by tree depth, V237) gets the parser's limit line instead, as in `keleut run`, while `diktor --repl` accepts both (V224, closed as an implementation limit by D577; IRSpec section 1); `--native-stack` here is the front-end stack, as in `keleut check`; `--max-depth`, `--gc-stress` and `--no-yield-prune` work as in `keleut run`; `--backend`, `--tier`, `--frontend` and `--strict-exhaustive` are accepted and ignored; record fields of a value whose type has a layout in keleut-front print in the order of the type's row, the order of the printed type (values whose type has no layout, such as records in a value whose type is larger than the layout size limit of 820 (the limit applies to the type of the whole displayed value; a top-level record of up to 409 `Int32` fields keeps its layout, while a pair of two 300-field records does not), print their fields in the byte order of the label spelling, fields with the same label from the outermost, independent of the session history (D559, V231)), while Diktor prints them in construction order; the order of a record's fields is the implementation's choice (D558, which closes V221 as conforming)). Set `KELEUT_DIKTOR` for `cargo test -p keleut-cli --test repl_cmd` to feed every corpus program to both REPLs and to compare `keleut run --frontend rust` with Diktor.
- `python3 bench/run.py --diktor PATH [--keleut PATH] [--configs ki,kj,kt1000,kw,dk,...] [--repeat N] [--warmup N] [--interleave] [--bench NAME,...] [--json OUT]` — time the programs in `bench/programs/` on each configuration (`--interleave` runs every configuration once per round instead of all repeats back to back; `--warmup N` discards N runs per configuration first) (`ki` interpreter, `kj` jit-only, `ktN` threshold=N, `kd` default, `kw` WasmGC, `dk` Diktor's tree evaluator, `dkir` `diktor --run-ir`, `dktc` `diktor --type-check`); KIR is written to a temporary directory, and the run fails if any configuration's stdout differs. `python3 bench/corpus.py --diktor PATH` sums the time of every `conformance/corpus/` program per configuration (the short-program cost of a tier setting).
- `target/release/kconform --pairs dk,dk-ir,kf,ki,kj,kt,ka,km,kw,x-ir,kr-ki,kr-kj,kr-kt,kr-ka,kr-km,kr-kw --suite all` and `target/release/kconform --pairs dk-ir,ki,kj,kt,ka,km,kw,x-ir,kr-ki,kr-kj,kr-kt,kr-ka,kr-km,kr-kw --suite depth --jobs 6` — every pair (the M101 acceptance; needs the default build of `keleut`, which has the LLVM back end). The pairs are `dk` (Diktor's tree evaluator), `dk-ir` (`diktor --emit-ir`, then `diktor --run-ir`), `kf` (Diktor, with keleut-front's stages first: `keleut dump tokens|ast` for the dumps and `keleut check` for inputs that stop in type checking), `x-ir` (`keleut emit-kir`, then `diktor --run-ir`), `ki` `kj` `kt` `ka` `km` `kw` (RustKeleut's backends on the KIR Diktor writes) and `kr-*` (the same backends after keleut-front); `--pairs` defaults to all of these pairs (with `--suite depth`, all but `dk` and `kf`, which it rejects); kconform reads the `backends:` line of `keleut --version`, and when `keleut` was built with `--no-default-features` it leaves the LLVM pairs (`kj`, `kt`, `ka`, `km`, `kr-kj`, `kr-kt`, `kr-ka`, `kr-km`) out of the default set with a note on stderr, and exits 64 if `--pairs` names one. The shim sends Diktor's run invocations of `ki` ... `kw` and `kr-*` to `keleut compat-diktor` with the pair's options and Diktor's IR options (`--emit-ir`, `--run-ir`, ...) to the real diktor. On a 32-core, 31 GB machine keep `--suite depth` at about 6 jobs: with 32 jobs the OOM killer stops `depth/gresume.t` in `ka` and `kr-ka` (exit 137). `--suite all` reports about 22 unused known differences, the V213 entries for `OCAMLRUNPARAM` blocks whose `ki`-group result happens to match the record; they are kept. The closing acceptance of a plan runs both commands three times: without `--extra`, with `--extra=--gc-stress` and with `--extra=--no-yield-prune` (D565), never two `--suite all` runs at once.
- `target/release/kconform --pairs dk,kr-ki,kr-kj,kr-kt,kr-ka,kr-km,kr-kw,x-ir --suite all` — compare the Rust front end feeding each backend (`kr-ki` interpreter, `kr-kj` JIT, `kr-kt` `--tier threshold=1`, `kr-ka` alternating tiers with seeds 1..8, `kr-km` `mixed=1..4`, `kr-kw` WasmGC; `kr-kj`, `kr-kt`, `kr-ka` and `kr-km` need the LLVM back end like `kj`) against Diktor; the pairs whose KIR Diktor writes (`ki`, `kj`, `kt`, `ka`, `km`, `kw` and `kconform expect`) pass `--frontend diktor` to `keleut run`, and the `kr-*` pairs pass `--frontend rust`; like `ki kj kt ka km kw`, the `kr-*` pairs must agree exactly with each other; in every RustKeleut backend pair (`ki`, `kj`, `kw`, `kr-ki`, ...) the shim routes `diktor --repl` to `keleut repl`, which always runs on the interpreter, so the backend pairs agree on REPL blocks. `target/release/kconform expect conformance/frontend-depth/repl.t` checks that the REPL continues after the parse and type-check limits.
- `target/release/kconform --pairs ki,kw --suite all` — compare the WasmGC backend (`kw`) with the interpreter; RustKeleut backends must agree exactly (no known-diff entry applies to a difference between backend pairs). G clauses are captured as lists of per-function frame records and resumed through each function's resume entry (`br_table` to the block after the call); `conformance/effects/` and `conformance/depth/gresume.t` test them. Programs with handler expressions inside `cancel` clauses, or with `return` clauses that can recurse, or with chains of nested `return` or class-N clauses (alone or alternating with `cancel` clauses), get the larger stack `B_prog` (see `--backend wasm` above) and run on the `Worker` path at the default L, with the stack cut at `STACK_CAP`; `keleut-cli`'s `tests/wasm_cmd.rs` stacks the `cancel` case about 600,000 levels deep on both paths and the `return` case and a chain of six `return` clauses 1,000,000 levels deep at the default L (a chain of six class-N clauses 399,000 levels deep at L = 400,000, and four alternating pairs of `cancel` and class-N clauses 298,000 levels deep at L = 300,000).
- `target/release/kconform --pairs ki,kj --suite all` — compare the LLVM JIT (`kj`) with the interpreter; needs a `keleut` with the LLVM back end (the default `cargo build --release`; kconform runs the `keleut` next to itself); `--extra=--gc-stress` also stresses `kj`. The same holds for the tiering pairs `kt` (`--tier threshold=1`), `ka` (`alternating=1..8`, eight runs) and `km` (`mixed=1..4`): `kconform --pairs ki,kj,kt,ka,km --suite all` and `--suite depth` compare all of them. For the LLVM pairs (`kj`, `kt`, `ka`, `km`, `kr-kj`, `kr-kt`, `kr-ka`, `kr-km`; the shim recognises them from the pair's options, not the pair's name) the shim drops a command's own `--backend` so that the pair's backend runs; for other pairs a command's own `--backend` wins, and kconform prints a `組の後段の上書き` line for every command whose `--backend` differs from the pair's. Under memory exhaustion (`ulimit -v`, Rust or LLVM heaps) the JIT pairs can abort with SIGABRT (exit 134) instead of exiting 3 (a known deviation like V215, recorded in M92). `cargo test --release -p keleut-llvm --test tier_alt` runs 1e8 tail calls alternating between the interpreter and the JIT on a 512 KiB stack.
- `target/release/kconform --pairs dk-ir,ki --suite depth` — run the logical-depth tests in `conformance/depth/` (they pass `--max-depth` to `diktor --run-ir` for `dk-ir`); add `--extra=--no-yield-prune` or `--extra=--gc-stress` to any run to repeat it without yield pruning or with frequent collection (see `--gc-stress` above; `--gc-stress` stresses `ki`, `kj`, `kt`, `ka`, `km`, `kr-ki`, `kr-kj`, `kr-kt`, `kr-ka` and `kr-km`; `kw` and `kr-kw` ignore it; `conformance/gc/` holds the collector tests: a 10^6-element list under `--native-stack 512k` and programs that must stay under `ulimit -v 524288`).
- `target/release/kconform --pairs dk ../diktor/test/*.t` — run Diktor's cram tests through the PATH shim and compare each command with the recorded expectation (add `--check-shim` to fail when a `diktor` call bypasses the shim).
- `target/release/kconform expect conformance/kir-bad/*.t conformance/kir-fixtures/1.0/*.t conformance/frontend-depth/*.t` — run conformance tests against their recorded expectations only (adding the `ki` options to `keleut run`); `--promote` rewrites them with the actual results (review the diff).
- `target/release/kconform kir-roundtrip` — on every corpus program, compare `keleut kir dis` and `asm` with Diktor's text and binary output and check the text → binary → text round trip; it also runs every `conformance/kir-fixtures/` sample `.kir` with `diktor --run-ir` and `keleut run` (same output and exit status) and runs `keleut kir verify` on every sample `.kir` and `.kirt`.
- `target/release/kconform extract-corpus [--check]` — regenerate (or check) `conformance/corpus/` after `diktor/test` changes.
- kconform finds the real Diktor through `--diktor`, then `KELEUT_DIKTOR`, then `../diktor/_build/install/default/bin/diktor`, and the `keleut` next to itself, so build both with `cargo build --release` first.

## Coding Style & Naming Conventions

Follow existing OCaml code: two-space indentation, `snake_case` values and filenames, and capitalized modules and constructors. Preserve Japanese literate explanations and column-zero `(* ... *)` article blocks. Do not run `ocamlformat` or `dune fmt`; they break that layout despite the existing `.ocamlformat` file. In `rustkeleut/`, write rustdoc comments in Japanese, and format with `cargo fmt`; the literate layout does not apply there. Follow nearby `.kel` examples when editing the specification.

## Testing Guidelines

Add focused regression cases to descriptive `test/*.t` files such as `trailing_comma.t`. Cover successful behavior and relevant diagnostics or exit codes. No numeric coverage threshold is configured.

RustKeleut conformance tests are cram-form `.t` files under `rustkeleut/conformance/`, with their `.kel`, `.kir` or `.kirt` inputs beside them; they call `keleut` directly, and `kconform expect` compares them with the recorded output. Never change `diktor/test` expectations for RustKeleut's sake; record unavoidable differences in `conformance/known-diffs.toml` with a ledger number.

Review golden-output differences before `dune promote`; commit expectation updates separately from implementation changes. Never hand-edit `test/sample/sample.kel`: synchronize it from the parent specification using `test/sample/README.md`, updating provenance and affected source references together.

## Commit & Pull Request Guidelines

Use small logical commits with `scope: summary` subjects; history uses `spec:`, `diktor:`, `test:`, and `doc:`. Follow `.claude/rules/commit.md`: Japanese messages on `ja/` branches, English elsewhere; never bypass hooks or signing.

PR descriptions should explain behavior changes, cite affected specification sections or issues, and report validation commands and results. Commit submodule changes within `diktor/`, then record its updated revision in the parent repository.
