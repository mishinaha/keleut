# bench

RustKeleut のバックエンドと Diktor の実行時間を測るツールである。
測った値と、そこから決めたことは `doc/log/261028-1-m93.md` にある。

## ファイル構成

| 場所 | 内容 |
| --- | --- |
| `programs/*.kel` | 計測用のプログラム。どれも標準出力に結果を書くだけで、入力を読まない |
| `run.py` | `programs/` の各プログラムを設定ごとに数回実行し、経過時間の中央値と最小値を表にする |
| `corpus.py` | `conformance/corpus/` の小さなプログラムをすべて実行し、経過時間の合計を設定ごとに出す |

## プログラム

| 名前 | 測るもの |
| --- | --- |
| `hello` | 起動と終了のコスト |
| `fib` | `Int32` の非末尾の再帰(`fib(32)`) |
| `tail32` | `Int32` の引数 2 個の末尾再帰 1,000 万回と、相互の末尾再帰 1,000 万回 |
| `tail32b` | `tail64` と同じ本体を `Int32` で書いた末尾再帰 1,000 万回(`tail64` と比較してボックス化のコストを見る) |
| `args6` | 引数 6 個の末尾再帰 1,000 万回(引数を渡すコスト) |
| `tail64`、`tailf64` | `Int64` と `Float64` の引数の末尾再帰 1,000 万回(引数を渡すたびに起こるボックス化のコスト) |
| `tailresume` | 分類 T の操作節(IRSpec 9.2 節)の末尾 `resume` を 500 万回 |
| `gen` | 分類 G の操作節で作る生成器(1,000 回の yield を 1,000 回繰り返す) |
| `gdepth1`〜`gdepth1000` | 深さ 1、10、100、1,000 の再帰の底からの yield を 2 万回(継続のコピーのコストと深さの関係) |
| `abort` | 分類 N の操作節への脱出を、深さ 10 で 20 万回、深さ 1,000 で 2,000 回 |
| `records` | レコードの作り直し、`with` による更新、レコードのリストの走査 |
| `strings` | 文字列の連結、部分文字列、比較、`show` |
| `typecheck` | let 多相つきの小さな型推論器で、生成した式 12,000 個を検査する(コンパイラに近い負荷) |

## 使い方

`rustkeleut/` で次のように実行する。
`keleut` は `cargo build --release` でビルドしたものを使う。
LLVM バックエンドの設定を測るので、既定の feature `llvm` を外さない。

```sh
python3 bench/run.py --diktor ../diktor/_build/install/default/bin/diktor \
  --configs ki,kj,kt1000,kw,dk --repeat 5 --json /tmp/bench.json
python3 bench/corpus.py --diktor ../diktor/_build/install/default/bin/diktor --configs ki,kt1,kt1000
```

設定の名前は次のとおりである。

| 設定 | コマンド |
| --- | --- |
| `ki` | `keleut run --backend interp` |
| `kj` | `keleut run --backend jit --tier jit-only` |
| `ktN` | `keleut run --backend jit --tier threshold=N`(`N` は 1、10、100、1000、10000、100000) |
| `kaS`、`kmS` | `--tier alternating=S` と `--tier mixed=S`(`S` は 1 か 2) |
| `kd` | `keleut run`(既定のバックエンドとティア) |
| `kw` | `keleut run --backend wasm` |
| `dk` | `diktor FILE.kel`(構文木の評価器。構文解析と型検査を含む) |
| `dkir` | `diktor --run-ir FILE.kir` |
| `dktc` | `diktor --type-check FILE.kel`(`dk` に含まれる型検査の時間の目安) |

`run.py` は次のように動作する。

- KIR は `diktor --emit-ir` で一時ディレクトリに書き、終われば消す。
  `--work DIR` を渡すと、そこに書いて残す。
- `dk`、`dkir`、`dktc` は遅いので、実行する回数を `--slow-repeat`(既定 3)で決める。
  それ以外の設定の回数は `--repeat`(既定 5)で決める。
- どの設定の標準出力も、最初の設定の標準出力と同じでなければならない。
  標準出力が違うか、終了コードが 0 でなければ、表の値に `誤` を付け、終了コード 1 で終了する。
  KIR を書けなかったプログラムは、標準エラーにその旨を書いて表から外し、同じく終了コード 1 で終了する。
  `dktc` は型検査だけを行い、出力がほかの設定と違うので、この比較から外す。
- 既定では、1 つの設定を指定した回数だけ続けて実行してから、次の設定に移る。
  `--interleave` を渡すと、1 回ごとにすべての設定を 1 度ずつ順に実行する。
  こうすると、負荷の変動がどの設定にも同じ程度に影響する。
  `--warmup N` を渡すと、測る前に各設定を `N` 回実行し、その結果を捨てる。
- 表の値は経過時間の中央値(ミリ秒)である。
  `--json FILE` を渡すと、すべてのサンプル(経過時間、終了コード、標準出力の SHA-256 の先頭 12 桁、最大 RSS)を JSON で `FILE` に書く。
- 出力の先頭の 2 行に、日時、CPU、論理コア数、カーネル、1 分間のロードアベレージ(出力では `負荷`)を書く。
  ほかの作業がコアを使っていると値が変動するので、ロードアベレージが 1 を超えるときは測り直す。
  測り直せないときは、ロードアベレージを記録し、`--interleave` を渡して測り、数 % の差を誤差とみなす。
- `--interleave` を渡しても、経過時間が数ミリ秒のプログラムや、1 回だけ大きく外れたサンプルがある設定では、最小値や最大値が中央値から 30 % ほど離れることがある。
  中央値と最小値の両方を見て比較する。

`corpus.py` は、KIR にできたプログラムのすべてを、設定ごとに `--repeat`(既定 3)回実行する。
1 回分の経過時間の合計について、中央値と最小値を秒で書く。
各プログラムについて、最初に実行したときの標準出力と終了コードを基準にし、その後の実行の結果と比較する。
結果が基準と違うか、実行が `--timeout`(既定 60 秒)を超えたプログラムがあれば、標準エラーにそのプログラムのパスと、食い違った 2 つの設定の名前を書き、終了コード 1 で終了する。
