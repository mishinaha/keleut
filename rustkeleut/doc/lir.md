# LIR の命令

本書は、RustKeleut の内部の中間言語 **LIR** の各命令の意味を定める。
LIR は crate `keleut-lir` が KIR から作る。
インタプリタ、LLVM バックエンド、WasmGC バックエンドは、同じ LIR からそれぞれのコード(レジスタバイトコード、LLVM IR、WasmGC のモジュール)を生成する。
LIR はファイルに書き出さず、バージョン間の互換性も保証しない。

KIR から LIR を作る処理を **LIR への変換**(lowering)と呼び、それを行う `keleut-lir` の部分を**変換器**と呼ぶ。
本書が扱うのは、2 節の表のパス 1〜12 が生成する命令である。
エフェクトを変換するパス 8 の命令、ハンドラのフレームになる関数 `$rt_handle`、防壁(`cancel` 節の実行中に、伝播中の状態を退避して守る手順)は 16 節に書く。
yield の枝刈り(パス 11)は 17 節に書く。

本書は、言語仕様 `doc/LangSpec.md` の節を「LangSpec §5.7」、KIR の仕様 `doc/IRSpec.md` の節を「IRSpec 8 節」のように書く。

## 1. 全体の構成

### 1.1 プログラム

LIR のプログラムは、次の表からなる。

| 表 | 内容 |
| --- | --- |
| 関数 | 先頭の部分は KIR の関数と同じ添字に置く。その後ろに、組み込みの値、`extern`、組み込みのインスタンスのメソッドそれぞれの本体の関数と、単位ごとの初期化関数を置く |
| グローバル | KIR と同じ添字。種類ごとの値は 1.6 節 |
| インスタンス | KIR と同じ添字。クラスのメソッドの順に、実装の関数と、その関数が受け取る辞書の個数(前提の個数 + メソッド自身の辞書の個数)を持つ |
| 型、クラス | KIR と同じ添字。コンストラクタの名前と引数の個数、メソッドの名前 |
| 組み込みのメソッド | `(クラス, 型, メソッド)` ごとの本体の関数(IRSpec 付録 A.3 の 44 個) |
| ラベル | レコードとヴァリアントのラベルの文字列 |
| シェイプ | レコードのシェイプ(1.5 節)。0 番は空のシェイプである |
| 文字列 | 文字列定数(任意のバイト列) |
| 初期化 | 単位ごとの初期化関数(初期化の順) |

単位は、KIR のプログラムを構成するコンパイル単位である(IRSpec 2 節)。
プログラムの実行とは、初期化関数を、コンテキストの深さ 0 で順に呼ぶことである。

### 1.2 関数、ブロック、レジスタ

関数は基本ブロックの並びである。
先頭のブロックが入口で、どの分岐も番号の大きいブロックへ向かう。
そのため、どの関数の制御フローも非巡回である。
Keleut には反復の構文がなく(LangSpec §5.7)、繰り返しは末尾呼び出しで書く。

**レジスタ**は関数ごとの仮想の格納先で、それぞれがちょうど 1 つの Rep を持つ。
Rep は KIR と同じく `bool`、`i32`、`i64`、`f64`、`str`、`any` の 6 種である。
`any` は**一様表現の値**(バックエンドが値の種類によらず同じ形式で持つ値。ネイティブの表現では 1 ワード)である。
`str` は文字列の参照で、一様表現の値として扱うときも表現を変えない。
レジスタは SSA 形式ではない。
`match` や `and` の合流では、各分岐が同じレジスタに書いてから合流のブロックへ分岐する。
検証器は、どのレジスタについても、読む位置に至るすべての経路で先に書かれていることを検査する。

関数の**引数**はどれも `any` のレジスタで、入口で値を持つ。
KIR の引数の Rep が `any` 以外なら、入口の `unbox` がボックス化していない値を取り出す。
返り値も `any` である。
種類が `dictabs` の関数の引数は、辞書の引数である。

**環境**は、クロージャが持つキャプチャの並びである。
関数は、入口の `depth_enter` の直後で、自分を呼んだクロージャの環境からキャプチャを `env_get` でレジスタに読む。
それ以降はキャプチャもほかの値と同じくレジスタで扱うので、フレームはクロージャを保持し続けない(1.8 節)。
キャプチャを持たない関数は、`call_direct` で環境なしに呼べる。

### 1.3 trap しないこと

LIR の命令は trap せず、未定義動作を持たない。
具体的には次のように定める。

- エラーになることがある演算(ゼロ除算、範囲外の添字、`Float64` から整数への変換)では、変換器が命令の前に明示的な検査と `error` への分岐を置く(パス 7)。
  命令そのものは**全域**である(どの入力にも結果を定めていて、trap しない)。
  たとえば `i32.div` は除数が 0 なら 0 を返す。
  プログラムは検査を通った後でしかその命令を実行しないので、この値はプログラムからは見えない。
- 実行時エラーになることがある命令は、1.7 節の「失敗しうる命令」だけである。

ただし、命令の意味には、KIR の型の健全性を前提にする箇所がある。
たとえば、`unbox` の元が同じ Rep の値をボックス化したものであることや、`ctor_tag` の対象が名目的な型の値であることである。
KIR の検証器は型の健全性を検査しない。
信頼の起点は、型検査を済ませたフロントエンドである。
この前提が破られたときの動作は処理系の内部エラーで、バックエンドは終了コード 70 で終了してよい。
各命令の節の「前提」の項に、その命令の前提を挙げる。

型検査を済ませたプログラムでも、この前提が破られる場合が 1 つある。
`console_write`(13 節)は、宣言された返り値の型によらず `r` を Unit にする。
KIR の操作表が持つのは、操作の名前、引数の個数、`never` と `runtime` の印だけで、返り値の型は持たない。
そのため変換器は、プレリュードが `Console.write` を `(String) => Unit` と宣言していることを確認できない。
`--prelude` で差し替えたプレリュードが別の返り値の型を宣言すると、そのプログラムは LIR の前提を満たさない。
たとえば `write: (String) => Int32` と宣言して `perform write("a") + 1` と書くと、変換器は Unit を `i32` に `unbox` する。
Diktor はこのプログラムで `a` を出力し、値を調べた箇所で実行時エラー(`Int32 ではありません: ()`)になって、終了コード 3 で終了する。

### 1.4 論理的な深さ

深さは IRSpec 11.2 節の規則で数える。
ランタイムはコンテキストの深さ `ctx.depth` と上限 `L` を持ち、各フレームは自分の深さを持つ。
LIR の深さの命令は次の 4 つである(パス 10)。

| 命令 | 置く位置 |
| --- | --- |
| `depth_enter` | 関数の入口の先頭 |
| `depth_push` | ユーザのコードを呼ぶことがある非末尾呼び出しの直前 |
| `depth_restore` | その呼び出しの直後 |
| `depth_check` | プリミティブ、組み込みのメソッド、組み込みの値のように、ユーザのコードを呼ばない非末尾呼び出しの位置 |

末尾呼び出しは深さを変えない。
呼び出し先が正常に戻ったとき、`ctx.depth` は呼び出し先の入口での深さに等しい。
非末尾呼び出しは、`depth_push` と `depth_restore` で囲むか、`ctx.depth` を変えずに呼び出し元の現在の深さで呼び出し先を実行するかのどちらかだからである。
後者に該当するのは、初期化関数の呼び出しと、メソッドの呼び出しの中で行う実装の関数の評価である(13 節)。
`depth_enter` はフレームの深さを `ctx.depth` から読むので、帰納法により、どの呼び出し先も入口での深さで戻る。
メソッドの値の呼び出し(`dict.rs`)は、この性質を使って、実装の関数の評価と、評価で得た関数の呼び出しを同じ深さで行う。

### 1.5 値の種類

LIR の値は次のどれかである。
一様表現の値のエンコーディングは、バックエンドがそれぞれ決める。
ネイティブのエンコーディングは crate `keleut-rt` の `value.rs` の冒頭に、WasmGC のエンコーディングは crate `keleut-wasm` の `rt.rs` の冒頭に書いてある。

| 値 | 内容 |
| --- | --- |
| Unit | 空のレコード |
| 真偽値、`Int32`、`Int64`、`Float64` | ボックス化していない値か、それをボックス化した一様表現の値 |
| 文字列 | 長さとバイト列 |
| データ | 型、コンストラクタの番号、フィールドの並び(宣言の順)。引数のないコンストラクタは型と番号だけ |
| ヴァリアント | ラベルの番号とペイロード |
| レコード | シェイプとフィールドの並び |
| クロージャ | 関数とキャプチャの並び |
| メソッドの値 | クラス、メソッド、辞書、メソッド自身の辞書の並び |
| 辞書 | 組み込みのインスタンス `(クラス, 型)`、ユーザのインスタンスと前提の辞書の並び、構造的な `Eq` のレコードかヴァリアントの辞書(ラベルと辞書の並び) |
| `Ref`、配列、可変配列 | 1 つの値の入れ物、値の並び |

**シェイプ**は、ラベルの番号の昇順に並べたラベルの並びである。
同じラベルが 2 つ以上あるときは、外側(後で追加したもの)を先に置く。
レコードのフィールドはシェイプの順に並ぶ。
このレイアウトは正準(canonical。一意に決まる形)で、同じラベルの多重集合を持つレコードは、どの経路で作っても同じシェイプになる。
LangSpec §18.3 により、ラベルの順は結果に影響しない。
プログラムのシェイプ表の番号は、ランタイムが作るシェイプの番号と一致させる(ランタイムは表のシェイプを先に登録する)。

### 1.6 グローバルの値

`global_get` が読む値は、グローバルの種類で決まる。

| 種類 | 値 |
| --- | --- |
| `fn` | その関数の、キャプチャを持たないクロージャ |
| `dictabs` | その関数の、キャプチャを持たないクロージャ(辞書の抽象) |
| `extern` | 本体の関数のクロージャ。実装名が IRSpec 付録 A.5 にないときは、呼ぶと実行時エラー 17 か 18 になる値 |
| `builtin` | 本体の関数のクロージャ |
| `value` | 初期化手順が `global_set` で置いた一様表現の値 |

### 1.7 実行時エラーと失敗しうる命令

**失敗しうる命令**は、次の命令である。

- 呼び出し(`call_direct`、`call_value`、`call_method`、`dict_app`)。呼び出し先で起きた実行時エラーがここへ伝わる。
- メモリを確保する命令。GC を実行してもヒープを拡張できないときに、メモリ不足(IRSpec 付録 B の 19 番)になる。
  長さを受け取る確保(`marray_new`、文字列を作る命令)は、長さが `N_alloc_max = 2^26` を超えるときもメモリ不足になる(IRSpec 11.6 節)。
- `depth_check` と `depth_push`。上限を超えると `depth_limit` の実行時エラーになる。
- `console_write`。書き込みに失敗すると出力エラー(終了コード 74)になる。
- エフェクトの命令のうち、`handler_find`(どのハンドラも処理しない操作)、`perform`(`p + 1` が上限を超えたときの `depth_limit` と、候補がないときの実行時エラー 9)、`cont_check`(16.5 節)、`cont_resume`(値スタックを拡張できないときのメモリ不足。16.4 節)。
  `call_clause` は、深さ `h + 1` が上限を超えたら、節を呼ばずに状態ワードに `ERROR` を設定し、番兵を結果に書く(状態ワードと番兵は 16.1 節)。
  エフェクトの終端命令 `tail_call_clause` も、候補がなければ実行時エラー 9 になる。
- `pending_suppress`。抑制の記録を書く前に行う標準出力の flush が失敗したら、巻き戻さずに出力エラー(終了コード 74)で終了する(16.4 節の防壁)。
  前の失敗の後でバッファに残したデータや、その後に追記したデータを書き出せなかった場合も、この失敗に含む。

失敗した命令より後の命令は実行されない。
バックエンドは、状態ワード `ctx.pending`(伝播中のエラーなどを持つランタイムの状態)に `ERROR` を設定し、そのフレームから番兵を返して戻る(16.1 節)。
番兵は、状態ワードが設定されていることを表す、返り値の位置に置く値である。
エラーは、番兵を受け取るハンドラのフレームを通るたびに `cancel` 節を実行しながら、呼び出し元へ伝わる。
最上位まで伝わったら、ランタイムは標準出力を flush し、メッセージ(IRSpec 付録 B)を標準エラーに書いて、終了コード 3(出力エラーは 74)で終了する。

### 1.8 フレーム(パス 12)

パス 12 は、各関数に次のものを付ける。

- **スロット**:各レジスタの格納先。
  スロットは、`any` の領域と、ボックス化していない値の領域に分ける。
  `any` と `str` のレジスタは `any` の領域(GC が走査する)に、`bool`、`i32`、`i64`、`f64` のレジスタはボックス化していない値の領域に置く。
  引数は `any` の領域の 0 番から順に置く(呼び出し元が値を書く位置である)。
  2 つのレジスタが同じスロットを使うのは、生存区間(1.9 節)が重ならないときだけである。
- **再開点**:非末尾呼び出しの命令。
  関数の中で位置の順に 0 から番号を振り、その呼び出しの後で生存しているレジスタの集合を付ける。
  呼び出しが書くレジスタは集合から除く。
  呼び出しの引数は呼び出し先のフレームの `any` の領域にコピーするので、呼び出し元の集合には入れない。
  メソッドを実行時に選ぶ呼び出しでは、引数をコピーする前に GC が起きることがあるので、本節で後述する規則で引数をルートに残す。
- **安全点**:メモリを確保する命令。
  確保をまたいで生存しているレジスタの集合を付ける。
  この集合は、その命令の後で生存しているレジスタから命令が書くレジスタを除き、命令のオペランドを加えたものである。
  オペランドを入れるのは、確保が GC を起こしても、新しい値にコピーする前のフィールドや文字列がルートに残るようにするためである。
  命令が書くレジスタは、確保を終えてから書く。
  生存区間(1.9 節)の上ではオペランドと書き込み先のレジスタが同じ位置で重なるので、両者が同じスロットを使うことはない。

生存しているレジスタの集合は、正確な生存解析で求める。
GC は、安全点と再開点で、この集合のうち `any` の領域のスロットだけをルートとして走査する。
集合に入らないスロットには、すでに死んだ値か、まだ書いていない値が残っていることがあるからである。

メソッドを実行時に選ぶ呼び出しは、引数を呼び出し先のフレームにコピーする前に、メモリを確保する関数を呼ぶことがある。
この呼び出しに該当するのは、`call_method`、`tail_call_method`、メソッドの値(`method_new` の値)を呼ぶ `call_value` と `tail_call_value` である。
辞書が前提付きのユーザのインスタンスのとき、これらの命令は、引数 `a…` を渡す前に、実装の関数を辞書 `p… ++ o…` で評価する(13 節)。
実装の関数の本体はクロージャを作る `closure_new` で、メモリを確保するので GC を起こすことがある。
この間、辞書 `d`、メソッド自身の辞書 `o…`、引数 `a…`(`call_value` では呼ぶ値 `f` も)は呼び出し元のフレームのスロットにだけあり、再開点の集合には入っていない。

インタプリタは、これらの値を呼び出し元のフレームのスロットに残したまま、実装の関数を通常のフレームとして上に積む。
呼び出し元のフレームヘッダの再開点には `PHASE` フラグを付ける。
実装の関数が戻ったら、呼び出しの命令を読み直し、得た関数を同じスロットの引数で呼ぶ。
末尾呼び出し版(`tail_call_method` と `tail_call_value`)も、実装の関数が戻るまで呼び出し元のフレームを残し、戻った後にフレームを再利用する。
そのため、`PHASE` フラグの付いたフレームでは、GC は再開点の集合に加えて、その呼び出しの命令のオペランド(`d`、`o…`、`a…`、`call_value` では `f`)のスロットもルートとして走査する。

フレームヘッダに書く再開点の番号は、バックエンドが持つ再開点の表の番号である。
この表は、LIR の再開点の項目(番号は LIR の再開点の番号と同じ)の後ろに、末尾呼び出し版の呼び出しごとの項目を追加したものである。
0 始まりで `k` 番目の末尾呼び出し版の項目(番号は LIR の再開点の個数 + `k`)は、終端命令が `tail_call_value` か `tail_call_method` であるブロックのうち、関数のブロックの順に 0 始まりで `k` 番目のブロックに対応する。
末尾呼び出し版の項目は、生存しているレジスタの集合を持たないので、`PHASE` フラグがないときのルートの集合は空である。
`PHASE` フラグの付いたフレームの呼び出しの命令は、表の項目が持つ命令の位置(`call_pc`)から求める。
LLVM バックエンドも同じフレームのレイアウトを使い、同じ規則に従う。
ただし、JIT の関数どうしの呼び出しは、先頭の 4 個の引数をレジスタで渡し、呼び出し先のスロットには書かない。
呼び出し先は、再開点と安全点の前に、生存しているレジスタをスロットに書く。
`$rt_handle` だけは、入口で引数をスロットに書く。
したがって、引数をレジスタで渡してもルートの規則は変わらない。
WasmGC バックエンドでは、ホストの GC が Wasm のローカル変数とオペランドスタックにある参照をルートとして扱うので、この規則による義務はない。

辞書が、前提を持たないユーザのインスタンス、組み込みのインスタンス、構造的な辞書のどれかのときは、実装の関数を評価しない。
構造的な `Eq` の比較(13 節の `call_method`)はランタイム関数が行う。
ランタイム関数は、構造的な辞書の項目(ラベルと辞書の組)が持つ辞書の `eq` を呼ぶ間、比較する両辺と辞書を `Root` で保持する。
比較を始める前に、呼び出し元のフレームヘッダの再開点を、この呼び出しの再開点にする。
末尾呼び出し版では、その項目は上に述べた末尾呼び出し版の項目で、呼び出し元のフレームのルートの集合は空である。

GC(crate `keleut-rt` の `gc`)は、メモリの確保の中でだけ起こる。
GC は、ランタイムコンテキストの `gc.top`(現在の最上段のフレームの論理的な位置)から呼び出し元を順にたどり、各フレームが止まっている**点**でルートの集合を決める。
点は、最上段のフレームがメモリを確保する命令で止まっているときは `gc.top_point`(`SAFEPOINT` フラグと安全点の番号)で、それ以外はフレームヘッダの 0 番のワードの上位 32 ビットである。

| 点 | ルートにするスロット |
| --- | --- |
| `SAFEPOINT` フラグ(`1 << 29`)と安全点の番号(`gc.top_point` だけ) | その安全点の集合 |
| LIR の再開点の個数より小さい項目の番号 | その再開点の集合。`perform` の項目ならオペランドも |
| それ以上の項目の番号 | 末尾呼び出し版の項目で、集合は空 |

`PHASE` フラグ(`1 << 31`)が付いていれば、項目の呼び出しの命令(末尾呼び出し版の項目ならブロックの終端命令)のオペランドもルートにする。
`YIELDED` フラグ(`1 << 30`)は取り除いて読む。
`$rt_handle` のフレームは、どの点でも `any` の領域の 0 番のスロットをルートにする。

バックエンドは、メモリを確保する前に次の規則を守る。

- メモリを確保する命令の前に、`gc.top` を現在のフレームの位置にし、`gc.top_point` をその命令の安全点にする(`GcState::at_safepoint`)。
  インタプリタは、確保する命令の前に置いた 1 ワードの命令 `safepoint` でこれを行う。
  安全点はフレームヘッダに書かない。
  フレームヘッダの点は、確保に失敗して巻き戻すときに、呼び出し元の項目として読まれることがあるからである。
  たとえば、`cont_make` が継続を作れずに区間(継続にするフレームの範囲。16.4 節)の最上段へ制御を移してエラーを伝播すると、ハンドラのフレームは本体の呼び出しの項目でエラーを受け取る。
- 命令の外でランタイムがメモリを確保するとき(`perform` の引数の配列)は、フレームが `perform` の再開点で止まっているので、`gc.top` を現在のフレームの位置に設定し、`gc.top_point` の代わりにフレームヘッダの点を使わせる(`GcState::at_frame`)。
- ランタイム関数がインタプリタを入れ子に呼ぶとき(構造的な `Eq`)は、フレームヘッダの点を呼び出しの再開点にし、`GcState::at_frame` で位置を設定してから呼ぶ。
- Rust のコード(呼び出し規約は ccc)から、管理されたフレームの連鎖に入る入口では、どのバックエンドも `GcState::enter_native` で外側の最上段の位置を `gc.outer` に積み、戻るときに `GcState::leave_native` で取り除いて、`gc.top` と `gc.top_point` を元に戻す。
  入口の最下段のフレームヘッダの 3 番のワードは「ネイティブの呼び出し元」を表す目印なので、GC はそこまでたどったら、`gc.outer` に積んだ位置から続ける。
  位置を積まない入口があると、GC はその入口より下のフレームをたどらない。
  この義務を負うのは、入れ子になった `Interp::run` の呼び出し(トップレベルの初期化コードの実行と、構造的な `Eq` の入れ子)である。
  管理されたフレームどうしの通常の呼び出し(フレームヘッダの 3 番のワードに呼び出し元の位置を書く)は、`enter_native` を使わない。
  LLVM バックエンドの JIT とインタプリタの境界(インタプリタから `enter_tailcc` で JIT の関数を呼ぶ入口と、JIT から `interp_stub` で入るインタプリタの呼び出し)は、ネイティブスタックの上では入れ子になるが、通常の呼び出しとして扱う。
  呼び出し先のフレームの 3 番のワードには本当の呼び出し元のフレームの位置を書き、`enter_native` を使わない。
  GC と継続は、この境界をまたいで呼び出し元を順にたどる。
  インタプリタは、呼び出されるたびに、その呼び出しの最下段のフレームの位置を記録し、そのフレームが戻るか番兵を返して戻ったときに、ネイティブの呼び出し元へ返る(`keleut-interp` の `native.rs`)。
- JIT の関数は、非末尾呼び出しの前に、再開点で生存しているレジスタをスロットに書き、フレームヘッダの 0 番のワードに再開点を書く。
  yield を受け取らない再開点(17 節)では `any` の領域のレジスタだけを書き、受け取る再開点ではボックス化していない値の領域のレジスタも書く。
  継続にコピーしたフレームの続きはインタプリタが実行するので、続きに必要な値がすべてスロットになければならないからである。
  メモリを確保する命令の前には、安全点で生存している `any` の領域のレジスタを書き、ランタイム関数が `GcState::at_safepoint` を行う。
  ただし、`box`、`ctor_new`、`rec_new` の小さなオブジェクトは、JIT のコードがヒープから直接確保することがある。
  これを確保の高速経路(fast path)と呼ぶ。
  高速経路では GC が起きないので、レジスタを書かず、安全点も記録しない。
  高速経路で確保できないときだけ、レジスタを書いてランタイム関数を呼ぶ。
  `--gc-stress` では高速経路のコードを生成しない。
  呼び出し先が実行時に決まる呼び出しが実装の関数を評価する間(`PHASE` フラグ)は、呼び出しの命令のオペランドもスロットに書く。
  エフェクトの命令(16 節)の前には、命令のオペランドをすべてスロットに書く。
  JIT は、ランタイム関数 `krt_fx` を呼んでインタプリタの同じ命令を 1 つだけ実行させ、書き込み先のスロットから結果を読む。
  `perform` の再開点で待つフレームはオペランドをルートに持つので、スロットへのこの書き込みはルートの規則も満たす。
  継続の再開(`cont_resume`)は、値スタックに復元した区間を、`krt_fx` の中で呼ぶインタプリタで実行する(最下段は復元した区間の最下段のフレームである)。
  `cont_make` が継続を作れなかったときは、区間の最上段から巻き戻した結果を、JIT のフレームがフレームヘッダの再開点(本体の呼び出し)の結果として受け取り直す。
  WasmGC バックエンドは、上に書いたとおりホストの GC がルートを扱うので、この義務を負わない。
- 状態ワードが `YIELD` の間、`perform` のフレームから現在のフレームの上までのフレームは、まだ継続にコピーされず、値スタックに残っている。
  GC は、状態ワードの `YIELD` が持つ `perform` のフレームの位置から、現在の最上段の手前までもたどる。
- GC は値スタックのフレームを、使用中のチャンクを変えずに読む(`ValueStack::ptr_at_ro`)。
  使用中のチャンクは、次のフレームを置く位置に影響するからである。
- GC の終わりに、ランタイムは値スタックのチャンクのうち、生存している最も上のフレームを含むチャンクと、その次の 1 つを残し、それより後ろのチャンクを解放する(`ValueStack::release_after_collect`)。
  生存している最も上のフレームは、状態ワードが `YIELD` ならその `perform` のフレーム、そうでなければ最上段のフレーム(`GcState::top`)である。
  次の 1 つを残すのは、チャンクの境界で呼び出しと戻りを繰り返すときに、チャンクを確保し直し続けないためである。
  置いたばかりでまだ最上段にしていないフレームも、この 2 つのチャンクのどちらかにある。
  注入(16.4 節)は、継続が持つフレームのコピー領域を、そのまま 1 つのチャンクとして値スタックにつなぎ、退避した状態ワード(`DISCARD` か `ERROR`)をそこから伝播させる。
  このチャンクをコピーチャンクと呼ぶ。
  次の 1 つが 1 MiB より小さいコピーチャンクで、その後ろに 1 MiB 以上のチャンクがあれば、コピーチャンクを解放してそのチャンクを残す。
  ただし、使用中の最後のチャンクが次の 1 つであれば、置いたばかりのフレームがそこにあるかもしれないので、コピーチャンクのまま残す。
  値スタックの予備チャンクは解放しない。
  フレームを捨てて戻るとき(`ValueStack::ptr_at`)にはチャンクを解放しない。
  フレームを置くとき(`ValueStack::place`)は、次のチャンクを再利用するときに、その後ろのチャンクを解放する。
  そのため、値スタックが保持するチャンクは、実行全体での最大の深さでは決まらない。
  保持するのは、最後の GC のときに残した 2 つのチャンクと、その GC の後に達した最も深い位置のうち、大きいほうまでである(後ろのチャンクを解放した後なら、これより少ない)。
- チャンクを解放した後、使用中の最後のチャンクが解放したチャンクであれば、ランタイムは使用中の最後のチャンクを、残したチャンクのうち最後のものに戻し、使用中のチャンクの範囲(`StackWindow`)を書き直す。
  JIT の関数は戻るときにランタイムを呼ばないので、使用中の最後のチャンクは最上段のフレームより後ろに残ることがある。
  JIT の関数は、フレームを置くたびに、この範囲をコンテキストの `win` から読み直す。
  また、ランタイム関数の宣言はメモリへの作用を制限していないので、LLVM は確保の呼び出しをまたいで、読んだ範囲を再利用しない。
  したがって、書き直した範囲は、次にフレームを置くときから有効になる。
- 区間のフレームを値スタックから読み直す処理は、その間の GC で区間のチャンクが解放されないように、区間のフレームをルートとして残す。
  `cont_make` は、継続を表に入れて、その添字を持つオブジェクトを確保するまで、状態ワードの `YIELD` を消さない(16.4 節)。
  オブジェクトを確保できなかったときに、区間の最上段へ制御を移すからである。
- ランタイム関数が 1 回の呼び出しの中で 2 回以上メモリを確保するときは、先に作ったオブジェクトを `Root` かランタイムの表に置いてから、次を確保する。
  引数で受け取ったワードは、呼び出し元のフレームの集合がルートとして保持する(安全点の集合は命令のオペランドを含む)。

GC はルートの集合のスロットのワードだけを読むので、ボックス化していない値の領域と、集合に入らない `any` のスロットは何を持っていてもよい。
論理的な位置は、値スタックのチャンクの境界の位置を含んでいる。
そのため、継続が区間を値スタックに復元するときは、位置を一律にずらさず、フレームを 1 つずつ配置し直して 3 番のワードを書き直す(16.4 節の `cont_resume`)。
注入のときは、コピーチャンクの中の位置をそのままフレームの位置にする(16.4 節)。
コピーしたフレームは最下段から隙間なく並んでおり、1 つのチャンクの中ではフレームがチャンクをまたがないからである。

キャプチャは入口でレジスタに読む(1.2 節)ので、関数がまだ使うキャプチャは、再開点と安全点の生存しているレジスタの集合に入る。
そのため、フレームヘッダは環境のフィールドを持たなくてよい。
再開点から実行を続けるバックエンド(継続の再開、インタプリタでの再開)も、スロットだけから続きを再現できる。

エフェクトの命令(16 節)は、ルートについて次の規則を追加する。

- `perform` の再開点で待っているフレームでは、再開点の集合に加えて、その `perform` のオペランド(`hr`、`saved`、引数)のスロットもルートとして走査する。
  節の選択が戻った後に、これらを読み直すからである(16.5 節の `perform`)。
  `PHASE` フラグの付いたフレームの規則と同じである。
- `$rt_handle` のフレームは、`any` の領域の 0 番のスロットにハンドラ記録を持つ(0 番の引数のスロットは再利用されない)。
  `cont_resume` は、復元したフレームのうち `$rt_handle` のフレームから、このスロットを読む。
- ハンドラ記録、継続、退避した状態ワードが持つワード(本体と節の関数の値、親や `res` のハンドラ記録と継続、継続の中のフレームのコピー、`perform` の引数の配列)は、ランタイムの表にある。
  表はルートではない。
  GC は、項目の添字を持つオブジェクト(種類 16、17、18)をマークしたときに、その項目のワードを走査する。
  マークを終えたら、オブジェクトがマークされなかった項目を表から取り除く。
  表のワードをすべてルートにすると、項目どうしの循環参照(`cont_resume` が差し替えたハンドラ記録の親、`handler_new` の `res` の継続、その継続のハンドラ記録)がいつまでも取り除かれないからである。
  ランタイムは、項目を表に入れてから、その添字を持つオブジェクトを確保する。
  表に入れたがまだオブジェクトのない項目は、オブジェクトができるまでルートである。
  取り除いた項目の添字は、次に表に入れる項目に再利用する。
  使い終えた継続のワード(ハンドラ記録、連鎖の切り出した部分の先頭、引数)は消さない。
  継続のオブジェクトは、継続を受け取った節のフレームが終われば到達できなくなり、項目ごと取り除かれるからである。
- 状態ワード `ctx.pending` のペイロード(`DISCARD` の値、`YIELD` と `DISCARD(NeverBody)` の引数の配列。`ERROR` はワードを持たない)と、ハンドラの連鎖 `ctx.handlers` もルートである。
- 継続の中のフレームのコピーは、値スタックの生存しているフレームと同じ規則で走査する。
  フレームヘッダの 0 番のワードの再開点(`PHASE` フラグと `YIELDED` フラグを除いた番号)の集合を使う。
  `YIELDED` フラグがあれば `perform` のオペランドを、`PHASE` フラグがあれば呼び出しの命令のオペランドを加える。
  `$rt_handle` のフレームのコピーは、0 番のスロットもルートにする。
  コピーの `any` の領域の全体を走査してはならない。
  フレームを置くときにスロットを消さず、`cont_make` もフレームをそのままコピーするので、集合に入らないスロットには死んだ値やまだ書いていない値が残っていることがある。

`keleut-lir` の生存解析は、ブロックを逆トポロジカル順にたどり、1 つの集合を書き換えながら進む。
集合を変えるたびに、変えたレジスタを変更ログに追記し、ブロックの入口の集合は変更ログの長さとして保存する。
入口の集合を使うときは、それより後の変更ログをたどって、現在の集合との違いを求める。
したがって、近くで使う入口の集合では、処理時間は変わったレジスタの個数に比例する。
変更ログが長く伸びてから使う入口の集合(長い節の後に置いた節の入口など)は、途中でコピーを作って保持する。
そうしたブロックでは、処理時間が集合の幅(レジスタの個数の 64 分の 1 のワード数)に比例する。
後続ブロックを持たない小さなブロック(エラーで終わるブロックなど)は、この集合を使わずに処理する。
検証器が行う定義の検査(前向きの解析)も、同じ仕組みで出口の集合を保持する。

集合は、値を保持したまま確保や呼び出しを重ねる関数(長いリストのリテラルなど)で大きくなる。
点ごとに集合の全体を持つと、サイズの合計が点の個数と生存している値の個数の積になる。
そこで `keleut-lir` は、各点の集合を、位置の順で次の点の集合からの差分として持つ。
差分を積み重ねた量がその点の集合のサイズを超えた点では、集合の全体を持つ(型 `Points`)。
保持する量の合計は差分の量の合計の 2 倍を超えず、1 つの点の集合を作り直す処理時間はその集合のサイズに比例する。
`keleut dump lir` の出力は各点の集合の全体を書くので、そうした関数では出力が長くなる。

### 1.9 生存区間

関数の命令に通し番号を振る。
引数は 0 とし、ブロックをトポロジカル順に並べて、各ブロックの命令と終端命令に 1 から順に振る。
レジスタの**生存区間**は、最初に書く位置から最後に読む位置までである。
ブロックはトポロジカル順に並ぶので、ある経路でレジスタが生存している位置は必ずこの生存区間に入る。
したがって、生存区間の重ならない 2 つのレジスタが同時に生存することはない。

## 3. 定数と移動

### `const`

`r = const c` は、定数 `c` をレジスタ `r` に置く。

- オペランド:定数は `unit`、`bool b`、`i32 n`、`i64 n`、`f64 0xHHHHHHHHHHHHHHHH`(ビット列)、`str "…"`(文字列表の添字)、`ctor0 T C`(引数のないコンストラクタ)、`dict_builtin C T`(組み込みのインスタンスの辞書)、`dict_inst0 I`(前提を持たないユーザのインスタンスの辞書)である。
- Rep:`r` の Rep は定数の Rep(`unit`、`ctor0`、`dict_builtin`、`dict_inst0` は `any`)である。
- 前提:`dict_builtin C T` の組 `(C, T)` は組み込みのメソッドの表にある(検証器が検査する)。
- 生成するパス:3(リテラル)、2(リテラルのパターン)、5(辞書)、7(検査の定数)。
- trap しない条件:常に成り立つ。
  `str` の定数はメモリを確保しない。

### `move`

`r = move s` は、`s` の値を `r` にコピーする。
`r` と `s` は同じ Rep である。
生成するパスは 3(合流のブロックへ分岐する前に、各分岐が合流のレジスタに書く)と 5(`Show[String]` は文字列そのものを返す)である。
trap しない。

## 4. ボックスと環境

### `box`

`r = box s` は、ボックス化していない値 `s`(Rep は `any` 以外)を一様表現の値 `r` にする。

- 生成するパス:4。
  関数の引数、返り値、データとレコードのフィールド、キャプチャ、グローバルに置く値は一様表現の値なので、ボックス化していない値をそこへ渡すときに置く。
- trap しない条件:ネイティブの表現では、`i64` と `f64` のボックス化はメモリを確保する。
  確保の失敗はメモリ不足である(1.7 節)。
  `bool`、`i32`、`str` は確保しない。

### `unbox`

`r = unbox s` は、一様表現の値 `s` から、`r` の Rep の値を取り出す。

- 生成するパス:4。
  関数の入口の引数、`env_get` の結果、グローバルの値、フィールドの値を `any` 以外の Rep のスロットに置くときと、プリミティブに渡すときに置く。
- 前提:`s` は、`r` の Rep の値を `box` したものである(`str` なら文字列)。
- trap しない条件:前提が成り立てば、常に成り立つ。

### `env_get`

`r = env_get i` は、現在の関数を呼んだクロージャの `i` 番目のキャプチャを、一様表現の値として読む。

- オペランド:`i` は関数のキャプチャの個数より小さい。
- 置く位置:入口のブロックの先頭にある `depth_enter` の直後に、使うキャプチャごとに 1 つずつ置く(検証器が検査する)。
  この位置より前には呼び出しも確保もないので、フレームは `env_get` のためにクロージャを保持し続けなくてよい(1.8 節)。
- 生成するパス:1。
  KIR の `env`、辞書の `env`、キャプチャの並びの `env` は、入口で読んだレジスタを使う。
  キャプチャは一様表現の値で持つので、KIR のキャプチャの Rep が `any` 以外なら、使う箇所に `unbox` を置く。
- trap しない条件:常に成り立つ(添字は検証器が検査する)。

## 5. 深さ

### `depth_enter`

関数の入口の先頭に 1 つだけ置き、`ctx.depth` をこのフレームの深さとして記録する。
生成するパスは 10 である。
trap しない。

### `depth_check`

呼び出し先の深さ `ctx.depth + 1` を上限と比較し、超えていれば `depth_limit` の実行時エラーにする。
`ctx.depth` は変えない。

- 生成するパス:10。
  ユーザのコードを呼ばずに終わる非末尾呼び出しの位置に置く。
  該当するのは、`dbuiltin` の辞書の `opcall` とメソッドの呼び出し(パス 5 がプリミティブにしたもの)、`extern` のプリミティブの直接呼び出し、組み込みの値(`Ref.new` など)の直接呼び出し、`extern` のグローバルへの `dictapp` である。
  IRSpec 11.2 節は、これらも非末尾呼び出しとして数える。
  実装のないプリミティブの非末尾呼び出しでは、`error` の前に置く(Diktor と同じく、深さの検査が先である)。
- trap しない条件:失敗は `depth_limit` の実行時エラーで、trap ではない。

### `depth_push`

`depth_check` と同じ検査を行い、通れば `ctx.depth` を 1 増やす。
生成するパスは 10 で、ユーザのコードを呼ぶことがある非末尾呼び出し(`call_direct`、`call_value`、`call_method`、`dict_app`)の直前に置く。

### `depth_restore`

`ctx.depth` をこのフレームの深さ(`depth_enter` が記録した値)に書き戻す。
生成するパスは 10 で、`depth_push` に対応する呼び出しの直後に置く。
呼び出し先が番兵を返して戻ったときも、バックエンドは呼び出し元に戻る時点で `ctx.depth` を呼び出し元のフレームの深さに書き戻す(16.1 節)。
trap しない。

## 6. 整数、浮動小数点数、真偽値

### `iN.add`、`iN.sub`、`iN.mul`、`iN.div`、`iN.rem`

`r = i32.add a b` などは、`a` と `b`(Rep は `i32` か `i64`)の二項演算である。
`N` は 32 か 64 である。

- 意味:`add`、`sub`、`mul` は、オーバーフローすると 2 の補数で折り返す(下位のビットだけが残る)。
  `div` は 0 へ切り捨てる商、`rem` はその剰余(符号は被除数と同じ)である。
  `div` と `rem` は全域で、除数が 0 なら 0、`MIN / -1` は `MIN`、`MIN % -1` は 0 である。
- 生成するパス:5(`Add`、`Sub`、`Mul`、`Div`、`Rem` の組み込みのメソッドと、同名のプリミティブ)。
  パス 7 は、`div` と `rem` の前に除数の検査(`iN.eq` と `branch`、`error 10`)を置く。
  また、`__string_sub` の範囲の検査で `i32.sub`(長さ - `len`)を使う。
  `Array.each` の内側のループの関数(12 節)は、添字を進める `i32.add` を使う。
- trap しない条件:どの入力にも結果を定めている。
  LLVM バックエンドは `nsw` を付けず、`sdiv` と `srem` の前に除数と `MIN / -1` の分岐を置く。
  WasmGC バックエンドは、`div_s` と `rem_s` を、trap することがある命令を置いてよい補助関数(`safe.*`)の中に置く。

### `iN.neg`

`r = i32.neg a` は、折り返す符号反転である(`-MIN` は `MIN`)。
生成するパスは 5 である。
trap しない。

### `iN.eq`、`iN.lt`、`iN.le`、`iN.gt`、`iN.ge`

`r = i32.lt a b` などは、符号付きの比較で、結果は `bool` である。
生成するパスは 5(`Eq`、`Ord` のメソッド)、2(リテラルのパターン、コンストラクタとヴァリアントの番号)、7(検査)である。
trap しない。

### `f64.add`、`f64.sub`、`f64.mul`、`f64.div`

`r = f64.add a b` などは、IEEE 754 の binary64 の演算(最も近い値へ丸める)である。
0 による除算は無限大か NaN になる。
生成するパスは 5 である。
trap しない。
バックエンドは浮動小数点演算の縮約(fma への融合)をしない。

### `f64.neg`

`r = f64.neg a` は、符号のビットを反転する。
生成するパスは 5 である。
trap しない。

### `f64.eq`、`f64.lt`、`f64.le`、`f64.gt`、`f64.ge`

`r = f64.lt a b` などは、IEEE 754 の比較で、どちらかが NaN なら結果は偽である。
`f64.eq` では `0.0` と `-0.0` は等しい。
生成するパスは 5、2(`Float64` のリテラルのパターン)、7 である。
trap しない。

### `f64.sin`、`f64.cos`、`f64.sqrt`、`f64.exp`、`f64.log`

`r = f64.sin a` などは、`extern "C"` の数学関数である。
`sin`、`cos`、`exp`、`log` は rtcore の `krt_sin` などの結果、`sqrt` は IEEE 754 の平方根である。
生成するパスは 5(`extern "C"` の直接呼び出しと、その本体の関数)である。
trap しない。
バックエンドはこれらを組み込み関数(intrinsic)に置き換えず、定数畳み込みもしない。

### `f64.trunc`

`r = f64.trunc a` は、`a` を 0 へ切り捨てた値である(NaN は NaN、無限大は無限大)。
生成するパスは 7(整数への変換の範囲の検査)である。
trap しない。

### `f64.is_nan`

`r = f64.is_nan a` は、`a` が NaN なら真である。
生成するパスは 7 である。
trap しない。

### `conv.i32_to_i64`、`conv.i32_to_f64`、`conv.i64_to_i32`、`conv.i64_to_f64`、`conv.f64_to_i32`、`conv.f64_to_i64`

`r = conv.OP a` は、数値変換である。

| 命令 | 意味 |
| --- | --- |
| `i32_to_i64` | 符号を拡張する |
| `i32_to_f64` | 正確に変換する |
| `i64_to_i32` | 下位 32 ビットを取る(折り返す) |
| `i64_to_f64` | 最も近い値へ丸める(等距離なら偶数) |
| `f64_to_i32`、`f64_to_i64` | 0 へ切り捨てる。全域で、NaN は 0、範囲外は最小値か最大値に飽和する |

- 生成するパス:5(同名のプリミティブ)。
  パス 7 は、`f64_to_i32` と `f64_to_i64` の前に次の検査を置く。
  `f64.is_nan` で NaN を検出し(NaN なら `error 11`)、`f64.trunc` と `f64.ge`、`f64.lt` で範囲 `-2^31 ≦ trunc(a) < 2^31` を検査する(範囲外なら `error 12`)。
  `i64` の範囲は `-2^63 ≦ trunc(a) < 2^63` である。
  どちらの範囲も上端は開いている。
- trap しない条件:どの入力にも結果を定めている。
  LLVM の `fptosi` は範囲外で poison になるので、バックエンドは検査の後でだけ使うか、飽和する変換を使う。

### `bool.not`

`r = bool.not a` は否定である。
生成するパスは 3(KIR の `not`。`!=` は `not` と `Eq.eq` で表す)、5(`inst_is_init` の検査)、7(`f64_to_i32` と `f64_to_i64` の範囲の検査)、9(初期化の検査)である。
trap しない。

### `bool.eq`

`r = bool.eq a b` は、2 つの真偽値が等しいとき真である。
生成するパスは 5(`Eq[Boolean]`)、2(`bool` のリテラルのパターン)、7 である。
trap しない。

## 7. 文字列

### `str.concat`

`r = str.concat a b` は、2 つのバイト列を連結した新しい文字列である。
生成するパスは 5(`Add[String]`、`__string_concat`)である。
メモリを確保するので、失敗しうる命令である(長さが `N_alloc_max` を超えるときと、ヒープを拡張できないときにメモリ不足になる)。
trap はしない。

### `str.eq`、`str.lt`、`str.le`、`str.gt`、`str.ge`

`r = str.lt a b` などは、バイトを符号なしの値として辞書順に比較する(rtcore の `bytes.c`)。
生成するパスは 5 と 2(`String` のリテラルのパターン)である。
trap しない。

### `str.len`

`r = str.len a` は、バイト数(`i32`)である。
生成するパスは 5(`__string_length`)と 7(`__string_sub` の検査)である。
trap しない。

### `str.sub`

`r = str.sub s pos len` は、`s` の `pos` バイト目から `len` バイトの部分文字列である。

- 意味:全域で、範囲外の部分は切り詰める(`pos` と `len` を `[0, 長さ]` に収めてから取り出す)。
- 生成するパス:5(`__string_sub`)。
  パス 7 が、前に `pos < 0`、`len < 0`、`pos > 長さ - len` の検査(どれかが真なら `error 13`)を置く。
  `0 ≦ len ≦ 長さ < 2^31` なので、`長さ - len` はオーバーフローしない。
- trap しない条件:確保の失敗を除いて、常に成り立つ。

### `show.i32`、`show.i64`、`show.f64`、`show.bool`

`r = show.i32 a` などは、値を文字列にする。
`i32` と `i64` は 10 進表記、`bool` は `true` か `false`、`f64` は LangSpec §16.2 の表記(rtcore の `f64show.c`。NaN は符号とペイロードによらず `nan`)である。
生成するパスは 5(`Show` の組み込みのメソッドと `__show_int32`)である。
メモリを確保するので、失敗しうる命令である。
`Show[String]` は文字列そのものを返すので、この命令ではなく `move` になる。

## 8. データとヴァリアント

### `ctor_new`

`r = ctor_new T C (f…)` は、型 `T` のコンストラクタ `C` の値を作る。
`f…` は、フィールドの位置(宣言)の順に並べた一様表現の値で、個数はコンストラクタの引数の個数に等しく、1 以上である。
引数のないコンストラクタは `const ctor0` にする。

- 生成するパス:3(KIR の `construct`)。
  変換器は、フィールドの式をソースに書いた順に評価してから、位置の順に並べる。
  書かなかったフィールドは Unit にする(Diktor と同じ)。
- trap しない条件:確保の失敗を除いて、常に成り立つ。

### `ctor_tag`

`r = ctor_tag v` は、データ `v` のコンストラクタの番号(`i32`)である。

- 生成するパス:2。
  型のコンストラクタが 2 つ以上あるときだけ、照合の前に置く。
- 前提:`v` は名目的な型の値である。

### `ctor_field`

`r = ctor_field v i` は、データ `v` の `i` 番目のフィールドである。
全域で、`i` がフィールドの個数以上なら Unit を返す。
生成するパスは 2 である。
前提は `ctor_tag` と同じである。

### `variant_new`

`r = variant_new L p` は、ラベル `L` とペイロード `p` のヴァリアントを作る。
ペイロードのないヴァリアントの `p` は Unit である。
生成するパスは 3 である。
メモリを確保するので、失敗しうる命令である。

### `variant_tag`

`r = variant_tag v` は、ヴァリアント `v` のラベルの番号(ラベル表の添字。`i32`)である。
生成するパスは 2 で、照合するラベルの番号と `i32.eq` で比較する。
`v` はヴァリアントでなければならない。

### `variant_payload`

`r = variant_payload v` は、ヴァリアント `v` のペイロードである。
生成するパスは 2 である。
前提は `variant_tag` と同じである。

## 9. レコード

KIR 1.0 は型を持たないので、変換器がシェイプを知ることができるのは、同じ関数の中で `rec_empty` と `rec_extend` の連鎖から作ったレコードと、`closed` のレコードのパターン(タプルのパターン)の照合対象だけである(パス 6)。
`open` のレコードのパターン(既定のレコードのパターン)は、パターンに書かないフィールドを持つレコードにも一致する(IRSpec 8 節)ので、シェイプを決めない。
それ以外のレコードには、実行時にシェイプを調べる命令を使う。

変換器がシェイプを記録するのは、フィールドが `KNOWN_RECORD_FIELDS` 個(64 個)以下のレコードだけである。
シェイプの分かるレコードに対するフィールドの除去、更新、拡張は、レイアウトをコピーした `rec_new` にするので、1 つの箇所の命令のサイズがフィールドの個数に比例する。
シェイプを無制限に記録すると、同じレコードを更新し続ける連鎖や、`let` で束縛したレコードを拡張し続ける連鎖で、LIR のサイズと LIR への変換にかかる時間が、連鎖の長さの 2 乗に比例する。
上限を超えるレコードは、シェイプの分からないレコードと同じように扱い、`rec_extend`、`rec_field`、`rec_restrict`、`rec_update` を使う。
そのため、1 つの箇所がシェイプの分かるレコードからコピーする既存のフィールドは 64 個以下である。
`rec_extend` の連鎖の値はコピーではなく、その個数は KIR のサイズに比例する。
`rec_empty` から作る連鎖は、上限を超えても 1 回の `rec_new` にする。

### `rec_new`

`r = rec_new S (f…)` は、シェイプ `S` のレコードを作る。
`f…` はシェイプの順に並べたフィールドの値で、個数はシェイプの長さに等しく、1 以上である。
空のレコードは `const unit` にする。

- 生成するパス:6。
  `rec_extend` の連鎖の元が `rec_empty` かシェイプの分かるレコードなら、連鎖の値をすべて評価した後で 1 回の `rec_new` にする。
  シェイプの分かるレコードの `rec_restrict` と `rec_update` も、新しいレイアウトの `rec_new` にする。
  シェイプを記録するのは、フィールドが 64 個以下の `rec_new` だけである(本節の冒頭)。
- trap しない条件:確保の失敗を除いて、常に成り立つ。

### `rec_get`

`r = rec_get v i` は、レコード `v` の `i` 番目(シェイプの順)のフィールドである。
全域で、`i` がフィールドの個数以上なら Unit を返す。

- 生成するパス:2、6。
  `closed` のレコードのパターン(タプルのパターン)では、残りのフィールドがないことを型検査が保証するので、パターンのラベルの並びからシェイプを決め、各ラベルのフィールドを位置で読む。
  同じラベルの `j` 番目の項目は、外側から `j` 番目のフィールドである。
  `open` のパターンにはこの命令を使わず、`rec_field` を使う。
- 前提:`v` のシェイプは、変換器が決めたシェイプである。

### `rec_extend`

`r = rec_extend v L x` は、レコード `v` の最も外側にラベル `L` のフィールド `x` を追加した新しいレコードである。
`v` が Unit なら、フィールドが 1 つのレコードになる。
生成するパスは 6 である。
シェイプの分からないレコードを元にする `rec_extend` の連鎖に使い、内側から順に追加する。
メモリを確保するので、失敗しうる命令である。
実行時には、rtcore の `shape.c` が新しいシェイプを求める。

### `rec_field`

`r = rec_field v L n` は、レコード `v` のラベル `L` のフィールドのうち、外側から `n` 番目(0 始まり)のものである。
全域で、そのフィールドがなければ Unit を返す。
生成するパスは 6(シェイプの分からないレコードの `rec_select`。`n` は 0)と 2(`open` と `rest` のレコードのパターン)である。
`open` のパターンでは、パターンに書いたラベルがあることを型検査が保証するので、前に `rec_has` を置かない。
照合対象がシェイプの分かるレコードなら、どちらのパターンでもこの命令を使わず、フィールドの値のレジスタをそのまま使う。
`v` はレコードか Unit でなければならない。

### `rec_has`

`r = rec_has v L n` は、レコード `v` のラベル `L` のフィールドのうち、外側から `n` 番目(0 始まり)のものがあれば真である。
生成するパスは 2(`rest` のレコードのパターン)である。
IRSpec 8 節のとおり、パターンのラベルを持たないレコードとの照合は失敗する。
trap しない。

### `rec_restrict`

`r = rec_restrict v L` は、レコード `v` から、ラベル `L` のフィールドのうち最も外側の 1 つを取り除いた新しいレコードである。
全域で、`L` がなければ `v` と同じフィールドのレコードを返す。
生成するパスは 6 と 2 である。
パス 6 は、シェイプの分からないレコードと、フィールドが 64 個を超えるレコードの `rec_restrict` に使う。
パス 2 は、`rest` のパターンの残りを作るときに使い、パターンの各ラベルを順に取り除く。
メモリを確保するので、失敗しうる命令である。

### `rec_update`

`r = rec_update v L x` は、レコード `v` のラベル `L` のフィールドのうち最も外側のものを `x` に置き換えた新しいレコードである。
フィールドの位置は変えない。
全域で、`L` がなければ `v` と同じフィールドのレコードを返す。
生成するパスは 6(シェイプの分からないレコードと、フィールドが 64 個を超えるレコードの `rec_update`)である。
KIR の `rec_update` は、レコードを先に、値を後に評価する。
メモリを確保するので、失敗しうる命令である。

## 10. 関数の値と辞書

### `closure_new`

`r = closure_new F (c…)` は、関数 `F`(種類は `lambda` か `dictabs`)とキャプチャ `c…`(一様表現の値)からクロージャを作る。
`c…` の個数は `F` のキャプチャの個数に等しい。
生成するパスは 1(KIR の `closure` と `dictabs`)である。
メモリを確保するので、失敗しうる命令である。

### `closure_set_cap`

`closure_set_cap c i x` は、クロージャ `c` の `i` 番目のキャプチャを `x` にする。

- 生成するパス:1。
  KIR の `letrec` だけが使う。
  変換器は、`letrec` が束縛するクロージャをすべて、キャプチャを Unit にして作ってスロットに置いた後、各クロージャのキャプチャをこの命令で埋める。
  そのため、キャプチャは同じ `letrec` のどのスロットも読める。
- 前提:`c` は同じ `letrec` で作ったばかりのクロージャで、まだほかへ渡していない。
  `i` は、`c` を作った `closure_new` の関数のキャプチャの個数より小さい。
  検証器は、同じブロックの中で `c` に最後に書いた命令が `closure_new` であることと、`i` がその関数のキャプチャの個数より小さいことを検査する。
  変換器は、1 つの `letrec` の命令を 1 つのブロックに置く。
- trap しない条件:前提が成り立てば、常に成り立つ。

### `method_new`

`r = method_new C m d (o…)` は、クラス `C` のメソッド `m` の値を、辞書 `d` とメソッド自身の辞書 `o…` から作る。
作る時点ではインスタンスを選ばない(IRSpec 5.4 節)。
生成するパスは 5(呼び出し先でない位置にある KIR の `method`)である。
メモリを確保するので、失敗しうる命令である。

### `dict_inst`

`r = dict_inst I (p…)` は、ユーザのインスタンス `I` に前提の辞書 `p…` を渡して作る辞書である。
`p…` の個数は `I` の前提の個数に等しく、1 以上である(検証器が検査する)。
前提を持たないインスタンスの辞書は `const dict_inst0 I` にする。
生成するパスは 5 である。
メモリを確保するので、失敗しうる命令である。

### `dict_record`、`dict_variant`

`r = dict_record (L d…)` と `r = dict_variant (L d…)` は、閉じた行の型に対する構造的な `Eq` の辞書である。
項目は、ラベルと、そのフィールドの型の `Eq` の辞書の組である。
項目は KIR の順(ラベル名のバイト列の昇順。同じラベルは外側から)に並ぶ。
比較の方法は 13 節の `call_method` に書く。
生成するパスは 5 である。
メモリを確保するので、失敗しうる命令である。

## 11. グローバルとインスタンス

### `global_get`

`r = global_get g` は、グローバル `g` の値(1.6 節)を一様表現の値として読む。
初期化の検査はしない。
KIR のグローバルの Rep が `any` 以外なら、続けて `unbox` を置く。
生成するパスは 3 である。
trap しない。

### `global_is_init`

`r = global_is_init g` は、グローバル `g` が初期化済みなら真である。
種類が `builtin` のグローバルは、プログラムの開始時に初期化済みである。

- 生成するパス:9。
  グローバルを読む前に、`bool.not`、`branch`、`error 2` とともに置く。
  パス 9 は、読む箇所を含む最も外側のトップレベルの実体の初期化手順がグローバルの初期化手順より後にあるときと、両者が同じ `def_fns` の初期化手順にあるときだけ、この検査を省く(IRSpec 10.3 節)。
  最も外側のトップレベルの実体は、関数の生成箇所を順にたどって着くルート関数で決める。
  ルート関数が決まらない関数(生成箇所が 2 つ以上あるものなど)では省かない。
- trap しない。

### `global_set`

`global_set g x` は、グローバル `g` に一様表現の値 `x` を置く。
初期化関数だけが使い、`def_value` の値と、`def_pattern` の照合が束縛した値を置く。
trap しない。

### `global_mark_init`

`global_mark_init g` は、グローバル `g` を初期化済みにする。
初期化関数だけが使う。
`def_pattern` では、照合が成功した後で、グローバルの並びの順に置く。
trap しない。

### `inst_is_init`

`r = inst_is_init I` は、インスタンス `I` が初期化済みなら真である。
生成するパスは 5 である。
`dinst` の辞書のメソッドの呼び出しで、引数をすべて評価した後(非末尾呼び出しでは `depth_push` の後)に、`error 6` への分岐とともに置く。
trap しない。

### `inst_mark_init`

`inst_mark_init I` は、インスタンス `I` を初期化済みにする。
初期化関数が、`def_instance` の実装をすべて評価した後に置く。
trap しない。

### `inst_set_value`

`inst_set_value I m x` は、インスタンス `I` のメソッド `m`(クラスの中の位置)の値として `x` を記録する。
初期化関数は、受け取る辞書の個数が 0 である実装の関数を、メソッドを書いた順に評価し、それぞれの評価の直後にこの命令を置く(IRSpec 10.1 節)。
trap しない。

### `inst_get_value`

`r = inst_get_value I m` は、`inst_set_value` が記録した値である。
生成するパスは 5 で、実装の関数が受け取る辞書の個数が 0 であるメソッドの呼び出しに使う。
`I` は初期化済みでなければならない(`inst_is_init` の検査の後でだけ使う)。
検証器は、`inst_get_value` と `inst_set_value` が指定するメソッド `m` について、実装の関数が辞書を受け取らないことを検査する。

## 12. 組み込みの値

本節の命令は、組み込みの値の本体の関数と、組み込みの値のグローバルを直接呼ぶ箇所(`call` の呼び出し先が `global "builtin/…"` であるもの)で使う。
直接呼ぶ箇所が非末尾呼び出しなら、前に `depth_check` を置く。
組み込みの値は、呼び出し先の深さで実行するからである(IRSpec 付録 A.4)。
添字と長さは一様表現の値で受け取り、`unbox` で `i32` にする。

### `ref_new`、`ref_get`、`ref_set`

`r = ref_new x` は、値 `x` を持つ新しい `Ref` を作る(メモリを確保する)。
`r = ref_get c` は `Ref` である `c` の値を読み、`ref_set c x` は `c` の値を `x` にする。
`Ref.set` の結果の Unit は `const unit` で作る。
`c` は `Ref` でなければならない。

### `array_len`、`marray_len`

`r = array_len a` と `r = marray_len a` は、配列の長さ(`i32`)である。
`a` は、それぞれ `Array`、`MutableArray` でなければならない。

### `array_get`、`marray_get`

`r = array_get a i` と `r = marray_get a i` は、配列の `i` 番目の要素である。
全域で、範囲外なら Unit を返す。
変換器は、前に `i < 0` と `i ≧ 長さ` の検査(どちらかが真なら `error 15`)を置く。

### `marray_set`

`marray_set a i x` は、可変配列の `i` 番目の要素を `x` にする。
全域で、範囲外なら何もしない。
変換器は、`marray_get` と同じ検査を前に置く。

### `marray_new`

`r = marray_new n x` は、すべての要素が `x` である長さ `n` の可変配列を作る。
全域で、負の長さは 0 とみなす。
変換器は、前に `n < 0` の検査(`error 16`)を置く。
長さが `N_alloc_max` を超えるときと、ヒープを拡張できないときは、メモリ不足(19 番)になる。

### `marray_freeze`

`r = marray_freeze a` は、可変配列をコピーした `Array` を作る。
メモリを確保するので、失敗しうる命令である。

`Array.each` と `pinned` はユーザの関数を呼ぶので、命令にせず、LIR の関数として本体を書く。
`pinned(f)` の本体は `depth_push`、`call_value f ()`、`depth_restore`、`return` である。
`Array.each(a, f)` の本体は、内側のループの関数 `(a, f, i)` を末尾呼び出しで呼ぶ。
ループの関数は、`i ≧ 長さ` なら Unit を返す。
そうでなければ、要素を `call_value` で `f` に渡し(`depth_push` と `depth_restore` で囲む)、`i + 1` を渡して自分を末尾呼び出しで呼ぶ。
こうすると、ユーザの関数は組み込みの値の深さ + 1 で実行される(IRSpec 付録 A.4)。

## 13. 呼び出し

呼び出しの引数と結果は、どれも一様表現の値である。
命令に付く `yield` か `noyield` の印は、KIR の印をそのまま引き継いだもので、パス 11 が再開点の印を決めるときに使う(17 節)。
呼び出し先が番兵を返して戻ったら、呼び出しの命令は、呼び出し元のフレームからも番兵を返して戻る(16.1 節の伝播)。
`opcall` から作るメソッドの呼び出しは、KIR に印がないので `yield` にする。

### `call_direct`

`r = call_direct y F (a…)` は、キャプチャを持たない関数 `F` を、環境なしに非末尾呼び出しで呼ぶ。
引数の個数は `F` の引数の個数に等しい。

- 生成するパス:3、5、初期化関数。
  パス 3 は、呼び出し先が種類 `fn` のグローバルである `call` と、組み込みの値 `Array.each` と `pinned` の直接呼び出しに使う。
  パス 5 は、適用する値が種類 `dictabs` のグローバルである `dictapp` に使い、辞書を引数として渡す。
  初期化関数は、`thunk` と実装の関数の評価に使う。
- 深さ:命令は深さを変えない。
  KIR の非末尾呼び出しから作ったものは、`depth_push` と `depth_restore` で囲む。
  初期化関数の呼び出しと、メソッドの呼び出しの中で行う実装の関数の評価は囲まず、`ctx.depth` を変えずに呼ぶ(1.4 節)。
  ハンドラ式と、末尾位置にない `resume` から `$rt_handle` を呼ぶもの(16.3 節)も囲まない。
  ハンドラのフレームは、ハンドラ式の位置の深さ `h`、または `resume` の位置の深さ `c` で実行されるからである。
- 失敗しうる命令である。

### `call_value`

`r = call_value y f (a…)` は、値 `f` に引数 `a…` を渡して、非末尾呼び出しで呼ぶ。

| `f` の値 | 動作 |
| --- | --- |
| 種類 `lambda` の関数のクロージャ | クロージャを環境として関数を呼ぶ |
| 本体の関数を持つグローバルの値(1.6 節) | 本体の関数を呼ぶ |
| 実装名のない `extern` の値 | 実行時エラー 17 か 18 になる |
| メソッドの値 | `call_method` と同じ方法でメソッドを選んで呼ぶ |

- 生成するパス:3(`call_direct` にも、メソッドの呼び出し、プリミティブ、組み込みの値の命令、`error` にも変換しない `call`)、5(`dinst` の辞書のメソッドの呼び出しで、選んだ値を呼ぶもの)。
- 前提:`f` は上の表のどれかで、引数の個数が関数の引数の個数に等しい。
- ルート:`f` がメソッドの値のとき、実装の関数を評価する間は、呼び出し元のフレームの再開点に `PHASE` フラグが付き、`f` と `a…` のスロットがルートになる(1.8 節)。
- 失敗しうる命令である。

### `call_method`

`r = call_method y C m d (o…) (a…)` は、辞書 `d` からクラス `C` のメソッド `m` を選び、引数 `a…` を渡して非末尾呼び出しで呼ぶ。
メソッドを選ぶのは、引数をすべて評価した後である(IRSpec 5.4 節)。

| `d` の値 | 動作 |
| --- | --- |
| ユーザのインスタンス `I`(前提 `p…`) | `I` が初期化の前なら実行時エラー 6 になる。そうでなければ、メソッドの値を求めて `a…` で呼ぶ |
| 組み込みのインスタンス `(C', T)` | 組み込みのメソッドの表から `(C', T, m)` の本体の関数を求めて呼ぶ |
| `dict_record` | `C` は `Eq` である。両辺のレコードを項目ごとに比較する |
| `dict_variant` | `C` は `Eq` である。両辺のラベルが等しく、そのラベルの項目の辞書の `eq` でペイロードが等しいときに真になる |

ユーザのインスタンスのメソッドの値は、実装の関数が受け取る辞書の個数が 0 なら `inst_get_value` の値で、そうでなければ実装の関数を辞書 `p… ++ o…` で評価した値である。
実装の関数の評価も、メソッドの値の呼び出しも、この `call_method` の呼び出し先の深さで行う。

`dict_record` の比較は、項目を順に処理する。
項目ごとに、両辺からそのラベルの最も外側のフィールドを取り出し、項目の辞書の `eq` を非末尾呼び出しで呼んで比較する。
`eq` は深さ + 1 で呼び、`depth_push` と同じ検査と、戻った後の深さの書き戻しを行う。
結果が偽なら、その時点で偽を返し、残りの辞書を呼ばない。
すべて真で、両辺に残りのフィールドがなければ、真を返す。
`dict_variant` の比較で `eq` を呼ぶ深さは、`dict_record` と同じである。

- 生成するパス:5。
  辞書が、辞書の引数、キャプチャ、構造的な辞書のどれかのときに使う。
  `dbuiltin` の辞書ではプリミティブの命令に変換し、`dinst` の辞書では `inst_is_init`、`inst_get_value`(または実装の関数の `call_direct`)、`call_value` に変換する。
- 深さ:`depth_push` と `depth_restore` で囲む。
- ルート:再開点の集合は `d`、`o…`、`a…` を含まない。
  ユーザのインスタンスの実装の関数を評価する間は、呼び出し元のフレームの再開点に `PHASE` フラグが付き、これらのスロットがルートになる。
  構造的な `Eq` の比較の間は、ランタイム関数が両辺と辞書を `Root` で保持する(1.8 節)。
- 失敗しうる命令である。
  構造的な `Eq` の比較は、LIR の関数にせず、ランタイム関数が行う。
  ランタイム関数は、ユーザのインスタンスの `eq` を、入れ子にしたインタプリタで呼ぶ。
  `Eq` のメソッドの型はエフェクト行を持たないので、`eq` の中で起こした操作は、その中のハンドラが処理する。
  入れ子の境界は、`DISCARD` と `ERROR` を外へ通す。
  境界の外へ `YIELD` が届いたら、内部エラーとして終了コード 70 で終了する。

### `dict_app`

`r = dict_app f (d…)` は、値 `f` に辞書の並び `d…` を渡す(IRSpec 7.5 節)。

| `f` の値 | 結果 |
| --- | --- |
| 種類 `dictabs` の関数のクロージャ | 辞書を引数、クロージャを環境として関数を呼んだ値 |
| `extern` の値 | `f` そのもの(辞書は捨てる) |

- 生成するパス:3(適用する値がグローバルでない `dictapp`)。
  適用する値が種類 `dictabs` のグローバルなら `call_direct` に、`extern` のグローバルなら `depth_check` と `global_get` に変換する。
- 深さ:`dictapp` は末尾呼び出しにならないので、常に `depth_push` と `depth_restore` で囲む。
- 失敗しうる命令である。

### `console_write`

`r = console_write s` は、文字列 `s` を標準出力のバッファに追記し、`r` を Unit にする。
バッファのサイズ、flush のタイミング、書き込みに失敗したときの扱いは、crate `keleut-rt` の `out.rs` の冒頭に書いてある。
書き込みの失敗は出力エラー(終了コード 74)である。

- 前提:プレリュードが `Console.write` の返り値の型を Unit と宣言している。
  KIR はこの型を持たないので、変換器も検証器も検査しない。
  `--prelude` で別の型を宣言したプログラムでは、`r` を読む命令の前提が破られることがある(1.3 節)。
- 生成するパス:3。
  エフェクトの表で `runtime` の印の付いた操作(プレリュードの `Console.write`)の `perform` を、この命令に変換する。
  エフェクトの名前では判断しない。
  `--no-prelude` のプログラムは、自分の `Console` を宣言できるからである。
- 深さ:深さを変えず、上限の検査もしない(IRSpec 11.2 節)。
- 失敗しうる命令である。

## 14. 終端命令

### `jump`

`jump b` は、ブロック `b` へ分岐する。
`b` の番号は、現在のブロックの番号より大きい。
trap しない。

### `branch`

`branch c b1 b2` は、`c`(`bool`)が真なら `b1` へ、偽なら `b2` へ分岐する。
どちらの番号も、現在のブロックの番号より大きい。
trap しない。

### `return`

`return x` は、一様表現の値 `x` を関数の返り値として返す。
trap しない。

### `tail_call_direct`

`tail_call_direct y F (a…)` は、`call_direct` と同じ呼び出し先を末尾呼び出しで呼ぶ。
フレームを再利用し、深さを変えない。
LLVM バックエンドは `musttail` の呼び出しに、WasmGC バックエンドは `return_call` に変換し、インタプリタはフレームを再利用する。
生成するパスは 3(末尾の印の付いた `call`)である。
`Array.each` の本体とループの関数にも使う。

### `tail_call_value`

`tail_call_value y f (a…)` は、`call_value` と同じ呼び出し先を末尾呼び出しで呼ぶ。
`f` がメソッドの値なら、実装の関数を評価する間は呼び出し元のフレームを残して `f` と `a…` のスロットをルートにし、評価が戻ってからフレームを再利用する(1.8 節)。
生成するパスは 3 と 5(`dinst` の辞書のメソッドの末尾呼び出し)である。

### `tail_call_method`

`tail_call_method y C m d (o…) (a…)` は、`call_method` と同じ方法でメソッドを選び、末尾呼び出しで呼ぶ。
ユーザのインスタンスの実装の関数は、末尾呼び出しの呼び出し先の深さ(呼び出し元と同じ深さ)で評価する。
この評価の間は呼び出し元のフレームを残して `d`、`o…`、`a…` のスロットをルートにし、評価が戻ってからフレームを再利用する(1.8 節)。
生成するパスは 5 である。

### `error`

`error N [operand]` は、IRSpec 付録 B の `N` 番の実行時エラーを起こす。
メッセージに必要な情報は、命令が持つか、オペランドで渡す。

| 番号 | 起こす場面 | 命令が持つもの、オペランド | 生成するパス |
| --- | --- | --- | --- |
| 1 | `hole` | | 3 |
| 2 | 初期化の前のグローバルを読んだ | グローバル(表示名はグローバルの表の `display`) | 9 |
| 3 | `letpat` と `def_pattern` の照合の失敗 | 照合した値(`any`) | 2 |
| 4 | `match` のどの節にも一致しない | 照合した値(`any`) | 2 |
| 5 | 範囲外の数値リテラル | リテラルの表記 | 3 |
| 6 | 初期化の前のインスタンスからメソッドを選んだ | インスタンス(`<C>[<T>]` はインスタンスの表の `display`) | 5 |
| 10 | 整数のゼロ除算 | | 7 |
| 11 | NaN を整数に変換しようとした | 変換(実装名) | 7 |
| 12 | 変換の結果が範囲外 | 変換(実装名)、元の値(`f64`) | 7 |
| 13 | `__string_sub` の範囲外 | | 7 |
| 14 | `__panic` | メッセージ(`str`) | 5 |
| 15 | 配列の範囲外 | | 7 |
| 16 | `MutableArray.new` の負の長さ | | 7 |
| 17、18 | 実装のないプリミティブを呼んだ | `extern` のグローバル(表示名と実装名が等しければ 17、違えば 18) | 3 |
| 19 | メモリ不足 | | メモリを確保する命令が起こす。`error 19` は書けず、検証器が拒否する |

17 と 18 は、LIR では同じ種類の `error` で表し、グローバルの表の `display` と実装名から番号を決める(`Program::error_number`)。
LIR をテキストに出力するときも、この番号を書く。

範囲外の数値リテラル(5 番)の `error` は、評価順のとおりの位置に置き、定数畳み込みの対象にしたり、前へ動かしたり、消したりしない(IRSpec 10.4 節)。
実行時エラーを起こした後の扱いは 1.7 節のとおりである。
実行時エラーは trap ではない。

### `unimplemented`

`unimplemented "…"` は、未実装の機能に実行が達したことを表す。
実行時には、標準出力を flush し、標準エラーに `keleut: 未実装: …` を書いて、終了コード 4 で終了する。

- 生成するパス:変換器。
  本体の関数を作れない組み込みの値(`"組み込みの値 …"`)と、変換器の内部エラー(`"内部の誤り: …"`)に置く。
- trap しない。

## 15. 未実装の機能

### `unimplemented_value`

`r = unimplemented_value "…"` は、未実装の機能に実行が達したことを表す命令である。
実行時の動作は `unimplemented` と同じで、標準出力を flush し、標準エラーに `keleut: 未実装: …` を書いて、終了コード 4 で終了する。
`r`(`any`)は、後に続く命令を変換できるようにするための値で、実行時に書かれることはない。

- 生成するパス:現在の変換器は生成しない。
  `handle`、ユーザの操作の `perform`、`resume` は、パス 8 がエフェクトの命令(16 節)に変換する。
  バックエンドは、LIR への変換がまだない機能のプレースホルダとして、この命令を残している。
- 呼び出しでも確保でもないので、再開点にも安全点にもならない。
- trap しない。

## 16. エフェクト(パス 8)

本節は、`handle`、ユーザの操作の `perform`、`resume` の LIR への変換と、変換で生成する命令の意味を定める。
これらの命令は、IRSpec 9 節と 11 節の動作を実装する。
ハンドラ式を実行する手順 `rt_handle`、継続を再開する手順 `rt_resume`、防壁は、すべてのバックエンドが共有する 1 つの LIR の関数 `$rt_handle` の本体である(16.3 節)。
バックエンドによって違うのは、番兵を返して戻ったフレームの扱い(16.1 節)と、継続がフレームを持つ形式(16.4 節)だけである。

### 16.1 状態ワード、番兵、伝播

ランタイムは次のものを持つ。

| 名前 | 内容 |
| --- | --- |
| ハンドラ記録 `hr` | ハンドラの起動ごとの 64 ビットの番号、エフェクト、操作節の表(書いた順に並べた操作、分類、節の関数の値)、本体の関数の値、本体に渡す継続、`return` 節と `cancel` 節(省略できる)、親、深さ `h` |
| 連鎖 `ctx.handlers` | 有効なハンドラ記録の単方向の連鎖(最も内側が先頭) |
| 状態ワード `ctx.pending` | `NONE`、`YIELD(hr, 節, 引数, 切り取りの先頭)`、`DISCARD(hr, Value v)`、`DISCARD(hr, NeverBody(節, 引数))`、`ERROR(種類, 文面)` |
| 継続 `k` | フレームのコピーの並び、継続をキャプチャしたハンドラ記録、連鎖の切り出した部分の先頭、選んだ G の節と引数、`Δ`、`used`、`alive` |

`YIELD` の `切り取りの先頭` は連鎖の切り出した部分の先頭、`ERROR` の `文面` はエラーメッセージである。
`ERROR` の種類は、実行時エラー、`depth_limit`、メモリ不足、出力エラー、どのハンドラも処理しない操作である。
状態ワードは、ほかに 3 種類の**目印**を持つ。
`clause_matched`、`clause_value`、`tail_resume` の目印で、操作節の関数とその呼び出し元(`perform` のフレームか `$rt_handle` のフレーム)の間だけで使う(16.6 節)。

**番兵**は返り値の位置に置くワードで、状態ワードが設定されていることを表す(ネイティブの表現では `0x2`)。
番兵は値ではない。
レジスタに番兵が入るのは、`$rt_handle` の中にある、番兵を受け取る呼び出しの結果だけである。

**伝播**:非末尾呼び出しの呼び出し先が番兵を返して戻ったら、呼び出し元は、呼び出しの種類に応じて次のように動作する。

| 呼び出し | 動作 |
| --- | --- |
| 通常の呼び出し(`call_direct`、`call_value`、`call_method`、`dict_app`) | 自分も番兵を返して戻る。`YIELD` なら自分のフレームを値スタックに残して継続に含め(再開点は呼び出しの前にフレームヘッダに書いてある)、それ以外ならフレームを捨てる |
| 番兵を受け取る呼び出し(`call_body`、`cont_resume`、`call_clause`、`call_cancel`) | 結果のレジスタに番兵を書いて、次の命令へ進む |
| `perform` | 節の選択の結果に応じて状態ワードを設定する(16.5 節) |

どの場合も、呼び出し元に戻るときに `ctx.depth` を呼び出し元のフレームの深さに書き戻す。
失敗しうる命令(1.7 節)が失敗したときは、状態ワードに `ERROR` を設定し、そのフレームから番兵を返して戻る。
`propagate`(16.6 節)も、状態ワードを変えずに、フレームから番兵を返して戻る。

パス 11 が `YIELD` を受け取らないと判定した再開点(17 節)で待っているフレームに `YIELD` が届いたら、`may_yield` の印が誤っている。
このとき、バックエンドは内部エラーとして終了コード 70 で終了する。

構造的な `Eq` の比較(13 節の `call_method`)では、ランタイム関数がバックエンドを入れ子に呼ぶ。
この境界は、`DISCARD` と `ERROR` を呼び出し元のフレームへ通す。
境界の外へ `YIELD` が届いたら、内部エラーとして終了コード 70 で終了する。
`Eq` のメソッドの型はエフェクト行を持たないので、型検査を済ませたプログラムでは起きない。

### 16.2 ハンドラ式、`perform`、`resume` の LIR への変換

**ハンドラ式**:`(handle tail|ntail E body ops… ret cancel)` では、本体、各操作節、`return` 節、`cancel` 節の関数の値を `closure_new` で作り、次の命令に変換する。

```
hr = handler_new E [(op class)…] [ret] [cancel] (body res clause… [ret] [cancel])
r  = call_direct yield $rt_handle (hr unit unit)        ; 末尾の handle なら tail_call_direct
```

`res` は、本体に渡す継続である。
ハンドラ式を書いた関数が G の節の関数かハンドラ式の本体の関数なら、その関数の継続のレジスタで、そうでなければ Unit である。
`$rt_handle` を呼ぶ `call_direct` は `depth_push` で囲まない(13 節)。

**`perform`**:ユーザの操作の `(perform E op a…)` は、引数を評価した後、次の命令に変換する。

```
hr    = handler_find E op
saved = handlers_get
r     = perform E op (hr saved a…)
```

`runtime` の印の付いた操作は `console_write` に変換する(13 節)。

**`resume`**:`(resume tail|ntail e)` は、`e` を評価して一様表現の値 `v` にした後、次の命令に変換する。

| 位置 | 命令 |
| --- | --- |
| T の節の背骨の上にある末尾 `resume` | `return v` |
| G の節の背骨の上にある末尾 `resume` | `tail_resume (v)` |
| 末尾位置にない `resume`(G の節の本体と、その中のハンドラ式の本体) | `cont_check ntail (k)`、`h = cont_hr (k)`、`r = call_direct yield $rt_handle (h k v)` |

背骨は、操作節の本体から末尾位置だけをたどった経路である(IRSpec 5.3 節)。
`k` は関数の継続のレジスタである。
末尾位置にない `resume` の `call_direct` も `depth_push` で囲まない。
再開した計算のハンドラのフレームは、`resume` の位置の深さ `c` で実行されるからである(IRSpec 11.4 節)。

**操作節の関数**:種類 `opclause` の関数は、KIR の引数の後ろに暗黙の引数 `x` と `sel`(どちらも `any`)を持つ。

- `sel` が 0 以上なら**選択フェーズ**である。
  `x` はハンドラ記録、`sel` はこの節の候補の番号(ハンドラ記録の操作節の表の中の位置)である。
  関数は引数のパターンを照合し、一致したらガードを評価する。
  一致しないかガードが偽なら、`tail_call_clause` で次の候補を末尾呼び出しで呼ぶ。
  一致して分類が T なら、そのまま本体を実行する。
  分類が N か G なら、`clause_matched (sel)` で戻る。
- `sel` が負なら**本体フェーズ**で、N と G の節だけが使う。
  `x` は、G の節では継続、N の節では Unit である。
  関数は引数のパターンをもう一度照合し、ガードを飛ばして本体を実行する。
  照合は副作用を持たないので、束縛は選択フェーズと同じになる。

本体の末尾の値と末尾 `resume` は、分類に応じて次のように変換する。

| 分類 | 末尾の値 `r` | 末尾 `resume(v)` |
| --- | --- | --- |
| T | `clause_value (r)` | `return v` |
| G | `return r` | `tail_resume (v)` |
| N | `return r`(`handle` が末尾なら末尾呼び出しも使う) | (書けない) |

T と G の節では、本体の最も外側の式が末尾位置にない(IRSpec 5.3 節)ので、本体の中の呼び出しは末尾呼び出しにならない。

**ハンドラ式の本体の関数**:種類 `handlebody` の関数は、暗黙の引数として、引き継ぐ継続 `res` を持つ(Unit のこともある)。
本体の中の末尾位置にない `resume` は、この継続を再開する(IRSpec 9.2 節)。

### 16.3 `$rt_handle`

`$rt_handle(hr, k, v)` は、ハンドラのフレームになる関数である(種類 `handler`)。
ハンドラ式から呼ばれたとき(`k` が Unit)は、`rt_handle` として、ハンドラを連鎖に入れて本体を呼ぶ(手順 1)。
継続を再開するために呼ばれたとき(`k` が継続で、`hr` は `k` のハンドラ記録)は、`rt_resume` として、`k` のフレームを自分のフレームの上に復元する(手順 2)。
どちらの場合も、その後は同じ手順 3〜4 で結果を処理する。
そのため、復元した計算は新しいハンドラのフレームの上で実行され、ハンドラ式の本体と同じ手順で終わる。

本体は次のとおりである(`keleut-lir` の `effect::rt_handle_body`)。
本節の「手順 N」は、次の番号付きの項目を指す。
`r` は本体か復元した計算の結果、`c` は `pending_class` の値である。

1. `is_cont (k)` が偽なら(ハンドラ式から呼ばれた場合)、`depth_check` で本体の深さ `h + 1` を上限と比較し、`handler_install (hr)`、`depth_push`、`r = call_body (hr)`、`depth_restore` を行う。
   上限を超えたら、ハンドラを連鎖に入れる前のエラーなので、`cancel` 節を実行せずに伝播する。
2. 真なら(`rt_resume`)、`cont_check tail (k)`(再開済みなら実行時エラー 7)、`r = cont_resume (k v)`、`depth_restore` を行う。
3. `r` が番兵でなければ、`handler_uninstall (hr)` を行う。
   その後、`return` 節があれば、それを `tail_call_value` で `r` を引数にして呼び、なければ `return r` とする。
4. 番兵なら、`c = pending_class (hr)` で場合を分ける。
   - 自分宛ての `DISCARD(Value v)`(1):`handler_uninstall`、`pending_take` を行い、`pending_value` の値を返す。
     `return` 節も `cancel` 節も実行しない。
   - 自分宛ての `DISCARD(NeverBody)`(2):`handler_uninstall`、`pending_take` の後、`tail_call_never` で N の節の本体を末尾呼び出しで呼ぶ(深さ `h`)。
   - 自分宛ての `YIELD`(3):`handler_uninstall`、`kk = cont_make (hr)`、`g = call_clause (kk)`(G の節の本体を深さ `h + 1` で呼ぶ)、`depth_restore` を行い、`g` で場合を分ける。
     `cont_make` の前にハンドラを連鎖から外すので、継続を作れずにメモリ不足になっても(16.4 節)、無効になったハンドラが連鎖に残らない。
     - 値なら、`cont_kill (kk)` を行う。
       `cont_used (kk)` が真なら `return g` とする。
       偽なら、`pending_discard (hr g)` の値 `p` を注入する値にして、`tail_call_direct $rt_handle (hr kk p)` とする。
       このとき、継続の中の `cancel` 節が内側から順に実行され、連鎖に入り直したハンドラの手順 4 の 1 が `g` を返す。
       LangSpec §13.6 のとおり、節の値が決まった後で計算を破棄する。
     - `tail_resume` の目印なら、`cont_kill` の後、その値 `v` で `tail_call_direct $rt_handle (hr kk v)` とする。
       これは G の節の末尾 `resume` で、スタックは増えない。
     - ほかのハンドラ宛ての `YIELD` なら、`propagate` で自分のフレームも継続に含めて戻る。
       再開されたら、`call_clause` の結果を受け取って続ける。
     - `DISCARD` か `ERROR` なら、節が脱出した(実行時エラーや破棄で節を途中で抜けた)場合である。
       `cont_kill` を行う。
       `cont_used (kk)` が真なら `propagate` とする(`resume` の後の脱出)。
       偽なら、`pending_take` の値 `p` を注入して `tail_call_direct $rt_handle (hr kk p)` とする(`resume` の前の脱出)。
       後者では、継続の中の `cancel` 節、`hr` の `cancel` 節、外側の `cancel` 節の順に実行される。
   - ほかのハンドラ宛ての `YIELD`(4):`propagate`。
   - ほかのハンドラ宛ての `DISCARD` と `ERROR`(5):`handler_uninstall` の後、`cancel` 節があれば防壁(16.4 節)の中で実行し、`propagate` で伝播を続ける。

`cont_resume` の結果と `call_body` の結果は、同じ手順 3〜4 で処理する。
そのため、再開した計算の中で決まった `return` 節の値と、`resume` しない節の値は、ハンドラ式の値ではなく、その `resume` の値になる(LangSpec §13.6)。

### 16.4 継続と防壁

**`cont_make (hr)`**:状態ワードが自分宛ての `YIELD` のとき、`perform` のフレーム(継続の最上段)から呼び出し元を順にたどり、現在のフレームの 1 つ上のフレームまでをコピーする。
コピーする順は最下段から最上段で、各フレームの深さのワードは、`hr` の深さ `h` からの差にする。
`Δ = p − h`(`p` は `perform` のフレームの深さ)、連鎖の切り出した部分の先頭、選んだ節、引数を継続に置き、状態ワードを消す。
コピー領域、表の項目、添字を持つオブジェクトは、状態ワードを消す前に、失敗を呼び出し元に返す方法で確保する。
確保できなければ、まだ値スタックに残っている区間の最上段(`perform` のフレーム)へ制御を移し、メモリ不足の `ERROR` をそこから伝播する。
区間の中にあるハンドラの `cancel` 節は内側から順に実行される。
`hr` のフレームは、本体の呼び出しの再開点で、この `ERROR` をほかのハンドラ宛ての `ERROR` として受け取る。

**`cont_resume (k v)`**:`v` が退避した状態ワードでなければ、現在のフレーム(深さ `c`)の上に、`k` のフレームを最下段から順に配置し直し、すべて置けたら `k` の `used` を立てる。
値スタックを拡張できずに途中で失敗したら、`k` を変えずに、メモリ不足の `ERROR` で失敗する。
このとき `k` は使われていないので、外側の `$rt_handle` は注入の経路で `k` の中の `cancel` 節を実行しようとする。
各フレームの深さのワードは、`c` に差を足した値にする。
3 番のワード(呼び出し元の位置)は、フレームを置いた位置に合わせて書き直す。
置いたフレームのうち `$rt_handle` のフレームについては、そのハンドラ記録の `h` を新しい深さにする(1.8 節)。
次に `k.hr.parent = ctx.handlers`、`k.hr.h = c`、`ctx.handlers = 切り取りの先頭` とする。
ここでの `切り取りの先頭` は、`k` が持つ連鎖の切り出した部分の先頭である。
最後に、最上段の `perform` のフレームへ制御を移し、`v` を `perform` の結果に書いて実行を続ける。
`v` が退避した状態ワードなら、フレームを配置し直さずに注入する。

注入では、フレームを配置し直す代わりに、継続のコピー領域をそのまま 1 つのチャンク(コピーチャンク)として、現在のフレームを含むチャンクの次につなぐ(`ValueStack::link_copy`)。
チャンクの領域を確保しないので、配置し直すためのチャンクを確保できずに通常の `resume` が失敗した後でも、注入は継続の中の `cancel` 節を実行できる。
深さのワード、3 番のワード、`$rt_handle` のハンドラ記録の書き直しは、配置し直す場合と同じである。
コピーチャンクをつないだ後に、最上段の `perform` のフレームへ制御を移し、`v` を状態ワードに設定して、そこから伝播する。
現在のチャンクのうち、現在のフレームの終わりより後ろの部分は使わない。
コピーチャンクのサイズはコピーの長さちょうどで、1 MiB より小さいことがある。
1 MiB 以上のコピーチャンクは既定のサイズのチャンクと同じように扱い、残して再利用する。
それまで次にあったチャンクは、コピーチャンクの次に移して残す。
それまで次にあったチャンクが、前の注入でつないだ 1 MiB より小さいコピーチャンクで、その後ろに 1 MiB 以上のチャンクがあれば、そのコピーチャンクを解放して、後ろのチャンクを移す。
巻き戻しの中で実行する `cancel` 節のフレームがコピーチャンクに入らなければ、`link_copy` がコピーチャンクの次に移したチャンクに置く。
新しいチャンクを確保する(`ValueStack::take_mem`)のは、そのチャンクがないときと、フレームが入らないときだけである。
チャンクの配列を拡張できずに、移したチャンクを捨てたときは、チャンクがないときとして扱う。
通常の `resume` がチャンクを確保できずに失敗した後なら、値スタックの予備チャンクがすでに次に使えるチャンクになっているので、新しいチャンクとして予備チャンクを使う。
1 MiB より小さいコピーチャンクを使い終えた後に、チャンクの境界を越えてフレームを置くときは、コピーチャンクを解放し、後ろの 1 MiB 以上のチャンクを再利用する(`ValueStack::place`)。
コピーチャンクを残して後ろのチャンクを解放すると、注入のたびに、次の境界でチャンクを確保し直すことになるからである。
注入に必要な確保は、つなぐチャンクの配列を拡張する確保だけである。
それを確保できなければ、`k` を変えずに、メモリ不足の `ERROR` で失敗する。

深さを `h` からの差で持つので、IRSpec 11.4 節のずれは、フレームを値スタックに復元するだけで反映される。
`k` の中にある、まだ再開していない継続 `k2` のフレームは、`k2` をキャプチャしたハンドラ記録の `h` からの差で深さを持つ。
そのハンドラ記録は `k` の中で始まったので、`k` を復元するとその `h` がずれる。
そのため、`k2` を再開しても捨てても(注入して復元しても)、`k2` のフレームは、ずれた後の `h` を基準にした深さで置かれる。
復元する前の深さの検査(`c + Δ` と上限の比較)は、末尾位置にない `resume` の `cont_check ntail` が行う(IRSpec 11.3 節)。

LLVM バックエンドとインタプリタは、継続のフレームを、値スタックの区間のコピーとしてこの形式で持つ。

WasmGC バックエンドは、値スタックの区間の代わりにフレームの記録の並びを持ち、手順が次の 4 点で異なる。

- 記録は関数ごとの構造体(`$Frame` の部分型)である。
  関数は記録の再開用エントリから呼ばれ、ローカルを復元して、`br_table` で再開点へ分岐する。
- `rt_resume` は、先に `k` の `used` を立て、`k.hr.parent` と `ctx.handlers` を書き換えてから、記録の並びの最上段から順に、各フレームに入り直す。
- 各フレームの深さは `c + (取り出したときの深さ − h)` にする。
  式の中の「取り出したときの深さ」は、継続をキャプチャしたときの、そのフレームの深さである。
  `k` の中の `$rt_handle` のフレームはハンドラの深さをローカルに持つので、ハンドラ記録の `h` は書き換えない。
- 入り直す途中で `YIELD` が起きたら、まだ入り直していない外側のフレームを `k` に追加しない。
  それらのフレームは番兵を受け取り、自分の記録を作り直す。

詳しくは `crates/keleut-wasm/src/func.rs` の冒頭に書いてある。

**防壁**:16.3 節の手順 4 の 5 では、`cancel` 節を次のように実行する。

1. `p = pending_take` で状態ワードを退避して消し、`l = limit_get` で現在の上限を保存する。
2. `c = call_cancel (f)` で `cancel` 節を深さ `h` で呼び、`depth_restore` を行う。
3. `c` が番兵なら、`pending_class` で場合を分ける。
   ほかのハンドラ宛ての `YIELD` なら、`propagate` で戻る。
   `p` と `l` はフレームのスロットに残るので、再開されたら、この手順 3 から続ける。
   それ以外なら、`pending_suppress` で抑制して記録する。
4. `limit_set (l)`、`pending_restore (p)` の後、`propagate` で元の伝播を続ける。

`cancel` 節が上限を超えて抑制されても、上限は節を実行する前の値に戻る(IRSpec 11.5 節)。

### 16.5 エフェクトの命令

オペランドはどれも `any` で、結果の Rep は表のとおりである。
`hr` はハンドラ記録、`k` は継続、`p` は退避した状態ワードの値である。
これらが値としてユーザのコードに渡ることはない。

| 命令 | 結果 | 意味 |
| --- | --- | --- |
| `handler_new E [(op class)…] [ret] [cancel] (body res clause… ret? cancel?)` | `any` | ハンドラの起動の新しい番号を振ったハンドラ記録を作る。メモリを確保する |
| `handler_find E op` | `any` | 連鎖の中で、エフェクトが `E` である最も内側のハンドラ記録。なければ `ERROR`(メッセージは `未処理のエフェクト操作: E.op`、終了コード 3) |
| `handlers_get` | `any` | 連鎖の先頭(空なら Unit) |
| `perform E op (hr saved a…)` | `any` | 表の後で説明する。再開点を持つ |
| `cont_check ntail\|tail (k)` | なし | `ntail` では、`k` の `alive` フラグが下りていれば(節の外)実行時エラー 8、再開済みなら 7、`c + Δ` が上限を超えれば `depth_limit` になる。`tail` では、再開済みかどうかだけを調べる |
| `is_cont (x)` | `bool` | `x` が継続なら真 |
| `cont_hr (k)` | `any` | `k` のハンドラ記録 |
| `handler_install (hr)` | なし | `hr.parent = ctx.handlers`、`hr.h = このフレームの深さ`、`ctx.handlers = hr` |
| `handler_uninstall (hr)` | なし | `ctx.handlers = hr.parent` |
| `call_body (hr)` | `any` | 本体の関数の値を、引き継ぐ継続を引数にして呼ぶ。番兵を受け取る。再開点を持つ |
| `cont_resume (k v)` | `any` | 16.4 節。番兵を受け取る。再開点を持つ |
| `is_pending (r)` | `bool` | `r` が番兵なら真 |
| `pending_class (hr)` | `i32` | 状態ワードを `hr` から見て分類する。1 は自分宛ての `DISCARD(Value)`、2 は自分宛ての `DISCARD(NeverBody)`、3 は自分宛ての `YIELD`、4 はほかのハンドラ宛ての `YIELD`、5 はほかのハンドラ宛ての `DISCARD` と `ERROR`、6 は `tail_resume` の目印 |
| `pending_take` | `any` | 状態ワードを値にして消す。メモリを確保する |
| `pending_restore (p)` | なし | 状態ワードに `p` を設定する |
| `pending_value (p)` | `any` | `DISCARD(Value v)` か `tail_resume` の目印が持つ `v` |
| `pending_discard (hr v)` | `any` | `DISCARD(hr, Value v)` の値を作る(注入する値)。メモリを確保する |
| `pending_suppress` | なし | 標準出力を flush し、標準エラーに `cancel 節で例外が抑制されました: …` を書いて状態ワードを消す。flush が失敗したら、記録を書かず、巻き戻しもせずに、終了コード 74 で終了する |
| `cont_make (hr)` | `any` | 16.4 節。メモリを確保する |
| `call_clause (k)` | `any` | `k` の G の節を本体フェーズで呼ぶ。深さ `h + 1` を上限と比較し、超えていれば呼ばずに、状態ワードに `ERROR` を設定して番兵を結果に書く(継続をまだ使っていないので、注入の経路に入る)。番兵を受け取る。再開点を持つ |
| `cont_kill (k)` | なし | `k` の `alive` フラグを下ろす。以後、`k` は節の外にある継続として扱う |
| `cont_used (k)` | `bool` | `k` が再開済みなら真 |
| `handler_has (hr) ret\|cancel` | `bool` | その節を持てば真 |
| `handler_get (hr) ret\|cancel` | `any` | その節の関数の値 |
| `call_cancel (f)` | `any` | `f` を、引数なしで、深さを変えずに呼ぶ。番兵を受け取る。再開点を持つ |
| `limit_get` | `i64` | 現在の上限(`depth_limit` の伝播中は `L + R`) |
| `limit_set (l)` | なし | 上限を `l` にする |

`cont_check` のメッセージは IRSpec 付録 B の 7 番と 8 番である。
`pending_suppress` の flush の失敗には、前の失敗の後でバッファに残したデータや、その後に追記したデータを書き出せなかった場合も含む。
どのエラーでバッファにデータを残すかは、IRSpec 9.7 節が定める。
`handler_find`、`perform`、`cont_check`、`cont_resume`、`pending_suppress` と、メモリを確保する命令は、失敗しうる命令である(1.7 節)。
`call_clause` は上限を超えても失敗せず、状態ワードに `ERROR` を設定して番兵を結果に書く。

**`perform E op (hr saved a…)`**:深さ `p` のフレームで、次の順に進む。

1. `p + 1` が上限を超えれば、`depth_limit` の実行時エラーにする(連鎖は変えていない)。
2. `hr` の操作節の表で、操作が `op` である最初の候補を探す。
   なければ実行時エラー 9(`handle のどの節にも一致しません: E.op(a…)`)にする。
3. `ctx.handlers = hr.parent`、`ctx.depth = p + 1` とし、その候補の関数を選択フェーズで、非末尾呼び出しで呼ぶ(引数は `a…`、`hr`、候補の番号)。
4. 戻ったら `ctx.depth = p` とし、結果で場合を分ける。
   - 値 `v`(T の節の末尾 `resume`):`ctx.handlers = saved` とし、`v` を結果にする。
   - `clause_matched (j)` の目印:`ctx.handlers = saved` とする。
     節 `j` が N なら、状態ワードに `DISCARD(hr, NeverBody(j, a…))` を設定し、フレームを捨てて伝播する(ガードは評価済みである)。
     G なら、状態ワードに `YIELD(hr, j, a…, saved)` を設定し、自分のフレームに `YIELDED` フラグを付けて残し、伝播する。
     このフレームが継続の最上段になり、`cont_resume` に渡した値がこの `perform` の結果になる。
   - `clause_value (r)` の目印:`ctx.handlers = saved` とし、状態ワードに `DISCARD(hr, Value r)` を設定して伝播する。
   - ほかのハンドラ宛ての `YIELD`(節の中から外側の G の操作を起こした場合):連鎖を変えず、フレームを残して伝播する。
   - `DISCARD` か `ERROR`:`ctx.handlers = saved` とし、伝播する。

節の選択、ガード、T の節の本体は、連鎖の先頭をハンドラの親に差し替えた、深さ `p + 1` のコンテキストで実行する(IRSpec 9.6 節の 3)。
`DISCARD(hr, NeverBody(節, 引数))` と `YIELD` は、パターンの束縛ではなく、操作の引数を `Array` の値にして持つ。
本体フェーズでパターンを照合し直すので、引数を持てば足りる。

### 16.6 エフェクトの終端命令

| 終端命令 | 意味 |
| --- | --- |
| `propagate` | 状態ワードを変えずに、番兵を返して戻る(16.1 節) |
| `tail_call_never (p)` | `p` は退避した `DISCARD(hr, NeverBody(j, a…))` である。節 `j` の関数を本体フェーズで、末尾呼び出しで呼ぶ(引数は `a…`、Unit、-1) |
| `clause_value (r)` | 状態ワードに `clause_value` の目印を設定し、番兵を返して戻る |
| `clause_matched (sel)` | 状態ワードに `clause_matched` の目印を設定し、番兵を返して戻る |
| `tail_resume (v)` | 状態ワードに `tail_resume` の目印を設定し、番兵を返して戻る |
| `tail_call_clause op (hr sel a…)` | `hr` の操作節の表で、番号が `sel` より大きく、操作が `op` である最初の候補を、選択フェーズで、末尾呼び出しで呼ぶ。なければ実行時エラー 9 になる |

目印は、操作節の関数を呼んだフレームだけが受け取る。
ほかのフレームに届いたら、内部エラーとして終了コード 70 で終了する。

## 17. yield の枝刈り(パス 11)

パス 11 は、各再開点に、`YIELD` を受け取ることがあるかどうかの印を付ける(`Frame::yield_points`)。
非末尾呼び出しの印が `noyield` なら、パス 11 はその再開点を「受け取らない」と判定する。
`yield` の印の付いた呼び出しと、エフェクトの命令のうち `perform` と番兵を受け取る呼び出しは、「受け取る」と判定する。
`dict_app` は KIR に印がないので、「受け取る」と判定する。
`keleut run --no-yield-prune` を指定すると、パス 11 を行わず、すべての再開点を「受け取る」として扱う。

LLVM バックエンドは、受け取らない再開点では、生存しているボックス化していない値をスロットに書かなくてよい。
WasmGC バックエンドは、受け取らない再開点の呼び出しの後に、ローカルをフレームの記録に保存するコードを生成しなくてよい。
インタプリタは、どの再開点からでもフレームの実行を続けられるので、この印でコードを変えない。
その代わりに、受け取らない再開点で待っているフレームに `YIELD` が届いたら、内部エラーとして終了コード 70 で終了する(16.1 節)。
これは `may_yield` の印の誤りを検出する検査である。
印が誤っているプログラムは、`--no-yield-prune` を付けたときと付けないときで結果が異なる。

検証器は、「受け取らない」と判定された再開点の呼び出しの印が `noyield` であることを検査する。
